一、业务背景与痛点

金融研究是一个高度依赖数据但又极度低效的领域。

一个券商研究员写一份行业深度报告的典型工作流：在 Wind/Choice 里翻 30 分钟行情数据，打开年报 PDF 手动摘抄三表数据，用 Excel 算估值指标，再去同花顺看资金流向和北向持仓，最后东拼西凑写成文字。一份 10 页的报告，数据采集和清洗占了 60% 以上的时间，真正的分析和洞察只占一小部分。

更关键的问题是：研究分析的质量完全依赖个人经验。同样是"分析贵州茅台的估值是否合理"，一个资深分析师会交叉验证 PE/PB/DCF 三种方法，对比白酒行业历史估值中枢，再结合北向资金和机构持仓趋势给出判断；而一个新手可能只看 PE 就下结论。这种质量差异无法通过简单的工具解决 —— 它需要将分析方法论固化到系统中。

我们的项目瞄准的就是这个问题：不只是帮研究员查数据，而是构建一个能自主执行完整研究流程的 AI 系统 —— 从数据采集、多维分析到生成可引用的研究报告，并且通过训练闭环持续提升分析质量。

二、项目定位

构建了一个从 AI 金融应用到模型训练的完整闭环系统：首先实现了基于 MCP 协议的金融研究助手（7 大分析能力域、43 个工具 + 6 Agent 深度研究），覆盖 A 股研究中从行情查询、财务分析、资金流追踪到行业对比的全链路场景；然后将其作为 Sandbox 环境，设计了三阶段数据合成流水线（10 万种子 → 30 万条高质量训练数据），最后通过 GRPO 算法训练出金融场景特化的工具调用模型。

三、核心叙事：数据飞轮

大多数 AI 金融产品止步于"帮用户查个数据" —— 本质上是一个自然语言转 SQL 的接口。我们的项目做了一件不同的事 —— 用应用本身来生成训练数据，再用训练出的模型来改进应用。

数据飞轮闭环
1
构建金融 MCP Server（43 个工具，覆盖 A 股全链路）
2
接入 Sandbox，LLM 在其中自主探索金融场景
3
三阶段合成：采样 → 筛选 → QA 生成（10 万 seed → 30 万条高质量数据）
4
GRPO 训练（Rule + LLM 混合奖励，Sandbox 重放验证）
5
训练后模型部署回应用，工具调用能力提升
↻ 更好的模型 → 更好的轨迹 → 更好的数据 → 更好的模型 …

这个闭环的价值在于：应用不仅是产品，也是训练基础设施。每一次用户查询都可能成为未来的训练样本。

四、技术模块

模块 1：金融 MCP Server — 渐进式工具编排

业务场景：用户问"贵州茅台最近的估值是否合理？"。这个看似简单的问题，背后需要：查实时行情算市值 → 拉利润表取净利润 → 计算 PE/PB → 对比白酒行业估值中枢 → 查北向资金和机构持仓验证市场情绪。这涉及行情、财务、估值、行业对比、资金流五个分析域的协同。

系统将 A 股研究的完整工作流抽象为 7 大能力域（Skill）：

Skill覆盖场景典型工具
行情分析实时/历史行情、技术指标日线行情、复权因子、涨跌停价
财务分析三表解读、盈利能力、偿债能力利润表、资产负债表、现金流量表、财务指标
资金流向主力/散户博弈、北向资金、融资融券个股资金流、北向持股、融资融券
行业对比板块轮动、同业对标、概念热度行业分类、概念成分、行业指数
估值分析PE/PB/PS 多维估值、历史分位每日指标、估值因子
股东研究十大股东、机构持仓、股权质押十大股东、机构持股、股权质押
深度研究万字级研究报告、多源交叉验证6 Agent 协作

技术挑战：43 个工具直接全量暴露给 LLM 会导致 ~15000 tokens 的 Context 膨胀和选择准确率骤降 —— 模型在"查个股行情"时也要读一遍"股权质押"的工具描述，认知负荷过高。

设计 — 渐进式披露（Progressive Disclosure）

本质是把一个困难的 43 选 N 问题分解为两个简单问题 —— 像人类分析师的思路一样，先判断"这个问题属于什么分析类型"，再选择具体工具：

Round 1 只看 7 个 Skill 摘要（~800 tokens），选择相关 Skill —— "估值分析是否合理"→ 选中「行情 + 财务 + 估值」
Round 2 只展开选中 Skill 的工具（平均 6 个），精确调用 —— 调用日线行情、利润表、每日指标
Round 3 基于真实数据生成分析报告 —— 交叉验证多维数据，给出结论
案例：用户问"贵州茅台最近的估值是否合理？"
  • Round 1 → LLM 看 7 个 Skill 摘要，判断涉及「行情分析 + 财务分析 + 估值分析」3 个 Skill
  • Round 2 → 系统展开 3 个 Skill 的工具清单（~18 个工具），LLM 精确调用：get_daily（日线行情） → get_income（利润表取净利润） → get_daily_basic（PE/PB/PS）
  • Round 3 → 基于真实返回数据，交叉对比得出：茅台当前 PE 25.3x，位于近 5 年 40% 分位，低于行业中枢 28x → 给出"估值偏低但需关注Q4业绩"结论
效果：Prompt 节省 60%+。更关键的是，这个认知负荷管理策略后来在数据合成中被复用 —— AgentFlow 的 Sandbox 也使用完全相同的三轮交互流程，确保合成数据的分布与真实使用一致。

关键文件：backend/app/mcp_server/server.py

模块 2：AgentFlow — 三阶段数据合成

业务动机：通用模型在金融场景的工具调用能力不够好 —— 问"茅台 2024Q3 单季营收同比增速"，模型可能调错接口、传错参数、甚至不知道该查什么。我们需要领域特化的训练数据来教模型"像研究员一样思考"。

问题：高质量 Agent 训练数据极度稀缺。人工标注成本高且覆盖面窄 —— 一个标注员一天可能只能写 20 条多轮工具调用的 QA，而我们需要数千条覆盖 43 个工具各种组合的训练数据。

设计 — 三阶段合成流水线

阶段输入过程输出
1. 轨迹采样 10 万条种子问题 LLM 在 Sandbox 中自主探索，构建分支轨迹树（branching_factor=2, max_depth=5） ~60 万条轨迹路径
2. 轨迹筛选 轨迹路径 按深度、信息丰富度、工具多样性打分；路径相似度去重（threshold=0.7） ~30 万条优质轨迹
3. QA 合成 优质轨迹 基于轨迹生成多跳推理 QA + 反捷径检查 ~30 万条高质量训练数据
案例：轨迹树分支探索

种子"分析茅台基本面"在 Sandbox 中探索时，LLM 可能走出两条不同分支：

  • 分支 A：先查行情 → 再查利润表 → 计算 PE（偏量化路径）
  • 分支 B：先查北向资金 → 再查机构持仓 → 分析市场情绪（偏情绪路径）

两条分支都是合理的分析路径，都可生成有效训练数据。

种子工程：不是简单的问题列表，而是结构化的 {slots + entities} 格式。例如同一个"估值分析"意图模板，通过组合不同的用户角色（散户/研究员/基金经理）、实体（茅台/宁德时代/比亚迪）、上下文（年报季/业绩暴雷/行业政策），可以生成数百条表述各异但分析路径一致的变体问题 —— 确保训练数据覆盖真实用户的多样化提问方式。

案例：一个"估值分析"种子模板如何扩展

模板：{角色}想知道{股票}的{分析类型}，背景是{上下文}

  • → "我是散户，帮我看看贵州茅台估值贵不贵？最近白酒板块跌了不少"
  • → "作为研究员，请分析宁德时代当前 PE 分位在行业中的位置"
  • → "基金经理想评估比亚迪在新能源车板块的估值合理性，考虑到Q3产能释放"

三条问题表述完全不同，但分析路径一致：都需要行情 + 财务 + 估值三个 Skill。

关键文件：AgentFlow/synthesis/pipeline.py、AgentFlow/synthesis/core/sampler.py、AgentFlow/sandbox/server/backends/resources/finance_research.py

模块 3：AgentFlow-Train — GRPO 训练与混合奖励

业务目标：让开源模型（Qwen3-8B/30B）在金融工具调用场景达到甚至超越商用 API 的水平 —— 降低推理成本的同时实现数据私有化，让金融机构可以在自有基础设施上部署，不需要将敏感的持仓、交易数据传输到第三方 API。

核心设计 — 三层混合奖励

奖励类型占比适用场景机制
Rule-based 40% 可验证任务 Sandbox 重放工具调用，对比真实 API 返回值
LLM Judge 15% 开放式任务 多维度 0-10 评分
Hybrid 45% 半开放式任务 可验证部分用规则，质量维度用 LLM
Sandbox 重放验证：对于可验证的金融数据，reward 来自真实工具执行结果。模型说"茅台 PE 是 30 倍"？系统会在 Sandbox 里真正调用 Tushare API，拿到真实 PE 值来对比。这不是猜测，是事实核查。
案例：一次 Rule-based 奖励计算
  • 问题："茅台 2024 年净利润是多少？"
  • 模型回答："茅台 2024 年净利润约 862 亿元" + 调用了 get_income(ts_code='600519.SH', period='20241231')
  • Sandbox 重放：真正调用 Tushare API → 返回 n_income = 862.28 亿
  • 奖励计算：数据误差 < 1% → reward = 0.95（高分）
  • 对比：如果模型编造"净利润 1200 亿"且没有调用工具 → reward = 0（零分）

技术栈选型

  • GRPO（而非 PPO）：无需额外训练 Critic 模型，组内相对排序天然适合多轮工具调用的多样性探索
  • verl 框架：只写了 2 个适配文件（reward_fn.py + data_preprocess.py），核心训练用官方实现 —— 不造轮子
  • sglang 推理：RadixAttention 共享多轮对话的 prefix KV cache，对工具调用场景加速显著
  • LoRA + FSDP2：Qwen3-30B MoE 模型在 param_offload 下单卡显存从 60GB 降到 12GB

关键文件：AgentFlow-Train/reward_fn.py、AgentFlow-Train/data_preprocess.py、AgentFlow/training/reward/

五、核心难点（STAR 格式）

难点 1：6 Agent 对抗式深度研究 — 三次失败后的正确答案
Situation

用户提出"帮我写一份比亚迪 vs 特斯拉的深度对比研报"。这在真实券商场景中是一份需要 2-3 天、涵盖财务对比、产能分析、市场份额、估值对标的万字级报告。LLM 单次生成幻觉严重、质量不可控。

金融领域的幻觉不仅"不好"，而且"危险" —— 一个编造的 PE 数据可能导致完全错误的投资判断。例如模型可能"自信地"说比亚迪 PE 是 15 倍（实际 25 倍），直接影响估值结论。

Task

构建可控、可追溯、质量稳定的研究报告生成系统，并且能提供完整的决策轨迹用于后续训练。

Action

三次迭代：

V0 黑盒（失败）
一个大 Prompt 直出完整报告。→ 幻觉严重。更致命的是：无法定位问题出在哪里 —— 是搜索不够、分析错误、还是写作编造？
V1 灰盒（失败）
拆为搜索→分析→写作三阶段。→ 审核 Agent 说"第三节数据不准"时，系统不知道该重做搜索还是重做分析。审核反馈和执行阶段之间存在"语义断层"。
V2 白盒（成功）
6 Agent 全拆分 + LangGraph 状态机 + 30+ 字段共享状态。
  • Architect — 像研究总监：分析问题 → 拆解为研究大纲（财务对比/产能分析/估值对标等章节） → 提出需要验证的假设
  • Scout — 像研究助理：并行搜索 Tushare 数据 + 网络资讯，提取事实，标注可信度（API 数据 > 机构研报 > 新闻资讯）
  • Analyst + Wizard — 像量化分析师：数据提取 → 计算同比/环比/CAGR 等指标 → 图表可视化
  • Writer — 像首席分析师：按大纲撰写，强制 [来源: 工具名] 引用格式，每个数据点都必须有出处
  • Critic — 像合规审核：检查 6 类问题（数据错误/逻辑矛盾/来源缺失/时效过期/结论过度/覆盖不全），质量低于阈值则精确标记哪个章节、什么问题，打回对应 Agent 修订
案例：6 Agent 如何协作完成"比亚迪 vs 特斯拉深度对比"
  1. Architect 拆解大纲 → 5 个章节（营收对比/毛利率/产能/市场份额/估值）
  2. Scout 并行搜索 → Tushare 拉比亚迪三表 + 博查搜索特斯拉 10-K + 行业新闻
  3. Analyst 计算 → 比亚迪营收 YoY +33%，特斯拉 YoY +2%；毛利率 20.1% vs 17.9%
  4. Writer 按大纲撰写 → "比亚迪 2024 年营收 6023 亿[来源: get_income]，同比增长 33%..."
  5. Critic 审核 → 发现"第3节市场份额数据无来源" → 打回 Scout 补充搜索
  6. Scout 补搜 → Writer 修订 → Critic 通过 → 输出万字研报
Result

报告质量从"随机波动"变为"稳定可控"。

关键副产品：白盒轨迹数据（query → plan → facts → analysis → draft → feedback → revision）直接构成 GRPO 训练数据。我们从一开始就将"可训练性"作为架构约束。

反思：三次迭代的核心教训 —— 可观测性是可控性的前提。这个认知贯穿了整个项目：MCP 的三轮编排让每次工具调用可追溯，白盒 Agent 让每个决策可审计，Sandbox 重放让每个奖励可验证。

难点 2：从"猜测奖励"到"事实核查奖励" — 混合奖励函数的设计
Situation

用 GRPO 训练金融工具调用模型时，核心问题是如何定义奖励。金融场景有特殊性：部分任务是可验证的（有确定答案），部分是开放式的（没有标准答案），还有大量是半开放的（结论开放但数据可验证）。

用统一的 reward model 处理这三类任务，要么对可验证任务不够精确，要么对开放式任务过于死板。

Task

设计一个能同时处理可验证、开放式和半开放式任务的奖励函数，且对可验证部分必须基于事实而非猜测。

Action

方案演进：

V1 全 LLM Judge（失败）
用 LLM 给所有回答打分 → 对可验证数据也在"猜"对不对，无法区分"回答了一个近似值"和"完全编造"。
V2 全规则（失败）
对所有回答做精确匹配 → 开放式问题无法规则评判，大量有价值的回答被误判为低分。
V3 混合方案（成功）
三层奖励 + Sandbox 重放。

最终设计四步：

  1. 标签系统：每条训练数据标注 verifiable=True/False 和 verification_method=api/compute/hybrid/llm_judge，路由到对应奖励计算器
  2. Sandbox 重放：对可验证任务，在 CPU 端的 Sandbox 中真正重放工具调用，拿到真实 API 返回值做对比。sglang 只负责 GPU 上的文本生成，奖励计算完全在 CPU 端完成 —— 生成和验证解耦
  3. 多维度 LLM Judge：对开放式任务，按信息完整性、数据支撑、逻辑连贯性、实用性四个维度独立评分
  4. Hybrid 融合：对半开放式任务，可验证字段用规则打分，质量维度用 LLM 打分，加权融合
案例：Hybrid 奖励如何处理"茅台估值是否合理"
  • 可验证部分（Rule, 60% 权重）：检查模型引用的 PE=25.3x 是否正确 → Sandbox 重放确认 ✓ → 0.95
  • 开放式部分（LLM Judge, 40% 权重）：评估分析逻辑是否自洽、是否考虑了多维因素 → 评分 8/10 → 0.80
  • 最终 reward = 0.95 × 0.6 + 0.80 × 0.4 = 0.89
Result

可验证任务的奖励信号零幻觉 —— 因为对的就是对的，错的就是错的，不存在"猜测空间"。开放式任务保持评判灵活性，半开放式任务兼顾精确性和灵活性。GRPO 训练收敛更稳定 —— 因为 reward signal 的噪声更小。

深层意义：在强化学习中，奖励函数的质量决定了训练的上限。我们的创新是把"应用本身"（MCP Server + Sandbox）变成了奖励计算的基础设施，而不是训练一个可能有偏差的 reward model 来猜测。

六、关键技术亮点速览

金融幻觉四层防御

金融领域的幻觉不同于一般 AI 幻觉 —— 一个错误的 PE 值、一个编造的营收数据，都可能直接影响投资决策。因此我们构建了从应用到训练的全链路防御：

数据层
所有财务数据必须来自工具调用，禁止 LLM 自行推算
防止模型"记忆"过期数据
生成层
Writer 强制 [来源: 工具名] 引用标注
让报告可追溯，用户能验证每个数据点
审核层
Critic 对抗式检查 6 类问题
模拟券商合规审核流程
训练层
Sandbox 重放验证，从源头让模型学会"不编造"
从根本上降低模型编造金融数据的倾向

多模型动态路由

同一系统内不同 Agent 使用不同模型 —— 本质是推理预算分配问题：

  • Scout（搜索）→ Qwen Plus（速度优先，搜索不需要深度推理）
  • Analyst（分析）→ DeepSeek V3.2 低温度（数值精度）
  • Writer（写作）→ DeepSeek V3.2 高温度（行文流畅）
  • Critic（审核）→ DeepSeek V3.2 中温度（严谨推理）

评测方法论

七-B、v0.8.3 — Tushare 真接入 + B-3 持仓预警引擎

本节记录 v0.8.3 新增的两个核心模块。

模块 A：Tushare Pro 真接入（8 个数据接口）

前期版本用 MockTushareService（LLM 生成假数据）做本地开发。v0.8.3 完成了从 mock 到真实 API 的全量切换——Protocol 模式让调用方代码零改动（依赖注入 + factory），通过环境变量 TUSHARE_MODE 切换 real / mock。

8 个接口：日线行情（daily）、利润表（income）、财务指标（fina_indicator）、资产负债表（balance_sheet）、现金流量表（cashflow）、股东户数（stk_holdernumber）、财报披露日历（disclosure_date）、公告（anns）。

  • sqlite 本地缓存（TTL=24h）：同一 ts_code + period 在缓存有效期内返回本地数据，避免重复调用。
  • Protocol + factory 模式（第 8 次应用）：TushareService 是 typing.Protocol，调用层不 import 具体类。
  • cassette 脱敏：VCR cassette 记录前过滤 token（filter_headers），CI 全程离线 replay。
  • 测试覆盖：8 接口 × 5 个 ts_code = 36 个 cassette e2e 测试。

模块 B：B-3 持仓预警引擎（分层架构）

银行公司金融部持续放贷后，需在财报发布季、公告高峰期等关键节点主动监控客户信用风险——参考穆迪早期预警信号（Moody's Early Warning Signals）设计。

两层架构：信号层（5 规则，并发数据计算）+ Agent 层（红色 alert 触发 5-agent 深度调查）。

5 个信号规则：资产负债率、现金流、股东户数、公告 LLM 分类、价格异动。

四道硬约束闸：日同客户去重 + 日总预算 ¥10 + 并发限 1 + 单次 ¥1 事后校验。

持续监控产品形态：日 cron + 披露日历事件触发 + 手动按钮 + email 通知 + 5 张 DB 表 + 前端 3 页。

已知 limitation：黄色默认不发 email（前端可配置）；配置页阈值持久化留 v1.x；全市场扫描留 v0.8.5。

测试：22 个 SignalRule 单元测试 + MonitoringService 三流端到端 + 10 个 golden case + e2e cassette（待录制）。

八、面试高频问答

一个面向 A 股研究场景的 AI 研究助手，覆盖从行情查询到万字研报生成的全链路；更关键的是，我把这个应用本身变成了训练数据的生产线 —— 用应用生成训练数据，用训练数据改进应用，形成数据飞轮。
券商研究员写一份深度报告，60% 以上时间花在数据采集和清洗上，真正的分析洞察时间被严重挤压。我们的系统让"提一个问题 → 得到一份有数据支撑、可追溯引用的研究报告"成为可能。同时，通过训练闭环持续提升开源模型的金融工具调用能力，使金融机构可以在自有基础设施上私有化部署，解决数据安全顾虑。
混合奖励函数设计。核心挑战是金融场景同时存在可验证、开放式、半开放式三类任务。创新是用 Sandbox 重放做"事实核查"替代传统 reward model 的"猜测"。
渐进式披露。A 股研究涉及行情、三表、资金流、估值等多个分析域，43 个工具全量暴露会让模型"选择困难"。渐进式披露让模型像人类分析师一样先判断分析类型再选工具，Prompt 节省 60%，更关键的是这个设计从应用层贯穿到数据合成层，确保训练数据分布与真实使用一致。
深度研究引擎的黑盒 / 灰盒两次失败。核心教训："可观测性是可控性的前提"。这个认知贯穿了整个项目：工具调用可追溯、Agent 决策可审计、奖励计算可验证。
PPO 需要额外训练 Critic 模型。GRPO 用组内相对排序替代 Critic，降低训练复杂度。更关键的是，GRPO 的 group sampling 天然鼓励多样性探索 —— 同一个金融问题可能有多种合理的工具调用路径，我们需要模型探索这些路径而非收敛到单一答案。
将应用本身变成训练基础设施。MCP Server 既是用户产品，也是 Sandbox 环境；工具调用结果既是用户答案，也是 reward signal。这种"应用即基础设施"的思路让数据飞轮成为可能。
(1) 从应用开发到训练闭环的全链路视野 —— 不只是"会调 API"，而是理解了 AI 应用的完整生命周期；(2) 金融领域的 domain knowledge —— 理解了研究员的工作流、分析方法论和行业惯例；(3) 奖励函数设计决定训练上限的深刻理解；(4) "可观测性是可控性的前提"的工程哲学。
两个方向：(1) 横向扩展覆盖面 —— 目前只覆盖 A 股，可以扩展到港股、美股、基金、债券；数据源从 Tushare 扩展到 Wind、Bloomberg；(2) 纵向深化分析能力 —— 引入更复杂的量化分析（因子模型、事件驱动策略），让系统不只是"查数据写报告"，而是能做初步的投资决策辅助。
