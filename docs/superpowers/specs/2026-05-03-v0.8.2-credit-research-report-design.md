## § 2 `CreditInvestigationReport` schema 设计

### 2.1 整体结构

按银行信贷调查报告业界标准模板(参考商业银行公司金融业务条线常见格式),定 6 个核心 sections:

```python
class CreditInvestigationReport(BaseModel):
    # Header
    company_name: str                      # 企业名
    request_id: str                        # 关联 trace
    generated_at: datetime                 # 生成时间

    # Sections(都必填)
    company_overview: CompanyOverview              # § 1 基本信息
    legal_qualification: LegalQualification        # § 2 主体资格
    financial_analysis: FinancialAnalysis          # § 3 财务分析
    industry_analysis: IndustryAnalysis            # § 4 行业分析
    risk_assessment: RiskAssessment                # § 5 风险评估
    credit_recommendation: CreditRecommendation    # § 6 信贷建议
```

### 2.2 各 section 详细字段

#### § 1 CompanyOverview(基本信息)

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| narrative | str | ✅ | 100-300 字综述 |
| unified_credit_code | str \| None | 可选 | 统一社会信用代码(KB 不一定有) |
| registered_capital | str \| None | 可选 | 注册资本 |
| main_business | str | ✅ | 主营业务一句话 |
| controlling_shareholder | str \| None | 可选 | 实际控制人 |
| listing_status | str \| None | 可选 | 上市 / 非上市 + 板块 |
| evidence | list[str] | ✅ | 引用的 chunk_id 列表 |

#### § 2 LegalQualification(主体资格)

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| narrative | str | ✅ | 200-400 字综述 |
| legal_status | str | ✅ | 法律主体合规情况 |
| business_qualifications | list[str] | ✅ | 经营资质列表(空 list 也行) |
| adverse_records | list[str] | ✅ | 不良记录(空 list 也行) |
| evidence | list[str] | ✅ | chunk_id |

#### § 3 FinancialAnalysis(财务分析)

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| narrative | str | ✅ | 400-800 字深度分析 |
| key_metrics | list[FinancialMetric] | ✅ | 关键财务指标(营收 / 净利 / 资产负债率 / ROE / 经营现金流等) |
| solvency_analysis | str | ✅ | 偿债能力 |
| profitability_analysis | str | ✅ | 盈利能力 |
| cash_flow_analysis | str | ✅ | 现金流分析 |
| year_over_year_summary | str \| None | 可选 | 同比变化(若有多年数据) |
| evidence | list[str] | ✅ | chunk_id |

```python
class FinancialMetric(BaseModel):
    name: str         # "营业收入" / "净利润" / "资产负债率"
    value: str        # "150 亿元" / "12.5%"  ── 字符串,不强制单位
    period: str       # "2024 H1" / "2024 全年"
    yoy_change: str | None = None   # "同比 +15%"
```

#### § 4 IndustryAnalysis(行业分析)

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| narrative | str | ✅ | 300-600 字 |
| industry_name | str | ✅ | 所属行业 |
| industry_outlook | str | ✅ | 景气度判断 |
| competitive_position | str | ✅ | 在行业中的竞争地位 |
| key_competitors | list[str] | ✅ | 主要竞争对手(空 list 也行) |
| policy_impact | str | ✅ | 相关政策影响 |
| evidence | list[str] | ✅ | chunk_id |

#### § 5 RiskAssessment(风险评估)

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| narrative | str | ✅ | 300-500 字 |
| operational_risks | list[RiskItem] | ✅ | 经营风险列表(空 list 也行) |
| financial_risks | list[RiskItem] | ✅ | 财务风险列表 |
| industry_risks | list[RiskItem] | ✅ | 行业风险列表 |
| compliance_risks | list[RiskItem] | ✅ | 合规风险列表 |
| overall_risk_level | Literal["low", "medium", "high", "very_high"] | ✅ | 整体风险等级 |
| evidence | list[str] | ✅ | chunk_id |

```python
class RiskItem(BaseModel):
    title: str         # "应收账款集中度高"
    description: str   # 一段描述
    severity: Literal["low", "medium", "high"]   # 单项严重度
    mitigations: list[str] = []   # 可缓释措施(空 list 也行)
```

#### § 6 CreditRecommendation(信贷建议)

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| narrative | str | ✅ | 200-400 字综合建议 |
| decision | Literal["approve", "reject", "approve_with_conditions"] | ✅ | 决策建议 |
| recommended_credit_limit | str \| None | 可选 | 建议额度("3 亿元" / "20 亿元",字符串) |
| recommended_term | str \| None | 可选 | 建议期限("1 年" / "3 年") |
| recommended_rate_range | str \| None | 可选 | 建议利率区间("LPR + 50bp ~ + 100bp") |
| guarantee_requirements | list[str] | ✅ | 担保要求(空 list 也行) |
| conditions | list[str] | ✅ | 附加条件(approve_with_conditions 时填) |
| evidence | list[str] | ✅ | chunk_id |

### 2.3 evidence 字段语义

每个 section 必须填 `evidence: list[str]`(chunk_id 列表)。规则:
- 至少包含 1 个 chunk_id(即"无引用"不允许通过 schema validation)
- chunk_id 必须是当次 retrieval 真的拿到过的 chunk(后续 v0.8.5 D1 引用 UI 可以校验)
- 数量上限不强制(LLM 倾向多引,质量靠 D1 metrics 评估)

**为什么 evidence 在 section 级而非 claim 级**:
- claim 级 = `[{statement: ..., evidence: [...]}]`,粒度最细但 schema 复杂 + LLM 输出不稳
- section 级 = 每个 section 一个 evidence list,平衡可追溯 + LLM 稳定性
- v0.8.5 升 claim 级是可选 future work

### 2.4 LLM 输出形态约束

writer 输出**整个 CreditInvestigationReport JSON**(不是 markdown)。markdown 由 schema → renderer 推。这样:
- schema validation 是真 source of truth
- markdown 渲染可改样式不影响 LLM
- 后续可加 PDF 渲染 / docx 渲染共用同一份 schema

## § 3 Writer agent 改造

### 3.1 改造前(当前)

```python
class Writer(Agent):
    def step(self, state: ResearchState) -> StepResult:
        prompt = build_writer_prompt(state)
        r = self._llm.chat(prompt=prompt, tier=self.model_tier, request_id=state.request_id)
        md, specs = _parse_writer_output(r.content)   # 解 free text JSON
        return StepResult(state_update={"report_markdown": md, "chart_specs": specs}, ...)
```

输出 `{report_markdown: str, chart_specs: list[ChartSpec]}`。

### 3.2 LLMService 前置扩展(本 spec § 1 第 2 块)

**当前 LLMService.chat 契约**(verify 实际代码 backend/app/services/llm_service.py:72):
```python
def chat(self, prompt: str, tier: Tier = "fast",
         schema: dict[str, Any] | None = None,    # JSON schema dict,不是 Pydantic class
         ...) -> LLMResponse:
    ...
    return LLMResponse(content=raw.content, parsed=None, ...)   # parsed 永远 None
```

即使传了 schema,LLMService **不做客户端 Pydantic 解析**,只把 schema dict 透传给 LLM provider。

**v0.8.2 扩展**(向后兼容):
```python
def chat(self, prompt: str, tier: Tier = "fast",
         schema: dict[str, Any] | type[BaseModel] | None = None,
         ...) -> LLMResponse:
    if isinstance(schema, type) and issubclass(schema, BaseModel):
        json_schema = schema.model_json_schema()
        pydantic_class = schema
    else:
        json_schema = schema  # legacy dict path
        pydantic_class = None
    # ... 透传 json_schema 给 client
    parsed = pydantic_class.model_validate_json(raw.content) if pydantic_class else None
    return LLMResponse(content=raw.content, parsed=parsed, ...)
```

LLMResponse.parsed 也要扩到 `BaseModel | dict[str, Any] | None`(memory `project_llm_service_contract` 契约扩展,需要更新 memory)。

### 3.3 Writer 改造后

```python
class Writer(Agent):
    name = "Writer"
    model_tier: Tier = "balanced"

    def step(self, state: ResearchState) -> StepResult:
        prompt = build_credit_report_prompt(state)
        r = self._llm.chat(
            prompt=prompt,
            tier=self.model_tier,
            schema=CreditInvestigationReport,    # ← 用扩展后 API,Pydantic class 直接传
            request_id=state.request_id,
        )
        assert isinstance(r.parsed, CreditInvestigationReport)   # 扩展后保证非 None
        report = r.parsed
        report.request_id = state.request_id
        report.generated_at = datetime.now()

        markdown = render_credit_report_markdown(report)   # ← 新:渲染器

        return StepResult(
            state_update={
                "credit_report": report,           # ← 新:结构化报告
                "report_markdown": markdown,       # 兼容老 SSE / 前端
                "chart_specs": [],                 # 兼容,留空(charts 不在 v0.8.2 scope)
            },
            span_metadata={"agent": "Writer", "model": r.model, "cost_cny": r.cost_cny},
        )
```

**关键变化**:
1. 先扩 LLMService 支持 Pydantic class(§ 3.2),再用扩展后 API
2. writer 不再手动 `json.loads + try/except`(交给 LLMService + Pydantic)
3. 输出新增 `credit_report: CreditInvestigationReport` field,旧 `report_markdown` 由 renderer 生成保留(避免 SSE / 前端硬改)
4. `chart_specs` 留空(v0.8.2 不做 chart;v0.8.5 加回)
5. memory `project_llm_service_contract` 需要在本 PR ship 后更新(契约扩展记录)

### 3.3 prompt 改造

`build_credit_report_prompt` 需要明确告诉 LLM:
- 你是银行公司金融部信贷研究分析师
- 任务:基于 Insights + 用户提供的企业名,产出"信贷调查报告"
- 报告必须符合 6 sections 结构(详 schema)
- 每个 section narrative + 关键 fields,且**每个 section 至少 1 个 evidence chunk_id**
- 风险等级 + 决策建议要保守(高风险时建议 reject 或 approve_with_conditions)
- 中文金融术语规范(资产负债率、经营性现金流、不良记录等)

完整 prompt 草稿在 implementation plan 里写,本 spec 只锁需求。

## § 8 Risks

### 8.1 R1 — schema 太严 LLM 输出 fail rate 高

**风险**:6 sections 全必填 + 子字段多,LLM 可能频繁 schema validation fail,需要 retry。

**Mitigation**:
- LLMService 已有 retry + structured output(项目契约,memory `project_llm_service_contract`)
- 可选字段尽量用 `| None`(已设计)
- evidence 至少 1 个 chunk_id(不空 list)是软约束,prompt 强调
- 实施时 dogfood 看真实 fail rate,> 20% 则放松 schema(改部分必填 → 可选)

### 8.2 R2 — Writer prompt 跑出来 narrative 质量差

**风险**:第一版 prompt 跑出来报告读起来生硬 / 不专业 / 中文金融语境不对。

**Mitigation**:
- 实施时 dogfood 5-10 次迭代,prompt 不在 plan 阶段冻结
- 准备一份"参考银行信贷调查报告"风格的范文(可以让 LLM 模仿)
- Critic 对 writer 输出做风格 check(已有 critic 5 维度)

### 8.3 R3 — KB 数据不够支撑 6 sections

**风险**:茅台 KB 主要是财报 + 政策,行业研报覆盖度可能不够,导致 IndustryAnalysis section 只能填空话。

**Mitigation**:
- Bocha web search 补行业实时信息(已 production)
- 真填不出来的 section,LLM 在 narrative 里诚实声明数据 limitation(prompt 鼓励)
- 不行就降级:demo 公司换比亚迪 / 中芯国际(行业研报覆盖度更好)

### 8.4 R4 — Cassette 录制 cost / max_tokens 风险

**风险**:B-1 完整跑一次会调多次 LLM(planner / 多 agent / writer),cassette 录制 cost 估算不准,且 writer 6 sections JSON 输出可能超 max_tokens=2048。

**Mitigation**:
- 录制前先 spike 单次 B-1 cost(memory `feedback_max_tokens_per_model_calibration`)
- writer step 单独把 max_tokens 提到 4096(只在 writer 提,不全局 sweep)
- cassette body match 用 spec v0.8.1 § 6 R4 inline policy

### 8.5 R5 — credit_report 字段加 ResearchState 影响 v0.5 cassette

**风险**:`ResearchState` schema 加新 field,v0.5 maotai cassette 重新跑可能 schema 不兼容(已有 cassette 录制时无此 field)。

**Mitigation**:
- `credit_report: CreditInvestigationReport | None = None` 用 default None,旧 cassette 仍 valid
- Pydantic 加新 optional field 是 backward-compat
- v0.5 cassette 不需要重录(本 PR 只录 v0.8.2 自己的 cassette)

### 8.6 R6 — LLMService schema 扩展破坏现有调用方

**风险**:LLMService.chat 签名扩展(`dict | type[BaseModel]`),所有现有调用方(planner / data_collector / analyst / critic / responder / chat_agent)都不能挂。

**Mitigation**:
- 扩展是 union 加项,不改原 dict 路径行为(向后兼容)
- 加 unit test 同时覆盖 dict 和 Pydantic class 两个路径
- 跑全 unit + integration 测试(v0.8.1 baseline 已绿)
- mypy strict 检查会捕获 type 不一致

### 8.7 R7 — assert isinstance 在生产代码

**风险**:Writer step 里用 `assert isinstance(r.parsed, CreditInvestigationReport)`,Python `-O` 模式会 strip。

**Mitigation**:
- 项目 production 不跑 `-O`(verify pyproject + Dockerfile)
- 或改成显式 if + raise,更稳但更啰嗦,实施时决定
