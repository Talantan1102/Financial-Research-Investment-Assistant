## § 1 问题陈述

### 1.1 v0.8.5 ship 的 4-plan 分叉做了什么

`backend/app/agents/plan_registry.py` 硬编码 4 个 plan(`capital_preservation` / `stable_growth` / `balanced` / `aggressive_growth`),每个 plan 4 个 subtask,每个 subtask 固定 `required_tools` tuple。

`research_planner.py` 的 LLM 角色是 "constrained router" — 只输出 `{plan_id, rationale}`,从 4 候选选 1。然后 `instantiate_plan(plan_id, target_name, ts_code)` 纯函数填模板。

### 1.2 复盘暴露的问题

**问题 1:破坏客观底稿层**

业界做尽调有清晰的分层:
- **卖方研报**(中信/中金/高盛):一份报告对应一只票,**不分客户**,数据采集 100% 标准化
- **买方/私行**(MS/UBS/招行私行):分两段 — **Layer 1 标的研究**(客观底稿,所有客户共用) + **Layer 2 客户适配**(按 KYC 裁剪)
- **量化**:按因子分,客户画像只影响因子权重不影响 pipeline 走法
- **LLM 类产品**(Bloomberg GPT / FactSet Mercury / 中信建投 AI):标的为主客户为辅,客户化在生成阶段调节,**不在 plan/tool-routing 层分叉**

v0.8.5 的设计把"客户适配"提前到了**数据采集**层 — `aggressive_growth` 客户不看偿债能力,`capital_preservation` 客户不看赛道。**同一只茅台不同客户看到的数据集不一样**。

**问题 2:跨客户不可比**

客户经理给同一个客户加配/减配同一只股票时,跨画像视角不可比较。原本卖方研报"客观底稿"的价值丢失。

**问题 3:组件 use case 无法复用底座**

[[v1-use-case-classification]] 定义 B-7 报告追问 / C-1 个股研究 等"组件 use case"应该寄生在 B-1 底座上。但 4-plan 分叉的 PLAN_REGISTRY 没有"通用底稿"概念,组件场景要么自建一份,要么硬塞进 4 个 plan 之一,都不自然。

### 1.3 量化症状

- v0.8.5 differential golden case 跑通了(3 组同 ts_code 改 input 输出差异 ≥ 0.85),证明 plan 层分叉是"有效"的 — 但**有效不等于对**
- dogfood 阶段未做"跨客户可比性"检验(因为这条 thesis 未提出)
- B-7 / C-1 use case 没启动设计,无法实测组件复用的痛点

## § 3 选 A 后内部 4 个细分 — 选 A4

砍 4-plan 分叉,塌缩到 1 个 plan,但"1 个 plan"的实现有 4 种成色:

| 细分 | LLM 智力空间 | 合规守护 | 客观底稿 | Cassette 友好 | 简历叙事 |
|---|---|---|---|---|---|
| **A1** 纯静态模板 | 0 | 静态写死 | ✅ | ✅ | 强(做减法) |
| **A2** 静态骨架 + LLM 选填 | 中 | 部分守护 | ✅ | ⚠️ | 弱(半 B 半 A) |
| **A3** 自由 LLM 规划 | 100 | 靠 LLM 自觉 | ❌ | ❌ | 弱(炫技但脆弱) |
| **A4** 模板引导 + Validator 守护 | 适度 | **Python validator 守护** | ✅ | ⚠️ 可控 | **极强(业界对齐 + 工程克制)** |

**选 A4**。

理由:
1. **A1 过简**,LLM 完全没角色,放弃了 LLM 在 tool 选择 / query 措辞 / optional dim 取舍上的智力价值
2. **A4 工程范式业界标准** — OpenAI Structured Outputs / Anthropic Structured / Instructor / DSPy / Microsoft TypeChat 全是这套"structured generation + deterministic validator"思路
3. **A4 保留 cassette 友好** — temperature=0 + seed → deterministic;validator 是纯函数;retry 上限收敛
4. **A4 简历叙事强** — "v0.8.5 → v1.x 复盘:从 4-plan 分叉退到 template + validator,业界 LLM 应用'让模型聪明 + 让规则可信'的标准做法"

## § 4 A4 核心设计 — Template / LLM / Validator 三块

### 4.1 Template — 约束与自由度声明

```python
# backend/app/agents/plan_template.py (新建)
DD_PLAN_TEMPLATE: PlanTemplate = {
    # 必须覆盖的维度 — 所有客户都跑,LLM 必须为每个产 ≥1 subtask
    "required_dimensions": [
        {"name": "财务全景", "tool_candidates": ["get_financials", "get_balance_sheet", "get_cashflow"], "min_tools": 2},
        {"name": "估值",     "tool_candidates": ["get_pe_history", "get_daily_basic", "get_peer_companies"], "min_tools": 1},
        {"name": "行业地位", "tool_candidates": ["get_industry_classify", "web_search", "kb_search"], "min_tools": 1},
        {"name": "风险底线", "tool_candidates": ["get_holder_change", "get_news", "kb_search"], "min_tools": 1},
    ],
    # 可选维度 — LLM 根据 user_message / chat 上下文决定是否产 subtask
    "optional_dimensions": [
        {"name": "近期催化",  "tool_candidates": ["get_forecast", "get_news"]},
        {"name": "资金动向",  "tool_candidates": ["get_money_flow"]},
        {"name": "同业对比",  "tool_candidates": ["get_peer_companies"]},
    ],
    # tool 白名单(防 LLM hallucinate)
    "tool_palette": [...],
    # 业务约束
    "constraints": {
        "max_subtasks": 10,
        "max_tool_calls_per_subtask": 3,
        "forbid_duplicate_calls": True,
    }
}
```

**关键设计**:`required_dimensions` 对所有客户**一样**(这是 A 的精神 — 客观底稿)。客户画像和 chat 信号只通过 prompt 影响 `optional_dim` 取舍和 tool args 措辞,**不影响 required 维度**。

**组件 use case 扩展性**:不同 use case(B-1/B-7/C-1)对应不同 template,但同一套 PlanTemplate schema + 同一个 Validator。例如 B-7 报告追问 template 可能只有 1-2 个 required_dim(focused query)。

### 4.2 LLM 任务

输入:
- Template
- 6 字段客户画像
- user_message
- chat-distilled signals(见 § 6)
- chat_known_tool_results
- Validator feedback(retry 时)

LLM 决定:
- 每个 `required_dim` 选哪几个 tool(从 candidates 内)
- `optional_dim` 要不要产 subtask
- subtask 的 `description` + `rationale`(人话)
- tool args(`web_search.query` 措辞 / `get_financials.period` 选哪个)

LLM **不能**决定:
- required 维度是哪些(template 硬编码)
- tool 白名单(hardcoded)
- 业务规则(min_tools / max_subtasks / no_dup)

输出: Pydantic-bound `ResearchPlan`。

### 4.3 Validator — 三层校验门

```python
# backend/app/agents/plan_validator.py (新建)
class ValidationResult(BaseModel):
    ok: bool
    errors: list[str]  # 喂回 LLM retry 的 feedback

def validate_plan(plan: ResearchPlan, template: PlanTemplate) -> ValidationResult:
    errors = []
    
    # L1. Schema — Pydantic 在 LLMService 那层已强制,这里只做 sanity
    
    # L2. 业务规则
    # 必填维度全覆盖
    for dim in template["required_dimensions"]:
        if not _has_subtask_for_dimension(plan, dim):
            errors.append(f"missing required dim: {dim['name']}")
        elif _tool_count_for_dim(plan, dim) < dim["min_tools"]:
            errors.append(f"dim '{dim['name']}' has < {dim['min_tools']} tools")
    
    # tool 白名单(防 hallucinate)
    for sub in plan.subtasks:
        for tool in sub.required_tools:
            if tool not in template["tool_palette"]:
                errors.append(f"tool '{tool}' not in palette (LLM hallucinated)")
    
    # 总数 / 去重
    if len(plan.subtasks) > template["constraints"]["max_subtasks"]:
        errors.append(f"too many subtasks: {len(plan.subtasks)} > {template['constraints']['max_subtasks']}")
    if _has_duplicate_calls(plan):
        errors.append("duplicate (tool, args) calls detected")
    
    # L3. 成本预算(optional)
    # 仅在 EVAL_COST_LIMIT_CNY 启用时校验
    if _is_cost_check_enabled() and _estimate_cost(plan) > _budget():
        errors.append(f"estimated cost {_estimate_cost(plan):.2f} exceeds budget")
    
    return ValidationResult(ok=not errors, errors=errors)
```

### 4.4 Retry + Fallback Ladder

```
LLM 生成 plan → validate_plan
                    ↓
            ok ── 进入 DataCollector
                    ↓
            fail ── errors 注入 prompt → LLM retry (上限 2 次)
                    ↓
            all fail ── fallback 到 SAFE_DEFAULT_PLAN (静态保底,见 § 5)
                    ↓
            SAFE_DEFAULT 进入 DataCollector + 在 trace 标记 fallback
```

**4 个关键决策**(2026-05-15 brainstorm 拍板):

- **D1**: LLM retry 上限 **2 次**
- **D2**: `SAFE_DEFAULT_PLAN` = § 5 的静态 7-subtask 全量 plan,一份代码两用(兜底 + cassette baseline)
- **D3**: 删除 Critic 的 `plan_correctness` scorer(Critic 从 7 维降到 6 维 — Validator 在生成时已守护)
- **D4**: 删除现有 planner retry 边,改加 **writer retry on factuality < 7.0**(注入 critic evidence feedback,上限 1 次)

## § 6 多轮对话场景 prompt 设计

### 6.1 问题陈述

DD 有两种触发路径:
1. **表单直入** — `/research` 路由 form 提交,user_message 是表单自由文本
2. **Chat escalation** — 用户在 chat 聊到一定程度 → escalate 到 DD(`escalation_protocol.py`)

第 2 条路径下,"user_message" 不是一段 fresh text,而是从 N 轮 chat 蒸馏出来。这个蒸馏怎么做是核心工程问题。

### 6.2 业界 5 种范式对比

| 范式 | 做法 | 代表 | 优点 | 缺点 |
|---|---|---|---|---|
| **R1. 摘要派** | LLM 把 N 轮 chat 总结成一段话当 user_message | LangChain `ConversationSummaryMemory` | 简单 | 信息丢失大,结构化信号丢 |
| **R2. 结构化抽取** | LLM 抽取 entities/preferences/已查 tool → typed fields | Anthropic context engineering / OpenAI Agents | 信号保真可校验 | 抽取层本身是 LLM 黑盒 |
| **R3. 原始 history** | planner prompt inline 完整 chat | Bloomberg GPT 早期 | 零信息丢失 | token 成本高 + 注意力稀释 + cassette 抖动 + 不审计 |
| **R4. Hybrid (业界主流)** | R2 主路径 + R1 fallback | Anthropic Claude Projects / Bloomberg AskBLP / Cursor / Notion AI | 信号 + 容错 | 工程复杂度高 |
| **R5. Gap 驱动两段** | LLM 先看 chat 决定"缺什么信息" → 推 planner | Google/OpenAI DeepResearch / Perplexity Pro | 自适应 | DD 维度已被 template 钉死,不适合 |

**选 R4**。金融场景几乎是事实标准(合规要求 distilled record,raw chat 不是 auditable artifact)。

### 6.3 你 codebase 已有的 R4 部件

| 信号 | 状态 | 来源 |
|---|---|---|
| `chat_known_tool_results` | ✅ 已接入 planner prompt | `_format_chat_known_tools()` |
| `chat_extracted_entities` | ✅ 已接入 analyst | `_format_chat_signals()` |
| `chat_extracted_preferences` | ✅ 已接入 analyst | 同上 |
| `EscalationExtractor` agent | ✅ 存在 | `agents/escalation_extractor.py` |

### 6.5 Confidence 计算机制 — C6 Composite

业界 6 种 mechanism 对比:

| # | 方法 | 业界 | 致命缺点 |
|---|---|---|---|
| C1 | LLM self-report | 极常用 | LLM **倾向 over-confident**(Kadavath 2022 / Lin 2022 calibration 差) |
| C2 | Token logprobs | OpenAI 部分支持,**Claude 不暴露** | 不可用 |
| C3 | Self-consistency | 学术经典,工业少用 | N 倍成本,cassette 难录 |
| C4 | LLM-as-judge | Anthropic/Notion 用 | 2x cost |
| C5 | Deterministic heuristic | production 必备 | rule 越多越脆弱 |
| **C6** | **C1 ∩ C5 取 min** | **Bloomberg/Cursor 用** | 复杂度略升 |

**选 C6**。

#### Step 1: LLM self-confidence

extractor schema 里 `llm_self_confidence: Literal["high","medium","low"]`,映射:
```python
_LLM_CONF_MAP = {"high": 0.9, "medium": 0.6, "low": 0.3}
```

#### Step 2: Deterministic features

5 个特征,每个 0.0-1.0:

```python
def compute_deterministic_confidence(
    extracted: EscalationPacket,
    chat_history: list[ChatMessage],
    target_ts_code: str,
    target_name: str,
    user_confirmed_escalation: bool,
) -> float:
    f = {}
    # F1. Chat 长度 — 太短信号不足
    f["chat_length"] = min(len(chat_history) / 5.0, 1.0)
    # F2. 核心 entity 频次
    mentions = sum(1 for m in chat_history if target_ts_code in m.content or target_name in m.content)
    f["entity_density"] = min(mentions / 3.0, 1.0)
    # F3. Explicit 触发词
    KW = {"尽调", "深度分析", "详细看看", "全面研究", "深入研究", "做个调研"}
    f["explicit_intent"] = 1.0 if any(k in m.content for m in chat_history[-3:] for k in KW) else 0.6
    # F4. Internal contradiction
    f["no_contradiction"] = 0.3 if _has_contradiction(extracted.discussion_focus) else 1.0
    # F5. User 明确点了 escalate 按钮
    f["explicit_confirm"] = 1.0 if user_confirmed_escalation else 0.7
    return sum(f.values()) / len(f)
```

#### Step 3: 取 min

```python
def compute_confidence(extracted, chat_history, ts_code, target_name, confirmed) -> float:
    llm = _LLM_CONF_MAP[extracted.llm_self_confidence]
    det = compute_deterministic_confidence(extracted, chat_history, ts_code, target_name, confirmed)
    return min(llm, det)
```

**取 min 而不是 avg/max 的理由**: 任一层 doubt 就 doubt(保守 fail-safe,金融场景对)。

#### Step 4: Threshold 0.7 + calibration

- v0 默认 `ESCALATION_CONFIDENCE_THRESHOLD=0.7`(env var)
- Dogfood 阶段记录 (confidence, downstream_quality) pair(downstream proxy = critic factuality + insight 分)
- 跑 ROC 找肘部点,调阈值
- 参考 [[c5-plan5-cost-optimization-done]] 的 posterior calibration weekly job

### 6.7 Fallback Ladder

```
EscalationExtractor 输出
        ↓
    confidence >= 0.7 ?
        │
   yes ── 走 multi-turn prompt(完整三字段注入)
        │
   no ── fallback to 摘要(R1):
            用 LLM 把 chat 最后 3 turn 总结一段话当 user_message
        │
        ↓ (摘要 LLM 也失败 OR confidence 仍 < 0.5)
   ── fallback to form-style(走原 user_message-only path)
```

**双层 fallback** 的理由:
- 第一层(摘要)保住"chat 有信号但抽取不够准"的常见 case
- 第二层(form-style)是终极兜底 — 不让 escalation 直接 fail

## § 7 Critic 改造 + Retry Edge 重做

### 7.1 Critic 6 维(删 plan_correctness)

`critic_subgraph.py` 的 `_planner_router` 从 7 个 `Send` 降到 6 个:

```python
# 删除

```

`PlanCorrectnessScorer` 类文件保留但从 wire 中移除(留作 v1.x archive,不删源码避免 git blame 噪音)。

### 7.2 Retry Edge 重做

**删除**:`research_graph.py` 现有的 `_retry_router`(基于 `plan_correctness < 8.5` → 回 planner)

**新增**:`_writer_retry_router`(基于 `factuality < 7.0` → 回 writer)

```python
_FACTUALITY_THRESHOLD = 7.0
_MAX_WRITER_RETRY = 1  # writer retry 比 planner retry 更贵(报告生成成本高),只给 1 次

def _writer_retry_router(state: ResearchState) -> Literal["retry", "continue"]:
    if state.critic_report is None:
        return "continue"
    fact_score = state.critic_report.get_score("factuality")
    if fact_score is None:
        return "continue"
    if fact_score < _FACTUALITY_THRESHOLD and state.writer_retry_count < _MAX_WRITER_RETRY:
        return "retry"
    return "continue"
```

```
START → research_planner → data_collector → analyst → writer → critic
                                                              ↓
                                          retry(fact<7.0 且 retry<1)
                                                              ↓
                                        writer_retry_transition → writer
                                                              ↓
                                                             END
```

`writer_retry_transition` 节点把 critic 的 factuality evidence 注入 `state.writer_critic_feedback`,writer prompt 接收后重写。

### 7.3 为什么 retry edge 从 planner 移到 writer

- v0.8.5 retry 边在 planner,假设是"plan 选错了重选"。A4 下 plan 由 validator 守护,**plan 不会"选错"**(选错就 fallback SAFE_DEFAULT)
- 真正容易出错的是 writer 把数据**用歪了**(generic boilerplate / 与 input 不 differential / 引用错 chunk)
- factuality 低分恰恰是这个症状,writer retry 比 planner retry 治标治本

### 9.2 录制约束

- **temperature=0 + seed 固定** — 确保 deterministic
- **Validator retry**:为了 cassette stable,DD_PLAN_TEMPLATE 的 prompt 设计要尽量让 LLM **一次过** validator(避免每次 retry 都录入 cassette)
- **VCR cassette 顺序敏感**:维持 critic subgraph 的 `to_thread` 不 wrap 现状(注释里的血泪史保留)

### 9.3 Differential Golden 改造

v0.8.5 的 differential golden case 验证"同 ts_code 改 input → 不同 plan_id"(因为 plan 层分叉,plan 必然不同)。

A4 下 plan **必须相同**(都 hit 同一个 DD_PLAN_TEMPLATE,validator 不允许偏离)。Differential 改为验证下游:

- Analyst 的 insight weighting 差异
- Writer 的 § 6 recommendation 差异(由 Python 覆写决定,本来就 deterministic)
- LLM-as-judge 评 "客户化适配度" ≥ 0.85
