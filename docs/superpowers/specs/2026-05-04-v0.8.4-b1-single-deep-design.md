## § 1 产品定位 reframe(从 spec § 2 双重身份 → 平台 + 2 persona + 共享底座)

### 1.1 问题陈述

现有 roadmap spec § 2 把用户分成两块:

- B 端:银行公司金融部 / 信贷审批中心 / 风险管理部(假想 persona)
- C 端:个人投资者(作者本人 dogfood)

**叙事问题**:这两类用户在业务场景 / 决策影响 / 数据需求 / 输出形态 / 决策模式 / 合规约束 6 个维度完全不同。共享底座只是**技术上**成立(LangGraph + tool registry + LLM service),**产品上**讲故事时分裂 — 面试官合理质疑"你这是 banking SaaS 还是 personal finance app"。

### 1.2 业界 alternatives

- **Notion AI / GitHub Copilot 模式**:单一 persona(知识工作者 / 开发者),产品定位极聚焦
- **Bloomberg Terminal 模式**:单一专业 persona(交易员 / 投研),功能极丰富但不跨用户层
- **微信生态模式**:多 persona 多场景,但靠超级 app 覆盖叠加,不强调 unify 叙事
- **AWS / Azure 平台模式**:不绑 persona,讲"infrastructure for X"horizontal 叙事

### 1.3 我们的取舍 — 平台 + 2 persona + 共享底座

```
                ┌─────────────────────────────────────────────┐
                │   投资研究 agent 平台(共享底座 — 主角)    │
                │   planner / agent 池 / tool registry /      │
                │   memory / context / observability / eval   │
                └─────────────────────────────────────────────┘
                           ↑                       ↑
                共享相通                   共享相通
                           │                       │
              ┌────────────┴───────┐  ┌────────────┴───────┐
              │ Persona 1:        │  │ Persona 2:         │
              │ 银行私行客户经理 │  │ 散户投资者         │
              │ (假想 banking)    │  │ (作者本人 dogfood) │
              ├────────────────────┤  ├────────────────────┤
              │ 主用:             │  │ 主用:             │
              │  ・B-1 重仓股尽调 │  │  ・C-1~C-7 短对话  │
              │  ・B-3 客户预警  │  │  ・C-4 持仓分析    │
              │  ・B-7 追问报告  │  │ 次用:             │
              │ 次用:             │  │  ・B-1 重仓股深调 │
              │  ・C 端 chat 协助│  │  ・B-3 持仓预警   │
              │   写客户简报      │  │   (个人组合视角)  │
              └────────────────────┘  └────────────────────┘
```

**核心叙事**:"投资研究 agent 平台,服务两类用户 — 银行私行客户经理(假想 banking persona)做投资标的尽调 + 客户持仓监控 + 客户追问;散户投资者(作者本人)dogfood 短对话 + 个人持仓监控。两类用户共享同一套 agent 底座,只是 use case 频次和 surface 不同。"

**对比之前 v option(单一私行 persona unify)**:reframe 不假装散户作者就是私行经理,承认两个真实 persona,但保留共享底座叙事。诚实性更高,简历讲故事时面试官不容易戳穿。

### 1.4 量化评估方案

定性评估:
- 面试 mock 测试 — 找 2-3 个朋友扮演面试官,分别用 v 单一 persona 和本 reframe 讲项目,记录被质疑的次数
- 简历 bullet 重写后,投递 5-10 家公司,收到面试邀请率作为间接信号

不强求量化(产品定位是主观叙事,不是 metric-driven 决策)。

## § 2 v0.8.4 Scope:B-1 Single Deep

### 2.1 问题陈述

按原 roadmap § 9,v0.8.4 是"D2 本地化 + D6 评测升级",工期 2.5 周。D2 已 dropped(2026-05-04,本地硬件受限),原计划缩为 D6 单做。

但 brainstorming 暴露:
- 9 个 use case 的 user journey 全部没在 spec 写过(只有 § 3 名字 + 输入输出形态四列)
- B-1 已 ship 但 backend 半装饰(Q3 audit)
- 前端无 user-discoverable 入口

**这意味着 D6 评测的 SUT(ResearchAgent)本身还有大问题,直接做 D6 是给半成品做评测**。

### 2.2 业界 alternatives(scope 切分)

- **a. 8 use case 全部端到端 polish**:4-6 周,roadmap 大改
- **b. B-1 + B-3 + C-1 三个 deep,其余 5 个轻入口**:2 周
- **c. 5 个 deep + 3 个轻**:3-4 周
- **d. 8 个全部"轻" entry 化**:1.5-2 周
- **e. B-1 single deep**(本 spec 选)— 一个 use case 极致 polish,其余 follow B-1 模板分批做:3-3.5 周

### 2.3 我们的取舍 — e (B-1 single deep)

理由:
1. **一个做扎实 > 9 个铺面表层** — Q3 audit 揭示"B-1 表面 ship 但 backend 装饰",同样问题在 B-3/B-7/C-x 大概率重复;先把 B-1 做到"输入字段真驱动 backend prompt + differential golden case 可证明"再 follow 模式做其他更稳
2. **B-1 是 banking 旗舰** — 跟简历"banking persona + 投研 copilot"叙事最对口
3. **B-1 物理形态对两个 persona 都有价值** — 私行客户经理用("客户重仓股尽调")+ 散户用("我的重仓股深度调研"),共享底座叙事天然
4. **跟 D6 自然 unblock** — 做 B-1 deep 时同步设计 differential golden case(改 input → 输出应该显著不同的对比测试),这正是 D6 的 SUT input

### 2.4 量化评估方案

v0.8.4 ship 完成定义:
1. B-1 (改名后 InvestmentDueDiligenceReport)backend 5 agent prompt 全部 condition on 6 input 字段,differential golden case 验证 ≥3 case(同 ts_code,改 `investment_objective` / `investment_horizon` / `risk_tolerance`,LLM-as-judge 评分 "loan-context appropriateness" ≥ 0.85)
2. Frontend `/research` 路由 + B-1 表单页 + 流式 progress UI + 报告渲染 + 错误兜底,从 landing 可 discover,从浏览器跑通端到端
3. Test:528 → ≥540 passed(B-1 e2e cassette 重录 + 新增 3 differential golden + frontend smoke);mypy 0 errors;ruff 全通
4. 无 LLM cost regression(单次 B-1 run cost ≤ 当前 baseline + 20%)
5. dogfood 跑 ≥10 个真实标的,作者主观 review report quality 改进显著

## § 3 B-1 Schema 重新设计:InvestmentDueDiligenceReport

### 3.1 问题陈述

v0.8.2 ship 的 `CreditInvestigationReport`:

- schema 命名"信贷视角",reframe 后两个 persona 都用"投资视角"更合适
- § 6 字段(`decision: approve|reject` / `recommended_credit_limit` / `recommended_term` / `recommended_rate_range` / `guarantee_requirements`)是放贷决策字段,reframe 后应该是投资建议字段
- `decision` 字段命名违规 — AI 在金融场景输出"决定"是合规红线,应该是 "recommendation"
- 缺 `disclaimer` 固定字段 — 监管对 AI 在金融的使用要求"辅助 + 可追溯 + 人决策",必须显式免责

### 3.2 业界 alternatives

schema 设计:

- **保持 `CreditInvestigationReport` 名字 + 改字段语义**:破坏向后兼容性又不解决叙事
- **拆 2 schema**(banking / retail 各一)— 工程量翻倍且失去共享底座叙事
- **改名 `InvestmentDueDiligenceReport` + 字段重新设计**(本 spec 选)— 单一 schema 服务两个 persona,叙事和工程都简化

字段命名:

- `decision` → `recommendation`(banking 出身的用户立刻 get 命名严谨度)
- `recommended_target_price` → `estimated_target_price_range`(estimated 后缀降权,合规更安全)
- recommendation 5 档(buy / overweight / hold / underweight / sell)对齐卖方研报标准化术语

### 3.3 我们的取舍 — 完整 schema diff

主类:

```python
class InvestmentDueDiligenceReport(BaseModel):
    # 主键 + snapshot
    target_name: str                      # 标的全称
    target_ts_code: str                   # 600519.SH 等
    request_id: str
    generated_at: datetime
    target_close_price_at_gen: float      # 新增:生成时收盘价
    target_market_cap_at_gen: float       # 新增:生成时总市值

    # 6 sections
    target_overview: TargetOverview              # § 1 (改名 from CompanyOverview,加估值快照)
    legal_qualification: LegalQualification      # § 2 (保留)
    financial_analysis: FinancialAnalysis        # § 3 (改投资视角,加 valuation_analysis)
    industry_analysis: IndustryAnalysis          # § 4 (保留)
    risk_assessment: RiskAssessment              # § 5 (改投资视角风险维度)
    investment_recommendation: InvestmentRecommendation  # § 6 (大改 from CreditRecommendation)

    # 新增免责
    disclaimer: str = DEFAULT_DISCLAIMER  # 固定字段,值见 § 3.4
```

§ 6 InvestmentRecommendation 完整定义:

```python
class InvestmentRecommendation(BaseModel):
    narrative: str
    recommendation: Literal[
        "recommend_buy",         # 买入
        "recommend_overweight",  # 增持
        "recommend_hold",        # 持有
        "recommend_underweight", # 减持
        "recommend_sell",        # 卖出
    ]
    recommended_position_size_pct: float        # % of client_total_aum
    recommended_holding_period: Literal["short_term", "medium_term", "long_term"]
    recommended_entry_price_range: PriceRange   # {low, high}
    recommended_stop_loss_price: float
    estimated_target_price_range: PriceRange    # 注意:estimated 后缀降权
    position_management_conditions: list[str]   # 加仓 / 减仓 触发条件
    evidence: list[str] = Field(min_length=1)
```

§ 1 ~ § 5 字段调整(节选关键):

- § 1 `TargetOverview` 加:`current_pe`, `current_pb`, `current_market_cap`, `dividend_yield`(估值快照)
- § 3 `FinancialAnalysis` 加:`valuation_analysis`(PE/PB 历史百分位 / DCF / 同业对比);视角换"盈利质量 / 成长性 / 投资回报 / 现金流"
- § 5 `RiskAssessment` 加:`market_risk`(beta / 流动性) / `growth_risk`(成长不达预期) / `event_risk`(黑天鹅) / `valuation_risk`(估值过高);overall_risk_level 保留 4 档

### 3.4 disclaimer 文本(固定)

```
本报告由 AI 模型(LLM)基于截至 {generated_at} 的公开数据辅助生成,仅供客户经理参考,不构成投资建议或具体买卖指令。投资决策应由客户经理结合客户具体情况及最新市场状况审慎判断。模型可能存在数据滞后、推理偏差或表述不准确的情况,使用前请验证关键数据的真实性。市场有风险,投资需谨慎。
```

### 3.5 量化评估方案

- Schema validation:Writer 输出 100% 符合 Pydantic schema(强制)
- 必填字段完整率:≥95%
- 字段命名 audit:无 `decision` / `approve` / `reject` 等放贷术语遗留(grep 验证)
- 兼容性:旧 cassette `test_b1_maotai_credit_report_cassette.yaml` 必须重录(已知 blast radius,见 `feedback_account_migration_blast_radius`)

## § 4 B-1 5 维 user journey

### 4.1 维度 1 — Entry point

**决策**:**D'(独立 `/research` 路由 + 客户列表入口 + B-1 表单页)**

- 新建 `/research` 路由 + B-1 表单页(`pages/research/b1-due-diligence.tsx`)
- 入口路径:landing 增加"投资标的尽调"卡片(私行 persona)+ chat 内"切换到 B-1 深度尽调"快捷按钮(散户 persona);两条 path 都到 `/research`
- 提交后跳 `/research/:id` 显示流式过程 + 最终报告
- `/research`(无 id)同时是历史列表页(按时间倒序展示所有 run,字段:ts_code / 标的名 / 生成时间 / TL;DR 截断)

理由:表单字段化输入比自由文本可控;`/research/:id` 可分享 / 可历史;跟 D6 SUT 直接对应。

### 4.2 维度 2 — Input form

**决策**:**6 字段 form**

| 字段 | 类型 | 必填 | 驱动 backend agent |
|---|---|---|---|
| `target_ts_code` | str (autocomplete from tushare basic API) | ✓ | DataCollector |
| `client_total_aum` | float CNY | ✓ | Writer § 6 仓位 base |
| `client_existing_position` | float CNY | ✗ | Writer § 6 加 / 持 / 减视角 |
| `investment_objective` | enum: capital_preservation / stable_growth / balanced / aggressive_growth | ✓ | Planner + Analyst |
| `investment_horizon` | enum: short_term (<6m) / medium_term (6-24m) / long_term (>24m) | ✓ | Analyst |
| `risk_tolerance` | enum: conservative / moderate / balanced / aggressive / very_aggressive | ✓ | Writer § 6 保守度 |

backend `ResearchRequest` 同步加结构化字段(原 `user_message: str` 保留,作为可选自由文本补充)。

理由:解决 Q3 audit 揭示的 "3 字段半装饰" 问题 — 6 字段每个都 explicitly 驱动某个 agent prompt,且每个都有 differential golden case 验证。

### 4.3 维度 3 — In-progress UI

**决策**:**C2(双栏 + 可折叠侧栏)**

- 主区:流式 markdown 增量(SSE event `report_chunk` → 实时拼接报告)
- 侧栏(可折叠):
  - 5-agent 状态条(pending / running / done / degraded / failed,每 agent 一行)
  - cost / latency live 数字(已用 ¥ / 已用秒)
  - Critic score 出来后显示 5 维分数 + total

SSE event 分发 mapping:`plan` → 侧栏 plan 摘要 / `data_progress` → 侧栏 tool 进度 / `insight` → 侧栏 insight 列表 / `report_chunk` → 主区 markdown 增量 / `critic_score` → 侧栏分数 / `done` → 整体完成态 / `error` → error banner

理由:portfolio 故事力最强(同时秀流式 + multi-agent + observability);用户有内容可读不无聊;现有 `pages/chat/component/research-detail/` 4 tabs 组件可演化复用。

### 4.4 维度 4 — Output rendering

**决策**:**D(混合 layout)**

- 顶部:**TL;DR 30 秒摘要**(2-3 句话核心结论 + recommendation tag + 仓位建议数字)+ disclaimer banner
- 主区:6 sections 长滚动 + 章节锚点
- 左侧 sticky:outline 导航(§ 1-§ 6 跳转)
- 右侧 collapsible:evidence list(展示 chunk_id + 原文 snippet);跟正文 inline footnote 编号联动(点击编号高亮侧栏对应 chunk)
- 底部固定 footer:disclaimer 完整文本(打印 / 导出时也带)
- 操作:Markdown copy 按钮 + 浏览器 Cmd+P 出 PDF;v0.8.5 加 Word / server-side PDF
- 响应式:桌面端优先,移动端 outline 折叠成顶部 dropdown

历史 / 分享:`/research/:id` 任何登录用户可访问,无加密,无失效(portfolio 阶段)

理由:TL;DR 是私行 + 散户都需要的 30 秒决策辅助;长滚动 + outline 给详读路径;evidence 侧栏直接服务 D1 强引用差异化卖点。

### 4.5 维度 5 — Error handling

**决策**:**降级优于失败 + Schema fallback markdown + Cost 硬切 + 错误透明可追**

10 类 error 场景处理决策:

| # | 场景 | 决策 |
|---|---|---|
| 1 | Form 输入校验 | antd Form validation,字段下方红字 |
| 2 | ts_code 不存在 | autocomplete 阶段 verify;backend 二次 verify 失败 fail fast |
| 3 | Tushare 数据空 | **降级继续**;§ 1/§ 3 标 ⚠;Critic 扣分 |
| 4 | Bocha 失败 | **降级继续** |
| 5 | KB 没命中 | **静默正常进行**(KB miss 是常态) |
| 6 | LLM 失败 | LLMService retry 1-2 次;fail fast;banner "本次未计费" |
| 7 | Schema validation fail | Writer retry 1 次(prompt 加错误反馈);fall back markdown-only |
| 8 | Cost budget 超限 | **fail fast**;partial 报告 + cost 透明展示 |
| 9 | SSE 网络断 | v0.8.4 不做自动重连,fail;banner 提示刷新;留 v0.8.5 做 reconnect |
| 10 | Agent crash | LangGraph 节点 try/except;run 状态 → failed;cost 已花算;"重试"按钮 |

env switch:`ERROR_VERBOSITY=verbose|friendly`(默认 verbose dogfood)

理由:degraded > fail fast 让 portfolio 系统体现"知道自己什么不行"的成熟度;cost 硬切防意外烧钱;错误透明可追便于 debug。

## § 5 Backend prompt 改造范围(Q3 audit 解决方案)

### 5.1 问题陈述

Q3 audit(2026-05-04,Explore agent 报告)揭示:v0.8.2 ship 的 B-1 backend 5 agent prompt 都不感知 input 字段(贷款金额 / 期限 / 用途),Rating 2/3 装饰性。

### 5.2 业界 alternatives

prompt 改造策略:

- **a. 单一 prompt 加 if/else**:在 system prompt 写 "if loan_purpose == 流贷 then ..." — 工程上脆弱,LLM 对 conditional logic 遵守度差
- **b. 多个 prompt 模板按 input 路由**:每种 `investment_objective` 一个 plan prompt,`investment_horizon` 切换 analyst prompt(本 spec 选)— 工程清晰,差异显式
- **c. RAG-based prompt assembly**:把 prompt 模板存 KB,按 input retrieve 拼接 — overkill 给单 use case
- **d. Fine-tune model**:不在 portfolio scope(数据量不够,YAGNI)

### 5.3 我们的取舍 — 5 agent 改造清单

| Agent | 改造内容 | 工期 |
|---|---|---|
| **Planner** | 4 个 plan 模板(对应 4 个 `investment_objective`):capital_preservation 模板偏重风险数据 / aggressive_growth 模板偏重成长数据等;Pydantic 输入加 `objective` 字段 | 1-2 天 |
| **DataCollector** | 按 plan 决定调哪些 tool;按 `target_ts_code` route(tushare / bocha / kb 各 sub-tool);保持现有并发 asyncio.gather | 1 天 |
| **Analyst** | prompt condition on `investment_horizon`(短期看技术 + 资金流;中期看基本面 + 估值;长期看赛道 + 行业地位);prompt 加 weighted instruction "对 capital_preservation 客户加权 risk insight" | 1-2 天 |
| **Writer** | 6 sections prompt 全部 condition on 6 字段;§ 6 投资建议按 `risk_tolerance` 调保守度(conservative → 更保守的 entry / stop_loss / position);按 `client_total_aum` × `recommended_position_size_pct` 算具体仓位 CNY | 2-3 天 |
| **Critic** | 加第 6 scorer "input_context_appropriateness":判断报告内容是否真针对 6 input 字段(differential),不是 generic boilerplate | 1 天 |

合计 backend 6-9 天。

### 5.4 量化评估方案

- Differential golden case:同 ts_code(茅台 600519.SH),3 组 input variation:
  1. capital_preservation + long_term + conservative(保守长期保本)
  2. aggressive_growth + short_term + very_aggressive(激进短期高成长)
  3. balanced + medium_term + balanced(平衡)
- LLM-as-judge 评分 "input_context_appropriateness":3 组报告差异显著(judge 评 ≥ 0.85)
- Critic score 第 6 维度:在所有 ≥10 个 dogfood run 上 ≥ 0.8
