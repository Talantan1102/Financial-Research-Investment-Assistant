## § 1 决策摘要

本次 brainstorming 收敛了三个核心决策,后续所有调度安排基于这三个 anchor。

### 决策 1:产品定位 = Broad(通用金融 agent 平台,投资尽调是 v1 use case)

**问题**:v0.8.4 已经把产品 reframe 为"投资尽调研报"(B-1 single deep + InvestmentDueDiligenceReport)。但作者列出的下一阶段 backlog(记忆系统 / 多 use case / session 管理 / skill 管理 / 护栏 / 自动修复)暗示的是通用 agent 平台,与窄定位有张力。

**业界 alternatives**:
- **Narrow product**(类似垂类 SaaS 路线):scope 收紧到投资尽调单一场景,横切层只做必要部分。代表:Hebbia / AlphaSense
- **Broad platform with pilot use case**(类似 LangChain + 自家 demo app):横切层做扎实,投资尽调作为首个 reference implementation。代表:LangChain + Open Devin / OpenManus
- **Vertical-first platform**(先垂直后平台):窄起步,运行 6-12 个月后水到渠成抽象。代表:大多数 startup 真实路径

**取舍**:作者明确选 broad(2026-05-05 brainstorming session,Q4 选项 B)。

**理由**:
- 作者已列出的 9 项独立模块全部是横切层组件(Memory / Trace / Session / Skill / Tool / Guardrail / Auto-repair / 多 use case / 前端),narrow 路线会浪费这些已经在脑子里成形的技术蓝图
- 求职定位是 LLM 应用算法 + infra,broad 平台路线在简历讲点上覆盖更多 infra 关键词(横切层架构 / 平台抽象 / agent runtime)
- v0.8.5 的 Skills bundle + plan_registry + ToolRegistry 在 broad 框架下天然延伸为平台横切层,而不是为单产品写的工具包,工作连续性更强

**简历叙事变化**:从"投资尽调研报 agent"变为"**通用金融 agent 平台,首个落地 use case 是投资尽调**"。短期不立刻改 README/portfolio,在 v0.9.0 ship 时统一 reframe。

**量化评估**:
- 工程量级:窄路线 1-2 个月可完成 v1.0,broad 路线需要 4-6 个月达到首个有平台感的 milestone(每天 4-5 小时 Claude Code wall time 投入)
- 简历讲点:窄路线 ~3 个亮点(单产品 + Skills + B-3 监控),broad 路线 ~7-8 个亮点(7 个横切层组件 + 多 use case + 前端架构)
- 失败风险:broad 路线最大风险是**永远在做基础设施,看不到 ship**;§ 2 milestone 设计直接缓解此风险

### 决策 2:节奏 = D(无外部 deadline,但必须设阶段 milestone 对抗"永远不 ship")

**问题**:作者非简历紧迫驱动(2026-05-05 brainstorming session,Q5 选项 D)。无 deadline 看似自由,但兴趣项目最大杀手是"做着做着永远在 spec 阶段"。

**业界 alternatives**:
- **纯兴趣节奏(无 milestone)**:做到哪算哪。失败模式 = scope creep + 永远不 ship
- **固定时间盒(每月一个 release)**:强制每个月有产出。失败模式 = 牺牲质量赶进度
- **阶段化 milestone(每 6-8 周一个有意义的 ship)**:节奏自定义但每阶段 end-state 清晰

**取舍**:阶段化 milestone。

**理由**:
- 无 deadline 不代表 scope 无限,作者在 v0~v0.8.5 已经验证"快迭代 + 阶段化 ship"的工作流非常成熟,降低节奏会让加速失效
- 阶段化 milestone 既给"看得见的进度感"(对抗动力流失),又允许每阶段时间弹性(对抗赶工)

### 决策 3:技术路线 = 路线 2(product-first)

**问题**:9 项 + 前端的实施顺序选择(2026-05-05 brainstorming session,Q6 选项)。

**业界 alternatives**(已在 brainstorming 中展开):
- **路线 1 infra-first**:先把横切层做扎实,再叠 use case + 前端。骨架强但前 2 个月没新 demo
- **路线 2 product-first**:先加 1-2 个 use case + 重构前端,横切层用最小可工作版,后面补
- **路线 3 交替式**:每阶段配一个横切 + 一个 use case 增量。节奏均匀但每阶段产出都不"完整"

**取舍**:作者选路线 2。

**理由 + 工程含义**:
- 短期能看到"看得见摸得着的产品"演进,作品感强,对抗 D 决策下"动力流失"风险
- 横切层用最小可工作版(MVP minimum viable cross-cutting layer),后续再补完整版
- 第二个 use case 即使有"复制粘贴第一个"的痕迹也可接受,作为 platform abstraction 的反面教材—— **当复制粘贴痛了再抽象**,而不是预先猜测抽象边界
- **关键:这条路线要求接受"前 2-3 个阶段横切层是债"**,不能心态崩溃。每个阶段有计划地还一部分债

## § 2 阶段化 milestone(路线 2 演进)

每个阶段 6-8 周 wall time(假设每天 4-5 小时 Claude Code 投入,周末加倍)。每个阶段必须 ship 一个有用户价值的 demo,不能纯 infra。

```
v0.9.0 ─── v0.9.x ─── v1.0.0 ─── v1.0.x ─── v1.1.0 ─── v1.x ───
   │         │         │          │           │           │
  use      前端     第二个     第三个       横切层      横切层
  case      MVP      use       use        还债-1      还债-2
  内化              case      case
```

### 阶段 1:v0.9.0 — 第一个 use case 内化(6-8 周)

**目标**:把"投资尽调"从 v0.8.5 的 plan_registry hardcode 1/4 拓展成真正完整、可 dogfood 的产品。

**内容**:
- 投资尽调 plan_registry 的另外 3 个 plan 实现(v0.8.5 只 hardcode 了 1 条主路径,其他 3 个是占位)
- 端到端 dogfood 5+ 真实股票,产出可发的研报样本
- 横切层 MVP:Trace 系统(已有 v0.8.5 雏形)+ Session 管理(单次研报 = 1 session,最简语义)

**Ship 标准**:能给非作者用户(朋友/导师)演示,5 分钟内出一份可信研报。

### 阶段 2:v0.9.x — 前端 MVP 重构(4-6 周)

**目标**:前后端配合,前端能展示 v0.9.0 内化的研报 + 历史 session 列表 + auth 改写。

**内容**(2026-05-06 brainstorm 收敛后):
- 前端死代码删除(`/chat` `/database` `/news` `/memory` 4 路由 + 对应 components / store / mock)
- 新建研报展示页(D 形态:PDF-like 长卷 + 流式 sticky progress overlay,Markdown + PDF 导出)
- 新建历史 session 列表(d 形态:antd Table + 时间分组 filter)
- /login UI 改写 + /register 新建(brand 化对开布局)
- 实施前置:本地 PG 跑起来 + CI 跑(1-2 天)+ legacy PG 加 `research_reports` 表(W2 持久化方案)

**Ship 标准**:前端跑起来不依赖 mock,后端 API 全部对得上;非作者用户能注册 + 跑 demo + 数据隔离。

**推迟到 v0.9.y**(等 DB 统一 spec ship 后):
- Trace 调试页 `/trace/:request_id`(形态已 anchor:Tree 视图 + raw payload 展开)
- 研报对比功能(multi-select + diff 视图,数据驱动等积累后)

**详细 spec**:`docs/superpowers/specs/2026-05-06-v0.9.x-frontend-rebuild-design.md`

### 阶段 3:v1.0.0 — 第二个 use case(6-8 周)

**目标**:加入第二个 use case(候选:行业研究 / 财报速读 / 概念追踪,具体看每周 dogfood 反馈倾向)。**这是平台感的第一次验证**。

**内容**:
- 选定第二个 use case 后单独 brainstorm + spec + impl

**Ship 标准**:两个 use case 都能从前端入口进入,功能可用。

### 阶段 4:v1.0.x — 第三个 use case + 复制痛点暴露(6-8 周)

**目标**:三个 use case 后,横切层债务全部暴露。这是 broad 平台的"真实压力测试"。

**内容**:

- 不抽象,继续暴露问题。在阶段末尾产出"复制痛点报告"——3 个 use case 之间到底有哪些重复

### 阶段 5:v1.1.0 — 横切层还债 round 1(8 周)

**目标**:基于阶段 4 的痛点报告,选 2-3 个最痛的横切层组件做扎实抽象。

## § 3 长程任务调度机制

### 3.1 三段式工作槽

| 槽位 | 时段 | 在场度 | 适合塞什么 | 不适合塞什么 |
|---|---|---|---|---|
| **晚上在场槽** | 19:00-23:00 | 作者全程在场 | brainstorm / dogfood / prompt 调优 / cassette 重录决策 / spec review | 纯样板代码(浪费在场时间) |
| **白天异步槽** | 09:00-18:00 | 作者不在 | implementation(plan 已定的 task)/ spec 草稿扩写(brainstorm 已完成)/ legacy cleanup / 文档刷新 | brainstorm / dogfood / 决策类任务 |
| **睡前无监督槽** | 23:00-09:00 | 完全无人 | cassette 批量重录 / golden case 跑批 / benchmark eval / nightly CI | 任何决策类、写代码类 |

### 3.2 槽位之间的 pipeline 依赖

```
晚上 brainstorm  ──→  晚上 spec  ──→  白天 plan/spec 扩写  ──→  白天 impl  ──→  晚上 dogfood/调优  ──→  睡前 cassette 重录
```

**关键约束**:**白天异步槽的原料 = 晚上已经 brainstorm/spec 完成的 epic**。库存不够白天就跑不起来。

### 3.3 库存管理(防止白天空转)

**库存指标**:`spec 已写 / plan 已写 / 还没 impl 的 task 数`

**水位线**:
- 库存 ≥ 3 个 task:白天槽满载(早上启动一个,中午启动一个,下午做 cleanup)
- 库存 1-2 个 task:白天槽部分用 + 部分跑过渡活
- 库存 0:白天槽全部跑过渡活(见 § 4)

**库存补充**:每个晚上槽必须产出至少 1 个新 spec/plan 进入库存。

### 3.4 风险控制

- **白天 PR 不自动 merge**:Claude 白天产出 PR 全部 draft,作者晚上 review/merge,失败 PR 第二天白天可以基于反馈重写
- **白天槽出错回退**:遇到决策类问题(typing 不确定 / schema 设计有疑问 / mock 行为不一致),白天槽必须**停下并写诊断报告**,不自作主张推进。作者晚上回来根据诊断决策
- **睡前无监督槽兜底**:每个睡前 task 必须有"失败时不破坏现有状态"的保证(只产生 artifact,不修改 main code)

## § 4 过渡期(前 2-4 周)白天槽安排

阶段 1 (v0.9.0) 的 brainstorm 还没做,库存为 0。前 2-4 周白天槽必须跑过渡活,不能空转也不能违反 D 决策强行推 v0.8.5+ 的事。

**优先级排序**:
1. **portfolio/简历 reframe 文档草稿**(对应决策 1 的简历叙事变化):从"投资尽调"→"平台 + use case 1"的 narrative 改写。Claude 白天写草稿,作者晚上 review。低风险高产出,且为后续作品集输出做准备
2. **legacy cleanup**:grep 死代码 + 未引用模块 + README 漂移修复。memory `feedback_legacy_barrel_eager_import_rot` 提示 legacy barrel 是 import chain rot 主犯,可顺势清理
3. **CI / dev 体验**:nightly job 优化、permission settings 整理、test infra 边角(memory `feedback_serve_path_no_ci_coverage` 提示 serve path 没 CI 覆盖)
4. **提前 spec 草稿**:阶段 1 (v0.9.0) brainstorm 完成后,白天 Claude 扩写 spec 细节(此时已经从过渡期切换到正式调度)

**过渡期 ≠ 没产出**。这些活每个都对项目长期有用,且都符合"低风险无人值守"标准。

## § 5 明确不做的事(scope 边界)

为对抗 broad 路线下"什么都想做"的陷阱,明确以下事项**不在 v0.9~v1.x 内**:

- **D2 本地化(本地 LLM + BGE)**:硬件受限,memory `project_v1_d2_dropped` 已记录。简历仍保银行 persona,但实施留 protocol 接口口子,v1.x 之后再说
- ~~**多用户 / 权限系统**:作者本人 dogfood 已足够,假设未来 v1.x 加一个 admin token 即可~~ **已修正(2026-05-06 brainstorm)**:保留基础多用户隔离 + 简单 username/password auth(不做 OAuth/SSO/RBAC/邮箱验证/密码找回)。理由:简历 demo 给朋友/面试官时,每个用户记录隔离;banking persona 也期待基础多用户能力。详见 `2026-05-06-v0.9.x-frontend-rebuild-design.md` § 6
- **生产部署 / SLA**:个人作品,不做高可用 / 多区 / 监控告警体系。Trace 系统是 debug 工具不是 SRE 工具
- **训练 / fine-tune**:全部用 API LLM,不进 fine-tune 任何模型(即使 portfolio 角度有讲点,工程量不匹配本路线)
- **移动端**:前端 MVP 只做 web,不做 mobile responsive(可以"不挂"但不专门优化)
