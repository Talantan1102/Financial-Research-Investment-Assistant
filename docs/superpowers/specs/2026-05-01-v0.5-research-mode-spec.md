## 0. 文档定位

### 为什么独立成 spec(而非内嵌 v0)

v0 chat agent skeleton 验证了"双模式共享底座"中的**对话模式**:LangGraph 状态图 + Typed Actor agents + ToolRegistry + EvalRunner SUT swap 全部跑通。**v0.5 是同一底座上的第二个 SUT —— 研报模式**,验证这套架构能不能扩展到"多 agent + parallel sub-agent dispatch"形态。

独立成 spec 的理由:
- **形态差异显著** —— 对话(2 agent 串行)vs 研报(5 agent + nested parallel dispatch),HTTP 契约 / Memory 需求 / eval 维度都不同
- **故事点不同** —— v0 是"agent 编排 baseline",v0.5 是"first real DispatchSubAgent + agent swarm consensus"
- **Plan B/C/D 横切契约的二次验证** —— 第一次(v0 chat)证明可用,第二次(v0.5 research)证明可扩展。两次足以让招聘官信"这个 protocol 不是 over-fit 一次性的"

## 2. 决策一:5-agent pipeline 范围(scope)

### ① 问题陈述

brainstorming 提出 5 个 agent(Planner / Collector / Analyst / Writer / Critic),但**到底全做还是分批做**?Critic 是最复杂的(5 维并行 + DispatchSubAgent 首次真启用),拆出去做单独 spec 也合理。

### ② 业界 alternatives

| 编号 | 形态 | 代价 / 收益 |
|---|---|---|
| **SC1. 全 5 agent + Critic DispatchSubAgent + 输出格式**(选) | 5-6h impl;portfolio 最强;Critic 调度复杂可能撞坑 |
| SC2. 4 agent(无 Critic) | 3-4h impl;Critic 留 v0.6;DispatchSubAgent placeholder 浪费 |
| SC3. 3 agent(无 Critic + DataCollector 拆出去) | 2-3h impl;故事点弱;两个 spec 才能讲清楚研报模式 |

### ③ 选择:**SC1 全 5 agent + Critic DispatchSubAgent**

**理由**:
- v0 spec 明确写"DispatchSubAgent 留 v0.5 启用",推迟 = 浪费 placeholder 信号
- 5-agent + nested dispatch 是业界 multi-agent 系统的典型形态(supervisor / worker / critic 三角),portfolio 故事密度最高
- v0 已为 v0.5 准备齐 enabler:SUT swap / SqliteSaver / ToolRegistry / Plan B Judge 模式
- 时间预算:同 v0 节奏(spec → plan → impl 3 天)

### ④ 量化评估方案

- **Agent 数量**: 5(spec § 1 已固定)
- **Sub-agent 数量**:Critic 内部 5 个评分 sub-agent
- **总 LLM 调用**: 单次研报请求 ≈ 1(planner) + 0(collector 调 tool 不直接调 LLM) + 1(analyst) + 1(writer) + 5(critic 5 维并行) = **8 次 LLM 调用**
- **单次研报 cost**: deepseek-v4-flash @ ~¥0.001 / call × 8 = **~¥0.008-0.012 / 研报**
- **单次研报 latency**: 串行 P50 = 1.5s × 4(planner→analyst→writer→critic 启动)+ 并行 P50 = 1.5s(critic 5 维并行 = max,不是 sum) ≈ **7.5-9s**

### ⑤ 风险

- **Critic subgraph + Send API 是 v0.5 第一次真用**(Spike 2 验证基本 LangGraph API 但 Send API 没动过)→ plan 阶段嵌一个 30s spike 验证 Send + reduce 语义
- **5 agent 串行 latency** 可能触发用户感知延迟(>5s);v0.5 SSE 进度事件流缓解(每 agent 完成发一个 progress event)

## 3. 决策二:LangGraph 拓扑形态

### ① 问题陈述

5 个 agent 的执行流程,**用什么 graph 拓扑**?扁平 5 节点 + Critic 内部异步调度?全 subgraph 组合?混合?

### ② 业界 alternatives

| 编号 | 形态 | 代表 |
|---|---|---|
| GT1. 单 mega-graph(扁平 5 节点) | Critic 内部用 `asyncio.gather` 调 5 sub-agent;LangGraph 看到的图是 5 节点 |
| GT2. 全 subgraph 组合 | 每个 agent 都是子图;Critic_sg 用 LangGraph Send API fan-out;LangChain Anthropic Cookbook research agent 走这条 |
| **GT3. 混合**(选) | Top graph = 5 扁平节点;只有 Critic_node 是 subgraph,内部用 Send API fan-out parallel scoring;LangGraph 官方 multi-agent example(supervisor + worker)走这条 |

### ③ 选择:**GT3 混合拓扑**

**Top-level graph(5 节点)**:
```
START → research_planner_node → data_collector_node → analyst_node → writer_node → critic_node → END
```

**Critic 内部 subgraph(LangGraph Send API)**:
```
critic_entry
    ├── Send(factuality_score_node, state)
    ├── Send(coverage_score_node, state)
    ├── Send(insight_score_node, state)
    ├── Send(structure_score_node, state)
    └── Send(conciseness_score_node, state)
        ↓ (LangGraph 自动 reduce,5 个 score 收敛到 critic_aggregate_node)
critic_aggregate_node → 返回 CriticReport
```

**理由**:
- v0 已经验过 LangGraph 1.x 基础 API + SqliteSaver,但 **Send API 没用过**;v0.5 Critic 是引入 Send API 的合理点位(局部学习,风险可控,Task 0 spike 验证)
- 4 个简单 agent(Planner/Collector/Analyst/Writer)硬塞 subgraph 是过度设计;它们就是 1 节点
- Critic 才是真正"扇出 + 收敛"的形态,subgraph + Send 在这里有真实表达价值
- Trace 可视化:Critic subgraph 让 5 维评分的 LLM 调用都挂在 subgraph trace 下,debug 友好

### ④ 量化评估方案

- **图节点数**:top 5 + critic subgraph 7(entry + 5 scoring + aggregate) = **12 节点**(可手画一图)
- **Send API 并行度**:5 个 sub-agent 并行,P50 latency ≈ 1.5s(等于单个 sub-agent latency,不是 sum)
- **Critic 序列化开销**:Send API reduce 阶段,LangGraph 自动 collect 5 个 sub-agent 返回 → critic_aggregate_node 拿到 list[CriticDimensionScore] 时 ≤ 100ms
- **Resume 正确性**:研报到 Critic 阶段中断,从 SqliteSaver checkpoint 恢复后,继续跑剩余维度评分(LangGraph subgraph 也支持 resume,L2 测试覆盖)

### ⑤ 风险

- **Send API 学习曲线**:Task 0 spike 1 ≤ 60s,验证 5-fan-out / reduce 行为(参考 v0 Spike 2 pattern)
- **Critic subgraph state 模式**:subgraph 状态隔离 vs 与外层 state 共享,Send API 默认行为需 spike 确认

## 4. 决策三:Critic 5 维度并行评分 + DispatchSubAgent 真启用

### ① 问题陈述

Critic 是 v0.5 的故事核心。**怎么落地 5 维度评分?**`DispatchSubAgent` 接口在 v0 是 placeholder,这次怎么真用?

### ② 业界 alternatives

**评分维度数量**:
| 编号 | 维度数 | 代价 |
|---|---|---|
| DM1. 3 维 | 简单,故事点弱 |
| DM2. 4 维(对齐 Plan C Judge) | 居中 |
| **DM3. 5 维**(选) | 故事点最强,5 个 LLM call 并行 cost ≈ ¥0.005 |
| DM4. 6+ 维 | 维度噪音(insight vs coverage 易混淆),诊断信号下降 |

**DispatchSubAgent 机制**:
| 编号 | 形态 | 代价 |
|---|---|---|
| **DS1. 构造时注入**(选) | `Critic(llm, sub_agents=[FactualityAgent(...), ...])`;清晰可测;Plan B/C/D DI 风格延续 |
| DS2. 全局 Registry | `SubAgentRegistry.register(...)` 在 app 启动时注册;有 mutable global state,测试间易污染 |
| DS3. classmethod 工厂 | `Critic.with_default_dimensions(llm)`;太隐式,扩展性差 |

### ③ 选择:**DM3 5 维 + DS1 构造时注入**

**5 个评分维度**:
| 维度 | 评分目标 | 评分依据 |
|---|---|---|
| `factuality` | 数据点是否准确 | 对照 DataCollector 收集到的原始数据 |
| `coverage` | 是否覆盖 ResearchPlanner 提出的子任务 | 对照 ResearchPlan.subtasks |
| `insight` | 分析深度(不只数据陈列) | LLM-judge 评估"这段话是分析还是流水账" |
| `structure` | 章节逻辑 / 引用 / markdown 格式正确性 | 内置 checklist + LLM-judge |
| `conciseness` | 长度合理 / 无冗余 | 字数 + LLM-judge"是否啰嗦" |

**Sub-agent 实现**(`backend/app/agents/critic_subagents/`):
```python
class FactualityScorer(Agent):
    name = "FactualityScorer"
    model_tier: Tier = "fast"

    def step(self, state: ResearchState) -> StepResult:
        prompt = build_factuality_prompt(state.report_markdown, state.tool_results)
        r = self._llm.chat(prompt=prompt, tier="fast", request_id=state.request_id)
        score = _parse_dimension_score(r.content)  # CriticDimensionScore Pydantic
        return StepResult(state_update={"factuality_score": score}, span_metadata={...})
```

        ...

    def dispatch_subagent(self, name: str, state: ResearchState) -> StepResult:
        """v0 placeholder 在这里被 override 为真实现 — 直接调用 self._scorers 中名字匹配的 sub-agent。"""
        target = next((s for s in self._scorers if s.name == name), None)

**Aggregate 阶段**(`critic_aggregate_node`):
- 收集 5 个 `CriticDimensionScore`
- 计算 `overall_score = mean(scores)`
- 输出 `CriticReport(dimensions: list[CriticDimensionScore], overall_score: float, summary_markdown: str)`

### ④ 量化评估方案

- **5 个 sub-agent 并行 latency**:max(5 LLM call) ≈ 1.5s
- **Sub-agent cost**:5 × deepseek-v4-flash ≈ ¥0.005 / 次评分
- **DispatchSubAgent placeholder 真启用**:v0 base.py 的 `NotImplementedError` 在 Critic 中被 override(L0 测试验证 placeholder→real 转换)
- **可扩展性**:加 1 个新维度 = 加 1 个新 Scorer subclass + 1 行 `Critic(llm, scorers=[..., NewDimScorer()])`,zero core code change(L1 测试验证)

### ⑤ 风险

- **维度间评分一致性**:同一份研报的 5 维评分可能冲突(structure 高 + insight 低)。v0.5 不解决,**aggregate 时记 metadata** 让分析时可见
- **Scorer 提示词一致性**:5 个 prompt 风格不统一会引入评分 bias;v0.5 plan 阶段提供共享的 `_BASE_SCORER_TEMPLATE`,各 Scorer 只填充各自评分维度的 rubric

## 5. 决策四:Agent I/O 契约扩展

### ① 问题陈述

v0 已经定义了 `Plan` / `ToolCall` / `ToolResult` / `GraphState`(对话场景)。研报场景需要新的 schema。**怎么扩展才不破坏 v0?**

### ② 选择:**附加新 schema,不动 v0 旧 schema**

**新增 schemas**(`backend/app/agents/schemas.py` 扩):

```python
class Subtask(BaseModel):
    """ResearchPlanner 输出的子任务。"""
    model_config = ConfigDict(frozen=True)

    subtask_id: str           # e.g. "stock_overview" / "financial_health"
    description: str
    required_tools: list[str] # 推荐工具,DataCollector 参考但可扩
    rationale: str


class ResearchPlan(BaseModel):
    """ResearchPlanner 输出。"""
    model_config = ConfigDict(frozen=True)

    subtasks: list[Subtask]
    target_entity: str        # e.g. "600519.SH"
    research_style: Literal["concise", "comprehensive"]  # v0.5 内部固定 comprehensive,留扩展
    reasoning: str


class Insight(BaseModel):
    """Analyst 输出的单个分析洞察。"""
    model_config = ConfigDict(frozen=True)

    subtask_id: str           # 关联回 Subtask
    finding: str              # 1-2 句话总结
    supporting_data: list[dict[str, Any]]  # 来自 tool_results 的 cite
    confidence: Literal["high", "medium", "low"]


class CriticDimensionScore(BaseModel):
    """单维度评分。"""
    model_config = ConfigDict(frozen=True)

    dimension: Literal["factuality", "coverage", "insight", "structure", "conciseness"]
    score: float = Field(ge=0.0, le=10.0)
    evidence: str             # 1-2 句话支持依据
    sub_agent_request_id: str # trace 反查用


class CriticReport(BaseModel):
    """Critic 聚合输出。"""
    model_config = ConfigDict(frozen=True)

    dimensions: list[CriticDimensionScore]   # 长度恒等于 5
    overall_score: float = Field(ge=0.0, le=10.0)  # mean of dimension scores
    summary_markdown: str    # 1-2 段话总结,可能附在研报末尾


class ResearchState(BaseModel):
    """LangGraph 研报状态(类比 v0 GraphState)。"""
    model_config = ConfigDict(arbitrary_types_allowed=True)

    # 入参
    user_id: str
    session_id: str
    user_message: str       # 原始用户研报需求
    request_id: str

    # ResearchPlanner 输出
    plan: ResearchPlan | None = None

    # DataCollector 输出
    tool_results: list[ToolResult] = Field(default_factory=list)  # 复用 v0 schema

    # Analyst 输出
    insights: list[Insight] = Field(default_factory=list)

    # Writer 输出
    report_markdown: str | None = None

    # Critic 输出
    critic_report: CriticReport | None = None

    # 横切
    span_stack: list[str] = Field(default_factory=list)
```

### ③ 量化评估方案

- **Schema 稳定性**:`Subtask` / `ResearchPlan` / `Insight` / `CriticReport` / `ResearchState` 字段在 v0.5~v1 不删除/不改名(同 v0 契约期)
- **Pydantic 验证开销**:`ResearchPlan.model_validate(...)` ≤ 1ms(L0 测试)
- **mypy strict 覆盖**:延续 `app.agents.*` strict tier

## 6. 决策五:研报输出格式

### ① 问题陈述

Writer 输出什么形态?纯 markdown?HTML?富文本嵌入图?

### ② 业界 alternatives

| 编号 | 形态 | 代价 |
|---|---|---|
| OF1. 纯 markdown text | 简单,无图 |
| **OF2. Markdown + chart placeholder**(选) | `![chart_id](chart://chart_id)` 占位符,真渲染留 frontend |
| OF3. HTML 直接生成 | LLM 生成 HTML 易出 invalid markup;不利于后续编辑 |
| OF4. 富文本 JSON(类似 Notion blocks) | 太复杂,前端需要专门 renderer |

### ③ 选择:**OF2 Markdown + chart placeholder**

**格式约定**:
- Writer 输出 `report_markdown: str`
- 普通 markdown 元素(标题 / 列表 / 表格 / 引用块)直接用
- 图占位符:`![描述](chart://{chart_id})`,其中 `chart_id` 是 Writer 自己分配的 UUID
- Writer 内部维护 `chart_specs: list[ChartSpec]`(chart_id + 数据 + 图表类型)输出在 `state.chart_specs`(v0.5 不渲染,只产出规格)
- 前端拿到 markdown + chart_specs,自己根据 chart_id 渲染(留 v0.6 frontend spec 实施)

**ChartSpec schema**(预留):
```python
class ChartSpec(BaseModel):
    model_config = ConfigDict(frozen=True)
    chart_id: str
    chart_type: Literal["line", "bar", "pie", "table"]
    title: str
    data: list[dict[str, Any]]  # 表格化数据
    x_axis: str | None = None
    y_axis: str | None = None
```

### ④ 量化评估方案

- **Markdown 输出长度**:研报 ~1500-3000 字(综合财务 + 行情 + 行业);单次 deepseek-v4-flash 输出 max_tokens 约 4000,一次出完
- **chart placeholder 数量**:典型研报 2-4 个图(K 线 + 财务趋势 + 估值对比),`chart_specs` list 长度对应
- **Markdown 解析正确性**:GitHub-flavored markdown,L1 测试用 `markdown` 库 parse → 无 unclosed tag(防 LLM 输出错语法)

### ⑤ 风险

- **图占位符冲突**:用户消息中含真 markdown 图片 `![](http://...)` 时不能误认成 chart placeholder。约束:placeholder 使用 `chart://` scheme(自定义),与标准 URL 区分

## 8. 决策七:Memory 范围

### ① 问题陈述

研报跨多分钟,**用户中断后能不能续跑?需要 Semantic Memory 吗?**

### ② 选择:**仅 LangGraph SqliteSaver checkpointer,Semantic 留 v1+**

**接入点**:`build_research_graph(...)` 调用 `SqliteSaver(...)`,`thread_id = f"research:{user_id}:{request_id}"`(注意:对话用 `chat:{user_id}:{session_id}`,前缀区分两种 graph)

### ③ 量化评估方案

- **Resume 正确性**:同 thread_id 第二次请求,LangGraph 自动从最后一个 checkpoint 续(L2 测试覆盖)

- **Storage 增长**:单研报请求 ~6 checkpoint write × ~2KB ≈ 12KB / 请求;100 用户 × 5 研报 = 500 请求 ≈ 6MB,可接受

## 9. 决策八:HTTP 路由形态

### ① 问题陈述

研报模式怎么发起?复用 `/api/v0/chat` 还是新 endpoint?

### ② 选择:**新 endpoint `POST /api/v0.5/research`**

**理由**:研报 vs 对话**产品形态完全不同**:
- 研报:单次长流程(7-9s),需要进度反馈(每 agent 完成一次 progress event)
- 对话:多轮短交互,需要 token 流

**HTTP 契约**:
```python
class ResearchRequest(BaseModel):
    target_entity: str         # e.g. "600519.SH" 或 "新能源行业"
    user_message: str          # 用户研报需求,e.g. "深度分析茅台基本面"
    research_style: Literal["concise", "comprehensive"] = "comprehensive"  # v0.5 占位


@router.post("/api/v0.5/research")
async def research(
    req: ResearchRequest,
    user: User = Depends(get_current_user),
    research_graph: CompiledStateGraph = Depends(get_research_graph),
) -> StreamingResponse:
    return StreamingResponse(
        _stream_research(req, user, research_graph),
        media_type="text/event-stream",
        headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"},
    )
```

**SSE 事件类型**(类比 v0 chat 的 6 种,研报场景定 7 种):
```python
class ResearchStreamEvent(BaseModel):
    type: Literal[
        "plan",          # ResearchPlanner 完成,数据 = ResearchPlan
        "data_progress", # DataCollector 每个 tool call 完成,数据 = ToolResult
        "insight",       # Analyst 完成,数据 = list[Insight]
        "report_chunk",  # Writer 流式产出 markdown 片段(如果 Writer 用 streaming chat)
        "critic_score",  # 每个 Critic dimension 完成,数据 = CriticDimensionScore(5 个)
        "done",          # 全流程完成,数据 = {"request_id", "total_cost_cny", "total_latency_ms", "report_markdown", "critic_report"}
        "error"
    ]
    data: dict[str, Any]
```

### ③ 量化评估方案

- **事件粒度**:单次研报 ~30-50 SSE events
- **首事件 latency**:`plan` 事件 ≤ 2s(planner LLMService.chat P50)
- **完整研报 latency**:`done` 事件 ≤ 12s(P95;P50 ≈ 8-9s per § 2.4)

## 10. 决策九:EvalRunner 适配

### ① 问题陈述

v0.5 怎么接入 EvalRunner?Plan C/D 老测试 + v0 ChatAgent SUT 测试不能破坏。

### ② 选择:**ResearchAgent 满足 SUT Protocol(同 v0 ChatAgent 模式)**

**ResearchAgent**(`backend/app/agents/research_agent.py`):
```python
class ResearchAgent:
    """v0.5 research agent — wraps the LangGraph 研报状态图 with a SUT-friendly interface."""

    def __init__(
        self,
        graph: CompiledStateGraph,
        trace_service: TraceService | None = None,
    ) -> None:
        self._graph = graph
        self._trace = trace_service

    async def run(self, user_input: str, request_id: str) -> SUTOutput:
        config = {"configurable": {"thread_id": f"research:eval:{request_id}"}}
        initial = ResearchState(
            user_id="eval",
            session_id=request_id,
            user_message=user_input,
            request_id=request_id,
        )
        final: dict[str, Any] = await self._graph.ainvoke(initial.model_dump(), config=config)
        return SUTOutput(
            request_id=request_id,
            response_text=final.get("report_markdown") or "",
            tool_calls=[
                tc for tr in (final.get("tool_results") or [])
                for tc in [ToolCall(tool_name=tr.tool_name, args=tr.args, rationale="")]
            ],  # 把 tool_results 倒推成 tool_calls(EvalRunner 评分 tool_correctness 用)
        )
```

**EvalRunner 不动**。`SUT` Protocol 接受任何实现 `run(user_input, request_id) -> SUTOutput` 的对象,ResearchAgent 直接满足。

**Judge 扩展**(additive,不破坏 v0):
- `Judge.score(case, sut_response, trace_summary, tool_calls=None, report_markdown=None)` 新加 `report_markdown` 参数
- 当传入 `report_markdown` 时,Judge 启用 `report_markdown_quality` 维度评分(与 Critic 5 维不同 —— Judge 是 LLM-as-judge eval pipeline 的维度,Critic 是产品内的内置 reviewer;两者职责不同但 prompt 可共享 rubric template 减少冗余)
- 默认 `report_markdown=None` 保持 Plan C/D 老行为

### ③ 量化评估方案

- **SUT swap 兼容性**:Plan C 老测试(bare LLMService SUT)+ v0 ChatAgent SUT + v0.5 ResearchAgent SUT 同时跑通
- **Eval 端到端**:v0.5 加 3-5 条 research_* GoldenCase,跑 ResearchAgent SUT,生成 EvalResult
- **新维度评分**:`report_markdown_quality` 维度仅在 SUT = ResearchAgent 时启用(对话 SUT 不评)
- **GoldenCase schema 扩展**:加 `expected_topics: list[str]` 字段(默认空,additive),供研报场景检查 coverage 用

## 12. 风险与未解问题

### 已识别风险

1. **Send API 学习曲线**:LangGraph 1.x Send API 是 v0.5 第一次真用,Task 0 spike 验证 fan-out + reduce 行为(参考 v0 Spike 2 pattern)。
2. **5 sub-agent 评分 prompt 一致性**:5 个独立 prompt 风格不统一会引入 bias。Plan 阶段提供共享 `_BASE_SCORER_TEMPLATE`,减少 LLM 之间评分尺度漂移。
3. **chart placeholder 跟用户输入冲突**:用户消息含 markdown 图片时不能误认。约束 `chart://` scheme,与 `http(s)://` 区分。
4. **完整研报 latency 7-9s**:用户感知慢。SSE 进度事件流缓解(每 agent 完成发一个 progress event,前端展示进度条)。
5. **mock_web_search 慢路径**:LLM-driven mock 每次 ~1s,DataCollector 串行调 4-5 个 tool 累积 4-5s。考虑 DataCollector 内部并行(asyncio.gather)调多个 tool。
6. **Cassette 录制 cost**:1 次 research 真打 ≈ 8 LLM call ≈ ¥0.05-0.10,record 成本可接受;但 nightly 跑 3-5 case ≈ ¥0.30-0.50 一晚,需在 nightly cron 设 cost limit(`EVAL_COST_LIMIT_CNY` 已 Plan D 设 20)。

### 未解问题(留 plan / v0.6 决定)

- Q1. Critic 5 维 sub-agent 是否共用 prompt template?共用 = 一致性好但 rubric 不灵活;分散 = 灵活但易漂移。Plan 阶段决定。
- Q2. Writer 用 streaming chat(token 流)还是 full-text chat(一次性)?v0 Responder 用 full-text;研报报告比 chat reply 长 5-10x,streaming 更友好但 Plan B LLMService 的 streaming API 待加(目前没有)。**v0.5 默认 full-text**,streaming 留 v0.6;但 SSE 事件已预留 `report_chunk` 类型。
- Q3. DataCollector 内部并行 vs 串行调 tools?并行 latency 收益大但错误处理复杂(一个 tool 失败影响其他?)。Plan 阶段决定。
- Q4. CriticReport.summary_markdown 是否附在研报末尾给用户看?**v0.5 默认不附**(研报已包含数据,Critic 评分是给 eval 用的内部信息),v0.6 frontend spec 决定是否前端展示。
- Q5. GoldenCase 的 `expected_topics` 字段如何评 coverage?直接子串匹配 vs LLM-judge 语义匹配?Plan 阶段决定。
