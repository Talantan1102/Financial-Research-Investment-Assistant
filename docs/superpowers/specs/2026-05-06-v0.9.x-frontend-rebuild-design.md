## § 3 研报展示页设计 — `/research/:id`

### 3.1 形态 D:PDF-like 长卷 + 流式 sticky progress

**问题陈述**:v0.8.4 后端通过 SSE 推 7 event,产出 `InvestmentDueDiligenceReport` JSON。v0.8.4 期间 dogfood 时 user 直接读后端 JSON 文件,没有真正的展示页消费这份数据。

**业界 alternatives**:
- A. PDF-like 长卷 + Markdown 渲染(类似 GitHub README)
- B. 左侧 nav + 右侧内容(类似 Anthropic docs / Confluence)
- C. 卡片折叠(类似 Notion / Linear)
- D. **A + 流式 sticky progress(混合 v0.8.4 已有 overlay)** ← 选定

**选定理由**:
- 接近真研报 UX(假想 banking persona 期待长文档),导出 PDF 自然
- v0.8.4 已 dogfood 过 progress overlay(commit `1984781` `7fc50ee`),保留这部分工作不浪费
- 长文档导航靠右侧 sticky mini ToC(antd Anchor 组件),不需要重设计

**量化评估**:
- 工作量:~3-4 天(markdown 渲染层 + Anchor + ToC + sticky progress overlay 复用)
- 风险:antd 5 风格偏管理后台,但研报正文是 markdown,antd 只做 chrome,可接受

### 3.2 数据流

```
用户进入 /research/:id
  ├─ 已完成研报(status=completed)
  │   GET /api/reports/:id  →  返回 InvestmentDueDiligenceReport JSON
  │   渲染:长卷 markdown + sticky ToC(可见 sections)+ 顶部元信息(target/cost/created_at)
  │   不显示 progress overlay(已完成)
  │
  └─ 进行中研报(status=streaming, 用户从 / landing 启动后跳转过来)
      EventSource /api/reports/:id/stream  →  SSE 7-event
      渲染:
        - 主体长卷流式增长(每个 section 完成 → 写入 partialSections → markdown 渲染)
        - sticky progress overlay 在视口底部(timeline + 自然语言进度日志,延续 v0.8.4 风格)
        - 完成后 progress overlay 自动 fade out
```

### 3.3 关键组件

- `pages/research/Detail.tsx` — 主页面,根据 status 切换展示模式
- `components/report-canvas/index.tsx` — 长卷主体(markdown 渲染 + Anchor ToC)
- `components/progress-overlay/index.tsx` — 复用 v0.8.4 已有 progress timeline,加自动 fade-out 逻辑
- `components/export-button/index.tsx` — Markdown 复制 + PDF 导出按钮(浏览器 print 转 PDF,无需后端)

### 3.4 数据 store

`store/report.ts` 内单一 `reportState`(避免拆 list/detail 两个 store 的 over-engineering):

```ts
interface ReportState {
  list: ReportListItem[]
  listLoading: boolean
  current: InvestmentDueDiligenceReport | null
  currentMeta: { id: string; target: string; cost: number; createdAt: string; status: 'streaming'|'completed'|'failed' } | null
  streaming: {
    active: boolean
    progress: ProgressEvent[]      // sticky overlay 用
    partialSections: Record<string, string>  // 流式增量 sections
  }
}
```

### 3.5 导出功能(v0.9.x 内做)

- **Markdown 复制**:把 `current` JSON 拼成 markdown 字符串(每 section 一段),`navigator.clipboard.writeText`
- **PDF 导出**:CSS `@media print` + `window.print()`,浏览器原生 PDF。无需引入 PDF 生成库

## § 4 历史 session 列表设计 — `/research`

### 4.1 形态 d:Table + 时间分组 filter

**问题陈述**:1 研报 = 1 session,历史列表是用户跨次访问的入口。需平衡信息密度(banking persona 偏好)和时间维度的可视性。

**业界 alternatives**:
- a. antd Table(列:target / 时间 / 状态 / cost / 操作)
- b. Card 卡片瀑布流
- c. Timeline 时间分组
- d. **混合 a+c**(Table + 时间分组 filter) ← 选定

**选定理由**:
- 信息密度高(可排序/筛选 by target、created_at、status、cost)
- 顶部加时间分组 filter(今天 / 本周 / 本月 / 全部)— 符合"研究记录"心智 + 不破坏 Table 主体

**量化评估**:工作量 ~1.5-2 天(antd Table + 时间分组 filter + 列表 API 对接 + 跳转 detail)

### 4.2 列结构

| 列名 | 数据来源 | 排序 | 筛选 |
|---|---|---|---|
| 目标 | `target_overview.target_name` | ✓ | 输入框 |
| 投资建议 | `investment_recommendation.recommendation` | ✓ | 多选(买入/持有/卖出/观望) |
| 创建时间 | `created_at` | ✓ | 时间分组 filter(顶部) |
| 状态 | `status`(streaming/completed/failed) | — | 多选 |
| 成本 | `cost`(¥) | ✓ | — |
| 操作 | 查看 / 删除(确认 modal)| — | — |

### 4.3 数据 API

- `GET /api/reports` → `ReportListItem[]`(分页 query: `?page=1&page_size=20`)
- `DELETE /api/reports/:id` → 204
- 后端 SQL filter `WHERE user_id = current_user.id`(隔离基础)

### 4.4 时间分组 filter 实现

不是后端 query 参数,纯前端基于 `created_at` 字段计算:

```ts
const groupFilter = useSnapshot(reportState).timeFilter  // 'today' | 'week' | 'month' | 'all'
const filteredList = useMemo(() => filterByTimeGroup(reportState.list, groupFilter), [...])
```

## § 5 Trace 调试页形态(只定形态,实施推迟到 v0.9.y)

### 5.1 形态 a:Tree 视图 + raw payload 展开

**问题陈述**:dogfood debug 时需要一个工具看 agent 执行流程,后端 sqlite spans 表已落库 trace 数据,但前端没有展示页。

**业界 alternatives**:
- a. **Tree 视图**(parent → child span 折叠树,展开看 raw payload) ← 选定
- b. Timeline 横向时间轴
- c. Graph(agent topology)
- d. 三栏混合(Tree + Timeline + Payload)

**选定理由**:debug 95% 用例 = "agent 出错了,看它调了什么、拿到什么、产出什么"。a 形态 + raw payload 展开就解决。Timeline / Graph 投入产出比不合算。

### 5.2 为什么实施推迟

Trace 调试页的 API 数据源 = sqlite spans 表(v0.5+ drift 时代默认 sqlite)。本 spec § 7 持久化方案选 W2(legacy PG),但仅迁移**研报存储**到 PG;v0.5+ 横切组件(checkpointer / KB / cache / Trace / Eval / monitoring)的 sqlite → PG 迁移由独立的 "DB 统一 spec" 承载(列入 v0.9+ roadmap § 6 brainstorm 队列)。

如果 v0.9.x 立即实施 Trace 调试页,API 层基于 sqlite 写;DB 统一后这部分 API 又要重写。推迟到 v0.9.y(DB 统一 spec ship 后)做一次对。

### 5.3 v0.9.x 实施时不做的事

- 不写 `/trace/:request_id` 路由
- 不写 trace 相关 components / api / store
- 不写后端 trace 读取 endpoint

但**形态决策**已 anchor,v0.9.y 实施时直接照此 spec 做。

## § 6 Auth 改造 — `/login` + `/register`

### 6.1 修正后的 scope

**保留**:
- `/login` 路由 + UI 改写
- 后端 auth API(legacy User 表 + JWT/session 已就绪,verify session 机制)
- `auth-guard` 组件(包裹需登录的路由)

- 邮箱验证流程
- 密码找回流程(忘密码先手动 reset DB)

- **左半屏 brand 区** + **右半屏简洁表单** 的对开布局

- 表单区:antd Form,但去除 antd 默认 padding,字段标签 floating-label 风格(更现代)
- 顶部加一行 hint:"假想 banking 风控分析师 demo 账号"(方便面试官 / 朋友直接试)
- /login 与 /register 同风格,唯一区别是表单字段 + 按钮文案

### 6.3 数据 store

`store/auth.ts` 保留(已有,只看是否需要小调整 typings)。

### 6.4 隔离机制 verify(实施时)

## § 7 后端连带工作 + 持久化

### 7.1 持久化方案 W2:legacy PG + `research_reports` 表

**问题陈述**:v0.8.4 fix commit `8bc71fa` 把研报存储改成 in-memory cache(进程重启就丢)。v0.9.x 需要持久化(否则历史列表无意义)。

**业界 alternatives**:
- W1. 临时 sqlite,DB 统一时迁 PG(违反 v0.7 决策)
- W2. **legacy PG 加 `research_reports` 表** ← 选定
- W3. LangGraph checkpointer 复用(架构混乱)

**选定理由**:
- 符合 v0.7 决策(`feedback_no_portfolio_simplification`)
- legacy SQLAlchemy 已经接 PG,加表不增加 DB 统一 spec 的迁移负担
- v0.9.x ship 后这部分稳定,不被未来 DB 统一影响

### 7.2 SQLAlchemy model 形态

```python
# backend/app/models/research_report.py
class ResearchReport(Base):
    __tablename__ = "research_reports"
    id = Column(String, primary_key=True)              # uuid 或 thread_id
    user_id = Column(Integer, ForeignKey("users.id"), nullable=False, index=True)
    target_name = Column(String, nullable=False, index=True)
    target_ts_code = Column(String, nullable=True, index=True)
    status = Column(String, nullable=False)             # streaming|completed|failed
    report_json = Column(JSON, nullable=False)          # InvestmentDueDiligenceReport 完整 JSON
    cost = Column(Numeric(10, 2), nullable=False, default=0)
    created_at = Column(DateTime, nullable=False, default=datetime.utcnow, index=True)
    updated_at = Column(DateTime, nullable=False, default=datetime.utcnow, onupdate=datetime.utcnow)
    request_id = Column(String, nullable=True, index=True)  # JOIN trace 用
```

迁移用 alembic(legacy 项目应已有 alembic 配置;若无,直接 `Base.metadata.create_all(engine)` 在 startup 触发,与 monitoring sqlite init 同模式)。

## § 9 风险点与不做的事

### 9.1 风险点

1. **legacy CRUD 未必完整 filter user_id**——实施时 grep 所有 query,补 filter。这是隔离机制的真实漏洞
2. **PG 硬依赖问题**——前置 task 必须 verify "本地 / CI 都能跑",否则 v0.9.x ship 阻塞
3. **SSE 端点路径变更**——v0.8.4 的 SSE 端点 path 可能要重命名为 `/api/reports/:id/stream`,verify 不破坏 v0.8.4 已 dogfood 过的流程
4. **删除组件 grep 工程**——`feedback_unguarded_imports_after_delete` 教训:必须 grep 所有引用,有用的不删,死代码删干净
5. **`industry.ts` store 性质**——verify 是 industry-assistant 残留(可删)还是 monitoring 现役依赖(保留)
6. **mockjs 卸载后影响**——verify 没有遗漏的 mock 引用导致 build 失败

### 9.2 不做的事(明确 scope 边界)

- **Trace 调试页**(实施推迟到 v0.9.y,等 DB 统一)
- **研报对比功能**(推迟到 v0.9.y,数据驱动)
