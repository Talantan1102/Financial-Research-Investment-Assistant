## 0. 文档定位

### 为什么 v0.6 独立成 spec

v0 + v0.5 把"双模式骨架"+"5-agent 研报 pipeline"立完了,但**所有外部数据源都是 mock**(`MockBochaService` LLM-driven mock)。**v0.6 是从 mock 到 production-grade 外部 API 接入的第一步**,引入 4 个 production reliability 概念:rate limit / circuit breaker / quota counter / cost budget。

- **故事完整性** —— 单一 portfolio 故事点:"production-grade external API integration"。塞进 v0.5 会冲淡研报 + multi-agent 故事

- **复用价值高** —— 4 个 production 概念(rate limit / circuit breaker / quota / cost budget)的 Pattern + 实现,**v0.7 真接 Milvus 时可直接复用**(同一个 reliability infra,换 backend)

## 3. 决策二:`BochaClient` = raw httpx wrapper

### ① 问题陈述

接博查 API 的最底层 client 用什么?现成 SDK?raw httpx?还是已有的 `requests`?

### ② 业界 alternatives

| 编号 | 形态 | 代价 |
|---|---|---|
| BC1. 博查官方 SDK(若存在) | 接口 surprise + 跟着 SDK 升版本走 |
| **BC2. raw httpx wrapper**(选) | ~80 行自写,完全控制 retry/timeout/凭证 |
| BC3. `requests` lib(同步) | async 路径需要 `asyncio.to_thread` 包装,跟 v0/v0.5 async 一致性差 |

### ③ 选择:**BC2 raw httpx**

**`BochaClient` 接口**:
```python
class BochaClient:
    """async client for Bocha Search API."""

    def __init__(self, api_key: str, *, base_url: str, timeout_s: float = 10.0) -> None:
        self._api_key = api_key
        self._base_url = base_url
        self._timeout_s = timeout_s

    async def search(
        self,
        query: str,
        *,
        search_type: Literal["general", "news"],  # 博查 API 实际 enum 见 Spike
        count: int,
    ) -> dict[str, Any]:
        """Raw HTTP call. Caller handles retry / rate limit / circuit breaker."""
        headers = {"Authorization": f"Bearer {self._api_key}"}
        ...

    async def aclose(self) -> None:
        """Close httpx AsyncClient."""
```

**理由**:
- 跟 v0/v0.5 `LLMService` 用 openai SDK 不同 — 博查 SDK 不一定优秀,raw httpx 风险可控
- 单文件 ~80 行,招聘官能直接读懂,故事点清晰
- v0.7 切别的搜索引擎只需替换这一个文件

### ④ 量化评估方案

- **`BochaClient` LOC**: ~80 行(含 init / search / aclose / 5 类 exception 触发逻辑)
- **真 API call latency P50**: 预估 ≤ 500ms(博查文档基准)
- **Spike 验证**: Task 0 验证 (a) 博查 API 实际 endpoint + auth header 形态;(b) `search_type` enum 实际值;(c) 错误响应 body 结构(用于 5 类错误分类)

## 4. 决策三:Reliability layer(rate limit + circuit breaker + retry)

### ① 问题陈述

外部 API 三个常见 production 问题:**限流 / 熔断 / 失败重试**。v0.6 做到什么深度?

### ② 业界 alternatives

**Rate limiter**:
| 编号 | 算法 | 代价 |
|---|---|---|
| RL1. token bucket | 实现复杂,适合突发流量;v0.6 不需要这种灵活性 |
| **RL2. sliding window**(选) | 简单 deque[timestamp] + 60s 内长度判断 |
| RL3. fixed window | 容易在窗口边界 burst 2x;不推荐 |

**Circuit breaker**:
| 编号 | 形态 | 代价 |
|---|---|---|
| CB1. 不做 | API 抽风时浪费 quota + 用户长等 |
| **CB2. 三态 (closed / open / half-open)**(选) | 经典实现,~50 行 |
| CB3. 五态 + 滚动错误率 | 过度设计,scope 爆 |

**Retry 策略**:
| 编号 | 形态 | 代价 |
|---|---|---|
| RT1. 不 retry | 网络抖动直接 fail,体验差 |
| RT2. 固定间隔 retry | 撞 thundering herd 风险 |
| **RT3. exponential backoff + jitter**(选) | 1s / 2s / 4s + ±200ms,业界标准 |

### ③ 选择:**RL2 + CB2 + RT3**

**`RateLimiter`**(`backend/app/services/rate_limiter.py`):
```python
class RateLimiter:
    """Sliding window rate limiter — N calls per window_s seconds."""

    def __init__(self, *, max_calls: int, window_s: float = 60.0) -> None:
        self._max_calls = max_calls
        self._window_s = window_s
        self._timestamps: deque[float] = deque()
        self._lock = asyncio.Lock()

    async def acquire(self) -> None:
        """Block (await) until a call is allowed."""
        async with self._lock:
            now = time.monotonic()
            # 清理过期戳
            while self._timestamps and now - self._timestamps[0] > self._window_s:
                self._timestamps.popleft()
            if len(self._timestamps) >= self._max_calls:
                wait_s = self._window_s - (now - self._timestamps[0])
                await asyncio.sleep(wait_s)
                # recurse to re-check
                await self.acquire()
                return
            self._timestamps.append(now)
```

**`CircuitBreaker`**(`backend/app/services/circuit_breaker.py`):
```python
class CircuitBreaker:
    """3-state breaker: closed / open / half_open.

    Transitions:
      closed → open: failure_threshold consecutive failures
      open → half_open: cooldown_s elapsed since opening
      half_open → closed: 1 successful call
      half_open → open: 1 failed call
    """

    def __init__(self, *, failure_threshold: int = 5, cooldown_s: float = 30.0) -> None: ...
    async def call(self, coro_factory: Callable[[], Awaitable[T]]) -> T: ...
    @property
    def state(self) -> Literal["closed", "open", "half_open"]: ...
```

**Retry**(集成到 `BochaClient.search` 的 caller, 即 `WebSearchTool`):
```python
async def _retry_with_backoff(
    coro_factory: Callable[[], Awaitable[T]],
    *,
    max_retries: int = 3,
    base_delay_s: float = 1.0,
    jitter_max_s: float = 0.2,
    retry_on: tuple[type[Exception], ...] = (BochaNetworkError, BochaServerError),
) -> T:
    """Exponential backoff: 1s, 2s, 4s, ... + uniform jitter."""
```

### ④ 量化评估方案

- **RateLimiter unit test**: 模拟 100 ms 内调 70 次(超过 60 次/分),assert 第 61 次被 await 阻塞至少 (window_s - 0.1)s
- **CircuitBreaker unit test**: 5 次连续失败 → state="open";cooldown 后 → state="half_open";1 次成功 → state="closed"
- **Retry unit test**: NetworkError 触发 3 次 backoff(1+2+4=7s,实际加上 jitter ±0.6s)
- **真 API**: 100 次随机查询,assert no 429 错误(rate limit 应该挡住),no 5xx(retry 应该掩盖)
- **集成 latency**: P50 ≤ 800ms(httpx 真请求 + rate limiter wait + 序列化),P99 ≤ 5s(含 1 次 retry)

### ⑤ 风险

- **博查具体限流值未知**: Task 0 spike 必须验证 (a) 单 API key 单分钟最多多少次;(b) 月度 quota 实际 1000 次还是按字符计费;(c) 是否有 burst allowance
- **CircuitBreaker 三态 race condition**: half_open 状态下 1 个并发请求才允许试探,多个并发到来时只有第一个能 try。需要 asyncio.Lock,L0 测试覆盖

## 5. 决策四:Quota + Cost budget 双层追踪

### ① 问题陈述

博查给你"月 1000 次免费"。**怎么追?**仅按次数?还是同时按金额(超免费转付费按次收费)?

### ② 业界 alternatives

| 编号 | 形态 | 代价 |
|---|---|---|
| QC1. 仅 quota counter(次数) | 简单,但超免费档无法用金额视角 cap |
| QC2. 仅 cost_budget(金额) | Plan D 现成,但失去"次数 × 单价"细节 |
| **QC3. 双层(quota + cost)**(选) | 两个 counter,各自 fail-fast 触发不同行为 |

### ③ 选择:**QC3 双层追踪**

**`QuotaCounter`**(`backend/app/services/quota_counter.py`)— SQLite 持久化:
```python
class QuotaCounter:
    """Persists call counts across restarts. SQLite-backed.

    Used for: hard rate limits with billing implications (e.g. month 1000 free
    calls before paid). Different from CostBudget (which is金额-based) and
    RateLimiter (which is sliding window 60s).
    """

    def __init__(self, *, db_path: Path, name: str, monthly_limit: int) -> None: ...
    def used_this_month(self) -> int: ...
    def remaining(self) -> int: ...
    def increment(self) -> None: ...  # called after each successful API call
    def would_exceed(self) -> bool: ...
```

`CostBudget` 复用 Plan D:
```python
search_cost_budget = CostBudget(
    name="bocha_search_monthly",
    limit_cny=20.0,  # ¥20/月 上限,超免费档后开始累计
    ...
)
search_cost_budget.charge(0.01)  # 假设博查超免费档 ¥0.01/次
```

### ④ 量化评估方案

- **QuotaCounter SQLite schema**: 单表 `search_quota_log(name TEXT, ts INTEGER, count INTEGER)` —— 每次 increment 写一行,query 时 SUM
- **CostBudget 复用度**: 0 行新代码到 `cost_budget.py`,仅在 production wiring 加 1 行 `CostBudget(name="bocha_search_monthly", limit_cny=...)`
- **协同检查**: WebSearchTool.run() 顺序:`circuit_breaker → rate_limiter → quota_counter.would_exceed → cost_budget.would_exceed → BochaClient.search → (success) → quota_counter.increment + cost_budget.charge`
- **跨进程一致性**: SQLite WAL mode 单 worker uvicorn 够;多 worker scale-out 留 v1+(用 Redis)

## 6. 决策五:错误分类 5 类

### ① 问题陈述

API 调用可能失败的原因有很多。**笼统 except Exception 还是细分?**细分到几类?

### ② 选择:**5 类**

```python
# backend/app/services/bocha_errors.py

class BochaError(Exception):
    """Base for all BochaClient errors."""


class BochaNetworkError(BochaError):
    """Network failure: DNS / connection / TLS / read timeout."""
    # → retry: yes (exponential backoff)


class BochaRateLimitError(BochaError):
    """HTTP 429: rate limit exceeded."""
    # → retry: NO (rate_limiter should have prevented this; if hit, signal breaker)
    # → circuit_breaker.record_failure (即使 rate_limiter 出 bug,breaker 兜底)


class BochaAuthError(BochaError):
    """HTTP 401 / 403: invalid or revoked credentials."""
    # → retry: NO (re-auth needed by human)
    # → fail loud (alert / log error)


class BochaServerError(BochaError):
    """HTTP 5xx: server-side error."""
    # → retry: yes (likely transient)


class BochaClientError(BochaError):
    """HTTP 4xx (other than 401/403/429): bad request / not found / etc."""
    # → retry: NO (request itself is wrong)
    # → log + raise immediately
```

**WebSearchTool.run** 区分各类的处理:
- `BochaAuthError` / `BochaClientError` → 包成 `ToolError(success=False, error=...)`,DataCollector 看到失败但其他 tools 不影响(v0.5 Task 4 已建立的"partial failure does not block"模式)
- `BochaNetworkError` / `BochaServerError` → retry 3 次,3 次都 fail 后包成 `ToolError`
- `BochaRateLimitError` → 触发 circuit_breaker.record_failure,然后包成 `ToolError`

### ③ 量化评估方案

- **5 类 unit test**: mock httpx response,各 status code 对应 raise 正确异常类
- **retry 决策对应**: `_retry_with_backoff` 默认 `retry_on=(BochaNetworkError, BochaServerError)` —— Auth/Client/RateLimit 都不 retry

## 7. 决策六:Mock vs Real 切换 = `BOCHA_MODE` env var

### ① 问题陈述

production 路径用真 BochaClient,测试 / 开发用 MockBochaService。**怎么切换?**

### ② 选择:**`BOCHA_MODE` env var,工厂函数选择**

`backend/app/services/bocha_factory.py`:
```python
"""Factory: build_bocha_client_from_env() — selects mock or real per BOCHA_MODE."""

class BochaService(Protocol):
    """Common interface for MockBochaService + BochaClient."""
    async def search(self, query: str, *, search_type: str, count: int) -> dict[str, Any]: ...


def build_bocha_service_from_env() -> BochaService:
    mode = os.environ.get("BOCHA_MODE", "mock")
    if mode == "mock":
        from app.service.mock_bocha_service import MockBochaService
        return MockBochaService(llm=build_llm_service_from_env())  # delegated factory
    elif mode == "real":
        return BochaClient(
            api_key=os.environ["BOCHA_API_KEY"],
            base_url=os.environ.get("BOCHA_BASE_URL", "https://api.bochaai.com/v1"),
        )
    else:
        raise ValueError(f"Unknown BOCHA_MODE: {mode}")
```

**production wiring**(`backend/app/router/research.py:get_research_graph`)改 1 行:`mock_bocha = build_bocha_service_from_env()`(原来直接 `MockBochaService(...)`)。

### ③ 量化评估方案

- **mock 路径零回归**: v0/v0.5 测试不动(`BOCHA_MODE` 不设默认 mock)
- **real 路径**: production / cassette 录制 + replay 设 `BOCHA_MODE=real`
- **新 .env 字段**: `BOCHA_API_KEY` + `BOCHA_BASE_URL`(已加 .env.example)

### ① 问题陈述

### ② 选择:**SQLite + in-memory 混合**

| 组件 | 存储 | 理由 |
|---|---|---|
| `RateLimiter._timestamps` | in-memory deque | 60s 滑动窗口,重启后归零没事(60s 内自然恢复) |
| `CircuitBreaker._state` | in-memory + 30s cooldown | 类似 |
| `QuotaCounter` | SQLite | 月度累计,重启不能丢 |
| `CostBudget` | SQLite | 同上;已 Plan D 实现 |

**SQLite 文件**: 复用 Plan C `eval.sqlite`(同一文件,新表 `search_quota_log` + `cost_budget_ledger`),不新建文件。

### ③ 量化评估方案

- **SQLite WAL mode**: 启用(单 worker uvicorn,write 不阻塞 read)
- **storage 增长**: QuotaCounter 月 ~1000 行 × ~50 字节 ≈ 50KB / 月,可忽略
- **跨 worker 一致性**: v0.6 仅支持单 worker uvicorn(`uv run poe serve` 已是)。多 worker 需要分布式 counter,留 v1+

## 12. 风险与未解问题

### 已识别风险

1. **博查 API 实际接口不熟** —— Task 0 spike 必须真打验证 (a) endpoint URL 路径;(b) auth header 格式(Bearer vs API-Key);(c) `search_type` enum 实际值;(d) 错误响应 body 结构。如果博查 API 与预期差异大,plan 可能调整 BochaClient 实现细节。
2. **博查月度 quota 实际数字** —— "1000 次"是用户估算,实际可能按字符计费 / 按 endpoint 分档。Spike 1 必须查博查文档 / dashboard 确认。如果按字符,QuotaCounter 接口需要从"次数"改"字符数",单位改但骨架不变。
3. **CircuitBreaker race condition** —— half_open 状态下并发请求必须有 1 个先 try,asyncio.Lock 处理。L0 测试覆盖。
4. **Cassette 录制 cost** —— v0.6 加 1 个 BochaClient cassette + 扩 research cassette,真 API 调用 ~10 次,cost ~¥0.005 record once。可接受。
5. **`BOCHA_API_KEY` 凭证管理** —— 不能进 git。`backend/.env.example` 加 placeholder,`backend/.env` 单独 gitignored(已 .gitignore 含 `.env`)。
6. **Mock 路径回归风险** —— v0/v0.5 18+ tests 用 MockBochaService,`build_bocha_service_from_env()` 默认 mock 必须保证零修改通过。

### 未解问题(留 plan / v0.7 决定)

- Q1. 博查 API 是否支持 `search_type="docs"`? v0.5 Task 2 假设支持(实际改成了 "report" 因为 MockBochaService 不支持 docs)。Task 0 spike 验证博查真 API 支持的 search_type 列表。
- Q2. retry 时机 — 连续 NetworkError 应该立刻 retry 还是先 short circuit?当前选立刻 retry,但如果 backoff 总时间超过 user-perceived latency 阈值(比如 5s),可能要 fail-fast 让用户看到错误。Plan 阶段决定。
- Q3. QuotaCounter 月初 reset — v0.6 不实现 cron。月初手动 truncate 表?或者按 month-aware 时间戳查询(SUM where month=current_month)?后者更简单,Plan 阶段决定。
- Q4. ChatPlanner / DataCollector 是否需要知道 quota 状态来调整 plan?(比如剩 5 次时只 plan 关键 subtask)留 v1+ 多 layer 优化。

```
       request →   │  CircuitBreaker  │
                   │   (closed?)      │
                   └────┬─────┬───────┘
                  yes ↓        ↓ no (open)
            ┌──────────┐    raise BochaServerError("breaker open")
            │ RateLimit │
            │  acquire  │ (await 直到允许)
            └────┬──────┘
                 ↓
            ┌─────────┐
            │ Quota   │
            │ check   │
            └──┬──┬───┘
            ok ↓  ↓ exceed
              │   raise BochaClientError("quota exceeded")
              │
            ┌─▼─────────────┐
            │ httpx request │
            └─┬─────────────┘
              ├ 200 → return result + breaker.record_success + counter.increment + budget.charge
              ├ 429 → BochaRateLimitError → breaker.record_failure (no retry, rate_limiter 应已挡)
              ├ 401/403 → BochaAuthError (no retry, fail loud)
              ├ 5xx → BochaServerError → retry × 3 (exponential + jitter)
              ├ 4xx (other) → BochaClientError (no retry)
              └ network → BochaNetworkError → retry × 3
```
