## § 1 决策摘要

### 决策 1:Position = materialized 表 + Trade write 同事务重算

**问题**:Position(当前持有数量 / 加权成本 / 浮盈)是 Trade 的衍生物,后端怎么把它端给 dashboard?

**业界 alternatives**:
- **A. View / 计算属性模式** — 不建 Position 表,每次查询从 Trade 当场聚合
- **B. Materialized Position 表 + Trade write 触发重算**(本决策)
- **C. Cached aggregate (lazy + TTL)** — A + 5 分钟内存 cache

**对比表**:

| 维度 | A 现算 | **B materialized** | C 缓存 |
|---|---|---|---|
| 数据存几份 | 1 (Trade) | **2 (Trade + Position)** | 1 + 内存 |
| Read 性能 | 算一下(毫秒级) | 直接读(微秒级) | 头次算后读内存 |
| 删 Trade 怎么处理 | 重算时该笔已不在,自动正确 | **走 recompute 一刀切**(不写专门 reverse) | 重算 + cache invalidate |
| 写路径责任 | 0 | Trade write 同事务 UPSERT Position | cache 失效逻辑 |
| 扩展性 | 量大撞性能墙 | **金融基础设施标准** | 中间路线 |

**取舍**:B。

**理由**:
- 双写一致性是金融数据基础设施核心问题,Position 表是金融机构标准做法,**作品集叙事价值在于解决了这个问题而非绕过**(memory `feedback_no_portfolio_simplification`)
- 删 Trade 24h 内的 Position 状态回退**不写专门 reverse 代码**,走 recompute 一刀切 — 避开 B 模式的常见陷阱(手写 reverse 容易漏)
- ACID 单事务保证 Trade 跟 Position 强一致,debug 时不会出现"Trade 表说卖了 Position 表说没卖"的灵异
- 加 `last_quote_price` / `last_quote_at` 字段后,Position 行 = "用户在某只股上的全部状态快照",后续监控 / dashboard / 详情卡共享同一份现价(决策 3 协同)

**量化评估**:
- v1.0 dogfood 量级:持仓 ≤ 20 只 + 一年 Trade < 200 笔 — 单事务 recompute 在 PG 上 < 10ms,量级层面 A/B 都不卡
- 真正区别在**架构纪律**:B 让"Position 状态"成为一等公民可观察(SQL 直查可验),A 让它隐式埋在 SQL 聚合里
- 测试覆盖增加:每条 Trade write 路径都要断言 Position 一致性(本 spec § 4 测试策略)

### 决策 2:编辑权限三态机校验 = service 层 guard

**问题**:product spec § 4.3 定义的"常规交易过 24h 不可改 / 24h 内可删 / 初始仓位始终可编辑"门禁,代码放哪里?

**业界 alternatives**:
- **A. Service 层 guard**(本决策) — Python `TradeService.update/delete` 顶部 if 检查
- **B. DB 层 check constraint / trigger** — PostgreSQL TRIGGER 拒掉非法 UPDATE
- **C. 双层防御** — A + B 都做

**对比表**:

| 维度 | **A service** | B DB trigger | C 双层 |
|---|---|---|---|
| 测试 | sqlite-override 跑 L0/L1 | 必须 PG container | 双倍 |
| 绕过 | service 是单 writer 入口 | DB 终极防线 | 任何路径都拦 |
| alembic 依赖 | 无 | 需要 trigger migration(PR-A 后) | 同 B |
| 当前体系 fit | 走 v0.9.x 已 ship 模式 | 跟 `Base.metadata.create_all()` + sqlite-override 不兼容 | 同 B |
| 工程量 | 30 行 Python + 单元测试 | trigger DDL + PG container 测试套迁移 | 双倍 |

**取舍**:A。

**理由**:
- v1.0 单 writer 路径(只有 FastAPI 的 TradeService),trigger 挡的是不存在的攻击面(没有 admin 后台 / 没有数据修复脚本 / CSV 导入推 v1.x)
- DB trigger 在当前体系(`Base.metadata.create_all()` + L0/L1 sqlite-override)不兼容,加 trigger 会推 L0/L1 测试套整体迁 PG container — 性价比极低
- 跟 Q1 选 B(materialized Position)的"专业精神"不冲突:Q1 解决的是真问题(数据一致性),Q2 的 trigger 是为想象中的入侵做的工程
- 留口子:v1.x 真有 admin 后台 / CSV 导入时,**届时**加 trigger,不会被锁死

**量化评估**:
- A 路径工程量:`TradeService.update/delete` 各 ~10 行 + L0 单元测试 ~50 行
- B 路径工程量:trigger DDL + raw SQL migration(等 PR-A 就位)+ L0/L1 套迁 PG container(`feedback_pg_test_container_pattern` 推广)≈ 几天工作
- v1.0 ship 优先级:A 路径不挡进度,B 路径会引导测试 infra 重构,**违背 product spec § 3 决策 3 minimalism**

### 决策 3:浮盈现价 = 跟监控 30 分钟周期一起刷,写 Position 表

**问题**:dashboard 浮盈展示需要"现价",这个数字从哪来 / 多新?

**业界 alternatives**:
- **A. Dashboard 渲染时实时拉 tushare** — 每次刷 dashboard 对持仓所有股打 tushare
- **B. 跟监控 30 分钟周期一起刷,写 Position 表**(本决策)
- **C. 分层 cache + 显式手动刷新按钮** — 基本 = B,但手动按钮粒度到单股

**对比表**:

| 维度 | A 实时 | **B 跟监控周期** | C 分层 |
|---|---|---|---|
| Tushare quota 消耗 | 高(连刷 dashboard 烧光) | 一天 ~16 次(=监控本身) | 同 B |
| 浮盈数据新鲜度 | 此刻最新 | 最长延迟 30min | 同 B + 单股可立即 |
| 跟异动判定一致性 | **不一致**(用不同 snapshot) | 一致(共享 snapshot) | 同 B |
| 实现复杂度 | dashboard handler 加 tushare 调用 | 监控引擎写 Position 字段 | B + 单股刷新接口 |

**取舍**:B。

**理由**:
- product spec § 5.3 已经定了**监控 30 分钟刷新**作为产品决策,Q3 选 B 是这个决策在工程层的等价实现 — 浮盈和异动判定共享同一份现价 snapshot
- Q1 选 B(materialized Position)后加 `last_quote_price` / `last_quote_at` 字段,Position 行 = "用户在该股上的全部状态快照",**逻辑闭合**
- spec § 5.3 已经写了"自动 + 手动刷新按钮",手动按钮触发监控引擎跑一次 → 自动写 Position 字段,本决策**不引入新刷新机制**
- A 路径还会让"为什么红线点开详情卡里的现价跟 dashboard 不一样"成为 debug 噩梦
- C 跟 B 实质相同,只多个单股粒度按钮 — v1.0 minimalism 不做(spec § 6.6 已显式不做单股粒度操作)

**量化评估**:
- B quota 一天 ~16 次 tushare 调用(对应 8 只持仓 × 2 次/小时 ÷ 监控扫描合并),A 路径连刷 dashboard 5 次 = 40 次叠加监控本身的 16 次 = 56 次/天(3-4x 烧)
- Tushare 闲鱼买不限调用,但**少打就少打**是工程纪律(`reference_data_sourcing_channels`)
- 用户感知延迟:30min 在长持散户场景可接受(spec § 5.3 用户决策已 anchor),手动刷新按钮覆盖"我现在就想看"

## § 2 数据模型

### 2.1 Trade 表

| 列 | 类型 | 说明 |
|---|---|---|
| id | UUID PK | gen_random_uuid() |
| user_id | UUID FK → users.id | `with_variant(String(36), "sqlite")` |
| ts_code | String(10) | tushare 标的代码,例 "600519.SH" |
| name | String(50) | 标的名称(autocomplete 回填) |
| type | Enum (`initial`, `buy`, `sell`) | 三态 |
| quantity | Integer | 股数(必填,> 0) |
| price | Numeric(12, 4) | 单价(必填,> 0) |
| trade_date | Date | 交易日期,默认今天 |
| note | Text NULL | 笔记(场景 M 种子) |
| created_at | TIMESTAMP NOT NULL | server default now() |

**Index**:`(user_id, ts_code, trade_date)` — 支持 Position recompute 时按 (user_id, ts_code) 拉 + 按 trade_date asc 排序。

### 2.2 Position 表(materialized,决策 1)

| 列 | 类型 | 说明 |
|---|---|---|
| id | UUID PK | |
| user_id | UUID FK → users.id | `with_variant` 同 Trade |
| ts_code | String(10) | |
| name | String(50) | 冗余字段(避 join,从 Trade 同步) |
| quantity | Integer | 当前持有数量(可为 0) |
| avg_cost | Numeric(12, 4) | 加权平均成本(quantity=0 时保留最后非零值) |
| total_cost | Numeric(14, 2) | 当前持仓总投入金额 |
| realized_pnl | Numeric(14, 2) | 累计已实现盈亏(随 sell 累加) |
| last_quote_price | Numeric(12, 4) NULL | 决策 3:监控周期写入 |
| last_quote_at | TIMESTAMP NULL | 决策 3:监控周期写入 |
| is_silenced | Boolean default false | v1.x 静默仓位口子 |
| updated_at | TIMESTAMP NOT NULL | recompute 时更新 |

**Unique constraint**:`(user_id, ts_code)` — 同用户同标的只一行。

**清仓再回来**:`quantity` 重算到 0 时**保留行**(realized_pnl 累计有价值),用户再买入是同一行 UPDATE 而不是新建。

## § 3 关键流程

### 3.1 Trade write → Position recompute(决策 1 核心)

```
TradeService.create(...)         # type=initial / buy / sell
TradeService.delete(trade_id)    # 24h 内,任何 type
TradeService.update(trade_id)    # 仅 initial type 允许

每条入口在事务内:
  1. 写入 / 删除 / 修改 Trade 行
  2. 对 (user_id, ts_code) 重新跑 Position recompute:
     SELECT 该 (user_id, ts_code) 的 Trade 全集 ORDER BY trade_date asc
     fold:
       initial / buy →
         total_cost += q * p
         quantity += q
         avg_cost = total_cost / quantity (if quantity > 0)
       sell →
         realized_pnl += q * (p - avg_cost)
         total_cost -= q * avg_cost
         quantity -= q
     UPSERT Position 行 (user_id, ts_code) 唯一键
  3. 事务 commit

不变量:Trade 写完后 Position 跟 Trade 严格一致(单事务保证)。
```

**关键设计点**:删 Trade **不写专门的 reverse 路径**,走同一条 recompute(那笔已不在,fold 自然回退)。

### 3.2 监控引擎 30 分钟周期 → 刷 Position 现价(决策 3)

```
监控引擎 cron 30min(扩展 v0.8.3 已 ship 的 B-3 引擎):
  对每个 active Position(quantity > 0 AND NOT is_silenced):
    1. pull tushare daily price(批量,单 API call 拉一批 ts_code)
    2. UPDATE position SET last_quote_price=?, last_quote_at=now() WHERE ...
    3. 顺手判异动(±5% 或 5 类公告,留给第 2 条 plan 实现)
```

**Dashboard 渲染时**:
```python
浮盈% = (last_quote_price - avg_cost) / avg_cost * 100
浮盈金额 = (last_quote_price - avg_cost) * quantity
显示 last_quote_at "最近更新 09:23" 时间戳
```

### 3.3 编辑权限三态机(决策 2)

```python
class TradeService:
    def update(self, trade_id: UUID, **fields) -> Trade:
        trade = self.repo.get(trade_id)
        if trade.type != TradeType.INITIAL:
            raise ImmutableTradeError("常规交易不可改字段,过 24h 也不可")
        # initial 始终可改
        updated = self.repo.update(trade, **fields)
        self._recompute_position(trade.user_id, trade.ts_code)
        return updated

    def delete(self, trade_id: UUID) -> None:
        trade = self.repo.get(trade_id)
        if datetime.utcnow() - trade.created_at > timedelta(hours=24):
            raise ExpiredDeletionError("超 24h 不可删,请录反向交易抵消")
        self.repo.delete(trade)
        self._recompute_position(trade.user_id, trade.ts_code)
```

**异常类型**:
- `ImmutableTradeError` — 常规 trade 字段修改尝试
- `ExpiredDeletionError` — 任何 trade 24h 后删除尝试

API 层捕获两者返回 4xx + 用户友好消息。

```
"录入你当前持有的股票"
循环表单(每条作 Trade(type='initial')):

  - 持有数量
  - 加权平均成本价(必填,可手算填)

```

## § 5 测试策略

| 层级 | 测试内容 | 用什么 |
|---|---|---|
| L0 unit | TradeService recompute 算法 / 三态机 guard | sqlite override(走 `with_variant`)+ pytest |
| L1 integration | Trade CRUD ↔ Position 一致性 / 删 Trade 自动 reverse | sqlite override + repo fixture |
| L2 e2e | Onboarding 链路 / 监控引擎写 quote → dashboard 读 | PG container(`pg_test_container` fixture) |

**必须覆盖的测试场景**:

1. **基本聚合**:序列 `initial 200@1450` → `buy 50@1500` → `sell 30@1600`
   - 期望 Position:`quantity=220, avg_cost≈1465.91, total_cost≈322,500.00, realized_pnl≈4,022.73`
2. **删 Trade 自动 reverse**:删上面的 buy → Position 应回到 `quantity=170, avg_cost=1450, realized_pnl=4,500.00(全 sell 按 initial 成本算)`
3. **三态机 ImmutableTradeError**:UPDATE 常规 trade 字段抛错
4. **三态机 ExpiredDeletionError**:25h 后 delete 任何 trade 抛错
5. **三态机 Initial 总可改**:48h 后 UPDATE initial trade 成功
6. **清仓再回来**:`initial 100` → `sell 100` → `buy 50` Position 行保留,`quantity=50`,`realized_pnl=...`
7. **监控周期写 quote**:跑监控引擎 → Position 行 `last_quote_price` / `last_quote_at` 被更新
8. **Multi-account 隔离**:user_a 的 recompute 不影响 user_b 同 ts_code 的 Position
9. **事务原子性**:Trade write 失败时 Position 不被修改(模拟 DB error 注入)
