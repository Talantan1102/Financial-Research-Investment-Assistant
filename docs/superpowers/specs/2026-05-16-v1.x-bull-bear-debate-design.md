# v1.x A5b — bull/bear multi-agent debate 设计

## § 1. 问题陈述

### 1.1 现状

v1.x A5a 已 ship 后,数字层 multi-model cross-check + outlier diagnosis 已经接通,但**叙事层仍是单 Writer 一次产 InvestmentDueDiligenceReport**。Writer LLM 单 prompt → 单 response 的范式天然有 **confirmation bias**:它倾向"找证据支持自己已经倾向的结论",而非主动列举反方证据。

具体表现(用茅台举例):
- Writer narrative 提"品牌护城河 30 年 / ROE 30% 稳定" → 没主动提"年轻一代不喝白酒 / 渠道库存高 / 反腐影响"
- 即使 Critic 7 维评分都 ≥ 7.0(factuality 没错事实 + valuation_consistency narrative 引用了 cross-check)→ **Critic 抓不到"一面之词"** —— 因为 factuality 只验"事实是否正确",不验"事实是否全面"

研究员行业术语:**单线叙事(one-sided narrative)** = 真正的尽调失败模式。严肃尽调 mandatory 双向论证(bull case + bear case 显式分章),客户(基金经理/风控部)需要看到"反方观点已经被严肃考虑过"才敢按建议下单。

### 1.2 业务驱动 — 为什么是这个 PR

A5b 是 v1.x **"双 hallucination 防御"** 计划的第二块:
- **A5a(已 ship)** 防 **数字 hallucination** — 多模型估值 cross-check + Python deterministic helper + OutlierDiagnosisAgent
- **A5b(本 PR)** 防 **叙事 hallucination** — bull/bear multi-agent debate

两块接力讲"防 hallucination"完整故事:数字层(A5a)→ 叙事层(A5b)。

### 1.3 portfolio 价值

本 PR 提供 5 个简历讲故事点:
1. **multi-agent adversarial debate paradigm 落地**:Bull/Bear 各被灌 30% 立场 prompt + 2 轮 rebut + Writer 综合 — 真"多 agent 防 single-LLM bias"
2. **shared state vs 重复 fetch 工程取舍**:advocate 共享 Analyst 产出的 valuation_analysis,不重 fetch tushare — 用 shared state 解 multi-agent sync 难题
3. **convergence 控制 + cost-aware tiering**:max_rounds=2 硬截断 + advocate 走 fast tier(low complexity task)+ Writer 走 balanced tier(high complexity synthesis)— 跟 v0.8.5 TierRouter 一脉相承
4. **LLM 自评元认知信号**:`strongest_argument` + `confidence` + `rebut_targets` 字段强制 advocate 区分凑数论据和真实强论据 + 显式声明反驳了对方哪些条 — 跟 A5a OutlierDiagnosis.confidence 同范式
5. **dialectical_balance 守护回路**:Critic 第 8 维 rule-based 评 narrative 是否真双向,低分触发 writer retry — 完整闭环

## § 2. 业界 mindset(adversarial debate paradigm)

### 2.1 LLM 单 prompt 的 systematic bias

学术界已证实(arxiv 2023-2024 multi-agent debate 相关 paper):
- 单 LLM agent 在产 narrative 时倾向 confirmatory(选证据支持自己已有立场)
- 给两个 LLM agent 各被灌不同立场 prompt → 各自论据**显著不同** → 综合后 narrative balance 提升

主流学术 / 框架:
- AI safety via debate(Irving et al 2018,DeepMind / Anthropic 起源)
- AutoGen (Microsoft, 2023) — multi-agent conversation 框架
- MetaGPT — role-based multi-agent
- 金融垂直:FinAgent (Zhang et al 2024) / FinRobot (AI4Finance Foundation 2024) / TradingGPT (Li et al 2023)

### 2.2 工业界 vs 学术界 debate 实现差异

| 维度 | 工业界(大基金 / 卖方研报)| 学术界(paper) |
|---|---|---|
| **debate 轮数** | 多 1 轮(parallel),罕见 N 轮 | 2 轮(rebut)or N 轮(convergence)|
| **advocate 视角共享** | parallel 各自陈述 | 多 rebut 互看 |
| **judge 综合** | 研究员自己脑补,无独立 judge | 多有显式 DebateJudge agent |
| **可观测性** | post-mortem 看 trace,不实时 | 实时 / 全 trace 公开 |
| **cost 控制** | 严格成本预算 | 较松(科研环境)|

A5b 选 **2 轮 rebut + Writer 综合(无独立 Judge)+ post-mortem trace**(B 范式)— 中间路线,跟工业实际更近但保留"真对抗"的核心价值。

### 2.3 真实研究员的 mandatory 双向论证

严肃尽调报告(投行 IPO / 大并购 / 卖方深度研报)都有 mandatory bull / bear sections:
- Bull case(看多论据 3-5 条):每条引用具体数字 / 事实(签约管道 / 业绩预告 / 估值分位)
- Bear case(看空论据 3-5 条):每条对应 bull 的弱点 / 反驳

A5b LLM 模拟这个工作流,把研究员的"内化辩证能力"显式拆成 2 个独立 LLM agent 角色。

## § 3. 决策 Q1 — Scope:Writer 前置 DebateOrchestrator(B 选项)

### 3.1 问题

bull/bear debate 在 graph 哪里跑?

### 3.2 Alternatives

| 选项 | 描述 | LoC | walltime | 简历叙事 |
|---|---|---|---|---|
| **A** | 替换 Writer 为 3-agent debate(BullAdvocate / BearAdvocate / DebateJudge 各独立 LLM,Judge 产 final report)| ~1000+ | 6-8 天 | 强(multi-agent 重构)|
| **B** | Writer 前置 DebateOrchestrator node(advocate 产 bull/bear lists,Writer 综合)| ~1000 | 4 天 | 中-强(三层递进延续)|
| **C** | Critic 后 DebateRetry node(only on narrative 一面之词 trigger)| ~300 | 1.5 天 | 弱(被动 patch)|

### 3.3 选择 B — 理由

1. **跟 A5a 范式延续**:A5a 在 Analyst 加 valuation hook + schema 加字段 + Critic 加维 + Writer prompt 改造,B 完全复用这个工作流。A 是重构,破坏面大。
2. **不破坏 v1.x A4 / A5a 已 ship**:Writer 现有 SOP 11 维 / post_process / retry edge / cassette 全保留;debate 是 Analyst → Writer 中间一个 node,前后不变
3. **简历叙事故事性**:"v1.x A4 plan template + A5a 数字 cross-check + A5b 叙事 cross-check" 三层连续递进,比 A 的一次性重写更有渐进 ship 节奏

### 3.4 评估

LoC ≈ 1000(advocate 200 + orchestrator 150 + schema 80 + critic 80 + Writer/wire 80 + tests 350 + dashboard 100 + docs);walltime ≈ 4 天(跟 A5a 同量级)。

## § 4. 决策 Q2 — debate 互动:顺序 2 轮 rebut(B 选项)

### 4.1 问题

advocate 之间是单轮独立 / 多轮 rebut / N 轮 convergence?

### 4.2 Alternatives

| 选项 | 描述 | LLM call 数 | 真"对抗" | 工程复杂度 |
|---|---|---|---|---|
| **A** | 单轮 parallel(各独立产论据,看不到对方)| 2 | 弱 | 低 |
| **B** | 顺序 2 轮 rebut(round 2 看对方 v1 后产 v2)| 4 | **真** | 中 |
| **C** | N 轮直到 convergence(2N) | 2N(N=3-5) | 真,ROI 递减 | 高(收敛检测复杂)|

### 4.3 选择 B — 理由

1. **2 轮足够撞透 adversarial debate 工业难题**:第 2 轮才出现 "shared state 同步" / "convergence 终止" / "judge bias when seeing both versions" — 简历亮点
2. **真"对抗"** vs A 的"独立陈述":bull v2 真在反驳 bear v1 弱点 → narrative quality 真升级,而非平均化
3. **cost 可控**:4 LLM call(2 round × 2 agent)≈ 单 Writer 1.5x,可接受。C 的 N 轮 cost 不确定
4. **学术界 multi-agent debate 主流做法**:AutoGen / MetaGPT 等 framework 默认 2-3 轮,2 轮覆盖率最高

### 4.4 评估

- Round 1:BullAdvocate + BearAdvocate parallel(asyncio.gather)≈ 1 advocate 的 latency
- Round 2:同 parallel ≈ 1 advocate 的 latency
- 总 latency ≈ 2 advocate latency(parallel 节约)
- 总 cost ≈ 4 LLM call × fast tier ≈ baseline Writer LLM call 的 30%(fast tier cheaper)
- Round 2 advocate prompt 加 round 1 对方输出 → prompt token 增长 ~30%,仍在 budget

## § 5. 决策 Q3 — 输出形态:v2 final + strongest argument + synthesis trace(C 选项)

### 5.1 问题

debate 完后,**给 Writer 看什么**?

### 5.2 Alternatives

| 选项 | schema 字段 | Writer prompt 长度 | 可观测性 | 简历亮点 |
|---|---|---|---|---|
| **A** | 只 final v2 list × 2 | +2 字段 | 短 | 弱 | "list" 单线 |
| **B** | 全 trace(v1 + v2 + rebut targets)| +6 字段 | 长(5K+ token 增量)| 强 | over-engineering |
| **C** | v2 final + strongest argument 自评 + synthesis trace(分流)| +5 字段 | 中 | 中(synthesis 进 trace 不进 prompt)| **强 — advocate self-evaluation 是 LLM 算法亮点** |

### 5.3 选择 C — 理由

**核心 design insight**:advocate **自评 strongest argument** 是 LLM 算法层有意义的设计点 — 强制 advocate 区分"凑数论据"和"真实强论据",防 advocate 论据稀释。这跟 A5a `OutlierDiagnosis.confidence` 同范式 — **LLM 输出自带元认知信号**。

Writer 拿到:
- `bull_case` / `bear_case`(= bull_v2 / bear_v2.arguments)
- `strongest_bull_point` / `strongest_bear_point`(= bull_v2 / bear_v2.strongest_argument)

`bull_v1` / `bear_v1` / `rebut_targets` 等完整 debate trace 进 `state.debate_trace`(可观测性 § 7),Writer 不直接读(避免 prompt token bloat)。

### 5.4 评估

- schema 加 5 字段(`bull_case` / `bear_case` / `strongest_bull_point` / `strongest_bear_point` 进 InvestmentRecommendation;`debate_trace` 进 ResearchState)
- Writer prompt 增量 ~1K tokens(可控)
- post-mortem dashboard 看 debate_trace 时能看完整对抗历史

## § 6. 决策 Q4 — Cost 控制:advocate fast tier + Writer balanced(B 选项)

### 6.1 问题

A5b 加 4 LLM call,如何控成本 + 保 narrative quality?

### 6.2 Alternatives

| 选项 | 描述 | 单 session 成本增量 | 故事性 |
|---|---|---|---|
| **A** | 全 balanced tier(advocate + Writer + Critic 全 balanced) | +60% / ~$0.015 | 平 |
| **B** | Advocate fast tier + Writer balanced | +20% / ~$0.005-0.008 | **强 — 跟 v0.8.5 TierRouter 一脉相承** |
| **C** | Adaptive by valuation_consistency(consistent → skip / moderate → fast / severe → balanced)| 0% - 60%(看 case) | 中 — 但逻辑错(数字 cross-check 跟 narrative bias 是不同问题)|

### 6.3 选择 B — 理由

1. **真正符合 task complexity**:advocate task("列 3-5 条论据,引用现有数字")是低复杂度 list-generation,Writer task("综合 + 改写 narrative")是高复杂度 synthesis。**Tier 应该 match task complexity,不是平均**
2. **简历叙事接 v0.8.5 范式**:"v0.8.5 TierRouter 让 critic fast、planner balanced,A5b 延续这个分层 — debate advocate 进 fast" — 一条主线
3. **撞工业难题**:fast tier LLM 可能给的论据深度不够 → dogfood 时校准 prompt 让 fast tier 输出 dense list → 撞 "tier vs quality trade-off" 真实问题(cost-aware engineering 亮点)
4. **不破坏 A5b 核心价值**:debate 价值是 "强制两个独立视角" 而非 "深度推理",fast tier 足够

C 选项**逻辑错**:数字 cross-check(A5a 管)跟 narrative bias(A5b 管)是不同问题,即使 valuation consistent 时,bull/bear 仍有价值(narrative bias 不依赖数字打架)。

### 6.4 评估

- Fast tier(qwen-turbo 同档)单次 ~$0.0008,balanced(qwen-plus 同档)~$0.0025
- 4 advocate × fast = $0.0032 增量(对比单 Writer balanced ~$0.005 baseline)
- 单 session 总成本:v0.8.5 baseline $0.025 + A5a $0.005 + A5b $0.005 ≈ $0.035(可接受)

## § 7. 决策 Q5 — Observability:DebateTrace + dashboard tab(B 选项)

### 7.1 问题

debate 是 4 LLM call,**怎么让 dogfood / 调试看到内部发生什么**?

### 7.2 Alternatives

| 选项 | 描述 | 工程量 | 实时性 |
|---|---|---|---|
| **A** | 复用 TraceService 不动(每 advocate 自动记 span)| 0 | post-mortem |
| **B** | DebateTrace dataclass + dashboard 加 debate tab | ~250 行 | post-mortem |
| **C** | trace_meta tag + SSE 实时事件 | ~350 行 | 实时 |

### 7.3 选择 B — 理由

1. **portfolio 验证 + dogfood 调试需要可视化 trace**:bull / bear 演化 + rebut 关系 + cost / latency breakdown 是核心 debugging surface
2. **post-mortem 够用**:你自己跑 ≤20 次 debate session 看 trace 就能 calibrate,不需要 SSE 实时
3. **dashboard 已有现成基础**(Harness Board / Reports tab 等),加一个 debate tab ~100 行 frontend 可控
4. **vs A**:A 看 trace 时需要手动拼 4 个 span 上下文,效率低;dashboard tab 一眼看清演化
5. **vs C**:实时 SSE 是 production polish(用户看 debate 过程),portfolio 用不到

### 7.4 评估

DebateTrace schema:
```python
class DebateTrace(BaseModel):
    bull_v1: AdvocateOutput
    bear_v1: AdvocateOutput
    bull_v2: AdvocateOutput
    bear_v2: AdvocateOutput
    total_cost_cny: float
    total_latency_ms: int
    rounds_completed: int  # 0/1/2 (failure path)
```

dashboard 视图:展示 bull v1→v2 + bear v1→v2 + 双方 rebut_targets 引用关系 + 成本面板。

## § 8. 架构 / 数据流

```
ResearchPlanner → DataCollector → Analyst (产 insights + valuation_analysis)
                                ↓
                                DebateOrchestrator (新 node)
                                │
                                ├── Round 1 (parallel via asyncio.gather):
                                │     BullAdvocate (fast tier) → bull_v1 (AdvocateOutput)
                                │     BearAdvocate (fast tier) → bear_v1
                                │
                                ├── Round 2 (parallel):
                                │     BullAdvocate (看 bear_v1) → bull_v2
                                │     BearAdvocate (看 bull_v1) → bear_v2
                                │
                                └── 输出:
                                      state.debate_trace = DebateTrace(...)
                                      Analyst.step() 写到 state(同 valuation_analysis 范式)
                                ↓
                                Writer (balanced tier)
                                │   prompt 加 cross-check block:
                                │     bull_case (= bull_v2.arguments)
                                │     bear_case (= bear_v2.arguments)
                                │     strongest_bull_point (= bull_v2.strongest_argument)
                                │     strongest_bear_point (= bear_v2.strongest_argument)
                                │   § 6 narrative 必须显式列举 ≥2 bull + ≥2 bear
                                │   post_process: classify_recommendation + position_size + 拷 valuation_analysis
                                │   post_process v1.x A5b: 也拷 bull_case / bear_case / strongest_*_point 进
                                │     InvestmentRecommendation 字段(从 state.debate_trace 派生)
                                ↓
                                Critic 8 维 (新增 dialectical_balance)
                                ↓
                                [retry on factuality OR valuation_consistency OR dialectical_balance < 7.0]
```

### 8.1 嵌入位置(B 选项落实)

- DebateOrchestrator 是**独立 node**,在 graph 里位于 Analyst 之后 / Writer 之前
- 或者**复用 Analyst 阶段**(Analyst node 内部 sub-step,跟 A5a `_maybe_compute_valuation_analysis` 同范式)— 推荐这个,**避免 graph 拓扑增加 1 个 node**

具体实施:Analyst.step() 调 `_maybe_run_debate(state)` 返 DebateTrace,写进 state_update。复用 A5a 已建立的 sub-step 模式。

## § 9. Schema 改动

### 9.1 新 schema:`AdvocateOutput`

```python
# backend/app/agents/debate_schemas.py (新文件)
from typing import Literal

from pydantic import BaseModel, ConfigDict, Field


class AdvocateOutput(BaseModel):
    """v1.x A5b: Bull/Bear advocate 单轮输出 schema (frozen)."""

    model_config = ConfigDict(frozen=True)

    arguments: list[str] = Field(min_length=3, max_length=5)
    strongest_argument: str = Field(max_length=300, description="advocate 自评最强一条")
    rebut_targets: list[str] = Field(
        default_factory=list,
        max_length=5,
        description="v2 才填 — 引用对方 v1 哪些论据被反驳(原文片段)",
    )
    confidence: Literal["high", "medium", "low"]


class DebateTrace(BaseModel):
    """v1.x A5b: 完整 debate 历史,dashboard 可观测."""

    model_config = ConfigDict(frozen=True)

    bull_v1: AdvocateOutput | None = None  # 失败 → None
    bear_v1: AdvocateOutput | None = None
    bull_v2: AdvocateOutput | None = None
    bear_v2: AdvocateOutput | None = None
    total_cost_cny: float = Field(ge=0.0)
    total_latency_ms: int = Field(ge=0)
    rounds_completed: int = Field(ge=0, le=2)
```

## § 10. Error Handling

| 失败场景 | 处理 |
|---|---|
| BullAdvocate round 1 LLM 失败 | catch + log warn → bull_v1=None;BearAdvocate round 1 仍正常跑(parallel 不阻塞) |
| Round 1 全失败 | DebateOrchestrator return None → state.debate_trace=None → Writer 不见 cross-check block(graceful skip 走 v0.8.5 单线路径) |
| Round 2 全失败但 round 1 成功 | 用 round 1 输出做 final(bull_case = bull_v1.arguments,bear_case = bear_v1.arguments)→ rounds_completed=1 |
| Round 2 单边失败(bull 成功 / bear 失败)| bull v2 + bear v1 ← 退到 round 1 final(避免 v1 vs v2 不对称的 unfair debate)|
| Pydantic schema 校验失败(LLM 返不合法 JSON)| 同 LLM 失败处理,retry 1 次(round 内)→ 仍失败:silent |
| Critic dialectical_balance scorer 在 bull_case / bear_case 都空时 | 评分 10.0 skip(跟 valuation_consistency=None 时同范式)|
