# v0.8.5 Constrained LLM Router with Self-Correcting Retry — Design Spec

> **Status:** Design (brainstormed 2026-05-05). Implementation deferred to v0.8.5 (after v0.8.4 ship).

## § 1 问题陈述

v0.8.4 的 Planner agent 是「自由生成 ResearchPlan」模式：

```python
# 当前 v0.8.4
class ResearchPlan(BaseModel):
    subtasks: list[Subtask]  # ← LLM 自由生成，每 Subtask.required_tools 自由组合
```

**3 个具体痛点（dogfood 验证）：**

1. **Prompt 改动 → plan 走样**：Planner prompt 加一句"请重视 KB 检索"，同 input 的 plan subtask 数量、tool 组合、顺序都可能变。
2. **评测失真**：Critic 6 scorers 的 `coverage` / `factuality` 评分混入 plan 自由度噪声 — 同 6 字段输入两次跑可能拿不同 plan，分数浮动 ±1.5。
3. **简历叙事不稳**：D6 系统化评测时无法 ground truth，「3 differential golden case 通过」变成 "在某个 prompt 版本下通过"，不可移植。

## § 2 8 个核心决策汇总

| # | 决策点 | 选择 | 否决项 |
|---|---|---|---|
| 1 | 架构方向 | LLM-driven router but schema 严约束 | 全 hardcode（去 LLM）/ LangGraph hard edges / Anthropic Skill bundle 替换整个 agent |
| 2 | Planner 输出 | `plan_id` (Literal 4 值) + `rationale` (≤200 字符) | 极简 router 无 rationale / router + subtask_count override |
| 3 | 6 字段 → plan_id 映射 | 主映射 + override 规则在 prompt | 严格 1:1（LLM 是装饰）/ 完全模糊（=plan-driven 老问题）|
| 4 | Subtask 内容 | template + ts_code format，required_tools hardcode | 全 hardcode 无个性化 / LLM 生成 description |
| 5 | 评测 | Unit test 防 regression + Critic 第 7 scorer plan_correctness | unit test only / scorer only |
| 6 | 改进闭环 | Production self-correcting retry，max 2 轮 | 离线 prompt iteration only / 混合 |
| 7 | tool inventory 扩展 | P0 + P1 共 8 新 tool（11 接口）| 不扩展 / P0+P1+P2 共 18 接口 |
| 8 | 金融 SOP 形态 | Skill bundle 文件（`app/skills/financial_research_sop.md`）| Inline prompt / Analytical tools(v0.8.6+) / 不加 |

## § 3 架构 overview

5-agent 架构不增不减，Planner 内部从「自由生成 ResearchPlan」改为「constrained LLM router」+ LangGraph 加 retry edge + Critic 加第 7 scorer。

```
ResearchPlanner (LLM router)
  ↓ output: (plan_id, rationale)
  ↓ Python: PLAN_REGISTRY[plan_id] → instantiate Subtasks (template format with ts_code)
  ↓
DataCollector (subtasks deterministic) → Analyst → Writer
  ↓
Critic (7 scorers — 加 plan_correctness)
  ↓
plan_correctness >= 8.5 OR planner_retry_count >= 2?
  YES → END
  NO  → retry edge
        ResearchPlanner.run(state, feedback=critic.plan_correctness.rationale)
        ... loop max 2 轮
```

## § 4 Components 改动

### § 4.1 `backend/app/agents/research_planner.py` — 重写

**旧（v0.8.4）:**
- 调 LLM 生成 `ResearchPlan(subtasks=[Subtask(description=..., required_tools=...)])`
- 4 plan template emphasis 写在 prompt 里，LLM 自由组合 subtasks

**新（v0.8.5）:**
- 调 LLM 仅输出 `(plan_id, rationale)`（schema enum 强约束）
- prompt 明确：默认主映射（objective → plan_id 1:1）+ 5-7 条 override 例外（user_message 含特定 keyword 时偏离主映射）
- 收 critic feedback 时（`retry_count > 0`），prompt 多附 critic.rationale 让 LLM 知道为什么被打回

**Output schema:**

```python
PlanId = Literal["capital_preservation", "stable_growth", "balanced", "aggressive_growth"]

class ResearchPlan(BaseModel):
    plan_id: PlanId
    rationale: str = Field(max_length=200, description="LLM 解释为什么选这个 plan")
    # subtasks 字段 deprecated — instantiate from PLAN_REGISTRY by plan_id
```

### § 4.2 新建 `backend/app/agents/plan_registry.py`

```python
class SubtaskTemplate(BaseModel):
    description_template: str  # "评估 {target_name}（{ts_code}）的财务健康度"
    rationale: str
    required_tools: list[ToolName]  # ToolName = Literal[5 个 tool 名]

PLAN_REGISTRY: dict[PlanId, list[SubtaskTemplate]] = {
    "capital_preservation": [...],   # ~4 subtasks 偏风险/财务/股息/下行保护
    "stable_growth":         [...],
    "balanced":              [...],
    "aggressive_growth":     [...],  # ~4 subtasks 偏成长/估值/行业/催化
}

def instantiate_plan(plan_id: PlanId, target_name: str, ts_code: str) -> list[Subtask]:
    return [
        Subtask(
            description=tmpl.description_template.format(target_name=target_name, ts_code=ts_code),
            rationale=tmpl.rationale,
            required_tools=tmpl.required_tools,
        )
        for tmpl in PLAN_REGISTRY[plan_id]
    ]
```

**4 plan 各自的 subtask 内容（description_template / required_tools）由 implementer 在 implementation 阶段设计 + dogfood 验证 + iterate**（plan 故意不写完整内容 — 见 `feedback_plan_specificity`）。 spec 契约只规定：每 plan 含 ~4 subtask，required_tools 从 5 个固定 enum 选 0-3 个 per subtask。

### § 4.3 新建 `backend/app/agents/critic_subagents/plan_correctness_scorer.py`

LLM-as-judge:

- **Input:** ResearchRequest 6 字段 + user_message + 选定的 plan_id + 选定的 rationale + override 规则原文
- **Judge prompt:** "评判 plan_id 选择是否符合 6 字段 + user_message。 评分 0-10。"
- **Output:** `score: float (0-10)` + `reasoning: str`

继承 `_BaseScorer`（跟 6 个现有 scorer 同 pattern）。 `Critic.scorers` list 6 → 7。

### § 4.4 `backend/app/orchestration/research_graph.py` — 加 retry edge

```python
graph.add_conditional_edges(
    "critic_subgraph",
    _retry_router,
    {"retry": "research_planner_node", "continue": END},
)

def _retry_router(state: ResearchState) -> Literal["retry", "continue"]:
    plan_score = state.critic_report.get_score("plan_correctness")
    if plan_score is None:
        return "continue"
    if plan_score < 8.5 and state.planner_retry_count < 2:
        return "retry"
    return "continue"
```

### § 4.5 `backend/app/agents/schemas.py` — ResearchState 加字段

- `planner_retry_count: int = 0`
- `planner_critic_feedback: str | None = None`（retry 时传给 Planner 的 critic.rationale）

### § 4.6 Tool inventory 扩展（P0 + P1，8 新 tool / 11 tushare 接口）

新建 8 个 Tool class（`backend/app/tools/`）+ TushareService 加对应 method：

| 新 Tool | tushare 接口 | 服务于哪些 plan |
|---|---|---|
| `get_daily_basic` | `daily_basic`（PE/PB/PS/股息率/总市值/换手率） | 全 4 plan（估值与流动性核心）|
| `get_balance_sheet` | `balancesheet` | capital_preservation（偿债能力）|
| `get_cashflow` | `cashflow` | capital_preservation + stable_growth（盈利质量校验）|
| `get_pe_history` | `daily_basic` 历史聚合 → 计算分位 | aggressive_growth + capital_preservation（估值高低判断）|
| `get_forecast` | `forecast` + `express` | aggressive_growth（领先指标）|
| `get_dividend_history` | `dividend` | stable_growth（红利配置要点）|
| `get_holder_change` | `stk_holdernumber` | aggressive_growth（散户化指标）|
| `get_money_flow` | `moneyflow` + `top_list` | aggressive_growth（短期资金博弈）|

5 个原 tool 保留（`get_stock_quote / get_financials / get_news / web_search / kb_search`）。 总计 13 tool。

`ToolName` Literal 由 5 → 13。 `PLAN_REGISTRY` 的 `required_tools` 从 13 个里选组合。

### § 4.7 新建 `backend/app/skills/financial_research_sop.md`

外置金融研究 SOP knowledge bundle，被 Analyst / Writer 的 system prompt 启动时读取注入。 内容覆盖 ~10-15 个研究维度的看法 + 解读规则：

```markdown
# 投资研究员 SOP（标准操作规程）

## 偿债能力评估
- 资产负债率 < 50% = 健康；50-70% = 警戒；> 70% = 高风险
- 流动比率 > 2 = 短期偿债无忧；1-2 = 一般；< 1 = 警戒
- 经营现金流 / 净利润 > 0.8 = 盈利质量好（利润真实变现）

## 估值水平
- PE 历史分位 < 30% = 低估；30-70% = 合理；> 70% = 高估
- PB 应结合 ROE 看（杜邦体系）— 高 PB 高 ROE 是合理溢价
- PEG = PE / 利润增速 < 1 = 估值合理；> 1.5 = 高估

## 成长性
- 营收同比 + 净利同比双升 = 健康；只有营收升净利降 = 警戒（成本扩张快于规模）
- 看 3 年复合增长率（行业景气可比性）
- ROE 提升 = 内生增长；下降 = 警戒（即使利润增也是规模扩张拖累）

## 行业地位
- 申万行业分位（市值 / ROE / 营收 ranking）
- 行业集中度（前 5 公司市占率）
- 政策/监管周期位置

## 风险因素
- 大股东质押率 > 50% = 平仓风险
- 限售解禁集中期 = 短期供给冲击
- 龙虎榜机构净卖出 = 短期资金流出
- ... (5-10 个 维度)

## 推荐评级与仓位规则
- recommend_buy: PE 历史分位 < 30% + 行业景气向上 + 财务健康
- recommend_overweight: 任意 2 个上述条件
- recommend_hold: 估值合理 + 财务健康，无明显催化
- recommend_underweight: 估值偏高 + 行业承压
- recommend_sell: 财务恶化 OR 治理风险 OR 估值显著偏高 OR 行业政策冲击

仓位建议（结合 risk_tolerance）:
- conservative + 高风险 = 0-3%
- moderate + 健康标的 = 5-12%
- aggressive + 强催化 = 15-25%
- very_aggressive + 强催化 = 25-30%（不超过）
```

**特点**：
- 单文件，version controlled，dogfood 时 iterate SOP 不动 prompt 代码
- Analyst / Writer 启动时 `_SOP_TEXT = (SKILL_DIR / "financial_research_sop.md").read_text()` 加到 system prompt
- 工程量小：~600 token markdown + 2 行 file read 代码

**为什么不放 inline prompt 里**？ 600 token SOP 全 inline 让 prompt 难读、难版本化。 单文件分离方便 dogfood 时实测哪段 SOP 写错（git history 可追溯）。

## § 7 风险 + 缓解

| 风险 | 概率 | 缓解 |
|---|---|---|
| LLM router 在 user_message 含模糊信号时 plan_correctness 低 → 频繁 retry | 中 | dogfood 收集低分 case → 加 unit test → 调 prompt（β 模式正是为此设计） |
| 4 plan template 的 subtask 内容设计不合理 → 整体报告质量低 | 中 | implementation 阶段 dogfood 5 ts_code × 4 plan = 20 case 实跑，主观 review |
| retry 收 critic feedback 后仍选错（不收敛） | 低 | max 2 轮硬上限 + Critic 评分扣分透明显示，用户能看到 |
| LLM cost 平均增 30-60%（plan_correctness scorer + 偶发 retry） | 低 | scorer cost ≤ ¥0.005，retry 触发率预计 < 15% |
| schema 变更 break v0.8.4 cassette | 高（必发生） | § 6.2 一次性重录 cost ≈ ¥1 |
| 8 新 tool 的 tushare API rate limit / 数据缺失 | 中 | TushareService 加 tier-1 retry + tier-2 graceful degrade（tool 返回 error 字段，DataCollector 继续）|
| financial_research_sop.md 内容设计不专业 → LLM 用错 SOP 误导分析 | 中 | dogfood 时人审报告 narrative，发现 SOP 错误立即修订（单文件 git log 易追）|
| 新 tool 数据返回 schema 变化 break Analyst prompt | 低 | 每 tool 严格 Pydantic args/output schema，Analyst 看的是结构化字段不是 raw |
