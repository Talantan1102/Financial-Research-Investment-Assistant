# 抽取保真度重建设计

> 记忆系统"把对话变成记忆事实"的环节(抽取器)又乱又不稳,评估已量化其写侧保真度仅 ~12%。
> 本设计走"模型无关的分层修复优先、每层用多跑取率量化、数据决定要不要换模型"(用户定向:选项一)。
> 全程自解释中文名,不用字母数字代号。

## 一、问题(评估已量化)

记忆系统的写管线里,**抽取器**负责把每段对话读成"用户事实"(谁对什么持什么观点、何时生效),写进图记忆。对话流记忆评估抓到:这一环又乱又不稳。

**量化**:白酒观点演化剧本(看多三年 → 看多两年 → 中性,跨 7 段会话)跑 3 次,写侧数据库断言聚合**仅 3/24 通过,Wilson 95% [0.04-0.31](~12%)**,且每次抽取结构都不同。

**五类翻车形态**(都来自真实 LLM 抽取的数据库 dump):

| 该做的 | 实际乱象(同一句"看多高端白酒,茅台五粮液,逻辑提价权",跑 3 次都不同) |
|---|---|
| 观点挂【白酒】板块 | 一会儿挂【茅台/五粮液】(个股)、一会儿【白酒Ⅱ】(行业)、一会儿【提价权】(概念)——**实体类型漂移** |
| 用"表达观点"关系 | 一会儿 EXPRESSED_VIEW、一会儿 PREFERS——**关系漂移** |
| 实体是名词 | 整句"看多高端白酒"被当成一个实体存进去——**脏实体** |
| 日期取对话时间 | 凭空编:valid_to=2027-04-01、reason 写"假设2025-04-15"、捏造时间区间——**幻觉日期** |
| 每次结果一致 | 作废链长度 1/2/3 版本随机、中性观点时而 active 时而被看多盖——**非确定性** |

抽取一乱,下游观点演化链就成不了形,系统记不住"用户现在对白酒什么看法、怎么变的"。这是整个记忆系统最弱的一环。

## 二、根因(分层,均引真实代码)

**先纠正一个事实**:抽取真跑的模型**不是** `claude-haiku-4.5`。`LLMExtractor.__init__` 的 `model="claude-haiku-4.5"` 是死参数,被 `MemoryLLMClientAdapter`(显式忽略 model)吞掉;实际由 `tier="fast"` 经 `TierRouter` 解析成 **deepseek-v4-flash**(弱快模型)。

1. **解码层最大熵(头号熵源)**:抽取调用链 `MemoryLLMClientAdapter.chat → LLMService.chat → _OpenAIAdapter.chat` 全程**不传 temperature / seed / response_format / tool-use**。`LLMService.chat` 签名里根本没有 temperature 形参;`_OpenAIAdapter.chat` 的 create 只有 `model/messages/max_tokens`;`LLMConfig.temperature=0.7` 是从未被读的死配置。抽取实际在**服务端默认温度 ≈ 1.0** 下自由文本采样 → 每跑结构都漂。**温度不降,prompt 改了也会被采样噪声稀释**,所以这是前置闸。

2. **prompt 层四缺**:`_EXTRACTION_SYSTEM_PROMPT` ——
   - **无对话日期锚**:用 `now()` 占位却从不在 prompt 注入"今天/这段对话发生在哪天"(user prompt 模板只有 episode_id+user+agent)→ 模型无时间锚,只能从训练分布采样一个貌似合理的日期 → 必然幻觉。
   - **无实体类型决策规则**:只教"选定类型后 label 怎么写"(Stock=ts_code、Industry=申万二级),从不教"这句该选哪个类型"。"看多高端白酒"在金融语义上**确实同时映射**行业(白酒Ⅱ)+代表股(茅台/五粮液)+主题(提价权),是真多实体歧义,prompt 不给优先级 → LLM 随机落子。更坏:"只抽用户显式表达的事实"反而**诱导模型替用户补具体个股**(高端白酒→茅台/五粮液),制造 Stock 误抽。
   - **无关系语义界定**:11 个关系类型平铺成一行字符串,零定义零边界零反例。EXPRESSED_VIEW 与 PREFERS 对"看多白酒"都成立 → 随机落一个。
   - **无 entity_label 形态约束**:没说"label 必须是名词性实体、不能是整句谓词短语" → 整句"看多高端白酒"放行。

3. **schema 层只查语法、且毁整批**:`ExtractedEntity/ExtractedEdge` 的 `field_validator` 只查"entity_type/rel_type 在不在白名单、importance 是不是三档"——纯成员资格校验,不查"归类对不对、label 规不规范、日期合不合理"。而且 pydantic 对 list 字段是**任一元素失败→整个 model_validate 抛 ValidationError**,`extract()` 对 `model_validate` 这行裸调用无 try/except,异常冒泡到 `PathBRunner` 的 `except Exception` → **一条坏边让整个 chunk 的事实全部丢失**。非确定性被这个 all-or-nothing 放大成段级波动。

4. **日期链 str 透传无兜底**:valid_from/valid_to 全程当不透明字符串,LLM 幻觉日期一路落 DB。唯一的兜底 `stamp_event_time` 在 prompt 外、**默认关**(生产 Celery 恒 False,只有评估显式开)、且**只覆盖 valid_from 不管 valid_to**。

5. **类型漂移→链永久脏(根因的下游放大)**:实体类型一漂就换 node_id,冲突消解 `conflict_resolver` 靠"源+关系+目标"精确三元组查现有边,目标 node 一变就 miss → 不作废旧观点 → 看多和中性落不同节点、互不覆盖 → 链永久脏。(实体归一已修了白酒/白酒Ⅱ 这层同义漂,但治不了 Industry↔Stock↔Concept 的**类型**漂。)

## 二·五、实测去风险结论(2026-06-09 端点探针,决定了下面的层级优先级)

写设计前先用只读探针(`_probe_endpoint.py` / `_probe_prompt_fix.py`)打真实端点(deepseek-v4-flash / DashScope)实测,**纠正了一个关键判断 + 验证了核心修法**:

1. **不是"高温随机",而是"系统性地错"**:对"看多高端白酒,提价权,茅台五粮液"这句,默认温下跑 4 次,4 次全是同一个**错**答案 `PREFERS → 600519.SH(Stock)`(关系错+实体错)。单 episode 上模型相当确定,只是稳定地挑错。先前 `--repeat` 看到的 run-to-run 漂主要来自跨会话/跨轮分组的累积,不是单次随机。
2. **prompt 规则是头号杠杆,且已验证一举生效**:在 system prompt 加"实体类型决策 + 关系裁决表"(target 板块→Industry、不补个股、逻辑进 properties;有方向词+对象→EXPRESSED_VIEW)后,同输入跑 4 次 → **4 次全对 `EXPRESSED_VIEW → 白酒Ⅱ(Industry)`**。弱模型照规则就对,且 4/4 完全一致。
3. **温度被端点接受但非主因**;**JSON 守约本就 4/4**,`response_format=json_object` 对解析率非必需(其 enum 强约束价值另算);**无需换模型**。

**结论 → 重排杠杆优先级**:把"prompt 裁决规则"提到第一(已实测一举纠错+稳定),温度/结构化/后校验降为**辅助加固**。这正是先去风险的价值——避免了把力气先砸在温度上(那不是主因)。

## 三、设计:分层修复(prompt 规则为主、其余加固,每层用多跑取率量化)

核心方法论:**加一层、量一次**。每层落地后跑 `viewpoint-baijiu --repeat 5`,看写侧通过率与 Wilson 区间是否收窄、run-to-run 是否趋同。按实测后的优先级排:**prompt 裁决规则(已验证主杠杆)→ 日期钉死 → 解码低温 → 结构化+逐边容错 → 自一致兜底**。

### 裁决规则层(prompt,★主杠杆·已实测一举生效,中)

放在最前,因为实测它单独就把"看多高端白酒"从 PREFERS→茅台(Stock)纠正到 4/4 全对 EXPRESSED_VIEW→白酒Ⅱ(Industry)。把"该挑哪个实体/哪个关系"从模型自由发挥变成有规则:

- **实体类型决策树 + 优先级**:观点的 target 按"用户表态的主体粒度"定——
  - 说"看多白酒/这个板块" → Industry(白酒Ⅱ);说"看多茅台/这只" → Stock;纯逻辑/主题 → Concept。
  - 一句话同时提行业+个股+逻辑时,**主 target 取用户表态的主语**("看多高端白酒"主语是板块→Industry),逻辑(提价权)放进 `properties.logic`,**不单独成观点边**;具体个股若用户只是举例(茅台五粮液)不单独建 EXPRESSED_VIEW。
  - 配反例:"❌ 用户说'看多白酒'别擅自抽成对茅台的观点"。
- **明确反制凭空补个股**:加规则"用户只说板块时,不要替他补具体个股标的"。
- **关系裁决对照表**(写进 prompt,让模型照表挑关系,不再随机落子)。当前 11 个关系类型只平铺一行名字、零判别依据,导致"看多白酒"随机被标 EXPRESSED_VIEW 或 PREFERS。对照表给每个关系一个判别要点 + 一句真实用户台词正例:

  | 用户说 | 该用的关系 | 判别要点 |
  |---|---|---|
  | "我看多白酒" / "茅台被高估了" / "白酒转中性" | EXPRESSED_VIEW(表达观点) | 对【某具体标的/行业】的**多空方向判断**(看多/看空/中性) |
  | "我偏好低估值高股息" / "喜欢价值投资" | PREFERS(偏好) | 跨标的的**风格/策略习惯**,不针对某一标的涨跌 |
  | "我不碰杠杆" / "不投题材小盘" | AVOIDS(规避) | 明确排斥的东西 |
  | "我在看新能源" / "帮我盯着宁德" | WATCHES(关注) | 关注了但还没下方向判断 |
  | "我研究过隆基年报" | STUDIED | 做过研究 |
  | "我持有600股茅台" | HOLDS | 持仓 → 归持仓模块,**不入记忆**(策略 A) |
  | "我把茅台卖了" | SOLD | 卖出动作 |

  **最易混的"表达观点 vs 偏好"判别死规则**:有"方向词(看多/看空/中性/高估/低估)+ 具体对象"=EXPRESSED_VIEW;只有"喜欢某种风格/策略"无具体标的方向=PREFERS。"看多白酒"必为 EXPRESSED_VIEW,**绝不可标 PREFERS**(这是评估里反复翻车的点)。
- **entity_label 形态约束**:必须是名词性实体,禁"看多/看空/买入…"开头的整句谓词短语。

### 解码低温层(辅助加固,小)

- 给**抽取专用**低温:抽取链显式传**低温(如 0.1–0.2,非 0)**。用户决策:不取 0——低温已把服务端默认 ≈1.0 的熵砍掉大半、又不至于让弱模型退化/脆化;残余抖动交给验收的 `--repeat` 多跑取率消化,不追求单跑完全一致。
- **关键约束**:`_OpenAIAdapter.chat` 是全 app 共享 chokepoint,**绝不动全局默认**(chat/research 需要创造性)。做法是给 `chat()` 链加一个可选 `temperature` 参数,**仅抽取路径传低温**,其余调用不变。
- **实现首步必做**:实测 deepseek-v4-flash 在 DashScope 兼容端是否真吃 `temperature`(开放问题,见六)。

### 日期钉死层(按 session 定,小)

日期不该靠 LLM 记。两手:
- **prompt 注入对话日期锚**:user prompt 模板塞"当前对话日期=<episode.created_at>";system prompt 加硬规则"valid_from 必须等于对话日期、不许假设/编造;观点未结束 valid_to 必须 null"。
- **代码钉死(更彻底)**:`stamp_event_time` 默认开 + 扩展到 valid_to——valid_from 由 episode 时间覆盖,valid_to 未结束强制 null。让 LLM 只管语义,日期完全由 episode 时间钉死,把幻觉移出 LLM 职责。
- **后校验兜底**:越界日期(episode 之外/未来)一律重置或丢该字段,不只是当前的"不可解析才 skip"。

### 结构化+逐边容错层(加固,中)

- **结构化输出**:抽取调用传 schema。最低 `response_format=json_object`(注意 DashScope 要求 prompt 含 "json" 字样,已知坑);进一步用 tool-use 把 `entity_type`/`rel_type` 设成 **enum**,从解码侧直接挡掉非法/越界取值。
- **校验改逐边容错**:把"一条坏边毁整批"改成"坏边丢弃+留痕、好边照常入库"。`model_validate` 包 per-edge try/except,`field_validator` 失败的边记 audit 跳过,不让整 chunk 全灭。
- **后校验护栏**(prompt/解码仍漏网的硬兜底):拒幻觉日期、拒脏 label(谓词短语模式)、entity_type 一致性检查。

### 自一致兜底层(可选,前面都做完仍不达标才上,大)

- 同 chunk 抽 N 次(N=3),对 (entity_type, rel_type, target) 做多数投票,日期取对话锚。
- 成本×N、延迟×N,Path B 是会话末批量、可接受;但**仅当前面各层做完仍不达标时才上**(实测裁决规则已给 4/4,边际收益可能很小)。

## 四、验收(评估驱动,这正是评估体系的兑现)

- 每层落地后跑 `viewpoint-baijiu --repeat 5`,记录写侧通过率 + Wilson 区间 + run-to-run 一致性。
- **目标**:写侧从 3/24(~12%)提升到 **≥ 18/24(75%)** 且 `--repeat` 多次结果趋同(方差显著下降);观点演化链稳定成形(看多→中性 落同一节点、旧版作废)。
- 达标后扩到 viewpoint 全族(8 段)+ time 族(5 段)`--repeat` 复测,确认不是只过拟合白酒一段。
- 全程 TDD:每层改动配 L0/L1 测试守护(prompt 注入、温度下传、逐边容错、后校验护栏各自有测)。

## 五、不做(克制,符合作品集定位而非生产级)

- **不动全局 LLM 温度**:只给抽取专用通道传低温(0.1–0.2),不波及 chat/research。
- **不重写 conflict_resolver**:实体归一(已做)+ 类型稳定后,精确三元组查询自然命中、链自成形。
- **自一致默认不开**:成本×N,作为前四层不达标的增量手段。
- **不引重型依赖、不追生产级健壮**:够把评估写侧抬到目标即可。
- **暂不换模型**:按选项一,先把模型无关层做到顶、用数据说话;deepseek-flash 加到顶仍不达标再议换 haiku/sonnet。

## 六、开放问题(实现首步/评审时定)

1. **端点能力实测 —— 已用探针测掉大半(见二·五)**:`temperature`(低温)**端点接受**✓;`json_object` 探针那档无返回(疑 hang/拒,需实现时再确认,但 JSON 守约本就 4/4、非必需);tool-use enum 未测。**最关键的"裁决规则 prompt 是否有效"已验证 4/4 纠正**。剩 `json_object`/enum 的确认放进结构化层实现时做,不阻塞主路径。
2. **实体粒度业务口径**:"看多高端白酒"主 target 钉 Industry(白酒Ⅱ),逻辑进 properties 不单独成边——这个口径要和 conflict_resolver 演化链定义 + 评估断言对齐(评估断言已期望 EXPRESSED_VIEW→白酒,口径一致)。是否允许同时落一条 Concept(提价权)边作辅助?默认**不**(避免多边干扰链),留口。
3. **生产 chat 抽取影响面**:抽取 prompt/结构化/温度改动会同时影响生产 Path A/Path B(Celery)。需确认这些是纯增强(更准更稳)不破坏现有行为,且 cassette 测试覆盖。
