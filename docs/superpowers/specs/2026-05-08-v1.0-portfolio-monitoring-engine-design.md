## § 1 决策摘要

### 决策 1:5 类公告 = 复用 `announcement` SignalRule,LLM prompt 收紧到 5 类

**问题**:product spec § 5.2 钦定 5 类公告(财报披露/业绩预告/ST/重大重组/重大处罚),怎么落到工程?

**业界 alternatives**:
- A. **复用现 `announcement` rule,LLM prompt 收紧到 5 类**(本决策)
- B. 拆 5 个独立 SignalRule(announcement_earnings / announcement_warning / ...)
- C. announcement 下分子类(LLM 输出 type + score,rule 内 dispatch)

**对比表**:

| 维度 | **A 复用 prompt** | B 拆 5 独立 rule | C 子类 dispatch |
|---|---|---|---|
| 工程量 | prompt 改写 + 5 类 enum + 测试 ~1 天 | 5 rule 文件 + 注册 + 测试 ~3 天 | A + 子类 dispatch ~2 天 |
| SignalRule 体系 | 5 → 5(不变) | 5 → 9 | 5 → 5(announcement 内变厚) |
| 详情卡 prompt 复用 | LLM 一次输出 type + summary,链路对齐 | 各自调 LLM,prompt 重复 | A 一致 |
| per-type 阈值差异化 | 不支持(spec 没要求) | 天然支持 | 留口子 |

**取舍**:A。

**理由**:
- spec § 5.2 + § 8.1 显式列了"v1.x 才考虑大股东减持/回购等",**当前没 per-type 差异化阈值需求** — B/C 提前为不存在的需求买单
- 5 SignalRule 体系结构不动,跟 v0.8.3 已 ship 模式一致
- LLM 一次输出 `{type, score, summary}`,详情卡可以复用 summary 字段,prompt 链路对齐

**量化评估**:
- A 路径:`announcement.py` 改 ~50 行 + LLM prompt 改写 + 5 类 enum + L0 测试 ~80 行
- 触发逻辑:type ∈ 5 类 且 score ≥0.8 → RED;type ∈ 5 类 且 0.5 ≤ score < 0.8 → YELLOW;其他 → GREEN
- 误报控制:单一 LLM 决策,可控;比 B 路径"5 个 rule 互相 trigger"更干净

### 决策 2:Scope = 删 `monitoring_customers`,scope 直换 `Position`

**问题**:v0.8.3 引擎 scope 是 `monitoring_customers`(独立 ts_code,无 user 维度),v1.0 需要 user × ts_code(从 Position 表)。怎么迁?

**业界 alternatives**:
- A. **删 `monitoring_customers`,scope 直换 Position**(本决策)
- B. 保留 customers,Position 写时同步 customers
- C. 加适配层 `load_active_subjects(scope_type)`,scope_type ∈ {customers, positions}

**对比表**:

| 维度 | **A 直换** | B 同步 | C 适配层 |
|---|---|---|---|
| 工程量 | run_scan 入口改 + drop 表 ~1.5 天 | Position write hook + 双表测 ~0.5 天(留债) | 适配层 + 双路径测 ~1 天 |
| 一致性 | Position 是 single source | 两表同步噩梦 | 单一抽象 |
| 跟 PR #34 决策 1 一致性 | 一脉相承(Position = Trade materialized 唯一抽象) | **架构倒退**(再加一张同步表) | 中间路线 |
| YAGNI | 干净 | 留死代码 | customers 路径以后没意义 |

**取舍**:A。

**理由**:
- Position 是 v1.0 的正确抽象,`monitoring_customers` 是 v0.8.3 的过渡产物(那时还没 user / 持仓概念)
- 不清算反而是技术债;**作品集叙事价值在于"v0.8.3 customers 是过渡 / v1.0 用 Position 是正确"的迁移叙事**
- spec § 8.1 显式不做 banking RM,A 不破坏架构口子(SignalRule 接 user_id 后,multi-tenant 加 tenant_id 列即可)

**量化评估**:
- A 路径:`monitoring_service.run_scan()` 改入参 `customer_ids` → `user_ids`;内部从 `positions` 表 join 拉 `(user_id, ts_code)`;`SignalRule.evaluate(user_id, ts_code)` 接口改造;drop monitoring_customers 表
- 改动 ~150 行 + L0/L1 重测 ~200 行
- v0.8.3 dogfood 阶段无生产用户,**直接删表不留兼容层**(memory `feedback_no_backward_compat_hacks`)

### 决策 3:详情卡预生成 = Celery + Redis 异步队列(承接 PR-D 提前)

**问题**:spec § 5.4 已定"预生成 / 用户点开 < 1s",detection cycle 标红那一刻怎么剥离 LLM 调用(LLM 耗 30s+,会阻塞 cycle)?

**业界 alternatives**:
- A. `asyncio.create_task` 进程内 fire-and-forget(minimalism 推荐)
- B. APScheduler one-shot job(复用现 scheduler)
- C. **Celery + Redis 异步队列**(本决策)

**对比表**:

| 维度 | A 自家厨房 | B 闹钟单跳 | **C 外卖系统** |
|---|---|---|---|
| 工程量 | ~1 天,零新依赖 | ~1.5 天,无新依赖 | ~3 天,加 Celery + Redis broker |
| 进程重启容忍 | 丢 in-flight | 丢 in-flight | **不丢**(Redis 持久化) |
| 可观察 | log only | log only | **flower / Celery events** |
| 跟 minimalism | 最贴 | 中 | **scope 扩张**(违反默认推荐) |
| 跟 roadmap #3.5 PR-D | 无重叠 | 无重叠 | **承接 PR-D Redis 提前到 v1.0** |

**取舍**:C。

**理由(显式承认违反 minimalism 默认推荐,见 memory `product_minimalism_default`)**:
- **作品集叙事**:工业级架构(Celery + Redis broker + worker 集群)是 LLM 应用 portfolio 的可见技术深度,面试 / 简历加分项
- **跟 roadmap #3.5 PR-D 一起做**:PR-D 本来就要装 Redis broker,v1.0 提前 ship 后 PR-D 缩窄到 cache 抽象层
- **失败容忍 by design**:Celery autoretry max_retries=2 + acks_late + worker 重启不丢,production-grade 故障模型
- **30 分钟 cycle 自然兜底**:即使 worker crash,30 分钟下一轮 detection 自动重新 enqueue,失败成本低

**量化评估**:
- 工程量:Celery + Redis 装 ~0.5 天 / `generate_detail_card` task ~0.5 天 / autoretry 配置 + 测试 ~1 天 / Celery worker fixture(对齐 pg_test_container_pattern)~1 天 = 3 天
- LLM cost:LLM 调用只对标红 alert(spec § 5.4),非全持仓;v1.0 dogfood 量级 ≤ 5 alert/cycle × 48 cycle/day = 240 LLM calls/day(可控)
- Redis 资源:dogfood ≤ 100 task/day,Redis 内存 < 10MB

### 决策 4:调度源 = Celery beat 全替代 APScheduler

**问题**:30 分钟刷新调度怎么实现?复用现 APScheduler 还是切 Celery beat?

**业界 alternatives**:
- A. APScheduler 不动 + Celery 处理(混合)
- B. **Celery beat 全替代**(本决策)

**量化评估**:

## § 2 架构总览

### 2.1 进程结构(部署后跑 4 个进程 + Redis)

```
┌─────────────────────────────────┐    ┌───────────────────┐
│  Web 进程 (FastAPI)             │    │  Redis broker     │
│   ─ /portfolio/* (用户 CRUD)    │    │   ─ task queue    │
│   ─ /monitoring/refresh (手动)  │ ←→ │   ─ celery beat   │
│   ─ /signals (dashboard 读)     │    │     schedule      │
└─────────────────────────────────┘    └─────────┬─────────┘
                                                 ↑↓
            ┌────────────────────────────────────┴────────────────┐
            │                                                     │
   ┌────────▼────────────┐                              ┌────────▼─────────────┐
   │ Celery beat 进程    │                              │ Celery worker 进程   │
   │  ─ schedule:        │                              │  ─ task:             │
   │    detection_cycle  │     enqueue                  │    detection_cycle   │
   │    (每 30min, 盘内) │ ──────────→  Redis  ───────→ │    generate_detail   │
   │    daily_full_scan  │                              │    cleanup_old       │
   │    (16:30 兜底)     │                              │  ─ concurrency: 4    │
   └─────────────────────┘                              └──────────────────────┘
```

### 2.2 核心数据流

**30 分钟 detection cycle(盘内时段)**:

1. Celery beat 时间到 → enqueue `detection_cycle` task
2. Worker 捡 task,从 `positions` 表拉所有 `quantity > 0` 的 `(user_id, ts_code)` 对
3. 对每只 ts_code(去重)调 `SignalDetector.detect()` 跑 5 SignalRule
4. 异动判定:任一 rule RED/YELLOW → 写 `monitoring_signals/alerts` 表标红
5. 标红那一刻 → enqueue `generate_detail_card(alert_id)` task(异步预生成)
6. 同时刷新 `positions.last_quote_price` / `last_quote_at`(跟 § 1 决策 3 portfolio 协同)

**详情卡预生成**:

7. Worker 捡 `generate_detail_card` task → 调 Writer(alert_writer mode)→ `UPDATE monitoring_alerts SET report_json/markdown, detail_status='ready'`
8. 失败:Celery autoretry max_retries=2,最终失败记 `detail_status='failed'`,用户点开看 fallback 简版

**用户读路径(dashboard)**:

9. `GET /signals?user_id=…` → 读 `monitoring_signals + alerts + positions`(无 LLM)
10. `GET /signals/{alert_id}/detail` → 读 `monitoring_alerts.report_markdown`(预生成 < 1s)

### 2.3 边界

- **Web 进程不直接调 LLM** — 所有 LLM 调用都在 worker 里
- **detection cycle 不阻塞** — 标红写完立刻返回,详情卡 task 独立队列
- **失败容忍 by design** — 单 task 失败不影响 cycle 继续,30 分钟下一轮自然兜底

### 3.2 详情卡 = 改造 monitoring_alerts(不新建表)

`monitoring_alerts` 已有 `report_json / report_markdown / deep_dive_text` 三个内容字段,刚好对应详情卡需要的"标题 / 正文 / 深度挖掘"。v1.0 加 `detail_status` 状态机:

```
detection_cycle 标红
   ↓
INSERT monitoring_alerts (..., detail_status='pending')
   ↓ enqueue Celery
generate_detail_card task
   ↓
UPDATE monitoring_alerts SET report_json=..., report_markdown=..., detail_status='ready'
   或失败 SET detail_status='failed', error_message=...
```

读路径:
- `detail_status='ready'` → 渲染 `report_markdown`
- `detail_status='pending'` → 渲染"详情卡生成中"占位
- `detail_status='failed'` → 渲染 fallback(标题 + 公告 raw 链接 + 错误提示)

## § 4 组件细节

### 4.1 Celery task 清单

| Task | 入参 | 干啥 | 队列 |
|---|---|---|---|
| `detection_cycle` | trading_day_only flag | 主 detection;扫所有 (user_id, ts_code);写 monitoring_runs/signals/alerts;标红 enqueue generate_detail_card | `default` |
| `generate_detail_card(alert_id)` | alert PK | 异步预生成详情卡;调 Writer alert_writer;UPDATE alerts.report_json/markdown + detail_status | `llm` |
| `daily_full_scan` | 无 | 16:30 收盘后兜底全量(覆盖 30min cycle 漏掉的) | `default` |
| `cleanup_old(days=7)` | 天数 | 清 7 天前的 monitoring_runs/signals/alerts | `default` |

队列分两个:
- `default` — detection 类(短任务、无 LLM、批量并发)
- `llm` — 详情卡 / deep_dive(单任务长、LLM 阻塞、并发要限,`rate_limit="5/m"`)

worker 启动:`celery -A app.tasks worker -Q default,llm --concurrency 4`

### 4.3 announcement rule 改造(决策 1)

```python
# backend/app/services/monitoring/signal_rules/announcement.py
SYSTEM_PROMPT = """你是 A 股公告分类器,只判定以下 5 类:
1. 财报披露(季报/半年报/年报)
2. 业绩预告(预增/预减/预亏)
3. ST / 退市风险警示
4. 重大资产重组 / 并购
5. 重大监管处罚 / 立案调查

如果不属于这 5 类(如减持/回购/高管变动),type 必须是 "其他"。
"""

USER_PROMPT_TEMPLATE = """公告标题:{title}
摘要:{summary}

输出 JSON:
{{"type": "<5类之一 or 其他>", "score": <0-1>, "reasoning": "<一句话>"}}
"""
```

`evaluate()` 触发逻辑:
- `type=="其他"` → GREEN
- `type ∈ 5 类 and score ≥0.8` → RED
- `type ∈ 5 类 and 0.5 ≤ score < 0.8` → YELLOW
- 其他 → GREEN

### 4.4 price_anomaly rule 对称化(spec § 5.1)

| 现 v0.8.3 | v1.0 |
|---|---|
| 单日**跌** ≥10% → RED | 单日 \|涨跌\| ≥10% → RED |
| 单日**跌** ≥5% → YELLOW | 单日 \|涨跌\| ≥5% → YELLOW |
| 60d 累计跌 ≥20% → YELLOW | **保留**(长趋势警示) |

### 4.5 SignalRule scope 联动 Position(决策 2)

```python
# v0.8.3
class SignalRule:
    async def evaluate(self, customer_id: str, ts_code: str) -> SignalResult: ...

# v1.0
class SignalRule:
    async def evaluate(self, user_id: UUID, ts_code: str) -> SignalResult: ...
```

`detection_cycle` 主流程伪码:

```python
@celery_app.task
async def detection_cycle():
    cycle_id = str(uuid.uuid4())
    positions = await db.execute(
        select(Position.user_id, Position.ts_code).where(Position.quantity > 0)
    )
    # 按 ts_code 去重(同一只股跨 user 共享 SignalDetector 结果)
    unique_codes = {ts_code for _, ts_code in positions}

    sem = asyncio.Semaphore(5)
    async def _scan(ts_code):
        async with sem:
            return await SignalDetector().detect(ts_code)
    results_by_code = {
        ts_code: await _scan(ts_code) for ts_code in unique_codes
    }

    # 把 SignalDetector 结果展开到 (user_id, ts_code) 维度
    for user_id, ts_code in positions:
        result = results_by_code[ts_code]
        if result.level in ("YELLOW", "RED"):
            alert_id = await create_alert(
                cycle_id, user_id, ts_code, result, detail_status="pending"
            )
            generate_detail_card.delay(alert_id)
        # 顺手刷新 Position.last_quote_price/at(跟 portfolio 决策 3 协同)
        await update_position_quote(user_id, ts_code, result.quote_snapshot)
```

注意:`SignalDetector.detect(ts_code)` 按 ts_code 去重(多 user 持有同股,LLM 调用只跑一次),**节省 API + LLM 成本**。

### 4.6 手动 /monitoring/refresh endpoint

spec § 5.3 提到"手动刷新按钮"。`POST /monitoring/refresh` → `detection_cycle.delay(user_filter=current_user_id)` → 立即返回 `task_id`。前端轮询或 SSE 看进度(SSE 实施推 v1.x,v1.0 用轮询)。

## § 5 错误处理

### 5.1 LLM 失败(`generate_detail_card`)

```python
@celery_app.task(
    autoretry_for=(LLMError, anthropic.APIError, openai.APIError),
    retry_backoff=True,        # exponential: 60s, 120s, 240s
    max_retries=2,
    rate_limit="5/m",          # 防烧 API quota
)
def generate_detail_card(alert_id: str):
    try:
        content = await writer.alert_writer(alert_id)
        update_alert(alert_id, report_json=content, detail_status="ready")
    except LLMError:
        raise  # autoretry kicks in
```

最终失败:`detail_status='failed'` + `error_message`;用户看 fallback;30 分钟下一轮自然 enqueue 重试(idempotent)。

### 5.2 Worker crash / 进程重启

```python
task_acks_late = True              # 跑完才 ack,crash 时 Redis 重派
worker_max_tasks_per_child = 100   # 防内存泄漏
worker_prefetch_multiplier = 1     # 不预取,crash 不丢多个
```

要求 task idempotent:
- `generate_detail_card(alert_id)` UPDATE 同行 — 安全
- `detection_cycle` 加 `cycle_id` UNIQUE + ON CONFLICT 跳过 — 不重复

### 5.3 Redis broker down

(A) Web 进程 enqueue 失败 → log + metrics + `detail_status='pending'` 保持(下一轮 cycle 自然补)

(B) Beat 失联 → detection 不触发 → dashboard 数据过期。**v1.0 不实施降级**(spec § 8.1 显式不做监控自己的 Redis 状态),留 v1.x。

### 5.4 Tushare API quota 耗尽

SignalRule 内 try/catch,失败返回 `SignalResult(level='GREEN', explanation='quota exhausted')` — 30 分钟下一轮自然恢复。**不重试**(quota 重试加剧)。

### 5.5 detection_cycle 超时

```python
@celery_app.task(soft_time_limit=300, time_limit=600)
def detection_cycle(): ...
```

dogfood 量级 ≤ 20 持仓,实测 < 30s。设 5 分钟 soft 给"未来 100 持仓 + 5 类公告 LLM"留余量。

### 5.6 数据库连接失败

主 PG 用 `pool_pre_ping=True`;失败 task `autoretry_for=(SQLAlchemyError,)`。

### 5.7 不做的(spec § 8.1 + YAGNI)

- ❌ Dead letter queue 单独 Redis 队列 — 失败状态记 alerts 表
- ❌ Sentry / 集中告警 — log + metrics 即可,v1.x 真痛了加
- ❌ detection cycle 跨进程分布式锁 — Celery beat 单例已保证
- ❌ Redis 连接池限流 — celery 自带
