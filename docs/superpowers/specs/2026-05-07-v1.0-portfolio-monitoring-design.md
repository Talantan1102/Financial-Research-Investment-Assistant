## § 1 决策摘要

### 决策 1:v1.0 第二个 use case = 持仓监控(B-3 + C-4 一体两面)

**问题**:v0.9+ roadmap § 2 阶段 3 列出第二个 use case 候选(行业研究 / 财报速读 / 概念追踪),但都属 C 端 short-form。Brainstorm session 用"能否独立打 ChatGPT"做硬度测试,发现:
- C-2 行业判断 / C-7 术语解释:ChatGPT 强项,我们做不过,**显式不做**
- C-3 事件追踪:能独立打,但跟 B-1 工程重复度高、dogfood 频率低(一年 8-12 次)
- C-1 个股研究 / C-5 财报速读:1-2 个真痛点,**实为组件**,寄生在支柱里才成立
- **C-4 持仓分析 与 B-3 持仓监控 是一体两面**(后台 daemon + 用户视角),共享数据 + 监控引擎

**业界 alternatives**:
- **Bloomberg Terminal**:专业级,但订阅制(数千美元/月),只服务专业研究员
- **雪球 / 蛋卷**:覆盖持仓记录,但缺乏 LLM 异动解读 + 上下文累积
- **券商 App 自带"持仓告警"**:仅价格阈值,无公告事件 + 无 LLM 摘要
- **Tiger Trade / Webull**:实时行情但无 LLM 解读

**取舍**:作者明确选**持仓监控(B-3 + C-4)**作为 v1.0 第二个 use case。

**理由**(对比 C-3 事件追踪):

| 判据 | 持仓监控 | C-3 事件追踪 |
|---|---|---|
| 数据护城河 | 持仓数据 ChatGPT 原理上做不了(质的差距) | 中国市场标的映射(量的差距) |
| 投资闭环 | B-1 研究 + B-3 跟踪 = 完整 buy/hold/sell | 离散信息源,不构成闭环 |
| dogfood 频率 | 每天(场景 A 早盘前 + B/C 全天) | 一年 8-12 次(议息/重大新政) |
| 组件价值链 | 是 C-1 / C-5 等组件的天然宿主 | 离散,不串组件 |
| 工程互补 | 多了 rule engine + 事件流(扩展简历技术覆盖面) | 跟 B-1 retrieval + writer 重复 |

**核心洞察**:之前用"独立打 ChatGPT"判据推 C-3 是狭隘的。**真正的平台产品,use case 不需要个个独立打赢 ChatGPT,而是它们一起构成 workflow,workflow 整体打赢**。持仓监控就是这个 workflow 的"主轴"。

### 决策 2:9 个 use case 重新分类 — 3 支柱 + 组件群 + 砍 2 个

之前 spec 里"9 个 use case 共享底座"叙事是虚的。Brainstorm 后重新分类:

```
独立支柱(3 个):
  ├── B-1 深度尽调       — 长报告、5-10 分钟、慢思考(已 ship v0.8.4)
  ├── B-3+C-4 持仓监控   — 一体两面,后台 daemon + 用户视角(本 spec)
  └── C-3 事件追踪       — 时间线 + A 股标的映射(留 v1.x)

组件(寄生在支柱里):
  ├── B-7 报告追问       — 寄生在 B-1
  ├── C-1 个股研究       — 寄生在 B-3 持仓 / 升级到 B-1
  └── C-5 财报速读       — 寄生在 B-3 监控 / B-1 财务节

显式不做(ChatGPT 强项):
  ├── C-2 行业判断       — 通用 LLM 在宏观行业判断上强,KB 13 篇覆盖不了
  └── C-7 术语解释       — 通用 LLM 教学解释能力远超任何垂类产品
```

**简历叙事改进**:从"9 个 use case 的平台"(虚)改为"**3 个支柱场景 + 组件式延伸,显式做了 use case 取舍砍掉 ChatGPT 强项的领域**" — "做减法的产品判断"是比"做加法的工程能力"更值钱的简历点。

### 决策 3:产品哲学 = aggressive minimalism

Brainstorm session 中,作者在每个产品决策点都倾向最克制版本。这是有判断的克制,而非 timid:**broad 平台路线最大风险是"什么都想做永远不 ship",克制对抗这个风险**。

具体体现:
- 推送、CSV 导入、券商 API、Watch list、价格触达、静默仓位 → 全推 v1.x
- 异动详情卡 D 区动作 → 砍("没必要")
- 30 分钟刷新而不是 5 分钟(更克制)
- 已查看回顾区 → 砍
- C-2 / C-7 use case → 砍

后续所有 v1.0 实施决策应**默认走克制版本**,v1.x escape hatch 通过架构留口子方式提供。

## § 3 产品 scope 边界(4 核心决策)

### 3.1 推送敏感度阈值 = 保守(±5% + 5 类公告)

**业界 alternatives**:
- 激进(±2% + 任何新闻):眼球抢但用户疲劳关闭通知
- 中等(±3-4%):仍偏频繁
- 保守(±5% + 重大公告):频次低但每次必有信号

**取舍**:保守。理由:v1.0 先训练用户信任,阈值调错可以再调,但用户关掉通知是永久性损失。

**协调**:阈值的意义在 v1.0 是"该不该在 dashboard 上高亮",不是"该不该 push"(见 3.3 不做推送)。dashboard 标红错了用户少看一眼(可逆),不会毁信任。

### 3.2 数据录入 = 手输

**业界 alternatives**:
- 手输:0 工程依赖,但 onboarding 摩擦
- CSV 导入:中等摩擦(用户得准备 CSV)
- 券商 API 接入:0 用户摩擦,但工程量大 + 各券商 API 不一

**取舍**:手输。理由:v1.0 优先 ship,CSV 留 v1.x,券商 API 留 v1.x+。

### 3.3 通知方式 = 仅 dashboard 标红(不做推送)

**取舍**:不做手机推送 / 邮件 digest。理由:推送基础设施成本高(需要 push channel 实现),v1.0 优先验证产品形态。dashboard 标红 + 用户主动打开覆盖 80% 真实使用场景。

**留口子**:架构上保留 push channel interface(空实现),v1.x 可平滑接入。

### 3.4 用户范围 = 仅散户(banking RM 留架构口子)

**取舍**:RM 视角不做真实施。理由:作者无法 dogfood RM 体验,避免在想象上花工程。

**留口子**:Trade / Position schema 都带 `user_id`,UI 不暴露 multi-account。

## § 4 数据模型

### 4.1 核心实体

```
Trade(交易记录 — 用户真正录入的)
├── id (auto)
├── user_id (multi-account 留口子,UI 不暴露)
├── 标的代码 (必填,tushare autocomplete)
├── 标的名称 (auto from tushare)
├── 类型 (买入 / 卖出 / 初始仓位)
├── 数量 (必填)
├── 价格 (必填)
├── 交易日期 (默认今天,可改)
├── 笔记 (可选,自由文本 — 场景 M 种子)
└── 创建时间 (auto)

Position(当前持仓 — 从交易记录算出,用户不直填)
├── 标的代码
├── 当前持有数量 (计算)
├── 加权平均成本价 (计算)
├── 总投入金额 (计算)
├── 累计已实现盈亏 (计算 - 卖出部分)
└── 当前浮动盈亏 (基于 tushare 实时价 计算)
```

**用户面对的录入表单仅一个 — 「新增交易」**,5 个字段 + 1 可选笔记。

### 4.2 Onboarding 路径(雪球做法)

**核心问题**:交易历史模式下,用户当前已经持有的股票,数据怎么进系统?

**业界 alternatives**:
- 路径 A 从今天起记:0 摩擦但 dashboard 起步空
- 路径 B 完整回溯:数据完整但摩擦极高(用户得查交割单)
- **路径 C 雪球做法**:当前持仓作为"day 0 一笔虚拟买入"录入,之后从今天起记新交易

**取舍**:**路径 C**。用户体验上跟"快照模式"几乎一样(每只持仓录一次"标的 + 数量 + 成本价 + 入仓日"),起步无痛;数据模型上是真正的交易历史(那笔录入是 type="初始仓位"的 Trade)。

### 4.3 编辑权限三态机

| Trade 类型 | 编辑权限 | 删除权限 | 理由 |
|---|---|---|---|
| 初始仓位(虚拟交易) | **始终可编辑** | 24h 内可删 | onboarding 容错(成本价填错最大风险点) |
| 买入 / 卖出(常规) | 永远不可改 | 24h 内可删 | 交易历史 immutable;24h 给手抖兜底 |

**过 24h 后输错的逃生通道**:用反向交易抵消(再录一笔反向 Trade,系统自动算清),不引入"调整交易"概念。

### 4.4 浮盈计算

基于真实成本价(用户填的初始仓位价格)计算浮盈,而非"从产品 day 0 算"。理由:用户填的成本价是事实,该按事实算。**v1.0 不做"持有期间每日历史曲线"**(需要回溯历史行情,工程量大),只显示当前浮盈数字。

## § 5 监控引擎

### 5.1 异动判定逻辑

```
异动 = 涨跌幅 ≥ ±5%  OR  重大公告(5 类)
```

### 5.2 重大公告范围(精选 5 类)

| # | 公告类型 | 触发理由 |
|---|---|---|
| 1 | **财报披露**(季报/半年报/年报) | 后续 LLM 摘要的核心入口,信号最强 |
| 2 | **业绩预告**(预增/预减/预亏) | 散户最敏感,提前披露下季业绩范围 |
| 3 | **ST / 退市风险警示** | 灾难级,可能直接腰斩 |
| 4 | **重大资产重组 / 并购** | 价格剧烈波动来源,通常停牌 |
| 5 | **重大监管处罚 / 立案调查** | 可能停牌,影响极大 |

**显式不做(留 v1.x)**:大股东减持、股票回购、高管变动、股东大会决议、大宗交易。理由:信号噪声比中等,需要复杂阈值过滤逻辑;v1.0 容忍漏报,真痛了 v1.x 加。

### 5.3 数据刷新频率 = 30 分钟

| 维度 | 5 分钟(实时倾向) | **30 分钟(选)** |
|---|---|---|
| API quota 燃烧 | 一天 ~50 次 | 一天 ~16 次(省 3 倍) |
| 盘中急速异动响应 | 5 分钟内 | 最长 30 分钟延迟 |
| 用户行为引导 | 偏被动接收 | 偏主动"我现在想看就刷" |
| 跟产品定位 match | 偏盯盘 | 匹配"长持散户" |
| LLM 预生成 cost | 高 | 低 |

**取舍**:30 分钟自动 + 手动刷新按钮。Worst case 盘中急速异动延迟 30 分钟用户可以接受,手动刷新覆盖"我现在就想看"场景。

### 5.4 异动详情卡生成时机 = 预生成

**业界 alternatives**:
- 实时生成:用户点开时调 LLM,等 30 秒-1 分钟。体验差
- **预生成**:监控引擎触发标红时异步生成详情卡内容。用户点开是"读静态内容",< 1 秒打开

**取舍**:预生成。代价:LLM cost 增加(但只对标红的少数股,不是所有持仓),换来体验质变。

```
│  ● 宁德      ¥165    -5.1% ↓    浮盈 -2.1%   行业政策      │
│  ─────────────────────────────                              │
│  ○ 招行      ¥38      +0.3%    浮盈 +5.1%                  │

│  ○ 海尔智家  ¥28      +0.1%    浮盈 +3.2%                  │
└─────────────────────────────────────────────────────────────┘
```

**设计决策**:
- **Layout = A 极简单列表**(异动行 ● 排前 + 静默 ○ 排后,中间分隔线)。**不**用"需关注 / 正常"分组标题(视觉色差已经分组,文字标题是 over-engineering)
- **字段密度 = 中**(标的 / 当前价 / 今日% / 浮盈% / 异动 tag)。持仓占比 / 市值留 C-4 持仓分析
- **排序**:异动行优先,组内按持仓市值降序(大仓位异动 > 小仓位异动)
- **总览栏**:总资产 / 今日% / 本月% / 持仓只数(短期 + 中期 + 规模感)

```
├──────────────────────────────────────────────┤
│   预生成于 2026-05-07 09:23                  │
└──────────────────────────────────────────────┘
```

**设计决策**:
- **A/B/C 三区结构**,无 D 区动作按钮(用户自己导航)
- A 区永远显示;B 区随事件类型变化(见 6.4);C 区**仅在用户有历史笔记时出现**
- 标注预生成时间戳

**为什么没有 D 区动作?** 持仓监控 v1.0 的职责是"准确告诉你发生了什么",不是"指导你下一步做什么"。后者用户自己有判断和工作流。强塞动作按钮 patronizing。

### 6.4 不同事件类型的 B 区内容

**关键约束**:B 区只能用**已存在的能力**(tushare + KB + Bocha + 通用 LLM),不寄生未实现的 use case(C-5 / C-3 等都没做)。

| 事件类型 | B 区怎么填 | 依赖 |
|---|---|---|
| 财报披露 / 业绩预告 | LLM 摘要(亮点 / 雷点 / 关键指标)+ 引用原公告 | tushare + LLM |
| ST / 退市 | 风险等级 + 处置建议 + 引用原公告 | LLM |
| 重组 / 并购 | 重组方案要点摘要 + 引用原公告 | LLM |
| 重大处罚 | 处罚摘要 + 影响判断 + 引用原公告 | LLM |
| 仅价格异动 | 行业对比(同行业平均涨跌)+ 近期新闻 top 3 + LLM 摘要 | tushare + Bocha + LLM |

**统一模式:LLM 摘要 + 引用回真实数据源**。不需要给每个事件类型起 use case 编号。

### 6.5 Trade 历史列表

```
┌──────────────────────────────────────────────┐
│  我的交易记录                                  │
├──────────────────────────────────────────────┤
│  2026-05-05  茅台  买入  50 股 @ ¥1500       │
```

### 6.6 显式不做的 UI

- 推送通道、邮件 digest
- 已查看回顾区(v1.0 看过即移走,无中间态)
- 标红事件历史回看(后端事件可保留,UI 留 v1.x)
- 笔记全文搜索(笔记数量 v1.0 最多几十条,Trade 列表手动滚够)
- RM 视角(只架构留口)

## § 7 标红生命周期

### 7.1 不同事件类型的生命周期

```
价格异动:
  触发 → 标红
  ├─ 用户点开详情卡 → 立即撤销 → 挪到正常栏
  └─ 未看 → T+1 09:30 自动撤销(开盘日切换,无论看没看)

公告异动:
  触发 → 标红
  ├─ 用户点开详情卡 → 立即撤销 → 挪到正常栏
  └─ 未看 → 触发 3 天后自动撤销(兜底过期)

同股新事件:
  触发 → 新标红事件(独立),不合并旧事件
  详情卡显示"过去 7 天异动 N 次"提示
```

### 7.2 视觉态(只 2 态,无中间灰红)

```
● 红 = 有未查看异动
○ 灰 = 正常 / 已查看 / 已过期
```

### 7.3 不做的状态机

- **静默此股**(场景 J):用户不能"屏蔽某只股的异动",留 v1.x
- **已查看回顾区**(决策 b):看过即移走,不提供"今日已查看 (3) [展开]"折叠区
- **事件序列合并**(Q3):同股新事件独立标红,不做"连续异动 N 天"合并语义
