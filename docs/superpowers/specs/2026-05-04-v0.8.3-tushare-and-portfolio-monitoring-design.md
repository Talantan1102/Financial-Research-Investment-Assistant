## § 0 背景与动机

v0.8.2 ship(PR #11)交付了 B-1 信贷调查报告 schema + Writer 改造 + 茅台 e2e demo,但**两个根本短板未解**:

1. **数据是 mock 的**(`app/service/mock_tushare_service.py` 用 LLM 生成假数据),所有"实时行情 / 财务比率"演示都不能向面试官真投出"这是真数据"
2. **产品形态是"问一次答一次"**(B-1 是 one-shot research),没有任何持续监控能力 — 而工业界 4 款标杆(Moody's Early Warning Signals / Perplexity earnings push / 同花顺自选股 / Hebbia)**全部有"持续监控"这一产品形态**(business spec § 3.3 insight 4)

v0.8.3 一次性补这两个短板:
- **真接 tushare** = 数据源升真,unlock 后续 v0.8.4-7 所有 use case 的真数据
- **B-3 持仓预警 = 监控产品形态首次落地**,简历能写"持续监控产品形态 + 分层架构(signal layer + agent layer)"

**为什么两件事捆一个 sub-version**:tushare 真接入是 B-3 信号检测的前置依赖(没有真数据,信号检测就是 mock-on-mock 嵌套表演),分两个 PR 反而引入耦合 PR 之间 cassette 失效 + 双方 prompt 调优互相打架。

## § 2 决策摘要(6 个核心决策 + alternatives + tradeoff)

按 memory `feedback_design_doc_format`,每个非平凡决策必须含**问题陈述 / 业界 alternatives / tradeoff / 量化评估**。

### Q1 — Tushare 接入 scope(8 接口 vs 3 接口 vs 全市场)

| Alternative | 描述 | 工期 | 量化 / 取舍 | 决议 |
|---|---|---|---|---|
| A — 最小集(3 接口) | 仅替换现有 mock(daily / income / fina_indicator) | ~1.5 天 | B-3 信号严重受限,只能算"价格异动 + 财务比率",无公告/股东/现金流信号 | ❌ |

| C — 大集(B + 全市场扫描) | 加 daily_basic + 龙虎榜 + 北向 | ~5 天 | 越界 v0.8.5 NL 选股 scope;v0.8.3 dogfood focus 散掉;工期超 12 天上限 | ❌ |

### Q2 — 监控触发模型(纯定时 vs 分层定时 vs 日频+事件 vs 按需)

| Alternative | 描述 | 工期 | 量化 / 取舍 | 决议 |
|---|---|---|---|---|
| A — 纯定时,统一日频 | 16:30 cron 跑全部信号 | 1 天 | 最简但 demo 时"等明天"才看到 alert,公告日当天看不到反应 | ❌ |

| **C — 日频 + 披露日历事件 + 手动触发** | 16:30 base + disclosure_date 事件触发 + 前端"立即扫描"按钮 | 1.5 天 | 对齐 Moody's Early Warning;demo 1 分钟看到结果;cost 可控 | ✅ |
| D — 全部按需 | 不跑 cron,只手动 | 0.5 天 | 直接放弃"持续监控产品形态",跟 business spec § 1 立论矛盾 | ❌ |

### Q3 — 监控引擎与现有 5-agent 框架的关系(套用 vs 精简 vs 分离 vs 分层)

| Alternative | 描述 | 工期 | 量化 / 取舍 | 决议 |
|---|---|---|---|---|
| A — 100% 复用 5-agent | 每客户跑完整 planner→...→writer | ~9 天 | planner 是 dead weight(信号集合固定不需规划);critic 对短 alert overkill;每客户 LLM cost ×3;架构强行套娃 | ❌ |
| B — 精简复用 | 保留 data_collector + analyst(改 SignalDetector) + writer,去 planner / critic | ~8 天 | 同根 LangGraph 但走"半套",叙事要解释为何砍 planner | 🟡 兜底 |
| C — 全新独立引擎 | 不走 LangGraph,直接 tool + LLM | ~7 天 | 5-agent 框架等于只服务 B-1;失去"共用底座"故事 | ❌ |
| **D — 分层架构(signal layer + agent layer)** | 监控引擎(scheduler + signal detector + escalation)是新代码;触发"红色"时 escalation 调用现有 5-agent 出 deep_dive | ~10 天 | 对齐工业标准(Moody's Agentic Solutions);两层各司其职;简历叙事最硬;**90% cost 省下来,严重情况质量不打折** | ✅ |

**Cost 量化对比(D vs A)**(假设 5 客户 × 30 天 daily,90% 绿色 / 10% 红色):
- A 方案:5 × 30 × ¥5 = **¥750/月**(每客户每天派"警察"全套 5-agent)
- D 方案:5 × 30 × ¥0.3(信号检测) + 5 × 30 × 10% × ¥5(escalation) = **¥45 + ¥75 = ¥120/月**
- D 节省 84% LLM cost,**红色 alert 质量与 A 相同**

### 3.1 接口清单(8 个)

| Tushare 接口 | 用途 | 复用方 |

| `daily` | 日 K 线(open/high/low/close/vol/amount/pct_chg) | `get_stock_quote` tool + signal: 价格异动 |
| `income` | 利润表(revenue / net_profit / EPS) | `get_financials` tool |
| `fina_indicator` | 财务比率(ROE / 毛利率 / 净利率 / 资产周转) | `get_financials` tool + signal: 财务比率恶化 |

### 3.3 Rate limit + Cache 策略

**Rate limit**(tushare Pro 高积分会员):
- 大部分财务接口 ≤ 500 次/分钟,日 K 线 ≤ 200 次/分钟
- 实现:`asyncio.Semaphore` + token bucket(`backend/app/services/rate_limiter.py` 已有,直接复用)
- 超限策略:exponential backoff,最多 retry 3 次

**Cache**(基于 sqlite):
- 财务接口(income / balance / cashflow / fina_indicator):**永久缓存按 (ts_code, end_date)**(财报披露后不变)
- 公告接口(anns / disclosure_date):**缓存 24h**(每天刷新)
- 行情接口(daily):**缓存到当日 16:00**(收盘前刷,收盘后冻结)
- 股东户数(stk_holdernumber):**永久缓存按 (ts_code, end_date)**

**Cache 表**:`tushare_cache` (api_name, params_hash, ts_code, end_date_or_query_date, response_blob, fetched_at, expires_at)

### 3.4 Cassette 策略(VCR)

按 memory `feedback_cassette_dynamic_prompt_values` + `feedback_cassette_host_in_match_on`:
- VCR `match_on`: ['method', 'host', 'path', 'query'](**不 match_on body** — tushare body 含 token,会泄露)
- token 在 cassette `before_record_request` hook 中 redact 替换为 `<TUSHARE_TOKEN>`
- 8 接口 × 5 ts_code(从 dogfood 5 客户挑)= 40 episode,估 ~50KB
- Cassette 路径:`backend/tests/cassettes/tushare/`

**Cassette host fallback**(避免 unset env 时走真网络):
- `TushareClient.__init__` 默认 base_url 必须等于 cassette 录制时的 host(`http://api.tushare.pro`)

### 3.5 对现有 tools 的改造

`get_financials.py` / `get_stock_quote.py`:
- `__init__(self, mock_tushare: MockTushareService)` → `__init__(self, tushare: TushareService)`(接 Protocol)
- 调用方法保持不变(`generate_income` / `generate_daily_data` 接口在两实现里都有)
- DI wiring 在 `app/orchestration/agent_graph.py` 改为读 `build_tushare_service()`

**Backward compat 取舍**:不保留旧 mock 路径(直接换 Protocol),理由 = mock_tushare_service.py 在 spec § 1.1 块 1 内被改造为 `MockTushareService` 实现 Protocol,旧调用方零迁移成本。

### 4.2 数据流

```
   APScheduler(每天 16:30)              手动触发(前端按钮)            披露日历事件触发
        │                                       │                              │
        └────────────┬──────────────────────────┴──────────────────────────────┘
                     ▼
        MonitoringService.run_scan(customer_ids: list[str])
                     │
                     ▼  (for each customer, 并发 max=5)
        SignalDetector.detect(customer)
                     │
                     ├─→ for each SignalRule: rule.evaluate() → SignalResult(level, value, threshold)
                     │
                     ▼
        汇总 alert_level = max(signal levels)
        ├─ 绿色: 写 monitoring_runs(无 alert)
        ├─ 黄色: 写 monitoring_alerts + signals;Writer 出 PortfolioWarningReport(deep_dive=None);notification 入站内
        └─ 红色: 同黄色 + EscalationCoordinator.escalate(customer)
                                    │
                                    ▼
                       (受 cost_budget + Semaphore 保护)
                                    │

                         现有 5-agent pipeline.run(customer, mode="alert_deep_dive")
                                    │
                                    ▼
                       deep_dive_section: str(填进 PortfolioWarningReport)
                                    │
                                    ▼
                       EmailNotifier.send(to_addrs, report) (异步,失败不阻塞)
```

### 4.3 Scheduler 实现细节

|---|---|---|
| `monitoring_daily_scan` | CronTrigger(hour=16, minute=30) | `MonitoringService.run_scan(all_active_customers)` |
| `monitoring_disclosure_check` | CronTrigger(hour=17, minute=0) | 查 `disclosure_date` 接口,对今日有公告的客户调 `MonitoringService.run_scan([cid])` |

**手动触发**:走 REST API `POST /api/monitoring/runs`,直接调 `MonitoringService.run_scan(customer_ids)`,异步执行,立即返回 `run_id`。

### 4.4 时区 + 节假日

- 时区:Asia/Shanghai(显式 set on APScheduler instance)
- 节假日:**v0.8.3 不做特殊处理**(节假日跑出来都是绿色,无害);v1.x 集成 `chinese_calendar` 跳过

### 4.5 与现有 scheduler_service 的关系

`app/service/scheduler_service.py`(legacy 模块,在 mypy ignore 范围)用 APScheduler 单例。**v0.8.3 在 `app/services/monitoring/scheduler.py` 新写一个 `MonitoringScheduler` 类**,内部访问同一个 `AsyncIOScheduler` 实例(通过 legacy `get_scheduler_service()` 拿单例),add_job 自己的 jobs。**不动 legacy news collection job**。

- 风险:legacy 单例从 `app.core.database` import `SessionLocal`,跨进程 / pytest 时 reset 需注意 — 写 fixture 处理(见 § 12.2)

## § 5 Signal Detector + 5 个 Signal Rule

### 5.1 SignalRule ABC

```python
class SignalLevel(str, Enum):
    GREEN = "green"
    YELLOW = "yellow"
    RED = "red"

class SignalResult(BaseModel):
    rule_name: str
    level: SignalLevel
    detected_value: float | str | None
    threshold: float | str | None
    explanation: str   # 给 writer / 用户看的
    raw_data_ref: dict[str, Any] | None  # 数据出处,trace 用

class SignalRule(ABC):
    name: str
    description: str
    @abstractmethod
    async def evaluate(
        self,
        customer: MonitoringCustomer,
        tushare: TushareService,
        bocha: BochaService,
        llm: LLMService,
        thresholds: dict[str, float],
    ) -> SignalResult: ...
```

### 5.2 5 个具体 Rule(关键阈值默认值,implementation 时可调)

| Rule | 数据源 | 黄色阈值 | 红色阈值 | 备注 |
|---|---|---|---|---|
| **financial_ratio** | tushare.fina_indicator + balance_sheet | 资产负债率单季环比 > +5pp 或 净利率 < 0 | 资产负债率 > 80% 或 连续 2 季亏损 | 取最近 4 季滑窗 |
| **cash_flow** | tushare.cashflow | 经营性现金流单季环比下滑 > 30% | 连续 2 季经营性现金流为负 | 取最近 4 季 |
| **shareholder_count** | tushare.stk_holdernumber | 单期股东户数环比 -10% 至 -20% | 单期股东户数环比 < -20% | 取最近 4 期 |
| **announcement** | tushare.anns(7 天) + LLM 分类 prompt | LLM 评分 0.5-0.8(可疑) | LLM 评分 > 0.8(高度负面) | LLM 走 cheap tier |
| **price_anomaly** | tushare.daily(60 天) | 单日跌幅 > 5% 或 60 日累计跌幅 > 20% | 单日跌幅 > 10% 或 连续 5 日累计 > 25% | 不含涨停 / 停牌 |

**汇总规则**:`alert_level = max(signal_levels)`;5 rule 全 green → run 无 alert;任意 yellow → yellow alert;任意 red → red alert(触发 escalation)。

**Cost 预算**:
- 4 个非-LLM rule:0 LLM cost(纯 tushare + 算)
- announcement rule:每客户 1 次 LLM 调用(cheap tier,~¥0.05),5 客户 / 天 = ¥0.25/天

### 5.3 阈值的可配置性

阈值默认值写在 `app/services/monitoring/signal_rules/defaults.py`,每个客户可在 `monitoring_customers.thresholds_override`(JSONB / TEXT)字段覆盖,前端配置页可改。**v0.8.3 阶段不做"按行业自动选阈值"**,留 v1.x。

### 5.4 与"业界 alternatives"对照

## § 6 Escalation 机制(分层架构核心)

### 6.1 EscalationCoordinator 职责

- 接收 `SignalDetector` 的红色 alert
- 检查 budget / 并发 / 去重三道闸
- 通过则调用现有 5-agent pipeline(`app/orchestration/agent_graph.py` 的 `ResearchGraph`)
- 拿到 `deep_dive_section: str` 回填 `PortfolioWarningReport`

### 6.2 三道硬约束闸

| 闸 | 阈值默认 | 实现 | 超 cap 行为 |
|---|---|---|---|
| **单次 escalation cost cap** | ¥1 | `cost_budget.guard(...)` 已有 service,wrap escalation 调用 | 跳过 escalation,alert 仍发送但 deep_dive=None,记录 `budget_per_call_exceeded` flag |
| **同时并发数** | 1 | `asyncio.Semaphore(1)` | 排队,FIFO |
| **每客户每天 escalate 次数** | 1 | DB 查询 `monitoring_alerts WHERE customer_id=? AND date=? AND escalated=true` | 跳过 escalation,alert 仍发送但 deep_dive=None,记录 `daily_dedup` flag |
| **整 monitoring 每日 cost cap** | ¥10 | 累加当日所有 monitoring 相关 LLM cost | 超 cap 后续 alert 全跳 escalation,记录 `daily_budget_exceeded` flag |

**所有 cap 都可在 `.env` / 配置页改**。

### 6.3 5-agent pipeline 复用模式

调用现有 `ResearchGraph.run()`,传入特殊参数:
```python
state = ResearchState(
    company_name=customer.name,
    request_id=run_id,
    mode="alert_deep_dive",          # 新 mode,5-agent 内部 prompt 走 alert 简化版
    alert_signals=signal_results,    # 让 analyst / writer 围绕已触发信号展开
    target_max_tokens=2000,          # cap deep_dive 长度,避免 cost 失控
)
result = await graph.ainvoke(state)
deep_dive: str = result.deep_dive_section  # 新增 field
```

**改动 5-agent 的代价**:
- ResearchState 新增 `mode: Literal["full_research", "alert_deep_dive"]` + `alert_signals: list[SignalResult] | None`
- planner / analyst / writer 的 system prompt 加分支(`if state.mode == "alert_deep_dive"`)
- writer 输出新字段 `deep_dive_section`
- ResearchState 沿用 `BaseModel` + reducer(memory `feedback_agent_abc_state_generic` — 走 generic Agent ABC,不要 type:ignore[override])
- LOC 估 ~80(不是大改)

### 6.4 Escalation 失败处理

- LLM 失败:retry 1 次,失败则 alert 仍发,deep_dive=None,记录 `escalation_failed` flag
- 超时(120s):同上
- Email 失败:不阻塞 alert 写库;email_notifier 内部 retry 2 次,最终失败记 `notifications.send_status='failed'`(用户在前端能看到)

CREATE TABLE monitoring_signals (
    id TEXT PRIMARY KEY,
    run_id TEXT NOT NULL REFERENCES monitoring_runs(id),
    rule_name TEXT NOT NULL,
    level TEXT NOT NULL,             -- 'green' / 'yellow' / 'red'

    id TEXT PRIMARY KEY,
    run_id TEXT NOT NULL REFERENCES monitoring_runs(id),

    report_json TEXT NOT NULL,       -- 序列化的 PortfolioWarningReport
    report_markdown TEXT,
    escalated INTEGER DEFAULT 0,
    escalation_status TEXT,          -- null / 'pending' / 'success' / 'failed' / 'budget_exceeded' / 'daily_dedup'

);

);

### 14.2 超 spec § 7.2 上限(7-12 天)2-3.5 天的理由

**business spec § 7.2 写 7-12 天是粗估,基于 B 方案(精简复用)+ 5 接口**。本 spec 选 D 方案(分层架构)+ 8 接口,scope 真实更大。**接受超期**有 4 个理由:

1. **memory `feedback_no_portfolio_simplification`**:不能用 portfolio 借口降低严谨度。D 方案 vs B 方案的 cost 节省 84% + 简历叙事更硬,工业级正确选择。
2. **简历叙事价值**:"分层架构(signal layer + agent layer)对齐 Moody's Agentic Solutions"是面试时能讲 5 分钟的故事;B 方案是"复用 5-agent",叙事弱。
3. **风险下界**:D 方案有"硬约束闸"(单次 ¥1 + 并发 1 + 每客户每天 1 + 总日 ¥10),失败模式可控。
4. **超期可吸收**:project-positioning roadmap § 8 累计 v1.0 = 32-48 天,本 sub-version 多 2-3.5 天对总工期影响 < 8%。

### 14.3 提前结束触发条件(implementation 时若发现)

- 如果 tushare 8 接口里有 ≥ 2 个不可用(API 调整 / 接口下线)→ 退到 5 接口 + 砍对应 signal rule
- 如果 escalation 在 dogfood 时持续超 ¥1 单次 cap → 改 deep_dive max_tokens 1500 → 1000
- 如果 5-agent 改 mode 分支动到 critic_subagents → 砍 critic 在 alert mode 下的运行,只跑 planner/data_collector/analyst/writer
