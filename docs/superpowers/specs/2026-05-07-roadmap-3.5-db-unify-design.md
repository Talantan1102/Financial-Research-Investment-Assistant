## § 1 决策摘要

### 决策 1:scope = 全扫(不窄起步)

**问题**:#3.5 是只修 PR #21 的双轨 bug + alembic 引入(窄,2-3 天),还是把 4 个 sqlite 组件 + LangGraph 一次性全迁(全,1-2 周)?

**业界 alternatives:**
- **窄起步,后续再迁**:每次撞痛点再迁一个组件
- **全扫一次到位**:一次性把 sqlite 残留全清(本决策)
- **保留 sqlite 组件 + 只统一 schema 管理**:改 model + alembic,不动 sqlite

**取舍**:全扫一次到位。

**理由:**
- 个人作品的简历叙事要"完整 PG 平台" —— sqlite 残留每出现一次都破叙事
- 这 4 个组件每个独立替换工作量都不大(1-2 天/个),拖到下次撞痛点反而每次重新进 brainstorm 一次,效率低
- alembic 只引基础设施不放业务进去意义不大,顺手把所有业务 schema 都收进 alembic 才形成完整闭环

### 决策 2:01-init.sql 全拿走变文档

**问题**:alembic 装上后,跟 `docker/init-db/01-init.sql` 怎么共存?

**业界 alternatives:**
- **alembic 管未来,init.sql 管初始**:平过渡,双源头共存但"未来 ≠ 现在"边界明确
- **alembic 全拿走,init.sql 清空变文档**(本决策):单源头,长期 zero ambiguity
- **只引 alembic 不付责任**:alembic 装上但不动 init.sql,等下次撞痛点再说

**取舍**:全拿走。

**理由:**
- 已经决定全扫(决策 1),保留 init.sql 没意义
- 双源头是漂移的根本来源,趁着抹了重来的窗口直接斩断
- init.sql 清空但保留文件 + 加注释说明"内容已迁 alembic baseline,见 backend/alembic/versions/...",对历史 spelunking 友好

### 决策 3:tushare_cache → Redis,其他全 PG

**问题**:cache 也走 PG 还是 Redis?

**业界 alternatives:**
- **全 PG**(连 cache 也):简化运维,只一个 DB
- **Redis for cache, PG for everything else**(本决策):Redis idiomatic,docker-compose 里早配好
- **跨服务专门做 cache 抽象**:工程量大,YAGNI

**取舍**:Redis for cache, PG for everything else。

**理由:**
- Redis 已在 `docker-compose.yml:25-37`(`industry_redis`,redis:7-alpine)早配好但没用,运维债已经付了不用就浪费
- cache 是 Redis idiomatic 场景:原生 TTL(`SET key value EX <ttl>`)、高频小读、淘汰策略
- PG 跑 cache 量也跑得动但不优雅(手写 expires_at 列 + 定期清理)
- "彻底"的含义是**"每个组件用最合适的存储 + 没有 sqlite 残留"**,不是"全部统一到 PG"

### 决策 4:本地 PG 抹了重来

**问题**:Mac 本地 PG 已有数据(test users / research reports / chat history),迁移过程怎么处理?

**业界 alternatives:**
- **保留 + alembic stamp head**:`alembic stamp head` 标记当前 db = baseline,不抹
- **抹了重来**(本决策):`docker compose down -v` 清 volume,alembic upgrade head 重建
- **备份重要表 + 抹 + 恢复**:中间路线

**取舍**:抹了重来。

**理由:**
- 个人 dev,无生产数据,dogfood 历史损失成本可接受
- 保留 + stamp 路线**前提是当前 schema 跟代码 model 完全一致** —— PR #21 已经查出双轨不一致,意味着 stamp 后立即触发 alembic autogenerate 检测到差异,要手补 1-2 个 migration,绕远路
- 抹了重来一句命令搞定:`docker compose down -v && docker compose up -d postgres redis && uv run poe serve`(lifespan 自动 alembic upgrade head)

### 决策 5:lifespan 用 `alembic upgrade head` 替代 `Base.metadata.create_all`,失败 fail loud

**问题**:app_main lifespan 怎么应用 schema?

**业界 alternatives:**
- **保留 `create_all`** + 加 alembic 双轨:已经被 PR #21 教训过,不行
- **lifespan 调 `alembic upgrade head`**(本决策):一次到位,startup 自动 migrate
- **不在 lifespan,用 separate `poe migrate` 任务**:CI/dev 都要记得手动跑,容易漏

**取舍**:lifespan 自动 upgrade,失败 **fail loud**(crash 而不是 graceful warning)。

**理由:**
- 当前 lifespan 的 try/except graceful catch(`app_main.py:197-211`)正是 PR #21 双轨 bug 隐藏 6 个月没暴露的根因 —— `create_all` 失败被吞了,业务以为一切 OK,直到查 users 表才发现没建
- 失败 fail loud 让"启动不来"等价于"schema 出问题",符合人类心智
- alembic upgrade head 失败的常见情形(连不上 DB / migration 冲突)都该 loud,run 都不该 run 起来

### 决策 6:PR 拆 5 个,A 是基础其余可并行

**问题**:1-2 周工作量是单 PR 还是拆?

**业界 alternatives:**
- **单大 PR**:一次性 review,可能很难 review,失败成本高
- **拆 5 个 PR**(本决策):基础 + 4 个组件,每个独立 ship + 有 e2e 守护
- **更细拆**(每个 sqlite 表一个 PR):太碎,工程开销大

**取舍**:拆 5 个。

**理由:**
- 每个组件独立 + 有自己的 e2e 守护,不会 1 个 bug 拖死整 PR
- A 必须先(alembic 基础设施),BCDE 之间无依赖可以并行甚至乱序
- 个人作品节奏接受"渐进 ship",每个 PR 1-3 天 wall time,符合"晚上槽 brainstorm/dogfood + 白天槽 impl"的 v0.9+ roadmap § 3 模式

## § 3 alembic 策略

**目录结构**:

```
backend/
├── alembic.ini                           # alembic 主配置
├── alembic/
│   ├── env.py                            # alembic 环境(读 POSTGRES_*)
│   ├── script.py.mako                    # migration 模板
│   └── versions/
│       └── 20260507_<hash>_baseline.py   # baseline migration(初始)
└── app/
    └── models/                           # SQLAlchemy 模型(单源头)
```

**配置要点**:

- `alembic.ini`:`script_location = alembic`,db url 用 env var(不 hardcode)
- `env.py`:从 `app.core.database import Base` + `app.models import *`(barrel)拿 metadata
- `target_metadata = Base.metadata`
- 用 sync engine(项目用 psycopg2-binary,不引 async)

**baseline 生成流程**:

```bash
# 1. 改完所有模型 + 装 alembic 之后
docker compose down -v
docker compose up -d postgres
cd backend
uv run alembic revision --autogenerate -m "baseline: all schema from legacy 01-init.sql + new sqlite migrations"

# 2. 人工 review 生成的 migration 文件
#    - 检查所有 legacy 表都在(13 张)
#    - 检查 spans / monitoring_* / eval_* 都在
#    - 检查 FK 类型全是 UUID(不是 VARCHAR)
#    - 检查没有奇怪的 drop_table(autogenerate 误判)

# 3. commit + 应用
git add backend/alembic/versions/<hash>_baseline.py
docker compose down -v
docker compose up -d postgres
uv run alembic upgrade head  # 应用 baseline

# 4. 启动 app verify
uv run poe serve  # lifespan 应该 noop(alembic_version 已在 head)
```

**LangGraph 边界**:

- LangGraph 的 `langgraph_state`、`langgraph_writes` 等表由 `PostgresSaver.from_conn_string()` 自动建
- **不进 alembic baseline** —— LangGraph 自己管自己 schema,跨版本兼容由 LangGraph 处理
- alembic env.py 不 import LangGraph 模型,baseline autogenerate 不会扫到这些表

### 4.6 模型 FK 类型修补(横切)

**当前已知 bug:**
- `app/models/chat.py` 的 `ChatSession.user_id` / `ChatMessage.user_id` 等大概率是 `String(36)` 而非 `UUID(as_uuid=True)`,跟 `User.id` 不匹配(PR #21 验证过)

**修补范围(grep audit 全清单):**

| 文件 | 表 | user_id 列预期 |
|---|---|---|
| `models/user.py` | users | id `UUID(as_uuid=True)` ← 标杆 |
| `models/chat.py` | chat_sessions / chat_messages / chat_attachments / long_term_memories | user_id 全 `UUID(as_uuid=True)` |
| `models/knowledge.py` | knowledge_bases / documents | user_id `UUID(as_uuid=True)` |
| `models/research_report.py` | research_reports | user_id `UUID(as_uuid=True)`(已是,作 baseline)|
| `models/research.py` | research_checkpoints | user_id 待检查 |
| 新加的 `models/trace.py` | spans | (无 user_id 概念,本身不需修)|
| 新加的 `models/monitoring.py` | monitoring_* | user_id 若有则 UUID |
| 新加的 `models/eval.py` | eval_runs / eval_results | user_id 若有则 UUID |

**统一变体写法**(让 sqlite-override 测试继续 work):

```python
from sqlalchemy import Column, String
from sqlalchemy.dialects.postgresql import UUID as PG_UUID

# User PK(标杆 — 也要有 with_variant,sqlite-override 测试需要)
class User(Base):
    __tablename__ = "users"
    id = Column(
        PG_UUID(as_uuid=True).with_variant(String(36), "sqlite"),
        primary_key=True,
        default=lambda: str(uuid4()),
    )

# 所有 FK 引用 user_id 的列同样写法
class ChatSession(Base):
    __tablename__ = "chat_sessions"
    user_id = Column(
        PG_UUID(as_uuid=True).with_variant(String(36), "sqlite"),
        ForeignKey("users.id"),
        nullable=False,
    )
```

(对照 `research_report.py:49` 已有的 with_variant 写法,统一抄到所有 UUID 列 —— PK + FK 都要)

**附带效果**:`tests/integration/conftest.py` 的 `_patch_uuid_columns_to_string()` hack 在所有模型补 with_variant 后**变成 no-op**(找不到没 variant 的 UUID 列)。但 § 10 规定本 spec 不清理,留着无害。

## § 5 lifespan 替换 + 启动行为变更

### 当前 lifespan(`backend/app/app_main.py:197-211`)

```python
try:
    Base.metadata.create_all(bind=engine)
    logger.info("PostgreSQL 表初始化完成")
except Exception as e:
    logger.warning(f"PostgreSQL 表初始化跳过(可能 PG 未启动): {e}")
    # 不 crash,业务路由调用时报 500
```

### 新 lifespan(本 spec 落地后)

```python
from alembic.config import Config
from alembic import command

cfg = Config("backend/alembic.ini")
cfg.set_main_option(
    "sqlalchemy.url",
    f"postgresql://{POSTGRES_USER}:{POSTGRES_PASSWORD}@{POSTGRES_HOST}:{POSTGRES_PORT}/{POSTGRES_DB}",
)
command.upgrade(cfg, "head")
logger.info("Alembic upgrade head 完成")
# 失败抛出,uvicorn crash startup —— fail loud
```

**行为变更总结:**

| 项 | 当前 | 之后 |
|---|---|---|
| Schema 不齐时启动 | log warning,业务路由 500 | crash startup,uvicorn 不 ready |
| 加新表流程 | 改 model + 重启(create_all 自动建)| 改 model + `alembic revision --autogenerate` + 重启(lifespan upgrade) |
| 改字段流程 | 不能(create_all 只加表)| `alembic revision --autogenerate` + review + upgrade |
| 多人并发改 schema | 没法处理(需要协调)| alembic merge revisions(标准流程)|

## § 9 风险与缓解

| 风险 | 概率 | 后果 | 缓解 |
|---|---|---|---|
| 模型 FK 类型修补漏一个(还有其他 user_id 列没改) | 中 | alembic baseline autogenerate 时 FK 报 datatype mismatch | PR A 强制 grep `Column.*String.*36.*user_id` 全部清掉 + autogenerate 后人工 review baseline |
| LangGraph PostgresSaver 跟 SqliteSaver 行为细节不一致(checkpoint resume 语义) | 中 | research graph 复跑场景(retry edge)出 bug | PR B 加 e2e 验证 graph 真跑通 + retry edge 触发 + resume 一致 |
| Redis 缓存击穿场景(高并发同 key miss) | 低(个人 portfolio) | tushare 真 API 被 burst 调用,触发 rate limit | YAGNI,先不处理,挂了重试 |
| alembic baseline autogenerate 跟 01-init.sql 内容不完全 match | 中 | 漏掉某个 legacy 表 / 缺索引 | PR A 实施时人工 diff baseline migration vs 01-init.sql,补齐遗漏 |
| 多 dev 环境 schema 漂移(开发者忘记跑 alembic upgrade) | 低(个人项目) | 启动时 fail loud 立即暴露 | fail loud 设计 + README 强调 |
| `_patch_uuid_columns_to_string()` hack 仍需要(tests/integration/test_user_isolation.py)| 高 | sqlite-override 测试可能仍要这个兼容层 | 不动,留着 |

## § 10 明确不做的事

为对抗"DB 统一 = 全部重构"的 scope creep,明确以下事项**不在本 spec scope**:

- ❌ **`_patch_uuid_columns_to_string()` hack 清理** —— L1 sqlite-override 测试还在用,留着
- ❌ **alembic 迁移测试**(testcontainers 风格的 forward/backward 测试)—— v1.x 再说
- ❌ **Redis 高可用 / SLA / 持久化策略调优** —— 个人 portfolio 不在乎
- ❌ **跨 LangGraph 版本 checkpoint 兼容性策略** —— 用 PostgresSaver 默认行为,不 over-engineer
- ❌ **eval 数据归档 / 压缩策略** —— 数据量小(nightly 几十行/天),YAGNI
- ❌ **trace_service 跨长期分析查询优化(分区表 / 列存索引)** —— 同上
- ❌ **生产部署 / 多区 / 备份恢复方案** —— 个人 portfolio,不在乎
