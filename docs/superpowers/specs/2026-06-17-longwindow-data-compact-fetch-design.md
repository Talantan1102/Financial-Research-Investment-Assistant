# 长窗口取数:紧凑取回设计(get_daily 去断崖)

> brainstorming 产物。承接 2026-06-17 调研 workflow `compact-longwindow-research`(六族方法论综述)
> 与反向出题 pass@k 的「CAGR/复杂-3y 战力断崖」诊断。
> 设计语言:本 spec 评决策,后续 plan 推实施,claude-context 沉淀长期 working memory。

## 1. 我们遇到的问题

### 1.1 现象:长窗口战力断崖

反向出题机跑 pass@k,按 难度×指标 分桶,断崖稳定落在**需要长窗口(近三年)数据**的题上:
CAGR(全部 3y)初版只有 13%,其余 1 年窗口的指标(波动/回撤/涨幅)都在 70%~93%。
断崖**不在"算不算得来"**(agent 有数据就算得对),而在**"取不取得齐长窗口数据"**。

### 1.2 真凶:get_daily 里一行静默截断

`backend/app/mcp_server/tools/get_daily.py` 写死:

```python
_MAX_ROWS = 260   # 单次最多 260 行,超出 df.tail(260) 只留最近 260 个交易日
```

后果:**不管请求几年,工具最多只返回最近 ~260 个交易日(约 1 年),更早的悄悄丢弃。**

- agent 的「预防性分段」**不是坏习惯,是被逼的**:问 3 年只拿回 1 年,要凑齐只能分多次按子区间取(第一年/第二年/第三年),因为单次物理上拿不到 3 年。
- 每次分段把一整年(~260 行 ~1.5 万字)倒进上下文 → 上下文堆满、循环步数(max_steps)烧光 → **凑齐之前就撞终止闸,死在最后一步 run_python 之前**。
- **静默正确性坑**:粗心的 agent 没察觉"问了 3 年只给了 1 年",直接拿 1 年算 3 年 CAGR,结果错且不自知。

### 1.3 修正上一轮诊断

上一轮把 CAGR 13%→40% 归因于「截断 note 从 read_cached_result 改引导 data_refs」。
摸代码发现:**get_daily 自身先 cap 到 260 行 ≈ 1.5 万字,永远到不了 24000 的超大截断阈值**,
那个 note 对 get_daily 这条路**从未触发**。CAGR 的提升**几乎全部来自 max_steps 18→26**
(多给回合容下被迫的分段拼装)——那是治标。**真正的根因是 260 静默 cap 逼出的分段。**

## 2. 调研结论与方案选择

### 2.1 六族方法论(详见调研 workflow 综述)

一条主线:**精确整段归约 vs 有损近似**。CAGR/波动/最大回撤是"每一天都必须参与"的精确归约,
所有有损手段(摘要压缩/采样/检索 RAG/降采样)都出局(调研有硬证据:RAG 在聚合类任务 1.51 F1;
compaction 留住高层信息 3/3 但具体数字 0/3;LTTB 抽稀产生幽灵谐波)。精确派只剩四族:

| 方法论族 | 对我们 |
| --- | --- |
| 代码执行 / 沙箱归约(写段代码、数据进沙箱、只回数字) | **已有 run_python,差"逼 agent 走这条"** |
| 外部句柄 / 引用旁路(大结果只回取货单号) | **已有 data_refs + 缓存** |
| 计算下推到数据侧(数据库/指标接口算好只回结果) | 不适用:上游 tushare 无"整段 CAGR"接口;自建违背框架最小化 |
| 可结合归约的算法代数(哪些指标能分块合并) | 当前用不上(725 天单块够);留作文档护栏 |
| (子 agent map-reduce) | 不适用:单条序列一次归约,多 agent 贵 15× 且跨段拼接易错 |

**结论:战场只在前两族,而且零件(沙箱+引用+缓存)我们都已经有——缺的是一道把 agent 摁回正道的约束。**

### 2.2 方案选择:改 get_daily 本身

- **方案 A(选定):改造 get_daily** —— 大区间取全量存缓存、只回"信息卡+取货单号";小区间照旧回数组。
  这个 MCP 工具只有 chat 在用(估值/信号/持仓走的是另一条 `tushare_service` 路径),改动爆炸半径小。
- 方案 B(否):新建专用工具 `get_price_series`。多一个工具 = 多一层 tool routing 风险(agent 要学会算指标时选它)。
- 方案 C(否):只删 cap 靠现有截断兜底。中等区间(260~~400 行)仍把整串数据灌进上下文,
  且现有截断的"前 600 字 digest"对价格序列不友好(看不出日期跨度/首末价)。

## 3. 端到端接线(已在代码中验证)

设计成立的命脉是「agent 能把 get_daily 的取货单号喂进 run_python 拿到完整序列」。已逐处确认:

1. **完整版进缓存**:`tool_hub.py` 对 MCP 只读数据工具走 `cache.get_or_compute`,
   按 `ToolResultCache.cache_key(user_id, "get_daily", args)` 存**工具返回的完整输出**。
2. **截断只动上下文副本**:`loop.py _cap_oversized_output` 把进上下文的副本换成 digest+ref,
   **缓存里那份始终是全量**。
3. **引用还原全量**:`code_interpreter_tool.py _resolve_refs` 校验 `ref` 以 `{user_id}::` 开头(防越权),
   `cache.get_raw(ref)` 取回完整 JSON,`json.loads` 后灌进沙箱 `data[变量名]`。

> 即「存全量 → 只回单号 → 沙箱凭单号算全量」链路现成就通,**唯一卡点就是 260 cap 把 3 年掐成 1 年**。

## 4. 设计

### 4.1 取数契约改造(核心)

**① 去掉 `_MAX_ROWS` 静默 tail** —— 大区间真取全量(全量随后被 §3 的缓存机制完整存下)。

**② get_daily 始终附一个紧凑 `summary` 子 dict**(从完整 df 现算,廉价、体积小):

```python
summary = {
    "ts_code": ts_code,
    "count": <交易日数>,
    "date_start": <首个交易日 YYYYMMDD>,
    "date_end":   <末个交易日 YYYYMMDD>,
    "first_close": <首日收盘>,
    "last_close":  <末日收盘>,
    "period_high": <区间最高(high 列 max)>,
    "period_low":  <区间最低(low 列 min)>,
}
```

**③ 行为分界(由现有超大截断阈值天然划开,移除 cap 后大区间才够得着它)**:

| 请求区间 | 序列化体积 | 进上下文的东西 | 完整数据 |
| --- | --- | --- | --- |
| ≤ ~1 年(~260 行,~15k 字 < 24000) | 不超阈值 | 数组 + summary(照旧,快速看盘/画近期 K 线不受影响) | 同在上下文 |
| > ~1 年(如 3 年 ~42k 字 > 24000) | 超阈值 | **只剩 summary + 取货单号(ref)** | 在缓存,凭 ref 取 |

> 不调全局 24000 阈值(它是为"1 年单序列 ~15k 字不误截"刻意抬上去的)。3 年 ~42k 字稳超阈值 →
> 自动走 ref;1~1.6 年的中间带仍 inline(全量一次到位、单次调用、不分段,可接受)。

### 4.2 通用「摘要存活截断」(让 §4.1 的 summary 不被截掉)

改 `_cap_oversized_output`:截断时**若 output 带 `summary` 字段则保留它**(与 ref 一起回),
取代"前 600 字 digest"这种对结构化数据不友好的兜底。无 `summary` 的工具退回原 digest 行为。

这样进上下文的就是那张"信息卡":agent 能核对范围对不对、有时连"这三年涨没涨"都能直接答,不必算。
这是一个**通用小改**:任何工具想让一段小摘要"挺过截断"都能用,贴合框架最小化。

### 4.3 系统提示立规矩(与 4.1 配套,堵 + 指)

往 `CHAT_SYSTEM_PROMPT` 加一条白话规矩,专治模型"宁可多搜几次小的"的训练本能:

> 算「每一天都要参与」的整段指标(年化收益 / 波动率 / 最大回撤等):
> 取数 → 拿到取货单号(ref)→ 在 run_python 里用 `data_refs` 把完整序列一次灌进沙箱算全量,只回结论。
> **不要把日线数据分段读进对话,不要用摘要 / 抽样估算这类指标。**

4.1 是"堵"(分段也只能拿到 ref、拿不到数据,分段无利可图),4.3 是"指"(明示正道),双管齐下。

### 4.4 分块代数护栏(纯文档,留口子)

把"哪些指标能精确分块合并、哪些不能"写进本 spec 当判据。**当前 725 天单块沙箱一口吃下、用不上**;
价值是将来真遇到"单块吃不下"(如十年分钟级数据)时照此安全切块,也挡住有人用降采样糊弄精确指标:

- **可精确分块合并**:总和 / 计数 / 最大 / 最小;均值 / 方差 / 波动率(每块只带 `个数,均值,平方和`);
  最大回撤(每块**额外带"块末累积水位"**,否则右段跌幅接不上左段高点会算错)。
- **不可(只能全量单遍或明示降级近似)**:精确中位数 / 分位数 / 排名。

## 5. 测试约定

- **单元(get_daily)**:大区间 → 输出只剩 summary + ref(不含完整数组),且缓存里是全量;
  小区间 → 照旧回数组 + summary;summary 各字段取值正确。
- **单元(_cap_oversized_output)**:带 `summary` 的超大结果 → 截断后保留 summary + ref;
  不带 `summary` 的 → 退回原 digest 行为(回归保护)。
- **回归验证**:重跑反向出题 CAGR/3y 桶,预期从 ~40% 大幅上行(真正拆断崖,区别于上轮加预算的治标)。

## 6. 范围 / 不做 / 风险

**不做(非目标)**:
- 不自建"计算下推"接口 / Text-to-SQL(上游 tushare 不提供整段指标接口;违背框架最小化)。
- 不引入新取数工具(方案 B 否)、不引入子 agent map-reduce(见 §2.1 末行,单序列归约用它是杀鸡用牛刀)。
- 不改 `tushare_service` 那条路径(估值 / 信号 / 持仓监控不受影响)。
- 不动小区间(≤ ~1 年)的现有行为。

**风险与边界**:
- 去 cap 后大区间会向 tushare 真取全量(3 年 ~725 行一次调用);真实数据源能力内,mock 同样支持。
- 画长区间 K 线 → 走 run_python(凭 ref 灌全量 → plotly figure → chart 事件旁路),不在上下文堆数组。
- ref 过期(缓存 TTL 到期 / 跨用户)→ `_resolve_refs` 已有明确报错指导模型"重调原工具",非本设计新增风险。
