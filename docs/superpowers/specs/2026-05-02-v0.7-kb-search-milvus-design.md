## 0. 文档定位

### 为什么 v0.7 独立成 spec

v0.6 把"web_search 真接入 + production reliability layer"立完了,但 **`kb_search` 仍是 mock**(`MockKbSearchTool` 借调 `MockBochaService` 假造 KB 结果,没有任何真实 corpus / 向量检索)。**v0.7 是从 mock-KB 到 production-grade 知识库检索的第一步**,引入 3 个新工业级子系统:vector DB(Milvus)+ embedding service + PDF 解析。

独立成 spec 的理由:
- **故事完整性** —— 单一 portfolio 故事点:"production-grade vector retrieval + RAG ingest pipeline"。塞进 v0.6 会冲淡 web_search reliability 故事;塞进 v0.8 frontend 完全错配
- **scope 边界清晰** —— v0.7 = vector DB 部署 + corpus 准备 + ingest pipeline + retrieval 接入,数据工程性质;v0.8 sqlite→PG migration 是结构化数据迁移性质,各自一个清晰故事点
- **复用价值高** —— 3 个新 Protocol(KbSearchService / EmbeddingService / PdfParser)各自 mock+real 双 backend,延续 v0/v0.5/v0.6 已三次验证的 Protocol+factory+env-switch 模式,本 spec 第 4-6 次应用,沉淀稳定

## 2. 决策一:Scope = Path 2 仅 Milvus + KB ingest,sqlite→PG migration 留 v0.8

### ① 问题陈述

v0.7 brainstorming 暴露了一个工业级 storage 升级问题:5 个组件(checkpointer / trace / eval / quota / 即将新增 ingest_state + embedding_cache)全在 sqlite,工业级 LLM 应用 production 主流是 Postgres。要不要在 v0.7 同时做 sqlite→PG migration?

### ② 业界 alternatives

| 编号 | 形态 | 工时 | 风险 |
|---|---|---|---|
| Path 1. v0.7 一锅炖(Milvus + sqlite→PG 全 5 组件迁) | 12-16h | 两条新链路同时不稳定,debug 时不知道是 Milvus 问题还是 PG migration 问题 |
| **Path 2. v0.7 仅 Milvus,v0.8 = sqlite→PG migration 独立 spec**(选) | v0.7 14-17h + v0.8 5-7h | 单 spec 主线清晰;v0.8 PG migration 单独故事点(alembic / dual-write / shadow read) |
| Path 3. v0.7 Milvus + checkpointer 单点迁 PG 试点 | 9-11h | "一半 sqlite 一半 PG" 中间态,跨 DB JOIN 不可能,debug 噩梦 |

### ③ 选择:**Path 2**

**理由**:
- **PG migration 本身值一个独立 spec**:alembic 接入 + dual-write + shadow read + 5 表 schema 设计 + connection pool tuning,塞 v0.7 反而稀释
- **debug 风险隔离**:v0.7 同时引入"新 vector DB"和"换结构化 DB"两条新链路同时不稳定,debug 时只一条新链路是 senior 行为
- **容器数量曲线平滑**:v0.7 起 milvus + etcd + minio 三个新容器已经够 mac 资源紧张(虽然 32GB 撑得住),v0.8 再加 PG 容器替换 sqlite 资源曲线更稳
- **memory `feedback_no_portfolio_simplification`**:不能因为是 portfolio 就降低工业级标准,但**scope 切分仍是 senior 信号**

### ④ 量化评估方案

- **v0.7 工时**:14-17h(单 spec 主线)
- **v0.8 工时(估算)**:5-7h(独立 spec)
- **总工时**:19-24h(分两 spec 比 Path 1 12-16h 多 ~5h,代价是降低 debug 风险 + 拆分故事点)
- **新加 sqlite 文件**:2 个(`.ingest_state.sqlite` / `.embedding_cache.sqlite`),v0.8 一并迁 PG

## 3. 决策二:Vector DB = Milvus(对比 pgvector / Qdrant / Chroma / Pinecone)

### ① 问题陈述

LLM RAG 应用的向量存储 + ANN 检索引擎选什么?候选近 6 种,各有强弱。

### ② 业界 alternatives

| 编号 | 名字 | 实现技术 | 部署形态 | 国内招聘识别度 | 真实业务规模 |
|---|---|---|---|---|---|
| **VDB1. Milvus**(选) | C++,Zilliz(中国公司) | docker-compose / k8s / Lite / Cloud | **极强**(蚂蚁/字节/腾讯) | 百万-亿级 ms 级 |
| VDB2. Qdrant | Rust,社区 | 单容器 / Cloud | 中(欧美主流) | 百万级 |
| VDB3. Weaviate | Go | 单容器 / Cloud | 中 | 百万级 |
| VDB4. Chroma | Python | pip 嵌入式 | 弱 | <1M |
| VDB5. Pinecone | 闭源 SaaS | 仅云 | 中 | 亿级(SaaS) |
| VDB6. pgvector | Postgres 扩展 | 单 PG 容器 | 中(欧美 startup) | <50 万后慢 |

### ③ 选择:**VDB1 Milvus**

**理由(应用 memory `feedback_no_portfolio_simplification` 的工业级三维评估)**:

**(a) 业界落地真实困难**:
- 真实业务规模假设(金融研究助手 1k-10k docs × 200-500 chunks = 200k-5M vectors)进入 Milvus 舒适区,pgvector 在 ~50 万后 HNSW P99 50-100ms
- Milvus 支持 IVF / HNSW / DiskANN / SCANN 多算法,pgvector 0.7+ 才有 HNSW
- 多 collection / 复杂 filter 场景 Milvus 表达力强

**(b) 业界一般怎么选**:
- LangChain RAG starter / Zilliz 官方 RAG 案例:Postgres + Milvus
- 国内 LLM 团队主流:MySQL/Postgres + Milvus
- Vercel AI SDK starter:Postgres + pgvector(欧美 startup)
- IBM watsonx 金融 ref arch:Postgres + Milvus

**(c) 我们怎么选**:portfolio 主战场是中国市场,Milvus 国内招聘识别度极高(Zilliz 是中国公司,蚂蚁/字节/腾讯公开技术博客都提)。pgvector 在欧美主流但国内薄。

### ④ 量化评估方案

- **collection 数**:3(`kb_research` / `kb_financial` / `kb_policy`)
- **预估 vector 量(v0.7 sample corpus)**:13 docs × 30-80 chunks/doc ≈ 400-1000 vectors,Milvus 性能曲线 idle
- **vector dimension**:1536(qwen-embedding-v3),v0.9 切 BGE-M3 后变 1024(reingest 不可避免)
- **索引算法**:HNSW(默认,平衡精度+速度),v0.8 调优时再考虑 DiskANN

## 4. 决策三:Milvus 部署 = docker-compose Standalone

### ① 问题陈述

Milvus 有 4 种部署形态:Lite(嵌入式)/ Standalone(单机 docker-compose)/ Cluster(k8s)/ Zilliz Cloud(SaaS)。v0.7 选哪个?

### ② 业界 alternatives

| 编号 | 形态 | 配置成本 | 索引能力 | Portfolio 故事 |
|---|---|---|---|---|
| MD1. Milvus Lite(嵌入式) | 15 分钟,零运维 | 仅 FLAT(暴力 KNN) | 弱(嵌入式 vector DB 可讲性低) |
| **MD2. docker-compose Standalone**(选) | 1-2h(yml + healthcheck + volume) | 全索引(IVF/HNSW/DiskANN) | **强**(本地起 Milvus 集群,etcd/minio 协同) |
| MD3. Cluster(k8s) | 4-6h | 全 + scale-out | 过度,v0.7 不需要 |
| MD4. Zilliz Cloud free tier | 30 分钟(注册 + credentials) | 全 | 中(用了 managed,但黑盒,看不到 etcd/minio 拓扑) |

### ③ 选择:**MD2 docker-compose Standalone**

**理由**:
- **Portfolio 故事最强**:展示对 Milvus 内部架构的理解(milvus 协调 + etcd metadata + minio 对象存储分离),面试官问"vector DB 怎么存数据"能答出"metadata 在 etcd,vector 数据落 minio"
- **production parity**:真实公司部署 Milvus 也是 k8s + 容器,docker-compose 拓扑跟生产同构
- **L1/L2 测试无缝**:Milvus 容器在本地起,L1 fixture(`milvus_test_container`)docker-compose up + healthcheck + cleanup
- **资源 OK**:32GB Mac 跑 milvus(2GB)+ etcd(<200MB)+ minio(~500MB)+ Mac 系统 + Docker Desktop + MinerU,余量足

### ④ 量化评估方案

- **`docker-compose.milvus.yml`**:3 service(milvus-standalone / etcd / minio)+ 端口映射(19530 / 9091 / 2379 / 9000)+ named volumes + healthcheck(`pg_isready`-style probe)
- **首次启动**:~30s(image pull + 容器初始化)
- **稳态资源**:~3GB RAM / ~500MB disk(v0.7 sample corpus)
- **失败模式**:容器没起来 / etcd 不可达 / minio 满了,5 类错误 raise 到 KbSearchService 上层(memory `project_v0.6_architecture_landed` 的 5 类错误模式镜像)

## 5. 决策四:KbSearchService Protocol 签名 = 工业级标准

### ① 问题陈述

KB 搜索的核心入口签名,锁定后影响上层 agent 调用形态。

### ② 业界 alternatives

| 编号 | 形态 | 接口表达力 |
|---|---|---|
| KS1. 最小化 | `search(query, top_k)` | 无 collection 路由 / 无 filter / 无 threshold,demo 形态 |
| **KS2. 工业级标准**(选) | `search(query, collections, top_k, threshold, filters)` | 跟 LangChain VectorStore / Pinecone 一致 |
| KS3. 留 hybrid mode 字段 | `search(query, ..., mode: dense\|sparse\|hybrid)` | YAGNI 反模式,v0.9 真接 BGE-M3 时还是要改签名 |

### ③ 选择:**KS2 工业级标准**

**`KbSearchService` 接口**:
```python
from typing import Protocol, Any

class KbSearchService(Protocol):
    async def search(
        self,
        query: str,
        collections: list[str] | None = None,    # None = 跨全部 3 类
        top_k: int = 5,
        threshold: float | None = None,           # 相似度过滤(cosine 距离 >= threshold)
        filters: dict[str, Any] | None = None,    # metadata 过滤,e.g. {"broker": "招商证券"}
    ) -> list["KbHit"]: ...

class KbHit(BaseModel):
    chunk_id: str
    chunk_text: str
    similarity: float
    metadata: dict[str, Any]  # 包含 doc_id / pub_date / source_url / 类型特定字段
```

**理由**:
- **业界事实标准**:跟 LangChain VectorStore.similarity_search / Pinecone client.query / pymilvus search 一致
- **支持多 collection 路由**:`collections=["research"]` 或 `["research","financial"]` 或 `None`
- **filters 支持金融业务真实查询**:`{"broker": "招商证券", "pub_date_after": "2024-01-01"}`
- **YAGNI 反对 KS3**:v0.9 BGE-M3 真接 hybrid 时 reranker / weight tuning 都会同时改,仅留 mode 字段不够;那时再改签名是 breaking change 但范围可控

**`filters` 字段白名单**(spec 阶段必须锁死,避免 reingest 噩梦):

| collection | 支持的 filter 字段 |
|---|---|
| 公共(全 3) | `pub_date_after` / `pub_date_before` / `source_type` |
| `kb_research` | `broker` / `industry` / `rating` / `analyst` |
| `kb_financial` | `company_code` / `fiscal_year` / `fiscal_quarter` / `section` |
| `kb_policy` | `issuer` / `scope` |

### ④ 量化评估方案

- **Protocol LOC**: ~30 行(Protocol + KbHit BaseModel + 异常类型)
- **mock backend**: 复用 `MockKbSearchTool`,~30 行 adapter 套上 Protocol
- **real backend `MilvusKbSearchService`**: ~150 行(连接管理 + 多 collection 并查 + filter expr 转换 + similarity 计算)

## 6. 决策五:Embedding 模型 = qwen API + EmbeddingService Protocol(留 BGE-M3 切换)

### ① 问题陈述

Embedding 模型决定 vector dimension,Milvus collection schema 创建时锁死。中文金融场景候选:qwen-embedding-v3 / BGE-M3 / m3e / OpenAI text-embedding-3 / bge-large-zh。

### ② 业界 alternatives

| 编号 | 候选 | 维度 | 调用方式 | 现 stack 兼容 | 中文金融 | Portfolio 故事 |
|---|---|---|---|---|---|---|
| **EM1. qwen-embedding-v3 API**(选 v0.7) | **1024**(API 限制 ∈ {64,128,256,512,768,1024},Spike 5 实测) | dashscope API | 复用 `DASHSCOPE_API_KEY` + `LLMService` | 强 | 中(常规 API) |
| EM2. BGE-M3 本地(留 v0.9) | 1024 | 本地 / API | ⚠️ 需 GPU 服务 | 强(C-MTEB SOTA) | 强(本地部署 + dense+sparse hybrid) |
| EM3. m3e-large 本地 | 1024 | 本地 | ⚠️ 需 GPU | 中(被 BGE 取代) | 弱 |
| EM4. OpenAI text-embedding-3 | 3072 / 可降 | API | ❌ 跟 DASHSCOPE 不同 vendor | 中(多语言,中文不专项) | 弱 |
| EM5. bge-large-zh 本地 | 1024 | 本地 | ⚠️ 需 GPU | 中(被 BGE-M3 取代) | 弱 |

### ③ 选择:**EM1 qwen API + EmbeddingService Protocol(预留 BGE-M3 切换口子)**

**`EmbeddingService` 接口**:
```python
class EmbeddingService(Protocol):
    async def embed(self, texts: list[str]) -> list[list[float]]: ...

    @property
    def dimension(self) -> int: ...

    @property
    def model_name(self) -> str: ...

class QwenEmbeddingService:
    """v0.7 default backend, 调 dashscope API.

    Note: dimension=1024 是 qwen text-embedding-v3 API 允许的最高维度
    (枚举 {64,128,256,512,768,1024},Spike 5 实测确认 1536 会被拒)。
    """
    dimension = 1024
```

## 9. 决策八:Chunking 策略 = SemanticChunker(A)+ section-based(B/C)+ 类型路由

### ① 问题陈述

每类 corpus 内容形态不同(研报连续叙述 / 财报章节明确 + 表格 / 政策条款式),chunking 策略选什么?

### ② 业界 alternatives

| 编号 | 形态 | 适用 corpus |
|---|---|---|
| CK1. 全统一 fixed-size + 边界感知 | 全部用 `RecursiveCharacterTextSplitter` 500/50 | demo 形态 |
| CK2. 全 semantic chunking(LLM judge) | 全部 propositional 切 | 过度,政策条款已天然分隔 |
| **CK3. 类型路由 + 借势**(选) | A 用 SemanticChunker / B/C 用 section-based + RecursiveSplitter | 真生产 |
| CK4. 全 fixed-size 无边界感知 | 纯 char 切 | 反模式(切句子) |

### ③ 选择:**CK3 类型路由 + 借势**

**3 套 chunker 设计**:

```python
# A 研报 → SemanticChunker(LangChain,基于 embedding 相似度切)
class SemanticChunkerForResearch:
    """
    Step 1: MinerU 解析得到 sections
    Step 2: 在每个 section 内用 LangChain SemanticChunker(threshold 调到 finance 域)
    Step 3: chunk size cap 800 tokens,过长强制切
    """

# B 财报 → section-based(MinerU sections 直接用)+ 表格独立 chunk
class SectionChunkerForFinancial:
    """
    Step 1: MinerU 解析得到 sections + tables
    Step 2: 每个 section 直接作为 chunk(若 > 800 tokens 用 RecursiveSplitter 二次切)
    Step 3: 每个 table 独立 chunk(markdown 形式),metadata 标 section_index
    """

# C 政策 → 条款拆分(自定义 separators)+ Recursive
class ClauseChunkerForPolicy:
    """
    Step 1: MinerU 解析得到 sections
    Step 2: 用自定义 separators 按"第X条" / "第X款" / "1.2.3" 切
    Step 3: 每条独立 chunk(< 500 tokens 也保留独立)
    """
```

**通用 chunking 参数(spec 阶段锁死,影响 reingest)**:
- chunk_size_default = 500 tokens(qwen tokenizer 近似 cl100k_base)
- chunk_size_max = 800 tokens(财报 section 上限)
- overlap = 50 tokens(SemanticChunker 自管理 / RecursiveSplitter 50)
- 中文 separators = `["\n\n", "。", "\n", "？", "！", "；", " ", ""]`
- 政策 separators = `[r"\n第[一二三四五六七八九十百千]+条", r"\n第[一二三四五六七八九十百千]+款", r"\n\d+\.\d+"]`(regex)

**理由**:
- **按 corpus 内容形态选最合适策略**是真正 senior 信号
- **A 研报 SemanticChunker 价值高**:连续叙述边界判断难,语义相似度切准确度 +5-10%
- **B 财报 section-based**:MinerU 已识别章节,直接用即可;表格独立 chunk 避免被 SemanticChunker 错切
- **C 政策条款式**:已有天然边界,SemanticChunker 是 over-engineering
- **避免 LLM judge propositional chunking**:每段 LLM call 太贵,SemanticChunker(embedding 相似度)5x 快且免一个 LLM call

### ④ 量化评估方案

- **3 个 chunker LOC**: ~250 行(共享 base class + 3 子类)
- **chunking 时间**: A semantic ~10s/doc / B section ~2s/doc / C clause ~1s/doc
- **chunk 数估算(13 docs)**: 400-1000 个 chunks
- **chunk-embedding 调用次数**: 1 次 batch(开发期反复跑用 cache 命中 ~80%)

```python
# Index: HNSW on `vector`,M=16,efConstruction=200(默认)
# Metric: COSINE(归一化向量后等价 inner product,适合中文 embedding)
```

**外部存储**:
- PDF 原件:`backend/data/sample_corpus/<type>/<doc_id>.pdf`(权威源,审计 / 重 ingest 都能溯源)
- 完整全文 / abstract:暂不存,**v0.8 PG migration 时加 `documents` 表**

**理由**:
- **filter 在 Milvus 内做(expr filter,fast)**:`broker == "招商证券" and pub_date > "2024-01-01"`
- **检索一次拿到 chunk_text + 元数据,无需跨 DB JOIN**(v0.7 没 PG)
- **PDF 原件作权威源**:不依赖 v0.7 没有的 PG,通过文件系统 single-source-of-truth
- **跟业界主流 schema 设计一致**:Milvus 官方 RAG 示例 / Pinecone metadata pattern / Zilliz 蓝皮书

### ④ 量化评估方案

- **Schema 字段总数**:公共 8 + research 5 + financial 5 + policy 3 = 各 collection 11-13 字段
- **单 chunk 存储**:vector 6KB + scalar 元数据 ~500 bytes ≈ 6.5KB
- **总存储估算**:1000 chunks × 6.5KB ≈ 6.5MB(Milvus disk)
- **Index 构建时间**:HNSW for 1000 vectors ~500ms

## 12. 决策十一:Reliability layer = embedding 复用 v0.6 + KbSearchService retry/LRU cache

### ① 问题陈述

v0.6 沉淀了 4 件 reliability(`RateLimiter / CircuitBreaker / QuotaCounter / CostBudget`)。v0.7 哪些复用?哪些新增?

### ② 业界 alternatives

| 编号 | 形态 | scope | Portfolio |
|---|---|---|---|
| RL1. 极简:仅 embedding API 走 reliability | -1h | demo 形态 | 弱(KbSearchService 无 retry,Milvus 抖动直接 502) |
| **RL2. 中等:加 KbSearchService retry + query cache**(选) | +1.5h | production 优雅退化 | **强**(hot query 缓存 + 退避重试) |
| RL3. 完整:RL2 + ingest retry + 全链路 metric | +2.5h | metric 没有 backend 做半吊子 | 中(留 v0.9 observability 完整) |

### ③ 选择:**RL2 中等**

**Reliability 复用矩阵**:

| Reliability 件 | 复用情况 | 说明 |
|---|---|---|
| `RateLimiter`(v0.6) | ❌ Milvus 本地无限速 | embedding API 那侧通过 LLMService 自动复用 |
| `CircuitBreaker`(v0.6) | ❌ Milvus 本地容器,不需要熔断 | embedding API 那侧 LLMService 已包 |
| `QuotaCounter`(v0.6) | ❌ Milvus 本地无配额 | embedding API 那侧已包 |
| `CostBudget`(v0.6) | ✅ 加 `qwen_embedding_monthly` 实例 | embedding call 自动经过,**v0.6 reliability 沉淀真正用上** |
| `Retry`(新加) | ✅ KbSearchService 包一层 | Milvus 连接 / 超时失败,指数退避 3 次 |
| `LRU cache`(新加) | ✅ KbSearchService 包一层 | query → result 缓存(size=1000, TTL=1h),命中跳过 embedding + Milvus |

**`ReliableKbSearchService` 接口**:
```python
class ReliableKbSearchService:
    """
    Wraps MilvusKbSearchService with retry + LRU cache.
    Keeps the same KbSearchService Protocol.
    """
    def __init__(
        self,
        inner: KbSearchService,
        cache_size: int = 1000,
        cache_ttl: int = 3600,
        max_retries: int = 3,
        backoff_base: float = 0.5,
    ):
        self._inner = inner
        self._cache = TTLCache(maxsize=cache_size, ttl=cache_ttl)
        ...

    async def search(self, query: str, ...) -> list[KbHit]:
        # 1. cache key = hash(query, collections, top_k, threshold, filters)
        # 2. 命中 → return + emit cache_hit metric
        # 3. miss → retry inner.search 3 次(指数退避,base 0.5s,max 4s)
        # 4. 成功 → set cache + return + emit cache_miss metric
```

**理由**:
- **embedding API 复用 v0.6 是关键故事点**:不是新做,是**让已有 reliability 沉淀真正用上**
- **KbSearchService retry 是 production minimum**:Milvus 偶发抖动直接 502 是反模式
- **Query cache 显著降低成本**:高频问题免费(开发期 + nightly + 用户重复问),命中率 metric 是 portfolio 故事
- **反对 RL3 完整 metric**:metric backend 缺位(v0.7 没接 prometheus / grafana),做半吊子价值低,留 v0.9

### ④ 量化评估方案

- **`ReliableKbSearchService` LOC**: ~120 行(包装层 + retry 装饰器 + LRU 集成 + metric emit)
- **Retry 策略**:指数退避 base=0.5s,max 3 次,total max 0.5+1+2 = 3.5s 等待
- **Cache 命中率(预估)**:开发期反复跑命中 70-90%,production 高频 query 30-50%
- **Cache invalidation**:reingest 后 cache 仍命中老结果(v0.7 不处理,留 follow-up;manual 清缓存:重启服务)

### ① 问题陈述

Ingest 是离线 batch 任务,形态选错影响开发体验和重跑安全性。CLI / API / Library?有无增量?有无缓存?

### ② 业界 alternatives

| 编号 | 形态 | 工时 | Production |
|---|---|---|---|
| IP1. 极简:一次性脚本无增量无缓存 | 1h | demo |
| **IP2. CLI + 增量 + 缓存 + 进度 + 错误隔离**(选) | 3h | production minimum |
| IP3. CLI + API endpoint + library | 5h | API endpoint 是反模式 |

### ③ 选择:**IP2 CLI + 增量 + 缓存 + 进度 + 错误隔离**

**CLI 设计**:
```bash
# 全量 ingest(增量,自动跳过已处理)
python -m app.scripts.ingest_kb \
  --collection research \
  --pdf-dir backend/data/sample_corpus/research/

# 强制重 ingest 某文档(失效缓存)

  --collection research \
  --doc-id 2024_zhaoshang_ningde \
  --force

# 跨 collection 全 ingest

# dry-run(只解析 + 切 chunks + 显示 token 数,不调 embedding API)
python -m app.scripts.ingest_kb --all --dry-run
```

**核心组件**:

```python
class IngestPipeline:
    """
    主流程:
      1. scan PDF 目录 + 读 manifest.yaml 拿元数据
      2. 对每份 doc:
         a. 查 IngestState 是否已 ingest(同 doc_id + content_hash 跳过)
         b. 调 PdfParser.parse(pdf_path) → ParsedDocument
         c. 路由 chunker(根据 source_type)
         d. 切 chunks
         e. 查 ChunkEmbedCache 命中,miss 调 EmbeddingService.embed(batch=25)
         f. 写 Milvus collection
         g. update IngestState
      3. 每 doc 失败:log + 跳过 + 继续下一 doc
      4. 进度条:[研报 3/5][chunks 47/82][cost ¥0.12][cache hit 35%][ETA 2m30s]
    """

class IngestState:
    """
    sqlite 文件:backend/data/.ingest_state.sqlite
    Schema:
      ingested_docs (doc_id PK, content_hash, ingested_at, chunk_count)
    去重:同 (doc_id, content_hash) 跳过;新 hash 重新 ingest 该 doc
    """

class ChunkEmbedCache:
    """
    sqlite 文件:backend/data/.embedding_cache.sqlite
    Schema:
      embeddings (cache_key PK, vector BLOB, model_name, dimension, created_at)
    cache_key = sha256(chunk_text + model_name + str(dimension))
    用途:开发期反复跑,chunk 不变直接命中,跳过 API call
    """
```

**理由**:
- **业界 production 主流**(LangChain / LlamaIndex / Pinecone reference 都是 CLI + 增量 + 缓存)
- **trick 1-5 全覆盖**:增量 / 缓存 / batch / 并行 / 进度条
- **API ingest 是反模式**:长任务 / 状态轮询 / 资源隔离 / 失败重试,production 几乎无人这么做
- **Library 抽象 YAGNI**:只 ingest 脚本调,无其他 caller,留 v1+ 真有需求再加

### ④ 量化评估方案

- **`IngestPipeline` LOC**: ~250 行
- **`IngestState` LOC**: ~80 行
- **`ChunkEmbedCache` LOC**: ~80 行
- **CLI argparse + main**: ~80 行
- **Progress / errors**: ~50 行
- **总 ingest LOC**: ~540 行

**新加 sqlite 文件**(memory `feedback_path_resolution_in_plans`):
- `backend/data/.ingest_state.sqlite`(显式绝对路径,避免 backend/backend/data 残留)
- `backend/data/.embedding_cache.sqlite`(同上)
