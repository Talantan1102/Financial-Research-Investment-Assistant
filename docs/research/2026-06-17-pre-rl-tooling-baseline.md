# RL 训练前的工具修复与计算能力基线(2026-06-17)

## 这份文档回答什么

我们为"计算型金融场景"建了反向出题 + pass@k,本意是给"要不要上 RL"提供依据。
核心论点:**断崖若是工具/口径问题,先修工具比上 RL 更对症**。本轮把 RL 训练前能做的
提升都做了,并量化了修复前后的计算能力基线——结论是**断崖确实是工具问题,修完后
留给 RL 的真实能力缺口很小**。

> 评测预算 max_steps=18,而生产 GateConfig 默认 12——评测已比生产宽松,故不靠提预算刷分。
> 基准已钉到已落定交易日(as_of=20260612),gold 一次算定、可复现。

## 一、战力断崖与真凶

pass@k 按 难度×指标 分桶,断崖稳定落在**需长窗口(近三年)数据**的题:CAGR 全部 3y,初版 13%。
断崖不在"算不算得来",在"取不取得齐长窗口数据"。

真凶:`get_daily` 里 `_MAX_ROWS=260` 的**静默 tail**——不管问几年,最多只返回最近约 1 年,
更早的悄悄丢弃。agent 的"预防性分段"不是坏习惯,是被逼的:问 3 年只拿回 1 年,只能分多次取,
每段把一整年灌进上下文 → 烧光循环步数,死在最后一步 run_python 之前。还是个静默正确性坑
(粗心 agent 拿 1 年当 3 年算,错且不自知)。

## 五、残留 15 个失败的定性:不是"算不出",是 agent 工具调用可靠性

逐条读完,残留**压根不是能力缺口**,而是 agent 把工具链跑歪/跑断:

| 残留类型 | 约数 | 具体例子 | 是 RL 目标吗 |
| --- | --- | --- | --- |
| trade_cal 漏 anchor 参数 → 报错就放弃 | ~4 | 古井/隆基/洋河/平安:**"调交易日历时缺 anchor 无法继续"**——它看懂了错误,却不重试 | **是** |
| fetch 错股票代码 | ~1 | 工行涨幅取成了 601988(中国银行)而非 601398 | **是** |
| 不照 trade_cal 窗口取数 | ~2 | 茅台用 03-02 当"三个月前",oracle 用 trade_cal 的 03-12 → 窗口对不齐 | **是**(对齐可靠性) |
| 窗口边界 × 紧容差临界 | ~3 | 差一两个交易日刚好顶破容差 | 否——容差边界 |
| judge 抽取抖动 | ~1 | LLM 判 set 的边界 | 否——判分 |

## 六、对 RL go/no-go 的结论(本轮最关键产出)

1. **断崖是工具问题,已修。** CAGR 13%→100%,0 "算不出",印证"先修工具比上 RL 更对症"。
2. **修完后,残留不再是"会不会算指标"(已解决),而是"能不能可靠地把工具链跑完"**——
   漏参、取错代码、不照窗口、报错就放弃。**agent 有知识(看懂错误),缺的是可靠性。**
3. **这恰恰是 RL 的正经靶子:工具调用可靠性 / 多步编排,不是计算能力。**
   所以结论不是"没 RL 什么事",而是更准的一句:**先修工具把"能不能算"解决掉,RL 该瞄准"能不能稳"。**
   用更多 prompt/工具兜底去堵每个 fumble 是 whack-a-mole(本轮 data_refs / 摘要捷径都曾这样自伤);
   "可靠编排工具"正是 RL 的强项,这才是对症的 RL 设计目标。

## 七、方法论沉淀

- **stale gold 坑**:反向出题用 as_of=今天 + live tushare,窗口含未回填的近端 bar → gold 每天漂移。
  正解:钉 as_of 到已落定交易日。**诊断纪律:某桶突然整桶崩,先用当前数据重算 gold 比漂移,再疑代码。**
- **复权 ≠ 价格回报**:pct_chg 累乘是"含分红的总回报",close 比值是"价格回报",两者差一个股息率;
  改口径前必须分清要的是哪个(本轮误把总回报当价格回报,基线 125→78)。
- **加 prompt/工具引导要全量回归**:summary 加 high/low、data_refs 规矩、复权口径都曾引入新桶的回归,
  单测拦不住,必须 pass@k 全量验。
