# RL 训练前的工具修复与计算能力基线(2026-06-17)

## 这份文档回答什么

我们为"计算型金融场景"建了反向出题 + pass@k,本意是给"要不要上 RL"提供依据。
核心论点:**断崖若是工具/口径问题,先修工具比上 RL 更对症**。本轮把 RL 训练前能做的
提升都做了,并量化了修复前后的计算能力基线——结论是**断崖确实是工具问题,修完后
留给 RL 的真实能力缺口很小**。

> 评测预算 max_steps=18,而生产 GateConfig 默认 12——评测已比生产宽松,故不靠提预算刷分。
> 基准已钉到已落定交易日(as_of=20260612),gold 一次算定、可复现。

## 一、战力断崖与真凶

pass@k 按 难度×指标 分桶,断崖稳定落在**需长窗口(近三年)数据**的题:CAGR 全部 3y,初版 13%。
断崖不在"算不算得来",在"取不取得齐长窗口数据"。

真凶:`get_daily` 里 `_MAX_ROWS=260` 的**静默 tail**——不管问几年,最多只返回最近约 1 年,
更早的悄悄丢弃。agent 的"预防性分段"不是坏习惯,是被逼的:问 3 年只拿回 1 年,只能分多次取,
每段把一整年灌进上下文 → 烧光循环步数,死在最后一步 run_python 之前。还是个静默正确性坑
(粗心 agent 拿 1 年当 3 年算,错且不自知)。

## 四、残留 16 个失败的定性:不是 RL 能力缺口

| 残留 | 数 | 性质 | 是 RL 目标吗 |
| --- | --- | --- | --- |
| 复杂/筛选 | 4 | 5 只股票 × 算涨幅+回撤,18 步(生产 12)撞预算天花板;去捷径后正确计算更费步 | 否——预算/scope 约束,非"不会算" |
| 简单/涨幅 | 7 | 窗口边界精度:差 1 个交易日 × 0.5% 紧容差;agent 与 oracle 同用 trade_cal window,偶发取数边界抖动 | 否——容差/边界,非能力 |
| 中等/相关 | 3 | 对齐后的边界/极端值;judge 抽取边界 | 否——口径/判分边界 |
| 波动/双指标 | 2 | 容差临界(rel 0.02 刚超) | 否——容差临界 |

残留**全是**预算天花板、容差临界、判分抖动——RL 在这些上**几乎无发挥空间**(改不了硬容差、
硬预算)。修复前那种"成片算不出来"(空答/断崖)才是能力问题,已被工具修复消化。

## 五、对 RL go/no-go 的结论

1. **断崖是工具问题,已修。** CAGR 13%→100%,0 空答,印证"先修工具比上 RL 更对症"。
2. **修完后真实能力很高(88.7%@18 步),残留非能力。** RL 的发挥空间被工具修复挤掉了大半。
3. **若仍要 RL,正确的靶子是"多步预算下的效率"**(如 5 股筛选一次批量算完),而非"会不会算指标"——
   但那已是 agent 行为/预算 scope 设计问题,且 prompt nudge 已多次显示易引副作用(data_refs / 摘要捷径
   都曾自伤),边际收益低、风险高,不在本轮继续追。

## 六、方法论沉淀

- **stale gold 坑**:反向出题用 as_of=今天 + live tushare,窗口含未回填的近端 bar → gold 每天漂移。
  正解:钉 as_of 到已落定交易日。**诊断纪律:某桶突然整桶崩,先用当前数据重算 gold 比漂移,再疑代码**
  (本轮一度被骗以为是回归,重算 gold 才发现 agent 是对的)。
- **加 prompt/工具引导要全量回归**:summary 加 high/low、data_refs 规矩都曾引入新桶的回归,单测过不了关,
  必须 pass@k 全量验。
