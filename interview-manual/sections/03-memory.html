03跨会话记忆系统

这一组带你拆开 AlphaScout 的「跨会话记忆」系统:为什么一个 AI 助手光靠上下文窗口记不住老用户、一条偏好如何被抽取存档又在下次对话里被想起、为什么记忆必须同时区分「事情发生的时间」和「系统知道的时间」,以及写入冲突消解、三路混合检索、个人记忆 vs 市场知识的分流、三套存储库的一致性这些工程硬骨头。从零基础类比讲起,逐步深入到真实算法与一致性设计。

Q1

先打个基础:一个 AI 助手为什么需要"跨会话记忆"?它的上下文窗口不是已经能记住对话了吗?两者差在哪?

★★☆☆☆
跨会话记忆上下文窗口持久化基础概念

🎯 考察点分析

这道题看着像"送分题",其实面试官在确认一件事:你是否真的分得清"模型当下读进去的那段文字"和"系统长期替用户保管的信息"。很多人把大模型当成一个"会记事的人",其实它每次回答都是从零开始读一遍材料——这个误解会让你后面所有关于记忆系统的设计都站不稳。所以面试官想看到:

  • 追问:上下文窗口到底"记"到什么时候为止?换一个新会话、或者过了一周再回来,它还在吗?(考你知不知道窗口的边界是"单次会话")
  • 追问:那为什么不干脆把所有历史聊天记录每次都塞回窗口里,不就"永远记得"了?(考你懂不懂容量和成本这两道现实墙)
  • 追问:如果要做持久记忆,信息该存在哪、什么时候再拿出来?(把概念引向工程实现:落库 + 按需检索回填)
  • 追问:在你的项目里,这个"长期记忆层"是怎么接进聊天主流程的?(考你有没有真做过,而不是背概念)

📚 原理讲解

先把最核心的一句话说清楚:上下文窗口不是"记忆",它是"当下摊在桌上的一摞材料"。

上下文窗口 = 桌上摊开的草稿纸

大模型回答问题的方式,是把"这一轮要参考的所有文字"——系统设定、你这次会话里说过的每句话、它自己刚回的话——一股脑读进去,然后接着往下写。这一摞文字就是上下文窗口。它有两个关键性质:

第一,它是临时的。就像你在草稿纸上演算,这张纸只在你这次坐下办事时有用;你起身离开(关掉会话)、或者换一张新纸(开一个新会话),上面写的东西就不在新纸上了。模型本身不会偷偷把旧纸收进抽屉——它没有抽屉。

第二,它是有限的。草稿纸再大也有边,写满了就得擦掉早先的内容腾地方。所以哪怕在同一次会话里,聊得太久,最早那几句也会被挤出窗口。

那"跨会话记忆"要解决的是什么?

是这种场景:用户上周跟你说过"我只想买低风险的标的",这周他换了个会话重新进来问"帮我看看这只股票"。这时候上周那张草稿纸早扔了,窗口里干干净净,模型根本不知道他偏好低风险。如果你想让助手"记得这个人",这条信息就必须在会话结束后还活着——它得被搬到对话流程之外的地方存起来,也就是落到一个数据库里。下次对话开场,系统再主动去库里把相关的几条捞出来,拼回新的草稿纸上,模型才"想得起来"。

所以两者的本质区别,不是"记得多 vs 记得少",而是"活在单次会话里" vs "活在会话之外的长期存储里"。窗口管不到会话边界以外,这是它的能力天花板,不是调大尺寸能解决的。

那不能把历史全塞回窗口吗?——两道现实墙

有人会想:既然落库再捞回来麻烦,我每次开会话就把这个用户过去所有聊天记录原样塞进窗口,不就永远记得了?两道墙拦住这条路:

第一道墙:装不下。窗口大小有上限,一个老用户聊了几百轮,原样回放根本超出窗口容量。

第二道墙:烧钱。模型按读进去的文字量(token)收费,每一轮都把全部历史重读一遍,成本会随历史线性膨胀,而且大部分内容跟当前这句话毫不相关,纯属浪费。

所以正确做法不是"回放全部",而是"抽取 + 按需检索":对话过程中把零散闲聊里真正有价值的事实(比如"偏好低风险")抽出来、结构化地存进库;下次只把跟当前问题相关的少量条目捞回窗口。在本项目里,回填给模型的"个人画像"只占大约 500 token 的预算,而不是整段历史——这正是为了绕开上面两道墙。

在本项目里它叫什么

这套长期记忆层叫分层记忆(HierarchicalMemory)。它通过一个统一接口——记忆协议(Memory Protocol)——挂进聊天主循环,替换掉原来那个只在单次会话内有效的会话内记忆(InSessionMemory)。"统一接口"的好处是:主循环只认这套接口,底下换成"只记当下"还是"跨会话持久"两种实现,主循环代码一行不用改。具体存进去、再想起来的完整机制,见本类第 2 题;为什么底层用 MemGPT × Zep 杂交,见本类第 3 题。本题只需站稳"窗口管不过会话边界、记忆库才能跨边界"这个地基。

💻 示例讲解

用一段教学伪代码对比两种"记忆"。注意看:只靠窗口时,新会话开场窗口是空的;接上持久记忆后,系统会先去库里捞回相关条目再开聊。

# ===== 场景:用户上周说过"我偏好低风险",这周换新会话再进来 =====

# 【方案 A】只靠上下文窗口
def chat_window_only(session, user_msg):
    # 窗口里只有"本次会话"说过的话,新会话开场 = 一摞空材料
    window = session.messages          # 上周那次会话的内容,这里根本不在
    window.append(user_msg)            # 把这句话也摊到草稿纸上
    return model(window)               # 模型只看得到当下这摞,记不起"低风险"

# 【方案 B】接上持久记忆层(本项目做法)
def chat_with_memory(session, user_id, user_msg, memory):
    window = session.messages

    # 开场先去"文件柜"里,按当前这句话捞回少量相关旧事实
    # 不是回放全部历史,只取最相关的几条(本项目个人画像约 500 token)
    recalled = memory.archival_memory_search(user_id, query=user_msg, k=5)
    window = inject_persona(window, recalled)   # 把捞回的事实拼回草稿纸开头

    window.append(user_msg)
    answer = model(window)                       # 现在模型看得到"偏好低风险"了

    # 会话过程中,把这轮里值得长期记住的事实抽出来、存回柜子
    # 关一会话也不丢,下次还能捞 —— 这就是"跨会话"的关键动作
    memory.write_episode(user_id, session.id, user_msg, answer)
    return answer

推演:假设用户历史里攒了 300 轮对话。方案 A 想"记得",只能把 300 轮全塞回窗口——可能直接超出窗口上限装不下,就算装得下,每轮也要为这一大坨历史重复付 token 费,而当前问题真正用得上的可能就一句"偏好低风险"。方案 B 只捞回约 500 token 的相关画像拼进去,既不爆窗口、又把每轮的检索回填成本压到很小一块,模型照样"记得你"。一句话:方案 B 用"抽取后按需捞"换掉了"原样全回放"。

⚖️ 决策对比

维度我们的选择:独立持久记忆层替代方案:只靠上下文窗口记
能否跨会话/跨天能。信息落库,换会话/换天捞回来不能。会话一关就清空,新会话从零开始
长历史容量不受窗口限制,库里随便存,按需取少量受窗口上限卡死,老用户历史装不下
每轮 token 成本只回填相关少量条目(画像约 500 token)想记得就得每轮重读全部历史,成本随历史涨
实现复杂度高。要额外建写入管线 + 检索管线两条零。模型自带窗口,什么都不用做
信息形态抽取后的关键事实,结构化、可检索原始聊天记录,杂、长、难精确取用

公允裁决:只靠窗口绝不是"差方案",它有真实优点——零实现成本、零额外延迟,而且在单次连续会话内它完全够用,本来就该让它管"当下这轮的上下文"。它唯一的死穴是管不过会话边界、也装不下长历史。我们要做的产品是"持续陪用户、记得他长期偏好的投研助手",这个需求天然落在窗口能力之外,所以才额外建一层持久记忆——代价是要多写两条管线:把对话里的事实抽出来存进库的写入管线,和下次对话按需把相关事实捞回来的检索管线。这两条管线正是本分类后面几道题要拆的内容。换句话说:窗口管"短期当下",记忆库管"长期跨会话",两者不是替代关系,而是分工。

📌 总结

  • 上下文窗口是"单次会话内摊在桌上的草稿纸":临时(会话一关就清空)、有限(写满挤掉旧内容),本质是会话内记忆,跨不过会话边界。
  • 跨会话记忆解决的是"这个用户上周/去年说过什么":信息必须落到对话流程之外的持久存储(数据库),下次再主动捞回拼进提示词。
  • 不能把历史全塞回窗口——两道墙:装不下(超窗口上限)、烧钱(每轮重读全部历史);所以只存抽取后的关键事实、按需检索少量回填。
  • 本项目里这层叫分层记忆(HierarchicalMemory),通过记忆协议(Memory Protocol)挂进聊天主循环,替换掉只在单会话有效的会话内记忆(InSessionMemory),两种实现可互换。
  • 窗口与记忆库是分工不是替代:前者管短期当下,后者管长期跨会话——代价是要多建写入与检索两条管线(见本类第 2、3 题)。

一句话速记:窗口=会话内的临时草稿纸,记忆库=会话外的归档文件柜;窗口跨不过会话边界,持久记忆才让助手"换天也记得你"。

Q2

你的记忆系统大体长什么样?拿"用户去年说过他偏好低风险"举例,这条信息怎么被存下来、又在下一次对话里被想起来?

★★★☆☆
记忆系统架构抽取检索写读两管线三库镜像

🎯 考察点分析

面试官想确认你不是把"记忆"理解成"把聊天记录原样存数据库,下次全读出来"。能不能讲清"写"和"读"是两条独立管线、中间存的是被提炼过的结构化事实而不是原话,是这道题的分水岭。我会用一个具体例子("偏好低风险")逼你把整条链路从头走到尾,看你哪一环讲不下去。

  • 追问:为什么不直接存原话?存了原话下次不也能读出来吗?(逼你说清"结构化事实"相比"原始文本"在检索和回填时的优势)
  • 追问:一条"偏好低风险"到底被存成了什么数据结构?字段有哪些?
  • 追问:下次对话开场,系统怎么知道该把这条而不是别的几百条记忆塞进窗口?
  • 追问:同一条记忆为什么要在三个不同的数据库里各存一份?不冗余吗?

📚 原理讲解

核心一句话:我的记忆系统不存对话,存"被抽出来的事实"。它拆成两条管线 —— 写的时候把对话提炼成结构化事实存进库,读的时候按当前问题再把相关事实捞回来。两条管线在时间上是错开的:写发生在你说完话之后,读发生在下一次会话开场或遇到具体问题时。

写:把一句口语抽成一张"事实卡片"

用户说"我偏好低风险",这是一句口语。写入侧有个叫 LLMExtractor 的环节,职责就是把口语翻译成一条结构化的"边"(edge)。这条边长这样:主体 = 用户,关系类型 = PREFERS(偏好),客体 = 低风险,再附上两个元信息 —— 一个重要性档位(强表态记 0.9 高,顺带提一句记 0.2 低),一个时间戳(这句话是哪天说的)。注意"低风险"被规范成一个名词性实体,而不是"我偏好低风险"这一整句话 —— 因为名词才好被后续按对象去匹配和遍历。

这条边最终落进关系库 PostgreSQL 的 chat_memory_edges 表(全量事实在这里,是主真相源),同时镜像一份进图库 Apache AGE、再镜像一份进向量库 Milvus。一份数据、三处副本,后面讲为什么。

读:开场画像 + 临场检索

读分两层。第一层是开场画像:下一次对话一开始,persona_populator 会扫这个用户当前还生效的几类边 —— 持仓(HOLDS)、偏好(PREFERS)、回避(AVOIDS)、关注(WATCHES),把它们拼成一段约 500 tokens 的"用户画像",直接塞进上下文窗口。所以模型还没等你开口,就已经"知道"你偏好低风险了。第二层是临场检索:你问了具体问题(比如"帮我看看这只票"),系统再用三路混合检索(archival_memory_search)去捞跟当前问题更相关的细粒度记忆。开场画像管"你是谁"的常驻底色,临场检索管"这次问题"的精准补充。

为什么一份数据要三处镜像

因为同一条事实有三种查法,各有所长:PG 擅长"按用户、按关系类型精确捞全量"(开场画像那几条 SQL 就是),AGE 擅长"顺着关系往下遍历"(比如从用户走到他持仓的股票再走到所属行业),Milvus 擅长"按语义相似找"(你问的词跟存的词不完全一样也能召回)。三库不是重复造轮子,是同一条边在三个角度各放一个副本,各自负责一种查询模式。三库之间怎么保证写一半崩了不脏,是另一道题(见本类第 8 题)。

💻 示例讲解

把"偏好低风险"这条信息,从写到读完整走一遍。下面是教学伪代码,只画逻辑骨架,真实实现里抽取走 LLM、落库分三处事务。

# ===== 写管线:一句口语 -> 一条结构化的边 =====
user_says = "我偏好低风险"

# 1) LLMExtractor 把口语抽成结构化的边(主体-关系-客体 + 元信息)
edge = {
    "rel_type":    "PREFERS",       # 关系类型:偏好(不是看多/持仓)
    "source":      "User",          # 主体固定是用户
    "target":      "低风险",         # 客体抽成名词性实体,不是整句谓词
    "importance":  0.9,             # 强表态 -> 高档(0.9 / 0.5 / 0.2 三选一)
    "valid_from":  "2025-06-20",    # 时间戳 = 说这话那天,不许编造
    "valid_to":    None,            # 还没被推翻,所以"至今有效"
}

# 2) 同一条边落进三处,各自擅长一种查法
pg.insert(edge)             # 关系库:全量事实 + 主真相源
age.create_edge(edge)       # 图库:供"顺关系遍历"
milvus.insert(embed(edge))  # 向量库:供"按语义相似找",1024 维

# ===== 读管线(下一次对话,可能隔了很久) =====
# 3) 开场:扫 4 类还生效的边,拼成 ~500 tokens 画像塞进窗口
persona = persona_populator(user_id)   # 只看 valid_to 为空(仍生效)的边
# persona 里这一行: "### 偏好方法(PREFERS)\n- 低风险"
window = system_prompt + persona + user_new_question

# 4) 遇到具体问题再三路混合检索,捞更细的相关记忆
hits = archival_memory_search(user_new_question)   # 图 / 向量 / 全文 三路融合

推演:假设用户去年说了 1 句"偏好低风险",今年又陆续聊了 200 轮别的。整段塞回方案要把这 200 轮全读进窗口(假设上万 tokens),模型还得自己在噪声里翻出那句话。我的方案:那 1 句被抽成 1 条边存着,今年开场时 persona_populator 只把这条(连同持仓/回避/关注共 4 类、合计约 500 tokens)拼进窗口 —— 模型一眼就看到"该用户 PREFERS 低风险",省掉了上万 tokens 的翻找。写入主路径是 archival_memory_insert 的 8 步 pipeline。

⚖️ 决策对比

维度我们的选择:抽取 + 检索替代方案:整段对话塞回
窗口占用只回填挑出的几条,开场画像约 500 tokens 封顶历史越长占用越大,迟早撑爆窗口
Token 成本常驻成本固定、可控每轮都把全部历史重算一遍,线性烧钱
信噪比喂给模型的是被提炼的关键事实,重点突出关键那句淹在海量寒暄里,模型要自己找
细节保真抽取可能漏抽 / 抽错,有信息损失风险原话全在,零损失
实现复杂度要写抽取、冲突消解、三路检索,工程量大极简,拼字符串即可
可控性事实结构化后能审计、能改、能按关系遍历一坨文本,改不动也查不动

公允裁决:整段塞回真有它的好 —— 实现简单到几乎不用写代码,而且零信息损失,你说过的每个字都还在。在对话很短、或者就想做个玩具 demo 时,它完全够用,硬上抽取管线反而是过度工程。我们仍选抽取 + 检索,是因为这是个会长期陪用户的金融助手:历史会无限增长,而窗口和预算不会。一旦对话攒到几百轮,整段塞回要么爆窗口、要么烧光预算、要么把关键偏好淹没在噪声里。我们用"抽取可能漏 / 检索可能召回不全"这个代价,换"成本可控 + 信噪比高 + 事实可治理"—— 而那个代价正是后面几道题在专门治理的(冲突消解见本类第 5 题、三路融合排序见本类第 6 题)。

  • 写入侧 LLMExtractor 把"我偏好低风险"抽成一条边:用户 —PREFERS→ 低风险,带重要性档位 + 时间戳,落进 PG 并镜像到 AGE 和 Milvus。
  • 读取侧分两层:开场 persona_populator 扫 4 类生效边(HOLDS/PREFERS/AVOIDS/WATCHES)拼约 500 tokens 画像进窗口;临场再三路混合检索捞细节。
  • 一份数据三处镜像各擅长一种查法:PG 精确捞全量、AGE 顺关系遍历、Milvus 语义相似 —— 不是冗余,是同一事实的三个查询角度。
  • 选抽取 + 检索而非整段塞回:用"可能漏抽 / 召回不全"的代价,换成本可控 + 信噪比高 + 事实可治理。

一句话速记:写时把对话提炼成"用户 —PREFERS→ 低风险"这张卡片存进三库,读时开场把卡片拼成画像、临场再检索补细 —— 模型看到的永远是挑出来的少量事实,不是整本聊天记录。

Q3

你为什么用 MemGPT 分层记忆 × Zep 双时态图杂交,而不是单纯照搬其中一个?各取了什么、丢了什么?

★★★★☆
MemGPTZep / Graphiti架构杂交选型权衡双时态图

🎯 考察点分析

这道题面试官不在乎你背没背过 MemGPT 和 Zep 这两个名字,而是想看你能不能把别人的论文拆开,只拿对你场景有用的零件,再说清代价。能背名字的人很多,能讲清"哪块取自谁、为什么不照搬整套、缝合处多付了什么"的人才是做过架构决策的。一个常见的失败回答是"我两个都用了,所以更强"——这是堆料,不是设计。

  • 追问:如果只用纯 MemGPT,你的金融场景具体会在哪个 query 上崩?给个例子。
  • 追问:Zep 默认绑 Neo4j,你换成了 PG + Apache AGE,这个替换不是免费的,你付了什么代价?
  • 追问:"杂交"听起来很美,但缝合层是要维护的。多出来的复杂度最后落在哪几个地方?
  • 追问:除了这两家,你还掺了别的来源吗?为什么不是纯粹的二选一拼装?

📚 原理讲解

先把两套东西讲成大白话。MemGPT(也叫 Letta,2023 年)解决的是"接口"问题:它把记忆当成一块分层的、可读写的存储,然后让 AI 自己拿工具去管它——就像给一个人一个会自动翻页的笔记本,桌面上摊开的那页是工作记忆,翻进去的旧页是归档,人自己决定写哪、查哪。我们直接照搬了它这套交互范式:给 agent 6 个记忆工具(往工作区追加/替换、往归档区写入/检索/沿关系走、回看历史对话),工作区还分了页——人设区 500 token、草稿区 1000 token,写满了自动把旧行翻进归档。

但 MemGPT 原版的归档是一堆扁平文本块——一条条独立的句子,谁也不认识谁。这在我们的场景里是致命的。

金融场景的硬需求:态度会随时间演化

散户对一只股票的看法不是一个静态标签,而是一条时间线:去年重仓茅台 → 三月加仓 → 五月清仓 → 后来又说"我当时记错了,没全卖"。如果归档只是扁平文本,这四句话躺在一起,系统根本不知道哪句作废了、哪句是最新的、哪句是对哪句的更正。你问"他现在还拿茅台吗",检索回来四条互相打架的文本,没法回答。

从 Zep / Graphiti(2025)取后端:双时态知识图谱

所以归档层我们换成了 Zep 那套双时态知识图谱:记忆不是文本块,而是带时间属性的"实体—关系"。"用户—持有→茅台"是一条边,这条边上挂着两组时间:事情真实发生的区间(几月持到几月),和系统知道这件事的时间。这样"卖出"就表现为给旧的"持有"边盖上一个失效时间、再长出一条新边,而不是把旧记忆删掉。历史可回溯、当前可查询,"态度演化"被结构化地表达出来了。(双时态本身是下一道题专讲,这里只说它是我们换后端的理由——见本类第 4 题。)

但我们没照搬 Zep 的存储:PG + Apache AGE,不上 Neo4j

Zep 默认把图存在 Neo4j 里。我们没跟——项目本来就有一套 PostgreSQL 基建(持仓、公告、会话都在上面),再为记忆单独引一个 Neo4j 是额外的运维负担。我们的做法是:PG 表存全量事实数据 + B 树索引(真正干检索/范围查询的活),Apache AGE 这个 PG 扩展只镜像一份图拓扑给 Cypher 多跳遍历用。这样绕开了 AGE 的一个已知短板——它的 agtype 索引能力弱,不适合扛全量查询。代价是图镜像写入只能做成"尽力而为":AGE 不可用时降级成告警,PG 始终是唯一真相源(这块的一致性是第 8 题的主题)。

还掺了第三方风味——所以不是简单二选一

真正落地时还借了两味:写入冲突谁覆盖谁,用的是 mem0 风格的 LLM 当裁判(覆盖/更新/并存,详见第 5 题);每条记忆都挂一个 provenance 证据外键(Anthropic Citations 风格,指回原始对话原文),防止 agent 凭空编。所以最终架构是"MemGPT 接口 + Zep 图后端 + PG/AGE 存储 + mem0 裁判 + Citations 溯源"五味缝合,不是把任何一家整套搬过来。

Q4

什么是双时态(bi-temporal)?为什么记忆系统必须区分"事件发生的时间"和"系统知道这件事的时间"?不区分会出什么问题?

★★★★★
双时态bi-temporal时间建模金融审计数据结构

🎯 考察点分析

这是记忆这一类里最硬的一题。面试官想确认:你做记忆系统时,是把时间当成一个"最后更新于"的简单戳子,还是真把它当成一个建模问题来设计。"双时态"在数据库学界是个有名字、有出处的概念(Snodgrass 1993),不是我临时编的口号。面试官会顺着往下挖:

  • 追问:同样是"这条记忆不再为真了",用户把茅台卖了,和用户说"你记错了我从没买过茅台",在你库里是同一种操作吗?如果不是,差在哪个字段?
  • 追问:如果只用一个时间戳会怎样?具体举一个它答不出来的查询。
  • 追问:为什么金融场景对这个比聊天机器人更敏感?合规、归因到底卡在哪?
  • 追问:代价呢?双时态写起来更麻烦,你凭什么觉得值?

能把"两套时间各管一件事、盖错字段就等于在撒谎"讲清楚,这题就稳了。

📚 原理讲解

先说人话。一条记忆里其实藏着两个完全不同的"时间问题":一个是现实问题——这件事在真实世界里从什么时候开始为真、到什么时候不再为真;另一个是系统问题——我这个系统是从什么时候才录入这条记录的、又是从什么时候把它划掉的。双时态(bi-temporal)的意思就是:这两套时间各记各的,谁也不替谁说话。

四个时间字段,两套各管两头

具体到我们存关系的边表(chat_memory_edges),每条边落了 4 个时间字段,正好两套、每套一头一尾:

  • 真实世界这一套:valid_from / valid_to——这件事在现实里何时开始为真、何时停止为真。比如"用户持有茅台"这条事实,从 5 月 1 日成立,到 6 月 10 日卖出截止。
  • 系统记录这一套:recorded_at / invalidated_at——系统何时把这条录进库(默认就是录入那一刻 now())、何时把它作废。
关键全在"两种不再为真"的区分

一条旧记忆"不再为真",现实里有两种截然不同的原因,而双时态用两个不同的字段把它们分开:

第一种:现实演化了。用户真的把茅台卖了。注意——他过去确实持有过,这段历史是真实发生的、不该被抹掉。所以我们做的是给旧边盖上 valid_to = 新事实的 valid_from(这件事的现实有效期到此为止),再插一条新边接上。旧记录原封不动地留在历史里,它只是"过期"了,不是"错"了。这对应冲突动作里的 UPDATE_VALIDITY。

第二种:系统当初记错了。用户澄清"我从来没买过茅台,你记错了"。这时旧记录是错误信息,现实里它从一开始就不该为真。我们做的是给旧边盖 invalidated_at = now()(系统在此刻意识到这条作废了),但绝不动 valid_to——因为现实里它根本没有一个"曾经为真的有效期"可言。这对应 CONTRADICT_EXISTING。

一句话:横轴(现实)管"事实变没变",纵轴(系统)管"我记错没记错"。盖错字段,就等于在向未来的查询撒一个谎。

为什么这正是金融场景的命门

双时态最值钱的地方,是它能回答一类"时间旅行"查询:"系统在 5 月 1 日那天,以为这个用户持有什么?" 这种问题在合规、复盘、归因里天天要问。监管要追责时问的是"你当时基于什么信息给的建议",而不是"你现在知道什么"。只有同时留着两套时间,你才能把时钟拨回 5 月 1 日,看到系统当时的认知快照。而且,把"曾经真实但已过期"和"压根就是错的"分开,正是合规与归因的分水岭——前者是正常的历史,后者是要被标记、被排除、甚至要留证据说明"我们错了并已纠正"的事故。混在一起,这两件事就再也分不开了。

💻 示例讲解

下面这段教学伪代码,演示同一条旧记忆碰到两种"不再为真"时,系统分别动哪个字段。注意两个分支只差一行,但语义天差地别。

# 库里已有一条旧边:用户 --持有--> 茅台
old_edge = {
    "rel": "持有", "target": "茅台",
    "valid_from": "2026-05-01", "valid_to": None,        # 现实里:从 5/1 起为真,还没截止
    "recorded_at": "2026-05-01", "invalidated_at": None, # 系统里:5/1 录入,未作废
}

def apply(old, new_fact_date, reason):
    if reason == "现实演化":
        # 用户真把茅台卖了 —— 旧事实是"过期",不是"错"
        # 只盖横轴:现实有效期到新事实开始那天截止;纵轴一个字不动
        old["valid_to"] = new_fact_date          # 5/1 持有 < valid_to < 6/10 卖出
        # old["invalidated_at"] 保持 None —— 这条记录依然是"真实发生过的历史"
        insert_new_edge(rel="卖出", valid_from=new_fact_date)  # 新边接续

    elif reason == "系统记错":
        # 用户澄清"我从没买过茅台" —— 旧记录是错误信息
        # 只盖纵轴:系统此刻把它作废;横轴 valid_to 绝不动
        old["invalidated_at"] = now()            # 系统在"此刻"意识到记错了
        # old["valid_to"] 保持 None —— 现实里它根本没有"曾为真的有效期"
        insert_new_edge(rel="未持有", valid_from=new_fact_date)

推演:假设两种情况都发生在 6 月 10 日。现实演化分支后,旧边变成 valid_from=5/1, valid_to=6/10, invalidated_at=None——它告诉未来的查询"用户在 5/1 到 6/10 之间确实持有过茅台";系统记错分支后,旧边变成 valid_from=5/1, valid_to=None, invalidated_at=6/10——它告诉查询"这条是 6/10 被作废的错误记录,别采信,但保留它好让审计看到我们纠过错"。现在把时钟拨回 5 月 7 日做审计:第一种情况里系统当时合理地以为用户持有茅台(因为那时事实确实成立),第二种情况里系统当时错误地以为持有(那条记录还没被作废,但其实从头就是错的)。只有 4 个字段都在,这两种"5/7 的认知"才区分得开。

公允裁决:单时间戳绝不是稻草人——它真的更简单、写入更快,对一个"只要记住用户口味、记错了改掉就行"的休闲聊天助手,它完全够用,多两套时间反而是过度设计。它输的只在一个点上:一个戳子没法同时回答"现实里何时为真"和"系统何时知道"这两个问题,而这两个问题在金融场景里恰恰都得回答。我们选双时态,是因为这个项目的查询里真有"系统在某天以为用户持有什么""这条是过期还是当初就错"这类需求;为此我们认下两笔代价:写入逻辑要按冲突类型分叉(填 valid_to 还是 invalidated_at),存储和查询都更重。换个不碰合规的产品,我会毫不犹豫地用单时间戳。

📌 总结

  • 双时态 = 一条记忆同记两套时间:真实世界(valid_from / valid_to,这件事现实里何时为真)和系统记录(recorded_at / invalidated_at,系统何时录入 / 何时作废),共 4 个字段。
  • 关键在区分两种"不再为真":现实演化(用户真卖了)只盖横轴 valid_to,旧记录仍是真历史;系统记错(用户澄清)只盖纵轴 invalidated_at,横轴一字不动。盖错字段=对未来的查询撒谎。
  • 不区分(单时间戳)就答不出"系统在某天以为用户持有什么"这类时间旅行查询,也分不开"错误记录"和"曾真实但已过期"——金融合规与归因正卡在这里。
  • 每次变化是新增一条边 + 标两套时间,而非就地覆盖,所以用户对某只股票态度的演化链可完整追溯。
  • 代价是写入要按冲突类型分叉填 valid_to 或 invalidated_at(见本类第 5 题),存储查询都更重;不碰合规的产品用单时间戳更划算。

一句话速记:横轴管"事实变没变",纵轴管"我记错没记错",两套时间各留各的,才能把时钟拨回过去看清系统当时的认知。

Q5

你的记忆写入是 8 步 pipeline + 4 种冲突动作:当一条新记忆和旧记忆矛盾时,系统怎么决定覆盖、更新、还是并存?

★★★★☆
写入管线冲突消解LLM 当裁判兜底设计幂等

🎯 考察点分析

这道题表面问"流程怎么走",真正想看的是:你有没有意识到"矛盾"其实有好几种,而且每种该用完全不同的处理方式。一个只会 UPDATE 覆盖旧值的人,和一个能讲清"卖了股票"和"系统记错了"是两码事的人,设计水平差一个档次。面试官在探这几件事:

  • 追问:"用户去年说看好某只股票,今天说不看好了"——这是覆盖旧记录,还是新增一条?为什么?这两种处理在审计上有什么差别?
  • 追问:判断该覆盖还是并存,你是写规则(if-else)还是交给大模型?各自的代价是什么?
  • 追问:大模型这次抽风,返回了一个你枚举里没有的动作,或者干脆超时了,整条聊天会崩吗?你怎么兜?
  • 追问:同一句话被系统重复处理两次(比如重试),会不会存进去两条一模一样的记忆?怎么防?

📚 原理讲解

先把"写一条记忆"这件事拆开。它不是简单的"INSERT 一行",而是一条 8 步流水线。一句对话进来后大致是:① 先把这一轮原始对话存成"事件原文"(我们叫 episode,留底用);② 从里面抽出/规整实体(谁、跟谁、什么关系);③ 去库里捞出"同一组关系当前还生效的旧记录",最多取 5 条来比对;④ 让大模型当裁判,判这条新记忆和旧记录是什么关系;⑤ 按裁判结果落库;⑥ 把这条边镜像到图数据库和向量库;⑦/⑧ 标记这条对话"已经抽取过了"。这道题的灵魂在第 ④⑤ 两步——冲突消解。

为什么"矛盾"不能一律覆盖

想象用户两句话:去年"我买了 A 股票",今年"我把 A 卖了"。如果你简单地把"持有"覆盖成"清仓",那"他曾经持有过"这段历史就被抹掉了。可在投资场景里,这段历史恰恰是有价值的——复盘、审计、解释"系统当时为什么给你推 A"都要靠它。所以关键洞察是:"卖了"不是"我记错了",它是现实本身变了。这两种"矛盾"在数据上必须分开记。

四种冲突动作(枚举固定四个)

我们让大模型把每次矛盾归到四类之一,落库的 SQL 各不相同:

  • 更新有效期(update_validity)——现实演化了。"买了→卖了"属于这类。做法:把旧记录的"有效期截止时间"(valid_to)填成新记录的生效时间,然后插入一条新记录。旧的没删,只是被标成"这段时间之前有效"。
  • 作废纠错(contradict_existing)——系统当初记错了。用户澄清"我从没买过 A,你搞错了"属于这类。做法:把旧记录的"作废时间"(invalidated_at)填成现在,再插一条新记录。注意它动的是另一个字段——表示"这条记录从来就不该存在",而不是"它曾经对过"。
  • 独立并存(append_new)——根本不矛盾。"看好 A"和"看好 B"是两回事,直接插新记录,旧的一动不动。
  • 完全重复(no_op)——啥也别写。同一句话又说了一遍,跳过,不制造冗余。

这里有个贯穿全局的设计:三种要写的动作,最后都是"新增一条边",而不是就地改写旧边。旧边永远留在库里,只是被打上"有效期到此为止"或"已作废"的标记。这样整条记忆的演化链就完整保存下来了——这正是配合双时态设计的地方(双时态本身见本类第 4 题,这里只用到它的两个字段)。

为什么裁判用大模型,而不是写 if-else

"区分'卖了'和'记错了'"本质是个语义理解题,规则很难穷举——同样一句"我不看好 A 了",可能是观点变了(更新有效期),也可能是在纠正你之前的误记(作废)。这种细微差别正是大模型擅长、规则不擅长的。代价是每次写入多一次大模型调用,以及落库 SQL 变复杂。

兜底:大模型靠不住时,保守新增

大模型会失败:调用超时、返回的 JSON 解析不出、或者返回一个枚举里没有的动作名。我们的处理是一律退回到"独立并存(append_new)",而不是抛异常打断用户聊天。理由是"保守、不丢信息":并存最多让库里多一条冗余,后续还能靠审计和校正修;但如果因为裁判失灵就把整轮对话搞崩,体验代价大得多。这叫 fail-safe(失败时倒向安全的一侧)。

防重复:一把幂等锁

同一句对话如果被系统重复处理(重试、并发),会不会存进两条一样的记忆?靠数据库一个 5 列联合唯一约束挡:(对话原文ID + 起点 + 终点 + 关系类型 + 生效时间) 必须唯一。同一段对话、同一组关系、同一个生效时间,数据库层面就不允许出现第二条。这让整条写入是幂等的——跑一次和跑两次,结果一样。

公允裁决:直接覆盖绝不是个蠢方案——它实现最简、延迟最低、零大模型成本,对"只要最新值、不在乎历史"的场景(比如一个临时的用户偏好开关)完全够用,工程上反而更稳。它真正的短板只在我们这个特定场景里才致命:投资助手要对"系统当时为什么这么建议"负责,历史和"演化 vs 纠错"的区分是刚需,而覆盖写把这些能力一次性抹平了。所以我们愿意为它付出"每次写入多一跳大模型 + 双时态 SQL 复杂度"的代价,并专门配了 fail-safe 新增来兜大模型失灵——本质是拿工程复杂度换"可审计、可演化"。如果哪天发现绝大多数关系根本不需要历史,把直接覆盖作为快路径、只对关键关系走四动作,会是更省的折中。

📌 总结

  • "矛盾"不止一种:"卖了"是现实演化、"记错了"是系统纠错、"两回事"是独立并存、"又说一遍"是完全重复——四种各有不同处理,这是整道题的核心洞察。
  • 四种动作落到 SQL:更新有效期动 valid_to、作废纠错动 invalidated_at(两个字段语义严格分开)、独立并存只插新边、完全重复啥也不写。
  • 三种要写的动作都靠新增边、从不就地删改旧边,所以记忆的整条演化链永久保留,可复盘可审计——这是它比"直接覆盖"强的根本。
  • 裁判交给大模型(语义题规则难穷举),但配 fail-safe:失败/返回非法一律退回"保守新增",不丢信息也不打断聊天。
  • 一把 5 列联合唯一约束保幂等,同段对话同组关系不会被重复抽成两条。

一句话速记:大模型判这条新记忆是"演化/记错/无关/重复"四选一,前三种都新增边留住历史、绝不就地覆盖,大模型失灵就保守追加兜底。

Q6

读取侧你用了图 / 向量 / 全文三路混合检索 + RRF v2 时间感知排序:三路怎么融合成一个排序?为什么排序要"感知时间"?

★★★★☆
混合检索RRF时间感知排序向量/图/全文名次倒数融合

🎯 考察点分析

面试官在探的是:你懂不懂"召回靠多路、排序靠融合"这套现代检索的标准打法,而不是无脑堆一个向量库就完事。三路检索各有盲区——全文查得到精确词但不懂语义,向量懂语义但漏精确词,图能顺关系链但要先知道从哪个点出发。能把它们融成一个排序,而且融合时还考虑了"记忆会过期"这个领域特性,才算把这道题答到点子上。

  • 追问:三路的原始打分量纲都不一样(全文是 BM25 分,向量是余弦距离),你怎么把它们放在一起比?
  • 追问:RRF 公式里那个常数 k=60 是干嘛的?调大调小会怎样?
  • 追问:为什么时间衰减要"分级"?给持仓和给一句临时观点用同一个衰减速度不行吗?
  • 追问:衰减为什么不一路降到零?降到零有什么坏处?

📚 原理讲解

先说召回。一条记忆(比如"用户持有贵州茅台")在三个地方各有一份索引:全文走 PostgreSQL 的倒排索引,中文先用 jieba 切词再做 BM25 打分,擅长精确命中——股票代码、专有名词;向量走 Milvus,用 qwen v3 把句子压成 1024 维向量做语义相似,擅长"换了个说法也能找到";图走 AGE 的 Cypher 多跳遍历,擅长顺着关系链走(从"用户"走到"持仓"再走到"这只股票所在行业")。图这一路比较重,需要先确定从哪个节点出发,所以默认搜索不带它,只有专门的遍历工具触发时才走。

三路怎么合成一个排序:RRF 只看名次

关键难点是:三路吐出来的分数压根不能直接比。BM25 分可能是几点几,向量距离是 0 到 1 之间,数量级、方向、分布全不一样。硬要加权相加,就得先做"量纲对齐"(归一化),而归一化本身又很脆——一条噪声极值就能把整列分数压扁。

RRF(Reciprocal Rank Fusion,名次倒数融合)的聪明之处是:我不看你的原始分,只看你排第几名。每一路把自己的结果排好序后,某条记忆排第 1 名就贡献 1/(k+1),排第 2 名贡献 1/(k+2),以此类推。一条记忆在三路里的"名次倒数"全加起来,就是它的基础分。这样三路天然就站在同一把尺子上了,根本不用对齐量纲。常数 k(这里取 60,是业界经典默认值)起"压平头部"的作用:k 越大,第 1 名和第 2 名的差距越小,融合越温和,对单路把某条偶然排到第一这种噪声更稳。

为什么还要"感知时间":记忆有保质期

光按名次融合还不够。市场知识可以是"客观对错",但用户记忆是"会过期的事实"。一年前说"我看好新能源",今天还按原样顶上来,既不准也烦人。所以基础分之外再乘两个权重:

第一个是重要性权重,把抽取时打的重要性分映射成三档(0.9→0.95、0.5→0.75、0.2→0.6)。注意低重要性映射到 0.6 而不是 0,故意不把它压死,保住长尾。

第二个是时间衰减:time_decay = 0.5 + 0.5 × exp(−Δt/τ)。Δt 是这条记忆"上次为真"到现在隔了多少天,越旧值越小。这里有两个领域设计:其一,τ(衰减时间尺度)按关系类型分级——持仓(HOLDS/SOLD)给 365 天,偏好(PREFERS/AVOIDS/WATCHES)给 180 天,观点(EXPRESSED_VIEW/STUDIED)给 90 天。背后的常识是"持仓比一句临时观点更耐放":你买了的股票半年后大概率还拿着,但你三个月前随口说的一句看法,早就不一定算数了。其二,衰减不归零,设了 0.5 的地板——再老的事实最多降到一半权重也不会消失,保住长尾召回和审计价值(谁说过什么仍查得到)。还有个细节:已经"作废过"的历史边,用它的失效时间(valid_to)而不是起始时间当衰减锚点,因为"最近一次为真的时间"才是更准的新鲜度参考。

💻 示例讲解

下面这段伪代码把"三路名次倒数 → 乘重要性 → 乘时间衰减 → 取前 5"的逻辑走一遍,省掉数据库和向量库的细节,只看排序怎么算出来。

    for rank, edge in enumerate(one_path, start=1):  # rank 从 1 开始
        base[edge.id] += 1.0 / (K + rank)            # 排得越靠前,加得越多

# 第 2 步:每条记忆再乘两个权重 —— 重要性 × 时间衰减
final = {}
for edge_id, base_score in base.items():
    meta = edges_meta[edge_id]                       # 关系类型/重要性/时间

    # 重要性映射成三档,低档故意保到 0.6 不压死,留长尾
    imp = {0.9: 0.95, 0.5: 0.75, 0.2: 0.6}.get(meta.importance, 0.75)

    # 时间衰减:越旧越小,但有 0.5 地板不归零
    # τ 按关系类型分级:持仓最耐放,观点最快过期
    tau = {"HOLDS": 365, "PREFERS": 180, "EXPRESSED_VIEW": 90}.get(
        meta.rel_type, 180)
    # 已作废的历史事实,用"上次为真的时间"当锚点更准
    ref = meta.valid_to or meta.valid_from
    days = (now - ref).days
    decay = 0.5 + 0.5 * exp(-days / tau)             # 落在 [0.5, 1.0]

    final[edge_id] = base_score * imp * decay        # 三者相乘 = 最终分

top5 = sorted(final, key=final.get, reverse=True)[:5]

推演:看记忆 a 和 b。a 在全文里排第 1(1/61≈0.0164)、在向量里排第 3(1/63≈0.0159),基础分≈0.0323;b 在向量排第 1、全文排第 2,基础分≈0.0327,两者几乎打平。现在引入时间:假设 a 是一条"持仓"(τ=365),60 天前的,decay=0.5+0.5×exp(−60/365)≈0.924;b 是一条"观点"(τ=90),同样 60 天前,decay=0.5+0.5×exp(−60/90)≈0.756。再设两者重要性都是 0.9(权重 0.95)。最终 a≈0.0323×0.95×0.924≈0.0284,b≈0.0327×0.95×0.756≈0.0235。结论:名次上几乎平手的两条,因为"持仓比观点耐放",老持仓 a 反超临时观点 b 排到前面——这正是"感知时间"想要的效果。

Q7

一句话进来,你怎么判断该查"用户的个人记忆"还是"市场知识库"?路由判错了怎么兜底?

★★★★☆
检索路由触发词分类LLM 兜底记忆 vs 知识库瀑布式决策

🎯 考察点分析

这道题表面问"怎么分流",其实面试官想看你有没有在"准确率"和"成本/延迟"之间做过真实权衡。一个助手收到"帮我看看我的持仓"和"最近半导体行业的研报怎么说",这两句话该去的地方完全不同:前者要翻用户自己的个人记忆(持仓、偏好、说过的话),后者要查公开的市场知识库(研报、财报、政策、新闻)。最省事的做法是两边都查,但那样每句话都要多打一次检索,贵且慢。所以面试官想确认你是不是用便宜的手段解决了大多数情况、只把难的留给贵的手段。

  • 追问:那"基于我的持仓推荐几只股票"这种又要个人记忆、又要市场数据的混合句,你怎么处理?(考你有没有 both 这一类)
  • 追问:规则匹配判错了、或者句子模棱两可,系统会怎样?会不会就直接答错?(考兜底设计)
  • 追问:两路结果都拿回来后,怎么防止模型把"用户的个人偏好"当成"市场客观事实"来对冲?(考结果回填的纪律)
  • 追问:为什么默认兜底是查记忆而不是查知识库?这个默认方向是拍脑袋还是有依据?

📚 原理讲解

核心是一个三层瀑布式路由:一句话进来,先用最便宜的手段试着判断,判不了再往下交给更贵的手段,最后还判不了就走一个安全的默认值。这三层在代码里就是一个函数 decide_retrieval_targets,它的输出永远是三选一:['memory'](只查个人记忆)、['kb'](只查市场知识库)、或 ['both'](两边都查)。

第一层:规则触发词(零延迟、零 LLM 成本)

大多数句子其实一眼就能定向。系统维护三份小清单:记忆类触发词 13 个(我 / 我的 / 上次 / 之前 / 持仓 / 偏好 / 看好 / 看空 / 态度…),知识库类触发词 11 个(研报 / 财报 / 公告 / 政策 / 市场 / 板块 / 新闻 / 宏观…),还有 both 类正则 6 条(像"基于我.*推荐""结合我.*""根据我.*分析")。这一层是纯字符串/正则匹配,不调任何模型,所以零成本零延迟。它的判断优先级很关键:

  • both 正则最高——因为"基于我的持仓推荐"里既有"我"(记忆词)又是混合意图,必须先被 both 正则抓走,否则"我"会把它误判成纯记忆;
  • 其次是双类命中——一句话里同时出现记忆词和知识库词(比如"我的消费板块偏好"里"偏好"是记忆词、"板块"是知识库词),判 both;
  • 再次是单类命中——只命中一类就走那一类;
  • 都没命中就返回空,把球踢给第二层。
第二层:LLM 兜底(只处理边界句)

规则没命中的,往往是没有明显关键词、但语义上有倾向的边界句。这时才调一次小模型(LLMRouterFallback),让它用受约束的 JSON 格式直接吐出 retrieval_targets 三选一加一句理由。这是典型的"precision 高的规则先行、贵的 LLM 兜边界"瀑布设计——不让 LLM 沾大多数句子,只让它干规则干不了的脏活。

第三层:默认兜底 = 查记忆

三种情况会落到最底层默认值:LLM 调用报错、LLM 输出的 JSON 解析/校验失败、或者规则没命中且根本没配 LLM。这三种一律返回 ['memory']。为什么默认偏记忆而不是知识库?因为这是个"个人化助手",绝大多数对话都围绕用户自己的上下文展开,判不准时偏向用户自己的持仓/偏好,比偏向一堆无关研报要安全得多。

结果回填:两段贴标签,防混淆

路由只决定"查哪里",查回来的结果还要正确地塞进给模型的提示词。两路结果会被显式切成 [用户上下文] 和 [市场知识] 两段,各贴标签,并附一句 disclaimer:个人偏好只是背景、不是投资结论,公开信息客观、和偏好相互独立——"用户偏好白马股 + 该股近期跑输大盘"是个 trade-off,不是矛盾。没有这个区隔,模型很容易把"用户喜欢白马"当成"市场事实",硬去对冲掉真实行情。(路由→检索这一步怎么把多路结果排成一个序,见本类第 6 题。)

💻 示例讲解

下面是三层瀑布的教学伪代码,只保留逻辑骨架。注意三层是"短路"的——上一层能定就不进下一层。

# 三份触发词清单(数量锁死:记忆13 / 知识库11 / both正则6)
MEMORY_WORDS = ["我", "我的", "上次", "持仓", "偏好", "看好", "看空", ...]   # 13 个
KB_WORDS     = ["研报", "财报", "公告", "政策", "市场", "板块", ...]          # 11 个
BOTH_PATTERNS = [r"基于我.*推荐", r"结合我.*", r"根据我.*分析", ...]          # 6 条正则

def rule_match(query):
    # 第一层:纯字符串/正则,零 LLM 成本
    # 优先级 1:both 正则最高 —— 防"我"这个记忆词把混合句遮蔽成纯记忆
    if any(re.search(p, query) for p in BOTH_PATTERNS):
        return ["both"]
    hit_mem = any(w in query for w in MEMORY_WORDS)
    hit_kb  = any(w in query for w in KB_WORDS)
    # 优先级 2:两类都命中 → 混合意图
    if hit_mem and hit_kb:
        return ["both"]
    # 优先级 3:只命中一类 → 走那一类
    if hit_mem:
        return ["memory"]
    if hit_kb:
        return ["kb"]
    return None          # 都没命中:把球交给下一层

async def decide_retrieval_targets(query, llm_fallback):
    decided = rule_match(query)
    if decided is not None:        # 第一层定了就短路返回,不碰 LLM
        return decided
    if llm_fallback is not None:   # 第二层:只有边界句才花这一次模型调用
        return await llm_fallback.decide(query)   # 内部:报错/解析失败 → ['memory']
    # 第三层:连 LLM 都没有 → 安全默认值
    return ["memory"]              # 个人化助手,判不准时偏向用户自己的上下文

推演:拿四句话走一遍——
① "我上次说的那只票现在怎么样"→ 命中记忆词"我/上次",第一层直接出 ['memory'],零模型调用;
② "最近有什么半导体行业的研报"→ 命中知识库词"研报",出 ['kb'];
③ "基于我的持仓推荐几只低估值的"→ both 正则"基于我.*推荐"先抓,出 ['both'](若没这条正则,"我"会把它误判成纯记忆);
④ "帮我捋一下思路"→ 三份清单都不命中,落到第二层 LLM 判,假如这次 LLM 返回的 JSON 解析失败,就兜底成 ['memory']。这样四句话里有三句零成本搞定,只有第四句花了一次模型调用,这就是瀑布省钱的地方。整套路由准确率目标是 ≥ 0.85(50 条 golden case 衡量)。

⚖️ 决策对比

维度我们的选择:触发词分类 + LLM 兜底替代方案:不分流,每句两边都查
实现复杂度要维护三份触发词清单 + 优先级 + LLM 兜底,代码更多最省心,不用判断、不会漏,几乎没有路由逻辑

公允裁决:"全查"绝不是稻草人,它实现最简单、永远不会因为路由判错而漏查,在检索量小、单次检索很便宜的系统里是完全合理的默认。它真正的代价不在"对不对",而在每句话都付双倍的检索成本和延迟,还把无关那一路的噪声塞进提示词——这在一个把检索结果直接拼进上下文的 chat 系统里会持续稀释信噪比。我们之所以仍选分流,是因为这个产品里常见问句的方向其实很好认(出现"我/持仓/偏好"几乎必是记忆,出现"研报/政策/板块"几乎必是知识库),用一层零成本的规则就能把大多数句子一眼定向,把贵的 LLM 只留给真正模糊的边界句。代价是要维护清单、判错有风险——所以我们没有裸奔,而是配了"默认偏记忆 + 提示词显式区隔"这套双保险:判错方向时偏向用户自己的上下文最安全,回填时贴标签让模型不会把个人偏好误当市场事实。本质上是用"可控的判错风险 + 一点维护成本"换"翻倍的成本延迟 + 噪声"。

Q8

记忆同时落在图数据库、向量库、关系库三个地方,写到一半崩了怎么保证不脏?一致性怎么做?

★★★★★
三方一致性事务原子性发件箱模式周期对账幂等去重

🎯 考察点分析

这道题在探:你把一份数据拆到三个互不知情的存储里之后,有没有真正想清楚"半路崩溃"会留下什么烂摊子。很多人答得出"用事务",但三个库不是一个事务能管的——关系库有事务、图库勉强能搭、向量库根本不进事务。面试官想看你怎么分层:哪些必须强一致、哪些可以"先欠着稍后补",以及补的时候怎么不补出重复、补漏的怎么被发现。

  • 追问:为什么不干脆把三个写操作都塞进一个分布式事务(2PC)?代价是什么?
  • 追问:向量库写失败你"吞掉异常不回滚",那这条记忆岂不是查不到了?最终怎么补回来?
  • 追问:对账作业重放时,同一条边被插了两次怎么办?靠什么保证幂等?
  • 追问:你说图库和关系库同事务,可万一生产环境根本装不上图库扩展呢?你的契约怎么改?

📚 原理讲解

先说清楚为什么是三个库。同一条记忆(比如"用户去年把某只股票清仓了")要被三种方式查到:关系库存全量事实、当主真相源;图库存它的拓扑关系(用户—持有—某股票,便于做多跳遍历);向量库存它的语义向量(便于用"模糊语义"召回)。三种查法各有长板,所以一份数据落三处。坏处就是:写到第二步崩了,三处会对不上——脏数据。

核心思路:按"能不能等"把三处分成两档

关键判断是:哪些必须当场一起成功、哪些可以晚一点补上。我们把关系库和图库划为"必须当场一起对"——因为图拓扑是真相源的一部分,边的数据和边的拓扑不能一个有一个没有。向量库划为"可以晚点补"——向量只是为了语义检索,晚几分钟补上,顶多是这几分钟里这条记忆模糊搜不到,但事实本身一点没丢,因为关系库里它是完整的。

第一档:关系库 + 图库,捆进同一个事务

关系库的 INSERT(写这条边的事实)和图库的建边命令,放进同一把"锁"里——要么一起提交,要么一起回滚。如果图库那条命令失败了,整个事务回滚,这条记忆当作没写过,交给上层重试。这样关系库和图库永远不会出现"一个有一个没有"。这里有个铁律:关系库是唯一真相源,图库是它的镜像。

第二档:向量库走"发件箱"(outbox),做最终一致

向量库故意不进上面那个事务。我们先内联试着写一次向量;一旦失败(嵌入服务挂了 / 向量库连不上),我们不抛异常、绝不回滚关系库,而是把"这条边待补向量"记成一行,塞进一张叫 pending_milvus_inserts 的发件箱表里,然后让主事务正常提交。这就是发件箱模式:把"待办的副作用"和主数据写在同一个数据库事务里持久化下来,保证主数据成功的同时"待办"一定不丢,稍后由后台慢慢兑现。

崩溃恢复:周期对账 + 幂等键兜底

光记下待办还不够,得有人去兑现、还得有人去发现"该写却没写"的漂移态。这就是对账(reconciliation)作业,它周期跑两件事:一是扫发件箱表,逐条重试"嵌入+写向量",成功就删行、失败就把重试次数加一、超过 3 次就告警留人工排查;二是反向扫描,找出"关系库写完了但向量还挂在发件箱 / 一段对话标记说抽过了但其实没抽完"这类不一致,修回去。

最后一道保险是幂等:对账重放、上层重试,都可能让同一条边被写第二次。我们靠一个由 5 个字段组成的唯一键(来源对话、来源节点、目标节点、关系类型、生效时间)来防重——同一条边再插也只会撞唯一约束被挡掉,不会插出重复。

💻 示例讲解

下面这段伪代码把"主事务强一致 + 向量库发件箱兜底"这一拍画出来。注意看异常处理:图库失败让整事务崩;向量库失败只是默默记一笔发件箱,绝不影响关系库提交。

# 写入一条记忆边:主事务把"关系库 + 图库"捆死,向量库走发件箱
def write_memory_edge(edge):
    txn = pg.begin()                       # 开一个关系库事务
    try:
        pg.insert("chat_memory_edges", edge)   # 第1档:写事实(主真相源)
        age_create_edge(txn, edge)             # 第1档:同事务建图边
        # 走到这里:关系库 + 图库 在同一把锁里,要么都成、要么都回滚

        # 第2档:向量库内联试一次,但它"不进上面这把锁"
        ok = try_milvus_insert(txn, edge)      # 嵌入 + 写向量
        if not ok:
            # 失败了:不抛、不回滚!只把"待补向量"写进发件箱表
            # 这一行 INSERT 跟上面的事实写在同一个事务里,所以绝不会丢
            enqueue_milvus_insert(txn, edge)   # 写 pending_milvus_inserts

        txn.commit()                       # 关系库 + 图库 + 发件箱 一起落地
    except AgeCypherError:                  # 图库建边失败 = 真相源不完整
        txn.rollback()                     # 整事务回滚,这条边当没写过
        raise                              # 交给上层重试

# 后台对账作业:周期扫发件箱,把欠的向量补上(幂等键防重复)
def reconcile_pending_milvus():
    rows = pg.select("pending_milvus_inserts", order_by="created_at", limit=200)
    for row in rows:
        if row.retry_count >= 3:           # 试满 3 次还不行
            alert("max_reconcile_retries_exceeded")  # 告警,留行做人工排查
            continue
        try:
            vec = embed(row.edge_text)      # 重新嵌入
            milvus_insert(vec, row.edge_id) # 重新写向量(唯一键挡住重复)
            pg.delete(row)                  # 补上了,删掉发件箱行
        except Exception as e:
            row.retry_count += 1            # 这轮又挂,计数+1 下轮再试

推演:假设写到"向量库这一步"机器断电。关系库的事实 + 图库的边已经在同一事务里提交了(主真相源完整),发件箱里也留了一行"待补向量"。机器重启后,对账作业每轮最多捞 200 行,捞到这条、重新嵌入、写向量、删行——补齐。整个过程里这条记忆从没脏过:期间它在关系库完整可查、在图库能遍历,只是"模糊语义搜"短暂搜不到。若对账连试 3 次都失败(比如向量库长时间宕),第 4 次不再盲试,直接告警让人介入。这套"主事务 + 发件箱 + 周期对账 + 幂等键"被 4 个混沌测试场景覆盖(向量库发件箱、进程重启、重复抽取、空操作回滚)。

⚖️ 决策对比

维度我们的选择(三库分工 + 发件箱/对账)替代方案(全放一个库)
一致性难度关系库+图库强一致、向量库最终一致,要写对账天然原子,单库事务自带,不操心一致性
查询能力图遍历 + 语义向量 + 全文,三种长板都拿到只有这一个库擅长的那种查法,另两种要么没要么很弱
崩溃半写主真相源永不半写;向量短暂滞后,对账补齐不存在跨库半写问题(根本没跨库)
去重5 列幂等唯一键,重放/重试不出重复单事务天然不会重复写
工程成本多出对账作业 + 容错矩阵 + 混沌测试,运维更重几乎零额外一致性代码
真实环境韧性图库装不上也能降级(图边 best-effort,关系库兜底)单点:这个库不擅长的查询直接没法做

公允裁决:单库方案真的更省心——一个事务就把原子性给了你,没有发件箱、没有对账、没有混沌测试这一堆活。如果记忆只需要一种查法,我会毫不犹豫选单库。但记忆系统恰恰要三种查法同时在线:图遍历找关系、向量找语义、全文兜底,没有任何单一存储能把这三件事都做好。所以我们用三库分工换查询能力,代价是把跨库一致性这块硬骨头自己啃下来——并且把代价压到最小:只让真正必须强一致的关系库+图库共事务,向量库这种"晚补无伤大雅"的退到最终一致,再用幂等键堵住重放。这个取舍在真实环境还被验证过一次:生产库装不上图库扩展、图镜像从未真正跑起来,于是契约直接改成"关系库是唯一真相源、图边降级为尽力而为"——三库分工的好处之一,正是它本来就能优雅降级,而不是整个系统瘫掉。

📌 总结

  • 分层是核心:关系库+图库属"必须当场一起对",捆进同一事务、败则整体回滚;向量库属"可以晚点补",退到最终一致。关系库是唯一真相源。
  • 向量库走发件箱模式:写失败不抛不回滚,只把"待补"记进 pending 表(跟主数据同事务持久化),保证主数据成功的同时待办绝不丢。
  • 崩溃恢复靠周期对账:扫发件箱重试补向量(成功删行/失败重试+1/超 3 次告警,每轮 ≤200 行),外加反向扫描"该写没写"的漂移态修回去。
  • 幂等唯一键(5 列)是最后一道保险:对账重放、上层重试都不会插出重复边。整套被 4 个混沌测试场景守护。
  • 真实环境会打脸:生产装不上图库扩展、图边曾毒死整事务——三库分工的好处之一就是能优雅降级,契约顺势改成"图边尽力而为、关系库兜底"。

一句话速记:必须强一致的(关系库+图库)捆一个事务,能晚补的(向量库)走发件箱+周期对账,幂等键防重放——半写永远脏不到真相源。冲突合并细节见本类第 5 题,读取检索见本类第 6 题。
