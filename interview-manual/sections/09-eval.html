09Agent 评估方法论

这一板块讲一件容易被低估的事:给一个会对话、会调工具的 AI 助手「打分」,远比给传统软件写单元测试难——因为它的输出不唯一、过程会绕路、还会一本正经地编数字。这里从「为什么评估难」讲起,一路深入到作者在 AlphaScout 上亲手搭的几套评估机器:四个互不重叠的评判角度、自动出金融计算题再自动判分的「反向出题机」、用大模型当裁判时怎么防它抽风、尽调报告的多指标拆解实验,以及记忆系统「跑一次就抓出五个隐藏 bug」的双层断言体系。每道题都尽量从直觉和类比讲清楚,再落到真实代码与跑出来的数字。

Q1

先打个基础:一个对话 / 工具型 AI agent,为什么「评估」比传统软件测试难?不能写几个单元测试断言就完事吗?

★★☆☆☆
Agent 评估评估方法论非确定性回答质量入门基础

🎯 考察点分析

这是一道开场摸底题。面试官不是想难住你,而是想确认你有没有真正给 AI agent 做过评估——还是只在 PPT 上写过「我们做了充分测试」。一个没踩过坑的人,会下意识地把 agent 当成普通函数,觉得「输入一句话、对一下输出字符串」就完事;真做过的人,第一反应是「输出根本对不上」。

  • 追问:那同一个问题问两次,agent 答得字字不同,你的断言写什么?(逼你说出「不能拿字符串做精确比对」这个核心矛盾)
  • 追问:就算这次答对了,你怎么知道它稳定对?(引出「单次成功 ≠ 可靠」,埋下连做多次度量可靠性的伏笔)
  • 追问:那你打算从哪些角度评?只看最后那句话够吗?(看你知不知道还有任务有没有真办成、中间步骤对不对、上线后好不好)

📚 原理讲解

先把「传统软件测试」是什么讲清楚。它的世界观是确定性:同样的输入,永远得到同样的输出。所以你能写一句话:「我喂 2 + 2,你必须还我 4,不是 4 就报红。」这种「输入 → 期望输出严格相等」的检查,就叫断言(assert)。它能成立,全靠那个「永远相等」的前提。

为什么 agent 把这个前提打碎了

对话 / 工具型 agent 有两个根本不同。第一,它的输出是自由文本:你问「这只股票最近涨了多少」,它今天答「最近一个月上涨约 8.3%」,明天可能答「过去 30 天涨幅大约在 8% 上下」。意思一样,字符串完全不同。世上没有一个「唯一正确的标准字符串」让你去比对。第二,它会自己调工具、走多步:先查行情、再算涨幅、可能还查一下有没有分红——这条「中间走了哪几步」的路径,每次也可能不一样。

打个比方:测一台计算器,你可以写死断言,因为 2+2 永远等于 4,答案是个点。但 agent 更像一个会聊天、会自己上网查资料的助手。评它,就像批改一篇作文——「写得好不好」是个程度问题不是对错问题,而且两个人写法不同都可以是好作文。你不能拿一把「等不等于标准答案」的尺子去量作文,得换一套打分的办法。

那要换成什么办法:四个相互独立的角度

实践里把评估拆成四个互不重叠的角度,按需取用(展开见本类第 3 题):

  • 回答质量——答得好不好。既然没有标准字符串,就请一个更强的模型当裁判,按评分标准给这段回答打分(像请特级教师批作文)。把主观「好」变成数字的具体办法见本类第 2 题。
  • 任务完成——事儿有没有真办成。比如「帮我下个单」,不看它嘴上说没说「已下单」,而去看数据库里订单到底建了没有。这是看「环境最终被改成什么状态」,比对文本可靠得多。
  • 过程轨迹——中间步骤对不对。哪怕答案蒙对了,如果它该查行情却没查、凭空编了个数,这条轨迹也是坏的。
  • 生产在线——上线后真实用户买不买账(点赞、有没有立刻重试、有没有放弃)。

单元测试,顶多只能盖住这四块里很小的一角——而且主要是「能写死断言」的那种确定性子集。

第二条暗线:单次成功 ≠ 稳定成功

就算某次它答对了,也别高兴太早。模型有随机性,这次对、下次可能就飘了。所以业界用「连做 k 次,是不是次次都成功」的概率来度量可靠性,而不是跑一次过了就算过。一个面试场景:你不会因为候选人一道题答对就录他,你会想知道「换几道同类题,他是不是都稳」。

💻 示例讲解

用一段教学伪代码,把「断言为什么会误杀 agent」演给你看。注意这不是真要这样写测试,而是演示错误做法会怎么崩。

# 反面教材:把 agent 当计算器,拿标准字符串做断言
def 用断言测计算器():
    结果 = 计算器.算("2 + 2")
    assert 结果 == "4"          # ✅ 永远成立,因为答案是确定的一个点

def 用断言测对话agent():
    回答 = agent.问("这只股票最近一个月涨了多少")
    # ❌ 我们以为标准答案长这样,就拿它去精确比对
    assert 回答 == "最近一个月上涨约 8.3%"
    # 但 agent 这次回的是「过去 30 天涨幅大约 8% 上下」
    # 意思完全对,字符串却不等 → 断言报红 → 好答案被误判成 bug

# 正确思路:不比字符串,换「打分 / 看终态 / 连做 k 次」
def 评对话agent(问题, k=5):
    成功次数 = 0
    for _ in range(k):                       # 暗线②:连做 k 次看稳不稳
        回答, 走过的步骤 = agent.问(问题)
        质量分 = 强模型当裁判.打分(回答, 评分标准)   # 角度①:好不好,按程度打分
        办成了 = 查数据库终态() == 期望终态          # 角度②:事儿有没有真办成
        if 质量分 >= 阈值 and 办成了:
            成功次数 += 1
    return 成功次数 / k                        # 报告「次次都成」的概率,不是单次过没过

推演:本项目自己撞过一个更狠的坑——连「标准答案」本身都不固定。我们有一套自动出的金融计算题(反向出题,见本类第 4 题),它的「金标准答案」是拿当天的实时行情算出来的。结果同一道题,把基准日钉到「今天」,答案每天都在漂:2026-06-11 生成的一批题,到 6-17 用新数据重算,141 道里有 57 道数值答案漂移超过 0.5%。其中「涨幅」这一桶,通过率从 31/45 假性暴跌到 6/45——agent 其实答对了(它算的 -23.30% 正好等于新算的标准答案),却被 6 天前冻结的旧标准答案(-22.98%)误判成错。连「标准答案」都会随时间变,这恰恰是「不能写死断言」最硬的实证。

公允裁决:单元测试断言绝不是「过时的笨办法」,它又快又便宜又确定,在它适用的地盘上无可替代——agent 里那些确定性逻辑(算涨幅的纯数学、工具参数的合法性校验、命令分支的固定路由)就该老老实实写断言守住,跑一次几毫秒。我们不是要废掉断言,而是认清它只能盖住 agent 行为的一小角:一旦进入「自由文本回答好不好、任务有没有真办成、多步轨迹对不对」这片地,精确相等的断言不仅无能为力,还会把好答案误杀成 bug(上面那 57 道漂移题就是活例)。所以正确姿势是两者分工:确定子集交给断言,开放行为交给四角度评估 + 连做 k 次。

📌 总结

  • 难在哪:传统测试靠「输入定 → 输出定」才能写相等断言;agent 输出是自由文本 + 多步工具调用,同一问题每次措辞 / 路径都不同,没有唯一标准字符串可比对。
  • 类比:测计算器(2+2 恒等于 4)能写死断言;评 agent 像批作文,好坏是程度、过程也可变,得换一套打分法。
  • 怎么评:分回答质量(强模型当裁判)、任务完成(比数据库终态)、过程轨迹(步骤对不对)、生产在线(真实反馈)四个相互独立角度按需取用,单元测试只盖得住其中很小一角。
  • 两条暗线:趋势从「匹配输出文本」转向「校验环境最终被改成什么状态」;单次成功 ≠ 稳定成功,用「连做 k 次都成功的概率」度量可靠性。
  • 不是废断言:确定子集(纯数学 / 参数校验 / 固定路由)照样写断言守住,只是开放行为得交给四角度评估。

一句话速记:计算器能写死断言,会聊天会查资料的助手得像批作文一样换四个透镜打分、再连做 k 次看稳不稳。

Q2

你大体怎么给这种 agent 打分?「答得好不好」这种主观的东西,你怎么把它变成可比较的数字?

★★★☆☆
评分方法LLM 裁判G-Eval量化指标pass@k

🎯 考察点分析

上一题(见本类第 1 题)已经说清"为什么不能写几个单元测试断言就完事"——因为 agent 的回答是开放的、没有唯一字符串可比。这一题接着逼问:既然没标准答案,你又凭什么说一版"比另一版好"?面试官真正想听的,是你有没有一套把"答得好不好"这种主观感受变成可累加、可横向比、可画曲线的数字的具体办法,而不是含糊地说一句"我们用大模型打分"。

这道题最容易暴露两种人。一种只会说"找几个人读一读、凭感觉打分",那他没意识到人工评分不可复现、不可回归、还贵;另一种张口就是"用 GPT 当裁判",但说不出裁判内部到底怎么把一句话变成一个稳定的数。真懂的人能讲出:打分有哪几种范式、为什么一个整数分还不够要摊概率、以及什么时候根本不该用大模型打分而该用程序去算。

  • 追问:大模型每次只吐一个整数分(比如就给个 4),大量样本卡在同一个分上、区分不开,你怎么办?
  • 追问:"直接打一个绝对分"和"两个答案比谁好"是两种范式,什么场景该用哪种?
  • 追问:有些金融题是能算出唯一答案的,你还用大模型当裁判吗?为什么不?
  • 追问:你怎么知道你这个裁判本身靠不靠谱?拿什么证明它打的分能信?

📚 原理讲解

先把整件事的目标说白:我们要做的,是把"这答案好不好"从拍脑袋点头,变成一张有评分量规的打分表——量规就是"什么样算 5 分、什么样算 3 分"写成明文,谁来打都照着同一把尺子。打分表能给出数字,数字才能累加、才能横向比、才能画成曲线看趋势。下面分三层讲:怎么打、怎么把整数分摊成连续分、以及什么时候干脆不用大模型打分。

第一层:打分的两大范式——直接打分 vs 成对比较

直接打分就是给一个答案一个绝对分,比如 1-5 或 1-10。它又分两种子玩法:一种是"先给标准答案再打",适合数学、计算这类有正解的题——讲究的做法是先让裁判自己独立把题解一遍,拿它自己的解当参考,再去看被测答案对不对(不然裁判容易被被测答案带跑);另一种是"只给评分标准打",适合开放对话这种没唯一正解的题,你给裁判一份评分量规,让它照着量规打。

成对比较是另一条路:不给绝对分,而是把两个答案摆一起,让裁判选谁更好,再把无数次"谁赢谁输"聚合成赢面或 Elo 排名(就像棋手积分,赢多了排名就高)。它的好处是人/模型判"A 和 B 哪个好"比判"A 值几分"稳得多——但要小心位置偏好:裁判会无脑偏爱排在前面那个答案。实测把甲乙交换位置跑两遍,只有约 65% 两遍方向一致,等于有三成情况它是在"偏好第一个"而不是真比好坏。治法是交换位置双跑取一致:两遍都说同一个赢才算赢,否则判平局(裁判去偏的具体坑见本类第 5 题)。

第二层:G-Eval 三步,把"主观"压成"连续可比的数"

光让大模型吐一个整数分有个硬伤:它倾向于把一大批答案都卡在同一个分(比如什么都给 4),于是几十个答案的分数挤成一坨,根本区分不出谁更好。G-Eval 这套方法用三步解决:

  • ①自动推理:把一条人写的评分标准(比如"连贯性")交给模型,让它自己展开成一串结构化的评估步骤——相当于把一句模糊的标准翻译成"先看这个、再看那个"的检查清单;
  • ②顺步骤打分:裁判照着上一步生成的步骤一条条推理,最后给出一个 1-5 的整数分;
  • ③概率加权:关键一步——不取那个整数,而是去看模型对每个分数 token 的概率,算期望。比如模型给 5 分的概率 0.6、4 分 0.3、3 分 0.1,那最终分 = 5×0.6 + 4×0.3 + 3×0.1 = 4.5。

第三步是这套方法的灵魂。它把离散的整数分抹成了连续的小数分:原本只能落在 1/2/3/4/5 五个点上,现在能落在 4.5、4.37 这种细缝里,大批样本不再卡同一个分,谁比谁强 0.1 都比得出来。本质是把模型自己的不确定性也当成信息摊进了分数里——它不太确定到底是 4 还是 5,那就给 4.5,比硬取一个整数诚实得多。在一个摘要评估数据集上,这套方法跟人类打分的相关系数到 0.514,大幅超过 ROUGE、BERTScore 这些只数字面重叠的老指标。

裁判本身可信吗:拿一致率自证

用大模型当裁判,第一反应该是"它打的分能信吗"。衡量办法是看它跟人类打分的一致率。好的裁判设计能让强模型与人类一致率到 80-90%。更有意思的是:在某基准上去掉平局后,裁判与人类一致率是 85%,而人类彼此之间的一致率只有 81%——也就是说,设计良好的裁判跟人的吻合程度,甚至超过了两个人之间的吻合程度。这给"用模型当裁判"提供了底气:它不是更随意,反而比人更稳定。

第三层:能算出唯一答案的题,根本不该用大模型打分

上面都是处理"开放、没正解"的回答。但本项目里有一大类是金融计算题——"这只股票过去一年涨了多少""年化是多少""两只股票相关性多少",这种题有唯一正确数值。对这类题用大模型当裁判是杀鸡用牛刀,还不可复现(同一道题它今天判对、明天可能判错)。我们改用程序化数值判分:用正则从答案里把数字抠出来,跟程序算好的标准答案比,带容差放行——涨幅用 ±0.5%、年化(CAGR)用 ±1% 的相对容差、相关系数用 ±0.01 的绝对容差、波动率用 ±2%。判完一道道题,再按题型分桶聚合成pass@k 百分比(连做 k 次都答对的比例,这套反向出题+判分机制见本类第 4 题)。这比"看一眼觉得对不对"可复现得多,跑十遍结果一样。

一句话收口:开放题用带量规的大模型打分(+概率加权摊成连续分),有正解的题用容差数值判分 + pass@k——对不同性质的题用不同的"变数字"办法,而不是一把尺子量到底。

💻 示例讲解

第一段是 G-Eval 的灵魂:为什么"摊概率"能把卡死的整数分救活。注意最后一步——不取整数分,而是拿模型给各个分数的概率算期望:

# 开放题:大模型当裁判,但不直接取整数分,而是把它的「不确定性」摊进分数
def g_eval_score(question, answer, rubric):
    # 第①步:把一条人写的评分标准(如「连贯性」)展开成结构化评估步骤
    steps = llm_unfold_into_steps(rubric)
    # 第②步:让裁判照步骤推理,但要它返回「各分数的概率」,不是只返回一个整数
    probs = llm_judge_with_logprobs(question, answer, steps)
    # probs 形如 {5: 0.6, 4: 0.3, 3: 0.1} —— 模型自己也拿不准是 4 还是 5

    # 第③步:概率加权求期望 —— 把离散整数分抹成连续小数分
    score = sum(s * p for s, p in probs.items())
    return score                         # 5×0.6 + 4×0.3 + 3×0.1 = 4.5,落在整数缝里

# 对比:若只取「最可能的那个整数分」,一大批答案全挤在 5 分,区分不开
def naive_score(probs):
    return max(probs, key=probs.get)     # 直接给 5,丢掉了「其实只有六成把握」这条信息

第二段是另一极:有唯一答案的金融计算题,根本不喊大模型,用程序抠数字比容差——可复现:

# 有正解的题:程序化数值判分,正则抠数 + 容差放行,不用大模型(可复现)
def numeric_judge(answer_text, gold, kind):
    got = extract_number(answer_text)            # 正则从答案里抠出那个数
    tol = {"涨幅": ("rel", 0.005),               # 涨幅:±0.5% 相对容差(CAGR 是 ±1%)
           "相关": ("abs", 0.01),                # 相关系数:±0.01 绝对容差
           "波动": ("rel", 0.02)}[kind]          # 波动率:±2% 相对容差
    mode, eps = tol
    if mode == "rel":
        return abs(got - gold) <= eps * abs(gold)
    return abs(got - gold) <= eps                # 落在容差内 = 这一道判对

# 一道道判完,按题型分桶聚合成 pass@k 百分比 —— 才有可横向比、可画桶的数字
def bucket_pass_rate(results):
    return {kind: sum(rs) / len(rs)              # 比「看一眼觉得对不对」可复现
            for kind, rs in group_by_kind(results).items()}

推演:① 概率加权——同一批答案若都硬取整数分,可能十个里八个都是 5,挤成一坨分不出高下;改成摊概率后,一个"六成把握给 5"的答案得 4.5、一个"九成把握给 5"的得 4.9,0.4 分的差就把它们排开了,几十个样本不再卡死在同一个点。② 数值判分——一道"某股票过去一年涨幅"题,程序算出标准答案 −23.30%,被测助手答 −23.18%,相对差 0.12% < 0.5% 容差,判对;换一个助手答 −22.5%,相对差约 3.4% > 0.5%,判错。把这一桶几十道题判完,聚合成"涨幅桶 pass@1 = 87%"这种数字——它能跟上一个版本的 81% 直接比,能画成回归曲线,这是人工"读一读点点头"给不出的。

⚖️ 决策对比

维度我们的选择:可量化指标(概率加权打分 / 赢面 / 容差数值判分 + pass@k)替代方案:人工主观看(人一条条读、凭感觉点头)
可复现性同一批答案跑十遍结果一样,能回归对比同一个人不同天、不同人之间打分都飘,不可复现
可横向比4.5 / 4.9 这种连续分能直接排序、画曲线、跟旧版本比"感觉这版好点"无法量化成可累加的数
区分度概率加权把整数分摊成小数,几十样本不卡同一分人也倾向打整数、打中庸分,大批样本分不开
成本 / 规模跑一批几乎零边际成本,能上千道题人读一道几分钟,几百道就是好几个工时,贵且累
细腻度 / 上限会漏掉人能察觉的微妙语气、事实硬伤等长尾问题人的判断细腻、能抓到指标抓不到的"说不出哪不对"
裁判可信度设计良好时与人类一致率 85% > 人类间 81%就是"人类那把尺",但人与人本身只有 81% 一致

公允裁决:人工主观看不是稻草人,它有一个量化指标永远追不上的真本事——细腻。一个有经验的人读一段回答,能闻出"事实虽然对但语气傲慢""逻辑通顺但其实没回答用户真正担心的事"这种微妙问题,这些往往是评分量规列不全、大模型也抓不到的长尾。所以最终交付前我们仍然会人工抽看一批,把它当"金标准锚点"和"找量规盲区"的手段。但它当不了日常迭代的主力尺子:不可复现意味着没法回归——你改了个 prompt 想知道是变好还是变坏,人工评分今天给 7、明天给 6,你根本不知道是模型动了还是人手抖了;不可比意味着没法画曲线看趋势;贵意味着上不了规模。我们之所以选可量化指标,是用"牺牲一点人的细腻"换来"横向可比、可回归、低成本"——而且数据反过来支持这个选择:设计良好的裁判跟人的一致率(85%)甚至高过两个人之间(81%),说明"机器更随意"是个错觉,它反而更稳。正确姿势是量化指标当日常主力尺子、人工抽看当锚点和盲区探针,不是二选一。

📌 总结

  • 打分两大范式:直接打分(给绝对分,数学题先让裁判独立解一遍当参考、开放题照量规打)和成对比较(比谁好,聚合成赢面/Elo)——后者更稳但要交换位置双跑治位置偏好。
  • G-Eval 把整数分摊成连续分:不取那个整数,取模型给各分数 token 的概率算期望(5×0.6+4×0.3+3×0.1=4.5),把模型自己的不确定性当信息摊进分数,缓解"一大批样本卡同一个分、区分不开"。
  • 有唯一答案的题不用大模型:金融计算题改程序化数值判分——正则抠数 + 容差(涨幅 ±0.5%、年化(CAGR)±1% 相对、相关 ±0.01 绝对、波动 ±2%),按桶聚合 pass@k,比"看一眼觉得对不对"可复现得多。
  • 裁判可信度拿一致率自证:设计良好时与人类一致率 80-90%,去平局后 85% 甚至高过人类彼此间的 81%——"机器更随意"是错觉,它反而更稳。
  • 量化当主力、人工当锚点:人工主观看胜在细腻能抓长尾,但不可复现/不可比/贵,当不了日常迭代的尺子;正解是量化指标做主力、人工抽看做盲区探针,不是二选一。

一句话速记:把"好不好"从拍脑袋变成带量规的打分表,再用概率把整数分摊成连续分;有唯一答案的题干脆用容差数值判分 + pass@k——牺牲一点细腻换来横向可比、可回归、低成本。

评估对话 / 工具型 agent,你用了哪四个相互独立的角度?为什么强调「相互独立」?

★★★★☆
四角度正交评估任务完成终态过程轨迹裁判去偏

🎯 考察点分析

这道题表面是「列举四个角度」,真正在探的是你有没有把「评估」拆成几个互不重叠的维度的系统观,还是只会甩一个总分。一个会对话、会调工具的 AI 助手,失败方式不止一种:有的答得花团锦簇但根本没把事做成,有的事做成了纯属瞎蒙(多调一堆工具、绕了大圈),有的线下全绿一上真实流量就崩。面试官想确认的是:你知不知道这几种「病」是不同的病,得用不同的「体检项」分别查,而不能指望一个分数同时照出全部短板。顺带还在看你是否清楚「用大模型当裁判」这件事本身自带系统性偏差——这是高级候选人和「只会跑个 LLM-judge 打个分」的初级候选人的分水岭。

  • 追问:「相互独立」到底独立在哪?能不能各举一个「只有这个角度能抓到、别的角度抓不到」的失败例子?
  • 追问:既然有了「任务有没有做成」(终态对),为什么还要单独看「过程轨迹」?终态对了不就够了吗?
  • 追问:你反复说「用强模型当裁判」,那这个裁判自己会不会出错 / 有偏好?你怎么治?
  • 追问:这四个角度在你这个项目里具体落地成了什么?哪个因为是个人作品只留了口子没真做?

📚 原理讲解

先给一个生活类比定调:体检不能只量体重。体重正常不代表没病——还得量血压、测血糖、做心电、拍影像,每一项查的是不同的器官、不同的病,任何一项异常都说明一件别的项目照不出来的事。评估对话 agent 同理:我用四个互不替代的角度,每个角度盯一类独有的失败模式。

四个角度,各盯一类病
  • 角度一 · 回答质量(用强模型当裁判):单条回答好不好——连不连贯、切不切题、有没有帮到人。判定形态是「让一个更强的大模型按评分标准打分 / 两个答案比谁好」。代表方法 G-Eval(按标准打分 + 概率加权)、MT-Bench(1-10 绝对分)、AlpacaEval(对标准答案算赢面)、Arena-Hard(成对比较)。这一层打分细节见本类第 2 题、裁判的坑见本类第 5 题,这里不重讲。
  • 角度二 · 任务完成(比对话结束后的「世界终态」):不看 agent 嘴上说了啥,只看对话结束后数据库 / 环境被改成了什么状态,和标注的目标状态比。代表 τ-bench(比数据库终态)、SWE-bench(改前失败、改后通过的可执行单测)、WebArena(手写校验函数查网站后端真实状态)。还有一个关键指标——连胜率(论文写 pass^k):同一任务连做 k 次、k 次全成功的概率,专门度量「稳定地做对」而非「偶尔蒙对一次」。
  • 角度三 · 过程轨迹(中间步骤对不对):把 agent 走过的「调了哪些工具、什么顺序、什么参数」这条序列,和参考序列做结构比对。代表 LangChain agentevals(纯规则、不用大模型、结果确定,匹配松紧有四档)、TRAJECT-Bench(把轨迹拆成工具名对不对 / 参数对不对 / 有没有多余步骤几个维度)、逐步奖励模型(给每一步打分)。
  • 角度四 · 生产在线(上线后真实流量上闭环):用户点赞(稀疏)+ 隐式信号(重试率 / 放弃率)+ 在线裁判(按抽样比例自动打分)+ 实时护栏(每个请求放行或拦截)+ A/B + 录制回放回归。
为什么强调「相互独立」——四种病互相照不出来

「独立」的精确含义是:这四个角度各测一类失败模式,而且不能互相替代——一个角度全绿,完全不保证另一个角度也绿。逐对说清:

  • 质量高 ≠ 任务成:助手可以把一段话写得连贯漂亮、切题、滴水不漏(质量裁判给高分),但它要改的那条订单根本没改成(终态错)。质量角度对此一无所知,因为它只读文本不查数据库。
  • 终态对 ≠ 过程对:最后状态改对了,也可能是瞎蒙的——多调了一堆无关工具、绕了三圈、靠运气撞对。终态比对给绿灯,但这条轨迹脆得很,换个输入就崩;只有过程角度能抓到「多调工具 / 步骤冗余」。
  • 线下全绿 ≠ 线上不崩:前三个角度都在你精心准备的测试集上跑,真实流量的分布、刁钻问法、长尾意图是你没想到的;只有生产在线角度能在真用户身上发现质量漂移。
  • 还有一条暗线把四角度都串着:角度一的「强模型裁判」自带系统性偏差——偏好排在前面的答案、偏好更长的答案、偏好自己写的答案。比如一个又长又空的回答会被裁判莫名其妙高看一眼。所以裁判这一层必须叠去偏:交换位置双跑、长度去偏、强制先写推理、多次采样投票。

结论:正确的做法是「正交补口」,而不是堆一个总分。把四个角度糅成一个数字,等于体检报告只给你一个「健康指数 78」——异常了你都不知道是血压还是血糖,定位不了短板,也就改不动。四个独立的分数才能告诉你「哪一项异常 = 哪种病」。

这四个角度在本项目里落成了什么

按「个人作品 / 克制主义」的定位,我没有四个角度都重装,而是各取最高性价比的那一刀:

  • 任务完成(终态):借 τ-bench 的思路,给金标准用例标注「对话后期望的工具副作用状态」,评终态而不是评对话文本;再叠「连做 k 次都成功的概率」守护稳定性。
  • 过程轨迹:接 LangChain agentevals——「强制必须命中某工具」用最严格模式做确定性回归;「是否多调了记忆 / 知识库工具」用子集模式(子集 = 实际走过的工具必须是参考的子集 = 不许多余,别和「超集」搞反)。
  • 生产在线:前端点赞绑到那次调用记录上;按问题类型分桶埋「重试 / 放弃」隐式信号。A/B 因为个人作品流量不足,只在架构上留了口子、没真实装。

💻 示例讲解

下面这段伪代码不是去算一个总分,而是把四个角度各跑一遍、分别返回各自的「绿 / 红」——故意凑一个「质量绿、终态红」的例子,看一个分数为什么会骗人:

# 同一条「改签订单」对话跑完,四个角度各查各的,绝不揉成一个总分
def evaluate(dialog, db_after, golden):
    report = {}

    # 角度一 · 回答质量:强模型裁判读「文本」,只看话说得好不好
    #   叠去偏:把甲乙位置交换跑两遍,两遍方向一致才算数(治「偏好第一个」)
    report["质量"] = judge_with_swap(dialog.final_reply, rubric=golden.rubric)

    # 角度二 · 任务完成:不读文本,只比「对话后数据库被改成了什么」
    #   连做 k 次都成功的概率(pass^k),度量「稳定做对」而非「蒙对一次」
    report["终态"] = (db_after.state == golden.expected_state)

    # 角度三 · 过程轨迹:把调过的工具序列和参考序列做结构比对(纯规则、不用大模型)
    #   子集模式 = 实际走过的工具必须是参考的子集 → 多调一个就判红(抓「瞎蒙绕路」)
    report["轨迹"] = is_subset(dialog.tool_calls, golden.reference_calls)

    # 角度四 · 生产在线:线下跑不出来,靠真实流量的隐式信号(这里用历史回放占位)
    report["在线"] = online_signals(dialog.session_id)  # 重试率 / 放弃率 / 点赞

    return report   # 返回四个独立结论,谁红就知道是哪种病,而不是一个糊住一切的数

# 反例:把四个揉成一个总分 —— 看似省事,实则把短板抹平
def evaluate_bad(dialog, db_after, golden):
    q = judge_with_swap(...)            # 0.95(话说得漂亮)
    done = (db_after.state == ...)      # False(订单其实没改成)
    # 加权一平均:0.95*0.7 + 0*0.3 = 0.665 → 看着「及格」,真相被埋了
    return 0.95 * 0.7 + (1.0 if done else 0.0) * 0.3

推演:同一条「帮我把最低价经济舱机票改签」的对话,助手回了一段非常得体、解释清楚改签政策的话。① 质量角度:裁判交换位置双跑都给高分,记 0.95,绿。② 终态角度:去查数据库——那张订单的状态压根没变(政策规定最低价不可改签,助手嘴上答应了但工具没真执行 / 执行失败),终态 ≠ 目标态,红。③ 轨迹角度:子集模式发现它还顺手多调了两次查询工具,红。四个独立结论一摆,我立刻知道病在「说到没做到 + 绕路」。可一旦走 evaluate_bad 把它们加权成 0.665,这个「及格分」会让我误以为只是小毛病,把一次彻底的任务失败粉饰成了 B+——这正是「单一总分掩盖一切」的具体长相。

公允裁决:单一 LLM 裁判绝不是稻草人——它真的好用:一个评分 prompt、几小时就能给任意自由文本回答打出和人类相当一致的分,几乎零标注成本,对「快速看一眼整体回答质量好不好」这个目的它是当前性价比最高的办法,我自己在角度一里用的就是它。它的问题不在「不好」,而在用它一个去覆盖全部:它本质上只是我四个角度里的第一个,只读文本、不查终态、看不见过程、跑不到线上,还自带偏好长答案 / 偏好排第一 / 偏好自己写的系统性偏差。把它当唯一标尺,等于只靠量体重来体检——体重这一项它量得很准,但你不能指望它照出血糖。所以我的选择不是「抛弃 LLM 裁判」,而是把它收编为四角度之一并给它叠去偏,另外三个角度去补它照不到的死角:终态补「说到没做到」,轨迹补「做成了但瞎蒙」,在线补「线下绿线上崩」。四个独立分数贵一点、麻烦一点,但换来的是「异常时知道是哪种病」——这对一个想体现评估深度的作品,是值得付的代价。

📌 总结

  • 四个相互独立的角度:①回答质量(强模型当裁判)②任务完成(比对话后数据库终态 + 连做 k 次全成功的概率 pass^k)③过程轨迹(调了哪些工具、绕没绕路)④生产在线(点赞 / 重试率 / 在线裁判 / 护栏 / A/B)。
  • 「独立」= 各测一类病、不能互相替代:答得漂亮可能没做成(终态错)、做成了可能瞎蒙(轨迹乱)、线下全绿线上仍崩——任一角度绿都不保证别的绿,所以要正交补口,不是堆一个总分。
  • 单一总分会掩盖短板:把四个揉成一个数,异常时你不知道是质量 / 终态 / 轨迹哪一项动了,定位不了、也就改不动;像体检只量体重照不出血糖。
  • 两条暗线:「强模型裁判」自带偏差(偏好第一 / 偏好长 / 偏好自己),必须交换位置 + 长度去偏 + 强制推理 + 多次采样;评估趋势是「校验终态」取代「匹配文本」、「连胜率」取代「单次成功率」。
  • 本项目落地:给金标准用例标终态(τ-bench 思路)、轨迹用 agentevals 最严格 / 子集模式查多调工具、点赞绑调用记录 + 隐式信号分桶;A/B 因个人作品流量不足只留口子。

一句话速记:质量 / 终态 / 轨迹 / 在线四把尺子各测一类失败,任一单独绿都不算数——正交补口,绝不糊成一个总分。

反向出题 + pass@k:你怎么自动造出金融计算题、又怎么判分?为什么是「反向」?

反向出题pass@k数值判分oracle穷举维度

🎯 考察点分析

这道题表面问"怎么自动造题",真正想看的是你有没有想清楚"标准答案从哪来"这件事。给 AI 助手判分,最难的从来不是判,是你拿什么去判——标准答案(行话叫 gold,金标准答案)本身得先靠谱。一般人会下意识地"先出题、再想答案",而答案如果靠人手算、人标注,那既慢又贵、还可能标错。我做的是把这个流程倒过来:先用一段确定性的纯函数(行话叫 oracle,神谕/标尺函数)把答案算死,再倒着编出题面。面试官想确认的是:你理解"答案先于题目"这个反转解决了什么瓶颈、又付出了什么代价。

  • 追问:"反向"到底反在哪?跟"先出题再算答案"比,省下来的是什么?
  • 追问:已经有一套判分器了(判工具选得对不对、有没有瞎编),为什么这里非要新开一条判分轨?
  • 追问:你不是简单地把所有"指标 × 股票 × 窗口"全排列一遍吗?这么穷举会出什么问题?
  • 追问:判分时助手答 "-23.30%"、标准答案是 "23.30",你怎么算它对?容差怎么定?

📚 原理讲解

整套东西可以拆成三件事:怎么把答案先算死、怎么倒着编出题、怎么判对错并汇总成一个稳定性分数。逐个说。

一、"反向"反在哪:答案先于题目

正向出题是"先有题、再去求答案":你写一道"茅台近一年涨了多少",然后得有人去把这个答案算出来或标出来。瓶颈就卡在这一步——人标得慢、贵、量上不去,还可能标错,而一旦标准答案本身错了,后面所有判分全是错的。

反向出题把箭头掉过来:先用一段冻死口径的确定性函数,吃真实股价、吐出标准答案,再拿这个答案去套一个题面模板,反向包装成一道中文问题。这么一倒,有两个直接好处——第一,答案天然正确,因为它就是那段公式算出来的,不存在"标错"一说;第二,能批量造,把"指标 × 股票 × 窗口 × 难度"几个维度一组合,程序自己就能吐出成百上千道,人完全不进环。类比:不是老师出卷子让学生写答案,而是先拿计算器把标准答案算好,再倒着编出题面。

二、出题的数据流:几个维度交叉,oracle 兜底算答案

生成器吃几个维度的笛卡尔交叉:15 只手挑的股票(分 5 个板块)× 5 个指标 × 3 个时间窗口(近三月 / 近一年 / 近三年)× 三档难度。每一格走同一条流水线:先确定窗口对应的真实交易日区间 → 用真实行情接口把这段的股价拉下来 → 交给 oracle 算出标准答案 → 把答案套进题面模板 → 落盘成一道题。

这里的 oracle 是一组互不依赖的纯函数,每个对应一个金融指标:区间涨幅、最大回撤、年化波动率、两只股的相关性、复合年增速(CAGR)。它们口径全部冻死(比如涨幅 = 期末价 ÷ 期初价 − 1,年化按 √252 个交易日,标准差自由度取 1),所以同样的输入永远吐同样的答案——这正是它能当"标尺"的前提。

三、为什么新开一条判分轨,而不复用现成的

系统里本来已经有一套对话判分器,但它判的是"工具选对了没、有没有瞎编(grounding)"——它根本不关心算出来那个数字对不对。而计算题的命门恰恰是数值要跟标准答案对得上。所以这里必须新开一条按答案形状判的轨。标准答案不是只有"一个数"这一种形状,于是判分器按四种形状分别处理:

  • 单值(scalar):从助手的回答文本里用正则把所有数字抓出来,只要有一个落进容差就算命中;
  • 双值(multi_scalar):像"回撤+波动"一题两问,两个数都得各自命中,缺一不可;
  • 排序(ranking):按候选股名在回答里首次出现的位置排个序,取前 N 个,跟标准名单顺序逐一比对;
  • 集合(set):像"筛出涨幅>0 且回撤<20% 的股票",比的是集合相不相等(空集合也是合法答案,得能正确判)。

容差是按指标定的、不是一刀切:涨幅用相对误差 0.5%、CAGR 用 1%(且接近零的涨幅不被放大),回撤 0.5% 相对,波动 2% 相对,相关性 0.01 绝对。为什么涨幅要特殊处理?因为一个接近零的涨幅(比如 0.1%)用普通相对误差会被无限放大,所以改成比"价格变成几倍"的相对误差,躲开这个数值陷阱。还有个细节:文本里 "-23.30%" 和 "23.30" 按绝对值视作同一量级,不被正负号或百分号干扰。

四、不走裸笛卡尔积:三道真实性闸

这是最容易被忽略、也最体现工程判断的一点。如果把几个维度无脑全排列,会造出一堆没意义甚至有害的题。所以出题前要过三道闸:

  • 闸一,合法配对矩阵:用一张硬编码的"指标能配哪些窗口"的表硬挡掉违和组合——比如复合年增速(CAGR)至少要两年才有意义,就只允许配近三年,不准配近三月;相关性只在同板块两两之间配,不去算"茅台和某只银行股的相关性"这种没分析价值的对。
  • 闸二,意图锚定:所有题都从一个真实的用户任务("研究一只股票")实例化出来,不是凭空拼字段,保证造出来的题是用户真会问的。
  • 闸三,裁判 + 流量对齐:用真实裁判口味和线上真实问法去校准——这一档在最小可用版本里留空,先把前两道闸打牢。

这背后是一条吃过亏的教训:穷举维度时别把"手头那张种子清单"当成全集,要按"数据/工具能供给什么"这个供给侧去切维度。当年因为没这么切,意图矩阵返工过两次(从 12 个膨胀到 20、又收回到 10)。

五、判分汇总成 pass@k:专找"战力断崖"

每道题不是只跑一次,而是注入一个冻结的参照日期(让助手心里的"近一年"跟出题时那段窗口精确对齐),把真助手跑 k 次。然后按 难度 × 指标 分桶,看"连考 k 次里至少成功一次的概率"。为什么要重复 k 次?因为大模型有随机性,跑一次的成败可能是运气;pass@k 看的是稳定性——哪个桶(比如"复杂档 × 排序")连考 k 次都飘,那里就是助手的能力断崖,正是要重点加固的地方。这也跟"pass@k 作为量化指标"的总论(见本类第 2 题)一脉相承。

💻 示例讲解

先看"反向"这一步——核心就是先算答案,再编题面,两个箭头是反的:

# 反向出题:不是「先出题、再求答案」,而是「先用标尺函数算死答案、再倒着编题面」
def make_one_case(stock, indicator, window):
    # 1) 先把这段窗口的真实股价拉下来(确定的交易日区间)
    prices = fetch_real_prices(stock, window)            # 真行情数据

    # 2) 用「标尺函数」把标准答案算死 —— 这就是 gold,天然正确
    #    interval_return / max_drawdown / cagr ... 口径全冻死,同输入同输出
    gold = oracle[indicator](prices)                     # 比如 区间涨幅 = 末价/首价 - 1

    # 3) 倒着把答案包装成一道中文题面(答案 → 题目,箭头是反的)
    question = template[indicator].format(name=stock.name, window=window_cn)

    # 4) 连同「答案的形状」一起落盘:单值 / 双值 / 排序 / 集合
    return Case(question=question, gold=gold * 100, shape="scalar",
                tolerance={"kind": "rel_mult", "value": 0.005})   # 涨幅容差 0.5%

# 真实性闸:不走裸笛卡尔积,违和组合先挡掉

再看判分:按"答案形状"分流,单值题就是抓数 + 容差比对:

# 判分:按答案形状分流;这里看最常见的「单值」
def judge_scalar(answer_text, gold, tol):
    # 从助手的整段回答里,用正则把所有数字都抓出来(去掉千分位逗号)
    nums = extract_numbers(answer_text)                  # "涨了 -23.30%" → [-23.30]
    target = abs(gold)                                   # "-23.30%" 与 "23.30" 按绝对值同看
    threshold = tol["value"] * target                    # 相对容差:0.5% × 标准答案
    # 只要抓到的任意一个数落进容差,就算命中
    return any(abs(abs(n) - target) <= threshold for n in nums)

# 集合题的坑:空集合也是合法答案,必须判得对
def judge_set(answer_text, candidates, gold):
    selected = {name for name in candidates if name in answer_text}
    return selected == set(gold)        # gold 可能是 [](一只都不满足),也得正确通过

推演:出题机算出茅台近一年涨幅标准答案是 -22.98%,落盘成单值题、容差 0.5% 相对(阈值 ≈ 0.115)。助手跑出来答 "近一年下跌了 -23.30%":正则抓到 -23.30,按绝对值比 |23.30 − 22.98| = 0.32 > 0.115,这一次判不通过。但跑 k 次里另几次答到 -23.05、-22.95,就落进容差判通过——于是这道题 pass@k(至少成一次)=通过,而单次成功率只有 60%。汇总到"简单档 × 涨幅"这个桶,如果一整桶 pass@k 普遍偏低,就说明助手连最基础的涨幅都算不稳,这就是要标红的断崖。最小可用版本先造 100–200 道,把流水线打通后可往上扩到上万道。

📌 总结

  • "反向"=答案先于题目:先用冻死口径的确定性标尺函数(oracle)把答案算死,再倒着套题面模板生成问题。这样答案天然正确、可批量造上万道,彻底绕开人工出题的瓶颈。

Q5

用 LLM 当裁判有哪些坑?(自由文本的集合 / 排序题判分、裁判抽取抖动)你怎么治?

★★★★☆
LLM-judge 抽取判分 集合/排序题 裁判抖动 确定性容差

🎯 考察点分析

这道题探的是:你是不是真的拿 LLM 当过判分器、并被它坑过。很多人以为「用大模型给答案打分」就是把答案丢进去让它说对不对——真上手就会发现两类坑:自由文本的集合 / 排序题判分(模型答案是一段话,不是一个能直接比对的结构),和裁判自己不稳(同一份答案判两次,边界情况结论会变)。一个好的回答会点出:能用确定性方法判的,就别让 LLM 沾手;只在「自由文本 → 结构」这一跳上用 LLM,而且用它当抽取器、不当打分器。

  • 追问:数值题(比如「涨幅是多少」)你为什么不用 LLM 判、而用确定性容差?哪些题型才轮得到 LLM?
  • 追问:集合题里「模型在分析中提到了茅台」和「模型把茅台选进了答案」怎么区分?正则判分为什么会把两者混为一谈?
  • 追问:裁判抖动你怎么量化、怎么压下去?

📚 原理讲解

先分清题型,判分方式完全不同。数值题(单值结果,如涨幅、最大回撤)答案是一个数,直接用确定性容差比对(相对误差是否在阈值内),压根不需要 LLM。需要 LLM 的只有一类:答案是自由文本、但要比对的是结构——比如「从这几只里挑出涨幅最高的 3 只」(集合题),或「按估值便宜程度排序」(排序题)。模型会用一整段话回答,你要从这段话里弄清楚它到底选了哪些、排成什么序,才能和标准答案比。

坑一:正则/字符串匹配判集合——把「提到」当「选中」

最朴素的做法是拿标准答案里的股票名去模型回答里做字符串匹配:匹配上就算「选中」。问题是模型回答里会顺带提到很多没被选中的名字——「五粮液、洋河也值得关注,但综合看我选茅台和泸州老窖」。正则一扫,五粮液、洋河全被算成「选中」,集合直接判错。实测这类题在正则判分下几乎全崩(集合题约 0/9 通过,量级数据)——不是模型不会做,是判分器读不懂「提到 ≠ 选中」。

坑二:裁判抖动——同一答案判两次结论不一样

把判分这一跳交给 LLM 后,它本身有随机性:边界情况(模型措辞含糊、选了 4 个但标准答案是 3 个)下,同一份答案判两次可能给出不同结论。这类裁判抖动是残留误差的一个来源(约 1 例量级),不是模型能力问题,是判分器自己的噪声。

💡 关键:别让 LLM 既「读懂答案」又「决定对错」。把它的职责缩小到只做一件事——把自由文本抽成结构(它到底选了 {茅台, 泸州老窖}),然后用确定性代码拿这个结构和标准答案比。理解语言交给 LLM,判对错交给不会抖的代码。
治法:LLM 当抽取器,不当打分器

判分拆成两步:① 让 LLM 从模型回答里抽出「最终选定集合 / 排序」这个结构;② 用确定性逻辑(集合相等 / 排序距离)拿抽出来的结构和标准答案比。这一改,集合题从约 0/9 拉到约 7/9(量级数据)。抖动则靠收紧抽取提示(明确「只要最终选定的,不要提到的」)和必要时多次采样取多数来压。

💻 示例讲解

对比两种判分(教学伪代码,只看逻辑)。模型回答是一段话,标准答案是集合 {茅台, 泸州老窖}。

# ❌ 正则判分:拿标准答案的名字去回答里做字符串匹配
answer = "五粮液、洋河也值得关注，但综合看我选 茅台 和 泸州老窖。"
picked = {name for name in 候选股票 if name in answer}   # 只要文本里出现就算选中
# picked = {五粮液, 洋河, 茅台, 泸州老窖} —— "提到" 被误当 "选中"
score = (picked == gold_set)                              # 判错：多了五粮液、洋河

# ✅ LLM 抽取判分：先让 LLM 把"最终选定"抽成结构，再用确定性逻辑比
selected = llm_extract(answer, 问题)   # LLM 只干一件事：读懂这段话最终选了谁
# selected = {茅台, 泸州老窖}          # "提到的" 不算，只要 "选定的"
score = (set(selected) == gold_set)    # 确定性比对：判对

推演:同一批集合题,判分方式一换,通过率从约 0/9 跳到约 7/9(量级数据)——提升的全是「判分器的理解力」,模型答案一个字没改。排序题同理:LLM 抽出有序列表,再用确定性的排序距离打分。数值题则全程不碰 LLM,只用相对误差容差。

可复现抽取那一跳需收紧提示压抖动完全可复现 ✓(它的真实优点)
适用题型集合 / 排序(自由文本→结构)数值题、精确字符串匹配够用

公允裁决:正则判分不是稻草人——它确定、零成本、完全可复现,数值题和「答案就是一个精确串」的场景它完全够用,我们的数值桶判分本来就是纯确定性容差、根本不上 LLM。它唯一的死穴是读不懂自由文本里「提到 ≠ 选中」,所以一碰到集合 / 排序这种「答案是一段话、要比的是结构」的题就系统性崩盘。我们的选择不是「用 LLM 取代它」,而是只在「自由文本 → 结构」这一跳借一下 LLM 的理解力,判对错仍然交回确定性代码——既拿回了准确度,又把 LLM 的不确定性圈在最小范围里。

🖼️ 图解

📌 总结

  • 先按题型分流:数值题用确定性容差判,完全不上 LLM;只有集合 / 排序这种「自由文本 → 结构」才需要 LLM 那一跳。
  • 正则判集合的死穴:把分析里「提到」的名字当成「选中」,集合题系统性崩(约 0/9)。
  • 治法是缩小 LLM 职责:让它当抽取器(读出最终选定的结构),不当打分器;判对错交回确定性代码 → 约 7/9。
  • 裁判抖动单列:边界 case 判两次会变,靠收紧抽取提示 + 必要时多次采样取多数压噪声。

一句话速记:能确定性判的别给 LLM;非用不可时,只让它把自由文本抽成结构,判对错仍交回不会抖的代码——集合题就是这么从 0/9 回到 7/9 的。

Q6

尽调报告质量评估:5 个指标 + 多版本消融控制变量。为什么要做消融?

★★★★☆
尽调报告评估5 指标分层消融实验控制变量真股价回测

🎯 考察点分析

这道题问的是「尽调报告」——系统给一只股票写一份几千字的投资分析报告,里面有引用、有财务数字、有风险判断、还有「该不该买、目标价多少」的结论。面试官想看你能不能把这么一个又长又主观的产物,拆成可量化、可归因的评估,而不是糊一个「LLM 打 8 分」就交差。重点不在「能列出 5 个指标」,而在第二步:你改了系统里某个模块,怎么知道是它的功劳?这就是「消融(ablation)」要回答的问题。

  • 追问:你已经有 5 个指标了,为什么还要跑 4 个版本?一个版本算一遍 5 个指标不就知道好坏了吗?
  • 追问:消融就是「关掉一个模块再测一次」——这跟科学实验里的「控制变量法」是不是一回事?为什么一次只能关一个?
  • 追问:如果你的某个指标有 bug,会让消融结论完全反过来吗?举个你真撞到的例子。
  • 追问:「预测准不准」你怎么客观判?报告说「看涨、目标价 30~35 元」,你拿什么当标准答案?

📚 原理讲解

先说评什么。一份尽调报告不是铁板一块,它有三个性质完全不同的部分,得用三种不同的尺子量(这套「按段分层」的思路借鉴了 Hebbia 的分层评估):

  • 抽取段(报告里「事实/数字」抄得对不对)——这部分有标准答案,可以程序化判。指标一(引用指标)看每句结论有没有真凭实据撑着:引用的资料确实支持这句话吗(精确率)、该写的章节都给了证据吗(覆盖率),两者取调和平均(F1)。指标二(数值指标)把报告里的财务数字抓出来,跟数据源对,允许 ±1% 的误差;还要把「三千万」这种中文写法归一成数字再比。
  • 总结段(风险讲得到不到位)——指标三(风险配对指标)。光列风险不算本事,关键是每个风险有没有配上一条有效的缓释措施。这个没法纯程序判,得请一个大模型当裁判,按四类风险桶逐个看「风险—缓释」是否成对、缓释是否真有效。
  • 推理段(结论靠不靠谱)——这是最硬的。指标四(预测指标)不靠裁判嘴下结论,而是等未来真实股价来揭晓:在报告的「截断时间点」之后取真实 K 线和公告当标准答案,默认看 90 天,判方向对不对、目标价区间有没有被触及、提示的风险旗标后来真出事的比例。指标五(综合裁判指标)用 3 个大模型分别打分再多数表决,谁跟大家差太远就记一笔分歧审计。
为什么光有 5 个指标还不够——总分能告诉你「好坏」,不能告诉你「谁的功劳」

假设你把这 5 个指标在系统上跑一遍,得到一行分数。现在你想知道:知识库(检索增强)到底帮了多少?那个反复审稿、打回重写的「评论家」模块,值不值这份算力?一行总分回答不了。因为总分是所有模块共同作用的结果,你看不到哪一格是谁贡献的。更糟的是:你把检索关掉再测,分数掉了 0.1——这 0.1 是检索的锅,还是这次跑的随机噪声?你根本分不清。

消融 = 控制变量法搬到系统评估上

消融的做法跟中学物理的控制变量法一模一样:一次只动一个开关,其余全部按住不动,看指标变化多少,就把这个差异归因到这个被动的开关上。本系统做了四个版本:基线版是完整的真系统(5 个智能体 + 7 个打分器 + 评论家);第二版只关检索(换成空知识库);第三版只关多智能体(换成单个智能体一把梭);第四版只关评论家(换成一个永远盖章通过的空评论家)。关键是生产代码一行不改,靠一个「管道工厂」按开关装配出不同版本。

这样一来,关掉检索后引用指标、数值指标各掉多少,就量化了知识库的边际贡献;关掉评论家后预测指标掉多少,就证明了那个反复审稿的模块到底值不值。「下降幅度」本身就是归因。

一个隐藏的前提:指标自己不能有「悄悄送分」的 bug

消融对比成立有个铁前提——指标必须诚实。如果某个指标在「该得 0 分」时悄悄返了满分,那你关掉一个模块、分数没怎么动,你会误判「这模块没用」,其实是指标根本没在量它。这不是假设,是真撞到的坑(见示例)。所以做消融的人,一半精力花在设计变体上,另一半花在堵住指标的虚高漏洞上。

💻 示例讲解

先看消融循环长什么样——核心就一句话:同一批案例,跑四遍,每遍只拨一个开关。

# 四个版本:每个版本只关掉一个模块,其余按住不动
变体清单 = {
    "V0 基线":    全开,                  # 真系统:5 智能体 + 7 打分器 + 评论家
    "V1 关检索":  把知识库换成「空知识库」,  # 只关这一个,别的不动
    "V2 关多体":  把多智能体换成「单体一把梭」,
    "V3 关评审":  把评论家换成「永远盖章通过」,
}

结果表 = {}
for 版本名, 如何装配 in 变体清单.items():
    系统 = 管道工厂.装配(如何装配)        # 生产代码 0 改动,只换装配
    本版本五项分 = []
    for 案例 in 同一批尽调案例:           # 关键:四个版本跑「同一批」案例
        报告 = 系统.写尽调报告(案例.股票)
        本版本五项分.append(打五项分(报告, 案例))  # M1~M5
    结果表[版本名] = 平均(本版本五项分)

# 归因:看每一格相对基线掉了多少
检索的贡献 = 结果表["V0 基线"]["引用指标"] - 结果表["V1 关检索"]["引用指标"]
评审的贡献 = 结果表["V0 基线"]["预测指标"] - 结果表["V3 关评审"]["预测指标"]

再看那个让消融「假成立」的真实 bug——它正是为什么指标必须先诚实、消融才有意义:

# ❌ 错的写法:数值指标在「该得 0 分」时悄悄变满分
分数 = (m.value if m else 1.0) or 1.0
# 陷阱:当 m.value == 0.0(真的全错)时,0.0 是「假值」,
#       `0.0 or 1.0` 会短路返回 1.0 —— 该 0 分的案例拿了满分!
# 后果:你关掉检索、分数纹丝不动,误以为「检索没用」,
#       其实是指标根本没在量,虚高把差异吃掉了。

# ✅ 修法:显式判 None,别让 0.0 被当成「没有值」
分数 = m.value if m is not None else 默认值

还有一个更隐蔽的、专门破坏消融的坑:引用覆盖率的分母。早期用「报告里实际写了的章节数」当分母——可「关多智能体」的简化版报告本来就少写了几个章节,分母跟着变小,覆盖率反而虚高。修法是把分母钉死成「本该写的 6 个章节」(固定 len(section_paths)),被砍掉的章节就老老实实记 0,消融对比才不被骗。

推演:假设基线版引用指标 0.82、数值指标 0.90;关掉检索后引用降到 0.55、数值降到 0.74。差值 0.27 和 0.16 就是知识库对「引用得有据、数字抄得对」的边际贡献,有理有据。但如果数值指标带着上面那个虚高 bug,关检索后它仍显示 0.90——你会得出「知识库对数值没帮助」的完全相反的错误结论。这就是为什么:消融实验的可信度,先由指标的诚实度决定。

⚖️ 决策对比

维度我们的选择:消融控制变量(4 版本 × 5 指标)替代方案:只打一个总分
能回答的问题好坏 + 谁的功劳(哪个模块出力多少)只有好坏,无法归因到模块
改了组件之后分数变化能定位到被改的那个开关分数变了,不知是它的功劳还是随机噪声
简历/汇报价值「检索贡献 +0.27、评论家贡献 +X」有数说话「系统得 8 分」——下次面试官追问就卡壳
实验成本要跑 4 倍实验(4 变体 × 同批案例)只跑 1 遍,便宜
对指标质量的要求极高:任一指标虚高,结论可能反转(见示例两 bug)低:反正只看一个粗略总分

公允裁决:「只打一个总分」绝不是稻草人——它便宜、快、上线监控只想知道「今天报告质量有没有崩」时完全够用,我们线上看板就该用它。它真正的短板只在一个场景下致命:当你要做架构决策、要回答「这个模块值不值得保留」时,总分给不出归因,你只能拍脑袋。我们仍选消融,是因为这恰恰是研发期最值钱的问题——证明知识库、多智能体、评论家各自的边际价值,是这个项目「技术深度」的核心证据。代价我们认:4 倍算力、外加必须先把每个指标的「悄悄送分」漏洞堵死(否则对比直接失真)。换句话说,总分是终点的体检,消融是研发期的解剖。

🖼️ 图解

📌 总结

  • 5 指标按段分层:抽取段(引用 F1 + 数值 ±1%)有标准答案、程序化判;总结段(风险配对)请大模型裁判;推理段(预测靠真股价回测 + 综合多裁判表决)。三种性质用三把不同的尺子。
  • 消融 = 控制变量法:一行总分只告诉你「好或坏」,无法归因到模块;消融一次只关一个开关,把指标下降量归因到具体组件——下降幅度本身就是边际贡献。
  • 生产代码 0 改动:四个版本靠「管道工厂」按开关装配(空知识库 / 单体一把梭 / 永远盖章的空评论家),不污染生产系统,消融才可复现。
  • 指标必须先诚实:「0.0 短路成满分」「分母用实写章节数而非应写章节数」两个真 bug 都会让被砍模块虚高,导致消融结论反转——做消融的一半精力在堵指标虚高漏洞。
  • 预测段不靠裁判嘴:M4 等未来真实股价揭晓,目标价命中谓词必须严格区间包含(low≤h≤high),曾有 bug 让破上界也算命中。

一句话速记:总分是体检报告(知道好坏),消融是解剖刀(一次切一刀,才知道哪个器官在出力)——但解剖前得先保证尺子不偷偷送分。

Q7

记忆对话评估:双层断言体系怎么搭?首次跑就抓出 5 个系统级 bug(生产抽取从未工作、图数据库毒事务等),这说明了什么?

★★★★★
记忆评估双层断言过程轨迹毒事务口语台词

🎯 考察点分析

这道题问的是一个很难评的东西:长期记忆。系统跟用户聊很多次,要记住「这个人三年前看多白酒、后来改口转中性」,下次他随口一问「我对白酒什么看法」,系统得答对、还得说出当初的逻辑和为什么放弃。怎么给这种「记没记住、记得对不对」打分?面试官想看的不是你能不能跑出一个分数,而是:当分数红了,你能不能说清楚是哪个环节坏了。这道题的题眼藏在后半句——「首次跑就抓出 5 个系统级 bug」。一个评估体系第一次开机就照出五处生产级的暗病(其中两处是「生产路径其实从来没工作过」),这本身就是对「评估体系该怎么设计」的最强论证。

  • 追问:你只看「数据库最后状态对不对」不就行了吗?为什么还要插一层「过程轨迹」断言?多写一层不是更累?
  • 追问:「生产抽取从未工作过」这种 bug,为什么以前所有测试都没抓到?是测试写得不够多吗?
  • 追问:读侧全红的时候,你怎么知道是「检索没召回」还是「记答错了」?这两个怎么区分?
  • 追问:你说测试台词必须用「真实散户口语」,这跟评估质量有什么关系?举个口语门控的具体漏洞。

📚 原理讲解

先把场景说清楚。一段评估脚本是一串多次对话(白酒观点演化:9 次对话,3 次埋有效信息「看多三年 → 改两年 → 转中性」,6 次是干扰噪声)。系统每次对话后会把内容「抽取」成记忆,存进一个图数据库(谁、对什么、持什么观点、什么时候)。聊完之后再向系统提问,看它答得对不对。整条流水线分两段:写阶段(把对话喂进去、抽成记忆)和读阶段(提问时检索记忆、生成回答)。

第一层:终态断言 —— 数据库最后长成什么样,对不对

写完之后直接查库,用 6 种确定性断言(零大模型参与,完全可复现)逐条验:① 新观点生效(「转中性」那条边现在是 active 的);② 旧观点作废(「看多」那条被打上失效);③ 版本链可溯(看多三年 → 看多两年 → 中性,三个版本都还在,作废 ≠ 删除,历史得能回看);④ 数量没虚增(重复提同一件事不该多长出一条边);⑤ 生效时间是事件时间(「我四月改主意了」要记成 4 月,不能记成今天录入的时间);⑥ 不该写的没写(持仓成本这种信息不归记忆管,库里不该出现)。这一层回答的是「最终状态对不对」。

第二层:过程轨迹断言 —— 流水线每一步到底跑没跑、召回没召回

光看终态有个致命盲区:分数红了,你不知道是哪一步坏的。所以第二层在流水线沿途插探针,像给病人插一排监护仪:写阶段看「口语门有没有放行这句话」「抽取这一步成功没」「图数据库那笔事务有没有被毒死」;读阶段看「检索到底召回了几条、召回了没」。这一层回答的是「过程哪一步出的事」。

首段脚本端到端冒烟 6 轮迭代后的结果是:写侧断言 5/8 绿(知识更新链路证明能工作:中性版生效 ✓、旧版作废 ✓、四版本链可溯 ✓),读侧全红。光看终态分,你只知道「读这边崩了」;但叠上轨迹层,病灶被精确锁死在检索层——召回探针显示一条都没召回到。只断终态,你永远定位不到这一层。

为什么首跑就抓出 5 个 bug —— mock 是一块「盖在死器官上的布」

这五个 bug 里,最刺眼的是两个「生产路径从来没工作过」:

  • 抽取层在真实大模型下从未成功:抽取代码用 chat(system=...) 这种调用方式,跟真实大模型服务的接口签名根本对不上,一调就报类型错误。可为什么以前没人发现?因为以前所有测试都用「录音回放」(cassette / mock)替身——录音里抽取「成功」是假象,真实大模型一上场立刻崩。生产那条批量抽取链路,在真实大模型下从来没成功跑通过一次。
  • 图数据库在生产里从未工作:生产库根本没装图扩展(AGE),镜像里也装不上——那条「把记忆同步进图」的路径生产环境从未真跑过。更阴的是另一个连带 bug:图查询失败会「毒死」整笔数据库事务(事务进入 aborted 状态),这时你在 Python 里 try/except 接住异常也救不回来,事务已经死了,后续所有写入全废——号称的「best-effort 尽力而为」名存实亡。修法是用 SAVEPOINT(子事务存档点)把图操作圈起来,失败只回滚到存档点,不毒死主事务。

另外三个:口语门白名单全是书面语,真实散户口语(「看多/转中性/割肉」)被静默跳过;向量批量形态和检索接口漂移;以及上面那两条的连带。结论很硬:cassette / mock 会系统性地掩盖「生产路径从未工作」,只有用接近真实的端到端栈 + 真实数据,这些死器官才会现形。这也是为什么测试台词必须用真实散户口语(项目里专门有个「散户口音」技能产语料、反 AI 腔)——你拿书面语去测,永远测不出口语门控的漏洞;口语台词一上,门控漏杀立刻暴露。

轨迹层还是「防躺赢」的关键 —— 弃答题会在检索全空时蒙混过关

有一类题是「弃答题」:正确行为是「我没跟你聊过这个,我没有这个信息」。现在检索层全坏、一条都召不回来——这时候系统因为什么都没检索到,反而「正确地」拒答了,弃答题白捡一分。如果你只看终态分,会被这分误导成「系统表现还行」。所以解读分数必须连着「检索健康度」一起看:轨迹层告诉你检索其实是空的,这分是躺赢来的,不算数。这就是终态层单独看会误诊、必须配轨迹层的硬证据。

评估的标准答案会随实时行情漂移、而且"复权 ≠ 价格回报"——这两个口径坑你是怎么发现并钉死的?

★★★★☆
gold 漂移复权口径可复现诊断纪律基准方法论

🎯 考察点分析

这道题问的不是某段代码怎么写,而是你有没有踩过"基准本身不可靠"这种最阴险的坑、又是怎么爬出来的。我们做了一套"反向出题"的金融计算评估:系统先用真行情数据自己算出标准答案(行话叫 gold,就是"金标准答案"),再把同一道题丢给被测的 AI 助手去算,两边一比就知道助手算得对不对(这套出题与判分机制本身,见本类第 4 题)。麻烦在于:gold 是用实时行情算的,而行情每天在动——于是你某天会看到一整批题的通过率突然崩盘。面试官想看的是:当 pass 率突然掉一截,你的第一反应是疑模型/疑代码,还是先怀疑"是不是我的标准答案自己飘了"?这考的是诊断纪律和对"基准可复现性"的敏感度。

  • 追问:通过率整桶崩,你怎么区分"是助手退步了"还是"是标准答案飘了"?具体怎么自证?
  • 追问:"复权"和"价格回报"差在哪?为什么混用会让你系统性判错一类股票?
  • 追问:有些股票在不复权下会显示"假暴跌",你为什么不靠改口径去修,而是直接换股?
  • 追问:一句话:基准的第一要务是"最新"还是"可复现"?为什么?

📚 原理讲解

两个坑表面无关,根子是同一个:基准里凡是"会动的输入",只要没冻死,算出来的标准答案就不可复现。一是时间在动,二是口径(同一个数有两种定义)没钉死。逐个拆。

坑一:标准答案随实时行情漂移

反向出题时,系统拿一段时间窗(比如"过去一年")的真实行情去算"这只股票涨了多少 / 最大回撤多少 / 年化多少",这个结果就是 gold。问题是我们当时把窗口的结尾设成"今天",数据走的是实时行情接口。这里藏着两个会让 gold 明天就变的因素:

  • 窗口结尾的那根"今天 K 线"还没落定:当天的收盘价、涨跌幅在盘中是浮动的,你今天算 gold 用的就是一个还在跳的数;
  • 数据接口会回填近几天:行情源(tushare)对最近几天的数据有补录/修正延迟,过两天再拉,近端几根 K 线的数值会被悄悄改掉。

结果就是:gold 一旦算出来落盘,从那一刻起就开始过期——同一道题,今天的标准答案和六天后的标准答案能差出去。这不是模型的问题,是基准自己飘了。

是怎么被抓出来的:一整桶通过率"假性崩盘"

不是事先想到的,是被现象逼出来的:某次跑评估,"涨幅"这一类题的通过率突然从 31/45 掉到 6/45。直觉会让你先疑"是不是助手退步了 / 是不是代码改回归了"。但真去翻一道具体的题:助手答的是 -23.30%,而当初落盘的旧 gold 是 -22.98%,判它错。可你用当下的数据重新算一遍 gold,得到的恰恰就是 -23.30%——助手算得分毫不差,是被那个六天前冻结、如今已经过期的标准答案误判了。一查全集:6 天里 141 道题中有 57 道标量型 gold 漂移超过 0.5%(涨幅 39 道、CAGR 12 道、回撤 4 道),整桶 pass 率是被这批漂移"假性击穿"的。

坑二:复权 ≠ 价格回报(同一个"涨幅"有两种定义)

算"一只股票涨了多少",看着只有一种答案,其实有两种口径,差一个股息率:

  • 不复权收盘价比值 = 价格回报:就是"期末价 ÷ 期初价 − 1",纯看股价本身涨了多少。这跟被测助手自然会用的算法是一致的。
  • 涨跌幅累乘 = 含分红再投的总回报:把每天的涨跌幅连乘起来,这个口径默认你把分红又买回了股票,所以会比价格回报高出一个股息率(实测工商银行高 6.87 个百分点,茅台/五粮液约 3.3 个百分点)。

两种都对,但不能混:如果标准答案用总回报、被测助手用价格回报,那么每一只分红股都会被系统性地判偏一个股息率——分红越高的票偏得越狠。

这个坑是怎么踩进去的:为修一个真问题、引入一个更大的问题

起因是个真 bug:有些股票做过拆股(比如 1 股拆成 3 股,股价当天就变成原来的三分之一),在"不复权收盘价"下会显示成一根"假暴跌的悬崖"。为了修这个,当时把口径改成了"涨跌幅累乘"的复权路径——拆股是修好了,但顺手把几乎所有分红股都错开了一个股息率,一条基线分数从 125 崩到 78。更要命的是:没有干净的办法只修拆股、不动分红——行情源的前/后复权是把拆股和分红一起调的,你一复权就同时变成了总回报。

两个坑的共同正解:把会动的输入全冻死

时间维度:把窗口结尾的 as_of 从"今天"钉到一个已经落定的历史交易日(实操钉到两周前的某个交易日),窗口里就不含还在跳的近端 K 线、也躲开了回填延迟,gold 一次算定、永久可复现。口径维度:坚持用"不复权收盘价比值",和被测助手对齐;拆股这个真问题用换股解决——把题池里唯一那只拆股票直接换成一只没拆过的同类股,而不是去改口径。一句话:基准的第一要务是可复现,不是最新、也不是最"完整"。

# 「涨幅」有两种口径,差一个股息率 —— 评估必须和被测助手用同一种
def price_return(close):
    # 不复权收盘价比值 = 价格回报(被测助手自然就这么算,标准答案也用它)
    return close[-1] / close[0] - 1

def total_return(pct_chg):
    # 涨跌幅累乘 = 含分红再投的总回报;比价格回报高一个股息率
    r = 1.0
    for x in pct_chg:        # 误用它当 gold,会把每只分红股判偏(工行差 6.87pp)
        r *= (1 + x / 100)
    return r - 1

# 拆股 vs 分红:看「收盘价比值的单日变动」和「当日涨跌幅」背离多大
def looks_like_split(close, pct_chg):
    for i in range(1, len(close)):
        price_move = close[i] / close[i - 1] - 1          # 不复权口径看到的「跌幅」
        divergence = abs(price_move * 100 - pct_chg[i])   # 与真实涨跌幅的背离

            return True            # 这只票拆过股 → 直接从题池换掉,而不是改口径
    return False

推演:① 漂移诊断——拿那道答 -23.30% 被判错的题重算 gold,新 gold = -23.30%、旧 gold = -22.98%,差 0.32pp 但够把它判错;全集 57/141 道漂移,于是确认涨幅桶 31/45→6/45 是假性崩盘,根因在 as_of=今天,改钉 20260612 后整桶恢复。② 拆股识别——题池里唯一的拆股票是比亚迪(002594),拆股当日"收盘价比值"显示暴跌约 67%、而真实涨跌幅只有零点几,背离 67% ≫ 15% 阈值,判定为拆股,换成没拆过的隆基绿能(601012),其最大单日背离仅 1.3%(那是分红),口径一致性恢复,基线从被错改时的 78 回到 125。

⚖️ 决策对比

维度我们的选择:钉死历史交易日 + 不复权价格回报替代方案:基准日取今天;复权口径(总回报)
时效性窗口结尾是两周前的交易日,数据"旧"一点as_of=今天最新鲜,反映此刻行情
可复现性窗口不含还在动的近端 K 线,gold 一次算定、永久可复现近端 bar 未落定 + 接口回填,gold 每天漂、不可复现
误判风险助手算对就判对,基准不会反咬助手答 -23.30% 等于 fresh gold,却被旧 gold -22.98% 判错
口径"完整性"价格回报不含分红,理论上"少了一块"总回报含分红再投,理论上更完整
与被测对齐和助手自然算法(不复权比值)同口径,可比比助手多一个股息率,系统性偏(工行 6.87pp)
拆股这个真问题用"换股"解决(比亚迪→隆基绿能),不碰口径改成复权能修拆股,但顺带错开所有分红股(基线 125→78)

公允裁决:替代方案不是稻草人,两条都有真实理由。"取今天"确实最新鲜——一个面向投资者的产品,用最新行情出题听起来天经地义;"复权总回报"在金融上也确实更"完整",它把分红再投也算进了收益,衡量"持有这只股票真正赚了多少"时它才是对的口径。我们之所以仍然不这么选,是因为这里要的是 benchmark,不是研报:基准的第一要务是"同一道题今天明天算出来一样",可复现性高于一切——一个会飘的标准答案,会让算对的模型被冤判、让你把假性崩盘误当成回归去瞎查代码,这比"旧两周"危害大得多。口径同理:总回报本身没错,但基准只要求和被测对象口径一致,被测助手算的是价格回报,那我的标准答案也必须算价格回报,谁更"完整"在这里不重要、对齐才重要。而拆股那个真问题,我们没有用"改口径"这种会牵连分红的重武器,而是用"换一只没拆过的同类股"这种外科手术解决——能用换数据解决的,绝不动会污染全局的口径。

📌 总结

  • 基准飘比模型退步更阴险:用"今天 + 实时行情"算的标准答案会每天漂(近端 K 线未落定 + 接口回填),6 天里 141 道有 57 道漂移,把涨幅桶 pass 率从 31/45 假性击穿到 6/45,助手其实答对了。
  • 诊断纪律:桶崩先疑基准:整桶通过率突然崩,第一件事是用当下数据重算 gold 跟落盘值比漂移,确认不是"自己飘了"再去疑代码——别一上来查回归。
  • 复权 ≠ 价格回报,差一个股息率:"涨跌幅累乘"是含分红的总回报,"不复权比值"是价格回报,工行差 6.87pp;评估必须和被测助手同口径,混用会系统性偏。
  • 真问题用换数据解,别用改口径:拆股的"假暴跌"是真问题,但改复权会牵连所有分红股(基线 125→78);改成"换一只没拆过的同类股"(比亚迪→隆基绿能)外科手术解决。
  • 可复现 > 最新 > 完整:把所有会动的输入冻死(时间冻成历史交易日、口径冻成一种定义并写进题面),是 benchmark 的方法论底线。

一句话速记:会飘的标准答案会冤判算对的模型——时间冻成历史交易日、口径冻成不复权价格回报,基准的第一要务是可复现。
