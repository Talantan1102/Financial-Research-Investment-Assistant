Q1

为什么要从 SQLite / 多数据库变体统一迁到全 PostgreSQL?迁移过程踩了什么?

★★★☆☆
数据库迁移PostgreSQL运维收敛测试夹具SQL 注入

🎯 考察点分析

这道题表面问"为什么换数据库",其实面试官在探的是工程收敛意识——你能不能识别出"维护两套并行的东西"是一笔长期利息,并且舍得花一次性成本把它一笔还清。很多人会觉得"测试用轻量的 SQLite、生产用 PG"是省事的标准做法,面试官想看你有没有意识到这里藏着一个昂贵的盲区:测试绿了不代表生产绿。具体盯三件事:

  • 追问 1:双轨到底贵在哪?——逼你说清不是"多维护一个文件"这么浅,而是类型系统、索引、并发语义三套东西都得各验一遍。
  • 追问 2:你怎么证明迁干净了,而不是"我觉得改完了"?——看你有没有把验收做成可机器判定的硬门槛,而不是靠肉眼 review。
  • 追问 3:迁移这么大,你怎么切的?一把梭还是分批?——考你有没有把不可逆的大改造拆成可回滚的小步。
  • 追问 4:迁的过程顺手发现别的问题了吗?——好的候选会讲出"重写老代码时撞见一个真实漏洞",这比"按计划执行"更可信。

📚 原理讲解

先解释背景。这个项目早期是个常见的省事配置:跑测试时连一个 SQLite(就是一个本地文件当数据库,零安装、跑完即删,本地开发很方便),真正上线时连 PostgreSQL(一个需要单独启动的、功能完整的数据库服务)。同一套数据表定义(我们叫 ORM model,就是用 Python 类描述"这张表有哪些列、什么类型")要同时能在这两个数据库上跑。问题是这两个数据库长得并不一样。

双轨真正的成本:三套语义各验一遍

表面看双轨只是"多一个文件",真实代价藏在三个地方,每个改动都要在两边各对一遍:

  • 类型对不上:PG 有原生的 UUID 类型(一种全球唯一的 ID)、JSONB(能高效查询的 JSON 列)、ARRAY(数组列);SQLite 这几样都没有,只能拿普通字符串、普通文本去凑。
  • 索引对不上:PG 给 JSONB 列建的那种特殊索引(GIN 索引,让你能快速搜 JSON 里的字段),在 SQLite 上根本不生效。你在测试里建的索引是个摆设,查询慢不慢测试根本看不出来。
  • 并发对不上:PG 用的是 MVCC(多版本并发控制,简单说就是"多人同时读写互不阻塞,各看各的快照");SQLite 是粗暴的"同一时刻只允许一个人写"。任何只在真并发下才暴露的 bug,SQLite 这一关永远拦不住。

这三条合起来就是一句要命的话:SQLite 不报的错,生产才暴雷。类型不兼容、索引没生效、并发竞态——这些在本地测试全绿,推上去才炸。你以为测试是安全网,其实它在这些维度上根本没张网。

最显眼的技术债:30+ 处类型分叉

为了让同一套 model 在 SQLite 上也能跑,代码里每一个 UUID 列都得挂一句"退化声明":在 PG 上用原生 UUID,在 SQLite 上退回成一个 36 位长的普通字符串(SQLAlchemy 里写作 with_variant(String(36), "sqlite"))。JSONB 列同理要退化成普通 JSON。全项目这种分叉有 30 多处,纯粹是为了迁就 SQLite 而存在的噪音——它不提供任何业务价值,只是双轨这个决定收的"利息"。

怎么迁:分四批,而不是一把梭

这么大的改造没有一次性掀桌,而是拆成四批可独立合入、可独立回滚的改动,按"碰得越多越优先"的顺序推:第一批删掉主 model 上全部类型分叉,同时把核心测试夹具从内存 SQLite 切到真 PG;第二批把两个早年用 sqlite3 裸接口手写 SQL 的子系统(链路追踪 trace_service、评估记录 eval_recorder)重写成走 ORM + PG;后两批清扫横切的边角料——tushare 行情缓存、配额计数器,以及对话引擎里残留的 SQLite 检查点存储。每一批都自带"这一批必须全绿、跟主干零回归"的验收,绝不积压。

一个故意不做的决定:暂不引 alembic

迁移期间明确约定先不引入数据库迁移工具 alembic(那是后续"DB 大统一"才做的事),表结构就靠启动时跑一遍 Base.metadata.create_all() 幂等建表("幂等"=表已存在就跳过,反复跑也不出错)。理由是这阶段只加表、不改字段,引 alembic 反而要先写一份空白基线、把工时翻倍。这是个克制的取舍:一次只收敛一条线,别顺手把范围撑大。

💻 示例讲解

第一段代码对照"迁移前后,同一个 UUID 列长什么样"——核心就是把那句迁就 SQLite 的分叉删掉:

# 迁移前:同一个 model 要同时讨好两个数据库
class EscalationRecord(Base):
    # PG 上用原生 UUID,但 SQLite 没有 UUID 类型,
    # 只好退化成 36 位字符串 —— 这句 with_variant 就是"双轨利息"
    id = Column(
        UUID(as_uuid=True).with_variant(String(36), "sqlite"),  # ← 噪音
        primary_key=True,
    )
    payload = Column(JSONB().with_variant(JSON, "sqlite"))       # ← 同款噪音

# 迁移后:只剩 PG 一套类型,model 回归干净
class EscalationRecord(Base):
    id = Column(UUID(as_uuid=True), primary_key=True)            # 纯 PG 类型
    payload = Column(JSONB())                                    # 纯 PG 类型

# 验收不靠肉眼,靠一行能机器判定的命令:
#   grep -rn with_variant backend/app   必须等于 0
#   —— 只要还剩一处分叉,这道闸就拦下,不许说"迁完了"

第二段是迁移第二批顺手修掉的一个真实漏洞。老代码把外部传进来的过滤条件直接拼进 SQL,等于把数据库大门钥匙交给调用方;重写成 ORM 时,加了一道白名单先把门锁上:

# 重写前(裸 sqlite3 拼 SQL):调用方传什么 key,就拼进 WHERE
#   filters = {"name": "x"} 还好,但 filters 的 key 不受控,
#   一旦 key 里夹带 SQL 片段 → 注入,等于把库交出去

# 重写后:先用白名单卡住"只允许这几个声明过的列名"
_ALLOWED_FILTER_KEYS = frozenset({"span_id", "request_id", "name", ...})

def query_spans(self, filters: dict) -> list[Span]:
    # 任何没在白名单里的 key,直接拒绝,根本不让它碰到 SQL
    unknown = set(filters) - _ALLOWED_FILTER_KEYS
    if unknown:
        raise ValueError(f"unknown filter keys: {sorted(unknown)}")
    stmt = session.query(TraceSpanRow)
    for k, v in filters.items():
        # 走 ORM 的列对象做等值过滤,值被参数化绑定,不再字符串拼接
        stmt = stmt.filter(getattr(TraceSpanRow, k) == v)
    return [self._row_to_span(r) for r in stmt.all()]

推演:第一批 PR 的体量——删掉 30+ 处类型分叉、19 个单元测试文件改用连真 PG 的 db_session 夹具、跑通 1100+ 个后端单测且跟主干零回归,整批墙上时间约 1.5 天 / 14 个 task。最关键的是那道验收闸:迁完后 grep -rn with_variant backend/app 的计数从 30 多归零,这是个机器能判定真假的硬证据,不是"我觉得改干净了"。这个数字今天去仓里 grep 仍然是 0,说明这条线收敛后再没回潮。

⚖️ 决策对比

维度我们的选择:全 PostgreSQL替代方案:SQLite 测试 + PG 生产双轨
本地起测试门槛需要一个 docker 起的 PG(多一个依赖)零依赖,clone 下来就能跑测试
测试可信度测试环境=生产真值,绿了基本就是绿类型/索引/并发错误测试不报,生产才暴雷
model 代码纯 PG 类型,干净每个 UUID/JSONB 列都挂一句退化分叉(30+ 处噪音)
每次改 schema 的成本只对一套类型/索引/并发语义两套各验一遍,且 SQLite 那遍验了等于没验
JSONB/ARRAY/GIN 索引能测能用SQLite 上根本不存在,无法在测试里验证
CI/启动复杂度多一个 PG service,但只此一套看似简单,实则把复杂度推到"生产才发现"

公允裁决:双轨方案不是没有道理——它真正的好处很实在:本地零依赖,任何人 clone 下来不用装任何东西就能跑测试,新人上手快、CI 启动也轻。对一个迭代飞快、schema 很少动、又不太用 PG 高级特性(JSONB 查询、数组列、并发事务)的小项目,双轨完全够用,甚至是更聪明的选择。我们最终还是选全 PG,关键在于这个项目恰恰重度依赖那些 SQLite 模拟不了的特性:链路追踪和评估记录里大量用 JSONB 存结构化数据、靠 GIN 索引查询,持仓监控又有真并发写入。在这种场景下,"本地零依赖"省下的那点便利,换来的是"测试通过但生产挂"的系统性盲区——而这正是一个想体现工程成熟度的作品最该消灭的东西。所以我们认了那个 docker 依赖,把测试环境对齐到生产真值。换句话说:不是双轨错了,是这个项目的特性让双轨的省事变成了假象。

📌 总结

  • 迁移的根本动机是运维收敛:消除"测试 SQLite + 生产 PG"的双套维护成本——类型、索引、并发三套语义本来都得各验一遍,而 SQLite 那遍验了约等于没验。
  • 双轨真正的贵不在"多一个文件",而在"测试绿不代表生产绿":类型不兼容、JSONB 的 GIN 索引没生效、MVCC 并发竞态,这些 SQLite 全不报,推上生产才炸。
  • 最显眼的技术债是 model 上 30+ 处专为迁就 SQLite 的类型分叉(with_variant),纯噪音;验收靠一行 grep 计数归零做硬门槛,不靠肉眼。
  • 改造拆成四批可独立回滚的 PR(删分叉 → trace/eval 迁 ORM → 缓存类 → 对话引擎检查点残留),第一批就涉及 19 个测试文件、1100+ 单测零回归。
  • 重写老代码时顺手堵了一个真漏洞:链路追踪的过滤条件原来直接拼 SQL 有注入风险,新版加了"只放行声明过的列名"白名单 + ORM 参数化。

一句话速记:不是 SQLite 不好,是这个项目重度用了 JSONB/索引/并发这些 SQLite 模拟不了的东西,于是双轨的"省事"变成了"测试通过但生产挂"的盲区——宁可本地多一个 docker 依赖,也要让测试环境对齐生产真值。

Q2

分层测试数据库策略:为什么所有层都连真 PG + 事务回滚隔离?容器化的测试夹具怎么复用?

★★★★☆
测试隔离PostgreSQLpytest 夹具容器化事务回滚

🎯 考察点分析

这道题面试官想看你有没有真的踩过"测试库和生产库不一致"的坑。很多人测试用内存数据库图快,结果上线才发现类型、索引、并发行为对不上。我想确认三件事:你为什么敢让所有测试层(单元/集成/端到端)都连同一个真数据库;你怎么保证成千上万个测试之间互不污染却又不慢;以及你怎么写夹具,让它在"开发者本机常驻数据库"和"持续集成临时容器"两种环境下都能正确启动和清理。

  • 追问:测试里调了 commit,事务回滚不就失效了吗?你怎么让 commit 也能被撤销?
  • 追问:每个测试单开一个数据库做物理隔离不是更干净?你为什么没这么做?
  • 追问:夹具探活为什么不能只看端口通不通?多探一步是在防什么?
  • 追问:异步那条线为什么反而显式关掉了回滚隔离?

📚 原理讲解

先说大方向。过去常见的做法是"分层":单元测试用假数据库(mock)或内存数据库(SQLite)换速度,只有集成测试才连真库。我们把这套拆了——所有需要数据库的测试,不管哪一层,统一连同一个真的 PostgreSQL 测试库。动机是消除两套数据库的维护成本:类型差异(像 UUID、JSONB、数组列)、特定索引、并发行为,在假库上根本暴露不出来。为什么要迁到 PG 本身,见本类第 1 题,这里只讲迁完之后测试层怎么落地。

隔离不是简单 rollback,关键在"保存点"

一库共用,最怕测试之间互相污染。我们的隔离机制是:每个测试开始时开一个外层事务,测试跑完直接把这个外层事务整体回滚,所有写入凭空消失。但这里有个魔鬼细节——如果测试代码自己调了 commit 怎么办?正常情况下 commit 一执行,数据就真落库了,回滚也救不回来,下个测试就被污染了。

解法是给会话设一个开关 join_transaction_mode="create_savepoint"。打开它之后,测试里调的每一次 commit 不再是真提交外层事务,而是降级成"保存点释放"(SAVEPOINT release)——你可以把外层事务想成一张大白纸,每次 commit 只是在纸上盖个"这段我认了"的小章,但纸本身没交出去。测试结束时把整张纸撕掉(外层 rollback),所有小章连同写入一起作废。这样既能让被测代码正常走它的 commit 逻辑,又不会真的污染数据库。

夹具是三层金字塔

启动和准备工作分三层,从慢到快、从全局到单测:

底层 · 起容器(整个测试会话只跑一次):负责把 PostgreSQL 容器拉起来、等它真的能连、把连接信息打包返回。这层最重,所以做成会话级,几千个测试共用一个容器。

中层 · 建 schema(整个会话只跑一次):拿到连接后建引擎,然后先把整个 schema 删干净再重建表。为什么不用普通的 drop_all?因为我们有循环外键(消息表和任务表互相引用),drop_all 需要给表排个删除顺序,循环引用排不出来会直接报错;而 DROP SCHEMA public CASCADE 是连根拔,不挑顺序。删完重建还要补回扩展(像 uuid 生成函数),因为它原来是建在被删的 schema 里的。

顶层 · 包事务(每个测试各一份):这就是上面讲的保存点会话——开外层事务、建带保存点模式的会话、测试结束回滚。另外它在开事务前还会先用一条独立连接把所有表清空一次,这是为了擦掉异步那条线留下的脏数据(下面会讲)。

容器夹具的复用哲学:外部已起则复用,自起则负责拆

这是这道题最实用的工程点。夹具不能假设容器一定是它自己起的。流程是:先探一下端口在不在听,如果已经有人起了(比如开发者本机常驻一个 PG),就直接复用、测完不动它;只有端口没人听时,夹具才自己 docker compose up,并打个标记"这是我起的";最后清理时只有打了标记的才 down。这样本机开发者的常驻库永远不会被测试误删,而持续集成里的临时容器测完会自动清掉。

还有个容易漏的点:探活不能只看端口通不通。端口在听不代表数据库真能接受查询。所以我们用专门的探活函数,拿真正的客户端去连一次、跑一条真查询才算数。PG 还多一步:处理"开发者本机有个旧数据卷、初始化脚本不会重跑"的兼容——容器的初始化 SQL 只在数据卷第一次创建时执行,旧卷上不会再跑,所以得手动确保测试库存在。

异步那条线为什么反着来

还有一条走异步驱动(psycopg v3)的会话工厂,它故意不做回滚隔离。因为异步测试经常跨多个 async with 块去观察状态变化,只有真 commit 了下一个块才看得见。代价是它会真的把数据写进库,所以前面顶层夹具才要在每个测试开头先清表——这俩是配套设计。

💻 示例讲解

下面用伪代码把"保存点回滚"和"复用还是自起"两个核心机制串起来,函数名沿用真实夹具的名字当锚点。

# ① 容器夹具:外部已起则复用,自起则负责拆(会话级,只跑一次)
def pg_test_container():
    started_by_us = False
    if not _is_port_listening(host, port):   # 端口没人听 → 没人起过
        docker_compose_up("postgres")        # 才自己起容器
        started_by_us = True                 # 打标记:这是我起的

    _wait_for_pg_ready(...)        # 探活:拿真客户端连一次,不是只看端口
    _ensure_test_db_exists(...)   # 兼容旧数据卷:初始化脚本不会在旧卷重跑
    _wait_for_pg_ready(...)       # 再确认测试库本身可连

    yield {"url": "..."}          # 把连接信息交给上层

    if started_by_us:             # 只拆自己起的;复用来的常驻库不动
        docker_compose_down("-v")


# ② 单测试夹具:保存点回滚隔离(每个测试各一份)
def db_session(engine):
    conn = engine.connect()
    outer_tx = conn.begin()                  # 开一个外层事务(那张"大白纸")

    session = sessionmaker(
        bind=conn,
        # 关键开关:测试里的 commit 降级成"保存点释放",而非真提交
        join_transaction_mode="create_savepoint",
    )()

    try:
        yield session            # 测试随便写、随便 commit
    finally:
        session.close()
        outer_tx.rollback()      # 整体回滚,撕掉白纸,所有写入连同 commit 一起作废
        conn.close()

推演:假设一个测试里插了 3 行、又调了 2 次 session.commit()。没有保存点模式时,这 2 次 commit 会把 3 行真落到 PG,下一个测试一查就撞上脏数据。开了 create_savepoint 后,这 2 次 commit 只是释放保存点(数据仍只活在外层事务里),测试结束 rollback() 把外层一撤,3 行整体消失,下一个测试看到的是干净库。整轮测试自始至终只起 1 个容器、每个测试只开 / 回滚 1 个事务,既不付建库开销,又能完全撤销写入。

⚖️ 决策对比

维度我们的选择(单库 + 事务回滚 + 保存点)替代方案(mock / SQLite 测试 vs 真 PG + 事务回滚)
贴近生产真值就是生产同款 PG,类型 / 索引 / 并发行为全真实mock 完全测不到 schema;SQLite 没有 JSONB、数组、特定并发语义
维护成本一套 schema、一套 SQL,无双轨SQLite 回到测试库与生产库双套维护,类型差异处处要兼容
单测速度每测试只开 / 回滚一个事务,容器全程复用mock / SQLite 内存库毫秒级、零容器依赖,确实更快
隔离干净度事务回滚 + 保存点,写入对跨测试不可见每测试单建库做物理隔离最干净,但会话级反复建库慢
启动门槛需要 Docker / 一个 PG 容器mock / SQLite 无任何外部依赖,开箱即跑
并行扩展当前单库;多进程各占一库的物理隔离显式推后每测试独立库天然适配多进程并行

公允裁决:替代方案不是稻草人——mock / SQLite 真的更快、零依赖,在纯逻辑、不碰数据库语义的单元测试里完全够用;每测试单建库做物理隔离也确实最干净。但我们的项目大量用了 PG 特有能力(JSONB、数组、循环外键、并发语义),这些恰恰是假库测不出、上线才爆的地方,双轨维护的隐性成本远高于一个容器的启动成本。所以我们在"贴近生产真值"和"隔离够快"之间选了中间路线:一个容器全程复用拿真值,每测试只开 / 回滚一个事务保速度,既不付反复建库的开销又能完全撤销写入。多进程并行各占一库的物理隔离不是不要,而是显式推到后续(并行测试框架当前还没装),不在这一版的范围里。

📌 总结

  • 所有测试层统一连同一个真 PostgreSQL 测试库,不再分"单元用 mock、集成才连真库",根本目的是消除假库与生产库的双轨维护和"上线才爆"的类型 / 索引 / 并发差异。
  • 隔离靠每测试一个外层事务 + 末尾整体回滚;关键开关 join_transaction_mode="create_savepoint" 把测试里的 commit 降级成保存点释放,否则一 commit 就真落库、跨测试累积污染。
  • 夹具是三层金字塔:起容器(会话级)→ DROP SCHEMA CASCADE 重建(会话级,能处理循环外键)→ 包事务回滚(每测试一份)。
  • 容器复用遵循"外部已起则复用、自起则负责拆":端口已听就用别人的库且测完不动,没人起才自己拉容器并在最后清掉;探活要拿真客户端连一次,不能只看端口。
  • 异步那条线显式不做回滚隔离(跨 async with 块要真 commit 才看得见状态),代价是会落库,所以每测试开头先清表配套兜底。

一句话速记:一个真 PG 容器全程复用,每测试一层外层事务包着"假 commit"(保存点),测完整体回滚——拿生产真值又不付建库开销。

模型注册表 / 白名单为什么需要?你怎么做模型切换、又怎么出"模型 × 题型"对比表?

★★★☆☆
模型注册表白名单 allowlist模型切换评测对比表RL 候选

🎯 考察点分析

这道题表面问"怎么换模型",其实我想看的是:当你的系统要从"只用一个写死的模型"走向"用户能选、评测能比、训练能挑"的时候,你有没有把一套基础设施同时服务生产和训练两个场景的设计意识。换模型谁都会改一行字符串,难的是改完之后默认行为零回归、打错模型名能当场报错、还能自动汇出一张能直接拿去做决策的对比表。

  • 追问:为什么不直接把模型名硬编码在调用点?之前明明所有逻辑层都只映射到一个模型。
  • 追问:你说有个"白名单",它到底防住了什么?不加它会出什么具体的脏数据?
  • 追问:那张"模型 × 题型"对比表是怎么生出来的?它最后是拿来回答什么决策的?
  • 追问:注册表里你如实记了一个小模型"不支持函数调用、账号没开通",为什么不给它做个降级兜底让它也能跑?

📚 原理讲解

先讲背景。系统里所有"找模型"的逻辑,原本走的是一层叫分级路由(tier_router)的抽象:上层只说"我要个快的 / 均衡的 / 强的"(fast / balanced / deep),由路由器把这三档解析成一个具体模型名。早期阶段这三档全部映射到同一个默认模型(deepseek-v4-flash),所以这层抽象当时看起来像是"为一个模型套了三个空壳"。

转折点是两个新需求同时出现:生产侧想让用户在每个会话里自己挑一个底层模型(挑完要能归因到那一轮回答上);训练评测侧想指定某个模型去跑反向出题的成功率测试,跑完多个模型还要自动拼成一张对比表。这两件事都需要一个能力:在不破坏"默认走分级抽象"的前提下,精确指定一个模型。

核心改动只有一个"模型覆盖口子"

实现上没有大动干戈。给底层 LLM 服务的两个入口方法(流式那个 stream_step、非流式那个 chat)各加一个可选参数 model,然后在解析模型那一行做个二选一:给了 model 就用它(先过白名单校验再映射),没给就照旧走分级路由解析 tier。一句话——分级抽象仍是默认大路,指定模型只是一个逃生口。默认路径一个字符没动,所以老代码回归成本为零;切换只发生在这一个单点,不会散落到几十个调用处。

注册表 = 白名单 + 元信息的唯一真相源

那个 model 参数不能让人随便填字符串,否则打错一个字母,请求会静默落到错模型上——这是最阴险的 bug,因为它不报错,只是悄悄污染你的对比数据。所以有了模型注册表:它是一份权威清单,每个模型是一条不可变记录(ModelSpec),五个字段——注册键 key、真实调用 id(dashscope_id)、大小 size、是否可用 available、是否支持函数调用 supports_tools。请求一个不在清单里的模型,直接当场抛错(fail loud),绝不放行。整个系统里只有这一处能把"注册键"翻译成"真实模型 id",出口收敛成一个点。

清单为什么按"大小"分两类——这是有训练含义的

清单里 5 个模型刻意分成两组:3 个大 API 模型(deepseek-v4-flash 默认、qwen-plus、qwen-max)代表能力天花板;2 个小模型(qwen2.5-7b、qwen3-8b)是可以本地微调的强化学习候选。这个分类不是装饰——前置基线测出系统残留的最大缺口是"工具调用的可靠性",而小模型恰恰在这一项上最弱。把它们摆进清单,就是为了用同一张对比表把"小模型差在哪、差多少"量化出来,直接回答"该挑哪个小模型来做强化学习、要补多少"。

💻 示例讲解

三段代码串起整条链路。第一段是注册表(白名单 + 校验出口),第二段是"模型覆盖口子",第三段是对比表怎么聚合。

# ① 注册表:一份不可变清单 + fail loud 校验(白名单的全部本质)
@dataclass(frozen=True)
class ModelSpec:
    key: str            # 对外的注册键,如 "qwen-max"
    dashscope_id: str   # 真实调用 id(只有注册表能把 key 翻成它)
    size: str           # "large"=能力天花板 / "small"=可微调的 RL 候选
    available: bool     # 账号当下能不能调(live 实测填,不猜)
    supports_tools: bool  # 支不支持原生函数调用(弱也照实记,不兜底)

_MODELS = (
    ModelSpec("deepseek-v4-flash", "deepseek-v4-flash", "large", True,  True),
    ModelSpec("qwen-plus",         "qwen-plus",         "large", True,  True),
    ModelSpec("qwen-max",          "qwen-max",          "large", True,  True),
    ModelSpec("qwen2.5-7b", "qwen2.5-7b-instruct", "small", False, False),  # 403 没开通
    ModelSpec("qwen3-8b",   "qwen3-8b",            "small", True,  True),
)

def dashscope_id(key):
    if key not in _BY_KEY:               # 不在清单 → 当场炸,绝不静默放行
        raise ValueError(f"model 不在清单: {key}")
    return _BY_KEY[key].dashscope_id

# ② 覆盖口子:就这一个二选一,决定了"默认零回归 + 切换走单点"
def resolve_model(model, tier):
    if model is not None:
        return dashscope_id(model)       # 指定了:过白名单校验再映射(逃生口)
    return tier_router.resolve(tier)     # 没指定:照旧走分级抽象(默认大路)

# ③ 对比表:对每个模型各跑一遍成功率测试,再拼成"模型 × 桶"矩阵
async def run_compare(cases, models):
    per_model = {}
    for m in models:                     # 每个模型单独跑一轮,互不污染
        per_model[m] = await run_passk(cases, model=m)
    return _compare_table(per_model)     # 行=模型,列=各题型桶 + 一列总分,每格=通过率

推演:拿 5 个模型里能跑的那几个去 run_compare。大模型(deepseek-v4-flash / qwen-plus / qwen-max)各行总分都不低;两个小模型里 qwen2.5-7b 因为 available=False 直接 403、连测都测不了(注册表如实标了"未开通"),qwen3-8b 能跑但在"工具可靠性"那一列明显塌陷。这张表读出来的结论是现成的:大模型行高、小模型行在某一列掉下去,那个掉下去的格子就标注着"= 强化学习要补的缺口"。整张表 5 个模型实测的结果,有 4 个支持原生流式函数调用,1 个 403——这些都是注册表里 live 跑出来如实填的,不是拍脑袋。

⚖️ 决策对比

维度我们的选择(注册表 + 覆盖口子)替代方案(硬编码模型名在各调用点)
改动量覆盖逻辑落在 2 个方法、tier→model 解析单点;默认路径零改动最省事:反正之前 tier 全映射到一个模型,直接写死字符串
给用户换模型每会话挑一次,沿调用链透传 model 参数即可想让用户选,就得到处翻出硬编码的地方逐个改
打错模型名不在白名单当场 fail loud(ValueError)静默落到错模型 / 调到不存在的 id,运行时才暴
评测公平性单点切换 + 权威清单,确保对比的是"同一批题、不同模型"切换散落多处,容易漏改一处 → 对比数据被污染却不自知
归因trace span 本就带 model,会话选择落新表 chat_session_model,归因现成没有统一记录点,事后查"这轮用的哪个模型"困难
小模型弱能力如实记 supports_tools=False、available=False,不兜底(若兜底)弱函数调用被悄悄补强,污染"原生能力对比"

公允裁决:硬编码方案真的更省事,尤其在"全系统只有一个模型"的早期,它没有任何多余抽象,读起来最直白。如果这个项目永远只用一个模型,硬编码就是对的。我们仍然选注册表方案,是因为需求已经明确转向了"用户可选 + 多模型评测":一旦有了第二个模型,硬编码的两个软肋会立刻发作——想换得到处改、打错名会静默污染评测数据。注册表方案把这两个软肋一次性堵死,代价仅仅是一份清单和一个二选一分支,而且默认路径不动、老代码零回归。另外有个容易被当成"缺陷"的设计要特意说清:我们故意不给弱小模型做函数调用兜底,如实把它记成"不支持"。因为这套基础设施的评测目标就是测"原生能力对比",一旦兜底,小模型的弱点就被补丁盖住了,那张对比表也就失去了"指导强化学习补哪里"的意义。

📌 总结

  • 一套基础设施服两个用途:生产侧让用户每会话选一个底层模型并记录归因;训练评测侧让指定模型跑成功率测试、多模型自动汇成对比表。
  • 切换的核心只有一个"模型覆盖口子":两个入口方法各加可选参数 model,给了就过白名单校验再映射,没给就照旧走分级路由——默认路径零回归。
  • 注册表是白名单 + 元信息的唯一真相源:5 个模型(3 大天花板 + 2 小 RL 候选),不在清单当场 fail loud;它是唯一把注册键翻成真实 id 的出口。
  • 对比表 run_compare 对每个模型各跑一遍,_compare_table 聚成"行=模型、列=题型桶+总分"的矩阵,小模型在"工具可靠性"桶的塌陷直接量化出强化学习要补的缺口。
  • 故意不给弱小模型做函数调用兜底、如实记录"不支持/未开通":兜底会污染"原生能力对比"这个评测目标。

一句话速记:分级抽象当默认大路、指定模型是逃生口、注册表当白名单守门,一个解析单点同时喂生产和评测,对比表里小模型塌陷的那一格就是 RL 要补的缺口。

依赖管理:为什么重型 / 可选依赖走可选 extras 而不是全塞进基础依赖?import 链的假设为什么要写冒烟测试验证?

★★★☆☆
依赖管理optional extrasimport 链冒烟测试磁盘约束

🎯 考察点分析

这道题表面在问"依赖怎么分组",其实面试官想看你有没有把"产品上的核心 / 可选"和"工程上的依赖放哪一组"分清楚——这是两件事,初级工程师常混为一谈。再往下,后半问"import 链的假设为什么要写冒烟测试验证",是在探你写设计文档时是凭直觉脑补、还是动手实测,以及你能不能讲清 grep 为什么不够。

  • 追问:知识库功能是核心功能,为什么它的依赖反而不进基础依赖?"核心"和"放哪组"是一回事吗?
  • 追问:你怎么验证一个模块到底依不依赖某个重型包?光 grep from pymilvus import 能看出来吗?会漏掉哪几种情况?
  • 追问:真正的依赖缺失报错(ImportError)发生在什么时候——程序一启动就崩,还是用到那个功能才崩?这影响你要不要写降级兜底吗?
  • 追问:你为这个假设写过一段一次性失败、然后整段回滚(git reset --hard)的代码吗?事后复盘学到了什么?

📚 原理讲解

Python 项目用 pyproject.toml 声明依赖。它有两栏:一栏是基础依赖([project] dependencies),装这个项目就一定会装的东西;另一栏是可选分组([project.optional-dependencies]),每组起个名字,装的时候要显式点名才会拉进来,比如 uv sync --extra kb。

核心 vs 放哪组:这是两件不同的事

很多人第一反应是"知识库是产品的核心功能,那它的依赖当然要进基础依赖"。这一步就错了。"功能是不是核心"是产品层面的判断;"依赖放哪一组"是工程层面的判断,真正决定它的是另一个问题:这堆包是不是每个环境每次装都非装不可?

本项目的知识库功能要解析 PDF、做向量检索,牵出 mineru / pymilvus 这类包,它们背后拖着 torch / cuda,体量到 5-8GB。云开发环境(Codespaces)总共才 32GB 磁盘,基础依赖一旦塞进去,光知识库这一坨就能把磁盘撑爆,连项目都拉不起来。更别说有人只想跑聊天、根本不碰知识库,也得干等 torch 下完。所以把它挪进可选分组——是不是核心不变,变的只是"装哪组依赖"这个选择被搬到了安装命令里。

装哪组,在安装命令里控制

解耦之后,环境各取所需:CI、生产、Mac 开发机磁盘管够,默认装齐(--extra dev --extra kb),产品功能一个不缺;Codespaces 受磁盘约束,走精简版(--extra dev),先把项目跑起来。本项目实际有四个可选分组:dev(lint / test 工具)、test(testcontainers[redis])、kb(4 个重型知识库依赖)、code-interpreter(只多一个 plotly)。

为什么 import 链的假设非要冒烟测试,不能 grep

拆完依赖,自然冒出一个担心:精简装(没装知识库那组)的时候,程序启动会不会因为某个模块 import 不到 pymilvus 而直接崩?直觉做法是 grep 一下"谁 import 了 pymilvus",看看它在不在启动链上。但grep 只能看到顶层、静态写死的 import 语句,看不到三种真实触发方式:

  • 函数体内的延迟 import:包写在函数里,只有调到那个函数才 import,grep 一眼扫顶层根本扫不到运行时才发生的事。
  • 子进程命令行调用:有些工具是当作命令行程序、靠开子进程跑的,压根不是 Python 的 import,grep from X import 完全不命中。
  • 链式传递 import:A 导入 C、C 导入 D、D 才导入那个重型包。你 grep A 看不见这条链末端的依赖。

还有个阴沟:项目里有 app/service/ 和 app/services/ 这种单复数别名目录,grep 容易认错哪个才是真正在跑的那条路径。结论是——设计文档里任何"某模块 import 会失败"的断言,实施第一步先 python -c "from X import ..." 在干净环境里实测,而不是靠 grep 脑补。校准一份设计文档的成本,远小于代码写完再整段删的成本。

💻 示例讲解

先看 pyproject.toml 的分组长什么样(精简到能看懂结构):

# [project] dependencies —— 基础依赖,装项目就一定有,保持轻
#   fastapi / sqlalchemy / openai / pandas ... (核心运行时)

# [project.optional-dependencies] —— 可选分组,要显式点名才装
# kb 组:4 个重型包,背后拖 torch/cuda,体量 5-8GB
kb = [
    "mineru[core]>=3.1.0",          # PDF 解析,拖 torch
    "pymilvus>=2.6.0",              # 向量库客户端
    "pdfplumber>=0.11.0",
    "langchain-text-splitters>=0.3.0",
]
# code-interpreter 组:numpy/pandas 已在基础里,只需补 plotly 画图
code-interpreter = ["plotly>=5.17"]

# 装哪组在命令里选:
#   精简(不装知识库)：uv sync --extra dev
#   完整(带知识库)  ：uv sync --extra dev --extra kb

再看那段被冒烟测试当场证伪、最后整段回滚的代码。原设计假设"路由模块的 import 链上有 pymilvus,精简装会崩,得包一层兜底返 503":

# ❌ 基于"脑补 import 链"写的兜底 —— 后来被实测证明是死代码
try:
    from app.router.knowledge_router import router   # 假设这行会因缺 pymilvus 崩
    app.include_router(router)
except ImportError:
    # 精简装时给个返 503 的占位路由 …… 但这个分支永远走不到
    app.include_router(make_503_stub())

# ✅ 实施前先跑一行冒烟测试,假设当场被推翻:
#   python -c "from app.router.knowledge_router import router; print('OK')"
# 结果在精简装下也照样 print OK —— 那个路由只做元数据增删改查,
# 只 import 了 sqlalchemy / fastapi / app.models,根本不碰 pymilvus。
# 于是 try/except 整段是死代码,git reset --hard 回滚。

推演:真正的 ImportError 不在程序启动链上,而在运行时——用户在对话里触发知识库检索,链路是 agent 调 kb_search 工具 → kb_search_service → milvus_client → pymilvus,这时精简装才会缺包报错。所以正确做法是:依赖拆分本身(把 4 个重型包挪进 kb 组)就已经达成目的;启动链上那段 503 兜底纯属基于错误假设的多余代码。代价对比很直白:跑一行冒烟测试是几秒钟,而基于脑补写完整段兜底再发现是死代码、整段删掉,是几十行代码加一次回滚——前者省下的正是后者。运行时缺包要不要优雅降级,是另一个独立问题,真撞到再说(YAGNI)。

⚖️ 决策对比

维度我们的选择(可选 extras)替代方案(全量基础依赖)
心智负担多一层"装哪组"的概念,新人要看 README 选命令装一次全都有,零额外概念,最省心
最小磁盘占用精简装可不带知识库那 5-8GB,32GB 环境装得下每个环境都被迫拖下 torch/cuda 几 GB
磁盘受限环境Codespaces 走精简版正常起得来直接装不下,项目拉不起来
只跑聊天的人不碰知识库就不用等 torch 下载哪怕只想跑聊天也得全量下完才能用
CI / 生产 / Mac默认装齐,产品功能不受影响同样装齐,这一类环境两者无差
配套纪律设计文档里"X import 会失败"的假设先冒烟实测无此问题(但也享受不到拆分的好处)

公允裁决:全量基础依赖真的有它的好——零心智负担,没有"装错分组功能缺一半"的坑,对磁盘管够、网速也快的环境(CI、生产、Mac 开发机)而言,它和可选 extras 在结果上没区别,反而更简单。我们之所以仍走可选 extras,唯一也是决定性的理由是磁盘受限的云开发环境:知识库那 5-8GB 一旦进基础依赖,32GB 的 Codespaces 直接撑爆。我们没有为了"看起来更工程化"而强行拆分,而是把拆分点精确卡在"是不是每个环境都非装不可"上——dev / test 这些轻量工具进可选组是顺手,真正的动因是那 4 个重型知识库包。本质上,可选 extras 是把"核心 vs 可选"这件产品判断,解耦成了"装哪组"这件安装时的选择,既保住了磁盘受限环境,又不动产品层级。

📌 总结

  • "核心 vs 放哪组"是两件事:知识库是核心功能不假,但它的依赖该进可选组还是基础依赖,取决于"是不是每个环境都非装不可",而不是产品上重不重要。
  • 拆分的真动因是磁盘:知识库那 4 个重型包拖着 torch/cuda 共 5-8GB,塞进基础依赖会撑爆 32GB 的云开发环境;挪进可选 kb 组,精简装就能绕开。
  • 装哪组在命令里选:CI / 生产 / Mac 默认装齐(--extra dev --extra kb),Codespaces 走精简版(--extra dev),产品层级不受影响。
  • import 链假设必须冒烟实测:grep 看不到函数内延迟 import、子进程命令行调用、链式传递 import,还会被单复数目录别名误判;一行 python -c 当场就能证实或证伪。
  • 真缺包在运行时,不在启动链:那段返 503 的启动兜底基于错误假设,被冒烟测试证伪后整段回滚——校准设计文档的成本远小于写完代码再删。

一句话速记:重型包进可选组、装哪组在命令里选;"会不会崩"别 grep 脑补,一行 python -c 实测胜过整段死代码回滚。
