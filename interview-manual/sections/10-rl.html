10RL 准备与工具可靠性

这一类讲的是一个反直觉的工程判断:当弱模型在某类任务上能力骤降,到底是模型不会算,还是工具在背后悄悄使绊子?作者用「反向出题 + 多次采样通过率」搭了一套评测台,先把工具坑挖干净,再决定强化学习该往哪打。从「怎么证明断崖是工具问题」一路到「怎么攒一批干净的训练料」,每一步都是先量化、再定靶、最后划清「修工具」和「上 RL」各自的边界。

Q1

你的结论是"先修工具比直接上强化学习更对症"。你怎么论证那个能力断崖是工具问题、而不是模型能力问题?

★★★☆☆
评测方法论工具可靠性RL前置判断断崖归因

🎯 考察点分析

这道题表面问"工具 vs 模型",其实在探一件事:你会不会在掏出强化学习这把重武器之前,先把"问题到底出在哪"诊断清楚。很多人一看到指标低就喊"上 RL 训练",但强化学习又贵又慢,如果真凶其实是一行代码,那就是拿火箭筒打蚊子。面试官想确认你具备的是归因能力,而不是堆资源的本能。

  • 追问:你凭什么说断崖"卡在取数、不卡在计算"?这两个假设你是怎么掰开、各自怎么证伪的?
  • 追问:如果改了一行代码后那一桶没满分、只升到 60%,你的结论会变吗?为什么"单改一行就整桶满分"是强证据?
  • 追问:你怎么排除"是你给的预算(步数)太少、模型其实算得来,只是没时间算完"这种混淆因素?
  • 追问:有没有踩过归因错的坑?你是怎么发现归错了的?

📚 原理讲解

先说背景。我们要给一个"能算金融指标的对话 agent"做体检:给它一只股票、一段时间,让它算年化收益、波动、最大回撤这些数。问题来了——如果体检分数不理想,你怎么知道是模型不会算,还是工具没把料喂齐?这两件事的修法天差地别:前者要重新训练模型(强化学习就是干这个的),后者改代码就行。

第一步:别看总分,要分桶看

总分是一团浆糊。一个 70 分,可能是每道题都 70 分(均匀的能力短板),也可能是九成题满分、一成题零分(局部塌方)。这两种长得一样但病因完全不同。所以我们做了两件事:一是反向出题——不靠人手攒题,而是先用确定的数据算出标准答案,再倒推出题目,这样每道题都有一个可对照的"金标准";二是多次采样通过率(业内叫 pass@k,同一题让 agent 独立答 k 次,看通过率),把偶发抖动平滑掉。然后把题按"难度 × 指标"切成一格一格,让断崖自己浮出来。

第二步:看断崖落在哪一格

结果非常干净:绝大多数格子都在 70%~93% 的绿区,唯独一格刺眼地红——需要近三年长窗口数据的年化收益(CAGR)那一桶,只有 13%。注意这个分布的形状:不是"越难越差"的斜坡(那才像能力问题),而是单格孤立塌方。同样是"算指标",1 年窗口的波动、回撤、涨幅全是绿的,凭什么换成 3 年窗口、换成 CAGR 就单独崩?能力是不会这么挑窗口长度的。

第三步:把"算不算得来"和"取不取得齐"掰成两个假设

这是整套论证的枢纽。我把断崖拆成两句话对立的假设:

  • 假设甲(能力问题):模型不会算长窗口的 CAGR。
  • 假设乙(工具问题):模型会算,但取数工具根本没把三年的数据给齐。

怎么分辨?去摸取数工具的代码。真凶是 get_daily 里写死的一行:不管你问几年,它最多只悄悄返回最近约一年的数据,更早的静默丢弃(连个警告都不给)。这一下两个现象全解释通了:agent 拿不到三年数据,只能笨办法分多次按子区间取,每段把一整年灌进上下文,步数烧光、死在最后一步开算之前;更阴险的是,粗心的 agent 没察觉"问三年只给了一年",直接拿一年当三年算,错且不自知。这不是"不会算",是"压根没拿到该算的料"。

第四步:做判决性实验,让证据自己说话

光有理论还不够,得有一刀切的实验。我把那行静默截断删掉(让长区间真取全量),别的什么都不动,重跑同一套题。结果:CAGR/3 年那一桶从 13% 直接拉到 100%,而且全题集零个"算不出指标"。这就是决定性证据——如果是模型能力问题,单改一行取数代码绝不可能让整桶从 13% 跳到满分。能力是训练出来的,改一行 I/O 代码改不动模型一丝一毫。它能跳满,只能说明:模型本来就会算,之前缺的只是料。假设乙成立,假设甲被证伪。

为什么这就够下"先修工具"的结论

因为这把"能不能算"这个伪缺口清掉了。修完之后再看残留的失败,已经不是"不会算",而是"调工具时漏个参数、取错股票代码、报错就放弃"这类工具调用可靠性问题——那才是真正该留给强化学习的靶子(这部分见本类第 4 题)。先修工具是一行代码的低成本高确定性杠杆;不修就上 RL,等于让算力去填一个工具坑制造出来的假能力缺口。

💻 示例讲解

下面这段伪代码不是真实实现,只是把"分桶 → 找孤立红格 → 做判决性实验"这条诊断逻辑走一遍,看清证据是怎么逼出结论的。

# 一、按「窗口长度 × 指标」分桶跑 pass@k,让断崖自己暴露
def diagnose(questions):
    buckets = {}
    for q in questions:
        # 同一题独立采样 k 次,通过率平滑掉偶发抖动
        rate = pass_at_k(agent_answer, q, gold=q.gold, k=8)
        # 关键:按「窗口长度」和「指标」二维归桶,而不是只看一个总分
        buckets[(q.window, q.metric)] = rate
    return buckets

before = diagnose(all_questions)
# 观察到的形状:只有一格孤立塌方,不是越难越差的斜坡
# {(1y, '涨幅'): 0.89, (1y, '波动'): 0.93, (1y, '回撤'): 0.87,
#  (3y, 'CAGR'): 0.13}   ← 单格刺眼的红

# 二、把两个假设掰开:断崖卡在「算」还是卡在「取」?
#   甲 能力问题:模型不会算 3 年 CAGR
#   乙 工具问题:模型会算,但取数工具没把 3 年数据给齐
# 摸代码 → 取数工具里一行静默截断:不管问几年,只悄悄返回最近约 1 年
def get_daily(ts_code, start, end):
    df = fetch(ts_code, start, end)
    return df.tail(260)   # ← 真凶:超出部分静默丢弃,agent 不知情

# 三、判决性实验:只删这一行,别的都不动,重跑同一套题
def get_daily_fixed(ts_code, start, end):
    return fetch(ts_code, start, end)   # 长区间真取全量,不再 tail

after = diagnose(all_questions)
# {(3y, 'CAGR'): 1.00}  ← 同一桶从 0.13 跳到满分,且全题集 0 个「算不出」

# 四、下判决:能力问题不可能被「改一行取数」治好
assert before[('3y','CAGR')] == 0.13 and after[('3y','CAGR')] == 1.00
# → 改的是 I/O,不是模型权重;整桶满分只能解释为「本来就会算,之前缺料」
#   结论:断崖是工具问题,先修工具;能力缺口很小,RL 别急着上

推演:关键不在代码多巧,而在这组对照数字。修复前:CAGR/3 年桶 13%,而同样难度的 1 年窗口指标在 70%~93%——同是"算指标",只有长窗口那格塌,这本身已经把矛头指向"窗口越长越取不齐",而非"算法不会"。修复后:那一桶 13% → 100%,全题集 0 个"算不出指标"。一行取数代码就能让整桶满分,这个因果链对"能力问题"是致命的——你没法用改 I/O 的方式给模型涨能力。所以下"先修工具"的结论,靠的不是直觉,是这组能复现的判决性数字。

📌 总结

  • 别看总分,要分桶。按"难度 × 指标"切格跑多次采样通过率,断崖会自己暴露;单格孤立塌方和均匀短板形状不同、病因不同。
  • 把"算不算得来"和"取不取得齐"掰成两个假设。这是归因的枢纽——前者是能力问题该上 RL,后者是工具问题改代码即可。
  • 用判决性实验下结论。只删取数工具一行静默截断、别的不动,那一桶 13% → 100% 且全题集 0 个"算不出";改一行 I/O 不可能给模型涨能力,所以这是工具问题的铁证。

  • 诊断纪律:某桶突然整桶崩,先用当前数据重算标准答案比对漂移,再怀疑代码——曾误把提升归因于一句提示文案,摸代码发现那条路从未触发,真因是那行静默上限。

一句话速记:断崖是"取不齐"不是"算不来"——分桶让它孤立现形,改一行 I/O 就整桶满分,这是工具 bug 的判决性证据,该先修工具再谈 RL。

Q2

RL 前的基线:某个指标桶从 13% 拉到 100%,你是怎么定位到真凶(取数工具的静默截断)的?为什么"agent 预防性分段取数"不是坏习惯而是被逼的?

★★★★☆
静默截断根因定位上下文预算取数工具分段取数

🎯 考察点分析

这是一道根因定位题,披着"调参提分"的皮。我们用反向出题给计算型金融场景打分(为什么这条路能把"工具问题"和"模型能力问题"分开,见本类第 1 题),发现专门考"近三年走势"的那一桶——年化收益率(CAGR,一笔投资每年平均涨多少)——分数低得离谱,只有 13%。面试官真正想看的是:你面对一个低分桶,是顺手加点预算把数字刷上去,还是钻进去找到那一行写死的代码;尤其想看你能不能把一个看起来像"agent 笨"的现象(它老爱把数据拆成好几段去取),翻译成"工具有缺陷,agent 是被逼的"。这考的是根因定位的纪律,不是调参手感。

  • 追问:你怎么确定瓶颈在"取不到数据",而不是"算不来 CAGR"?分桶分数能告诉你什么?
  • 追问:"静默截断"为什么比报错的截断更危险?它埋了几种坑?
  • 追问:你上一轮把这个桶从 13% 提到 40%,归因对了吗?后来怎么发现归因错了?
  • 追问:修完之后你把步数预算从 26 退回 18,分数还是满的——这一步是为了证明什么?

📚 原理讲解

先说现象。所有低分都集中在一类题上:要看近三年数据才能算的指标(CAGR 全是三年窗口)。而只看一年的指标(波动率、回撤、涨幅)分数都在七成以上。这个分布本身就是一条线索:断崖不在"算不算得来"(agent 拿到数据就算得对),而在"取不取得齐三年的数据"。换句话说,瓶颈在取数,不在计算。

真凶:取数工具里写死的一行 260 上限

顺着"取数"摸进取数工具 get_daily(给一只股票一段日期,返回每天的开高低收),发现它里头写死了一行:_MAX_ROWS = 260——单次最多返回 260 行,大约一年的交易日。超出的部分用 df.tail(260) 只留最近的,更早的悄悄丢掉,不报错。后果是:不管你请求几年,它最多只回最近一年。这就是"静默截断"——它不是拒绝你、也不告诉你被砍了,而是默默给你一份缺斤少两的数据,封皮上还写着"已成交"。

这一行同时埋了三个坑

第一,静默正确性坑:粗心的 agent 没察觉"我问了三年它只给了一年",直接拿一年的数据当三年算 CAGR,错且不自知——这是最阴的,因为它不崩、不报错,就是悄悄算错。第二,逼出分段:稍微细心的 agent 发现拿回来的不够,只能换策略——既然单次拿不到三年,那就分多次按子区间取:第一年一段、第二年一段、第三年一段。第三,烧光预算:每段把整整一年(约 260 行、约 1.5 万字)倒进对话上下文,三段下来上下文堆满、循环步数烧光——还没凑齐数据,就先撞上终止闸,死在最后那一步计算之前。题目本该走到 run_python 把数据灌进沙箱算 CAGR,可它根本没机会跑到那一步。

"预防性分段不是坏习惯,是被逼的"

这里要替 agent 正名。模型分段取数,看着像它"养成了个坏习惯"——明明能一次取完偏要拆成三次。但真相是:单次物理上就拿不到三年,分段是它在工具约束下唯一能凑齐数据的办法。把它当坏习惯去改提示词("别分段、一次取完")是治标:你让它别分段,它一次取回来的还是只有一年,数据照样不全。根因是那一行 260 上限。这一点很重要,因为它决定了你该改提示词还是改工具。

曾经的弯路:把功劳记错给了文案改写

诚实地说,我上一轮归因错过。当时把这个桶从 13% 提到 40%,记功记在"改了截断的提示文案、引导 agent 去取缓存"上。后来摸代码才发现:get_daily 自己先把数据 cap 到 260 行(约 1.5 万字),而那条文案是绑在"超大结果截断阈值 24000 字"上触发的——一年的数据才 1.5 万字,永远够不着 24000 这条线,所以那条文案对这条路从未触发。40% 那次提升几乎全部来自另一个动作:把步数预算从 18 调到 26(多给几个回合,容下那些被逼出来的分段拼装)。那也是治标——多给回合只是让它有空间把分段勉强拼起来,既没堵住静默算错,分段本身还在继续烧上下文。这段弯路本身就是答案的一部分:分桶分数会骗你,只有摸到那一行代码才算定位到真凶。

真正的修法:改取数契约,让分段"无利可图"

落地的修法(函数名都是真的)是改取数契约本身:① 删掉 260 静默上限,长区间真取全量存进缓存;② 数据太大时,进对话的不再是几万字原始数组,而是一张紧凑信息卡 _summary(首末收盘、区间天数)外加一个取货单号 ref;③ agent 凭这个单号,经代码解释器里的 _resolve_refs 把完整序列一次性灌进沙箱算全量——单号校验必须以 {user_id}:: 开头,防止越权取别人的缓存。这样一来分段彻底无利可图:你就算分十段去问,每段回的也只是一张信息卡 + 单号,拿不到更多原始数据,反而是凭单号一步取全量最划算。该桶 13% → 100%;而且步数预算退回 18,仍然 0 空答——证明这回的提分不靠加预算。

💻 示例讲解

用伪代码对比修复前后,重点看那一行 260 上限怎么连锁出整条死亡链路:

# ===== 修复前:取数工具里写死的一行,静默砍三年为一年 =====
_MAX_ROWS = 260                      # 约一年交易日

def get_daily(ts_code, start, end):
    df = tushare.daily(ts_code, start, end)   # 真去取了三年
    if len(df) > _MAX_ROWS:
        df = df.tail(_MAX_ROWS)       # 悄悄只留最近一年,不报错、不提示
    return to_columns(df)            # 封皮写着"成交",其实缺斤少两

# agent 侧:发现拿回的不够三年,只能被逼分段(不是它笨,是工具拿不到)
seg1 = get_daily(code, "2023", "2024")   # 第一年 ~1.5万字 倒进上下文
seg2 = get_daily(code, "2024", "2025")   # 第二年 ~1.5万字 又涨一截
seg3 = get_daily(code, "2025", "2026")   # 第三年 …上下文触顶、步数烧光
run_python(merge(seg1, seg2, seg3))      # ← 撞终止闸,根本走不到这一步

# ===== 修复后:删上限,真取全量进缓存;太大只回"信息卡 + 取货单号" =====
def get_daily(ts_code, start, end):
    df = tushare.daily(ts_code, start, end)   # 不再 cap,三年全量
    out = {"summary": _summary(df), "dates": ..., "close": ...}
    return out                       # 完整版随后被缓存按 (user_id, 工具, 参数) 整份存下

Q3

采集 SFT 训练料:为什么轨迹要隔离标准答案、关掉降级、只收自然终止的?这三个坑各是什么?

★★★★☆
SFT轨迹采集答案泄漏隔离降级污染自然终止热启动种子

🎯 考察点分析

这道题表面问"怎么收数据",实际在探:你有没有真正理解监督热启动(在强化学习之前,先用一批高质量样例把模型"喂"到会用工具的水平)到底要让模型学什么。监督学习有个朴素而残酷的特性——你喂进去什么,它就照着学什么,包括你不想让它学的东西。所以会区分两种候选人:一种把"收数据"当成"把对话记下来存盘",另一种知道每一条原始轨迹里都埋着会把模型带歪的污染源,采集本身就是一道清洗工序。

  • 追问:如果标准答案跟着轨迹一起喂给模型,模型会学到什么"看起来对、实则有害"的行为?为什么这比单纯过拟合更隐蔽?
  • 追问:"关掉降级"这一步——降级机制本来是为了什么存在的?为什么在线上是优化、在采集时却是污染源?这说明同一段逻辑的"对错"是相对目标而言的。
  • 追问:为什么不直接拿标准答案 + 人工编一段工具调用,造出"理想轨迹"来喂?为什么非得让真模型真跑一遍?
  • 追问:种子轨迹该用强模型还是弱模型自己生成?这个选择对后续强化学习的天花板意味着什么?

📚 原理讲解

先把场景说清楚:我们有一个评测系统(harness),它会让模型在多轮对话里反复调金融数据工具(取行情、查交易日历、跑 Python 算指标),最后给出一个数值或排序答案。模型每一步的发言、每一次工具调用、工具返回的结果,都自然地堆在一条标准的多轮对话记录(messages)里。这条记录天生就是合法的训练料结构——不用我们另造格式。问题在于:直接把它存下来当训练料,会带进三类污染。

坑一:降级污染——上下文组装会把老工具输出"就地缩水"

线上有个省钱机制:对话越滚越长,早几轮调工具拿到的大段结果(比如一年的日线行情,上万字)会被就地替换成一个占位符,免得每轮都把它重新塞进上下文烧 token。评测里这个降级阈值默认是 1320 字,一年日线必然超标、必然被换掉。这在线上是优化;但如果我们照着这份"被缩过水"的对话记录去存训练料,模型学到的就是一条工具结果残缺的脏样本——它会看到"调了工具,然后结果不见了,凭空就接着算"。这是教模型幻觉。所以采集时要把这个降级关掉,让大段工具输出原样落盘。

坑二:拐杖污染——撞步数闸后注入的那句"系统提示"不是模型行为

模型如果一直绕、撞到步数上限,评测系统会替它注入一句话,大意是"(系统:已达执行上限,请基于已有信息直接给出最终回答)",逼它收尾。这句话是 harness 的拐杖,不是模型自己的自然发言。如果它进了监督训练料,模型就会学到"撞墙时等系统来推我一把"——这是把急救措施当成正常套路在教。所以只收自然终止(模型自己判断完事了、主动给答案)的轨迹,撞闸退出的整条丢掉;导出时再用一道白名单正则兜底,把任何带系统注入文案的样本扫掉。

坑三:轨迹只信对话记录,不信工具账本

系统里另有一份"工具调用账本(ledger)",但它为了省空间,只存了参数的哈希值——不可逆。你想知道这条轨迹真正取了哪只股票、哪个时间窗口,从账本里捞不回来,只能去对话记录里解析工具调用的参数原文。这条坑提醒的是:轨迹的唯一真相源是 messages,别图省事去读那份给监控用的账本。

为什么标准答案必须物理隔离

原来的评测脚本图方便,把标准答案(gold)写进了每一行记录里。这对算分没问题,但对采训练料是致命泄漏:监督学习会一视同仁地学你喂的所有字段,标准答案在场,模型学到的就成了"怎么偷看答案",而不是"怎么一步步把题解出来"。落地做法是产物物理分离——轨迹文件(trajectories_raw.jsonl)里只有干净轨迹、绝无答案;答案和判分结果另存一个文件(judgements.jsonl)。两份文件物理隔开,训练侧只能拿到前者。

清完污染还不够,得过两道筛选闸才算"可用种子":第一道判对(对同一道题反复采样、收紧容差复判,防止蒙对的样本混进来);第二道判过程干净(自然终止 ∧ 所有工具调用都成功 ∧ 没有尾部失败/熔断/原地打转 ∧ 步数不超过这道题该有的理想步数)。过了就给一个干净度分数(cleanliness_score),同一道题如果有多条干净轨迹,只留分最高的那一条。

💻 示例讲解

下面这段伪代码把"采集即清洗"的流程走一遍。注意三个坑各对应一行很轻的处理——不去改模型循环本身,只在采集入口拧几个旋钮。

# 采集模式:让最强模型真跑一遍这道题,边跑边清洗
def collect_one(case, strong_model):
    # 【坑一·关降级】给依赖传一个大到不可能触发的阈值,
    #   让大段工具输出原样留在对话里,不被缩成占位符
    deps = build_deps(downgrade_char_threshold=10**9)

    # 真模型 + 真工具 + 真循环跑一遍,拿到完整最终状态
    final = run_loop(case, strong_model, deps)

    # 【坑二·只收自然终止】撞步数闸退出的整条丢掉
    if final.halt_reason != "natural":
        return None

    # 第一道闸:判对(收紧容差,防蒙对)
    if not judge_strict(final.answer, gold=load_gold(case)):
        return None

    # 第二道闸:过程干净打分(工具全成功 / 无尾部失败熔断打转 / 步数达标)
    score = cleanliness(final)            # 越高越干净
    if score is None:
        return None

    # 【坑三·只信对话记录】取数区间/股票代码从 messages 的
    #   工具调用参数里解析,绝不读那份只存哈希的账本(ledger)
    meta = parse_args_from_messages(final.messages)
    meta.update(source_model=strong_model.name,
                n_steps=final.n_steps,
                cleanliness_score=score)   # meta 里【没有】gold / passed

    # 【答案隔离】轨迹和答案落到两个物理隔开的文件
    return Sample(messages=final.messages, meta=meta), \
           Judgement(case_id=case.id, gold=load_gold(case), passed=True)

# 出口:同一道题多条干净轨迹,只留干净度最高的一条
best = max(samples_of_case, key=lambda s: s.meta["cleanliness_score"])

推演:对每道题采样 k=5 次、每题最多保留 2 条,跑完整套题预计产出约 200~280 条干净样本。导出的 meta 只带 source_model / n_steps / cleanliness_score,绝不带 gold/passed。降级阈值线上默认 1320 字、采集时拧到 10**9,这一行之差就是"工具结果完整"和"残缺脏样本"的分界。种子用当前能跑通本系统的最强模型生成,经模型切换模块的注册表挂上去——这正是那个模块第一个真正的用处:换更强的老师只需在注册表加一条配置。

⚖️ 决策对比

维度我们的选择:完整干净轨迹替代方案:只落每题最后一次答案
模型学到什么从空白到答案的整条调工具解题示范只有最终答案,解题过程全丢,没有可学的示范
工程量大:要趟三个坑(关降级 / 剔系统注入 / 只信对话记录)+ 两道筛选闸极小:把最后一行答案存盘即可
答案泄漏产物物理分离,轨迹文件里绝无标准答案答案本身就是数据,等于直接喂答案
样本合法性标准多轮对话结构天生合法,可直接喂监督训练单条答案不是多轮交互,撑不起工具编排的学习
用途能当强化学习前的监督热启动地基顶多当一份答案表,无法热启动

公允裁决:替代方案不是没道理——它最省事,而且如果你的目标真就只是"留一份答案对照表",它完全够用,清洗那三个坑反而是浪费。它的真正短板只在我们的目标上才暴露:监督热启动要让模型学的是"怎么一步步调工具把题解出来"这个过程示范,只留最终答案恰好把这个过程整个丢掉了,等于没有任何可学的东西。我们明知道趟三个坑 + 两道闸工程量更大,仍然这么选,是因为换来的是结构天生合法的标准多轮训练料、并且隔离了答案泄漏——这是强化学习之前监督热启动的地基,省不得。另一处权衡是种子来源:宁可用最强模型当老师,也不用弱模型自蒸馏、更不凭空人工编(标准答案里没有工具序列、手编参数容易跟真实取数漂移),因为热启动的质量直接决定后续强化学习能爬到的天花板,源头不能将就。(基线怎么定靶子见本类第 2 题,工具修好后强化学习瞄准什么见本类第 4 题。)

📌 总结

  • 监督学习"喂什么学什么",所以采集训练料本质是一道清洗工序,不是单纯存盘。
  • 三个坑各对应一道轻处理:关降级(阈值 1320→10⁹,让工具输出原样落盘)、只收自然终止(撞闸丢掉 + 白名单正则剔系统注入)、抽真实参数只信对话记录不信工具账本。
  • 标准答案必须物理隔离:轨迹文件绝无 gold,答案/判分另存一个文件,否则模型学的是"偷看答案"而非"解题轨迹"。
  • 两道筛选闸——判对(复判防蒙对)+ 过程干净(自然终止∧工具全成功∧无尾部失败∧步数达标)给干净度分,同题只留最高分一条。
  • 种子用最强模型当老师(经模型切换模块注册表挂),不弱模型自蒸馏、不人工编;预计 k=5 产出约 200~280 条干净样本,因为热启动质量决定强化学习天花板。

一句话速记:轨迹采集是清洗——关降级补全工具输出、剔拐杖只留自然终止、参数只信对话记录,再把答案物理锁进另一个文件,喂给模型的才是"解题示范"而不是"偷看答案"。

Q4

工具修好之后,为什么强化学习该瞄准"工具调用可靠性 / 多步编排"而不是"计算能力"?这个靶子是怎么定出来的?

★★★★☆
RL 目标定义多步编排工具调用可靠性靶子定法数据驱动决策

🎯 考察点分析

面试官问这道题,想看的不是"你知道 RL 能优化 agent",而是你怎么把一个模糊的"上 RL"诉求,收敛成一个具体、可学、有信号的训练目标。很多人一说强化学习就奔着"让模型更聪明、算得更准"去——这恰恰是这道题想戳破的误区。真正的好答案要证明:你是先把残留失败逐条读完、做完定性分类,再反推出靶子,而不是拍脑袋选了个时髦的方向。

  • 追问:你凭什么说"计算能力没有可学的缺口"?拿什么数据支撑这个判断?
  • 追问:"漏参就放弃""取错代码"这些,为什么不能继续用 prompt 和工具兜底,非得上 RL?
  • 追问:残留失败里有几个是容差边界、判分抖动,你为什么把它们排除出 RL 靶子?不排除会怎样?
  • 追问:RL "擅长可靠编排"是凭感觉说的吗?为什么这类问题正好对上 RL 的强项?

📚 原理讲解

先把背景对齐(细节见本类第 1、第 2 题):我们给"算指标"这类金融任务建了一套自动出题 + 多次重试评测,先发现一个能力断崖——CAGR(年化增长率)那一桶只有 13% 通过。查下来真凶是取数工具的静默截断,不是模型不会算。工具修好后,这一桶从 13% 直接拉到 100%,整套题的通过率从原始 96/141(68%)升到 126/141(89.4%)。

关键的一句话先说在前面:不是"修完工具就没 RL 什么事了",而是更准的——先修工具把"能不能算"解决掉,RL 该瞄准"能不能稳"。这道题的核心就是回答:那个"稳"的靶子,是怎么从数据里读出来的。

靶子是逐条读残留读出来的,不是拍脑袋选的

修完工具还剩 15 个失败。我们没有立刻去猜该学什么,而是把这 15 个一条一条读完、定性归类。读完发现一个反直觉的事实:全题集 0 个"算不出"——只要 agent 拿到了正确数据,指标全都算得对。所以失败压根不是能力缺口,而是 agent 把工具链跑歪、跑断了。具体长这样:

  • 漏 anchor 参数、报错就放弃(~4 个):调交易日历工具时漏了一个必填参数,工具报错说"缺 anchor 无法继续",agent 看懂了这个错误,却不重试,直接放弃。这不是不会算,是不会从一个可恢复的错误里爬出来。
  • 取错股票代码(~1 个):问的是工商银行(601398)的涨幅,agent 却去取了中国银行(601988)的数据。算法没问题,喂进去的"主语"错了。
  • 不照交易日历窗口取数(~2 个):把某个日历日当"三个月前",而标准答案是按交易日历对齐的那一天,两边窗口差几天对不齐,结果就偏。

把这三类放一起看,共同点非常清楚:漏参、取错代码、不照窗口、报错就放弃——全是多步编排没跑稳,没有一个是不会算指标。一句话总结这个洞察:agent 有知识(它看懂了错误),缺的是可靠性。

为什么"能力"不该是靶子,"可靠性"才是

RL 是用奖励信号去学一套策略。哪里有可学的缺口,信号才有去处。计算这块已经 0 失败,等于这块没有缺口可学,拿 RL 去学"把指标算对"是在浪费训练信号——奖励永远是满分,模型学不到任何新东西。

而"漏参重试、取对代码、照窗口取数"这些恰恰是一整套"可靠地把工具链跑完"的策略问题:多步、有状态、每步的对错要到链路末端才结算。这正是 RL 最擅长的形态——它学的不是单点知识,而是跨多步的稳定行为序列。所以靶子要从靶心的"计算能力"外移到中环的"多步编排可靠性"。

还要把"不该 RL 修的"剔出去

剩下约 4 个残留是另一回事:窗口边界刚好顶破很紧的容差、或者 LLM 判分在边界上抖动。这些不是 agent 行为的问题,是工具口径和评测尺子本身的问题。我们明确把它们标成"非 RL 目标"。为什么要专门剔?因为如果不剔,你会拿 RL 去"修评测本身"——奖励信号被噪声毒化,模型学到的是怎么迎合一把抖动的尺子,而不是怎么把活干稳。这一步对应本类第 3 题讲的"奖励必须确定性可复现":能用 RL 学的可靠性问题,和工具/评测口径问题,必须分清。

💻 示例讲解

用一段教学伪代码演示"靶子是怎么从残留里定出来的"——核心是先分类、再判断每一类该归谁管,而不是上来就训:

# 输入:工具修好后剩下的 15 个失败,每个是一条完整轨迹
residual_failures = load_failures(after_tool_fix=True)  # len == 15

buckets = {"计算能力": [], "编排可靠性": [], "评测口径": []}

for f in residual_failures:
    # 第一刀:agent 拿到正确数据后,指标算错了吗?
    if f.got_correct_data and f.metric_wrong:
        buckets["计算能力"].append(f)        # 真·能力缺口 → 实际命中 0 条

    # 第二刀:是 agent 自己把工具链跑歪/跑断的吗?
    #   漏参报错却不重试 / 取错股票代码 / 不照交易日历窗口对齐
    elif f.is_orchestration_fumble():
        buckets["编排可靠性"].append(f)      # ~7 条:这才是 RL 能学的

    # 第三刀:是尺子本身的问题?(顶破紧容差 / 判分边界抖动)
    else:
        buckets["评测口径"].append(f)        # ~4 条:修工具/容差,别拿 RL 修

# 定靶:只有"agent 行为可学 且 奖励能确定性复现"的那一桶,才进 RL
rl_target = buckets["编排可靠性"]            # 漏参重试 / 取对代码 / 照窗口取数

assert len(buckets["计算能力"]) == 0         # 计算没缺口 → 拿 RL 学算指标是浪费信号
assert buckets["评测口径"] not in rl_target  # 口径问题进了靶子会毒化奖励

推演:15 个残留过完这三刀——计算能力桶命中 0 条(这是定靶最硬的证据,直接否掉"RL 学算指标");编排可靠性桶约 7 条(漏 anchor 报错就放弃 ~4 + 取错股票代码 ~1 + 不照窗口取数 ~2),全是有状态的多步行为,正好是 RL 的强项;评测口径桶约 4 条被明确剔出。靶子由此落定:RL 瞄准这 ~7 条代表的"多步编排可靠性",而不是空空的"计算能力"。

⚖️ 决策对比

维度我们的选择:RL 学稳定编排替代方案:RL 学把指标算对
有没有可学的缺口残留 ~7 条全是编排没跑稳,缺口实打实修工具后全题集 0 个"算不出",计算这块没缺口
训练信号利用奖励落在"链路有没有可靠跑完",有梯度可学奖励永远满分,信号被浪费,学不到东西
对不对 RL 的强项多步、有状态的可靠行为序列,正是 RL 擅长的单点算术,prompt/工具早就能搞定,杀鸡用牛刀
解法是系统性还是打地鼠学的是一整套"可靠跑完工具链"的策略,系统解(同我方,替代方案此处无优势)
会不会误伤评测口径容差/判分抖动 ~4 条已剔出靶子,信号干净容易把口径问题也当能力练,毒化奖励

公允裁决:替代方案"让 RL 把指标算对"并非全无道理——如果残留里真有一批"数据对了但算错"的失败,那它就是正解,毕竟算术也是可程序校验、奖励确定性最好的一块(这点本类第 3 题展开)。它输就输在前提不成立:我们把 15 个残留逐条读完,计算能力桶命中 0 条,这块根本没有缺口给它学。而继续用 prompt/工具去兜底每一个 fumble,本轮已经反复自伤过——"data_refs 规矩""摘要捷径"这些单点补丁都曾引入新桶的回归,单测拦不住,堆得越多越脆,这是典型的打地鼠。RL 学的是一整套可靠编排策略,是对症的系统性解法,所以靶子最终落在"多步编排可靠性"而不是"计算能力"。

📌 总结

  • 靶子是读出来的,不是选出来的:把修复后残留的 15 个失败逐条定性,发现 0 个"算不出",问题全在 agent 把工具链跑歪/跑断——这才反推出"该学可靠性"。
  • 计算没缺口,学它是浪费信号:工具修好后 CAGR 桶 13%→100%、整体 96/141→126/141,只要数据对,指标都算得对;RL 学算指标奖励永远满分,学不到东西。
  • 编排可靠性正中 RL 强项:漏参重试、取对代码、照窗口对齐都是有状态的多步行为序列,RL 学的是一整套"可靠跑完工具链"的策略,是系统解,不是单点补丁。
  • 把口径问题剔出靶子:容差边界、判分抖动 ~4 个明确标"非 RL 目标"——拿 RL 去修评测尺子会毒化奖励,能 RL 学的可靠性和工具/口径问题必须分清。
  • 一句话定调:先修工具把"能不能算"解决掉,RL 该瞄准"能不能稳"。

一句话速记:残留 0 个"算不出"、全是编排 fumble——所以 RL 瞄"稳",不瞄"算"。
