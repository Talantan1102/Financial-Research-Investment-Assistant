01项目总览与架构

从这里开始,我们先把 AlphaScout 整体看一遍:它解决什么问题、由哪三块产品组成、技术栈和数据流怎么串起来,以及作为一个「个人作品」它在哪些地方刻意做深、哪些地方刻意留口子。这几道题是面试官摸清项目全貌的开场,也是后面深挖单点的地图。答好它们的关键,是既能讲清「是什么」,又能把「为什么这么选」的产品判断和架构取舍说出来。

Q1

AlphaScout 是什么?请从它的三个产品支柱(深度研究 / 持仓监控 / 对话助手)和整体架构讲起。

★★☆☆☆
产品定位架构总览三支柱use-case 取舍做减法

🎯 考察点分析

这是开场题,面试官表面问"你做了个啥",真正想听的是两件事:一是你能不能用一句话把项目讲清楚(很多人讲了五分钟还没说清自己到底做了什么);二是你这个项目有没有产品判断——是把所有能想到的功能一股脑塞进一个聊天框,还是想清楚了"哪些该做、哪些坚决不做"。一个 LLM 应用岗最怕的就是候选人只会"接个 API 写个 prompt",所以这道题其实在筛"你是不是真的对着场景做过取舍"。

  • 追问:你说有三个支柱,凭什么是这三个?当初是不是想做更多、后来砍掉了?砍的依据是什么?
  • 追问:既然都是"金融助手",为什么不做成一个对话框全包?分成三块不是更累吗?
  • 追问:这三块有没有共用的东西?如果完全独立,那"一个项目"的说法还成立吗?
  • 追问:哪些需求你故意没做?为什么?(这一问是在挖"做减法"的判断力)

📚 原理讲解

先一句话定性:AlphaScout 是一个用大模型(LLM)驱动的金融研究 / 投资助手,面向中国 A 股(就是上海、深圳证券交易所上市的股票)的散户和研究者,是我的个人作品项目。它不是一个万能聊天机器人——这一点是理解整个项目的钥匙。

什么叫"产品支柱"?用日常类比

把 AlphaScout 想成一栋楼,它不是一根柱子撑起来的开间大厅,而是有三根独立的承重柱,每根柱子撑起一类完全不同的使用场景。之所以要分三根而不是一根,是因为这三件事的"节奏"根本不一样,就像家里的烤箱、冰箱、门铃是三台机器:

  • 深度研究(深度尽调)= 烤箱:你下单要一份某只股票的完整尽职调查报告,它要"慢慢烤"——单次约 5 到 10 分钟的慢思考,产出的是一篇长报告。你点了之后去喝杯咖啡再回来。
  • 持仓监控 = 门铃 / 安保:它在后台无人值守地一直盯着你持有的股票,定时扫描有没有出大事——出了重要公告或者价格/财务异常,就"按门铃"提醒你。你平时根本不用碰它,它自己在跑。
  • 对话助手 = 随手问的对讲机:这是实时聊天,你打字问"帮我看看这家最近的现金流",它秒级调用工具、查数据、结合它记住的你之前说过的话来回答。

关键点:慢思考的长报告、后台无人值守的盯盘、实时秒回的对话,这三者在三个维度上根本不同——延迟(几分钟 / 一直在后台 / 秒级)、触发方式(用户点一下 / 定时器自动 / 用户打字)、交付物(一篇报告 / 一条提醒 / 一段回话)。机制天差地别,所以各自成一根柱子。

这三根柱子是"砍出来的",不是一开始就有

这是这道题最值钱的地方。项目早期的叙事是"有 9 个使用场景,共享一套底座",听起来很丰满。但真正坐下来 brainstorm 后,发现这个"9 个"是虚的。我用了一把很硬的尺子来量每个场景:"这个功能能不能独立打得过 ChatGPT?"——也就是,用户为什么不直接去用通用大模型,而要来用我的产品?量下来:

  • 9 个里有 2 个直接砍掉(显式不做):"行业宏观判断"和"金融术语解释"。这两件事恰恰是通用大模型的强项——它读过的宏观资料、它的教学讲解能力,任何一个垂类小产品都做不过。留着它们只会稀释产品定位,所以坦然砍掉。
  • 有 3 个降级成"寄生组件":个股研究、财报速读、报告追问。它们是真痛点,但单独拎出来不够"单飞"的门槛——必须靠平台集成才成立。于是让它们寄生在三根柱子里(比如"报告追问"长在深度研究里,"财报速读"长在持仓监控里),不单独成柱。
  • 真正能独立成立的只有 3 个,就是上面那三根柱子。

所以"做减法"本身就是项目的一个卖点:显式地砍掉 ChatGPT 的强项领域,把精力集中在垂类产品真能做深、做出差异的地方。在面试里,"敢砍"比"啥都做"更值钱。

底座:三根柱子站在同一块地基上

分柱子不等于三个互不相干的项目。三根柱子共享同一套底层基础设施:① 数据——行情和财报都来自 tushare(一个 A 股数据接口);② 知识库(KB)——研报 / 财报 / 政策文档切块入库,供检索;③ 跨会话记忆——记住用户的偏好和历史;④ 大模型网关——统一接各家大模型。三根柱子都插在这块地基上,但各自是独立交付的场景,而不是"同一个大模型 prompt 的不同分支"。这就是"一个项目、三个场景"能同时成立的原因。

💻 示例讲解

用一段伪代码把"三根柱子各自的入口和节奏"画出来——重点不是真实代码,而是让你看清三者的触发方式和机制根本不同,共享的只有底座。

# ① 深度研究:用户点一下 → 慢思考流水线,几分钟后产出一篇报告
def deep_research(ts_code):              # ts_code = 股票代码,如 "600519.SH"
    data = tushare.fetch(ts_code)        # 共享底座:取行情/财报数据
    # 多个 agent 接力跑(估值交叉验证、多空辩论…),慢但深
    report = run_multi_agent_pipeline(data)   # 约 5-10 分钟
    return report                        # 交付物 = 一篇长报告

# ② 持仓监控:没有人点,定时器自己触发(后台无人值守)
@celery_beat(schedule="每 30 分钟,交易日盘中")   # 定时器自动跑
def monitor_positions():
    for pos in get_all_positions():      # 扫每个用户的每只持仓
        events = scan(pos)               # 查 5 类公告 + 价格/财务异动
        if events:                       # 出事了才提醒,平时静默
            push_to_board(pos.user, events)   # 交付物 = 一条提醒

# ③ 对话助手:用户打字 → 实时一边想一边调工具,秒级回话
def chat(user_msg, user_id):
    memory = recall(user_id)             # 共享底座:跨会话记忆
    # 一个"裸 while 循环":模型想 → 调工具 → 看结果 → 再想,直到答完
    while not done:                      # 自研循环,不套重框架
        action = llm.step(user_msg, memory, tools)
        if action.is_tool_call: run_tool(action)   # 实时调数据/KB
    return action.answer                 # 交付物 = 一段回话

# ⚠️ 三个入口完全不同:一个被"点"、一个被"定时器叫醒"、一个被"打字"驱动;
#    但 tushare 数据 / 知识库 / 记忆 / 大模型网关 是同一套底座,被三者共用。

推演:同样是"关心贵州茅台(600519.SH)",三根柱子的反应天差地别。你主动点"深度研究"→ 系统花约 5-10 分钟跑多 agent,回你一篇带估值交叉验证和多空辩论的长报告。你什么都不做→ 持仓监控的定时器每 30 分钟自己醒一次,某天扫到一条"重大重组"公告(属于它盯的 5 类公告之一:财报 / 业绩预告 / ST / 重大重组 / 重大处罚),立刻在看板上"按门铃"提醒你,全程无人值守。你随手打字问"它现金流咋样"→ 对话助手秒级调工具查数,结合记忆里你上次说过"我偏好低负债的票"来组织回答。一份需求、三种节奏——这正是为什么不能用一个对话框全包。

⚖️ 决策对比

维度我们的选择(多支柱架构)替代方案(单体 chatbot:一个对话框 + 一个大 prompt 全包)
延迟节奏三档分治:慢思考几分钟 / 后台常驻 / 实时秒回,各按本来的节奏跑全压进一个对话循环,慢任务卡住快回答,后台盯盘根本塞不进去
触发方式点一下 / 定时器自动 / 打字,三种入口各自独立只有"用户打字"一种入口,无法做"无人值守"的后台监控
交付物长报告 / 提醒卡 / 对话,各自打磨到位都被压成"一段聊天回复",长报告与盯盘提醒都做不深
上手成本用户要理解三个入口,认知略重一个对话框,零学习成本,最直观
实现/维护要维护 3 套交付路径,工程量更大一套代码全包,最省事
产品定位显式砍掉 ChatGPT 强项,"做减法"成简历亮点啥都想做,定位模糊,和通用 chatbot 撞车

公允裁决:单体 chatbot 绝不是稻草人,它有真实优点——一个对话框零学习成本、一套代码最省事、迭代最快,对"需求同质、都能在几秒内答完"的场景(比如纯问答机器人)它就是正解,分支柱反而是过度设计。我们仍选多支柱,核心理由是这三类需求在延迟、触发、交付物上根本不是一类东西:你没法让一个"等用户打字"的对话循环去做"无人值守、定时器叫醒"的后台盯盘,也没法让一个追求秒回的循环里嵌一个要慢烤 5-10 分钟的报告流水线——硬塞进去,结果是每一块都做不深。代价我们认:要多维护 3 套交付路径而不是 1 套。但换来的是每个场景都按它本来的样子被打磨,外加一个更值钱的副产品——"敢砍掉 ChatGPT 强项"这个做减法的产品判断,在面试里比"功能堆得多"更能体现成熟度。

📌 总结

  • 一句话定性:AlphaScout 是个 LLM 驱动的 A 股研究 / 投资助手个人作品,不是万能 chatbot,而是围绕 3 根相互独立的产品支柱组织。
  • 三根柱子各有节奏:深度研究(慢思考约 5-10 分钟出长报告,多 agent 流水线)/ 持仓监控(后台无人值守,Celery 定时引擎扫 5 类公告 + 异动)/ 对话助手(实时秒回,自研裸 while 工具调用循环)——延迟、触发、交付物三方面根本不同。
  • 共享一块底座:三柱都接同一套 tushare 数据 + 知识库 + 跨会话记忆 + 大模型网关,所以"一个项目、三个场景"同时成立。
  • 是砍出来的:原 9 个场景用"能否独立打过 ChatGPT"这把尺子重新分类 → 3 支柱 + 3 寄生组件 + 2 个显式不做(行业判断 / 术语解释);"敢砍 ChatGPT 强项"这个做减法的产品判断,是比堆功能更值钱的亮点。
  • 为何不做单体 chatbot:三类需求延迟/触发/交付物根本不是一类东西,硬塞进一个对话循环会每块都做不深;代价是要维护 3 套交付路径(详细技术栈与数据流见本类第 3 题,个人作品的取舍见本类第 2 题)。

一句话速记:AlphaScout = 三根节奏不同的柱子(慢报告 / 后台盯盘 / 实时对话)站在同一块底座上,加上"敢砍掉 ChatGPT 强项"的做减法判断。

Q2

这是个人作品项目,你怎么权衡"生产级健壮"和"体现算法 + 应用设计深度"?哪些地方刻意做厚、哪些刻意留口子?

★★★☆☆
作品定位工程取舍克制主义技术深度架构留口子

🎯 考察点分析

这道题表面问"你怎么取舍",其实面试官在确认三件事:你有没有清晰的项目定位(知道这是作品不是上线产品),你砍东西时有没有判据(还是凭感觉乱砍),以及你留口子时是不是真留了演进能力(还是嘴上说说)。能把"做厚"和"留口子"各举出有迹可循的例子,并说清两者背后是同一条准绳,才算答到点子上。

  • 追问:你说"砍掉冗余",那多租户、灰度发布这种企业能力你也砍了?凭什么判断它是负资产而不是必需品?
  • 追问:你明明定位是"不追求生产级",为什么持仓监控偏偏上了 Celery + Redis + 独立数据库这套工业级架构?这不矛盾吗?
  • 追问:"留口子"和"功能没做完"边界在哪?怎么证明你是有意识地留,而不是写不完找借口?
  • 追问:chat 控制流你为什么放着 LangGraph 现成的崩溃恢复不用,自己手写一个裸循环?生产场景这不是开倒车吗?

📚 原理讲解

核心是先认清这是个人作品(portfolio):目标不是扛住真实流量,而是让看代码的人(面试官、读者)能看出我在大模型算法和大模型应用设计上做了哪些非显然的判断。定位变了,"好"的标准也跟着变——生产级项目里"健壮、兼容、可运维"是硬指标,作品级项目里它们退居二线,头排坐的是"可讲性"。

一条贯穿全局的判据:可讲性

我给每个要留下来的主路径都过一遍同一个问题:站在这段代码前,面试官能不能看出这里用了什么大模型技术、为什么这么设计、做了哪些不显然的选择? 能,就值得做厚;不能,只是把功能堆全,那它就是负资产。多租户、复杂权限体系、灰度发布这类企业抽象,讲不出任何算法或应用设计的深度,只会稀释代码、增加维护面——所以"砍掉冗余实现"的优先级,被我放在"保持兼容"之上。

做厚:显式违反克制默认,只为换技术深度

我的产品默认是有判断的克制(能砍的功能尽量砍,免得陷进"什么都想做、永远不交付")。但有几处我故意违反这个默认去做厚——判据还是可讲性。最典型的是持仓监控引擎:详情卡预生成走 Celery + Redis 异步队列、监控数据从 sqlite 改成统一的 PostgreSQL。这两条都被明确记成"违反克制默认",理由是这套异步任务 + 单一数据库的工业级架构,是作品里看得见、讲得出的技术深度。同类还有跨会话记忆(双时间轴图谱 + 三路混合检索)和对话评估体系。

留口子:架构留接口,而非功能做满

留口子的手法是"架构上预留扩展点,功能上只做最小子集":第一版只实现够讲清主线的部分,后续版本沿接口平滑扩展。三个具体例子——推送通道写成空实现的接口(签名在、逻辑暂空)、静默仓位字段预留默认 false、多账户的用户标识 schema 留在数据库里但界面不暴露。这样既不破坏整体那股"一致的克制气质",又保住了演进能力。能接受的简化包括:用 mock 服务替真服务、单进程部署、简化运维。

💻 示例讲解

把"判据"写成一段伪代码,最能说明做厚和留口子其实是同一把尺子量出来的两端:

# 决策准绳:对每个候选特性,只问一个问题——它有没有"可讲性"
def 怎么处理(特性):
    # 可讲性 = 面试官能看出"用了什么大模型技术 + 为什么这么选"
    if 特性.能展示算法或应用设计深度:
        return "做厚"        # 即使违反克制默认也上,比如监控引擎的异步队列
    if 特性.是企业抽象 and not 特性.能讲出深度:
        return "直接砍"      # 多租户/复杂权限/灰度——负资产,砍它优先于保兼容
    if 特性.以后可能要 and 现在讲不出新深度:
        return "留口子"      # 架构上留接口,功能上先不做满

# "留口子"长什么样:接口在、字段在,但实现/界面先空着
class 推送通道(协议):
    def 发送(self, 消息): ...           # 空实现,第一版不接真渠道

is_silenced = 字段(默认=False)          # 静默仓位:字段预留,界面暂不暴露
user_id     = 字段()                    # 多账户:schema 留着,界面只给单用户

# 对比"做厚":同一个项目里,监控引擎敢上工业级三件套
监控引擎 = Celery 异步队列 + Redis + 统一的 PostgreSQL   # 故意违反克制,换可见深度

推演:带数字看就更清楚。持仓监控引擎共落地 5 个工程决策,其中"详情卡预生成"和"监控库改 PG"2 个被明确标为违反克制默认——占比不到一半,说明做厚是精挑的,不是无脑堆。另一端的留口子(推送空实现 / 静默字段默认 false / 多账户 schema 隐藏),代码量几乎为零却保住了 v1.x 扩展路径。一头肯花 5 个决策的重投入,一头近乎零成本占位,落差恰恰证明这把尺子在真用。

⚖️ 决策对比

维度我们的选择(作品级·有判断的克制)替代方案(生产级·框架白送 + 企业抽象)
头号指标可讲性——能看出用了什么大模型技术、为什么这么选健壮 / 兼容 / 可运维,扛真实流量与故障

没做满的功能架构留接口(空实现/默认字段/隐藏 schema),v1.x 再扩一次做满,或上完整 feature flag 灰度体系

崩溃恢复 / 边界容错取消=整轮重跑、审批门自造,不追求自动恢复框架级 checkpoint 自动续跑,边界情况兜得全
部署 / 外部依赖单进程 + mock 服务可接受,简化运维多进程 / 容器编排 / 真实第三方接入

公允裁决:替代方案真不是稻草人——LangGraph 的 checkpoint 与中断恢复是实打实的工程便利,生产环境里"进程崩了能从断点续跑"价值极高;企业抽象也确实是上线必备。但放到个人作品这个语境,决策权重整个翻了个:对我而言"框架便利 / 崩溃恢复"几乎不计分,真正计分的是叙事深度(控制流 100% 是我自己写的、每一步都讲得清)和可读性(约 200 行单文件读完整个对话循环)。所以我看完逐步轨迹级和业务级两轮对比后,仍然选了裸 while——不是因为它更健壮,恰恰是因为我不拿健壮当筹码。同理,企业抽象在生产是资产、在作品是负资产,差别只在谁来读这份代码。

Q3

整个系统的技术栈和数据流是怎样的?一条用户消息从前端发出到落库,经过哪些组件?

★★★☆☆
技术栈数据流自有控制流持久化解耦

🎯 考察点分析

这道题表面问"用了哪些技术、消息怎么走",真正想看的是你能不能端到端地把一个 AI 对话系统讲通:每一层选了什么、为什么这么分,以及最关键的——一条消息进来之后,推理这件事到底跑在哪个进程、状态存在哪、前端断了会不会把任务弄丢。面试官最怕的是候选人只会背技术名词("我们用了 React + FastAPI + Redis"),却讲不清这些组件之间真正的数据流和职责边界。能把"DB 是唯一真相、推理在独立进程、实时层只做转发"这套解耦讲明白,才算真的搭过会话型系统。

  • 追问:用户发完消息就关了浏览器,这条回答还会不会跑完、会不会落库?为什么?
  • 追问:推理为什么不在处理 HTTP 请求的那个进程里直接跑,非要丢给一个独立的后台进程?
  • 追问:前端看到的是逐字打字,这字到底是后端一个一个 token 推过来的,还是前端自己造的?
  • 追问:对话循环的"大脑"是一个现成的 agent 框架,还是你自己写的?中间出错、打转、烧钱了谁来兜?

📚 原理讲解

先把技术栈按层摆开,再讲一条消息怎么穿过它们。

技术栈分层:各层选了什么

前端是 React 19 + Vite,状态管理用 valtio(轻量的可变对象 + 订阅,无 reducer 样板,前端怎么组织见本类第 1 题对应的前端分类)。后端是 Python 的 FastAPI。大模型走阿里云 DashScope 托管的几个模型(qwen-plus / qwen-max / deepseek-v4-flash),统一经一个 OpenAI 兼容客户端调用,用的是原生函数调用(模型自己决定要不要调工具、调哪个)——这点很关键,后面的对话循环就建在它之上。数据源是 tushare(A 股行情、财报),默认走 mock 方便开发,一个开关能切真数据。存储是双层:Postgres 当唯一的持久化真相库,Redis 当实时事件层和队列;离线的重活儿走 Celery 异步任务;向量检索(知识库、长期记忆)用 Milvus。这套分层不是为炫技堆的,每个组件都对应一个明确职责,下面这条数据流会把它们一个个串起来。

一条消息的端到端旅程

用户在对话框敲完一句话点发送,前端发一个 POST 到对话接口。后端入口干的第一件事不是去调模型,而是先落库:把这条用户消息写进 Postgres,同时建一条"任务"记录(chat_task),状态机标成 queued(排队中)。这一步是整套设计的地基——数据库是唯一真相:只要消息和任务进了库,后面无论前端断不断、进程崩不崩,这件事都"算数了"。

接着任务被入队,真正的推理交给一个独立的后台进程(Celery worker)去跑,而不是在处理这个 HTTP 请求的 web 进程里同步算。这是第二个核心解耦:推理和传输分家。web 进程处理完"落库 + 入队"就可以返回了,它的生命周期跟推理无关;哪怕用户立刻关掉页面、哪怕 web 进程自己崩了,后台 worker 照样把这一轮跑完。worker 在收尾的 finally 块里 commit 助手回复到 Postgres——所以"前端断开"和"任务完整性"被彻底剥离开了。

对话循环:自研的"裸 while 工具调用环"

worker 里跑的不是某个现成框架的图,而是一段自己写的 while 循环(代码在 backend/app/chatloop/)。一圈的节拍是:把当前窗口喂给单个模型(规划和回复合成一个角色)→ 模型用原生函数调用决定这圈调哪些工具 → 派发工具(既有 MCP 工具也有进程内工具,核心 6 个给完整说明书、其余的先给"瘦条目"按需展开,叫渐进披露)→ 把结果记进台账 → 回到圈首再来一轮,直到模型不再调工具、自然给出答案。为什么自己写而不用框架,见下面的决策对比。

每一圈圈首都要过四道终止闸,它们是零 I/O 的纯函数(只看状态、不碰外部),专门防循环失控:① 硬步数上限(默认 12 圈,撞了就停);② 预算闸(每轮对话烧到 0.10 元或 12 万 token 就停,防一句话把钱烧穿);③ 打转检测(这一圈调的工具签名集合跟上一圈一模一样 → 判定原地打转);④ 跨签名连续失败(换着参数硬试、连续失败 5 次 → 判定在乱试)。另有一个烧签名机制:同一个工具用同样参数失败到 3 次,这个签名就被封堵,后面再想这么调直接拒掉,逼模型换方法。撞闸的处理也讲究:不是静默截断(那样用户会看到回答莫名其妙断在半截),而是 force_conclude——喂一句系统提示、把工具开关锁死,逼模型基于已有信息把话说完,并如实告诉用户"到上限了"。

实时层:Redis Streams + 前端打字机

worker 一边跑一边把事件(token、调了哪个工具、费用更新、结束等)XADD 进 Redis Streams(像一条带序号、可重放的日志,留 24 小时)。web 端有个 SSE 接口去 XREAD 这条流,把事件转发给前端。注意这里的分工:web 只做转发,不做推理。前端拿到 token 后,用 RAF(浏览器渲染节拍)做打字机模拟,以约 30 字/秒的速度逐字吐出——视觉上等同 token 级流式,但调速权在前端。因为有 Streams 的序号,断线重连只要带上"我上次读到第几号"就能续读不重复,这点见前端分类的 SSE 题,这里不展开。

把"恢复能力"单独承担起来

因为 DB 是真相、推理在独立进程,系统就能在这之上挂一圈韧性能力:任务有 6 个状态(排队 / 运行 / 完成 / 已取消 / 部分 / 出错);取消走 Redis 的发布订阅(一个任务一个频道),worker 收到信号就停下、把已生成的部分存成"部分完成";重试能从已存的状态接着来;还有一个 Celery 定时任务每 60 秒扫一遍"卡死的任务"(比如 worker 崩了)自动标错、让前端能重试。这些都不依赖任何图框架,是持久化和解耦这套地基自己撑起来的。

💻 示例讲解

下面这段教学伪代码把"入口落库 + 入队"和"后台 worker 跑循环 + 四道闸"两段串起来。重点看职责怎么分、闸在哪一步拦,不是源码细节。

# ① web 入口:只做"落库 + 入队",绝不在这里跑模型
async def post_chat(user_msg, session_id):
    # 先把用户消息和任务写进 Postgres —— 数据库是唯一真相,先落了才算数
    db.insert_message(session_id, role="user", text=user_msg)
    task = db.create_chat_task(session_id, status="queued")   # 6 状态机的起点
    enqueue_worker(task.id)        # 推理丢给独立后台进程,本请求立刻可以返回
    return {"task_id": task.id}    # 前端拿这个 id 去订阅实时流(关页面也不影响下面继续跑)

# ② 后台 worker:跑自研的 while 工具调用循环
def run_chat_task(task):
    state = init_state(task)
    try:
        while True:
            # 圈首先过四道终止闸(纯函数,只看状态、不碰外部)
            halt = check_gates(state, cfg)        # 步数12 / 预算0.10元 / 打转 / 连续失败5次
            if halt:
                # 撞闸不静默截断:逼模型基于已有信息收尾,并如实告知用户
                return force_conclude(state, reason=halt)

            # 单个模型一次决策:原生函数调用决定这圈调哪些工具
            step = llm.stream_step(window=assemble_context(state), tools=schemas)
            emit_to_redis_stream(task.id, step.tokens)   # 边跑边把 token XADD 进 Redis Streams

            if not step.tool_calls:        # 模型不调工具了 = 自然停,这就是答案
                return state

            calls = filter_burned(step.tool_calls, state)  # 烧签名:失败满3次的调用直接拒
            results = tool_hub.dispatch(calls, state)       # 派发 MCP / 进程内工具
            state = record(state, results)                  # 结果记进台账,供下一圈打转/失败判定
    finally:
        # 不管正常结束、撞闸、还是被取消,收尾都把助手回复 commit 进 Postgres
        db.commit_assistant_message(task, state)            # 前端断没断,都不影响这条落库

推演:设想用户问"帮我看下这六只持仓最近怎么样",发完就关了浏览器。入口已经把用户消息和任务落了库(queued),web 进程返回、用户的页面关了也无所谓。后台 worker 接手:第 1 圈模型决定批量查这六只的行情和公告,第 2~3 圈逐个解读……正常约五圈就收敛(步数上限设 12 就是给了一倍垫)。假设其中某只的某个工具用同样参数连查三次都失败,烧签名机制把它封堵,逼模型换个角度作答而不是死磕。整轮烧了大概 0.04 元,没碰到 0.10 元的预算闸。worker 在 finally 里把最终回答 commit 进库——用户半小时后重开页面,看到的是一条完整的回答,而不是"任务白跑了"。如果当时用户没关页面,他看到的是约 30 字/秒的逐字打字效果,字来自 Redis Streams 转发、由前端打字机调速。

⚖️ 决策对比

维度我们的选择(自有控制流:裸 while + 自造闸/取消/重试)替代方案(框架编排:LangGraph 回环图,白送 checkpoint/interrupt)
控制流来源一段自己写的 while 循环,每一步都看得见、改得动用图的节点和边描述流程,运行由框架调度
中间状态快照不存每圈快照;重试 = 整轮从头重跑框架自动给每圈存 checkpoint,能从中间圈续
恢复能力来自哪独立 worker + Redis Streams + DB 是真相,单独承担很大一部分恢复能力内置在图框架里
循环失控防护自造四道闸 + 烧签名,撞闸 force_conclude 收尾需自己在图里加预算/打转判定,框架不默认管
可读性 / 叙事新人顺着 while 读一遍就懂,适合作品讲解得先懂框架的图心智模型才能读懂流程
上手成本高:流式、取消、重试这些基础设施全自己搭低:框架现成给你 checkpoint / interrupt

公允裁决:框架编排不是稻草人——它白送的每圈 checkpoint、内置中断、成熟的图调度,在很多 agent 项目里是实打实省事的,真要做"从中间某一步精确续跑"它几乎是首选。我们之所以仍选裸 while,核心理由是这套系统的"一轮对话是原子的"语义:用户重试就是整轮从头重跑,中间圈的 checkpoint 根本没有消费者——框架最值钱的那个能力在这里用不上,留着反而是负担。而真正需要的恢复能力(关页面续看、进程崩了不丢任务、取消保留部分结果),已经由"独立 worker + Redis Streams + 数据库是真相"这套地基单独扛起来了,不依赖图框架。再叠加项目本身追求控制流自有、可读、好作为作品讲述的取向,裸 while 是更贴合的选择——而不是因为框架"不好"。

📌 总结

  • 技术栈分层:前端 React 19 + Vite + valtio;后端 FastAPI;大模型走 DashScope 托管的 qwen/deepseek 经 OpenAI 兼容客户端 + 原生函数调用;数据源 tushare(默认 mock 可切真);存储是 Postgres 持久 + Redis 实时/队列,异步走 Celery,向量检索用 Milvus。
  • 一条消息的旅程:POST 入口先落库(写用户消息 + 建任务,标 queued)→ 入队 → 独立 worker 跑循环 → 事件经 Redis Streams 转发回前端 → finally 把助手回复 commit 进 Postgres。
  • 两个核心解耦:数据库是唯一真相(落了才算数)、推理与传输分家(在独立 worker 跑)——所以前端断开、web 崩了都不影响任务完整性。
  • 对话大脑是自研的裸 while 工具调用循环:单模型 + 原生函数调用决定调哪些工具,每圈过四道纯函数终止闸(步数 12 / 预算 0.10 元·12 万 token / 打转 / 连续失败 5 次)+ 烧签名(失败 3 次封堵),撞闸 force_conclude 而非静默截断。
  • 实时层与落库分开:worker XADD 事件进 Redis Streams,web 只做 XREAD 转发不推理,前端用 RAF 打字机约 30 字/秒模拟逐字流式;恢复能力(6 状态机 + 取消 + 重试 + 60s stale 自愈)由这套地基单独承担,不依赖图框架。

一句话速记:POST 落库入队 → 独立 worker 跑裸 while 循环(单模型 + 原生函数调用 + 四道闸)→ 事件经 Redis Streams 转发给前端打字机 → finally 落库到 PG;DB 是唯一真相、推理与传输解耦,所以断线不丢任务。

Q4

这个项目里你最自豪、或者最难的技术点是什么?为什么难?

★★★★☆
技术亮点跨会话记忆自有控制流评估方法论深做法 vs 浅做法

🎯 考察点分析

这是一道"开放式深挖题"。面试官不在乎你选哪个亮点,而是在看三件事:你能不能说清一个东西到底难在哪(而不是只说"我做了 X");你的"难"是不是真的工程难题(而不是把简单事讲玄乎);以及你有没有意识到同一个需求有浅做法和深做法,你为什么愿意付深做法的代价。回答最忌讳的是堆术语、单点炫技,或者把"我用了某框架"当成技术深度。

  • 追问:"这个难点,最浅的实现长什么样?差在哪?"——逼你给出浅 vs 深的对照,证明你知道便宜路在哪、为什么没走。
  • 追问:"为这个深做法你多付了多少工程量?值吗?"——看你有没有成本意识,是不是为难而难。
  • 追问:"如果再来一次,哪个地方你会做浅一点?"——看你能不能反过来批判自己的选择。
  • 追问:"这个东西怎么证明它真的对?"——把话题引到评估,看你是不是只会写不会验。

📚 原理讲解

我会先给一个统一的判断标准:一个技术点难不难,看的是"非显然选择的密度",不是单点有多炫。意思是,在这个模块里,每隔几步就会遇到一个"主流怎么做、我为什么偏离"的岔路口,而且每个岔路口的选择都得有据可查。我手里有三个这样的亮点,面试时我会挑一个深讲(通常是跨会话记忆),另两个点到。

亮点一:跨会话长期记忆(让助手"记得你说过的话")

浅做法是:每次对话把历史摘要塞回提示词。问题是它表达不了"演化"——比如"用户三个月前重仓某只股票,上个月清仓了"。摘要里只有一句最新结论,旧态丢了,而"态度怎么变的"恰恰是投资场景最值钱的信息。

我的深做法是 MemGPT 风(让模型用工具自己读写记忆)+ 知识图后端的杂交,共 8 个里程碑落地。最难的是三处:第一,双时间轴模型(学术上叫 bi-temporal,源自 Snodgrass 1993),给每条记忆挂四个时间字段——"现实世界里这件事从何时到何时成立"(生效起/止)+"系统何时记下/何时作废了这条记录"(记录时刻/作废时刻)。两条时间轴分开,才能既回答"他现在怎么看"也回答"他上个月怎么看",还能区分"他真的改主意了"和"我之前记错了"。第二,三路混合检索 + 时间感知排序:关键词(BM25)、向量、图谱三路一起召回,再用一个带时间衰减的融合公式排序(score = Σ 1/(60+rank) × 重要性权重 × 时间衰减),衰减的半衰期按关系类型分档——"持有/卖出"这种慢变的给 365 天,"偏好/回避"给 180 天,"看过/研究过"给 90 天。第三,三个库写一致:同一条记忆要同时落到关系库、图库(Apache AGE)、向量库(Milvus),靠一个幂等唯一键 + 对账任务兜底,还专门压了 4 个故障注入场景验证。这一摊撞实了 16 个工业难题 + 6 条算法补丁。

亮点二:对话 agent 的裸 while 控制循环(自己写"思考循环",不套框架)

浅做法是调一个 agent 框架白送的循环。我的深做法是把工业级 agent loop 的事实标准逐项自己实现:四道终止闸(自然停 / 步数上限 / 预算上限 / 回合边界)、打转检测(给每圈的工具调用算个"签名指纹",这圈和上圈签名一样就判定在打转)、烧签名(同一个签名失败 3 次就永久封堵,不让它再试)、上下文窗口四区(稳定前缀 / 历史区 / 本回合轨迹 / 尾部动态区——动态状态绝不能进前缀,否则前缀一变,缓存折扣全废)、工具渐进披露、以及插话(steering)走 Redis List 而不走发布订阅——因为插话不能丢、取消可以丢,两路信号可靠性要求不同,就该用两种原语。详细机制见本类第 3 题的数据流部分。这套设计经过三轮 20 路对抗核查调研,每处偏离主流都标了可溯源的取舍理由。

亮点三:把"个人作品"的评估做出深度

浅做法是端到端丢给一个大模型打个分。我沉淀了对话/工具型 agent 评估的四个相互独立的角度:回答质量(用强模型当裁判)、任务完成(比对话结束后的数据库终态)、过程轨迹(比对工具调用序列)、生产在线信号。并真的落了地:记忆有 50 条金标准 + 4 个指标、30 条投毒攻击用例、还有一个 5 段序列的双时间轴差分测试。这里有两条暗线值得讲——强模型当裁判有系统性偏差(偏好第一个/偏好长答案)必须去偏;趋势是评"环境最终被改成什么状态"而非"匹配输出文本",用"连做 k 次都成功的概率"度量可靠性。详见本类第 2 题对"哪里做厚"的讨论。

💻 示例讲解

我用记忆亮点里最具体的一处——双时间轴怎么表达"态度演化"——来演示浅做法和深做法的差距。下面是教学伪代码,关键是看"记一条记忆时,系统到底存了什么"。

# 浅做法:摘要里只有一句最新结论,旧态被覆盖
summary = "用户偏好:看好新能源板块"   # 上个月那句"重仓白酒"被冲掉了,无法追溯

# 深做法:每条记忆挂两条时间轴,旧态不删只标失效
def record_view(user, target, view, today):
    # 找到这个用户对同一标的、还"在生效"的旧记录
    old = find_active(user, target)
    if old:
        # 不删旧记录,只把它的"现实生效止"和"系统作废时刻"补上
        old.valid_to = today        # 现实世界:这个态度到今天为止
        old.invalidated_at = today  # 系统:今天起这条不再是最新结论
    # 写一条新记录,生效起=今天,生效止暂空(=至今仍成立)
    return Memory(user, target, view,
                  valid_from=today, valid_to=None,
                  recorded_at=today, invalidated_at=None)

# 于是两类问题都能答,因为旧态还在库里:
#   "他现在怎么看?"   -> 取 valid_to IS NULL 的那条
#   "他三个月前怎么看?" -> 取 valid_from <= 那天 <= valid_to 的那条

推演:假设用户 3 月说"重仓白酒",5 月说"清仓换新能源"。浅做法到 5 月时库里只剩"看好新能源",再问"他对白酒态度变了吗"只能瞎猜。深做法库里有两条记录:白酒那条 valid_from=3月、valid_to=5月,新能源那条 valid_from=5月、valid_to=空。问"现在"取后者,问"3 月"取前者,问"变了吗"直接看到两条对比——表达力是完整的。再叠加检索侧的时间衰减:τ 给"持有/卖出"365 天,意味着半年前的持仓信息仍有较高权重不会立刻沉底,这正是投资场景需要的"慢记忆"。

⚖️ 决策对比

维度我们的选择(深做法)替代方案(浅层实现 / 候选人自选 highlight)
记忆怎么存双时间轴知识图 + 三路混合检索 + 时间感知排序每轮把历史摘要塞回提示词
能不能答"演化"能:旧态不删,标失效;现在/过去都可查不能:摘要只剩最新一句,旧态被覆盖
控制循环怎么来裸 while 自造四道闸/打转/烧签名/窗口四区调框架白送的 loop
偏离主流的依据每处有可溯源取舍(三轮 20 路对抗核查)框架默认即答案,无需解释
怎么证明对四角度评估 + 投毒 30 case + 时序差分 5 序列端到端丢给一个大模型打个分
工程量代价大(16 工业难题 + 6 算法补丁 / 逐闸自造)小(几乎开箱即用)

公允裁决:浅做法绝不是错——对绝大多数项目它就是对的:上线快、维护省、依赖少,框架白送的循环和"塞摘要"足以覆盖大量场景,真出问题再升级也来得及。我之所以仍走深做法,理由很窄:一是这是个人作品,刻意要体现算法 + 应用设计深度(本类第 2 题专门讲了"哪里做厚、哪里留口子"的取舍),浅做法没有可讲性;二是投资场景的"态度演化""零容忍幻觉"恰好是浅做法的盲区。所以我会诚实承认:如果是赶交付的生产项目,记忆我会先上"塞摘要 + 向量检索",控制流我会先用框架——把深做法留到指标真出问题再做。深做法换来的不是"更快上线",而是"非显然选择的密度",这才是这道题想要的东西。

📌 总结

  • 先立判断标准再选亮点:难不难看"非显然选择的密度",不是单点炫技;手里备三个亮点(记忆 / 控制循环 / 评估),深讲一个、点到两个。
  • 记忆:双时间轴四字段让"态度演化"可查 + 三路混合检索 + 时间衰减排序(τ 分 365/180/90 天)+ 三库写一致,撞实 16 工业难题 + 6 算法补丁。
  • 控制循环:裸 while 自造四道闸 + 打转检测 + 烧签名 + 窗口四区(动态状态不进前缀保 KV-cache 折扣),每处偏离主流都标取舍。
  • 评估:四角度方法论 + 50 金标准 4 指标 + 投毒 30 case + 时序差分 5 序列,两条暗线(裁判去偏 / 评环境终态 + k 次通过率)。
  • 给公允裁决:浅做法上线快维护省,生产项目我会先走浅做法;深做法的代价是工程量,换来的是可讲性而非更快交付——诚实承认这点反而加分。

一句话速记:挑一个难点深讲它的"浅 vs 深"对照,把难度落在"非显然选择的密度"上——记忆做双时间轴、控制流自造每道闸、评估做四角度,而不是塞摘要 / 套框架 / 大模型打分。
