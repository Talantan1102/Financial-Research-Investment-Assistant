08会话持久化与可靠性

把一个会话式 AI 助手从「单进程长连接」改造成「推理脱离网页请求生命周期」的可靠系统:消息进数据库不蒸发、关页面重开能接着看、能取消能重试、卡死能自愈。这一类带你走完整条会话持久化与容错链路——从三个根因的逐个根治,到数据库即真相 + 推理进程解耦的架构骨架,再到取消/重试/自愈的具体机制。前两题相对入门,后面逐步深入到状态机收敛与系统化调试方法论。

Q1

对话会丢、会卡住、会前后不一致——这三个根因分别是什么?你怎么逐个根治的?

★★★☆☆
会话持久化数据库即真相根因分析SSE 流式

🎯 考察点分析

面试官抛出三个症状(丢、卡、不一致),其实是在看你能不能把表象拆成根因、再判断这些根因之间是不是互相耦合的。初级答法会把它当三个独立 bug 一个个补;资深答法会先识别出它们彼此喂养,然后给一个有先后次序的根治路线,而不是东打一枪西打一枪。

  • 追问:三个根因里,哪一个是「源头」?为什么单修任何一个都不解决问题?
  • 追问:你说前端有重连逻辑,那为什么测试是绿的、生产却 404?(考你对「伪绿」的敏感度)
  • 追问:你没有一次性大改,而是分了三卷。每一卷分别覆盖了哪个根因?为什么这个顺序?
  • 追问:把会话留在内存里不是更简单吗?你为什么非要引入数据库这一层?

📚 原理讲解

先把三个症状对到三个根因。我当时审视聊天会话的生命周期,发现的不是三个孤立的 bug,而是一条互相喂养的因果链。

根因一:中间状态完全不入库(对应「会丢」)

原来的流式处理函数把模型吐出来的事件,直接通过 SSE(服务器推送给浏览器的长连接)一股脑「吐」给页面,吐完就不留底了。整条链路里没有任何一处把消息写进数据库——唯一例外是「研报升级」那条岔路写过一条消息。结果就是:用户发的话、助手回的话,全都不进库。页面一刷新,历史就蒸发。这是源头。

根因二:服务端感知不到客户端断开(对应「会卡 / 算力白烧」)

流式函数里没有「检测浏览器是否已经断开」这一步。所以你关掉页面后,后台推理照样跑到结束——但因为根因一不写库,这些辛苦算出来的结果没有任何接收者,等于算力白烧。注意它怎么被根因一喂养的:正因为不入库,断开之后产物才没人接;如果当初入了库,哪怕你断开,结果也安静地躺在库里等你回来取。

根因三:前端假装能重连(对应「前后不一致」)

前端代码里煞有介事地拼了一个重连用的地址,想用「上次收到的事件号」去续上断掉的流。但后端压根没有这个接收地址——只有一个发起对话的入口。生产环境里这个重连请求必定 404,然后无脑重试到放弃。更隐蔽的是:前端测试用 mock 把这条不存在的路径假装实现了,所以测试一片绿,是伪绿。它同样被前两个根因喂养:后端因为没解耦、没续看能力,所以根本接不住重连;前端只好「假装」自己能重连。

关键:三者耦合,只修一个等于没修

这就是这道题的核心。不入库 → 断开后产物无人接收;后端接不住 → 前端只能假重连。你单独修任何一个,另外两个还在拖后腿。所以正确的解法不是补三个 bug,而是换一个底座:让数据库成为唯一可信来源,推理过程不再「飞」出去,而是每一步都落盘。

💻 示例讲解

先看「飞出去」的旧写法——为什么它三个根因同时踩中:

# ❌ 旧写法:事件直接吐给浏览器,吐完不留底
async def _stream_chat(request, prompt):
    async for event in graph.astream_events(prompt):   # 模型/工具一步步产出事件
        yield to_sse(event)                            # 直接推给浏览器,推完即焚
    # 注意:这里没有 append_message —— 用户和助手的话都不入库
    # 也没有 request.is_disconnected() —— 浏览器关了后台还在跑,但产物没人接

再看换底座之后的骨架。两条关键改动:发起入口先把用户消息落库;推理搬进独立后台进程,在 finally 块里无条件落库助手回复(断不断开都落):

# ✅ 新写法:数据库即真相,推理过程在后台落盘
# 第一步,发起入口:先把用户这句话写进库,再排一个后台任务
async def post_chat(request, prompt):
    repo.append_message(role="user", text=prompt)      # 用户消息立刻入库,刷新也不丢
    task = repo.create_task(status="queued")           # 建一条任务记录
    enqueue(run_chat_async, task.id)                   # 推理交给独立后台进程
    return {"task_id": task.id}                         # 浏览器拿到任务号,之后凭它续看

# 第二步,后台进程:跑完(或被打断)都要在 finally 里落盘
async def run_chat_async(task_id):
    partial = []
    try:
        async for event in graph.astream_events(...):
            partial.append(event)
            event_bus.push(task_id, event)             # 推到事件总线,谁订阅谁能看
    finally:
        # 关键:无论正常结束、还是浏览器早断了,助手回复都在这里入库
        repo.append_message(role="assistant", text="".join(partial))
        repo.update_task(task_id, status="done")

推演:用户发问后第 2 秒关掉页面。旧底座:后台跑满 30 秒,结果无人接,历史里只剩 0 条聊天消息(那条研报升级路径除外),刷新一片空白。新底座:用户消息在第 0 秒已入库;后台第 30 秒在 finally 落下助手回复;30 秒后重开页面,先拉历史(2 条消息齐全),再凭任务号订阅还没看完的增量。三个症状一次性消失,因为它们本来就是同一个底座问题。

⚖️ 决策对比

维度我们的选择:数据库即真相替代方案:内存态会话
会话存哪Postgres 的消息表 + 任务表,是唯一可信来源留在网页进程的内存里
页面刷新重开先拉历史,一条不少内存里没绑住,刷新即全丢
进程重启推理在独立后台,web 重启不影响,库里数据还在进程一重启,内存连同会话一起没
客户端断开不影响任务完整性,产物照样落盘等你回来取没人接的产物直接丢,算力白烧
工程量大:要建表、要把推理搬出请求进程、要做事件总线小:不用建表、不用解耦,几行就能跑通
适用场景要「关电脑回家还能续看」的严肃会话产品一次性 demo、单轮问答、不在乎丢历史

公允裁决:内存态真的更轻——不建表、不解耦,原型阶段几行代码就能流式吐字,对「发一句看一句、刷不刷新无所谓」的 demo 完全够用,这是它实打实的优点,不是稻草人。我们仍然选数据库即真相,是因为产品承诺的是「关掉页面、回家重开还能接着看」,这个承诺内存态从物理上就给不了:进程重启或刷新,内存里的东西就没了。一旦认定数据库是唯一真相,推理过程就不能再「飞」出去,而要由后台进程在 finally 里负责落库——这反而顺手把三个互相耦合的根因一起根治了。换句话说,我们不是为了存数据而存数据,是这个底座天然消解了那条因果链。

📌 总结

  • 三根因不是三个独立 bug,是一条耦合链:消息不入库(会丢)→ 断开后产物无人接(会卡)→ 后端接不住所以前端假重连(不一致)。只修一个不解决问题。
  • 源头是「不入库」:原代码全程零落库,只有研报升级那条岔路写过 1 条消息;一旦认定数据库即真相,另外两个根因的解法自然浮现。
  • 修法关键是把推理搬出网页请求、在 finally 里无条件落库:断不断开,助手回复都进库,客户端断开不再影响任务完整性。
  • 分三卷渐进而非一次大改:打地基(落库)→ 关页面续看(搬进后台)→ 容错(取消/重试/自愈),每卷可独立交付与回滚,累计 3/3 全覆盖。
  • 替代方案不是错,是不够:内存态会话更轻,但给不了「关电脑回家还能续看」的承诺。取消/续跑/自愈的细节见本类第 3、4 题。

一句话速记:把数据库当成唯一真相,推理不再「飞」出去而是步步落盘,一条耦合链上的三个症状(丢/卡/不一致)就一起断了。

Q2

"数据库即真相" + 把 agent 和传输层解耦(agent 跑在独立的 Celery 进程):为什么要这么拆?解耦买到了什么?

★★★★☆
进程解耦Celery数据库即真相Redis Streams架构权衡

🎯 考察点分析

面试官想看你是不是真的理解「一次模型推理」和「一条 HTTP 请求」是两个生命周期完全不同的东西。新手会把模型推理直接挂在用户那条流式请求上,觉得"反正用户连着,我边算边推给他"——这在 demo 里能跑,一上真环境就开始丢任务、白烧算力。我抛这道题,是想听你能不能把"为什么要拆成两个进程"讲到根上,而不是背一句"用 Celery 异步"就完事。

  • 追问:你说推理放独立进程,那用户那条 SSE 请求还剩下哪些活?它和真正干活的进程之间靠什么联通?
  • 追问:为什么不直接在网页进程里开一个 asyncio 后台任务就好了,非要拉一整套 Celery?这俩在"用户关页面"和"代码热重载"两个场景下分别会怎样?
  • 追问:"数据库即真相"具体真相到哪一层?模型一轮吐几百个小片段,这些也全进数据库吗?
  • 追问:用户中途关掉浏览器,你的后台进程要不要停下来?你靠什么判断"用户走了",判断到了又做不做事?

📚 原理讲解

先把问题摆清楚。一轮对话从用户发问到模型答完,可能要跑 5 到 10 分钟(量级估计):中间要查行情、读研报、调好几次工具、再让模型综合。最朴素的写法是把这整段计算挂在用户的那条流式连接(SSE)上——网页进程一边算一边往这条连接里塞字。问题在于:这条连接的命,和用户的浏览器、和网页进程本身,是绑死的。用户一关页面、网页进程一重启,这段算到一半的推理就跟着没了,而它可能已经烧掉好几毛钱的模型调用。

第一刀:把"干活的"和"端茶送水的"拆成两个进程

我的拆法是:真正的模型推理搬到一个独立的后台进程里跑(用 Celery worker)。这个推理循环早期是用图编排框架(LangGraph)搭的,后来重设计成一个裸的 Python while 工具循环(我们内部叫 ToolLoop,这块细节归本类第 1 题和 Chat Loop 那章)。而面向用户的网页进程(FastAPI)被砍到只剩四件轻活:① 把这一轮任务入队丢给后台;② 从中间的事件管道里转发事件给浏览器;③ 把用户的取消、重试信号转发给后台;④ 鉴权。注意:网页进程从此不碰任何模型推理,它只是个搬运工。这样一来,推理的生命周期就和"用户那条 HTTP 请求"彻底脱钩了。

第二刀:让数据库当唯一的真相,而不是那条连接

"数据库即真相"的意思是:一轮对话算没算完、答案是什么,以最终落进 Postgres 的那行记录为准,而不是以"有没有成功推给某条连接"为准。后台进程在收尾时,不管用户还连不连着,都会在一个 finally 收尾块里把助手回复落库、把任务状态置成终态。这就根治了"算出来了却没人接、于是蒸发"的老毛病。

存储为什么是双层的

关键认知:模型一轮会吐出几十到几百个小片段(token chunk,量级约 50–200 个),这些是给打字机效果用的实时流,如果每个都写一次数据库,数据库会被打爆,也没意义。所以存储分两层各司其职:

  • 实时事件层 = Redis Streams:key 形如 chat:events:{会话}:{任务},只活 24 小时(TTL)。后台进程每产一个片段就往里写一条(XADD),网页进程从里面读(XREAD)再转发。Redis Streams 天生支持"从某个位置往后重读",这正好对上 SSE 断线重连后"接着上次的位置续播"的需求。
  • 持久层 = Postgres:只存"用户问了一句、助手答了一句"这样的整段摘要(各一行),外加任务状态。几百个碎片不进来,只进 Redis。

一句话:碎片走 Redis(便宜、会过期、能重读),结论走 Postgres(永久、是真相)。

客户端断开:检测,但不杀

网页进程会用 request.is_disconnected() 察觉用户关了页面。但它的反应只是"我不往这条死连接转发了",绝不给后台发取消信号。后台进程根本不知道用户走没走,它只管把这一轮算完、落库。用户回家重开页面,看到的是完整答案——这就是解耦买到的"长任务"能力。

💻 示例讲解

下面用教学伪代码对照两种写法。先看反面——把推理挂在请求里:

# ❌ 反面写法:推理和用户的 HTTP 请求绑死
async def chat_endpoint(request, user_msg):
    async for piece in run_inference(user_msg):   # 模型边算边吐,挂在这条请求上
        yield piece                                # 直接推给浏览器
    # 致命点:用户一关页面 / 进程一重启,这个协程就被掐断,
    # 算到一半的结果谁都没存,几毛钱模型调用直接蒸发

再看我们的写法——网页进程只入队和转发,推理在另一个进程:

# ✅ 网页进程:只做"入队 + 转发",不碰推理
async def chat_endpoint(request, user_msg, session):
    user = authenticate(request)                  # ① 鉴权
    task_id = create_task(session, status="queued")  # 在 PG 建一行任务(真相起点)
    enqueue_run_chat(task_id, session, user_msg)  # ② 入队 → 丢给后台 Celery,立即返回

    # ③ 从 Redis Streams 把事件转发给浏览器(SSE)
    last_id = "0"
    while True:
        events = redis.xread(f"chat:events:{session}:{task_id}", last_id)
        for ev in events:
            if await request.is_disconnected():   # 用户关页面了?
                return                            # 只停转发,绝不通知后台停!
            yield ev; last_id = ev.id
            if ev.type in ("done", "error_done"): return

# ✅ 独立 Celery 进程:真正干活的地方
def run_chat(task_id, session, user_msg):         # 另一个进程,与网页请求无关
    mark_running(task_id)
    try:
        for piece in ToolLoop().run(user_msg):    # 跑 5-10 分钟也无所谓
            redis.xadd(f"chat:events:{session}:{task_id}", piece)  # 碎片只进 Redis
    finally:
        # "数据库即真相":不管用户还连不连着,结论都落 PG
        append_assistant_message(session, final_text)   # 整段答案进 Postgres
        mark_done(task_id)                              # 任务置终态

推演:假设一轮推理跑 6 分钟、吐了 120 个片段。第 3 分钟用户关了浏览器:网页进程那条 while 在下一次 is_disconnected() 命中后 return 退出,SSE 转发结束;但 Celery 进程对此一无所知,继续把剩下的工具调用跑完,在第 6 分钟把这 120 个片段全写进 Redis(还能再活 24 小时),并把整段答案落进 Postgres、任务置 done。用户晚上回家重开页面——前端拿 active_task_id 一查,任务已 done,直接从 PG 渲染完整答案。全程零丢失、零白烧。换成反面写法,这一轮在第 3 分钟就连人带算力一起没了。

⚖️ 决策对比

维度我们的选择:独立 Celery 进程替代方案:网页进程内 asyncio 后台任务
首字延迟多一跳入队 + 事件总线,略慢几十毫秒最低——同进程内存里直接吐,无跨进程开销
代码热重载(开发期 reload)worker 是另一个进程,网页 reload 不碰它,推理照跑reload 一次就连进程带后台任务一起杀,推理蒸发
网页进程崩溃 / OOM推理在别的进程,继续跑完,用户重开看到完整结果后台任务跟着进程一起死,算到一半全丢
长任务(5–10 分钟)天然 fire-and-forget,扛得住asyncio 任务挂在 web 进程内,对这种时长太脆弱
横向扩容worker 可多实例独立扩,和网页并发解耦推理算力和网页 QPS 绑死,扩一个就得扩另一个
基础设施成本项目已有 Celery+Redis(持仓监控、跨会话记忆都在用),边际成本≈0不用引新依赖,纯进程内,最轻

公允裁决:asyncio 后台任务真有优势——它首字延迟最低、不引任何新依赖、代码最简单,对一个"算几秒就完"的轻量场景,它就是更对的选择,我不会强行上 Celery。它输在两个我恰好踩中的硬约束上:一是开发期的代码热重载,reload 一次就杀掉进程内一切后台任务,推理直接蒸发,这在 dogfood 时反复咬人;二是本场景的任务真能跑 5–10 分钟,这种时长挂在网页进程的内存里太脆。再加上我这个项目本来就为持仓监控和跨会话记忆养着一整套 Celery+Redis 运维层,推理走 Celery 几乎是零边际成本,还白捡了"天然多实例、真 fire-and-forget"。三个因素叠加,我宁可吃那几十毫秒延迟,选独立进程。换个没有现成 Celery、任务又都是秒级的项目,我大概率会反过来选 asyncio。

🖼️ 图解

📌 总结

  • 核心动机:一次模型推理(5–10 分钟量级)和一条 HTTP 请求,生命周期完全不同,绑在一起就会被用户关页面、被进程重启连累。拆开,推理才能脱离请求独立活着。
  • 解耦买到三样东西:① 网页进程崩溃/热重载不影响推理;② 客户端断开只断 SSE 转发、用 is_disconnected() 检测但绝不通知后台停;③ 隐含支持长任务,"关电脑回家继续看"成立。
  • "数据库即真相"= 一轮算没算完以落进 Postgres 的那行记录为准,而不是以"有没有推给某条连接"为准;后台进程在 finally 收尾块里无条件落库。
  • 存储双层各司其职:碎片(50–200 个/轮)走 Redis Streams(便宜、24 小时过期、能从某位置重读,正好对上 SSE 续播);结论走 Postgres(永久、是真相)。
  • 选 Celery 而非进程内 asyncio:不是因为它"更高级",而是本项目已有整套 Celery+Redis 运维层(边际成本≈0)+ 任务真能跑很久 + 开发期热重载会杀进程内后台任务。换个秒级、无现成 Celery 的项目我会反选。取消与续跑见本类第 3 题。

一句话速记:把"干活的进程"和"端茶的进程"拆开,让数据库而不是那条连接当真相——用户关页面、网页崩了,推理照样跑完、答案照样落库。

Q3

用户点了取消、或者服务重启,你怎么干净地中断和恢复一轮对话?(Redis 发布订阅取消 + 断点续跑)

★★★★☆
取消Redis 发布订阅整轮重跑断点续跑退役SSE 断线重连

🎯 考察点分析

这道题表面问"取消"和"恢复",其实面试官想确认三件事:你知不知道取消是异步信号、不是同步函数调用(推理跑在另一个进程里,你按不到它);你能不能区分"中断"和"恢复"是两个独立问题(中断要干净落库、恢复要行为不漂移);以及你有没有为不同可靠性需求选不同传输的判断力。最能拉开差距的,是你能不能讲清"断点续跑"为什么在我们这儿被砍掉了——这恰好暴露你是抄了个时髦方案,还是真理解自己系统的语义边界。

  • 追问:推理在 Celery worker 里跑,网页进程怎么"按停"它?信号怎么跨进程传?
  • 追问:取消信号你用了 Redis 发布订阅(Pub/Sub),插话(steering)却用了 Redis List,为什么不统一?
  • 追问:取消那一刻已经生成了一半的文字,怎么办?会进下一轮的上下文吗?
  • 追问:你原来设计的是"从断点接着跑",现在为什么改成整轮从头重跑?省下来的钱不要了?

📚 原理讲解

先把场景拆成两个完全不同的问题。一个是主动中断:用户点了"停止",我要让正在跑的那一轮干净停下。另一个是故障恢复:服务崩了或热重启了,我要让用户感觉不到、或者一键重来。两者的难点不一样,放一起讲会糊。

中断:取消是一封"信",不是一个开关

关键前提是推理不在网页进程里跑,而在独立的 Celery worker 进程里(为什么这么拆,见本类第 2 题)。网页这边根本碰不到那个正在跑的协程,没法直接 cancel() 它。所以取消必须当成"跨进程发一封信":网页收到 POST /chat/cancel/{任务id},往一个 Redis 频道 chat:cancel:{任务id} 发一条信号,立刻返回 202(我只负责把信送出去,不等对方读)。worker 进程里常驻着一个监听协程,订阅这个频道,收到信就把一个进程内的 asyncio.Event 置位(set)。

真正"停下来"靠的是协作式取消:推理循环不会在任意一行被强行打断,而是在两个安全检查点主动看一眼这个 flag——一个是每圈的边界(一轮里可能调好几次工具,圈与圈之间),另一个是流式吐字的间隙(每吐一个 token 检查一次)。一旦发现 flag 置位,就抛一个自定义异常 CancelledByUser。它被 finally 块接住,走"半成品落库":已经生成的文字以 partial 状态存进库——只供前端展示那半句话,不会进下一轮的对话窗口。这就是"干净"的含义:不是粗暴掐线,而是停在一个一致的状态上,该存的存、该标的标。

为什么取消用发布订阅、插话却用 List

这是这套设计里最见功力的一笔。两路信号的可靠性要求不同。取消可以偶尔漏:发布订阅是"最多送一次",worker 那一刻没在监听就丢了——但没关系,用户没停下来会再点一次,漏一次不致命。插话(用户在 AI 答的过程中追加一句"顺便也看下毛利率")绝不能丢:worker 流式输出那几秒恰好不在监听频道,发布订阅会把这条插话直接吞掉。所以插话改用 Redis List(LPUSH 进、worker 在圈边界 RPOP 取),List 是持久队列,worker 没空读也稳稳排着,等下一个圈边界再消费。一句话:能漏的用广播,不能漏的用队列。

恢复:断点续跑为什么被砍了

这是这题最大的坑。最初的设计是"断点续跑":借 LangGraph 的 checkpoint,从最后一个稳定状态接着跑,不重头,省 token。听起来很美。但 2026-06-05 把 LangGraph 整个移出了对话路径(改成裸 Python 的工具循环,为什么换见对话循环重设计),checkpoint 也跟着退役了。退役的真正理由不是"框架换了",而是语义层面 checkpoint 没有消费者:我们把"一轮对话"定义成原子单位——重试就是整轮重来,中间圈存下来的那些 checkpoint 根本没人会去"接着跑"。为一个没人用的东西维护一套断点机制,是负债。

所以现在的恢复是整轮从头重跑。POST /chat/retry/{任务id} 只接受 error / partial / cancelled 三种状态(done / running / queued 会被拒,返 409),创建一个新任务、parent_task_id 指向旧任务形成审计链。重跑要做到行为不漂移靠两件事:用户消息用 rebuild_turn_user_message 重建(原始那句 + 这一轮里所有插话,按时间序拼回去);历史用 rebuild_context 取到上一轮为止——那半成品的 partial / error 行不进窗口,所以重跑看到的输入和第一次开跑时一模一样。

另一种恢复是服务重启:网页进程崩了或热重载,前端的 SSE 长连接断开,它用指数退避重连 GET /chat/stream/{任务id},带上本地最后收到的事件序号(last_event_id),服务端从那个序号之后续读 Redis Stream。这里要点出来:Celery worker 全程没受影响,推理一直在跑——断的只是"看直播"的那根线,重连上就接着看,不用重算。

💻 示例讲解

把"取消"这条链路用伪代码串起来,看信号怎么从网页一路传到循环里、又怎么被干净接住。

# ① 网页进程:收到取消请求,只负责把"信"发出去,不等回执
async def chat_cancel(task_id):
    # 往该任务专属频道发一条广播,立刻返回 202(异步生效)
    await cancel_bus.publish_cancel(task_id)      # 频道 = chat:cancel:{task_id}
    return Response(status_code=202)              # 我不知道 worker 收没收到,这就是"最多送一次"

# ② worker 进程:一个常驻协程订阅频道,收到就置位进程内的 flag
cancel_event = asyncio.Event()                   # 同进程内的"已被取消"开关
async def cancel_listener():
    async for _ in cancel_bus.subscribe_cancel(task_id):
        cancel_event.set()                       # 收到第一条就置位,然后退出监听
        return

# ③ 推理循环:不在任意行被打断,只在"安全检查点"主动看 flag
async def run_one_turn(state):
    while True:
        # 检查点 A —— 每圈边界(一轮里要调好几次工具,圈与圈之间看一眼)
        if cancel_event.is_set():
            raise CancelledByUser("cancelled at loop boundary")
        async for delta in llm.stream(state):
            # 检查点 B —— 流式吐字的间隙(吐一个 token 看一眼,长回答里也能及时停)
            if cancel_event.is_set():
                raise CancelledByUser("cancelled during stream")
            emit_token(delta.text)               # 同时累积已流出的文字,留着落库
        ...

# ④ 接住异常,走"半成品落库" —— 这一步是"干净"的关键
try:
    final_state = await run_one_turn(state)
except CancelledByUser:
    emit_event({"type": "cancelled"})            # 通知前端:这轮被你停了
finally:
    listener_task.cancel()                       # 收尾常驻监听协程
    # 已流出的文字以 partial 状态入库:只供展示那半句,绝不进下一轮窗口
    await persist_partial(text="".join(emitted_tokens))

推演:假设一轮答到第 3 圈、已经吐出约 40 个字时用户点了停止。网页发出 202(立即返回,不卡用户)。信号经 Redis 频道到 worker,监听协程置位 flag。下一个安全检查点命中——可能是当前 token 间隙、也可能等到第 3 圈结束的边界——所以取消的感知粒度约 1-3 秒,不强保证 1 秒内,因为它停在"自然边界"而非任意一行。命中后抛 CancelledByUser,那 40 个字以 partial 落库给前端展示,任务状态标 cancelled。用户随后若点"重试",走整轮重跑:新任务的输入 = 那一轮的原始消息 + 期间插话,历史取到上一轮为止,partial 那半句不进窗口,所以重跑得到的输入与第一次完全一致。

⚖️ 决策对比

维度我们的选择替代方案(硬杀进程 vs 发布订阅 + 断点)
中断方式软取消:发布订阅传信号,循环在安全检查点自己抛异常停硬杀:Celery revoke + SIGTERM 直接掐死 worker 子进程
半成品文字finally 兜底,已流出文本以 partial 落库供展示进程被杀,内存里的半成品全丢,无法落库
取消粒度约 1-3 秒(停在自然边界,不强保 1 秒内)近乎瞬时,但代价是状态不一致
恢复方式整轮从头重跑,历史从 rebuild_context 重建checkpoint 断点续跑,从最后稳定圈接着跑
恢复正确性行为不漂移:输入与首跑一致,partial 不进窗口省 token,但与"一轮即原子"语义冲突,中间圈无消费者
系统复杂度无需维护 checkpoint;重试逻辑就是"重新跑一遍"要维护每圈的 state 快照、续跑入口、版本兼容

公允裁决:两个替代方案各有真本事。硬杀是最快的——信号一到进程立刻没了,毫不拖泥带水;在"取消必须毫秒级生效"的场景(比如 worker 跑飞了要止损)它是对的。但对话场景里,用户点停止图的是"别再花我的钱、别再让我等",1-3 秒完全可接受,而保住那半句话能展示、保住状态一致可重试,价值更高,所以我们选软取消。断点续跑更不是稻草人——它真能省 token,在长链路 agent 里很主流。我们砍它不是因为它不好,而是因为它和我们的语义打架:既然把"一轮"定义成原子单位、重试就是整轮重来,那中间圈的 checkpoint 就没有任何消费者,维护它纯属负债。换句话说,断点续跑是为"可以从中间继续"的系统设计的,而我们刻意选了"不从中间继续"。把不匹配的好方案硬塞进来,比没有它更糟。

📌 总结

  • 取消是异步信号不是同步调用:推理在另一个进程里,网页只能发"信"(Redis 频道)立刻返 202,worker 自己在安全检查点读 flag、主动抛异常停。
  • 协作式取消换来干净:停在每圈边界 / 流式间隙而非任意一行,代价是 1-3 秒粒度,收益是 finally 能把半成品以 partial 落库——只展示、不进下一轮窗口。
  • 能漏的用广播,不能漏的用队列:取消漏了用户会再点,用最多送一次的发布订阅;插话不可丢,用持久的 Redis List。
  • 断点续跑被语义砍掉:把"一轮"定为原子单位后,中间圈的 checkpoint 没有消费者,重试改成整轮重跑——靠重建用户消息 + 取到上一轮的历史保证行为不漂移。
  • 服务重启 ≠ 重算:worker 推理不受网页崩溃影响,前端 SSE 带 last_event_id 续读 Redis Stream 即可接上直播。

一句话速记:取消是发一封"可丢的信"+ 循环在安全点自杀,恢复是"整轮重来"而非"接着跑",因为我们把一轮定成了原子。

Q4

一个对话任务有 6 个状态 + 一个自愈扫描器,怎么保证它不会永远卡在某个中间状态?

★★★★☆
状态机自愈扫描器心跳检测Celery Beat卡死恢复

🎯 考察点分析

面试官想看的不是"你定义了几个状态",而是你有没有把"中间状态会卡死"当成一个必然发生的故障来设计——分布式系统里跑任务的那个进程随时会 OOM、被杀、机器重启,而它一死,就再也没人去把"跑了一半"的任务收尾了。一个成熟的工程师会主动说出这条:谁也没法保证 worker 不死,关键是 worker 死了之后由谁来兜底。

  • 追问:任务卡在"跑中"状态,到底是哪个环节出了问题让它前进不了?是谁本该把它推到终点却没推?
  • 追问:为什么不让任务自己每 30 秒上报一次"我还活着"(心跳),而要派一个外部进程去巡查?
  • 追问:你怎么知道一个任务是"真的卡死"还是"只是这轮推理比较慢"?5 分钟这个数是怎么定的?
  • 追问:扫描器把它标成失败之后,用户怎么知道、又怎么重新跑?重试是接着旧任务跑,还是另起一个?

📚 原理讲解

先把任务的"一生"画清楚。一轮对话会落成一个任务记录,它的状态只能沿着一条收敛的路走:入队 → 跑中 → 一个终点。终点有四种:正常做完、被用户取消、做了一半(中途被打断但有部分产出)、出错。另外还有一种特殊情况——任务连入队都没成功,可以直接跳到"出错"。一旦走到任意一个终点,这条记录就定死不再变了。

为什么"跑中"是唯一危险的中间状态

"入队"很短暂,马上就被领走变成"跑中"。四个终点是稳定的。唯一会让任务无限期悬在半空的,就是"跑中":跑这个任务的 worker 进程如果 OOM 被系统杀掉、或者主机重启,那一刻它正捏着这个任务,死的时候来不及把状态改成任何一个终点。结果就是:数据库里这条记录永远停在"跑中",前端转圈圈转到天荒地老。

有人会说——任务队列自带的"结果后端"不是会记录任务跑完没吗?问题是它同样不可靠:worker 崩的时候,这个结果后端很可能也只停在"已开始"(STARTED)这个中间态,永远不更新。死的进程没法报告自己死了,这是这类问题的根。

兜底的关键:由一个"绝不会跟着一起死"的进程来巡查

既然死掉的进程救不了自己,就得找一个外部的、独立的进程来兜底。这个角色由定时调度进程(Celery Beat)来当——它和跑任务的 worker 是两个独立的进程,worker 死了它还活蹦乱跳。我们给它派了个活儿,每 60 秒跑一次:扫一遍所有"跑中"的任务,凡是started_at(开始时间)超过 5 分钟还停在"跑中"的,就判定它卡死了,直接把它标成"出错",错误信息写清楚"超过 5 分钟没有心跳,worker 大概率崩了"。这就给每一条"跑中"都铺了一条通往终点的兜底路。

心跳怎么判:复用已有的事件序号,不另造轮子

怎么判断一个任务"还活着"?直观方案是让 worker 自己每 30 秒往库里写一行"我还在"。但这个方案有两个硬伤:worker 一死,心跳也跟着死——而恰恰是 worker 死了的场景才需要心跳救命,它却失灵了;另外每 30 秒写一次纯粹是给数据库添写压。我们换了个巧劲:任务每往前端推一个事件(比如吐一段字、调一个工具),就把一个事件序号(last_event_seq)加一。这个序号天然就是"活着的证据"——只要它在动,任务就在干活。5 分钟内序号一动不动,就等于没心跳。不用新建任何东西,白捡一个心跳信号。

5 分钟这个阈值怎么来的

正常跑一轮推理大概 30 秒到 3 分钟,所以 5 分钟无更新基本可以断定是死锁或崩溃,误杀正常慢任务的概率极低。这个阈值加上 60 秒的扫描节奏,把"永远卡在跑中"硬生生兜成了"最多卡 1 分钟左右就被标成出错并可重试"。

标完之后:让在线用户立刻看到

扫描器把任务标成"出错"还不够,得让用户马上知道。所以它在标记的同时,往事件流里塞一条"出错完成"(error_done)的事件,在线的页面通过推送通道(SSE)立刻收到,前端把转圈换成红色错误徽标 + 一个重试按钮。这里有个干净的设计:重试不是去复活那条卡死的旧记录,而是新建一个全新的任务,用 parent_task_id 把新旧两条串成一条链。旧的那条永远定格在"出错",证据链完整;新的从"入队"重新开始。

💻 示例讲解

下面是自愈扫描器的核心逻辑(教学伪代码)。注意它本身极短——难点不在代码,在于"由谁来跑、什么时候跑"这个编排上。

# 这个函数被注册成定时任务,由独立的调度进程每 60 秒触发一次。
# 关键:它跑在跟 worker 不同的进程里,worker 崩了它照常工作。
async def scan_stale_chat_tasks(repo, event_bus, stale_minutes=5):

    # 判据 = 状态还停在 running,且开始时间已经超过 5 分钟。
    # (正常一轮推理 30 秒~3 分钟,超 5 分钟没收尾,99% 是崩了)
    stale_tasks = await repo.find_stale_running_tasks(min_age_minutes=stale_minutes)
    if not stale_tasks:
        return 0  # 没有卡死的,直接收工

    marked = 0
    for task in stale_tasks:
        # 第二步:把这条"跑中"硬拉到终态"出错"。
        # 错误信息写明白原因,方便事后排查,也给前端展示用。
        await repo.mark_error(
            task.id,
            error_message="stale: 超过 5 分钟没有心跳,worker 大概率崩了",
        )
        # 第三步:往事件流塞一条"出错完成",让在线页面立刻收到。
        # 前端凭这条把转圈换成 红色徽标 + 重试按钮。
        await event_bus.xadd_event(
            task.session_id, task.id,
            {"type": "error_done", "reason": "stale"},
        )
        marked += 1
    return marked  # 返回这一轮救活了几个,方便观测

# 心跳怎么判"活着"?不另造,复用已有的事件序号:
# 任务每推一个事件给前端,就把 last_event_seq 加一。
# 序号在动 = 任务在干活;5 分钟纹丝不动 = 没心跳 = 卡死。
async def on_event_pushed(repo, task_id):
    await repo.bump_seq(task_id)  # 序号 +1,等于打了一次心跳

推演:假设 worker 在某个任务跑到第 90 秒时被系统 OOM 杀掉。这条任务停在"跑中",last_event_seq 冻住。① 接下来的 5 分钟内,扫描器每分钟来一次,但因为 started_at 还没满 5 分钟,先放过。② 第 5 分钟一过,下一次扫描(最坏再等约 1 分钟)命中它,标成"出错"并推事件。③ 用户屏幕上的转圈变成红色徽标 + 重试按钮,点重试 → 新建一条全新任务,parent_task_id 指向这条死掉的,从"入队"重新跑。整条链最坏的卡死可见时间 ≈ 5 分钟阈值 + 1 分钟扫描间隔,且永不无限悬挂。

⚖️ 决策对比

维度我们的选择:6 态状态机 + 独立扫描器兜底替代方案:无状态机(靠队列结果后端 / 任务内心跳)
谁来收尾死任务独立调度进程,跟 worker 不共命,worker 死它还活结果后端/心跳都在 worker 自身,worker 死则一起失灵
卡死的可见性5 分钟阈值 + 60 秒扫描,最坏 ≈ 6 分钟必被标错并可重试结果后端可能永远停在"已开始",无人推进,无限悬挂
心跳成本复用已有事件序号,零新增写入任务内每 30 秒额外写一行心跳,纯加写压
状态可解释性4 种终点语义清晰(完成/取消/部分/出错),前端按态渲染只有"成功/失败"二态,丢失"做了一半"这种中间语义
实现复杂度需多维护一张状态字段 + 一个定时任务几乎零额外代码,直接读队列自带结果
重试语义新建任务 + parent 链,旧记录留证不被覆盖原地重跑,容易把失败现场冲掉,排查困难

公允裁决:无状态机方案真有它的好——代码几乎为零,直接信任队列自带的结果后端,小流量下大多数时候也跑得好好的。任务内心跳也不是没人用,业界很多系统就这么干,实现直观。我们之所以仍选重的那条,是被一个具体故障教育的:worker 进程会因为推理吃内存而 OOM 被杀,一旦它捏着任务死掉,自带结果后端就僵在"已开始",用户那边转圈无限期不结束——这是真实发生过的卡死,不是假想。任务内心跳救不了这种场景,因为需要心跳的那一刻心跳本身已经死了。把兜底逻辑挪到一个绝不与 worker 共命的独立进程,是唯一能闭环的做法;而既然要兜底,就顺手把状态语义做细(区分"做了一半"和"彻底失败"),让前端能精确渲染。多维护一张字段和一个定时任务,换来"永不无限卡死"的硬保证,这笔账划算。

🖼️ 图解

📌 总结

  • 任务状态沿"入队 → 跑中 → 四种终点(完成/取消/部分/出错)"单向收敛,终点定死不再变;唯一会无限期悬挂的中间态是"跑中"。
  • 卡死的根因是 worker 进程会 OOM/被杀/重启,死的时候来不及收尾——死掉的进程救不了自己,队列自带结果后端同样可能僵在"已开始"。
  • 兜底必须交给一个不与 worker 共命的独立进程:定时调度进程每 60 秒扫"跑中且超 5 分钟"的任务,拉回"出错"并推事件,把"永远卡死"兜成"最多卡 1 分钟左右就可重试"。
  • 心跳不另造表,复用已有的事件序号(每推一个事件加一);5 分钟无变化即判卡死——阈值来自"正常推理 30 秒~3 分钟"。
  • 重试是新建任务 + parent 链,不复活旧记录,失败现场留证。取消与重启恢复的机制见本类第 3 题。

一句话速记:死掉的进程救不了自己,所以让一个绝不跟它一起死的外部时钟,每分钟巡查一遍"跑太久的跑中态",把它拉到终点。

Q5

你沉淀过一条教训:"第 N 轮修复 = 第一阶段重做"。这是什么意思?系统化调试在这里教了你什么?

★★★★☆
系统化调试方法论数据流追踪反向追踪dogfood 教训

🎯 考察点分析

这道题表面在问一条口号,实际在看你有没有一套可复用的调试纪律——而不是凭手感东补一枪、西补一枪。面试官想确认两件事:一是你能不能识别「我已经在原地打转了」这个信号,二是你识别之后会换什么打法。能把一次真实的、连补 6 轮都没好的翻车讲清楚,比背十条「最佳实践」更有说服力。

  • 追问:「第一阶段」具体指什么?为什么是「重做第一阶段」而不是「再补一个组件」?
  • 追问:你凭什么定「3 轮」这个阈值?多了少了会怎样?
  • 追问:那次真根因是个很小的字段缺失,为什么前 6 轮都没看见它?
  • 追问:这种活为什么 AI 帮不上忙、必须靠人?

📚 原理讲解

先把这句口号翻译成大白话。「第一阶段」是系统化调试方法论里的第一步:不急着改代码,先把整条数据流插上探针(打日志),从你看到的那个坏结果出发,沿着链路一段一段往回走,找到第一个「数据本该对、却已经不对」的地方。这叫反向追踪。「第 N 轮修复 = 第一阶段重做」的意思是:当同一个 bug 你已经连着补了 3 轮以上还没好,这本身就是一个强信号——问题根本不在你一直盯着的那个组件里,而在组件之间、在架构层面。这时候唯一正确的动作,是立刻停下打补丁,回到第一步,把整条链路的可观测性重新建起来,而不是凭直觉猜「那下一个组件试试」。

为什么「连补 3 轮没好」=「跨组件问题」

打一个补丁,本质是一次赌注:你赌「坏的地方在组件 X」。如果赌对了,一补就好。连续赌错 3 次,概率上说明你的假设空间一开始就错了——坏的不是任何单个组件,而是它们之间的接口约定:A 以为自己传了某个字段,B 以为自己收到了,中间其实丢了。这种问题站在任何一个组件内部看都「正常」,只有把整条链路连起来看才暴露。所以继续在单个组件里猜,是在错误的搜索空间里穷举,补到天荒地老也命中不了。系统化调试技能里把这条写死成判据:同一问题失败 3 次以上,默认按架构 / 跨组件问题处理。

那次翻车:6 轮补丁,根因是一个缺失的小字段

第二卷做「关掉页面还能续看」时 dogfood,撞上「流式不显示」——发了问题,打字机就是不吐字。我连着补了 6 轮,每轮都在猜下一个组件的症状:是不是打字机调速坏了?是不是事件总线没推?是不是渲染没触发?全没用。第 7 次我才照纪律回到第一步,拿命令行工具把那条服务器推送(SSE)的流端到端打通、逐段看真实数据,反向追到第一个偏离点——前端用来给流式 token 去重的那个序号字段(seq),在新后端推出来的事件里压根没带。

后果是一条非常隐蔽的因果链:字段不存在 → 在前端取出来是「未定义」→ 去重判断写的是「序号 > 上次序号才放行」→ 而「未定义 > 任何数」在这门语言里恒等于 false → 每一个 token 都被当成重复给跳过了 → 打字机的队列从头到尾一个字符都没排进去 → 页面自然空白。而用户手动刷新能看到完整回复,是因为那走的是「从数据库重新拉历史」的另一条路,跟实时流没半点关系——这个假象还额外误导了我几轮。修复(提交 a4ddf02)很小:把去重逻辑从「序号大于上次才放行」改成「只有当序号确实存在、且小于等于上次序号时,才判定为重复并跳过」;字段缺失或是新序号,一律放行。

这就是「打补丁 vs 重做第一阶段」的取舍

打补丁是局部猜测,成本低、见效快——但前提是你猜对了组件。重做第一阶段是先建立整条链路的可观测性,前期要花十几分钟搭探针、打通端到端,但一旦搭好,根因往往一击命中。这道题真正的答案不是「别打补丁」,而是知道什么时候该从前者切到后者:第 3 轮无效,就是切换信号。早一轮做那次端到端追踪,这 6 轮试错就全省了。

💻 示例讲解

先看那个「未定义 > 0 恒为 false」的坑——它是整条因果链的扣机:

# ❌ 旧去重逻辑(伪代码):序号大于上次才放行
def on_token(ev, last_seq):
    # 后端新路径推出来的事件里根本没带 seq 字段
    # 取一个不存在的字段,得到的是「未定义」(下面用 None 代表)
    if ev.seq > last_seq:          # None > 0 → 在前端语言里恒为 false
        enqueue_to_typewriter(ev)  # 这一行永远到不了 → 打字机一个字都没收到
        last_seq = ev.seq
    # 结果:每个 token 都被当成「重复」悄悄跳过,页面全程空白

再看反向追踪是怎么一段一段往回走、最后定位到这个扣机的。注意:它不是改代码,是在每个交接处打一个探针,看数据在哪一段开始不对:

# ✅ 第一阶段:从坏结果出发,沿链路反向插桩追踪(教学示意)
# 链路顺序:  后端产事件 → 推上事件总线 → SSE 推到浏览器 → 前端去重 → 打字机 → 渲染
#            ①            ②             ③             ④         ⑤        ⑥(坏在这:空白)

# 从⑥往回问,每段只问一句「数据到这儿还对吗」:
assert 渲染层.收到字符数 == 0           # ⑥ 空白,确认坏结果
assert 打字机队列.长度 == 0            # ⑤ 队列是空的 → 往前一段
assert 去重函数.放行次数 == 0          # ④ 一个都没放行!偏离点很可能在这
#      ↑ 第一个「本该 > 0、实际为 0」的地方 = 反向追踪的命中点

# 锁定④后,用命令行把 SSE 流原样打出来,核对真实 payload:
#   curl -N /chat/stream/{task_id}
#   → data: {"type":"token","text":"..."}   ← 看:压根没有 seq 字段!
# 至此真根因落地:不是打字机坏、不是总线没推,是②③交接处丢了 seq 约定

推演:前 6 轮分别赌在组件 ⑤⑥(打字机、渲染)和 ②③(总线、推送)上,每轮平均花十几分钟改+验,6 轮 ≈ 一个多小时全打了水漂,因为根因在④的判断式、且是被②③喂进来的脏数据触发的,站在任何单个组件里都看着「正常」。第一阶段反向追踪只问了 3 个「数据还对吗」就把范围收敛到④,再一条 curl 看到真实 payload 缺 seq,一击命中。判据很朴素:第 3 轮没好,就该切到这套打法,而不是去赌第 7 个组件。

⚖️ 决策对比

维度我们的选择:3 轮无效就重做第一阶段(反向追踪)替代方案:继续按症状打第 N+1 个补丁
前期成本高:要先给整条链路插桩、端到端打通,十几分钟起步低:盯着最可疑的组件改一行,马上能验
命中方式从坏结果反向走到第一个偏离点,定位精确猜一个组件赌一次,猜对即中
试错成本曲线一次性投入,之后大概率一击命中每轮线性叠加,猜不中就无限往上累
对跨组件 bug正好擅长:接口约定丢字段这类一眼现形几乎无效:站在单组件里看处处「正常」
适用时机同一 bug 已失败 3 次以上 / 怀疑是架构层第 1-2 轮、根因明显落在某个组件内
这次实际代价早一轮切过来,可省下后面那几轮试错实际连补 6 轮才被迫回头,一个多小时打水漂

公允裁决:继续打补丁不是蠢办法——头一两轮它确实更快:根因落在单个组件内时,直接改那一行、立刻验证,比花十几分钟搭一整套探针划算得多。日常 90% 的小 bug 就该这么修,上来就重做第一阶段反而是杀鸡用牛刀。它唯一的死穴是跨组件问题:坏在接口约定上时,你在任何单个组件里都看不出毛病,补丁就退化成在错误空间里瞎猜,成本线性叠加还命不中。所以我们不是否定补丁,而是给它划一条止损线——第 3 轮还没好,就把它当成「这不是组件级问题」的信号,立刻切到反向追踪。这条线不是拍脑袋,是系统化调试技能里写死的判据;那次正是因为没守住它,白白多补了三四轮。

🖼️ 图解

📌 总结

  • 口号翻译:同一 bug 连补 3 轮以上还没好,别再猜第 N+1 个组件,立刻回第一步——把整条数据流插桩、从坏结果反向追到第一个偏离点。
  • 判据写死:失败 3 次以上,默认按架构 / 跨组件问题处理。连错 3 次说明假设空间本身错了,坏的是组件之间的接口约定,不是任何单个组件。
  • 真实代价:那次「流式不显示」连补 6 轮没用,真根因只是后端事件少带了一个去重序号字段——「未定义 > 0」恒为 false,token 被全部跳过,打字机一个字都没排进队列。修复(提交 a4ddf02)只改一行:序号存在且 ≤ 上次时才判重复。
  • 取舍不是非黑即白:头一两轮补丁更快、日常小 bug 该这么修;它的死穴只在跨组件问题。关键是给补丁划一条「第 3 轮止损」的线,该切就切。
  • 为什么这段贵:样板代码和单测模板 AI 能秒出,但跨组件根因定位是 review-heavy、靠人推理的「人-bound 段」——这正是这条教训最值钱的地方。取消/续跑见本类第 3 题。

一句话速记:连补 3 轮没好,就别再猜组件,回去把整条链路插上探针、从坏结果反向走到第一个偏离点——补丁是赌,反向追踪是查。
