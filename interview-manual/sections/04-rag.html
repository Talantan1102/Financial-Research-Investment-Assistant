04知识库与 RAG

这一组聚焦 AlphaScout 的知识库摄取与检索(RAG)链路:金融文档怎么切块、用什么 embedding 入向量库、中文场景的工程坑,以及评估体系还缺什么。从「为什么不能一刀切」这类入门取舍,逐步深入到 embedding 选型权衡、离线评估缺口,最后到「什么时候根本不该用 RAG」的边界判断。

Q1

你的知识库切块按类型路由:研报走语义切、财报走章节切、政策走条款切。为什么不能用一个固定大小一刀切?

★★★☆☆
切块策略类型路由RAG 摄取中文金融语料

🎯 考察点分析

面试官想看的不是"你会不会用 splitter",而是你有没有意识到:切块的好坏取决于语料长什么样,而不同语料长得不一样。一刀切是任何 RAG demo 的默认起点,愿意为它加一层路由,说明你真去看过文档的形态、并且为"切碎会损失什么"算过账。这是从"会调库"到"懂权衡"的分水岭。

  • 追问:固定大小切块到底会切坏什么?对研报、财报、政策各举一个具体的坏例子。
  • 追问:既然要按类型分,为什么不干脆三类都用最聪明的"语义切"?统一成语义切不就也对齐内容了吗?
  • 追问:多写两套 chunker 是有成本的(代码、维护、加新语料类型),这笔账你怎么算划算的?
  • 追问:路由的"钥匙"是什么?如果来一份没标类型的文档,你的系统会怎样?

📚 原理讲解

切块(chunking)是 RAG 摄取阶段的第一步:把一份长文档剁成若干小段,每段单独算向量、单独检索。检索时命中哪一段,就把哪一段塞进上下文给模型。所以一段的边界划在哪,直接决定了"被检索到的那块信息完不完整"。如果一刀切,把一句话、一张表、一个完整论点从中间劈开,检索回来的就是半截信息,模型只能瞎猜另一半。

三类语料的"形态"根本不同

关键洞察:文档不是无差别的字符流,它有结构,而三类金融语料的结构来源不一样:

  • 研报是连续叙述(分析师写的一段段论证),段落之间没有显式分隔符,边界只能靠语义判断——哪里话题转了,哪里就该切。
  • 财报经过 MinerU(PDF 解析器)处理后,已经被识别出明确的章节("管理层讨论""主要会计数据"…),而且表格特别多,表格是高密度的结构化信息。
  • 政策有天然的条款边界("第十二条""第三款"),这是法规体裁自带的、肉眼可见的分割线。

形态不同,最合适的切法就不同。所以系统在 router.py 里用一个 chunker_for(source_type) 当分发器:看文档的 source_type 字段(research / financial / policy 三选一),把它送进对应的 chunker;不认识的类型直接报错,不允许"裸奔"。

三套 chunker 各自的机制

研报 — 语义切(SemanticChunkerForResearch):在每个章节里按中文句末标点(。?!)拆成句子;少于 5 句的小章节不折腾,直接合成一块;5 句以上才请 embedding 服务把每句变成向量,算相邻两句的 cosine 距离(1 − 余弦相似度,值越大说明话题跳得越远),距离超过阈值 0.4 的地方就划一刀。最后兜底:任何一块超过 800 token,再用递归字符切强行打散,防止单块过大。

财报 — 章节切(SectionChunkerForFinancial):顺着 MinerU 给出的章节走,一章一块(超 800 token 才二次切)。最关键的一条:每张表单独成块,绝不进 splitter。表格信息密度高,被字符切刀劈开就会丢上下文(行头和数据被拆散,数字就没了意义)。

政策 — 条款切(ClauseChunkerForPolicy):把全文拼起来,用正则按"第X条/第X款"这类天然边界一刀刀切,不做语义切、不加 overlap、不设大小下限。短到 500 token 以下的小条款也独立保留——因为对法规来说,"一条就是一个完整语义单元",拆开或合并都会破坏检索的可引用性。

为什么政策不也上语义切?因为边界已经白送了:再去给每句话算 embedding 才能找边界,既是过度工程,又额外烧一次次 embedding 调用的钱,换不来任何收益。这正是"按形态选策略"的反面教材——好的工程是用最省的手段达到目的。

💻 示例讲解

下面这段伪代码把"路由 + 三种切法的核心差异"压成一个骨架,看清逻辑怎么分叉就够,真实实现里还有 token 上限兜底等细节。

# 一个分发器,按文档自带的类型标签选 chunker
def chunker_for(source_type):
    if source_type == "research":   return semantic_chunk   # 研报:语义切
    if source_type == "financial":  return section_chunk    # 财报:章节切 + 表格独立
    if source_type == "policy":     return clause_chunk     # 政策:条款切
    raise ValueError("未知类型,不允许裸奔")   # 没标类型就报错,而不是默默一刀切

# 研报:靠"话题跳了多远"找边界
def semantic_chunk(section):
    sents = split_sentences(section)            # 按 。?! 拆句
    if len(sents) < 5:                          # 太短不折腾,整段一块
        return [join(sents)]
    vecs = embed(sents)                         # 每句算一个向量(花钱的一步)
    chunks, buf = [], []
    for i, s in enumerate(sents):
        buf.append(s)
        # 相邻两句"语义距离" = 1 - 余弦相似度;跳得太远就在这切一刀
        if i < len(sents)-1 and distance(vecs[i], vecs[i+1]) > 0.4:
            chunks.append(join(buf)); buf = []
    return chunks + ([join(buf)] if buf else [])

# 财报:顺章节走,但表格"另起炉灶",绝不进字符切刀
def section_chunk(doc):
    chunks = [sec.text for sec in doc.sections]
    chunks += [tbl.markdown for tbl in doc.tables]   # 每张表独立成块
    return chunks

# 政策:边界是白送的,正则一刀刀切,不算 embedding
def clause_chunk(doc):
    full = join(doc.sections)
    return regex_split(full, r"第[一二三四五六七八九十0-9]+条|第…+款")

推演:假设一段研报有 8 句,前 5 句讲"营收增长",第 6 句话锋一转聊"原材料涨价风险"。语义切会在第 5、6 句之间量到一个大距离(比如 0.55 > 0.4),正好在话题转折处划一刀——检索"营收"时拿到干净的前 5 句,不会混进风险段。换成固定 600 字一刀切,这一刀大概率落在某句话中间,把"营收同比增长 23%"拦腰截断,检索回来只剩"营收同比增长",数字丢了。再看财报:一张含 12 行的利润表,语义切/字符切都会把它劈成两三块,行头和数据分家;章节切让它整张保留,检索"净利润"时一次拿到完整表。政策那份:8 个条款本就 8 条清晰边界,正则切一次成型,0 次 embedding 调用;若硬上语义切,等于为 8 条都跑一遍逐句 embedding,纯属白烧钱。

⚖️ 决策对比

维度我们的选择(类型路由:研报语义 / 财报章节 / 政策条款)替代方案(固定大小一刀切:全走递归字符切 500/50)
研报连续叙述语义距离找话题转折处下刀,块内语义自洽固定字数硬切,大概率从句子中间断,语义割裂
财报表格整表独立成块,信息密度高的部分完整保留表格被字符切刀劈碎,行头与数据分家,数字失去意义
政策条款顺天然边界切,一条一块、可整条引用无视"第X条"边界,一条被切成两半或两条粘成一块
成本政策/财报零 embedding,只研报花句向量,花在刀刃上零 embedding,全程纯字符,确实最省
实现/维护约 250 行、3 个子类继承同一抽象基类,加新语料要写新子类一个 splitter 全包,几乎零维护
定位按内容形态选最合适策略——senior 信号能跑通的 demo 形态

公允裁决:固定大小切块不是稻草人,它有真实优点——零 embedding 成本、一份代码全语料通吃、几乎不用维护,对"语料同质且无结构"的场景(比如一堆纯文本博客)它就是正确答案,上路由反而是过度设计。我们仍选类型路由,是因为金融语料恰恰是异质且强结构的:研报靠语义、财报有表格、政策有条款,三种结构被同一把固定刀切坏的方式各不相同,而损失的都是检索质量(半截句子、碎表格、断条款)。多写约 250 行换来的是"每类语料都按它本来的样子被切"。需要补充诚实的一点:阈值 0.4 是初值(标注"调研后再调",代码里还没看到自动调优),800 token 上限是否偏碎,这些参数是否最优目前缺离线指标来验——见本类第 4 题。

🖼️ 图解

📌 总结

  • 切块决定检索质量:边界划错=检索回半截句子/碎表格/断条款,模型只能瞎补另一半,这是 RAG 摄取阶段的源头损失。
  • 三类语料形态根本不同:研报连续叙述(靠语义找边界)、财报有明确章节+多表格、政策有"第X条"天然边界——同一把固定刀切坏它们的方式各异。
  • 策略要配形态:研报语义切、财报章节切+表格独立、政策条款切;政策不上语义切是因为边界白送,硬切是过度工程还白烧 embedding 钱。
  • 路由不是免费的:约 250 行、3 子类继承同一基类,换来"每类按本来样子被切";固定大小切块对同质无结构语料才是正解,不是稻草人。
  • 诚实的缺口:阈值 0.4 与 800 上限是否最优,目前缺离线指标来验——见本类第 4 题;中文计 token 的坑见本类第 3 题。

一句话速记:文档有结构,而三类金融语料的结构来源不一样,一把固定刀切坏它们各有各的坏法,所以按类型路由,各用一把称手的刀。

Q2

Embedding 你为什么选 qwen text-embedding-v3 当主力而不是 BGE-M3?"同维互换不重建 collection"是什么工程考量?

★★★★☆
embedding 选型同 vendor 复用Milvus 维度约束在线 API vs 本地模型可演进性

🎯 考察点分析

面试官表面问"你选了哪个 embedding 模型",其实在看两件事。第一,你做技术选型时,看的是不是只有"哪个榜单分数高"——榜单分数高的那个(BGE-M3)你恰恰没用,这就逼你说出"分数之外还有什么更重要的工程成本"。第二,"同维互换不重建 collection"是个很具体的钩子,只有真把向量库跑起来、踩过 schema 锁死的人才答得出来。背榜单的人到这里会卡壳。

  • 追问:既然 BGE-M3 中文金融榜单更强,你不用它,是不是把性能让给了省事?这个权衡你怎么向团队解释?
  • 追问:"换 embedding 模型必须重建向量库"——这个 breaking change 到底卡在哪一层?为什么不是改个配置就行?
  • 追问:"复用 reliability"具体复用了什么?如果直接调 SDK 不走你那条链,会少掉哪些保护?
  • 追问:真到 v0.9 要切 BGE-M3,你的切换动作是什么?能不能不停服?

📚 原理讲解

先把 embedding 这一步在系统里的位置说清楚。上一题(见本类第 1 题)把文档按类型切成了一块块文本,这一步要把每一块文本变成一串数字(向量),后面检索时拿用户问题的向量去跟这些块的向量比"谁离得近"。模型就是干"文本→向量"这个翻译的。选模型,本质是在选这个翻译器,而翻译器一旦定下,后面整个向量库都是按它的输出格式建的。

第一层:为什么是 qwen v3 而不是榜单更强的 BGE-M3

核心不是分数,是"同 vendor 复用"。这个项目在更早的阶段就攒下了一套调用大模型的"可靠性四件套":限速器(防止把厂商接口打爆被封)、成本预算(花到上限自动刹车)、自动重试(网络抖一下不至于整批失败)、脱敏(日志里别把密钥漏出去)。qwen 的 embedding 接口跟项目里聊天用的大模型是同一家厂商(阿里 dashscope)、同一把密钥 DASHSCOPE_API_KEY。所以 embedding 调用顺着同一条服务链走,这四件套白捡——不用为 embedding 单独再搭一套限速和预算。这句话在简历叙事里很关键:之前辛苦攒的可靠性层,到这一步真正被第二个场景复用上了,不是摆设。

那 BGE-M3 输在哪?它不是不好,而是要"本地起一个 GPU 服务"。在当前阶段,为了一个 embedding 模型去拉一台 GPU、做模型部署运维,成本和这一阶段的目标不匹配。它真正的强项——原生支持"稠密+稀疏+多向量"的混合检索——是个更后面阶段才吃得上的红利,所以被有意推迟,而不是被否掉。OpenAI 的 text-embedding-3 则直接出局:跨厂商,前面那套可靠性复用全丢,而且它是多语言通才、中文不专项,放在中文研报/财报/政策这种场景没有额外好处。

第二层:维度为什么是 collection 的硬约束

向量库(Milvus)里,一张表(collection)在创建时就要写死"我存的向量是多少维的",这个维度跟它上面建的索引(比如 HNSW 这种近邻图)是绑死的。维度就像水管口径:你建表时声明了 1024,这张表所有的向量、整个索引结构都按 1024 铺好了。后来想塞一个 1536 维的向量进去,口径对不上,塞不进去——不是报个错那么简单,是这张表的索引根本没法容纳。

这就引出"同维互换"为什么值钱。qwen v3 的输出维度是可选的 {64,128,256,512,768,1024}(实测 1536 会被接口拒,1024 已是它的上限),我选了 1024;而 BGE-M3 默认也正好是 1024。两边同维,意味着将来从 qwen 切到 BGE-M3,这三张表(研报 / 财报 / 政策)的结构原封不动,只需要把所有文本块拿出来用新模型重新算一遍向量、写回去(reingest)。表不用动,服务可以平滑过渡。

反过来想象一下不同维的代价:如果新模型是 1536 或 3072 维,口径变了,你必须把三张表全删了重建(drop & recreate),再全量重灌。这中间向量库是空的,检索是瞎的,没有平滑迁移路径。所以"同维"看着像个巧合,实际把"换模型=伤筋动骨的破坏性变更"降级成了"换模型=重算一遍数据"。这是个能省掉一次大手术的工程考量。

💻 示例讲解

看两段逻辑就懂了。第一段:切换模型为什么不该直接 new 一个类,而是改环境变量、让工厂去读;第二段:维度对不上时,向量库会在哪一步把你拦下来。

# 切 backend 的正确姿势:改 .env 里的 EMBEDDING_MODE,不要在业务代码里直接 new 类
# 工厂读环境变量决定造哪个翻译器,业务代码只认 "EmbeddingService" 这个统一接口
def build_embedding_service_from_env():
    mode = os.getenv("EMBEDDING_MODE", "qwen")   # 默认走 qwen,这是当前主力
    if mode == "qwen":
        # 同一把密钥 DASHSCOPE_API_KEY,顺着同一条服务链走 → 限速/预算/重试/脱敏白捡
        return QwenEmbeddingService(api_key=os.environ["DASHSCOPE_API_KEY"])
    if mode == "bge_local":
        # 当前是占位实现,真调用会 raise,提示这是后续阶段才做的本地 GPU 部署
        return BGEEmbeddingService()
    raise ValueError(f"未知的 EMBEDDING_MODE: {mode!r}")

# 两个翻译器都声明自己是 1024 维 —— 这就是"同维"的源头
QwenEmbeddingService.dimension = 1024   # 选 1024(可选到 64,实测 1536 被拒)
BGEEmbeddingService.dimension = 1024    # 默认也 1024 → 同维

# 向量库这一侧:维度在建表时就写死,塞错维度直接被拦
def upsert(collection_dim: int, vector: list[float]):
    if len(vector) != collection_dim:
        # 这一刀拦在写入口:口径对不上,索引压根容不下,不是改配置能绕过的
        raise DimensionMismatch(f"表是 {collection_dim} 维,来的向量是 {len(vector)} 维")
    # 同维才能走到这:表不动,只是把这一块的向量重新写进去
    milvus.insert(vector)

推演:假设全量灌一次知识库,约 13 份文档、切成几百到上千块,每块算一次向量。开发期反复灌同一批数据时,有个缓存兜底(键是"文本+模型+维度"的哈希),命中率约 80%,意味着大部分块不必重复调接口。整批接口调用按文档量级估算成本约 ¥0.14–0.35。调接口时还有个实测坑:文档说一批能传 25 条,实际 11 条以上就被拒,所以一批最多 10 条(_QWEN_MAX_BATCH=10),embed() 内部会自动把大列表切成 10 条一批发出去。将来切 BGE-M3,因为同是 1024 维,这三张表(研报/财报/政策)不删不重建,只是把这几百上千块拿新模型重算一遍写回——一次"重灌",不是一次"重建"。

调用约束有限流(一批≤10)、按量计费,接口稳定性看厂商本地无限流、延迟可控、可微调,代价是自己运维

公允裁决:BGE-M3 不是被打败,是被排期。它的两大真本事——中文金融语料上更领先、原生支持稠密+稀疏的混合检索——都是实打实的优势,后续阶段正是冲着这两点才要切它。但在当前这一阶段,目标是"先把生产级的向量检索跑通",而不是"把检索质量调到极致"。为这个目标去背一台 GPU 服务和一套独立可靠性层,投入产出不划算。qwen v3 用"同厂商复用 + 无新依赖 + 严控范围"赢下当前;而我提前把维度对齐到 1024,等于给 BGE-M3 留好了无缝接入的口子——所以这不是二选一的牺牲,是先后顺序的安排。

📌 总结

  • 选 qwen v3 当主力,赢点不是榜单分数,而是"同厂商同密钥",让 embedding 调用顺着已有服务链走,限速/预算/重试/脱敏四件套白捡——这是之前攒的可靠性层第一次被第二个场景真正复用。
  • BGE-M3 不是被否,是被排期:它中文金融更强、原生支持混合检索,但要起 GPU 服务,与当前"先跑通生产级检索"的目标不匹配,留作后续。
  • 向量库的维度在建表时就和索引绑死,是硬约束;换一个不同维的模型不是改配置,而是把表全删重建的破坏性变更。
  • 我把 qwen 的维度对齐到 1024,正好和 BGE-M3 默认同维——于是"换模型"从"删表重建三张表"降级成"只重算一遍向量",给后续切换留好了无缝口子。
  • 切换动作是改环境变量让工厂去造对应翻译器,而不是在业务代码里直接 new 类;业务代码只认统一接口,这是同一套"接口+工厂+环境开关"模式的又一次复用。

一句话速记:选 qwen 是为了白捡同厂商的可靠性,对齐 1024 维是为了让以后换 BGE-M3 只需重灌、不必拆库。

Q3

中文切块有什么坑?为什么要用中文分隔符 + tiktoken 计 token,而不是直接按字符数切?

★★★☆☆
中文 NLPtokenizer切块tiktoken分隔符

🎯 考察点分析

这道题表面问"切块",其实在探你有没有踩过中文文本处理的两个经典坑:一是分隔符,二是计数单位。很多人直接抄 LangChain 的 RecursiveCharacterTextSplitter 默认配置就上,而那套默认是给英文调的——分隔符是英文标点、size 按字符卡,搬到中文上两头都漏风。面试官想看你能不能把"为什么默认配置在中文上失效"讲清楚,而不是背 API。

  • 追问:LangChain 默认分隔符切中文会出什么具体后果?切点会落在哪?
  • 追问:既然已经按字符切了,为什么还要再引一个 tiktoken 算 token?这两道卡口是互斥还是配合?
  • 追问:你用 cl100k_base 当 tokenizer,但你的 embedding 是 qwen 的,这俩不是一家的,误差怎么办?为什么不直接用 qwen 自己的分词器?
  • 追问:如果哪天想把 cl100k_base 换成更准的 encoder,有什么风险?

📚 原理讲解

切块的目标是:把长文档切成一段段大小可控、边界干净的小块,每块送去算 embedding 再入库检索。"大小可控"和"边界干净"是两个独立的要求,中文在这两点上都和英文不一样,所以默认配置会同时在两处翻车。

坑一:分隔符——英文标点切不到中文句末

递归切块器的工作方式是:给它一串"分隔符优先级列表",它先试最高优先级的分隔符切;如果切出来的块还是太大,就降一级换下一个分隔符再切,层层回退。LangChain 默认列表是英文那一套——双换行、英文句号 .、空格。问题是中文一句话结尾是句号"。"(全角),不是英文点"."。一段中文研报里几乎匹配不到英文句号,切块器没地方下刀,只能一路回退到最低优先级的"空字符串",也就是硬按长度从字中间砍断。结果就是"宁德时代营收同比……"被从"营"和"收"中间劈开,语义碎掉,检索时这一块谁都对不上。

修法很直接:把分隔符列表换成中文的。项目里用的是 ["\n\n", "。", "\n", "?", "!", ";", " ", ""] 这 8 个,从段落空行 → 中文句号 → 单换行 → 问号叹号分号 → 空格 → 空串,按这个优先级递归回退。这样它会优先在段落和句号处断,只有实在没办法了才硬切。

坑二:计数单位——字符数 ≠ token 数

embedding 模型吃的是 token,不是字符,它有 token 上限。可中文"1 个字 ≈ 1.33 个 token"(项目实测口径),英文反过来一个 token 能盖好几个字母。如果你直接拿"字符数"当 chunk 大小的标尺,就等于拿一把刻度错位的尺子去量 token 预算:量出来的块要么偏大、撑爆 embedding 上限被截断;要么偏小、浪费上下文窗口。错位幅度大约 ±33%,不是小数。

所以项目里是两道卡口配合,不是二选一:字符切块器先用 chunk_size=600 字符给一个粗粒度边界(它的活是"在哪断"),然后 base.py 里的 count_tokens() 用 tiktoken 真去数这块有多少 token,做最终是否超 800 token 的判定(它的活是"够不够大、超没超")。一个管边界,一个管预算。

为什么用 tiktoken 的 cl100k_base

这里有个看似别扭的点:embedding 用的是 qwen,token 却用 OpenAI 系的 cl100k_base 来数。原因是需要一个稳定、可复现、本地能算的 token 估计值来卡 chunk_size_max。cl100k_base 对 qwen 分词只是个近似(误差约 ±20%),但它离线、确定、零网络开销,拿来当"卡上限的标尺"足够了——切块阶段要的是一个一致的度量,不是精确到个位的 token 数。真正的 embedding 分词在 dashscope 服务端用它自己的 tokenizer(见本类第 2 题),那是另一回事。

关键告诫:这个 encoder 一旦定下就别换。每个 chunk 入库时都把 count_tokens() 算出的值写进 tokens 字段。你换个 encoder,所有历史 chunk 的 tokens 字段口径就全变了、和新块对不齐,等于污染了整库的元数据。

💻 示例讲解

下面这段伪代码对比"光按字符切"和"两道卡口配合"的差别。注意字符切块器只负责给边界,真正判超限的是 token 计数。

# 同一段中文研报,400 字。中文约 1.33 token/字 => 真实 token ≈ 532

# 做法 A:只按字符切,拿字符数当 token 预算的标尺(错误)
#   英文默认分隔符在中文里匹配不到 => 一路回退到硬切,切点落在字中间
splitter_wrong = RecursiveCharacterTextSplitter(
    chunk_size=800,            # 把 800 当"token 上限"直接拿来卡字符 —— 单位错位
    separators=[".", "\n\n"],  # 英文标点,中文文本里几乎切不到句末
)
# 结果:这 400 字(≈532 token)被当成"才 400,没超 800"留成一整块,
#       而真实 token 已逼近上限;且断点劈在"宁德时代营|收"字中间

# 做法 B:中文分隔符给边界 + tiktoken 数 token 做兜底判定(项目做法)
splitter = RecursiveCharacterTextSplitter(
    chunk_size=600,            # 字符上的粗粒度边界(600 字 ≈ 800 token)
    chunk_overlap=50,          # 相邻块留 50 字重叠,防句子被边界一刀两断
    separators=["\n\n", "。", "\n", "?", "!", ";", " ", ""],  # 优先段落、句号处断
)
rough_chunks = splitter.split_text(text)   # 第一道:在哪断

CHUNK_TOKEN_MAX = 800
for chunk in rough_chunks:
    n = count_tokens(chunk)                 # 第二道:tiktoken cl100k_base 真数 token
    if n > CHUNK_TOKEN_MAX:                 # 超限才二次强切,字符边界没法替它判这个
        chunk = force_resplit(chunk)        # 兜底:再切到 800 token 以内
    # 把 n 写进 chunk.tokens 入库 —— 所以 encoder 一旦定就不能换,否则历史值失真

推演:一段 400 字的中文,真实 token ≈ 400 × 1.33 ≈ 532。做法 A 把它当"才 400 字,离 800 还远"留成整块,实际 token 已经逼近上限、留给后续摘要的余量被吃光,而且断点还劈在字中间;做法 B 先在句号处给干净边界,再用 count_tokens() 实测 532 < 800 放行——边界对齐了,预算也算准了。错位的那 ±33% 正是 A 翻车、B 不翻车的来源。

⚖️ 决策对比

维度我们的选择(中文分隔符 + tiktoken token 感知切)替代方案(纯按字符数切)
实现复杂度多引一个 tiktoken 依赖 + 一道 token 兜底判定最简,一个字符切块器搞定,零额外依赖

公允裁决:纯按字符切真有它的好——实现最省、零依赖、对纯英文或不在乎 token 预算的场景完全够用,而且字符数本身也是确定可复现的,不能说它"不准"得一无是处。它真正的问题是用错了标尺去量中文的 token 预算:中文 1 字 ≈ 1.33 token,拿字符卡 size 会让真实 token 飘 ±33%,加上英文默认分隔符在中文里几乎切不到句末。我们多付的代价就两条:引入 tiktoken、且 cl100k_base 对 qwen 只是 ±20% 近似;换来的是切点对齐语义、大小对齐 embedding 的 token 预算、且整库口径可复现。对一个中文金融语料库,这笔账划算——所以我们选 token 感知切,但保留字符切块器做粗粒度边界,两者配合而非取代。

📌 总结

  • 中文切块两个坑:分隔符(LangChain 默认英文标点切不到中文句末,会硬切在字中间)和计数单位(中文 1 字 ≈ 1.33 token,按字符卡 size 会让真实 token 预算飘 ±33%)。
  • 修分隔符:换成中文 separators 列表 ["\n\n", "。", "\n", "?", "!", ";", " ", ""],按优先级递归回退,优先在段落和句号处断。
  • 修计数:字符切块器用 600 字符给粗粒度边界,tiktoken count_tokens() 实测 token 做"超没超 800"的最终判定——两道卡口配合,不是二选一。
  • tiktoken 用 cl100k_base 是为了一个离线、确定、可复现的 token 估计来卡上限;它对 qwen 只是 ±20% 近似,但当标尺够用。embedding 真正的分词在 dashscope 端(见本类第 2 题)。
  • 这个 encoder 锁死不能换:每个 chunk 的 tokens 字段都是它算的,换 encoder 会让整库历史口径失真。

一句话速记:中文切块要换两把尺——分隔符换中文(否则切在字中间),size 换 token(否则字符数和真实预算错位 1.33 倍)。

Q4

你的知识库评估目前只有 agent 端到端的 LLM 裁判,缺少切块 / embedding / 检索的离线指标。为什么这是个缺口?该怎么补?

★★★★☆
评估体系离线指标检索质量IR 指标评估缺口

🎯 考察点分析

这道题面试官不是在问"你会不会写 eval",而是在看你有没有意识到端到端评估的盲区——能不能区分"评最终效果"和"定位是哪个组件坏了"这两件根本不同的事。会做 RAG 的人很多,知道 RAG 链路是切块 → embedding → 检索 → 生成四段串联、每段都能独立量化的人才是真正调过系统的人。

  • 追问:你现在端到端的分数掉了 10 分,你怎么知道是切块切碎了、embedding 选错了,还是检索 top_k 设小了?
  • 追问:离线指标要建 ground-truth(每条 query 标相关 chunk),这个标注成本不低,为什么还值得做?光靠端到端不行吗?
  • 追问:你说要算 recall@k / mrr / ndcg@k,这三个分别衡量什么?为什么不只看 recall?
  • 追问:如果暂时没精力建完整标注集,有没有低成本的 sanity check 能先把明显的坑兜住?

📚 原理讲解

先说现状。我这套知识库的评估,目前只有一层:端到端的 LLM 裁判(LLM-as-Judge)。具体说,eval_runner.py 拿一批标注好的 golden case(golden_set_v0.jsonl),喂给被测系统(整个 agent),跑完拿到回答和工具调用轨迹,再让一个强模型当裁判去判"这个回答对不对、该调的工具调没调"。它评的是 agent 最末端的输出文本。

为什么这是个缺口:黑盒分数无法定位到层

问题在于,RAG 是一条流水线:用户问题先切块入库、再 embedding 成向量、检索时按相似度召回、最后把召回的片段塞给大模型生成答案。端到端 eval 把这四段全揉进一个分数里。分数掉了,你只知道"系统变差了",却不知道是哪一段的锅——是切块把财报表格切碎了导致召回片段不完整?是 embedding 模型对中文金融语料召不准?还是检索 top_k 设太小漏了关键段?黑盒分数不可定位、不可做控制变量实验。

更具体地说,有一串参数我现在压根没人验过:语义切块的距离阈值 0.4 是不是最优、财报 chunk 800 token 上限是不是切得太碎、qwen text-embedding-v3 和 BGE-M3 谁召回更好、KbSearchService.search 的默认 top_k=5 / threshold=None 是直接拍的、v0.9 计划接的 reranker 到底有没有正收益。这些都是组件级的问题,端到端 eval 一个都答不了。(阈值 0.4 / 800 上限是本类第 1 题路由策略的产物;qwen vs BGE-M3 见本类第 2 题。)

这个缺口是有意为之,不是忘了

要讲清楚一点:这不是疏忽。早期版本里已经塞了 Milvus 部署、三个服务接口、整条入库链路、一份样本语料,如果再加上检索调优的完整评估通路,工作量直接爆掉。所以当时显式把"检索调优 + 离线指标"推迟到下一个版本,因为它需要一套能每晚跑的基线(nightly baseline)才有意义。识别缺口并主动划定边界,本身就是工程判断。

该怎么补:补一层分层离线指标

补法分四步。第一步,建 ground-truth:每条 query 人工或半自动(让 LLM 先标、人复核)标出"哪些 chunk_id 是真正相关的"——这正是当前没做、成本所在的那部分。第二步,算离线 IR 指标:

  • recall@k:相关 chunk 有没有进 top-k。衡量"漏没漏"。
  • mrr(平均倒数排名):第一个相关 chunk 排在第几名,越靠前越好。衡量"准不准"。
  • ndcg@k:考虑相关度分级 + 位置折扣的综合排序质量。衡量"排得好不好"。
  • 外加 chunk 尺寸分布(oversize/undersize rate):看切块健康度,有没有大量 <100 token 的碎片或卡在 800 上限的巨块。

只看 recall 不够:recall 高但相关 chunk 全排在第 5 名(mrr 低),实际上下文窗口只塞前 2 段就漏了。三个指标互补。第三步,写实验脚本(scripts/eval_kb_retrieval.py),固定 query 集 × {切块配置 × embedding 配置 × top_k} 做网格搜索。第四步,结果落盘到 tests/eval/results/kb_retrieval/,可重现、可对比。

关键:离线指标和端到端 eval 不是替代关系,是互补。离线指标负责定位到组件(哪段坏了、哪个配置更好),端到端 eval 负责验最终任务效果(召回准了答案是不是真变好)。两层都要。

💻 示例讲解

下面是离线检索评估的核心循环——教学伪代码,看清楚"网格怎么跑、指标怎么算"即可,不是源码:

# ground-truth: 每条 query 标注哪些 chunk_id 真正相关(这一步最贵,是当前缺的)
gold = [
    {"query": "贵州茅台 2024 毛利率",          "relevant": {"chunk_812", "chunk_815"}},
    {"query": "上市公司分红比例监管要求",         "relevant": {"chunk_1203"}},
    # ... 几十条覆盖研报/财报/政策三类语料
]

def recall_at_k(retrieved, relevant, k):
    # 前 k 个里命中了多少相关 chunk / 一共有多少相关 chunk —— 衡量"漏没漏"
    hit = len(set(retrieved[:k]) & relevant)
    return hit / len(relevant)

def mrr(retrieved, relevant):
    # 第一个相关 chunk 排在第几名,取倒数 —— 排第 1 得 1.0,排第 5 得 0.2
    for rank, cid in enumerate(retrieved, start=1):
        if cid in relevant:
            return 1.0 / rank
    return 0.0   # top-k 里一个相关的都没有

# 关键:把切块/embedding/top_k 当"自变量"做网格,而不是只跑一套默认配置
for chunker_th in [0.3, 0.4, 0.5, 0.6]:     # 语义切块距离阈值(默认 0.4 待验)
    for emb in ["qwen_v3", "bge_m3"]:        # embedding A/B(本类第 2 题的对比对象)
        reingest(chunker_th, emb)            # 改了切块/embedding 必须重新入库重算向量
        for k in [3, 5, 10]:                 # 检索 top_k(默认 5 是拍的)
            scores = []
            for case in gold:
                got = kb_search(case["query"], top_k=k)   # 返回 chunk_id 列表
                scores.append((recall_at_k(got, case["relevant"], k),
                               mrr(got, case["relevant"])))
            record(chunker_th, emb, k, mean(scores))       # 落盘 -> 画 recall heatmap

推演:假设跑出来 top_k=5 时 qwen 的 recall@5 = 0.72、BGE-M3 = 0.78,而把切块阈值从 0.4 调到 0.5 后 qwen 的 recall@5 升到 0.81——这一下就定位了:原来切得太碎(0.4 切边界太频繁)才是主因,换 embedding 反而是次要因素。这种结论端到端 eval 永远给不出,它只会告诉你"换了配置答案分数从 71 涨到 79",但说不清功劳是切块还是 embedding 的。这就是分层指标的价值:把一个黑盒分数拆成可归因的若干条曲线。

⚖️ 决策对比

维度我们的选择(现状 + 计划补的)替代方案(端到端 eval vs 分层离线指标)
评估对象离线指标评单层(切块/embedding/检索),端到端评最终答案,两层并存纯端到端只评最终答案文本 + 工具调用
可定位性分数掉了能归因到具体某一层、某个配置黑盒,坏了不知道是哪段的锅
控制变量实验能做阈值网格 / embedding A/B / top_k 曲线做不了——改一个参数答案变了,功劳说不清
可重现性IR 指标确定性强,固定 query 集每次结果一致LLM 裁判有抖动,同一回答评分可能漂
标注成本高:要给每条 query 标相关 chunk_id(当前缺口所在)低:只需标"问题→期望答案",无需 chunk 级标注
贴近真实任务离线指标≠最终效果,召回高不代表答案好直接评最终任务,最贴近用户真实体验

公允裁决:端到端 eval 绝不是该被替换掉的废物,它有两个真实优势——不需要 chunk 级标注(标注成本低很多)、直接对齐真实任务(召回再准,如果生成环节没用上,用户拿到的还是烂答案,这只有端到端能抓)。所以它必须保留,作为"最终效果"的守门员。但它的代价是黑盒:无法定位、无法做控制变量。分层离线指标恰好补上这两点,代价是要先付 ground-truth 标注的成本——这正是当前还没做的原因,不是不知道要做,而是上一个版本 scope 已满,主动推迟了。正确答案是两者并存:离线指标定位组件、端到端验最终效果。谁也替不了谁。

🖼️ 图解

📌 总结

  • 缺口本质是"不可定位":端到端 LLM 裁判把切块/embedding/检索/生成揉成一个黑盒分数,分数掉了说不清是哪一层的锅,也做不了控制变量实验。
  • 补法是加一层分层离线指标:建 ground-truth(每 query 标相关 chunk_id)→ 算 recall@k / mrr / ndcg@k + chunk 尺寸分布 → 网格脚本跑「切块×embedding×top_k」→ 结果落盘画 recall 热力图。
  • 三个 IR 指标互补:recall 看漏没漏、mrr 看相关项排第几、ndcg 看整体排序质量,只看 recall 会被"召回了但排很后"骗过去。
  • 两层不是替代是互补:离线指标定位组件、可重现、能网格搜索;端到端 eval 不需 chunk 级标注、直接对齐真实任务。决策对比里端到端的两个优势必须承认,正确答案是并存。
  • 缺口是主动推迟不是疏忽:上个版本 scope 已塞满 Milvus + 入库链路,检索调优 + nightly 基线被显式推到下一版——识别并划定边界本身是工程判断。低成本兜底:手写 query 肉眼看 top_k 命中、看 embedding 缓存命中率(~80%+)、看 chunk token 直方图有没有大量碎片或卡上限。

一句话速记:端到端 eval 只告诉你"系统坏了",分层离线指标(recall@k/mrr/ndcg@k + chunk 尺寸)才告诉你"哪一层、哪个配置坏了"——前者验效果、后者定位,代价是先建 ground-truth 标注。

Q5

RAG 和"直接把长文档塞进上下文"之间你怎么权衡?什么时候其实不该用 RAG?

★★★☆☆
RAG vs 长上下文权衡取舍语料规模成本检索

🎯 考察点分析

这道题问的是判断力,不是"你会不会搭 RAG"。如今上下文窗口动辄几十万 token,确实有不少场景"直接把整篇喂进去"又简单又准。面试官想看你能不能讲清楚:RAG 是为了解决什么问题才存在的?它带来了哪些额外代价?以及——什么时候该克制,别上 RAG。能主动说出"这种情况我不上 RAG"的候选人,比一上来就背切块/embedding/检索流程的,段位高一截。

  • 追问:你的知识库到底多大?这个量级塞得进上下文吗?(逼你给出真实规模数字,而不是空谈)
  • 追问:除了"塞不下",RAG 还能做到长上下文直塞做不到的什么事?(看你能不能答出按来源/字段过滤、缓存复用,而不是只会说"省 token")
  • 追问:RAG 引入了哪些新的出错环节?这些环节你测了吗?(把成本算全,别只讲好处)
  • 追问:给你一个只有两三篇短文档的需求,你还上向量库吗?(考你会不会过度设计)

📚 原理讲解

先把两条路线讲明白。长上下文直塞:把整篇(或整批)文档原文塞进模型这一次对话的输入里,让模型自己在里面找答案。RAG(检索增强生成):提前把文档切成小块、每块算一个"语义指纹"(embedding 向量)存进向量库;用户提问时,先把问题也转成向量,去库里捞出最相关的几块,只把这几块喂给模型。一个是"全量端上桌",一个是"按需点菜"。

RAG 的存在前提:语料根本装不进上下文

我们这个金融研究助手,真实业务规模的假设是 1000 到 10000 篇文档,每篇切成 200 到 500 个小块,合起来是 20 万到 500 万个向量。这个量级,任何上下文窗口都装不下——哪怕窗口再大十倍也没用。所以这里 RAG 不是"可选优化",是"不先检索就没法干活"的硬约束。这是判断要不要上 RAG 的第一个锚点:语料总量塞不塞得进。

RAG 真正多出来的能力:按字段过滤,只命中相关子集

我们的语料分三种来源:券商研报、公司财报、监管政策。用户问"招商证券对某公司怎么看",这只该去研报里找;问"某公司三季度营收多少",只该去财报里找;问"某项补贴政策",只该去政策里找。我们把三种来源放进三个独立的"库"(collection),每条记录还带着发布机构、发布日期、公司代码这类标签。检索时可以先按这些标签过滤,只在相关子集里捞。长上下文直塞做不到这种过滤——它要么把所有东西一锅端进去(token 爆炸、注意力还被无关内容稀释),要么得另写一套规则在外面先挑文档。这是第二个锚点:是否需要按来源/属性过滤。

成本结构:一次性摊销 + 双层缓存 vs 每次全量重付

RAG 把"算向量入库"做成一次性开销:一篇文档入库一次,之后无数次提问都复用。而且我们在两层都加了缓存——算向量这一步有本地缓存(开发期反复跑,命中率约 80%,等于省掉绝大部分重复计算);查询这一层有 LRU 缓存(容量 1000、有效期 1 小时),高频重复的问题第二次问基本是免费的。反观长上下文直塞:每问一次,整篇文档的 token 都要重新付一遍费,而且喂得越长、响应越慢、模型注意力越被稀释。这是第三个锚点:同一批文档会不会被反复查。

但 RAG 不是免费午餐:它新增三层出错环节

这是回答里最容易被忽略、却最能体现判断力的部分。上了 RAG,你就引入了三个原本不存在的失败面:① 切块边界切得好不好(切碎了关键信息就召不回);② embedding 召回准不准(语义指纹捕捉得对不对);③ 检索调参(取前几个、相似度阈值卡多少)。这三层在我们项目里恰恰还缺独立的离线评估(这块怎么补,见本类第 4 题)。所以 RAG 的复杂度,只有在语料规模/复用频次撑得起时才划算。

💻 示例讲解

用一段决策伪代码,把"先判断、再选路线"的逻辑走一遍。注意它不是真实源码,只是把判断锚点显式化:

def 选择回答策略(语料):
    总_token = 估算总token(语料)            # 全部文档加起来多大
    篇数     = len(语料.文档)
    会反复查 = 语料.是否长期复用            # 这批文档以后还会被问很多次吗
    要按来源过滤 = 语料.来源数 > 1          # 研报/财报/政策 这种多源场景

    # 锚点一:总量塞得进 且 就一两篇 且 一次性 —— 直接塞,别上重型方案
    if 总_token < 上下文上限 and 篇数 <= 2 and not 会反复查:
        return 长上下文直塞(语料)          # 不切块、不建库,实现最简单也最准

    # 锚点二:结构有天然边界 且 需要全文连贯推理(如逐条对照整份政策)
    #         切碎反而丢上下文 —— 这种也别切,整篇塞
    if 需要全文连贯推理(语料) and 总_token < 上下文上限:
        return 长上下文直塞(语料)

    # 否则:语料大 / 多源要过滤 / 高复用 —— RAG 不可替代
    return RAG检索(语料)                   # 切块→算向量入库→按标签过滤→取前k块

推演:两边各代一组数。场景 A:用户上传一份 8 页的政策原文,只想就这一份逐条问。整篇约 1 万 token,远小于窗口,就 1 篇、还要逐条连贯对照——走左路直塞:零建库成本、不会因切碎丢上下文,答得又快又准。场景 B:我们的真实知识库,1k–10k 篇、20 万–500 万个向量,三种来源要分开查——这个量级根本塞不进任何窗口,必须走右路 RAG:入库一次性摊销,查询命中 LRU 缓存时几乎零成本,还能按"只查研报、且发布机构=招商证券"精确过滤。判断标准全在那三个锚点:总量、是否多源过滤、复用频次。

⚖️ 决策对比

维度我们的选择(语料大时上 RAG)替代方案(长上下文直塞整篇)
能承载的语料规模20 万–500 万向量也能扛(先检索再喂)受窗口硬限,总量超出就直接做不了
能否按来源/字段过滤三个库 + 标签过滤,只命中相关子集做不到,要么全塞要么外挂一套挑选规则
成本模型入库一次性摊销 + 算向量缓存(命中≈80%)+ 查询 LRU 缓存(1000/1h)每次提问整篇 token 重新付费,越长越慢、注意力越稀释
实现复杂度切块/embedding/向量库一整套,重把原文拼进 prompt 即可,极轻
新增失败面切块边界 + 召回质量 + 检索调参 三层(且当前缺离线评估)没有这三层,出错点少
全文连贯推理切碎后跨块推理会丢上下文,是弱项整篇在场,逐条对照式推理是强项

公允裁决:长上下文直塞绝不是"落后方案",在它的射程内反而更优:语料总量塞得进、就一两篇、一次性不复用、或需要逐条连贯对照时,直塞不引入切块/召回/检索三层失败面,不把有天然结构的内容切碎,实现还最简单——这种情况硬上 RAG 才是过度设计(同我们"政策有天然条款边界就不做语义切""财报表格不进切分器"的克制一脉相承:天然装得下/不能切碎的,就别上重型方案)。我们之所以仍以 RAG 为主力,纯粹是被真实规模逼的:1k–10k 篇、上百万向量的多源金融语料,塞不进任何窗口、又必须按来源精确过滤、还要被反复查询——这三条同时成立,RAG 才不可替代。判断的本质不是"谁更先进",而是对着语料规模、是否需过滤、复用频次、是否需全文连贯这四把尺子量一量。

🖼️ 图解

📌 总结

  • RAG 是被规模逼出来的:1k–10k 篇、20 万–500 万向量塞不进任何窗口,必须先检索再喂,这时 RAG 不是优化是刚需。
  • RAG 多出长上下文做不到的两件事:按来源/标签过滤只命中相关子集(三库 + 机构/日期/公司码),以及入库一次性摊销 + 算向量缓存(≈80%)+ 查询 LRU 缓存(1000/1h)。
  • 三种情况别上 RAG:① 总量塞得进、就一两篇短文;② 有天然结构、需整篇连贯推理(切碎反丢上下文);③ 一次性不复用,建索引摊销不回来。
  • RAG 的代价要算进去:它新增切块边界、召回质量、检索调参三层失败面,而这三层当前还缺离线评估(见本类第 4 题),复杂度只在规模/复用撑得起时才划算。
  • 判断锚点就四把尺子:语料规模、是否需过滤、复用频次、是否需全文连贯——量一量再决定,而非默认上 RAG。

一句话速记:语料塞得进且就一两篇一次性就直塞,装不下/要分来源过滤/要反复查才上 RAG——别为两篇文档建一座向量库。
