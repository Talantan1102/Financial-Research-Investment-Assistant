07代码解释器与工具沙箱

代码解释器与工具沙箱这一类讲的是:与其给模型一堆写死的计算函数,不如让它当场写 Python 跑。围绕这个能力,本类拆解四件事——把「让模型写代码」和「跑预审脚本」的边界划在哪、怎么复用已有沙箱并隔离与留 Docker 换插口、为什么交互图走旁路事件而不进模型上下文、以及实测才暴露的两个非显然坑(绘图依赖与数学库线程数)。这些题既能讲清产品取舍,又能展示「让模型生成的代码安全执行」这个面试高频考点上的分层工程方案。

Q1

你为什么让 LLM 现场写 Python 跑(代码解释器),而不是给它一堆固定的计算工具?这个边界划在哪?

★★★☆☆
代码解释器工具边界产品取舍克制最小化

🎯 考察点分析

这道题面试官表面问"为什么加代码解释器",真正想看的是你划工具边界的判断力:你能不能说清"什么算一个工具",而不是看到需求就堆功能。给 LLM 一个能现场写代码跑的工具,听起来很酷,但它带来执行不可信代码的安全代价、占一个常驻的工具名额——这都是要还的债。会划边界的人,能讲清这个债为什么值得欠。

  • 追问:你本来就有"跑预写脚本"的工具了,代码解释器和它有什么本质不同?为什么不把它做成那个工具的一个增强参数?
  • 追问:哪些计算应该固化成固定工具、哪些必须让模型现场写?这条线划在哪个维度上?
  • 追问:你之前明明定过"通用计算不开工具名额"的原则,现在又开了,这算不算自己打脸?你怎么判断这次破例是清醒的还是一时冲动?
  • 追问:多花的代价具体是什么?你拿什么换来的?

📚 原理讲解

先说清两个工具长什么样,它们是这道题的两个主角。一个叫"跑技能脚本":仓库里事先写好、人工审过的脚本(比如一段估值计算的脚本),模型要用的时候只是选个脚本名、传几个参数,自己不写一行代码。另一个叫"代码解释器",对外叫 run_python:模型当场写一整段任意的 Python 源码,丢进沙箱跑出来。这两个工具看着都是"执行代码",但模型在里头扮演的角色完全不一样——前者是"点菜",后者是"下厨"。

边界划在"需求能不能被穷举"上

关键判断不是"这事算不算计算",而是"这类计算需求能不能事先列全"。能列全、能预审的,就固化成固定脚本——比如一套 DCF 估值流程,逻辑是定的,写一次审一次,以后模型选名字传参就行,安全又可信。列不全的呢?用户会问"把这家公司近五年营收画成趋势图""这几只股票的估值指标对比一下出张图"——这种"二次计算 + 任意可视化"的组合是无穷无尽的,你永远列不完。固定工具碰到这种需求只能把数字念出来,既做不了二次加工、也产不出图。这块缺口,只有让模型现场写代码才能补。

为什么是新工具,不是老工具加个参数

有人会想:既然都是"执行代码",给"跑技能脚本"加个"也能传源码"的参数不就行了?不行,因为这俩的安全画像是相反的。跑预审脚本的代码是人写人审的,可信;模型现场写的代码是生成出来的,不可信。一旦工具能接不可信代码,那道 AST(把代码解析成语法树后逐个节点扫黑名单)安全扫描的分量立刻变重——它从"锦上添花"变成"最后一道闸"。把可信和不可信两种语义塞进同一个工具,等于让调用方在"安全可信"和"高危需扫描"之间反复横跳,边界一糊,安全推理就没法做了。所以它们语义正交,刻意不合并。

这是清醒地破了一条旧决策

聊天主循环重新设计时定过一条原则:"通用计算固化进技能脚本,不给它开工具名额。"代码解释器是有意识地破这条。破得有没有道理,看一个判据:这是不是一种"模型自己写新代码"的全新能力?是。它跟"跑预审脚本"根本不是一回事,值一个独立的工具名额。设计文档里把这个张力诚实地标了出来——不是忘了旧决策,是认了它、然后清醒地偏离它。这种"破例时把账算给自己看"的习惯,比"从不破例"更值钱。

💻 示例讲解

用一段伪代码对比两个工具在"路由层"的样子。注意模型在两边交出去的东西完全不同——一边交脚本名,一边交源码。

# —— 工具 A:跑预写技能脚本(可信路径)——
# 模型只挑名字 + 传参,不写代码;脚本是仓库里人工审过的
run_skill_script(
    script_ref="valuation/dcf",      # 选一个已存在的脚本
    payload={"ticker": "600519", "wacc": 0.09},
)
# 安全画像:可信 —— 代码人写人审,AST 扫描只是兜底

# —— 工具 B:代码解释器 run_python(不可信路径)——
# 模型当场写一整段源码;需求穷举不完,只能现写
run_python(
    code=(
        "import plotly.graph_objects as go\n"
        "rev = data['revenue']          # 近五年营收,从别的工具拿来的\n"
        "fig = go.Figure()\n"
        "fig.add_scatter(x=rev['year'], y=rev['value'])  # 画趋势线\n"
        "result = '近五年营收趋势已画'   # 给模型看的结论\n"
    ),
    data={"revenue": {"year": [2021, 2025], "value": [109, 170]}},
)
# 安全画像:不可信 —— 源码是模型生成的
# 进沙箱前先过 AST 黑名单:open / socket / subprocess / __import__ 一律拦

推演:假设用户要"五年营收趋势图 + 三只股票估值对比图"。走固定工具:你得为这两种需求各预写一个脚本并审过,而下周用户再问"营收和净利润画双轴",你又得加第三个——需求是发散的,固定工具永远在追尾。走代码解释器:这三个需求都是模型现写几行 plotly 搞定,一个工具名额(它的完整调用文档常驻在上下文里)兜住一整类无法穷举的需求。代价是这一个名额下接的是不可信代码,所以那道 AST 扫描必须扛得住——这就是为什么聊天主循环原有的 14 个工具全是"查数据/检索/控制"类、都不需要这层防护,而 run_python 作为升上去的第 15 条工具文档,是唯一需要把"执行不可信代码"当一等公民对待的。

⚖️ 决策对比

维度我们的选择(两者并存:固定脚本 + 代码解释器)替代方案(只给固定计算工具)
覆盖范围可枚举计算走固定脚本;无法穷举的二次计算/任意图走现写代码,缺口被补上只覆盖事先列得全的计算,新需求来了就得加新脚本,永远追尾
安全画像固定脚本可信;代码解释器明确标"不可信",靠 AST 黑名单 + 断网 + 内存限额 + 一次性目录多层兜底全程可信代码,安全推理最简单,几乎不用考虑逃逸
工具名额成本多占 1 个核心组(core)常驻名额(完整调用文档常驻可见)零额外名额,上下文最省
可视化能力模型现写 plotly,任意图都能出(散点矩阵/箱线/对比图)只能把数字念出来,产不出图
对旧决策清醒地破"计算零名额",并把账写进设计文档严守旧决策,不破例

公允裁决:只给固定计算工具这条路真有它的好——所有进沙箱的代码都是人写人审的,安全推理干净到几乎不用想逃逸;上下文里也不用多养一个工具名额,极致省。如果产品只服务一小撮固定的计算场景,它就是更对的选择,克制原则也偏向它。我们仍然没走它,只因为一个事实顶不住:用户的"二次计算 + 画图"需求是穷举不完的,固定脚本注定在追尾,而追尾的代价是用户问到时只能干念数字。所以决策不是"用代码解释器替换固定工具",而是两者并存——能预审的计算继续走固定脚本,需要当场写新代码或画图才落到代码解释器。顺带说一句,被否的还有两个极端:"只给聊天用"被否,因为深度研报流程也要画图;"做成通用代码执行服务"也被否,那是过度设计,违背克制默认。

📌 总结

  • 边界的判据不是"算不算计算",而是"这类需求能不能事先列全":能列全、能预审的固化成脚本;列不全的(任意二次计算 + 任意画图)才让模型现写代码。
  • "跑预审脚本"和"代码解释器"语义正交、刻意不合并:前者代码可信、模型只传参;后者代码不可信、模型当场写——硬塞进一个工具会让安全画像反复横跳。
  • 这是清醒地破例:破了"通用计算零名额"的旧决策,因为"模型自主写代码"是一种全新能力,值一个独立工具名额,并把这笔账诚实写进设计文档。
  • 代价被明算出来:执行不可信代码让 AST 黑名单扫描分量变重,外加一个核心组(core)常驻名额——拿这点债换住一整类穷举不完的需求。
  • 决策是并存不是替代;沙箱怎么复用与隔离见本类第 2 题,产出的图怎么旁路不进上下文见本类第 3 题。

一句话速记:能列全的计算固化成可信脚本,列不全的让模型现写代码——边界划在"要不要模型自己写新代码",代价是多扛一份不可信代码的安全债。

Q2

代码解释器怎么复用已有的技能执行沙箱(内联入口)?怎么隔离、又怎么留了换 Docker 的口子?

★★★★☆
沙箱复用进程隔离内联入口 execute_sourceDocker 留口AST 黑名单

🎯 考察点分析

这是一道"既要复用又要留后路"的工程取舍题。让大模型当场写 Python 跑(为什么不给固定工具,见本类第 1 题),意味着要执行不可信代码——面试官想看你是不是上来就喊"上 Docker",还是先盘清楚仓库里已经有什么、复用要补哪块短板、怎么把"更强隔离"留成一个不破坏现有代码的换插口。这考的是框架最小化的判断力,不是堆隔离层数。

  • 追问:已有的技能执行器原本只跑磁盘上的脚本,内联源码(模型现写的字符串)是怎么塞进去的?为此加了什么新入口?
  • 追问:隔离到底有几层?内存、CPU、网络、文件、超时分别靠什么挡住?哪一层是这次代码解释器评审时新补的?
  • 追问:既然要扫掉用户码里的 open/exec,那你套 plotly 主题、注入数据这些动作又用到了这些禁用 API,怎么自圆其说?
  • 追问:哪天想换成真正的容器隔离,要改几个文件?工具层会被动到吗?

📚 原理讲解

先讲底子。仓库里早就有一套给"技能脚本"用的执行沙箱(SkillExecutor),它的隔离不是进程内 exec 那种纸糊的,而是真起一个子进程,外加内存/CPU 上限、网络黑名单、一次性工作目录、超时杀进程组——而且配套有二十多条已有的安全测试在守。代码解释器要执行的也是不可信代码,需求几乎一模一样。所以第一个决策是:不新建沙箱,复用这套。新建一套等于把那二十多条安全测试重写一遍,还多养一套运维,违背框架最小化。

原版只跑磁盘脚本,所以要补一个"内联入口"

但原版有个硬约束:它的入口 execute() 是"给我技能名和脚本路径,我去磁盘上把文件读出来扫一遍再跑"。模型当场写的 Python 是一段字符串,根本没有磁盘文件。所以加了个新入口 execute_source(source, payload, timeout_s):直接拿这段字符串做 AST 安全扫描,扫过了就写进一次性临时目录的 user_code.py,再走同一条子进程执行路径。隔离逻辑一行没改,只是把"先读盘"换成"先落盘"。

隔离是多层叠加,全套白嫖

子进程起好后,挡住越界的有四道:① 内存——非 macOS 用 RLIMIT_AS 把虚拟内存压到 256MB;② CPU——RLIMIT_CPU 限 CPU 时间,死循环烧不久;③ 网络——AST 黑名单里 socket.socket/requests.*/httpx.* 全在,代码里写不出联网调用;④ 文件 + 环境——只跑在一次性临时目录里,跑完整个目录 rmtree 删掉,子进程的环境变量只放行 PATH/LANG/LC_ALL/LC_CTYPE 四个,其余全抹掉。再加超时:子进程用 start_new_session=True 起独立会话,超时直接 SIGKILL 整个进程组,防止用户码 fork 出的孙子进程漏网。

"可信 wrapper"这个巧思:扫用户码,不扫包装层

这里有个看似矛盾的点:我们禁掉了用户码里的 open/exec/compile,可套 plotly 主题、把数据注入命名空间、捕获 print、抓出图对象再序列化——这些动作恰恰要用 open/exec。解法是两段代码、两种信任级别:用户码写进 user_code.py(要过 AST 扫描);另写一段我们自己控制的可信包装层 interp.py(不过扫描,所以能正常用 exec/open),由它去 exec 用户码。包装层需要的数据和主题,用 base64 编码后注进去——base64 是纯 ASCII,避开了把一坨 JSON 拼进源码字符串时的引号转义地狱。

执行语义:无状态单发,天生契合

为什么这套一次性子进程沙箱用着这么顺?因为代码解释器的执行语义是无状态单发——每次调用 = 一段完整脚本 + 一个一次性目录,跑完即焚。它没有 Jupyter 那种长寿 kernel,也就没有 kernel 生命周期、并发隔离、内存泄漏面这些麻烦。代价是模型迭代时要重发全量代码(多花点 token),换来的是架构极简。这跟"一次性子进程"是天作之合,不用额外造任何状态管理。

Docker 的口子:抽一个单方法 Protocol

哪天想要更强隔离(真容器),怎么不动工具层就换掉?把沙箱底座抽成一个 ExecutorBackend 协议,只有一个方法 run_code(source, data, timeout_s)。v1.0 唯一实现 SkillExecutorBackend 把活委派给 execute_source;DockerExecutorBackend 接口位置已经留好、本期不实装。真要换,只新增一个后端实现,工具层(CodeInterpreterTool)一行不动——它只认这个协议。

💻 示例讲解

下面用伪代码把"内联入口"那一段走通——重点看用户码和可信包装层是怎么分家的:

# 工具层只认一个协议,不关心底下是子进程还是 Docker
class SkillExecutorBackend:
    async def run_code(self, source, data, timeout_s):
        # 委派给新增的内联入口
        return await executor.execute_source(source, data, timeout_s)

async def execute_source(source, payload, timeout_s):
    # 1) 只扫「用户码」—— open / exec / subprocess.* / requests.* 命中就拒
    scan_script_safety(source)          # 不过就直接返回 safety_scan_rejected

    # 2) data 和绘图主题用 base64 注进可信包装层
    #    （纯 ASCII,避开把一坨 JSON 拼进源码的引号转义坑）
    wrapper = WRAPPER_SRC.replace("__DATA_B64__", b64(payload)) \
                         .replace("__IOS_B64__", b64(theme))

    # 3) 落进一次性临时目录:用户码一份、可信包装层一份
    with one_shot_workdir() as wd:       # 跑完整目录 rmtree
        write(wd / "user_code.py", source)   # 这份过了扫描
        write(wd / "interp.py", wrapper)     # 这份是我们写的,不扫,能用 exec/open
        # 4) 走同一条子进程路径(隔离逻辑一行没改)
        return await run_subprocess(wd / "interp.py", wd, timeout_s)

# 可信包装层内部(简化):它能用 exec/open,因为它不经扫描
#   exec(open("user_code.py").read(), {"data": _DATA})   # 注入 data 变量
#   figs = ns.get("figures") or [ns["fig"]]              # 从命名空间抓图
#   print(json.dumps({"result": ..., "figures": figs}))  # 序列化成契约 JSON

推演:用户码若写了 requests.get("http://..."),在第 1 步 AST 扫描就被拦(命中黑名单),返回 safety_scan_rejected,根本起不了子进程。若是死循环,子进程跑满 30s(默认上限,最高 300s)触发超时,对独立会话整组发 SIGKILL;若申请超过 256MB 内存,RLIMIT_AS 让分配直接失败。三种越界各有一道闸,且都复用原有的二十多条安全测试,没新写一套。

⚖️ 决策对比

维度我们的选择(复用技能执行器 + 留 Docker 口)替代方案(新建一套沙箱 vs 复用技能执行器)
隔离强度子进程 + rlimit + AST 黑名单 + 断网 env + 一次性目录(中上)新建/上 Docker:容器级隔离最强;进程内 exec:几乎为零
运维成本零新增——就是个子进程Docker 要装/管/起容器,重;进程内 exec 零运维
已有测试复用白嫖底座 25+ 条安全测试新建沙箱要把安全测试重写一遍
改动量只新增一个内联入口 execute_source新建沙箱要从头写隔离、env、超时、扫描全套
换更强隔离实现一个新后端即可,工具层不动没抽象层时,换隔离要动调用方
作品叙事体现取舍判断,不堆冗余隔离层进程内 exec 隔离最弱,作品减分

公允裁决:新建一套/上 Docker 的隔离确实最强,容器级边界是子进程 rlimit 比不了的——这不是稻草人,真要跑社区上传的任意代码,Docker 是正解。我们没选它,是因为这是个单用户作品:仓库已有的子进程沙箱功能高度重合,再上 Docker 等于功能重复 + 凭空多一套运维,违背框架最小化;而它能挡住的额外攻击面(比如内核级逃逸),在"单用户 + 断网兜底"下风险很低。进程内 exec 那头则相反——零运维但隔离最弱,任意代码能直接读宿主文件,作品上拿不出手。所以落点是复用,代价是要给原本只跑磁盘脚本的执行器补一个内联入口;同时用一个单方法 Protocol 把 Docker 路径留成 v1.x 换插口——既拿到复用的全部好处,又没把"更强隔离"的门焊死。

📌 总结

  • 复用不是省事,是省一套安全测试:仓库已有生产级子进程沙箱 + 二十多条安全测试,新建沙箱要全重写;上 Docker 则与现有功能重复还多养运维——所以复用,只补一个内联入口。
  • 原版只跑磁盘脚本,内联入口 execute_source 是关键补丁:把模型现写的字符串先 AST 扫描、再落进一次性目录的临时 .py,然后走同一条子进程,隔离逻辑一行没改。
  • 隔离是四道叠加闸,各挡一类越界:RLIMIT_AS 挡内存(256MB)、RLIMIT_CPU 挡死循环、env 白名单只放 4 个变量 + AST 黑名单挡联网、一次性目录 + 超时 SIGKILL 进程组挡逃逸与漏网孙进程。
  • "可信包装层"化解扫描悖论:用户码过 AST 扫描(禁 open/exec),我们自己写的包装层不扫(可用 exec/open 去套主题、注入数据、抓图),数据走 base64 注入避开转义坑。
  • Docker 留口是一个单方法 Protocol:底座抽成 ExecutorBackend,换更强隔离只新增一个后端实现,工具层一行不动——既拿到复用好处,又没焊死升级门。

一句话速记:复用子进程沙箱白嫖隔离与测试,加一个内联入口跑模型现写的码,再用一个单方法协议把 Docker 留成不动工具层的换插口。

Q3

为什么 plotly 交互图走单独的图表事件、而不进 LLM 的上下文?如果进了会怎样?

★★★★☆
图表旁路KV-cacheSSE 事件上下文污染成本控制

🎯 考察点分析

这道题表面在问"图怎么渲染",底下其实在考你对一条铁律的理解:模型的上下文窗口是稀缺、昂贵、且会被复用的资源,什么东西配进、什么东西必须挡在外面,要有清醒的判断。代码解释器画的 plotly 交互图,是一个典型的"用户需要看、但模型不需要看"的产物——你怎么处理它,直接暴露你有没有把"给前端渲染"和"喂给模型推理"这两件事拆开想。

  • 追问:一张 plotly 图的 JSON 大概多大?塞进回喂模型的 tool 消息里,具体会连累后面几轮?为什么是"后面每一轮"而不只是这一轮?
  • 追问:模型既然看不到图,它怎么知道"图画出来了"、又怎么在回复里跟用户提这张图?你给它留了什么线索?
  • 追问:这条旁路落在代码哪一层做?为什么不是工具自己发事件,而是放到编排循环里做?
  • 追问:你为什么不复用已有的图表渲染链路(比如固定几类图的 ECharts 配置),非要走 plotly?

📚 原理讲解

先讲清楚一个反直觉的事实:模型根本不需要看图。一张折线图对人来说是"一眼看懂趋势",但对模型来说,figure JSON 就是一大堆坐标点、颜色、布局参数的字典——它读这些数字推不出什么有用结论,反而被一堆噪声淹没。模型需要的是"图画成了、画的是什么结论",而不是图里每个点的 x/y 值。

为什么"进上下文"是灾难:KV-cache 铁律

一张 plotly 交互图序列化成 JSON,体量可达数 KB。代码解释器的输出会作为 tool 消息回喂给模型,进入对话历史。这里有个关键点:这段历史不是只用一次——它会跟着对话一路滚下去,每一轮新的推理都要把它重新读一遍(KV-cache 里它一直占着位置)。所以一张几 KB 的图塞进去,不是污染"下一轮",而是污染"从此往后的每一轮":窗口被顶掉一块、每轮 token 成本被抬高一截,而这部分开销换来的是模型完全用不上的坐标点。如果用户连画三张图,这个雪球会越滚越大。

旁路怎么走:figures 在编排层被剥离

解法是给图开一条专用通道:走 chart 这种服务端推送事件(SSE),figure 直接送到前端渲染,压根不经过模型的上下文。落点很具体——在聊天循环 loop.py 的 _extract_and_emit_charts 这个后处理环节里:它检查每个工具的 output 里有没有 figures 这个键(这就是约定,谁产图就放这个键,无需改循环逻辑),有就逐张发 chart 事件,然后把 figures 从 output 里 pop 掉,换成一个 charts_rendered 计数;就算没图,也把空的 figures 键清掉,保证回喂模型的 output 永远是干净的紧凑结构。

chart_id 为什么要确定性

每张图的 id 是四段拼出来的:{请求 id}-{step}-{结果序}-{图序},没有任何随机数。这意味着同一次执行重跑,id 完全可复现——前端能稳定对应、调试能对上号、测试能断言。这是"可观测/可测试"的小细节,但面试官爱听。

职责单一:工具不碰副作用

代码解释器工具本身只老老实实返回 {result, figures, stderr, elapsed_s} 四个字段,它不发 SSE、不碰缓存、不写摘要。发 chart 事件、剥离 figures、超大结果截断这些副作用,统一集中在循环的后处理里做。这符合本项目"loop.py 是唯一有副作用的编排壳"的分工——工具是纯函数式的,所有"对外界产生影响"的动作收口在一处,谁出问题一眼能定位。

💻 示例讲解

下面这段伪代码还原"工具产图 → 循环剥离 → 一分两路"的逻辑。注意工具有多老实、剥离有多简单:

# —— 工具侧:只负责返回结构化结果,绝不碰 SSE / 缓存 ——
def code_interpreter_tool(...) -> dict:
    out = run_sandbox(code)              # 在沙箱里跑 LLM 写的 Python
    return {
        "result":   out["result"],       # 模型要看的:结论 / 数值
        "figures":  out["figures"],       # 一堆 plotly 字典,每个可达数 KB —— 模型不要看
        "stderr":   out["stderr"][:500],  # 自纠用的报错,截到 500 字节防刷屏
        "elapsed_s": out["elapsed_s"],
    }

# —— 循环后处理:唯一有副作用的地方,把图剥出来旁路掉 ——
async def _extract_and_emit_charts(results, state):
    for ridx, r in enumerate(results):
        figures = r.output.get("figures")
        if figures:                       # 约定即接线:谁产图就放 figures 键
            for fidx, fig in enumerate(figures):
                # 确定性 id:无随机,可复现、可测试、前端可对应
                chart_id = f"{state.request_id}-{state.step}-{ridx}-{fidx}"
                await emit("chart", chart_id=chart_id, figure=fig)  # 上路:直送前端渲染
            r.output.pop("figures")       # 把图从模型侧 output 里彻底抠掉
            r.output["charts_rendered"] = len(figures)  # 只给模型留一个计数
        else:
            r.output.pop("figures", None) # 没图也清掉空键,保持模型侧 output 干净
        # 图剥完了,再量真正进窗口的体积做超大截断(顺序很重要)
        cap_oversized_output(r, state)

推演:假设这一轮模型让代码解释器画了 2 张图,每张序列化后 4 KB。若走"进上下文":回喂的 tool 消息约 8 KB,这 8 KB 从此每一轮都被重读——聊 10 轮就是这块 token 被算了 10 次,而模型一次都没真正"用"到坐标点。走旁路后:8 KB 的图经 chart 事件直送前端用 PlotlySpecRenderer 渲染,回喂模型的只剩 result + "charts_rendered=2" + 两个 chart_id,几十字节量级。前端照样画出交互图,模型也知道"画了 2 张、id 是啥"能在回复里提它——上下文干净 + 成本可控 + 图能渲染,三个目标同时满足。

维度我们的选择(图表事件旁路)替代方案(图 JSON 进上下文)

公允裁决:替代方案不是没道理——它确实最省事,不用单开事件通道、不用在循环里加剥离逻辑,代码量更少,新手最容易先这么写。如果图只有几十字节、对话只有一两轮,这点污染可能也无所谓。但代码解释器的图是 plotly 交互图、动辄数 KB,而对话是多轮长程的——"省一次实现的事"换来的是"每一轮都付的成本",这笔账长期看完全不划算。更要命的是,这些坐标点模型根本读不懂、用不上,纯粹是负收益的噪声。所以我们宁可多花一条事件类型 + 一个后处理环节,把图彻底挡在窗口之外。判断标准很清晰:这个产物用户要看、模型用得上吗?用户要看但模型用不上的,一律旁路。

📌 总结

  • 图给人看、不给模型看:plotly figure JSON 可达数 KB,坐标点对模型是噪声;它要的只是"画了、画的什么结论"。
  • 进上下文会污染"往后每一轮":tool 消息进对话历史后被反复重读(KV-cache),数 KB 图顶掉窗口、每轮抬高 token 成本,画得越多雪球越大。
  • 旁路落点具体:循环后处理检测 output 里的 figures 键(约定即接线),逐张发 chart 事件后 pop 掉,换成 charts_rendered 计数;空键也清,保模型侧 output 干净。
  • chart_id 确定性:四段式 请求 id-step-结果序-图序 无随机,可复现、可测、前端可对应。
  • 职责单一:工具只返回 {result, figures, stderr, elapsed_s},所有副作用收口在 loop——谁出问题一眼定位。这些图由哪个沙箱产出见本类第 2 题,plotly 依赖与线程坑见本类第 4 题。

Q4

你踩的两个坑——plotly 要用精简构造避开地图依赖、沙箱要把数学库设成单线程避免内存爆——各是怎么定位和解决的?

★★★★☆
plotly 依赖坑OpenBLAS 单线程内存超限 OOM端到端冒烟诊断链复盘

🎯 考察点分析

这道题不考"你会不会装包"。面试官想看的是:你能不能把一个看起来玄学的报错(装包失败、容器里莫名 OOM、前端空白图)倒推到根因,而不是抬一下内存上限、换一个版本号碰运气。这考的是定位方法论——尤其是"哪一层的测试才能照出这个坑"的元认知。

  • 追问:为什么单测和 mock 测试照不出沙箱 OOM?你是怎么意识到必须上真子进程的?
  • 追问:OpenBLAS 的内存为什么和线程数挂钩?把线程锁成 1 除了省内存,还顺带换来了什么好处?
  • 追问:遇到内存爆,最直觉的修法是把 256MB 上限抬高。你为什么没这么做?
  • 追问:这两个坑有什么共性?能不能抽象出一条"这类坑该用什么测试守"的规律?

📚 原理讲解

两个坑分属前后端,但诊断套路一模一样:症状 → 根因 → 修法,而且都卡在"低层测试照不出、必须真环境跑"这个点上。我分开讲。

坑一:全量 plotly.js 拖来一条连不上的地图依赖

前端要画交互图,最直觉的是装官方全量 plotly.js。但它内部为了支持地图类图表,依赖了 mapbox-gl,而这条依赖是 git 型的"奇异子依赖"(exotic subdep)——它不走正常 npm registry,而是要去 GitHub 拉源码。我们用的包管理器 pnpm v11 有个开关叫 blockExoticSubdeps,默认会拒绝这种 git 子依赖;雪上加霜的是本机网络连不上 GitHub,就算放行也拉不下来。更隐蔽的一点:pnpm 的 auto-install-peers 默认开着,会自动替你把这个 peer 依赖拉进来——也就是说你根本没主动要它,它自己冒出来把装包整个搞挂。

定位手段很朴素:装包时冒烟报错。错误信息直接点名 mapbox-gl 和 exotic subdep,顺藤摸瓜就找到了根。修法是换成 plotly.js-dist-min——这是官方预构建好的单包,把需要的东西打成一个文件、不再去拉那条地图依赖;再用 react-plotly.js/factory 这个工厂函数把单包"喂"给 React 组件(这正是官方文档给 bundler 用户推荐的接法);装包命令再补一个 --config.auto-install-peers=false,从源头掐掉自动拉 peer 的行为。

坑二:沙箱里 numpy/plotly 一跑就内存爆

沙箱给每个子进程套了 256MB 的地址空间硬上限(RLIMIT_AS,具体见本类第 2 题)。问题出在数值计算底座:numpy、pandas、plotly 底下都靠 OpenBLAS 做矩阵运算,而 OpenBLAS 默认按 CPU 核数起线程,并且每个线程都预先占一块内存"竞技场"(arena)。机器有几核它就开几个线程、占几块 arena,一乘起来轻松撑爆 256MB,直接报 OpenBLAS error: Memory allocation still failed。

关键在于:这个坑只有真子进程 e2e 测试才抓得到。mock 测试里既没有真的 subprocess、也没有真的 OpenBLAS 在跑,它永远复现不了——你的单测全绿,沙箱却跑一个炸一个。

修法不是抬内存上限(那会破坏沙箱的隔离承诺),而是在构造子进程环境时,用 _minimal_env() 注入四个"锁单线程"的环境变量:OPENBLAS_NUM_THREADS / OMP_NUM_THREADS / MKL_NUM_THREADS / NUMEXPR_NUM_THREADS 全设为 1。线程数压到 1,arena 就只占一块,内存稳稳守在上限内。意外之喜:单线程顺带让数值结果可复现——多线程下浮点求和的累加顺序不确定、结果会有末位抖动,锁单线程后每次跑都一模一样。对作品里以串行小计算为主的脚本(比如现金流折现 DCF)来说,牺牲的那点并行性能基本无感。

共性:这类坑是低层测试的盲区

两个坑、加上端到端真浏览器跑全栈才暴露的另两个坑(下面对比表会带到),指向同一条规律:涉及真子进程、真包管理器、真浏览器渲染的坑,mock 和单测照不出来,必须把测试推到"真环境冒烟"那一层。这也是我后来把验证手段从"单测绿"升级到"e2e 真子进程 + 真浏览器跑全栈"的直接动因。

💻 示例讲解

看坑二的修法落点——构造子进程时怎么把环境"削干净"并锁单线程。这是教学伪代码,锚点函数名 _minimal_env 与仓内一致:

# 只放行最小白名单环境变量,其余一律不继承(隔离 + 收敛攻击面)
ENV_WHITELIST = {"PATH", "LANG", "LC_ALL", "LC_CTYPE"}

# 把数值库全部锁成单线程：每个线程会预占一块内存 arena，
# 多线程下 N 块 arena 在 256MB 上限里直接撑爆 → OOM
SINGLE_THREAD = {
    "OPENBLAS_NUM_THREADS": "1",   # numpy / pandas 底层的 BLAS
    "OMP_NUM_THREADS": "1",        # OpenMP 并行
    "MKL_NUM_THREADS": "1",        # 万一换 Intel MKL 也兜住
    "NUMEXPR_NUM_THREADS": "1",    # numexpr 表达式引擎
}

def _minimal_env():
    # 第一步：从当前环境里只挑白名单里的变量
    env = {k: v for k, v in os.environ.items() if k in ENV_WHITELIST}
    # 第二步：强行盖上单线程设置（守内存上限 + 让结果可复现）
    env.update(SINGLE_THREAD)
    return env

# 起子进程时把这套环境喂进去；外加地址空间硬上限做兜底
subprocess.Popen(
    [sys.executable, script_path],
    env=_minimal_env(),          # 单线程环境，避免 OpenBLAS 爆内存
    preexec_fn=apply_rlimit_256mb,  # 256MB RLIMIT_AS（本类第 2 题）
)

推演:假设机器是 8 核。默认情况下 OpenBLAS 会起 8 个线程,每个线程预占一块 arena;就算每块只要几十 MB,8 块叠起来加上 numpy 数组本身,256MB 上限瞬间被击穿,报 Memory allocation still failed。换成 NUM_THREADS=1 后只剩 1 块 arena,内存占用从"按核数翻倍"降回单份,稳稳卡在上限内跑通。代价:8 核的并行算力没用上——但 DCF 这种几十行的串行小计算,本来也吃不到并行红利,无实质损失。

公允裁决:默认配置不是傻方案——全量 plotly.js 在能联网、不限内存的常规环境里用着没毛病,官方也确实把它当主推包;OpenBLAS 多线程在算力充足的服务器上是性能默认值,跑大矩阵明显更快。它们错只错在不匹配我们这套约束:本机断网拉不到 GitHub、沙箱给每个子进程死死卡 256MB。我们没有去松约束(抬内存、放行 git 子依赖)——那等于拆掉沙箱隔离和断网兜底这两块基石;而是反过来让依赖和线程配置去适配约束。单线程牺牲的并行性能,对一个以串行小计算为主的个人作品几乎为零损失,换来的是"装得上、不爆内存、结果还可复现"。更深一层的教训是:这类坑 mock/单测照不出,必须把验证推到真环境冒烟那一层,否则你会带着满屏绿勾把坑发到生产。

📌 总结

  • plotly 坑:全量 plotly.js 拖来 mapbox-gl 的 git 子依赖,被 pnpm 拒 + 本机断网双杀;换 plotly.js-dist-min 单包 + factory 建组件 + 关 auto-install-peers,装包冒烟即抓出。
  • 内存坑:OpenBLAS 按核数起线程、每线程占一块 arena,在 256MB 上限下 OOM;修法不是抬内存(那破隔离),而是四个 NUM_THREADS=1 锁单线程。
  • 单线程白送一个好处:守住内存上限之余,顺带让浮点累加顺序确定、数值结果可复现;串行小计算无并行损失。
  • 元规律:涉及真子进程/真包管理器/真浏览器的坑,mock 与单测照不出,必须把验证推到 e2e 真环境冒烟那一层。
  • 同类两坑:工具放 deferred 让模型看不到输出契约 → 裸调写错(升 core 修);figure 进 valtio 变只读、plotly 就地 mutate 抛错被静默吞 → 空图(深拷成可变对象修)。

一句话速记:两条诊断链同一个教训——约束变了(断网 + 256MB),就让依赖和线程去适配约束,而不是松约束;而这类坑只有真环境冒烟照得出。
