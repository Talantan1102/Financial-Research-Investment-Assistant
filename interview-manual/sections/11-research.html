11检索与深度研究

这一组聚焦 AlphaScout 的「深度研究」能力——它怎么把网络搜索、知识库检索和多智能体写作拼成一份有据可查的研报,为什么刻意只给研究、不给买卖建议,以及怎么用一套指标量化研报质量。前两题从产品取舍切入,后两题深入检索-合成的工程链路与评估方法,整体由浅入深。

Q1

深度研究模式为什么刻意"不给投资建议"?这个产品决策背后的考量是什么?

★★★☆☆
产品决策去推荐化深度研究合规免责评估自洽

🎯 考察点分析

这个问题表面问"为什么不给建议",其实面试官想看的是:你能不能把一个看似"砍功能"的动作,讲成一个想清楚了的产品决策。一个只会加功能的工程师,和一个知道"为了把另外几件事做对、要主动放弃哪件事"的工程师,差别就在这里。所以我会重点听你能不能把三层动机讲全、有没有把放弃的代价也摊开说。

  • 追问:"不给建议"是改了几行文案,还是真把能力删了?能不能举出代码上的证据?(想确认你不是嘴上去推荐、实际只改了个标题)
  • 追问:既然连目标价都不给了,为什么估值区间("它值多少")反而保留?这两个不都是数字吗?
  • 追问:去掉推荐,产品的金融差异化是不是就没了?你拿什么补?
  • 追问:这个决策跟你们的评估体系有什么关系?为什么说它"顺手解决了评估最大的痛点"?

📚 原理讲解

先说背景。这个产品里有一种"深度研究"模式,对一只股票产出一份六节的长报告:公司概览、合规资质、财务分析、行业分析、风险评估,以及最后的综合研判。最初这份报告的定位叫"投资尽调建议",最后一节是直接给客户经理一个可执行的结论:买入还是卖出(五档评级)、目标价多少、建议仓位百分之几、入场价区间、止损价定在哪。说白了就是替人下单。

2026 年 6 月 4 日做了一个决策:把整份报告从"尽调建议"重新定位成"深度研究",刻意不再给这些指令性的结论。注意"指令性"(prescriptive)这个词——意思是"告诉你该怎么做"的字段。被砍掉的大约是七个:五档买卖评级、建议仓位、建议持有期、建议入场价区间、建议止损价、建议目标价区间、仓位管理条件。

关键:这是真删能力,不是改文案

面试时最容易被戳穿的就是这里。我们做的不是把标题从"投资建议"改成"综合研判"就完事。代码层面是真的把能力拿掉了:报告 schema 里原来那个 InvestmentRecommendation(投资推荐)类,整类重命名成了 InvestmentSynthesis(综合研判),里面那些指令性字段直接不存在了;字段说明里白纸黑字写着"不给买卖评级/目标价/仓位"。更彻底的是,负责"算出推荐"的那套引擎也一起退役了——分类评级的脚本、计算建议仓位的脚本、那份推荐规则表,全部从仓库里删掉。删到磁盘上文件都不在了,这就不是文案游戏。

为什么删了推荐,反而保留估值区间和多空辩论

这是这道题最见功力的一刀。直觉上"估值区间"和"目标价"都是数字,凭什么留前者删后者?区别在于它们回答的是不同性质的问题:

"它值多少"——估值区间是一个研究结论。我用多个模型交叉验证(市盈率法、市净率法、现金流折现的三种情景)算出"这家公司内在价值大概在某个区间",这是基于公开材料的分析判断,跟"它能不能涨"无关。这类结论留下。

"你该买还是该卖"——这是一个对未来的押注,本质是替读者承担决策风险。这类结论删掉。所以原来缩在角落的多空辩论(看多方论点 bull_case、看空方论点 bear_case,各最多五条),反而被提拔成最后一节的主体:把正反两面摆平、不下结论,判断权交还给读者自己。一句话——呈现两面、不替你拍板。

三层动机

(1) 更贴评估主流。业界通用的深度研究评测基准(像 DeepResearch Bench、GAIA、RACE 这些),没有一个是去评"投资预测准不准"的,它们评的都是研究质量本身——有没有据、引得对不对、全不全面。报告里"给推荐"这一块恰恰是唯一一个跟主流脱节的东西。去掉它,产品就回到了深度研究评估的主航道上。

(2) 跟免责声明自洽。报告底部那行固定免责声明,从一开始就写着"不构成投资建议或具体买卖指令"。结果正文里却堂而皇之给五档评级和止损价——这是自己打自己脸。去推荐之后,声明和正文终于说一致了。

(3) 顺手拆掉评估最大的雷。这一层是连带好处,细节归本类第 4 题。简单说:只有"推荐/预测"这一个维度,打分时必须拿"报告生成日之后真实发生的涨跌"来对。可裁判模型的知识截止日往往晚于历史回测的那个时间点,它"记得未来"——这是致命的数据泄露。删掉推荐,这把唯一需要"未来真相"的尺子就没了评测对象,泄露问题随之消失。

💻 示例讲解

用对比的方式看最后一节的数据结构怎么从"指令"变成"研判"。下面是教学伪代码,锚点用真实类名 InvestmentSynthesis。

def render_section_6(report) -> str:
    # 关键:此处不再有 "if rating == 买入: print(目标价)" 这种下结论分支
    # 取而代之的是左右并排陈列双方论点,中间不做裁决
    return two_column(report.synthesis.bull_case,    # 左:看多

推演:同一只股票,旧版第 6 节会吐出"评级=买入、目标价=¥X、仓位=20%、止损=¥Z"四个可执行指令;新版第 6 节吐出的是"看多 5 条 + 看空 5 条 + 一句呼应估值区间的描述",零个指令性字段。配套的免责声明常量(在 schema 文件第 16–22 行)继续挂在报告底部,这下正文和它不再矛盾。被删的不只是这几个字段,还有上游那两个算推荐的脚本和那份规则表——能力是从根上拔掉的。

⚖️ 决策对比

维度我们的选择:只给研究不给建议替代方案:继续给出投资建议
对使用者的"好用度"给两面论点 + 估值区间,读者自己拍板,门槛略高直接给评级 + 目标价 + 仓位,客户经理拿来就能用,体验更顺手
产品差异化靠数值校验 + 多模型估值 + 多空辩论撑金融味,差异化更"绕""敢下买卖结论"本身就是最直接的差异点,辨识度高
合规风险与免责声明自洽,个人作品不向散户下指令,稳给散户下具体买卖指令,合规风险高、个人作品不合适
评估可行性四把尺子评"对材料忠不忠实",不碰未来真相,可复现多一把"预测命中"的尺子,但它必须拿截止日之后的涨跌打分
数据泄露无泄露——没有任何一项需要"未来真相"来评分裁判模型"记得未来",致命泄露(详见本类第 4 题)
评估主流贴合度回到通用深度研究评测主航道(无一评投资预测)"评预测"偏离主流基准,自成一套难对标

公允裁决:给建议这条路绝不是没价值——它确实更"好用",对客户经理是即拿即用,差异化也最直接,而且"预测命中率"是唯一一把能拿客观未来真相打分、不依赖裁判模型主观的尺子,失去它是实打实的损失。我们仍然选择不给建议,是因为三点压过来:一是个人作品给散户下买卖指令既不合规也不合适;二是那把"未来真相"的尺子会顺带把整个历史回测污染成数据泄露,等于用一把会作弊的尺子量东西,不如不要;三是去掉它产品才回到深度研究评估的主流航道上。代价(失去那把客观尺子)我们用数值校验对真值、多模型估值、多空辩论这三样补回来——判断这个交换划算,而且整体更自洽。

📌 总结

  • 定位换了:报告从"投资尽调建议"重定位为"深度研究",2026-06-04 砍掉约七个指令性字段(评级/目标价/仓位/止损等)。
  • 真删能力:不是改文案——推荐类整类重命名为综合研判,上游算推荐的两个脚本和规则表都从仓库删除。
  • 留对了东西:"它值多少"的估值区间是研究结论,留;"你该买卖吗"是押注,删。多空辩论被提拔成压轴,呈现两面、不替读者拍板。
  • 三层动机:贴评估主流(通用基准无一评投资预测)+ 与免责声明自洽 + 顺手拆掉评估里"未来真相"造成的数据泄露(详见本类第 4 题)。
  • 代价想清楚了:失去唯一一把拿客观未来真相打分的尺子,改用数值校验对真值 + 多模型估值 + 多空辩论补,判断这个交换划算且更自洽。

一句话速记:不是不敢下结论,而是有意把"它值多少"(研究)留下、把"你该买卖吗"(押注)交还给读者——一刀同时换来合规自洽、评估去泄露、回归主流三件事。

Q2

为什么要接外部搜索?搜索结果怎么喂进研究链路?

★★★☆☆
外部搜索工具接入可靠性数据采集生产级 API

🎯 考察点分析

这道题表面问"为什么要联网",真正想看的是:你能不能讲清楚知识库的能力边界在哪里,以及当你决定调一个会花钱、会限流、会失败的真实第三方 API 时,工程上要补哪些功课。面试官最怕听到"接个搜索 API 不就一行 requests"这种答案——那说明你只碰过 demo,没碰过生产。

  • 追问:知识库(向量库)已经能检索了,为什么还非得接实时搜索?它俩各自的"盲区"是什么?
  • 追问:搜索 API 会超时、会被限速、会扣费。这四件事(限流 / 熔断 / 配额 / 成本)你分别用什么手段兜底?为什么这么排序?
  • 追问:搜索回来的原始 JSON 长什么样不归你管,下游 agent 又要统一格式。这个"翻译层"放在哪一层?为什么不让每个工具自己解析?
  • 追问:为什么自己写 80 行 httpx,而不直接用官方 SDK?换一家搜索引擎你要改几个文件?

📚 原理讲解

研究链路里负责"找数据"的角色叫数据采集器(DataCollector)。在接外部搜索之前,这个项目所有外部数据源都是假的——用一个大模型现编一段"看起来像搜索结果"的文字塞回去(早期的 MockBochaService)。这能让流程跑通、让测试稳定,但有个根本盲区:它永远只知道训练时见过的东西,触达不到"此刻刚发生的事"。

知识库为什么不够

知识库(本项目用 Milvus 向量库)能检索的,只有你事先灌进去(ingest)的那批语料——你导了哪些研报、财报、政策,它就只能在这些里面找。它擅长"这家公司护城河的历史分析在哪份研报里",但回答不了"今天早上这家公司发了什么公告""最近一周的舆情怎么样"。这类时效性信息根本不在库里。接实时搜索,本质就是给数据采集器开一扇窗,让它能拉到知识库里没有的当下事实。两者是互补关系,不是替代关系(知识库做"深"的存量,搜索做"新"的增量)。

接的是什么、底层怎么搭

接的是博查(Bocha)搜索 API。底层不用官方 SDK,而是自己写了一个约 80 行的 BochaClient——本质就是"拼好请求头、发一个 POST、按状态码分类结果"。自写的理由很实在:SDK 的封装好不好是别人说了算,自己写则把超时、重试、凭证完全攥在手里;更关键的是,哪天要换一家搜索引擎,只需要换掉这一个文件,上层链路一行都不用动。

原始结果怎么变成下游能吃的东西

博查返回的是它自家结构的 JSON(嵌套在 data.webPages.value 里,字段叫 name/siteName/datePublished 这种)。BochaClient 内部有个 _normalize() 把它拍平成统一形状:每条结果就是 {标题, 链接, 摘要, 片段, 站点名, 日期}。这一步很要紧——它把"博查的方言"翻译成"链路的通用语",所以下游 agent 永远只见统一格式,换搜索引擎时下游无感。

结果怎么进研究链路

项目里有两个搜索工具:网页搜索(web_search,通用)和新闻搜索(get_news)。它俩拿到归一化结果后,数据采集器把每条结果包成一个 ToolResult,通过一次状态更新 {"tool_results": 结果列表} 写进研究状态(state)。再往后的分析师 / 撰写 agent,就从 tool_results 这个共享黑板上读数据,去分析、写报告。注意两个工具共用同一套可靠性设施(同一个限流器 / 熔断器 / 配额计数器实例),不是各搞各的——因为它们打的是同一家 API,额度和故障必须共账。

从假到真的开关 + query 不是裸发

mock 和真实之间靠一个环境变量 BOCHA_MODE 切换,默认是 mock,这样老测试零回归;设成 real 才走 BochaClient 真打博查。还有个细节:数据采集器不会把用户原话裸发给搜索,而是用投资目标(保本 / 稳健 / 进取)和投资期限等上下文给 query 追加关键词(比如保本目标会补"风险评估 偿债能力"),让搜出来的东西更对路。

💻 示例讲解

下面这段伪代码展示一次真实搜索从"进闸门"到"喂下游"的完整走法。关键是看四道可靠性闸门的顺序:先做不花钱就能拒的预检查(配额、成本),再进熔断器,熔断器里面才排队限流、真发请求、按需重试。

# 一次外部搜索:四道闸门 + 重试 + 归一化 + 喂下游

async def reliable_search(query, count):
    # 闸门1:配额预检查——这个月用超了就直接拒,连请求都不发(省钱省时)
    if 配额计数器.本月已用 >= 月度上限:        # 上限示例 1000 次/月
        raise 配额超限

    # 闸门2:成本预检查——累计花费超预算(示例 ¥20/月)直接拒
    成本预算.断言未超额()

    # 闸门3:熔断器——最近连续失败 >= 5 次就「跳闸」,30 秒内一律快速失败
    #         不再去捶一个已经挂掉的服务(closed → open → half_open 三态)
    async def 一次尝试():
        # 闸门4:限流器——滑动窗口,60 秒内最多 N 次;超了就 await 排队
        await 限流器.获取许可()
        return await 带重试地真发请求(query, count)

    result = await 熔断器.call(一次尝试)

    # 成功了才计数、才记账(预检查只是「估」,真发生了才落账)
    配额计数器.加一()
    成本预算.记一笔(单次约 ¥0.01)
    return result


async def 带重试地真发请求(query, count):
    for 第几次 in range(3):                      # 最多重试 3 次
        try:
            return await bocha_client.search(query=query, count=count)
        except (网络错误, 服务端5xx错误) as e:   # 只有这两类才重试
            延迟 = 1.0 * (2 ** 第几次) + 抖动(0, 0.2)  # 1s / 2s / 4s + ±200ms
            await asyncio.sleep(延迟)
            continue
        # 限速429 / 鉴权401 / 客户端4xx → 不重试,重试也没用,直接抛
    raise 最后那个错误

# 拿到结果后(已被 _normalize 拍平成 {items:[{title,url,summary,...}]}):
结果列表 = [打包成ToolResult(条目) for 条目 in result["items"]]
state.更新({"tool_results": 结果列表})            # 写进共享黑板,下游 agent 来读

推演:假设博查那头抽风,连着返回 5xx。第 1 次失败 → 等 1s 重试;第 2 次失败 → 等 2s 重试;第 3 次还失败 → 抛错(总共 3 次 attempt,延迟 1s/2s/4s 中实际只睡前两次)。这一连串失败会喂给熔断器;如果短时间累计到 5 次连续失败,熔断器跳闸 open,接下来 30 秒所有搜索请求不再真发、直接快速失败,等冷却期过了进 half_open 放一个试探请求探活。错误细分 5 类、只有网络 / 服务端两类重试,是因为另外三类(限速 429 / 鉴权 401 / 请求本身畸形 4xx)重试纯属浪费——你再发 100 次,401 还是 401。

⚖️ 决策对比

公允裁决:纯知识库 + mock 这条路不是稻草人——它在早期阶段是正确的选择:让整条研究流水线先跑通、让测试稳定、不引入凭证和限流负担,而且故意只用 1 行 import 就能在后面切真,把"接真 API"这件重活儿留到值得做的时候再做。它真正的、唯一的硬伤是来源是假的:大模型现编的"搜索结果"对一份要给人看的研究报告是致命的,因为研究产物的生命线就是"有据可查、来源可追"(怎么保证不编造来源,见本类第 3 题)。一旦研究质量上升为目标,假来源就不可接受,实时搜索的工程负担也就值得付。所以这不是"新方案碾压旧方案",而是阶段目标变了:从"先让它转起来"变成"让它说真话",决策随之翻面。

  • 接搜索的理由是补盲区:知识库只覆盖事先灌进去的静态语料,搜索补的是它够不到的当下事实(最新公告 / 新闻 / 舆情),两者互补不替代。

Q3

深度研究的编排:多源检索 → 深读 → 带引用合成,怎么保证有据可查、不编造来源?

★★★★☆
多阶段流水线引用接地防幻觉多智能体评审 Critic

🎯 考察点分析

"写一篇深度研报"这件事,最容易出的事故不是写得不好看,而是它把数字编圆了——一个看起来专业、引用齐全、结论笃定的报告,里面的关键数据其实是模型凭语感脑补出来的。这道题我想看的是:你有没有把"防编造"做成系统结构层面的约束,而不是在提示词里写一句"请不要编造数据"就当解决了。换句话说,你的流程里有没有让"每个结论都能反查到它依据的原始数据"这件事,是被 schema 和评审机制硬性兜住的。

  • 追问:你说每个分析洞察都"挂着"原始数据,那这个"挂"是嘴上说说,还是数据结构上真做了字段约束?哪个字段?
  • 追问:就算分析阶段挂了数据,最后写报告时模型还是可能加一句没出处的话。你最后这一关靠什么拦?
  • 追问:你这个"评审"打分,跟你们离线那套评估指标是同一套东西吗?如果不是,职责怎么分?
  • 追问:多搞这么多阶段,小十次模型调用、7 到 9 秒延迟,凭什么不一把梭哈让模型一次吐出整篇?省下来的钱和时间不香吗?

📚 原理讲解

先讲为什么不能一把梭哈。如果给模型一个大提示词"请就贵州茅台写一篇深度研报",它会一口气吐出一篇文从字顺的东西。问题在于:这中间没有任何可校验的中间产物。它说的"2024 年营收 1500 亿"到底是查到的,还是顺嘴编的,你无从分辨——因为取数和写作糊成了一团,没有留痕。防编造的第一性原理是:要让"结论"和"它的证据"在结构上可分离、可反查。一团糊在一起的文本做不到这件事,所以必须把流程拆开。

我们把深度研究拆成一条五阶段的串行流水线:计划 → 取数 → 深读 → 合成 → 评审,每个阶段一个独立的智能体,各自读写一块结构化的中间状态。下面逐段讲,重点看每一段"留了什么痕"。

阶段一:计划 + 多源取数(把意图拆成可执行的取证清单)

用户一句"分析下茅台的基本面",太笼统了没法直接取数。第一个智能体(研究规划器)先把这句话拆成一串子任务,每个子任务带一个"推荐用哪几个工具"的清单(比如"盈利能力"这个子任务推荐调财务数据工具)。然后取数智能体照着这张清单,并行地去调多个数据源——股票行情、财务报表、新闻、联网搜索、知识库检索,五个来源一起取(底层用并发把这些工具调用一把发出去,谁失败了也不拖累别人)。取回来的所有原始结果,统一塞进状态里的一个"工具结果"池子。这一步留下的痕是:一份带子任务编号的计划,和一池子原始取数结果。(联网搜索/新闻怎么接进来、怎么喂,见本类第 2 题,这里不重讲。)

阶段二:深读(分析必须挂回它依据的原始数据)

这是防编造的第一道结构性约束。深读智能体(分析师)读那池子原始结果,产出一条条结构化的"分析洞察"。关键不在它写了什么,而在这个洞察对象长什么样——它的数据结构强制带三个字段:一是它关联回的子任务编号(这条洞察是在回答计划里的哪个子任务),二是一个叫supporting_data 的列表(明确指向工具结果池子里它所依据的那几条原始数据),三是置信度(高/中/低三档)。注意这是字段级的硬约束:一条洞察如果不挂证据,它在结构上就是不完整的。这就把"分析必须有据"从一句口号变成了 schema 兜底。

阶段三:带引用合成(图用自定义协议占位,跟真图片区分)

合成智能体(撰写器)把这些挂好证据的洞察组织成最终的 Markdown 研报。这里有个小而关键的设计:报告里要插图,但 v0.5 阶段先不真渲染,而是写一个占位符 ![描述](chart://chart_id),同时单独产出配套的图表规格,前端拿到后再去渲染真图。为什么用 chart:// 这个自定义协议头而不是普通的 http(s)://?因为用户消息里可能本来就带真实的 Markdown 图片链接,得有个办法把"我们自己的图占位"和"外部真图片"区分开,不互相误认。

阶段四:多智能体评审(不编造来源的核心防御)

前面三阶段留了痕,但留痕不等于自动校验。真正的防编造闭环在这第四关:一个评审智能体(Critic)对成稿做多维评分。它的实现有意思——它是项目里第一次真正启用"子智能体扇出"机制的地方(在此之前这个机制只是基类里一个会抛"未实现"的占位)。评审环节用框架的扇出能力,并行派出多个独立的打分员各管一维:事实准确性、计划覆盖度、洞察深度、结构、简洁度……各自打完分再归并成一份评审报告(总分取各维均值)。(下面为了讲清结构,按 v0.5 的五维基线展开;现网评审已扩到 8 维——多了输入上下文恰当性、估值一致性、辩证平衡三维,调用数和延迟也相应上升,讲法不变。)

这 5 个打分员里,有两个是直冲"有据可查"来的:事实准确性打分员专门对照阶段一收集到的那池子原始工具结果给事实打分(它的评分标准就是一句很直白的话:"所有数据点准确给 10 分……严重失实给 0 分"),它就是在查"报告里的数字跟我们实际取到的数据对不对得上";覆盖度打分员则对照计划里的子任务清单,查报告有没有漏掉某个原计划要分析的点(评分标准:"所有子任务都覆盖给 10 分……完全偏题给 0 分")。这两条对照线,就是"有据可查"被内置成产品里一个常驻审稿人的样子。

一个容易混的边界:产品内审稿 ≠ 离线评估

这个 Critic 是产品内的审稿人——它给每一篇实际产出的报告打分、不合格还能触发重写。它跟离线评估体系里那个"裁判"是两套不同职责的东西:Critic 在生产链路里逐篇把关,离线评估是拿一批样本算指标、做消融实验、横向比版本。两者可以共用同一套评分标准模板来减少重复,但别把它们当成一回事。(研究产物怎么做离线指标化评估,见本类第 4 题。)

💻 示例讲解

用伪代码串起整条链路,重点看两处"留痕约束":洞察对象怎么挂证据(阶段二),以及评审怎么扇出并对照原始数据打分(阶段四)。

# ① 阶段二的核心:洞察对象是带强制证据字段的结构,不是一段自由文本
class Insight(BaseModel):
    subtask_id: str                       # 关联回计划里的哪个子任务(回溯线 1)
    finding: str                          # 这条分析说了什么
    supporting_data: list[dict]           # 指回原始工具结果里的依据(回溯线 2)——不挂就不完整
    confidence: Literal["high", "medium", "low"]  # 置信度,三档

# ② 阶段四:评审用"扇出"机制并行派 N 个打分员,各管一维
def critic_fan_out(report, plan, tool_results):
    # N 个打分员一次性并行发出去(不是一个个排队),延迟 ≈ 单个最慢的,不是 N 个相加
    # 下面是 v0.5 五维基线;现网已扩到 8 维(+输入上下文恰当性/估值一致性/辩证平衡)
    scorers = ["事实准确性", "计划覆盖度", "洞察深度", "结构", "简洁度"]
    scores = parallel_dispatch(scorers, report=report, plan=plan, tool_results=tool_results)
    return aggregate(scores)              # 归并:总分 = 各维均值

# ③ 两个直冲"有据可查"的打分员,各自对照不同的"真相源"
def 事实准确性打分(report, tool_results):
    # 对照 = 阶段一取到的那池子原始数据。报告里的数字跟它对不上 → 扣分
    return llm_score(report, 参照=tool_results,
                     标准="所有数据点准确给 10;严重失实给 0")

def 计划覆盖度打分(report, plan):
    # 对照 = 计划里的子任务清单。漏掉某个原计划要点 → 扣分
    return llm_score(report, 参照=plan.subtasks,
                     标准="所有子任务都覆盖给 10;完全偏题给 0")

推演:一篇典型研报,整条链路的调用结构是:计划 1 次、深读 1 次、合成 1 次,加上评审 N 维并行 N 次(下面这些量级是按 v0.5 五维基线 N=5 估的,现网 N=8,调用数和延迟相应上升)。因为评审这 N 次是并行扇出的,它的延迟约等于其中最慢那一个(量级估计约 1.5 秒),而不是 N 次相加;整条链路串行+并行下来,延迟中位数约 7.5 到 9 秒,完成事件 95 分位不超过 12 秒,单篇成本约 0.008 到 0.012 元。产出的报告正文约 1500 到 3000 字,通常带 2 到 4 个图占位。假设撰写器某处把营收数字写飘了,事实准确性打分员一对照那池子原始财务数据就会给低分,低于阈值(7.0)直接触发撰写器带着评审意见重写一次——编造的数字在这一关就被拦下,而不是流到用户面前。

⚖️ 决策对比

维度我们的选择(多阶段带引用 + 评审扇出)替代方案(一次性生成 / 单个大提示词一把吐)

公允裁决:一次性生成真的更省——省 token、省延迟、实现也最简单,对"随便写写、不要求严谨"的轻量场景,它完全够用,多阶段那套反而是过度工程。我们仍然选多阶段,核心就一条:金融研报的红线是数字不能编,而一次性生成在结构上根本没有办法兜住这条红线——它没有可校验的中间产物,"别编造"只能靠提示词喊话,喊话拦不住一个语感很好的模型顺嘴造数。多阶段的代价(小十次调用、7 到 9 秒)买到的是:每个结论都能反查到原始数据,事实准确性打分员拿成稿去对照那池子真实取数,编造在出门前就被截住。另外补一个内部子权衡,免得显得我们无脑堆结构:拓扑上我们并没有把 5 个智能体全做成子图(那才是过度设计——4 个简单智能体硬塞子图毫无收益),只有评审这一个因为要扇出多个并行打分员才用了子图,其余 4 个就是扁平节点;扇出机制也是构造时注入打分员而非搞一个全局注册表(全局可变状态容易污染测试)。该克制的地方克制,该上结构的地方(防编造这一关)才上。

🖼️ 图解

📌 总结

  • 防编造是结构问题不是提示词问题:把深度研究拆成计划→取数→深读→合成→评审五阶段,每步留下可校验的结构化中间产物,而不是一团糊在一起的文本。
  • 第一道结构性约束在深读:每条分析洞察的数据结构强制带 supporting_data(指回原始数据)+ subtask_id(关联回计划)+ 置信度——分析必须有据,是 schema 兜底不是口号。
  • 合成时图用自定义协议 chart:// 占位,跟用户消息里可能存在的真图片 http(s):// 区分,前端再渲染。
  • 核心防御在评审:第一次真启用"子智能体扇出",并行派多个打分员(v0.5 基线 5 维、现网已扩到 8 维);事实准确性对照原始取数、覆盖度对照子任务清单,这两条对照线就是"有据可查"的内置审稿人;事实分低于阈值触发重写。
  • 这个产品内审稿人(逐篇把关)跟离线评估的裁判(批量算指标)是两套不同职责,可共用评分标准模板,别混(离线评估见本类第 4 题)。

一句话速记:把研究拆成五阶段、让每条洞察用 schema 硬挂回原始数据、再用并行评审拿成稿去对照真实取数和计划——编造在出门前就被那个内置审稿人拦下,代价是小十次调用、7 到 9 秒。

Q4

研究产物的质量怎么评估?(把尽调报告评估那套用到研究体裁上)

★★★★☆
离线评估指标化回测防数据泄露消融实验

🎯 考察点分析

这道题问的是:当系统产出一篇带数据、带引用的长研究报告时,你怎么判断它"好不好"?面试官想看的不是你会不会请人读一遍打个印象分,而是你能不能把"好不好"拆成可复现、可比较、可消融的若干个具体信号,并且承认每个信号的边界。这背后是一个工程师对"评估也是要建系统的"这件事有没有体感。

  • 追问:报告里一句"营收 150 亿元",你怎么程序化地判它对不对?引用了某段资料,你怎么知道那段资料真的支持这句话、不是模型瞎编的来源?
  • 追问:评估要"假装回到某个截止日"只喂模型那天之前的信息,可一旦模型偷看到未来,整个回测就作废。这个数据泄露的坑从哪几处冒出来?你怎么堵?
  • 追问:就算每个指标都算出来了,你怎么知道是"检索"贡献的分,还是"多智能体"贡献的分?(消融的动机)
  • 追问:这套离线指标,和产品里每篇报告都跑一遍的在线评审,是同一套东西吗?(边界,见本类第 3 题)

📚 原理讲解

先说结论:我们没有发明一套全新的研究评估,而是把尽调报告质量评估那一整套基础设施直接迁过来用——因为"长报告 + 带引用 + 带数字"这个形状,尽调报告和深度研究报告是一模一样的。评估不是"看一眼",而是 4 个相互独立的指标模块,每个都是一个真实的纯函数文件,合起来给报告打一张多维度的分。提一句:本来还有第五把"预测回测"的尺子,但它随去推荐决策(本类第 1 题)一并下线了——正因为只有它需要"未来真实股价"来打分、会把整个回测污染成数据泄露,删掉推荐时顺手把它也撤了,如今现网只剩 4 把。

三段式分层:把"评一篇报告"拆成抽取 / 摘要 / 推理三层

一篇研究报告里有三种本质不同的内容,各自要用不同手段验:

  • 抽取层(它有没有照搬错事实):引用对不对(指标一,M1)、数字对不对(指标二,M2)。这层尽量程序化——能用代码和库里的真值对的,绝不交给大模型拍脑袋。
  • 摘要层(它有没有把要点配齐):风险点和对应的缓解措施有没有成对出现(指标三,M3)。这层结构性强但语义判断绕不开,用一个小模型当裁判。
  • 推理层(它整体写得好不好):报告的综合质量,让多个大模型各自投票打分再取众数(指标五,M5,共识)。这一层最主观,所以才上大模型裁判。(原本这层还有一把"预测回测"的尺子,要拿截止日之后的真实股价反过来验报告的看多/看空方向——但它随去推荐决策一并下线了,见本段开头。)

这个分层的好处是:越靠抽取层越客观、越便宜、越该用代码;越靠推理层越主观,才上大模型裁判。不会因为"反正都是大模型评"就把"营收数字对不对"这种本该查表的事情也丢给模型。

指标一(引用)真实在做什么:它验的是"不编造来源"

这是最能体现"不是看一眼"的一个。它遍历报告的 6 个 section,对每条引用(一个 chunk_id),真的拿这个 id 回知识库里把那段原文捞出来(kb_lookup)。捞不到——说明模型编了个不存在的来源——记一次 lookup_failures;捞到了,再用一个小模型裁判判断:这段原文到底支不支持报告里那句话(supports)。最后:

  • 精确率 = 被裁判确认"确实支持"的引用数 / 总引用数(模型引的料,有几成是真站得住的)。
  • 引用覆盖率 = 有非空引用的 section 数 / 应有的 section 总数(有几成 section 是有据可查、不是空口说白话的)。
  • 两者取 F1 作为这个指标的最终值——既要引得准,也要引得全,缺一个都拉低。

这一步直接对应了"有据可查、不编造来源"那道防线(见本类第 3 题);第 3 题讲的是产品里怎么合成带引用的报告,这里讲的是离线怎么验那些引用真不真。

评估基础设施:把生产流水线整个当被测对象(全链路黑盒回测)

核心范式是把整条生产流水线当被测黑盒——回测器不去 mock 生产里的某个函数,而是把整条真实的研究流水线当一个黑盒喂进去:回测器负责装配数据适配器和评估用的大模型,流水线接什么就跑什么。生产和评估走的是同一家大模型供应商(阿里百炼 DashScope,比如 deepseek-v4-flash 这类),评估时用一个换装器(LLMSwapper)在同一供应商内部切换打分用的具体模型——这一步不是随便换,而是为了配合下面这个工程坎里的防泄露需要。

评估的第一道工程坎:防数据泄露

回测的逻辑是"假装回到某个截止日,只让流水线看到那天之前的信息,评估它在当时那个信息面下能产出多好的报告"。但如果链路里任何一环偷看到了截止日之后的事实,这个"回到过去"的前提就破了,整个回测就作废。泄露有两个来源:

  • 数据层泄露:tushare 适配器做双层截止日防御——既在请求里注入截止日参数,又对收到的每一行按公告日二次过滤,两道都筛掉截止日之后的行。一个三层扫描器(LeakDetector)再兜底:扫 tushare 行的公告日、扫知识库 chunk 的发布日、扫拼好的 prompt 文本里出现的日期,任何一处出现晚于截止日的就报泄露。
  • 模型自带的泄露:大模型的训练知识截止日本身就是泄露源——评估用的 DashScope 模型(deepseek-v4-flash 截止日 2026-04,qwen 系列也都 ≥2024),你要回测 2024–2025 那些时点,它脑子里可能早就"知道"后来发生了什么。理想方案是换一个训练截止日足够老的模型来评,但这家供应商可用的模型截止日全都 ≥2024——"换老截止日模型防泄露"在当前供应商下其实做不到。所以这里是知情地接受残留泄露:回测主线(2024–2025 时点)承认模型自带知识可能偷看到未来这一缺陷,只有把截止日设到所有模型训练截止之后(2026-04-30)的那条 sanity 副线,才能跑出真正无泄露的回测。这是受供应商约束的取舍,不是已落地的干净防线。
控制变量消融 V0–V3:回答"到底是哪个组件在贡献分"

光有总分还不够,你得知道钱花在哪个组件上值不值。做法是用工厂模式,在生产研究智能体零改动的前提下,装配出四个变体跑同一批 case:V0 是完整流水线、V1 去掉检索(换空知识库适配器)、V2 去掉多智能体(换单体流水线)、V3 去掉评审。同一个 case 跑四遍写四行回测记录,横着一比就知道:去掉检索掉了多少分、去掉评审掉了多少分——哪个组件最值钱一目了然。

💻 示例讲解

下面用教学伪代码走一遍"引用指标(M1)"的真实逻辑——它最能说明"评估是查证,不是看一眼":

# 指标一:验报告"不编造来源" —— 真去库里捞原文 + 小模型判是否支持
def compute_citation_metric(report, kb_lookup, judge):
    total_cited = 0          # 总引用条数
    supported = 0            # 被裁判确认"确实支持"的条数
    sections_with_evidence = 0
    REQUIRED_SECTIONS = 6    # 应有的 section 总数(固定分母,消融才有意义)

    for section in report.sections:          # 遍历 6 个 section
        evidence = section.evidence or []    # 这个 section 引的 chunk_id 列表
        claim = section.narrative            # 这个 section 的论断(整段当一个 claim)
        if evidence:
            sections_with_evidence += 1

        for chunk_id in evidence:
            total_cited += 1
            chunk = kb_lookup(chunk_id)      # 关键:拿 id 真去库里捞原文
            if chunk is None:
                continue                     # 捞不到 = 编造的来源,不计入"支持"
            # 小模型裁判:这段原文到底支不支持这句论断?
            if judge.supports(claim, chunk["text"]):
                supported += 1

    # 精确率:引的料里有几成真站得住
    precision = supported / total_cited if total_cited else 1.0
    # 覆盖率:几成 section 是有据可查的(分母用"应有"而非"现有")
    coverage  = sections_with_evidence / REQUIRED_SECTIONS
    # 取 F1:既要引得准,也要引得全
    return f1(precision, coverage)

推演:假设报告 6 个 section 里 5 个有引用(覆盖率 = 5/6 ≈ 0.83);一共引了 10 条料,其中 1 条 chunk_id 在库里根本捞不到(编造来源)、还有 1 条捞到了但裁判判"原文不支持这句话",剩下 8 条确认支持,那么精确率 = 8/10 = 0.80。F1 = 2 × 0.80 × 0.83 / (0.80 + 0.83) ≈ 0.81。注意那条捞不到的来源,既拉低了精确率(分母 +1、分子不变),又暴露在 lookup_failures 计数里——这正是"看一眼"永远抓不住的东西:人读报告时,根本没法核对每个 chunk_id 是否真存在于库里。数字指标(M2)同理,把报告里"营收 150 亿"和 tushare 真值比,差距在 ±1% 容差内算对。

🖼️ 图解

📌 总结

  • 评估不是"看一眼",是 4 个独立指标模块:按抽取(引用 M1 / 数字 M2)、摘要(风险配对 M3)、推理(多模型共识 M5)三段分层,越客观的层越用代码、越主观的层才上模型。原有的"预测回测 M4"随去推荐决策一并下线(它是唯一需要未来真股价、会引发数据泄露的尺子,见本类第 1 题)。
  • 引用指标的精髓是真去库里捞原文:每个 chunk_id 都 kb_lookup 核对,捞不到=编造来源,捞到再让小模型判是否支持,最后取精确率与覆盖率的 F1——这是人工读报告永远做不到的逐条查证。
  • 评估基建是回测,范式是 把整条生产流水线当被测黑盒(Pipeline-as-SUT),生产代码零改动,只在外面装数据适配器和换装器。
  • 防数据泄露是第一道工程坎:数据层靠双层截止日过滤 + 三层扫描兜底,这部分堵死了;但模型自带知识这道——因评估和生产同走 DashScope、它可用模型截止日全 ≥2024——堵不住,回测主线(2024–2025 时点)知情接受残留泄露,只有 cut_off=2026-04-30 的 sanity 副线才真正无泄露。
  • V0–V3 控制变量消融把"总分好"细化成"哪个组件值这份成本":同 case 多跑、列对列比,检索/多智能体/评审各自的贡献一目了然。这套离线指标和产品里每篇报告都跑的在线评审是刻意分开的两套体系(见本类第 3 题)。

一句话速记:把"好不好"拆成可查证的 4 个指标,用回测当被测黑盒、数据层双层过滤+三层扫描防偷看未来(模型自带知识这道因供应商截止日全 ≥2024 只能主线知情接受、sanity 副线才干净)、用消融看清每个组件值不值——印象分给不了这些答案。
