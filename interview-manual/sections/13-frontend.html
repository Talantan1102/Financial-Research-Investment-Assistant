Q1

🎯 考察点分析

这道题表面问"前端怎么搭",真正想看的是你能不能把一个会话型 AI 产品的前端讲清楚:产品形态(为什么是对话框而不是表单)、状态怎么分仓(哪些状态放哪、为什么)、流式数据怎么从后端一路喂到屏幕上。面试官想确认你不是只会拼组件,而是理解"流式 + 多会话 + 断线重连"这些 AI 应用前端特有的工程难点。

  • 追问:为什么把"正在流式播放的那条会话状态"单独放一个仓,而不是塞进会话列表里?塞进去会出什么乱子?
  • 追问:网络断了一下,后端还在出字,前端怎么接着读、不重复也不丢?为什么不是重新发一遍提问?
  • 追问:用户在 A 会话流式播放时点开了 B 会话,你怎么保证 A 的流不会把字写到 B 的窗口里?
  • 追问:表单式 UI 参数明确、好做校验,你为什么放弃这个好处选了更难搭的对话流?

📚 原理讲解

整个前端按"先搭骨架、再填血肉"分两层落地。第一层是基础设施层:应用外壳(顶部栏 + 左侧 240px 会话侧栏 + 中间对话区)、对话页路由、几个独立的状态仓、一个流式数据 hook。第二层是内容渲染层:对话区内部的 7 个子组件(消息列表、文本气泡、工具调用卡片、研报卡片、流式指示器、输入区、费用计)。之所以拆两层,是个很实在的工程原因——一个大计划会让起草环节卡住,把每一步的输出体量缩小,反而推得动。

状态怎么分仓:每个关注点一个 proxy

状态管理用的是 valtio。它的心智模型很轻:用 proxy() 包一个普通的可变 JS 对象,谁想改状态就直接给对象的字段赋值(state.x = 1),组件侧用 useSnapshot 订阅,只有真正读到的字段变了才会重渲染。不需要写 action type、不需要 reducer 样板。每个关注点开一个仓:当前会话(流式状态)、会话列表、深度研究确认包、登录态、研报、知识库……一仓一个 proxy(),互不耦合。

这里有个关键设计决策:每条会话"正在流式播放"的状态(草稿文本、流式阶段、已收到的最大事件序号、费用)只放在当前会话单例仓里,会话列表仓只存"有哪些会话、各自标题/预览/时间",不碰流式。切会话就是把单例仓整个重置一遍。为什么非得这样?因为流式是一条有生命周期的连接(开始→出字→结束/出错),如果把它挂到会话列表的每个条目上,多会话切换时你得同时管 N 条流的开关,SSE 生命周期会乱成一团;收敛到单例仓后,"同一时刻只有一条活跃流"成了天然不变量。

流式怎么走:一个自研 hook + 标签联合事件

服务端用 SSE(服务器推送事件)逐 token 往下吐,前端用一个自研 hook 消费这条流。后端推的不只是文字 token,还有"开始第几步""调了哪个工具""费用更新""要不要升级成深度研究""结束了"这类控制事件——联合类型里一共锁定了 26 种事件(以 SSEEvent 联合的实际成员计,echarts/plotly 是 chart 事件的子形态不单独计),每种有固定字段(schema)。前端把它们建模成一个标签联合类型(discriminated union):每个事件带一个 type 标签,联合里每一支对应一种事件。hook 拿到一帧就解析,是 token 就喂给打字机往草稿上拼字;是其它事件就调 dispatchEvent(ev),里面按 type 分发到对应的状态改动,没显式处理的落默认分支。加新事件类型 = 联合里加一支 + switch 加一个 case,编译器会逼你把每支都处理掉,漏了会报错。

控制事件靠一个单调递增的序号 seq 守护:带了 seq 的事件,只有比"已见过的最大序号"大才生效,否则当重复跳过。要注意一个真实坑——逐 token 的流式 payload 不带 seq,所以这层去重对 token 不生效,token 的不重复另靠后端按起点回放和前端整段重连来保证(见下文)。

两个工业难点

第一是断线重连续读。提问走的是 POST,但流是一个独立的 GET 流地址。断线后不重发 POST(否则又跑一遍模型、又花一遍钱),而是直接 GET 这条流并带上 last_event_id 参数。后端从 Redis Streams 里按这个起点回放剩下的事件——传不同起点就能从那之后续读,这个偏移续读的机制后端是真支持的。但当前前端的取舍是简单优先:所有重连入口一律把 last_event_id 固定传 '0',也就是整段从头重放,反正 token payload 不带 seq、本就不依赖前端去重,整段重放最稳。"按记住的偏移精确续读"这条更省流量的路,后端口子留着、前端暂未走。第二是多会话切换:切到新会话前,先把旧会话的流(底层是一个 AbortController)abort 掉,再起新连接,保证不会有两条流同时往状态里写、把别的会话的字写串。

💻 示例讲解

下面这段教学伪代码把三件事串起来:状态仓怎么分、事件怎么 dispatch、断线怎么续读。重点看逻辑怎么走,不是源码细节。

# ① 状态分仓:当前会话(单例,含流式状态)与 会话列表(只存元信息)分开
current_chat = proxy({
    "session_id": None,
    "messages": [],            # 已落定的历史消息
    "streamingDraft": "",      # 正在逐字拼的助手回复草稿
    "streamingStatus": "idle", # idle / streaming / reconnecting / error
    "last_seq": 0,             # 已见过的最大事件序号,用于去重续读
})
chat_sessions = proxy({"sessions": []})   # 只存 标题/预览/时间,不碰流式

# ② 一个 dispatch 函数:按事件标签(type)分发到状态改动
def dispatch_event(ev):
    if ev["seq"] <= current_chat["last_seq"]:
        return                              # 旧事件(重连重放到的)直接跳过,保证不重复
    current_chat["last_seq"] = ev["seq"]
    if ev["type"] == "token":
        current_chat["streamingDraft"] += ev["content"]   # 逐字拼到草稿
    elif ev["type"] == "tool_call":
        current_chat["streaming_phase"] = "tool"          # 切到"正在用工具"指示
    elif ev["type"] == "done":
        flush_draft_as_message()                          # 草稿定稿成一条历史消息
        current_chat["streamingStatus"] = "idle"
    # …其余事件(联合共 26 种)各一个分支,没显式处理的落默认分支

# ③ 断线重连:不重发提问,直接 GET 同一条流
#    后端支持按 last_event_id 偏移续读;当前前端一律传 '0' = 整段从头重放
async def subscribe_to_task(task_id, last_event_id="0"):
    abort_old_stream()                      # 切会话/重连前先掐掉旧连接,避免双流写串
    res = await GET(f"/chat/stream/{task_id}?last_event_id={last_event_id}")
    async for frame in res:                 # 后端从该起点之后回放事件(传 '0' = 全部)
        ev = parse(frame)
        if ev["type"] == "token":
            typewriter.enqueue(ev["content"])  # token 走打字机,视觉等同逐字流
        else:
            dispatch_event(ev)              # 控制事件进 dispatch

推演:假设一条回答要吐 200 个 token,用户在第 120 个时网断了 2 秒。重连走的不是重发提问,而是直接 GET 同一条流——省下"再跑一遍模型、再花一遍钱"这笔大头(这才是断线续读的真正价值)。关键点要讲准:当前前端 last_event_id 固定传 '0',后端就把这条流从头整段重放一遍,前端拿到完整草稿覆盖式重建、再继续往后拼,用户只感觉"卡了一下又接上了"。有人会以为前端记着 last_seq=120、让后端只补 121~200,但 token payload 压根不带 seq,这条精确续读路前端并没走;后端虽支持按偏移续读,前端选了"整段重放最省心"。这套行为有 4 个守护测试盯着:正常消费、abort、断线重连+退避、会话切换 swap,改 hook 时任何一个挂了就说明回退了。整套前端测试约 143 个 / 39 个文件。

⚖️ 决策对比

维度我们的选择(chat-first 单一对话框)替代方案(表单式 UI:填股票代码/日期/分析类型再提交)
需求形态开放式:用户事先不知道要问什么,问题会一路追加确定式:适合参数已知的固定查询
多轮澄清对话天然承载追问、补充、改主意表单是一次性提交,装不下来回澄清
升级深研对话里点 ⚡ 触发,弹出确认包让用户改字段,确认后看研报渲染,全在一个流里得另开一套表单和页面,流程割裂
输入能力一个输入区 4 通道:普通消息 / 斜杠命令 / 上传 / 深度研究一堆固定字段,加能力就加字段,越堆越笨重
参数校验弱项:参数藏在自然语言里,得靠模型/确认环节兜强项:字段明确,前端直接做校验和必填
实现成本高:得自己搭 SSE 流式、状态机、断线续传这些基础设施低:标准表单 + 一次请求一次响应即可

公允裁决:表单式不是稻草人,它在"参数明确、易校验、实现简单"这三点上是真优势,做确定性查询(比如"查某只股票某天收盘价")它又快又稳,我们也确实为此付出了自建流式基础设施的代价。但金融研究的需求本质是开放、多轮、会临时升级深研的,表单把人框死在固定字段里,既接不住"我再问一个""换个角度看看",也塞不下深度研究的确认环节。chat-first 用一条对话流把 提问→澄清→升级深研→看研报 全部统一了。说到底是产品形态决定的:这东西本身就是个会话型助手,表单只能服务确定性查询,而不是这个产品的主线。

📌 总结

  • 前端分两层落:基础设施层(外壳 + 240px 侧栏 + 对话路由 + 多个 valtio 仓 + 流式 hook)先搭骨架,内容渲染层(ChatPane 内 7 个组件)再填血肉——拆开是为了让每一步输出体量可控。
  • valtio 一仓一关注点:proxy() 建可变对象、useSnapshot 订阅,没有 action/reducer 样板。当前会话、会话列表、深研确认包、登录、研报、知识库各一仓。
  • 关键不变量:流式状态只放当前会话单例仓,切会话整仓重置;不提到会话列表仓,否则多会话切换时多条 SSE 生命周期会乱。
  • 流式靠自研 hook:SSE 逐 token 推,26 种事件建模成标签联合,token 走打字机、控制事件走 dispatchEvent 按 type 分发;加事件类型就加一支 + 一个分支。
  • 两个工业难点有 4 个测试守护:断线后不重发 POST(省一次推理)、直接 GET 同一条流——后端支持按 last_event_id 偏移续读,当前前端固定传 '0' 整段重放(token 无 seq、不靠前端去重);切会话 abort 旧流再起新流。
  • 选 chat-first 不选表单,是因为金融研究需求开放、多轮、会临时升级深研,产品本质是会话型助手;代价是自建流式基础设施。

一句话速记:一条对话流统一"提问→澄清→升级深研→看研报",流式状态收敛到单例仓 + 自研 SSE hook 用标签联合事件驱动,断线不重发 POST、直接 GET 同一条流整段重放(后端可偏移续读),切会话靠 abort 防写串。

Q2

记忆页面的图可视化:用图引擎画关系图 + 时间线 + 审计,怎么把一个记忆系统可视化给用户看?

★★★☆☆
记忆可视化Cytoscape 力导向图双时态线型编码时间线自绘审计与一键否决

🎯 考察点分析

这道题表面是"前端怎么画图",其实是在探一件更深的事:你的后台是一个会自己往里写东西的记忆系统——它把用户在聊天里透露的持仓、偏好、观点抽成"实体之间的关系",而且每条关系还有"什么时候开始生效、什么时候失效"的时间属性。面试官想看你能不能把这么一坨抽象的、用户根本看不见的内部状态,翻译成用户一眼能懂、还能动手管的界面。这考的是产品同理心 + 数据可视化选型 + 对"双时态"这个数据结构的理解,三样一起上。

  • 追问:记忆数据本质是图(谁和谁有关系),你为什么不用最省事的表格,非要上力导向图?表格做不到的到底是哪一点?
  • 追问:"双时态"是什么意思?一条记忆"当前有效 / 已经结束 / 被推翻"这三种状态,你在图上怎么让用户不点开就分辨出来?
  • 追问:时间线那块为什么不直接装个现成的时间线库,要自己用 SVG 画一百多行?省下来的是什么、代价是什么?
  • 追问:用户怎么知道"系统在记我"?光做个页面没人去看也白搭,你怎么把这个页面跟聊天主流程缝起来?

📚 原理讲解

先说清楚要可视化的东西长什么样。记忆系统里存的不是一句句话,而是一张图:节点是实体(你这个用户、某只股票、某个行业、某个指标……),边是关系(持仓、关注、偏好、回避、表态、卖出……)。一条边还带着两个时间维度——"这条关系从哪天开始有效、到哪天失效",这就是双时态(bi-temporal):同一个事实在不同时间点可能有不同的真假。比如"持仓茅台"这条边,三月买入时生效,五月卖出后就该标成"已结束",而不是直接删掉——因为五月之前它确实成立,删了就丢了历史。

为什么是三个视图,而不是一个

同一份记忆数据,用户有三种完全不同的看法需求,硬塞进一个视图反而都看不好,所以拆成三个 tab:

关系图(MemoryGraph)回答"谁和谁有关系"——这是图结构最本质的问题,只有摊成节点连线才看得出来。时间线(MemoryTimeline)回答"这些关系在时间上怎么排"——哪条先发生、哪条还在持续、哪条已经结束,横轴一拉就清楚。审计(MemoryAuditLog)回答"系统记错了我能不能纠"——它是用户的控制权入口,把被推翻的历史按时间倒序摆出来,并提供一键否决。

关系图:颜色编实体、线型编时态

关系图用 Cytoscape.js(一个专门画图结构的引擎)画力导向图。它有两套视觉编码:7 种实体类型用 7 种颜色区分(用户=蓝、股票=绿、行业=橙、指标=紫……),11 种关系类型用中文标签标在边上(持仓、关注、表态……)。最巧的是双时态用线型编码:当前有效=实线、已结束=虚线、被推翻=点线。这样用户不用点开任何东西,扫一眼就知道哪条关系还活着、哪条作废了。点开一条边会从右侧滑出一个抽屉,显示这条关系的生效起止时间、重要度和系统当初为什么这么记。

布局选的是力导向(代码里写 cose)——它把节点当成互相排斥的小球、把边当成弹簧,自己弹到一个舒展的平衡态。为什么不选分层(dagre)或广度优先(breadthfirst)那种规规矩矩的树形?因为单用户的记忆量级大约就是 50-200 条边,这个规模下力导向最直观、最像"一团关系网";真要上到一千多条边,力导向会乱成毛线团,那时才需要换成增量渲染的布局(cola),这个口子留着但还没到。这是个典型的"按当前数据量级选最合适的,而不是一上来就上最重的"决策。

时间线:刻意不引第三方库

时间线那块做了个反直觉的决定:不用任何现成时间线库。市面上的 vis-timeline、react-calendar-timeline 都是 200KB 以上的大块头,而我只需要"横轴是时间、每条关系画一根按类型分色的条、悬浮显详情"这点功能。为这点功能背 200KB,在单个视图上不划算。所以用纯 SVG/CSS 加 dayjs(一个轻量日期库)自己画了约 150 行:把每条边的起止日期换算成横轴上的百分比位置和宽度,被推翻的条降低透明度,鼠标悬浮弹 tooltip。功能够用,体积几乎为零。

审计:用户的控制权落地

审计视图用一张表格,默认按"被推翻时间"倒序列出系统纠正过的历史;一个开关可以切到"当前有效"列表,每行配一个二次确认的一键否决按钮——用户觉得系统记错了,点一下,这条关系立刻失效、不再参与后续检索。注意这里只做单条否决,"否决一条会不会牵连相关的其它条"(级联否决)留到后面。这一块的意义不在功能多,而在它把"这是你的记忆,你说了算"这句话变成了能点的按钮。

让用户知道"系统在记我"

光有页面不够,得有人去看。两手:一是首次登录后在应用骨架顶层一次性弹一个引导弹窗,讲清"我会自动记 4 类信息、你有 3 项控制权",用 localStorage 打标记保证不重弹,还故意延迟 800 毫秒避免跟登录框撞一起;二是把记忆页和聊天主流程缝起来——当 agent 在回答里引用了某条记忆,它会带一个 [查看] 锚点,点了直接跳到关系图并把那条边高亮出来。这样"系统在记我"不是一句空话,而是随时能点开查证的。

💻 示例讲解

核心逻辑就两段:一是把一条记忆边"分类"成三种时态状态,二是把状态翻译成线型。这两步决定了用户看到的实线/虚线/点线。下面是教学版的精简写法。

# ① 把一条边分类成三种时态状态(纯函数,不碰渲染)
def classify_edge_status(edge):
    # 被人工/系统推翻过 —— 最优先,说明这条记错了
    if edge.invalidated_at:
        return "invalidated"   # 被推翻
    # 有失效时间 —— 曾经成立,现在结束了(如卖出后的"持仓")
    if edge.valid_to:
        return "ended"         # 已结束
    # 没失效时间也没被推翻 —— 当下仍然成立
    return "current"           # 当前有效

# ② 状态 → 视觉编码:线型 + 颜色 + 粗细
#    用户不点开就靠"线长什么样"分辨一条记忆还活不活
EDGE_STYLE = {
    "current":     {"line": "solid",  "color": "#262626", "width": 2},   # 实线 黑
    "ended":       {"line": "dashed", "color": "#8c8c8c", "width": 1.5}, # 虚线 灰
    "invalidated": {"line": "dotted", "color": "#bfbfbf", "width": 1},   # 点线 浅
}

# ③ 把后端给的边,组装成图引擎能吃的元素
def to_graph_edge(edge):
    status = classify_edge_status(edge)
    style  = EDGE_STYLE[status]
    return {
        "source": edge.source_node_id,
        "target": edge.target_node_id,
        "label":  REL_LABELS_ZH.get(edge.rel_type, edge.rel_type),  # 持仓/关注…
        "line_style": style["line"],   # 实线? 虚线? 点线?
        "color":      style["color"],
    }

# ④ 聊天里点 [查看] 锚点 → 跳到记忆页并高亮那条边
#    锚点格式: [查看](#mem-{edge_id})  →  /memory?highlight_edge={edge_id}
def on_chat_anchor_click(edge_id):
    navigate(f"/memory?highlight_edge={edge_id}")
    # 关系图读到这个参数,就把对应的边描成醒目色并居中

推演:假设用户三月说"买了茅台",系统记下一条 持仓→茅台 的边,valid_from=3月、valid_to=空、invalidated_at=空。这时 classify_edge_status 走到第三个分支返回 current,图上画成黑色实线。五月用户说"清了茅台",系统给这条边补上 valid_to=5月(而不是删除),再分类就返回 ended,同一条边变成灰色虚线——历史保住了,状态也对了。要是系统压根记错(用户根本没买),用户在审计页一键否决,补上 invalidated_at,边变成浅色点线且不再参与检索。三种线型,对应三种生命状态,全靠这一个纯函数判出来。

Q3

用户画像可编辑界面:双轨语义 + 原子操作,用户手动改画像怎么不和系统的自动学习打架?

★★★★☆
用户画像双轨语义原子操作人机不打架双层保护

🎯 考察点分析

这道题表面是个 UI 题——给用户开个口子改自己的画像。但面试官真正想看的是:当两个写入者(用户手动改、系统后台自动学)对同一份状态各写各的,你怎么设计数据模型和写入路径,让它们不互相覆盖。这是分布式状态里很经典的"并发修改 / 谁是权威"问题,只是搬到了"人 vs Agent"这个场景。能不能讲清楚冲突从哪来、在哪一层拦掉,直接区分出"会画 UI"和"会设计系统"两类候选人。

  • 追问:如果用户手动写的一条和系统学到的一条文字一模一样,系统下次改那条会不会误伤用户那条?你靠什么保证不会?
  • 追问:为什么不是简单地"用户改的优先级高"打个标记就行?为什么要在数据结构上做物理隔离?
  • 追问:用户编辑了一条系统学来的画像,这条之后归谁管?系统还会不会再去动它?
  • 追问:这份画像最终要喂给大模型当 prompt 的一部分。你改了底层存储形态(从一大段文本改成一行一条),怎么保证喂给模型的内容和缓存前缀不被破坏?

📚 原理讲解

先说清楚画像是什么:它是一小段描述"这个用户是谁"的文字——比如"风格偏稳健""重仓新能源""不碰 ST 股"。这段文字会被拼进每轮对话的系统提示里,让模型知道在跟谁说话。问题在于这段文字有两个来源:用户自己在界面上声明的,和系统在对话里默默观察沉淀出来的。两边都想写,就会打架。

打架的根源:一个 blob,分不清来源

最早这份画像是存成一大段 markdown 文本(一个 blob)。这就埋了雷:系统想更新画像时,只能在这段文本里做字符串替换("把这句换成那句")。它根本分不清要替换的那句是用户亲手写的、还是它自己上次写的。一旦替换命中了用户写的那句,用户的话就被系统悄悄改掉了——用户会觉得"我明明写了风格稳健,怎么自己变成激进了"。这种静默覆盖是体验灾难,而且事后无法追溯。

解法第一步:把 blob 拆成一行一条,每条盖个来源章

我们把存储形态从"一段大文本"改成一行一条(row-per-item):每条画像是数据库里独立的一行,有自己稳定的 UUID,而且关键是——每行带一个 source 字段,值要么是 user(用户声明的)要么是 agent(系统观察的)。这就是"双轨"的物理基础:数据层面上,两条轨道的每一条都自带身份证。前端据此把画像物理拆成两个区:上面"你声明的",下面"agent 观察到的",一眼就能看出哪些归自己、哪些是系统猜的。

解法第二步:服务层 + 提示词双层,让系统永远够不到用户区

光有标记还不够,得真正拦住。我们在两层都设防。服务层:系统要修改某条画像时,走 apply_agent_replace,它查询时硬性 filter_by(source='agent')——这条 SQL 过滤器从根上就把用户区那些行排除在查询结果之外。所以哪怕用户区有一条文字和系统要改的完全一致,系统也扫不到它、改不了它。这是物理隔离,不是靠优先级比大小。提示词层:我们还在给模型的指令里白纸黑字写明——"你声明的"区是用户的主权区,你的替换工具只能匹配"agent 观察到的"区,你要是觉得用户区某条过期了,去向用户提议,不许直接动手。两层一起兜底:就算模型哪天不听话想越界,服务层的 SQL 过滤也让它够不着。

不打架的方向:升级是单向的

那用户和系统就老死不相往来吗?不是。我们设计了一条单向通道:用户编辑了系统学来的某条,这条就自动"升级"成用户区的——在 update_item 里把它的 source 从 agent 改成 user,重排到用户区末尾,前端配一个 200 毫秒的高亮动画,告诉用户"这条现在归你掌管了,系统不会再动它"。注意方向只有 agent→user 一个方向,系统永远不会把用户区的东西降级回去。所以两条轨道在数据层互不可达,唯一的交互是用户主动把一条拽到自己这边,这就把"双向打架"变成了"单向认领",冲突从根上消失。

原子操作 + 不撒谎

每次写入都是一个原子操作:先把主写入落到数据库并提交,提交成功后再去同步那份给模型用的缓存(_sync_to_working_block,把所有行重新渲染回那段 markdown,保证喂给模型的注入路径和缓存前缀都不变)。这里有个细节很能体现工程素养:缓存同步失败只打一条 warning,绝不向调用方报错——因为主写入已经实打实落库了,跟用户说"失败了"是撒谎,缓存陈旧下一轮自然会被重渲染追平。另外系统的替换如果没匹配上(包括它想改的内容其实命中了用户区这种情况),不会静默丢掉,而是退化成新增一条(fallback append),保证写入不丢。

💻 示例讲解

下面用精简伪代码展示三条关键路径:系统替换怎么被 source 过滤器挡在用户区之外、未命中怎么退化新增、用户编辑怎么触发单向升级。重点看逻辑走向,不是源码复刻。

# 系统(agent)想改某条画像:只能在自己那条轨道里找
def apply_agent_replace(user_id, old_text, new_text):
    # 关键:filter_by(source='agent') 从查询就排除了用户区
    #       哪怕用户区有一条文字和 old_text 一模一样,这里也扫不到它
    candidates = query(PersonaItem) \
        .filter_by(user_id=user_id, source='agent') \
        .order_by(position).all()

    matched = [c for c in candidates if c.text.strip() == old_text.strip()]
    if matched:
        matched[0].text = new_text   # 命中:就地改 agent 区这一条
        commit()
        sync_to_cache(user_id)       # 主写已落库后,再同步给模型用的缓存
        return matched[0]

    # 没命中(含「其实命中的是用户区」这种情况)→ 不丢写,退化成新增一条
    log.warning("没在 agent 区匹配到,退化为新增")
    return apply_agent_append(user_id, new_text)


# 用户编辑某条:如果它原本是系统学来的,就把它「升级」归用户掌管
def update_item(user_id, item_id, new_text):
    item = query(PersonaItem).filter_by(item_id=item_id, user_id=user_id).first()
    item.text = new_text
    if item.source == 'agent':
        item.source = 'user'                      # 单向升级:agent → user
        item.position = next_position(user_id, 'user')  # 重排到用户区末尾
    commit()                                      # 这一步是原子的:一次提交落库
    sync_to_cache(user_id)                        # 前端再配 200ms 高亮动画提示
    return item

推演:假设用户区有一条"我偏稳健",系统这轮也想把它学来的"风格激进"改成"我偏稳健"。系统调 apply_agent_replace(old='风格激进', new='我偏稳健'):查询因 filter_by(source='agent') 只拿到 agent 区的行,用户那条"我偏稳健"压根不在候选里,所以用户的话毫发无损;系统这条在 agent 区被就地改成"我偏稳健"。再看升级:用户点开系统学来的"重仓新能源"改成"重仓光伏",update_item 发现这条 source 是 agent,于是把它 source 置为 user、position 重排到用户区末尾、一次提交落库,前端 200ms 高亮一闪——这条从此进了用户主权区,系统的 filter_by(source='agent') 再也扫不到它。整个过程零覆盖、零丢写。

⚖️ 决策对比

维度我们的选择(可编辑双轨)替代方案(只读画像)
用户能否纠错能:系统学错了用户可直接改,改完自动归用户掌管不能:只能看,系统学歪了也只能干瞪眼
覆盖冲突风险有风险,但靠 source 字段 + 服务层 SQL 过滤 + 提示词双层化解,两轨在数据层互不可达零风险:只有系统一个写入者,根本不存在打架
实现复杂度高:两套写入路径、升级重排逻辑、提示词双层约束、缓存同步都要维护低:一个 blob 只读展示即可,最省事
存储形态一行一条带 source 的稳定 UUID,可逐条溯源一大段文本足够,无需区分来源
对项目的价值给了一个亲手验证"系统自管理记忆写得准不准"的入口没有这个 dogfood 入口,只能盲信系统
用户体感"画像是我和系统共建的,我说了算""系统在背后给我贴标签,我管不着"

公允裁决:只读画像绝不是稻草人——它实现最省事、而且从根上消灭了覆盖冲突这个最棘手的问题,对一个不需要用户参与画像维护的产品,只读完全够用,还少维护一大堆代码。我们仍然选可编辑双轨,核心是两个判断:其一,系统自动学画像必然会学错(它在猜),没有纠错入口,错误会越积越多且无人能修;其二,这个项目本身要验证"自管理记忆"这套机制写得准不准,可编辑界面正好是那个亲手 dogfood 的入口。代价我们认:多维护两套写入路径和升级逻辑。但关键是——我们没有用"承担覆盖风险"换取可编辑,而是用 source 字段把冲突在数据层就消解掉了,所以可编辑的好处拿到了,只读那份"零冲突"的好处也基本保住了。被我们直接否掉的中间方案是"系统继续改同一段 blob、只在界面上标个颜色区分来源"——那样系统替换时根本无法在数据层区分来源,必然误伤,所以才下决心改成一行一条带 source。

🖼️ 图解

📌 总结

  • 冲突的根因是"一个 blob 分不清来源",解法第一步就是改成一行一条带 source 字段——双轨的物理基础在数据结构,不在 UI。
  • 不打架靠双层防护:服务层 filter_by(source='agent') 从 SQL 查询就排除用户区,加提示词里明令禁止越界,两层兜底。
  • 系统永远够不到用户区,哪怕文字一模一样——这是物理隔离,不是优先级比大小。
  • 人机交互被设计成单向升级(agent→user):用户一编辑就把那条认领过来,把"双向打架"降维成"单向认领",冲突从根上消失。
  • 原子写 + 不撒谎:主写落库后才同步缓存,同步失败只 warning;系统替换未命中则退化新增,绝不静默丢写。

一句话速记:给每条画像盖个"谁写的"的章,系统的手在数据层就被 source 过滤器挡在用户区之外,用户一编辑就把那条单向认领过来——于是人和系统永远不在同一条轨道上抢同一行。

★★★☆☆

🎯 考察点分析

这道题表面问"你为什么造个看板",其实面试官想确认三件事:一是你能不能跳出"功能堆叠"思维,把一个需求(我要记住自己项目的决策)抽象成一个统一的数据底座,再让多个界面共享它;二是你懂不懂"文档会过期"这个老问题的根因——叙事和代码各写各的,所以会漂移;三是你做工程取舍时,会不会为了花哨硬塞 LLM,还是清楚地把模型圈在边界、留好降级。

  • 追问:为什么不直接写个 README 或者几篇 markdown?多一个看板的成本花在哪、换回了什么?
  • 追问:5 个视图听起来很多,它们之间是各自维护数据还是共享?如果共享,改一处怎么让其它视图自动跟上?
  • 追问:视图之间点来点去的联动,是规则写死的还是模型推的?为什么这么选?
  • 追问:你在哪里用了大模型?如果本机没 API key 或者向量库挂了,看板还能不能演示?

📚 原理讲解

先说动机。这个项目是个长期独立作品,决策密度很高:每个模块为什么这么设计、当时还有哪些备选、最后取舍掉了什么、踩过什么坑。这些东西如果只散落在提交记录和脑子里,过两个月自己都讲不清,面试时更没法系统地讲。常规做法是写一篇"项目故事"的 markdown,但它有个致命问题:代码改了,文档不会自己改。叙事和代码是两份独立的真相,时间一长必然漂移,读者读到的是过期信息。

核心思路:一份卡片底座,多个视图都从它 render

看板(项目里叫"研发知识看板/Harness Board")的破题点是:不写离散的文档,而是把每条知识固化成一张结构化卡片,叫 DeepCard。一张卡片就是一个模块的完整决策档案,字段包括"它是什么(what)、为什么这么做(why)、有哪些备选(alternatives)、最终选了哪个(chosen_alternative)、取舍代价(tradeoff)、踩的坑(lessons_learned)、量化指标(metrics)、关键代码入口(code_anchors)、关联的决策/能力(linked_decisions / linked_capabilities)"等。

关键在于:所有视图都从这同一份卡片集合渲染,而不是各写各的页面。所以那篇"项目故事"不再是一份会过期的文档,它是从 DeepCard 集合实时 render 出来的。工作流变成:改代码 → 改对应卡片字段 → 故事、鸟瞰图、闪卡全部自动跟着更新。一份底座,同时服务四个场景——给自己 onboard、系统化梳理模块、面试讲项目、主动召回防遗忘。

5 个视图:同一份卡片的 5 种翻阅姿势

同一份卡片集合,按不同维度切出 5 个视图:① 网格(首页 /,所有卡片平铺,角标显示完成度);② 模块深读(/cap/{id},点开一张卡的双栏弹层,可以行内编辑,还有 AI 草拟按钮);③ 系统鸟瞰(/overview,用图引擎做力导向布局,节点按 7 个维度染色,节点大小 = 关键代码入口数 + 1,模块越重节点越大);④ 故事时间线(/story,按 git 提交时间排序,每张卡渲染成"问题 → 决策 → 结果"三段式,正好映射卡片的 why / tradeoff / lessons 三个字段);⑤ 闪卡(/flashcards/today,SM-2 间隔重复,对抗遗忘)。

联动:5 条全是确定性规则,不用模型

视图之间能互相跳转,这些联动全部是写死的确定性规则,一行 LLM 都不碰——因为"点这张卡看详情"这种导航不需要推理,用模型只会更慢更不可靠。5 条联动都收敛到"模块深读弹层"这个枢纽:网格的卡片点一下→深读弹层、鸟瞰图节点点一下→深读弹层、故事里的卡片点一下→深读弹层;而深读弹层里又能反向链回去——点关联决策→跳到决策锚点,点关联能力→跳到鸟瞰图并高亮居中那个节点。

LLM 只在边界用,而且可降级

大模型只出现在两个非主路径的地方:一次性批量预填卡片(用脚本跑,把现有文档草拟成结构化字段),以及深读弹层里的按需 AI 草拟按钮。两处都用受约束的 JSON 输出 + provenance(出处)模糊匹配校验:模型给的每条引述都要能在源文件里找到,找不到就直接 reject 那个字段,防止它编造。降级也想好了:本机没 key,就走手写的 seed 卡片路径,演示不受阻;向量库挂了,相关推荐退化成关键词匹配并挂 banner 提示;LLM 不可用,深读弹层就藏掉 AI 草拟按钮,退回纯手编。

💻 示例讲解

用伪代码说清两件事:第一,一份卡片底座怎么 render 出多个视图(故事不再过期的来源);第二,LLM 预填时 provenance 校验怎么挡住编造。

# 一、所有视图共享同一份卡片集合,render 时各取所需
cards = load_deep_cards()        # 唯一真相:全部 DeepCard

def render_story(cards):
    # 故事 = 按 git 提交时间排序后,把每张卡的三个字段映射成三段式
    # 注意:这里没有独立的 story.md,故事是 render 出来的 —— 所以永不过期
    for c in sort_by_commit_time(cards):
        yield {
            "problem":  c.why,              # 当时要解决什么
            "decision": c.tradeoff,         # 取舍了什么
            "outcome":  c.lessons_learned,  # 结果与教训
        }

def render_overview(cards):
    # 鸟瞰图 = 同一批卡片换个画法:节点大小随关键代码入口数,模块越重越大
    return [
        {"id": c.cap_id,
         "size": len(c.code_anchors) + 1,   # +1 保证空卡也能看见
         "color": dimension_color(c.dimension)}
        for c in cards
    ]

# 二、LLM 预填的字段必须过 provenance 校验,编造的直接丢弃
def accept_field(value, quote, source_files):
    # 模型每给一个字段,要附一条"我是从哪句话得出的"引述
    # 这句引述要能在源文件里模糊匹配到,否则判定为幻觉
    if fuzzy_find(quote, source_files):
        return value          # 有据 → 采纳
    return None               # 查无此句 → reject 该字段,绝不入库

推演:当前看板入库 64 张 DeepCard、覆盖全部 7 个维度,每张卡按 tradeoff / alternatives / lessons 派生 0-3 张闪卡。闪卡走 SM-2:每天新卡 5 张 + 到期 20 张,答完按 0-5 自评打分,记忆越牢的卡间隔越拉长。假设我今天改了某模块的取舍,只需在深读弹层里改那张卡的 tradeoff 字段——故事时间线对应那段的"决策"自动变了,这张卡派生的取舍类闪卡也跟着 regenerate(且保留原有的复习进度),鸟瞰图若代码入口数变了节点也会变大。一处改,全盘同步,这就是"故事不过期"的工程含义。

⚖️ 决策对比

维度我们的选择:交互式看板替代方案:README / markdown 文档
初始成本高:要搭卡片底座 + sqlite + 向量库 + 5 视图 + 联动 + 预填校验低:打开编辑器就能写,零依赖
会不会过期不会:叙事从卡片 render,改代码→改卡片→全视图自动同步会:代码和文档是两份真相,改一边另一边不动,必然漂移
翻阅方式多视角:按模块深读 / 按全局架构 / 按时间讲故事,同一份数据 4 种切法线性:从头读到尾,想换个角度看得自己脑补
对抗遗忘内置 SM-2 闪卡主动召回,到期自动推送复习无:读过就忘,靠自觉重读
面试可讲性故事时间线 = 现成的"讲项目"脚本,且和代码一致得临时翻文档拼,还可能讲到过期信息
维护心智统一字段模型,加模块=填一张卡;但要学会这套结构自由发挥,但越写越乱,长文档没人愿意维护

公允裁决:README 真的有它的好——写起来快、零依赖、谁都会用,对一个小项目或一次性说明,它就是最优解,硬上看板纯属过度工程。它的真正软肋只在"长期 + 高决策密度 + 要反复讲"这个组合下才暴露:文档会过期、是线性的、不抗遗忘。这个项目恰好三条都中,所以我愿意付那笔工程成本,把知识固化成结构化卡片,换来"叙事自动跟代码同步 + 多视角翻阅 + 可复习"。本质是一笔用工程成本买"知识不过期"的交易;如果项目小、不需要反复讲,我会毫不犹豫地只写 README。

📌 总结

  • 一份底座,多个视图:不写离散文档,把每条决策固化成结构化 DeepCard 卡片,5 个视图全从同一份卡片集合 render——这是"叙事不过期"的根本机制,改代码→改卡片→故事/鸟瞰/闪卡自动同步。
  • 5 视图 = 一份数据的 5 种翻阅姿势:网格鸟瞰按结构、故事按时间、深读按模块、闪卡按记忆,对应 onboard 自己 / 系统化梳理 / 面试讲项目 / 主动召回四个场景。
  • 联动全确定性:5 条跨视图跳转一行 LLM 都不用,因为导航不需要推理;网格/鸟瞰节点/故事卡片点击全收敛到深读弹层这个枢纽,弹层再反向链回鸟瞰高亮与决策锚。
  • LLM 圈在边界且可降级:只在一次性预填和按需草拟用模型,且用受约束 JSON + provenance 校验挡幻觉(引述查无此句即 reject);无 key 走手写种子、向量库挂退关键词、LLM 挂退纯手编,演示永不被阻塞。
  • 取舍清醒:看板不是默认更优,它只在"长期 + 高决策密度 + 要反复讲"时才值回工程成本;小项目我会老实写 README。

一句话速记:把项目知识固化成一份结构化卡片底座,5 个视图都从它 render 所以叙事自动跟代码同步,联动全用确定性规则、LLM 只在边界且可降级。
