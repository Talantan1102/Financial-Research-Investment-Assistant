02Chat Loop 引擎

这一类考察候选人对 AlphaScout 对话引擎的理解——它从一张 LangGraph supervisor 单程图,被重新设计成一个手写的 Python while 工具调用循环。8 道题按难度从易到难排:先从「对话式 AI 为什么要来回好几轮」这种零基础概念讲起,再走到为什么退役框架、四道终止闸、上下文窗口的 KV-cache 经济学、工具渐进披露、对话中途插话的原子性,最后落到不用框架直接对接原生 function calling 踩过的工程坑。重点不是「知道有这些机制」,而是能讲清每个决策的收益、代价和被否决的替代方案。

Q1

先打个基础:一个对话式 AI 助手回答用户问题,为什么常常需要"来回好几轮"(模型想一下 → 调个工具 → 看结果 → 再想)?为什么不能"问一次就答完"?

★★☆☆☆
对话 agent 循环动机 依赖型多跳 工具调用 基础概念

🎯 考察点分析

这是 Chat Loop 这一类的入门题,面试官不指望你背架构,而是想确认一件最基础的事:你是否真的理解"为什么 agent 要循环"这个出发点。很多候选人一上来就背"LangGraph、while 循环、状态机",但被追一句"那不循环行不行"就答不上来。一个想清楚了的人,会从一个具体的问题讲起——这个问题为什么"问一次答不完",从而自然推出"必须来回好几轮"。

  • 追问:你能不能举一个"问一次就答完"完全够用的例子?(探你是否知道循环不是处处都需要,简单问题一圈就停了)
  • 追问:那为什么有些问题就是一圈不够?到底卡在哪?(探你能否说出"下一步要做什么,取决于上一步查到了什么"——也就是依赖型多跳)
  • 追问:"来回好几轮"这个"轮",程序事先知道要转几圈吗?(探你是否理解圈数不是写死的,而是模型边看边定)
  • 追问:如果工具调用报错了,一问一答的做法会怎样?循环又有什么不一样?(探你是否看到循环顺带解决了"看着错误自己改"的问题)

📚 原理讲解

先把"对话 agent"这个词拆开。这里说的"助手",不是只会聊天的那种,而是能动手去查数据、能调用外部工具的助手——比如查一只股票现在多少钱、调出一份持仓清单、读一份财报。"工具"你就理解成"助手会用的一个个小程序",每个工具能干一件具体的事(查行情、查持仓、查财报……),模型自己不知道这些实时数据,得靠调工具去问。

先看一个一圈就够的简单问题

用户问:"茅台现在多少钱?" 助手心里想:这个我不知道,得查行情 → 调一次"查行情"工具 → 拿到 1680 元 → 直接告诉用户。一来一回,完事。这种问题确实"问一次就答完"——因为答案只依赖一次查询,助手一开始就知道要查什么。

再看一个一圈远远不够的问题

用户问:"我持仓里跌得最惨的那只,它最新财报怎么样?" 这句话里藏了一个先后依赖:

  1. 助手得先查到你的持仓清单,看清里面到底有哪几只股票、各自跌了多少;
  2. 看完才知道——哦,跌得最惨的是"宁德时代";
  3. 这时候才知道下一步要去查谁:查"宁德时代"的财报;
  4. 拿到财报数据,才能动笔回答。

关键就在第 3 步:"接下来要查谁",在第 1 步查出来之前,谁都不知道——程序不知道,模型也不知道,因为答案就藏在第 1 步的返回结果里。我们给它起个名字叫"依赖型多跳":查了 A 才知道要查 B。这种任务,你没法在一开始就把所有查询步骤一次写完,因为后面的步骤要看着前面的结果才能决定。

一个特别好用的日常类比:查资料写报告的人。你不会闭着眼睛一口气把报告写完。你是:先想"我要查什么" → 去图书馆借一本书(调一个工具) → 翻完发现还缺一个数据 → 根据刚翻到的内容再借一本 → 直到材料够了,才动笔写。"再借哪一本",取决于"上一本翻到了什么"。对话 agent 的循环,就是把这个"想 → 查 → 看 → 再想"的过程搬给了模型。
那"循环"到底是什么?

循环的本质,就是给模型装一个"想 → 做 → 看 → 再想"的反馈回路:

  • 想:模型说"我想调'查持仓'这个工具";
  • 做:程序真的去把这个工具调一遍;
  • 看:程序把工具返回的结果(持仓清单)喂回给模型;
  • 再想:模型看完结果,再决定——是收尾回答了,还是接着调下一个工具(查那只跌得最惨的财报)。

这一圈"调一次模型 → 执行工具",我们叫一个圈(iteration)。一个问题可能转一圈就停,也可能转好几圈,直到模型觉得"材料够了"才生成最终回答。

对比一下"问一次就答完"的老做法

本项目早期的旧架构,就是典型的"一问一答骨架":模型一次性出一份计划(要调哪几个工具)→ 程序把这些工具批量执行 → 另一个模型拿结果合成回答。听起来也有工具,但有个致命点:工具的结果根本不回到出计划那个模型手里。也就是说,模型是"蒙着眼睛把整盘棋一次下完"的,它够不着"看到结果再决定下一步"这种需要回看的任务。简单问题它能凑合,碰上依赖型多跳就抓瞎了。

(这一题只讲"为什么需要这个环"。环里面一圈的数据到底怎么流、"单 LLM 既决策又说话"是什么意思,见本类第 2 题;环怎么停下来、有哪几道终止条件,见本类第 4 题。)

💻 示例讲解

下面用最精简的伪代码,把"问一次就答完"和"循环"摆在一起,你一眼能看出区别在哪。

# ① 一问一答:一条直线,工具结果不回模型,够不着依赖型多跳
def answer_once(question):
    plan = model.make_plan(question)      # 模型蒙着眼一次性出全部计划
    results = run_all_tools(plan.tools)   # 工具批量执行
    return other_model.write(results)     # 另一个模型合成回答 —— 到此结束,没有"再看一眼"


# ② 循环:给模型装一个"想 → 做 → 看 → 再想"的反馈回路
def answer_with_loop(question):
    state = [question]                    # 对话上下文,会越攒越多
    while True:                           # 这个 while 就是"环"
        step = model.think(state)         # 想:模型看着目前所有信息,决定下一步
        if step.is_final_answer:          # 看够了 → 收尾,跳出环(简单问题这里一圈就停)
            return step.text
        # 否则模型要求调工具(比如先"查持仓")
        result = run_tool(step.tool_call) # 做:程序真去把工具调一遍
        state.append(result)              # 看:把结果喂回去,下一圈模型就能"看到"它
        # 回到 while 顶部 —— 再想:基于刚查到的持仓,决定接下来查谁的财报

推演:拿"我持仓里跌得最惨的那只财报怎么样"走一遍循环——
第 1 圈:模型想"先查持仓" → 调"查持仓"工具 → 拿到清单(发现宁德时代跌最惨) → 喂回。
第 2 圈:模型这才知道要查谁,想"查宁德时代财报" → 调"查财报"工具 → 拿到财报 → 喂回。
第 3 圈:模型觉得材料够了 → 直接给出最终回答,跳出环。
注意:程序事先并不知道这题要转几圈,因为"第 2 圈查谁"是第 1 圈的结果决定的。本项目里给这个圈数留了个上限作参考——一个"六只持仓挨个分析"的场景大约要转 5 圈,代码里把硬上限设成 12,留了一倍的垫(防止万一转不停)。换成上面那个一问一答版本,它在第 1 步就把计划定死了,根本走不到"看到持仓再决定查谁"这一步。

公允裁决:一问一答并不是"差方案",它在三件事上是实打实的赢家——延迟低、成本可预测、实现简单。对"茅台现在多少钱"这类一查就完的问题,它甚至和循环效果一样(循环碰到这种问题也是一圈就自然停,几乎没多花)。它真正够不着的,只有两类场景:一是依赖型多跳(下一步依赖上一步的结果),二是工具报错时的自我纠正(看着错误改了重试)。我们的判断很简单:简单问题循环也是一圈就停,代价可以忽略;而复杂问题没有循环就根本做不了。既然两头都要兼顾,统一用循环、再用一道上限闸把"万一转不停"的成本风险兜住,是更划算的买卖。

📌 总结

  • 循环的根本动机是"依赖型多跳":查了 A 才知道要查 B。下一步要做什么,藏在上一步的结果里,所以非得"看到结果再决定下一步"——这正是一问一答做不到的。
  • 循环 = 给模型装一个"想 → 做 → 看 → 再想"的反馈回路。模型说想调工具,程序真去调,把结果喂回去,模型看完再决定收尾还是继续。转一圈叫一个 iteration。
  • 圈数不是写死的,是模型边看边定。简单问题(茅台多少钱)一圈就自然停;复杂问题(六只持仓挨个分析)可能要转五圈左右,程序事先并不知道。
  • 一问一答不是稻草人。它延迟低、成本可预测、实现简单,简单问题完全够用;它只够不着两类场景——依赖型多跳,和工具报错时"看着错误自己改"。
  • 我们的取舍:统一用循环(简单问题反正一圈就停,没多花),再用一道上限闸兜住"万一转不停"的成本风险。

一句话速记:复杂问题的"下一步"藏在"上一步的结果"里,程序事先不知道要调几次,只能让模型边看结果边定——这就是为什么要循环。

Q2

你这个对话引擎的主循环,一轮对话(turn)里到底怎么转?从组装上下文、调一次大模型、到执行工具、再回到模型,数据是怎么流动的?"单 LLM 既决策又说话"是什么意思?

★★★☆☆
主循环解剖 单 LLM 数据流 turn 结构 决策与表达合一

🎯 考察点分析

上一题(本类第 1 题)讲的是"为什么要来回好几轮"的动机;这一题面试官把镜头怼到环的内部——你说要循环,那一圈到底是哪几步、顺序为什么是这个、数据从哪进哪出。这是在分辨两类候选人:一类只会背"Agent 就是一个 while 循环",一类真能把循环画成一张数据流图、说清"谁是真相、谁是投影、谁 append 回谁"。能不能把"单 LLM 既决策又说话"讲透,是这道题的分水岭——它考的是你有没有意识到,这一个看似简单的设计,其实是把旧架构里两个分工的模型合并掉的结果。

  • 追问:你说每圈都"组上下文",那这个上下文是新攒的还是历史累加的?上一圈工具查到的东西,下一圈模型看得到吗?(探你是否真懂"单一真相 + 每圈投影")
  • 追问:"既决策又说话"——程序怎么知道这次模型是在"决策"还是在"说话"?你靠什么判据分叉?(探你能否落到"带不带 tool_calls"这个具体信号上,而不是含糊其辞)
  • 追问:循环什么时候停?是你数圈数数到几就停,还是模型自己决定?(探你是否理解"自然停"是模型不再要工具,而非外部计数)
  • 追问:turn 和你说的"圈"是一回事吗?(探术语精度:turn=一问一答=一个异步任务;圈=turn 内 while 的一次迭代)

📚 原理讲解

先把两个词钉死,后面全靠它俩区分,讲错一个整段就乱:

  • turn(一轮对话):一条用户消息进来 → 一个最终回答出去,这整个过程叫一个 turn。它对应后台一个独立的异步任务(Celery task)。用户视角看到的"我问了一句、它答了一段",就是一个 turn。
  • 圈(iteration):一个 turn 内部,那个 while 循环转一次,叫一圈。一个 turn 可能转 1 圈(简单问题,模型张嘴就答),也可能转 5 圈(复杂问题,查了又查)。
一句话:turn 是外面看到的"一问一答",圈是里面藏着的"想一下/查一下"的每一次。一个 turn 套着 N 圈。
循环本体:一个裸 while,每圈固定这几拍

主循环就是一个 async def run() 里的 while True(在 loop.py 里,本体约 200 行)。它不是什么神秘的框架调度,就是老老实实一拍接一拍走。一圈的节拍(删掉枝节,留主干):

  1. 取消检查:看用户有没有按"停"。有就在圈边界干净地中断(为什么必须在圈边界、不能半路砍,见本类第 7 题的 turn 原子语义)。
  2. 终止闸判定:一组纯谓词,问"该不该停了"(花超预算了?转太多圈了?在原地打转?)。该停就逼模型用手头信息收个尾。四道闸为什么是四道,见本类第 4 题。
  3. 并入插话:把用户中途补的话塞进来(见本类第 7 题)。
  4. 组窗口:把当前状态投影成一份发给模型的消息数组(assemble_context)。这一步是纯函数,不碰任何外部 I/O。窗口怎么切四个区、怎么省 token,见本类第 5 题——本题只说它"把状态投影成消息"。
  5. 单次流式调 LLM:stream_step,把窗口、可用工具的说明书一起发给一个模型,流式拿回结果。
  6. 折叠输出:apply_step 把模型这圈吐的内容写回状态。
  7. 分叉判定:模型这次带没带 tool_calls?
    • 没带 → 它不想再调工具了,这段 content 就是最终答案,自然停,turn 结束;
    • 带了 → 程序去执行这些工具(dispatch),把结果折叠回状态(apply_results),回到圈首,让模型下一圈带着工具结果再想。
数据流的"单一真相":一切围着 state.messages 转

这是整道题最该答漂亮的地方。整个循环的唯一真相(single source of truth)是一个东西:state.messages——一个 OpenAI 格式的消息列表(list[dict],每条带 role:system / user / assistant / tool)。它就是这个 turn 到目前为止发生过的一切的账本。

围着它转的有两类动作,分清楚很关键:

  • 投影(读):每圈 assemble_context 把状态投影成发给模型的消息数组。注意是"投影"不是"就是"——它会按窗口策略裁剪、降级老内容(细节见本类第 5 题),但底稿来自 state.messages。投影是只读的派生品,不改真相。
  • 追加(写):模型回的 assistant 消息、工具回的 tool 消息,都 append 回 state.messages 的尾部。下一圈再投影时,这些新尾巴自然就一起发出去了。
所以"上一圈查到的东西下一圈看得到吗?"——看得到。因为工具结果作为 tool 消息 append 进了真相账本,下一圈投影会把它带上。这正是"查了 A 才知道要查 B"能跑通的物理基础:每一圈模型看到的都是截至此刻的完整轨迹。
"单 LLM 既决策又说话":两个模型合并成一个

这句话的分量,要对照旧架构才看得出来。旧架构是两个模型分工:一个叫 planner,专门"出计划"(决定调哪些工具);另一个叫 responder,专门"措辞"(把工具结果合成人话)。两次 LLM 调用,各管一摊。

新架构把这俩合并成一个。同一个模型,在循环里同时干两件事:

  • 决策:这一步要不要调工具、调哪个、传什么参数;
  • 表达:直接生成给用户看的那段文字。

而且它在同一次流式回复里二选一:要么吐 tool_calls(我要调工具,你去执行),要么吐最终文字(我想好了,这是答案)。判据就是这次回复带不带 tool_calls——这是程序区分"它在决策"还是"它在收尾"的全部依据,简单到一个布尔判断:

  • 带 tool_calls → 程序去执行工具、继续循环(它在决策);
  • 不带、finish_reason == "stop" → 这段 content 落定为 final_response,自然停(它在表达)。

"决策与表达合一",说的就是这件事:不再有"谁负责想、谁负责说"的分工,一个脑子从头管到尾。至于"为什么"要这样合并、合并的整体收益,那是架构决策题(见本类第 3 题);本题只负责把"合一长什么样、靠什么判据分叉"讲清楚。

纯函数核 + 不纯壳:为什么这么分

顺带提一个让这个循环好测的设计:有副作用的活(调 LLM、分发工具、发事件)只集中在 loop.py 这个"壳"里;判定逻辑(终止闸、窗口组装、状态折叠)全是零 I/O 的纯函数。好处是:闸该不该停、窗口怎么投影、状态怎么折叠,这些都能脱离任何运行时环境(不用起数据库、不用连模型)直接拿假数据单测。壳薄、核纯,这是它好维护的根。

        if (halt := check_gates(state)):
            return force_conclude(state, halt)   # 逼模型用手头信息收尾

        # ② 投影:把"真相账本"state.messages 组装成发给模型的窗口
        #    这是只读派生，不改 state.messages 本身
        messages = assemble_context(state)

        # ③ 单 LLM 一次流式调用：既决策又说话，二者合一
        step = await llm.stream_step(messages=messages, tools=schemas)

        # ④ 折叠输出：把模型这圈吐的 assistant 消息 append 回真相账本，step += 1
        state = apply_step(state, step)

        # ⑤ 分叉判据 = 带不带 tool_calls
        if not step.tool_calls:
            # 不带 → 它在"表达"：这段就是最终答案，自然停，turn 结束
            return state                          # final_response 已落定

        # 带 → 它在"决策"：去执行工具，结果作为 tool 消息 append 回真相账本
        results = await tool_hub.dispatch(step.tool_calls, state)
        state = apply_results(state, results)     # tool 消息进 state.messages

        # 回圈首 → 下一圈投影会带上刚 append 的 tool 结果，模型据此再想一步

推演:假设用户问"我持仓里那几只票最近财报怎么样"。第 1 圈:模型看不到持仓清单,于是吐一个 tool_calls(查持仓)——这是决策;程序执行,把"持仓=贵州茅台、宁德时代"作为 tool 消息 append 进 state.messages。第 2 圈:投影把这条新尾巴带上,模型现在看到了具体是哪两只票,于是再吐 tool_calls(查这两家财报)——又一次决策;结果再 append 回去。第 3 圈:模型攒齐了信息,这次不带 tool_calls 了,直接吐一段总结文字——这是表达,finish_reason=="stop",自然停。这一个 turn 转了 3 圈、调了 3 次 LLM(每圈恰好一次,turn 账单里 llm_calls 就等于圈数 step)。三圈用的是同一个模型,没有"换人合成"——这就是"单 LLM 既决策又说话"在一条真实数据流上的样子。

📌 总结

  • 主循环=一个裸 while,每圈固定节拍:取消检查 → 终止闸 → 并入插话 → 组窗口投影 → 单次流式调 LLM → 折叠输出 → 带 tool_calls 就执行工具再回圈首、不带就自然停。
  • 数据流只有一个真相:state.messages。每圈把它投影成发给模型的消息(只读派生);模型的 assistant 消息、工具的 tool 消息都 append 回它。下一圈连同新尾巴一起再发——所以上一圈查到的,下一圈一定看得到。
  • "单 LLM 既决策又说话"=两个模型合并成一个:旧架构 planner 出计划、responder 措辞分两次调;新架构一个模型在循环里既决定要不要/调哪个工具,又直接生成给用户的文字。
  • 决策与表达的判据=带不带 tool_calls:带→去执行、继续循环(决策);不带且 stop→content 落定为最终答案、自然停(表达)。停不停是模型自己决定的,不是外部数圈数。
  • turn ≠ 圈:turn=一问一答=一个异步任务;圈=turn 内 while 的一次迭代;每圈恰好一次 LLM(turn 账单里 llm_calls 就等于圈数)。

一句话速记:一个真相账本(state.messages)+ 一个既决策又说话的模型 + 一个"带不带工具调用"的分叉,循环到模型不再要工具为止。

Q3

你为什么把 chat loop 从 LangGraph supervisor 单程图退役成裸 Python while 循环?这个决策的收益和代价各是什么?

★★★★☆
架构迁移 框架退役 裸 while 循环 自有控制流 turn 原子语义

🎯 考察点分析

这道题问的是"为什么换框架",不是"换成什么"——它表面上是个技术选型题,底下藏着对一个工程师判断力的三重检验。第一,你是被框架的功能清单牵着走,还是真把每一项功能对照自己的场景算了笔账:这个 checkpoint、这个 interrupt 原语,在我的循环里到底有没有人用?第二,你能不能诚实地说出代价——退役一个跑得好好的框架是破坏性动作,不是免费午餐,只谈收益不谈代价的人多半没真做过迁移。第三,也是最关键的,你拿出来的"我不选框架"的论据,是不是真正击中了框架存在的理由,还是在打稻草人(把对方说得一无是处)。

  • 追问:LangGraph 自带 checkpoint、interrupt、事件透出、状态管理这四样,你一个裸 while 怎么补上?还是说你根本不需要补?
  • 追问:"中间圈的 checkpoint 没有消费者"——这句话什么意思?为什么它能反过来证明裸 while 是对的?
  • 追问:破坏性替换、没有新旧并存期,万一切过去发现行为退化了怎么办?你怎么保证回归面可控?
  • 追问:多圈循环每圈都要调一次大模型,成本和延迟会不会反而比原来"两次大模型搞定"的单程图更差?

📚 原理讲解

先把旧架构说清楚,不然没法谈"换"。旧的 chat 是一张单程图:第一个大模型(规划者)读完用户问题,一次性吐出一份结构化的"我要查这几样东西"的计划;然后一段纯函数路由把计划分发出去;工具批量执行;最后第二个大模型(应答者)拿着工具结果合成回答。注意一个致命特征:工具结果不回流给规划者。计划在第一步就定死了,后面只是照单执行。这是一条直线,不是一个圈。

为什么要换:七个够不着的缺口

这条直线在七个地方对不齐"一个像样的工具型 agent 该有的样子"。我把它们列出来,因为这七条才是真正的迁移动机——不是"while 比图时髦":

  • 依赖型多跳够不着。"先查持仓清单,看到里面有哪几只股票,才知道接下来该查谁的财报"——这种"查了 A 才知道要查 B"的链路,单程图天生做不到,因为计划在看到 A 的结果之前就已经定死了。
  • 没有预算闸。没法按 token 或金额封一个硬上限,烧多少算多少。
  • 上下文只会"超阈值就压缩",不会"按需检索式地选"。窗口满了就一刀切地砍,没有"这一圈我只把相关的捞进来"的能力。
  • 推理过程没有真流式。旧的"直接回答"路径是靠事后补发文字 hack 出来的假流式,用户看到的不是模型真的在边想边说。
  • 打断只能取消整轮。用户想"插一句话改个方向"是做不到的,要么忍着等完,要么整轮取消重来。
  • 没有审批门的挂载点。"这步动作危险,先让用户确认"这种闸没地方插。
  • 工具报错只能让应答者道歉,没有自纠回路。查错了就是查错了,模型没机会"看到报错→改参数→重试"。

这七条的共同点是:它们全都需要"模型看到中间结果后,再决定下一步"。而单程图的本质就是"下一步在看到中间结果之前就定死了"。所以这不是修修补补能解决的——它要的是一个能回头的圈,而不是一条直线。

骨架怎么选:三个候选 × 三面镜子

确定要"圈"之后,圈有好几种盖法,我摆了三个候选,用三面镜子各照一遍:

  • 裸 Python while 纯正派——控制流百分之百自己写,不依赖任何框架。
  • LangGraph 双节点回环——继续用框架,但把单程图收敛成一个"规划↔工具"来回跳的回环。
  • 事件溯源 + reducer——更重的一套,把每个状态变化当事件存下来、用归约函数推演当前态。

三面镜子是:可行性(能不能落地)、研报对齐(跟业界主流 agent 循环的做法是否一致)、作品价值(这是个面试作品,要不要把"控制流我自己掌控"这件事讲透)。最后定的是裸 while。事件溯源太重、收益用不上;LangGraph 双节点回环留着框架但其实没用上框架的好处;裸 while 在"控制流百分之百自有 + 可读性 + 能讲清楚的作品叙事"上三面通吃。

压垮 LangGraph 的那根稻草:turn 原子语义

很多人会问:就算要做成圈,为什么不用框架的圈?毕竟 LangGraph 自带 checkpoint(断点续跑)、interrupt(暂停人工介入)、事件透出、状态管理这四样,听起来都很有用。这里有个关键洞察,也是整个决策的承重墙——turn 原子语义。

什么是 turn 原子语义?一个 turn,就是"用户发一条消息 → 系统给出一个最终回答"这一整段。我把它定义成不可分割的原子:重试 = 整个 turn 从头重跑,不存在"恢复到第几圈接着跑";运行中插话 = 并入当前这个 turn,而不是排成下一个新问题。

这条语义一立,framework 的四项职能就逐项失效:

  1. checkpoint 结构性失效。框架的 checkpoint 是为"跑到一半挂了,从断点续上"准备的。但既然我的重试规则就是"整 turn 重跑",那"每圈存一个检查点"这件事压根没有消费者——没有任何代码会去读"第 3 圈的检查点"然后从那儿接着跑。一个没人读的功能,就是死重量。更扎心的是:生产环境的 worker 路径,现状本来就是 checkpointer=None(检查点没真正接上),这套机制一直是半接通的摆设。
  2. 控制流被收回。图的核心价值是"它替你管节点之间怎么跳"。但我现在要的就是百分之百自己管跳转(为了那七个缺口),框架替我管反而碍事。
  3. 事件透出改成循环主动发射。原来靠框架在节点边界吐事件;现在循环自己在该发的地方主动发,更直、更可控。
  4. interrupt 原语用不上。框架的暂停-恢复原语,在"整 turn 重跑、插话并入"的语义下没有用武之地。

注意这个论证的方向:不是"我讨厌框架所以退役它",而是"turn 原子语义一旦成立,框架这四项职能各自失去了消费者,退役只是承认既成事实"。反过来,正因为没有"恢复到第几圈"这回事,裸 while 的合理性被坐实了——它不需要在每圈留检查点这个负担。这是这道题的题眼。

收益:不只是"少个依赖"

真正的收益里,最值得讲的是一个连带的"简化红利"。旧架构里,要拿到"这一轮最终跑出来的状态",得做三个动作的拼接:从事件流里捞特定的结束信号、按节点名匹配、再异步查一次图的状态。三个接缝,任何一个错位都是 bug。换成裸 while 之后,final = await loop.run(state) 一个函数返回值就是最终状态——三个接缝一起消失,那个为了假装流式而补发文字的 hack 也跟着删掉了。这种"换了骨架,顺手干掉一堆历史接缝"的红利,是评估迁移收益时最该看重、却最容易被忽略的部分。

💻 示例讲解

用最精简的伪代码把"直线 vs 圈"的结构差异摆出来,你一眼就能看出为什么单程图够不着依赖型多跳。先看旧的单程图:

# 旧:单程图 —— 一条直线,计划在看到结果前就定死
async def old_supervisor(question):
    plan = await planner_llm(question)        # 大模型①:一次性出全部计划
    results = []
    for call in plan.tool_calls:              # 照单执行,不回头
        results.append(await run_tool(call))
    answer = await responder_llm(question, results)  # 大模型②:合成回答
    return answer
    # 致命点:results 永远不回流给 planner —— "查了A才知道查B" 做不到

再看裸 while 的圈。注意它把"规划"和"应答"合并成同一个模型,在循环里既决策又说话(这块机制属于本类第 2 题,这里只点到为止),关键是工具结果回流、模型据此决定下一步:

# 新:裸 while —— 一个圈,结果回流,模型看了再定下一步
async def tool_loop(state):
    while True:
        messages = assemble_context(state)            # 每圈现组窗口(纯函数)
        step = await llm.stream_step(messages, tools) # 单模型:既决策又说话
        state = apply_step(state, step)
        if not step.tool_calls:                        # 模型不再要工具 → 自然停
            return finalize(state)                     # ← 返回值就是 final_state
        if halt := check_gates(state):                 # 四道闸封顶(成本/步数兜底)
            return await force_conclude(state, halt)
        results = await dispatch(step.tool_calls)      # 执行工具
        state = apply_results(state, results)          # 结果折叠回 state,下一圈模型能看见
        # ↑ 回到 while 顶 —— 模型看到 results 后,自己决定要不要再查、查什么

推演:"监控六只持仓"这个典型场景,旧图是固定两次大模型(规划 + 应答);裸 while 大约转五圈、留了一倍垫到上限 12 圈才硬停。表面看"五圈五次大模型 vs 两次",成本似乎涨了。但实际不是这么算的:① 旧图的两次里,规划那次必须把"该查什么"全猜对——猜不对就只能给个差答案,而裸 while 用多花的几圈换来了"依赖型多跳能真的查对";② 简单问题(比如"茅台今天涨了吗")裸 while 一圈就自然停,跟单程图成本相当,不会平白多烧;③ 多圈的成本上限被四道闸封顶(本类第 4 题细讲),最坏情况有硬天花板。所以"多圈一定更贵"是个错觉:贵的部分买到了正确性,便宜的场景一圈就走,最坏情况有闸兜底。

📌 总结

  • 动机是七个缺口,不是赶时髦。依赖型多跳、预算闸、检索式上下文、真流式、插话改向、审批门、错误自纠——这七条全都要"模型看到中间结果再定下一步",而单程图的本质恰恰是"下一步在看到结果前就定死",修不动,只能换成能回头的圈。
  • 退役框架的承重墙是 turn 原子语义。重试=整轮重跑、插话=并入当前轮,这条语义一立,LangGraph 的 checkpoint / 控制流 / 事件 / interrupt 四项职能各自失去消费者(checkpoint 尤其,生产路径本就 checkpointer=None 半接通)。退役是承认既成事实,不是打稻草人。
  • 收益里最值钱的是简化红利。取最终状态从"三接缝拼接"变成一个函数返回值,假流式 hack 顺手删掉——迁移收益要算这种连带账,不只是"少个依赖"。
  • 代价诚实摆出:破坏性替换、回归面大。用分期实施(前几期纯新增、最后一期才切)+ 差分金标准锁行为 + 重录真实对话流,把大爆炸降级成可回退的渐进切换。多圈成本顾虑则由四道闸封顶 + 简单问题一圈自然停兜底。
  • 裁决是场景特定的。如果我的 turn 可以恢复到中途(长任务),checkpoint 立刻有消费者,答案会反过来——所以这是个有前提的决策,不是"框架一律不如手搓"的口号。

一句话速记:不是嫌 LangGraph 差,而是 turn 一旦"原子化",它最值钱的 checkpoint/interrupt 全失去消费者,留着只剩死重量——于是退役成一个能让结果回流、控制流百分之百自有的裸 while 圈。

Q4

你的循环有"四道终止闸",为什么需要四道而不是一道?各拦什么情况?

★★★★☆
终止闸 预算闸 打转检测 烧签名 连续失败连

🎯 考察点分析

这道题表面问"你有几道闸",真正在探的是:你有没有把"agent 跑不停"这个抽象问题拆成几种不同的失效模式,还是只会用一个 for i in range(N) 兜底。一个只设了步数上限的人,和一个为每类坏情况都画过一道防线的人,对"自主循环到底哪里会出事"的理解深度差很远。面试官会顺着往下挖:

  • 追问:步数上限本来就能兜底任何死循环,你为什么还要另外三道?它们各自能比步数上限"早多久"止损?
  • 追问:"打转"(同样工具同样参数反复调)和"乱试"(每次换个参数硬碰)是两回事吗?你怎么分别抓?
  • 追问:检测打转你是让模型自己反省"我是不是在重复",还是用外部规则判?为什么?
  • 追问:撞了闸之后你是直接抛异常截断、还是有别的处理?用户会看到什么?

📚 原理讲解

先把场景说清楚:这是一个"模型想一下 → 调个工具 → 看结果 → 再想"的循环(主循环怎么转见本类第 2 题)。理想情况下,模型查够了数据自己就停下来开始作答——这条自然停是主路径,占绝大多数 turn。问题在于剩下那一小撮 turn:模型可能停不下来。而"停不下来"不是一种病,是四种病,每种的病灶和早期症状都不一样。用一道闸去拦四种病,等于不管什么病都拖到"烧满 12 圈"才送急诊。

四种失效模式,四道闸各管一种

我把它们按"圈首判定顺序"列出来——每圈开头,在花钱调模型之前,先依次过一遍这几道闸:

  • ① 自然停:这一圈模型没再要求调工具(not tool_calls),说明它准备直接作答了。这是正常出口,不是"闸",是循环的主路径。展开讲见本类第 2 题。
  • ② 硬迭代上限(max_steps=12):拦"怎么都停不下来的死循环"。这是最后一道兜底,数值上算过:六只持仓的监控场景大约五圈就够,留了一倍垫。它是别的闸全失灵时的保险丝。
  • ③ 预算闸(max_cny 或 max_tokens 任一超):拦"按钱/token 封顶"。防的是少数几圈就把成本炸穿——比如某一圈塞进一个巨大上下文,步数还没到 12,钱已经花光了。步数和花钱不是一回事,所以要单独一道。
  • ④ 打转检测(spinning):拦"原地踏步"——连续两圈,模型发起的工具调用签名集完全相同(同样的工具、同样的参数)。这种死循环步数和预算都还远没到顶,但它已经在做无用功了,越早掐越省。
加强项一:烧签名(burn)——同一个错误别死磕

打转闸抓的是"两圈完全一样"。但有种更隐蔽的:模型并不是每圈都重复,而是某一个具体调用反复失败(比如老用一个查不到的代码)。我给每个 (工具, 参数哈希) 签名记一个失败计数,失败累计到 burn_threshold=3 次,这个签名就被"烧掉":之后模型再发同一个签名,直接在分发前被拒,并喂回一句"该调用已连续失败 3 次被熔断,请换方法"。这不是终止整个循环,而是定点封杀一条死路,把模型从这条路上推开。

这里有个反直觉的细节:如果模型流式吐出的 JSON 参数是残缺的、算不出签名,我不在这一步丢弃它,而是放行,交给下游工具的 schema 校验产出一条指导性错误喂回模型。在这里静默吞掉反而更危险——模型不知道发生了什么。坏参数这一环属于 function calling 工程坑,展开见本类第 8 题。
加强项二:连续失败连(repeated_failures)——抓"换参数硬试"

后续一次精度修补又补了个洞:有一种乱试,打转闸和烧签名都拦不住。设想模型这样查:query_kb(09988.HK) ❌ → query_kb(9988) ❌ → query_kb(BABA) ❌。每圈参数都不一样,所以签名集永远不重复(打转闸不响),也没有哪个单签名失败到 3 次(烧签名不响)——但它显然在瞎试。我加了一道跨签名的闸:从台账末尾往回数连续 success=False 的条数,达到 max_consecutive_failures=5 就 halt。门槛比烧签名(3)宽一档,因为"连续失败 5 次"是更强的"这条线索走不通"信号。

加强项三:分发前预算预检(budget_margin_exhausted)

预算闸③是"已经超了才停",但有个时序问题:这一圈 LLM 成本入账后,余量可能只够再调一次模型、不够"再跑一批工具 + 又一轮模型"了。所以在分发工具之前再做一次预检:剩余预算低于上限的 budget_dispatch_margin_ratio=0.2(20%),就整轮跳过工具、直接收尾,把留下的那 20% 余量专门留给收尾那次 LLM 调用。这是"花超之前先刹车",而不是"撞墙了再算账"。

两个贯穿全篇的设计决策

打转检测靠外部裁判,不靠模型自省。我没让模型每圈自问"我是不是在重复";而是用台账(ToolLedger)记录的签名集指纹做确定性比对,零 LLM 调用。调研里一个结论很硬:没有外部反馈的纯自省,在推理任务上不升反降——模型自查自己有没有打转,本身就不可靠。指纹比对是确定性的,它说重复就是真重复。

撞闸不抛异常、不静默截断,而是逼模型收尾 + 如实上报。任何一道闸触发,走的都是 _force_conclude:往对话里塞一句系统消息"已达执行上限,请基于已有信息直接作答",并把 tool_choice 钉成 none(这一圈不许再调工具),让模型用手头已有的信息给出一个最终回答。同时发一个 loop_halt 事件向看板和用户如实归因。撞闸的原因有两套口径:事件层给前端看板看的是机器码(max_steps / budget / spinning / repeated_failures),喂给模型的系统消息用映射表翻成中文人话("已达预算上限"等)——机器要归因、模型要看懂,两边别将就。

💻 示例讲解

下面这段伪代码把"圈首一串闸"的判定顺序和撞闸去向画出来。真实实现里判定逻辑全在零 I/O 的纯函数 check_gates 里,循环本体只负责编排:

# 圈首:在花钱调模型之前,依次过闸(顺序固定)
def check_gates(state, cfg):
    # ② 硬迭代上限:最后兜底的保险丝
    if state.step >= cfg.max_steps:           # 12
        return "max_steps"

    # ③ 预算闸:钱或 token 任一超顶就停(少数几圈也可能炸穿)
    if (state.budget_spent_cny >= cfg.max_cny       # 0.10 元
            or state.budget_spent_tokens >= cfg.max_tokens):  # 120k
        return "budget"

    # ④ 打转:连续两圈"工具+参数"签名集完全相同 = 原地踏步
    if state.step >= 2:                        # 有两圈才能比
        cur  = state.ledger.signature_set(state.step)
        prev = state.ledger.signature_set(state.step - 1)
        if cur and cur == prev:
            return "spinning"

    # 加强:跨签名尾部连续失败(每圈换参数硬试,上面两道都漏检)
    if state.ledger.trailing_failure_count() >= cfg.max_consecutive_failures:  # 5
        return "repeated_failures"

    return None   # 全过 → 放行,正常调模型


# 循环本体:撞闸不抛异常,逼模型收尾
halt = check_gates(state, cfg)
if halt:
    await emit("loop_halt", reason=halt)      # 机器码给看板归因
    return await force_conclude(state, halt)  # 中文人话喂模型 + tool_choice=none 收尾

推演:假设模型陷入"换参数硬试"——查阿里港股代码,09988.HK ❌ → 9988 ❌ → BABA ❌ → 09988 ❌ → 0700 ❌。看四道闸怎么反应:步数才到 5,max_steps=12 不响;假设每圈很轻,预算远没到顶,预算闸不响;每圈参数都不同,签名集永不重复,打转闸不响;没有哪个单签名失败满 3 次,烧签名也不响。但连续失败连数到第 5 条 success=False 就 halt——精准抓住了前三道都漏检的乱试。如果只有一道 max_steps=12,这个 turn 会白白再烧 7 圈、多花一倍 token 才停。

⚖️ 决策对比

维度我们的选择(四道闸 + 三加强)替代方案(单一 max-steps 上限)
实现成本多写 4~5 个纯谓词 + 一套台账签名记账一行 if step >= N,最简单
打转(原地踏步)spinning 闸第 2 圈就掐白跑满 12 圈才停

定点死磕烧签名封单条死路,把模型推开换方法无,只能整体硬停

公允裁决:单一 max-steps 上限真的有它的好——一行代码、零状态、永远不会误杀,而且它能兜住任何死循环(这也是为什么它仍是我的第②道闸保险丝)。如果这是个低频、低成本、人盯着的脚本,我也会只写它。它的代价只在规模化、自动化、要花钱的场景才暴露:打转、乱试、单圈超支这三种坏情况,它都得拖到上限才止损——既烧钱又拖延迟,而且用户拿到的是被硬截断的半截回答。我没有用更激进的方案(比如按每个工具的成本模型选择性跳过"只跳重型工具")——因为我没有可靠的每工具成本模型,那是 YAGNI;预算不足时我的选择是整轮工具都不分发,简单且可证。四道闸 + 三加强不是为了炫技,是因为"停不下来"本就是四种病,一道闸治不了四种病。

🖼️ 图解

📌 总结

  • "agent 停不下来"不是一种病而是四种:死循环、超预算、原地打转、定点死磕——一道闸治不了四种,所以分治:max_steps 兜底、预算闸封顶、spinning 抓打转、烧签名封单条死路。
  • 后补两道精度闸堵了缝:连续失败连(尾部连失≥5)抓"换参数硬试"的乱试——前面所有闸都漏检它;分发前预算预检(剩余<20%)在花超之前刹车,而非撞墙再算账。
  • 打转/乱试用台账签名指纹做确定性裁判,不靠模型自省——调研结论:无外部反馈的纯自省在推理任务上不升反降。
  • 撞闸不抛异常、不静默截断,而是 force_conclude 逼模型基于已有信息收尾 + 发事件如实归因;归因有两套口径:机器码给看板、中文人话给模型。
  • 替代的单 max-steps 不是稻草人——它简单、永不误杀、能兜任何死循环,所以仍是第②道闸;只是另外三种坏情况它都得烧满 12 圈才止损。

一句话速记:停不下来是四种病,四道闸 + 三加强各治一种,且打转靠指纹不靠模型自查。

Q5

"窗口四区"(KV-cache 分区)是怎么切的?为什么这样切能省 token、省钱,还能稳住 prefix cache 命中?

★★★★★
窗口四区 KV-cache 稳定前缀 省 token 位置工程

🎯 考察点分析

这题是整个对话引擎里最"省钱见真章"的一题。面试官想确认:你知不知道大模型计费里有个隐藏的便宜口子(请求前缀如果逐字节没变,这部分输入按大约两折计费),以及你有没有把对话上下文的物理布局当成一门"工程"来设计——而不是每轮随手把所有东西拼成一坨发出去。能答到"为什么动态状态要赶到尾部"这一层,就说明你真的理解了缓存命中的机制,而不是背名词。

  • 追问:这个"便宜口子"到底是怎么触发的?为什么一个字变了整段折扣就没了?
  • 追问:"每轮都变"的状态(比如第几步、预算还剩多少)你放哪了?为什么不能图省事塞进开头?
  • 追问:大窗口模型其实很少真撑爆,那省这点 token 到底省的是什么钱?
  • 追问:老的大工具结果占地方,你直接删掉不就完了?为什么要费劲做"可逆降级"?
  • 追问:你怎么知道这套设计真的生效了、缓存真命中了?有没有数字盯着?

📚 原理讲解

先讲清楚那个"便宜口子"。我们用的模型(阿里云 DashScope 上的 qwen)有一个隐式 KV-cache:你这一次请求开头的那一段文字,如果跟上一次请求开头逐字节完全一样,模型内部就能把上次算过的中间结果直接复用,不用重算。复用的代价是——这段命中的输入,大约只按正常输入价的两折收钱。这是白送的折扣,但有一条铁律:从第一个变化的字节开始,后面全部作废。哪怕你只在开头第三行改了一个数字,这行之后的所有内容缓存全废,折扣拿不到了。八路外部调研全票点名这一条,它是整个设计的地基。

一轮对话里,上下文长什么样

每"圈"(模型想一次 + 可能调一次工具,叫一个 step)结束后,我们要把当前对话状态投影成一个发给模型的消息数组。如果随手拼,会发现一个尴尬:既有从头到尾都不变的东西(角色设定、工具清单),也有每圈都在变的东西(现在第几步、预算还剩几毛)。这两类混在一起,就等于每圈都在前缀里埋了个会变的字,缓存天天作废。

所以我们按"哪些恒定、哪些在变",把上下文从上到下切成四个连续区段,顺序刻意安排成"越往上越稳、越往下越动":

  • 区一 · 稳定前缀区(逐字节恒定):一条 system 消息,里面是角色定位、工具使用纪律、用什么时候查记忆/查知识库的启发式、人格设定的稳定部分、技能元数据清单、以及全部工具的 schema。这些东西一个 turn 里从头到尾一个字都不变,就是为了吃满那个两折折扣。
  • 区二 · 历史区:上文的压缩摘要 + 最近 4 个 turn 的原文。压缩边界一旦定好,这一圈一圈也是稳的。
  • 区三 · 本 turn 轨迹区(只增不改):这一轮里,模型说的话、它发起的工具调用、工具返回的结果,一对一对地往后追加(append-only)。注意是"只在末尾加",前面已经写下的内容不动——这样区三本身对前面区段也是稳定前缀。
  • 区四 · 尾部动态区(每圈重写):整个上下文里唯一每圈都重写的一小段,就放在最末尾。内容是一条 user 消息:(今天 2026-06-22 周日。第 3/12 步,预算剩 ¥0.07。),如果用户中途插了话,也并到这里(插话怎么进来归本类第 7 题)。
核心招式:动态状态绝不进前缀。步数、预算这种每圈都变的数字,要是放在开头,从那个字起前面所有缓存全废。把它们全部赶到最末尾,每圈就只有这一小段没命中(miss),前面长长的几千上万字全部命中折扣。而且末尾恰好是模型注意力召回最强的位置——既省了钱,又把"当前要紧的状态"摆在了模型最看得见的地方,一举两得。这叫位置工程。
参考日期为什么也在尾部

"今天是哪天"这个信息,直觉上像个稳定设定,会想塞进开头。但它在评估和强化学习场景下要被冻结成某个历史 as-of 日期,生产里又是真实今天——一旦它进了稳定前缀,不同会话/不同模式前缀就不一致,缓存白破。所以它被刻意放在区四尾部最前面,跟着动态状态一起走。

省钱省的不只是"别溢出"

很多人以为上下文优化就是防止撑爆窗口。但现在窗口动辄几十万 token,真溢出是低频事件。真正的钱漏在别处:窗口装得下的时候,你每转一圈,都会把前面那几千字的老工具结果原样、全价再发一遍。一轮对话转五六圈,同一份大结果就被全价计费五六次。这才是日常账单的大头。

于是有两道互补的"少花钱"机制:

  1. 老圈大工具结果降级(可逆,不是删除):超过基准阈值(1320 字符)的老圈工具结果,content 被换成 [全文已缓存 ref=...] + 200 字摘要。全文没丢,还在结果缓存(ToolResultCache)里,模型想看可以用专门的工具按 ref 取回。协议红线很硬:只改 content,绝不删消息、绝不动 role 和 tool_call_id——因为 assistant(发起调用)和 tool(返回结果)是配对的,切破配对模型直接报 400。还有保护名单:最近一圈永远全文、失败消息永不降级、加载技能的结果永不降级。
  2. 总量压力安全阀(只在真挤时才收紧):拼完估算总量如果超过窗口的 0.85,就把降级阈值逐级减半(1320 → 660 → 330 → 200),多榨几圈老结果,直到落回安全线。阈值每轮严格减半,从 1320 榨到下限 200 最多约 3 轮就到底,不会死循环。平时不触发,所以正常对话该全文还是全文。
怎么证明它真生效了

两道保险。其一,一条 CI 回归测试死守稳定前缀:断言连续两圈组装出来的区一 system 消息逐字节相同。谁哪天手滑往角色设定或人格里塞了个时间戳、计数器之类会变的东西,这条测试立刻变红,赶在它上线悄悄毁掉两折缓存之前就拦下来。其二,缓存命中率被当成一等指标:每圈把模型回传的输入 token 总数和其中命中缓存的 token 数累加,turn 结束算 命中率 = 命中 token / 输入 token。这个数字是验证"窗口四区稳定前缀"这套设计到底有没有生效的唯一硬证据。

下面是组装逻辑的教学版伪代码,只保留"四区怎么拼 + 动态状态怎么赶到尾部"这条主线:

def assemble_context(state, deps):
    # ---- 先做可逆降级:老圈大工具结果换成「摘要 + ref」----
    # 注意:只改 content,绝不删消息、绝不动 role/tool_call_id
    downgrade_old_tool_messages(state, threshold=1320)

    msgs = []

    # 区一 · 稳定前缀区:一个 turn 里逐字节恒定 → 吃 KV-cache 两折
    #   角色 + 工具纪律 + 人格稳定部分 + 技能清单 + 工具 schema
    msgs.append({"role": "system", "content": deps.system_message_content})

    # 区二 · 历史区:摘要 + 最近 4 个 turn 原文(压缩边界后也稳)
    msgs.extend(deps.history_block)

    # 区三 · 本 turn 轨迹区:这一轮的 assistant / tool 消息,只往末尾追加
    msgs.extend(state.messages)

    # 区四 · 尾部动态区:整个上下文里唯一每圈重写的一小段,放最末尾
    #   步数、预算每圈都变 —— 绝不能放前面,否则前缀缓存从此全废
    #   参考日期也放这里前置,刻意不进稳定前缀
    remaining = deps.max_cny - state.budget_spent_cny
    tail = f"(今天 {today_str}。第 {state.step + 1}/{deps.max_steps} 步,"
    tail += f"预算剩 ¥{remaining:.2f}。)"
    msgs.append({"role": "user", "content": tail})

    # ---- 安全阀:总量逼近窗口才逐级收紧(阈值减半,最近一圈永保护)----
    while estimate_tokens(msgs) > 0.85 * deps.window and threshold > 200:
        threshold = max(200, threshold // 2)   # 1320 → 660 → 330 → 200
        downgrade_old_tool_messages(state, threshold)
        msgs = reassemble_regions(state, deps)

    return msgs

推演:假设一轮对话稳定前缀区是 6000 token(工具 schema 占大头),前几圈攒下来的历史和轨迹有 4000 token,每圈尾部动态区约 30 token。某一圈发出去时输入约 10030 token。因为前 10000 token 逐字节没变,命中缓存按两折计:命中部分 ≈ 10000 × 0.2 = 2000 的等效计费,只有尾部那 30 token 全价 miss。命中率 ≈ 10000 / 10030 ≈ 0.997。反例:如果把"第 3 步/预算 ¥0.07"这行错误地塞进开头第二行,那么从这行起后面 10000 token 全部 miss,这一圈就得按全价 10000+ 计,折扣彻底拿不到——而且这种事在线上是悄无声息的,只有那条逐字节断言的 CI 测试能提前抓住它。

工具渐进披露:为什么不一次把所有工具塞给模型?分档依据是什么?

🎯 考察点分析

这道题表面在问"工具怎么暴露给模型",真正想确认的是:你有没有把"工具描述"当成一项占着上下文窗口、每一轮都要重发的常驻成本来管理。很多人把工具一股脑塞进 prompt,从不算这笔账。面试官想看你能不能把"描述要写得厚才好用"和"常驻 token 要省"这对矛盾拆开,并给出一个能随工具数量增长而不爆的方案。

  • 追问:每多一个工具,常驻成本到底涨在哪?为什么"叠了 KV-cache 命中"之后这笔开销还是省不掉?(考你是否理解工具 schema 是稳定前缀的一部分,见本类第 5 题)
  • 追问:你按什么标准把工具分进"核心组"和"延迟组"?给我一个具体例子,说说为什么某个工具进了延迟组。
  • 追问:延迟组只给了名字和一句话,模型看不到完整参数怎么调?如果它瞎调、参数填错了,系统怎么把它接住、引导它自己补全?
  • 追问:你自己也承认 14 个工具其实"不够多、不值得上这套机制"。那你为什么还要做?这笔账靠什么成立?(考你敢不敢诚实标注代价,而不是吹方案完美)

📚 原理讲解

先说清楚要省的是哪块钱。一轮对话里,发给大模型的请求由两部分组成:一是对话内容(系统提示、历史消息、工具返回的结果),二是工具清单(每个工具的名字、用途描述、参数定义,也就是 schema)。这道题只管第二块——工具清单这块怎么省。对话内容那块怎么省是本类第 5 题的事。

关键认知:工具清单是稳定前缀的一部分。它在一次会话里绝不增删、绝不改动,每一圈调模型时原封不动重发一遍。好处是它能被 KV-cache 命中、不重复计费推理;但坏处是它始终占着上下文窗口的固定一块,工具越多这块越大,挤占的是真正该留给对话和数据的空间。所以"工具描述写得越厚越好用"和"常驻块要尽量薄"是直接打架的。

核心思路:把工具分三档,厚文档挪到"按需"那一档

解法是不把所有工具平等对待,而是分成三组(组的成员在一次会话里固定不变):

  • 核心组(完整 schema):高频用的数据工具 + 控制关键的工具。这些给完整的参数定义常驻,但把冗长的用途说明换成一句精炼的"触发描述"(brief),既能直接调、又不臃肿。事实卡列的核心组是:查行情、查财报、查知识库、查用户记忆、装载技能方法论、提议升级深度研究这几个。
  • 延迟组(瘦条目):低频工具。只露一行"瘦标签"——名字 + 一句话触发描述 + 必填参数的名字和类型,把可选参数、枚举取值、示例、硬约束统统剥掉。一个瘦条目大约 30–60 token(量级估计来自设计文档),比完整 schema 薄一大截。
  • search_tools(殿后一个内置工具):一个"按需取文档"的工具。模型想用某个延迟工具又不确定怎么填参数,就调它,把目标工具的完整使用文档(参数 schema + 硬约束 + 示例 + 何时用/何时不用)检索出来。

厚文档为什么能"零常驻"?因为 search_tools 检索回来的完整文档是以工具返回结果(tool_result)的形式追加进对话消息的——它进的是"对话内容"那一块,而且是 append-only、只在用到时才出现。它完全不碰工具清单那一块,所以不会破坏 KV-cache 的稳定前缀。这样一来,描述可以写得要多厚有多厚(放进按需文档里),而常驻块只付一行瘦标签的钱。一对矛盾就这么解开了。

瘦条目为什么不能是"空壳"

有个反直觉的实测教训:延迟组的瘦条目,参数部分不能写成空的(空 properties)。冒烟测试里发现,如果瘦条目连必填参数名都不给、参数是个空对象,模型干脆绕开这个工具不调——它觉得"这工具我不知道怎么用,算了"。所以瘦条目必须保留必填参数的名字和类型,让模型能直接试着调一次;那些细节(可选参数、枚举、约束)才推给 search_tools 按需取。这是"薄到能省钱"和"薄到模型还认得它是个能用的工具"之间的那条线。

裸调自纠:模型直接调延迟工具调错了,怎么接住

模型不一定老老实实先查文档。它可能看着瘦标签就直接调延迟工具(裸调),结果参数填错了。这时系统的处理是:派发器拿真实的完整 schema去校验,校验失败 → 在报错信息后面追加一句指引"可以调 search_tools('某工具') 获取参数文档" → 下一圈模型就自己去查文档、补全参数再调一次。整个回路不需要人工兜底,模型在错误反馈里自己学会了正确用法。

最后,这套机制还配了一条增长纪律:加新能力前先问它是哪一类——只有"新数据源"才配占一个工具名额;"方法论"进技能(约 100 token 的元数据常驻,正文按需装载);"确定性计算"写成技能脚本(零工具名额)。这跟技能的渐进披露(元数据常驻 + 正文按需)是对称结构,本题只聚焦工具、不展开技能,技能那条线见本类第 3 题。

Q7

用户在 agent 跑到一半插话,你怎么做到不破坏状态?讲讲 steering(Redis List)和 turn 原子语义。

★★★★★
插话 steering Redis List vs pub/sub turn 原子性 FIFO 队列 取消 vs 插话

🎯 考察点分析

这道题在探一件最容易翻车的事:并发改写共享状态。agent 正在一圈圈地「想 → 调工具 → 看结果」,这时用户在对话框里又敲了一句话(比如「别看区域酒,只看高端白酒」)。这句话从一个完全独立的 HTTP 请求进来,而 agent 正在另一个进程里跑着、还在往前端吐字。面试官想看的是:你有没有想清楚这句插话什么时候、在哪个安全点被读进来,读进来之后怎么动状态才不会把正在进行的这一轮搞坏。这是典型的「两个执行流碰同一份数据」问题,工业界的事故大半出在这里。

  • 追问:插话信号为什么走 Redis List 而取消信号走 pub/sub?同样是「外面给跑着的 agent 递个信号」,凭什么用两种不同的原语?
  • 追问:插话到达时,这一圈大模型已经决定了要调三个工具,你是让它把工具跑完再读插话,还是当场作废?作废的话,大模型协议里「assistant 发起的每个 tool_call 都必须有一条对应的 tool 结果消息」这条红线你怎么守住?
  • 追问:「turn 原子」到底原子在哪?如果 agent 跑到第五圈崩了,中间那四圈的状态去哪了?用户点「重试」会发生什么?
  • 追问:你这套占位结果会不会污染「连续失败就熔断」那道闸?为什么不会?

📚 原理讲解

先把背景对齐。一次完整的「用户问一句 → agent 转好几圈 → 给出最终答复」,我们叫一个 turn(一轮)。agent 在一个 turn 内部会循环很多圈:每圈调一次大模型决定干啥、执行一批工具、把结果喂回去再转下一圈。插话(steering)就是:用户在这个 turn 还没跑完时,又补了一句话,希望并入当前这轮、改变 agent 接下来的走向——而不是等它跑完、当成下一个全新问题。

第一层:为什么插话用 Redis List,取消却用 pub/sub

这是全题最值钱的判断。两个信号看起来都是「外面往跑着的 agent 递个东西」,但对「丢不丢得起」的容忍度天差地别。

pub/sub(发布订阅)是「最多送达一次」:发的那一瞬间,如果没人正趴在频道上听,这条消息就永远没了。问题是——agent 在流式吐字的那几秒里根本不在听频道(它在一圈一圈跑循环、在往前端推 token)。用户偏偏最爱在这几秒里插话。如果用 pub/sub,这句插话就当场蒸发了。

而插话的语义要求是 「必须并入当前 turn,一句都不能丢」。所以它得用 Redis List 这种持久化队列:用户那条话先 LPUSH 进队列存着(不管 agent 此刻在不在听),agent 跑到圈与圈之间的安全边界时,主动 RPOP 把队列里攒着的全部取出来。存着 + 主动取 = 必达,绝不漏。

取消为什么反而可以用 pub/sub? 因为取消「丢得起」——万一这次取消信号没被听到,用户看 agent 还在转,再点一次取消就是了,代价是多等一两秒。插话丢了却补不回来:用户以为自己改了方向,agent 却照旧在错方向上烧钱跑完。丢失容忍度不同,就该分用两种原语,而不是图省事一刀切。这是「按可靠性需求选原语」的典型决策。

顺带说一个常被忽略的细节:LPUSH(从头进)配 RPOP(从尾出)= FIFO 先进先出,先到的插话先并入,顺序不乱。队列 key 是 chat:steer:{task_id},每个 turn 一个全新的 task_id,带 1 小时 TTL——这一点在最后一层会解释为什么重要。

第二层:两个检查点,各管一种插话

光有队列还不够,关键是 在循环的哪几个点去 RPOP。我们在一圈里放了两个检查点,各管一段时间窗里到达的插话:

  1. 圈首检查点:管「上一圈的工具批正在执行的那几秒里」到达的插话。工具跑完、要进新一圈时,先把这期间攒的插话取出来并入。
  2. 分发前检查点:管「本圈大模型已经决定好要调哪些工具、但还没真正派发执行」的那个瞬间到达的插话。这是后来专门补的一个点。

为什么要补第二个点?设想用户的插话是「改方向」型——大模型这一圈刚决定要去查五份区域酒的财报,用户此刻说「别看区域酒」。如果只有圈首检查点,这五个工具会先吭哧吭哧全跑完(几秒 + 真金白银的 token),下一圈圈首才读到插话,发现「白跑了」。加上分发前检查点后,延迟从「整整一圈」缩到「当前这次大模型流」那一小段,而且立省一整批已经不需要的工具。

第三层:分发前插话到达,怎么「取消批 + 重规划」还不破协议

这是最考验功底的地方。分发前检查点发现有插话时,本圈那批工具一个都不执行了。但这里埋着一条大模型的协议红线:assistant 那条消息里如果发起了 N 个 tool_call,那么接下来的消息里每一个 tool_call_id 都必须配一条 tool 结果消息,缺一条下次请求就报错。工具明明没跑,哪来的结果?

解法是给每个被取消的工具补一条占位结果,内容是固定一句话:「用户插话,本轮工具未执行,请结合新指令重新决定」。这样既守住了「每个 id 都有 tool 消息」的红线,又如实告诉大模型「这批没跑、你重新想」。然后把用户的插话作为一条新的 user 消息追加到消息列表尾部,continue 回到圈首,让大模型结合新指令从头决定这一圈干啥。

第四层:为什么这套操作「不破坏状态」

核心在一句话:消息列表是 append-only 的单一真相,插话只往尾部追加,从不回改任何已有消息。插话进来无非两个动作——尾部追加一条 user 消息、给被取消的工具补几条占位 tool 消息。已经存在的消息一个字都不动。所以不存在「两个执行流改同一个字段打架」的经典并发坑。

还有个精妙的不变量:占位结果不进台账(ledger)。台账只由真正的工具派发(ToolHub.dispatch)来记。占位结果是循环自己造的、绕过了派发,所以它不会被计入「连续失败次数」,也就不会误触发「连续多次失败就熔断」那道闸(那道闸见本类第 4 题)。如果占位被当成「失败」记进台账,用户多插几句话就可能把 agent 误熔断——这个坑被这条不变量挡住了。
第五层:turn 原子语义——崩了就整轮重来,不留半拉子

最后回答「turn 原子」。原子的意思是:一个 turn 要么完整跑完落库,要么就当它没发生过,中间那些圈的状态不持久化、崩溃即弃。具体三条:

  • 取消:已经流到前端的文字会落库,但只标成「partial(半截)」仅供展示,不是恢复点——下次不会从这半截接着跑。
  • 重试:整个 turn 从头重跑。输入是「原始那句 user 消息 + 这个 turn 期间并入的全部插话」。这里有个便宜:工具结果有缓存,重跑时工具大多缓存命中,真正要重新花钱的只有大模型调用本身。
  • 不留中间态:循环跑到第五圈的那个内部状态对象,根本不写库,进程崩了就丢。这恰恰是「原子」的实现方式——没有半拉子状态可供恢复,自然就不会从一个不一致的点接着跑。

这也回答了「为什么不打断当前 turn / 重启对话」里那个最隐蔽的坑:因为 steer 队列的 key 带着 task_id、每个 turn 一个新 key、还有 1 小时 TTL,所以取消之后队列里万一残留的插话会自然过期、绝不会泄漏到下一个 turn。业界有名的「插话串台」事故,根源往往是跨 turn 复用同一个队列——我们每 turn 换新 key,从结构上就不复用,这类问题压根不存在。

💻 示例讲解

先看写读两端怎么用 List 凑出「不可丢 + FIFO」。写端在那个独立的 HTTP 请求里,读端在 agent 的循环里:

# 写端(独立 HTTP 请求收到用户插话):LPUSH 存着 + 刷 TTL,不管 agent 在不在听
async def push(self, task_id, message):
    key = f"chat:steer:{task_id}"        # 每个 turn 一个新 key,1h TTL
    await self._redis.lpush(key, message.encode())   # 头插
    await self._redis.expire(key, 3600)              # 每次写都刷,turn 内不过期

# 读端(agent 循环里):RPOP 循环,把攒着的全部尾取出来 = FIFO
async def pop_all(self):
    out = []
    while True:
        raw = await self._redis.rpop(self._key)   # 尾取
        if raw is None:                            # 空了就停
            break
        out.append(raw.decode())
    return out                          # LPUSH 头进 + RPOP 尾出 = 先到先并入

再看循环主体里那两个检查点,重点是分发前那个「取消批 + 重规划」怎么守住协议红线:

while True:
    # 检查点一(圈首):并入「上一圈工具执行期间」到达的插话
    for msg in await self._steer.pop_all():
        state.messages.append({"role": "user", "content": msg})   # 只往尾部追加

    step = await self._llm.stream_step(messages, tools)   # 调一次大模型
    state = apply_step(state, step)

    if not step.tool_calls:          # 大模型不再要工具 → 自然收尾(见本类第 4 题)
        return state

    # 检查点二(分发前):大模型已决定工具、但还没派发执行 —— 此刻有插话?
    steers = await self._steer.pop_all()
    if steers:
        # 给每个本该执行的工具补「占位结果」,守住协议红线:
        # assistant 发起的每个 tool_call_id 都必须有一条 tool 消息,缺一条下次就 400
        interrupted = [_steer_interrupted_result(c) for c in step.tool_calls]
        state = apply_results(state, interrupted, step.tool_calls)  # 折叠 tool 消息
        for msg in steers:
            state.messages.append({"role": "user", "content": msg})  # 并入插话
        continue        # 原工具批一个没跑,回圈首让大模型结合新指令重新决定

    results = await self._tool_hub.dispatch(step.tool_calls, state)  # 才真正派发
    # 注意:占位结果走的是上面那条 apply_results 旁路,不经 dispatch,
    #       所以不记台账 → 不污染「连续失败」计数 → 不会误触发熔断闸

推演:用一个真实场景算笔账。用户问「帮我看看白酒板块」,agent 第三圈刚决定要并发查 6 家区域酒的财报(假设每个工具约 1.5 秒、整批约 1.5 秒墙钟 + 一笔不小的 token),就在这 1.5 秒的窗口里用户插话「区域酒别看了,只盯高端白酒」。若只有圈首检查点:这 6 个查询全跑完、结果喂回大模型、再转一圈才读到插话——整整一圈白烧 + 6 次工具调用白做。加上分发前检查点:插话在「大模型刚出 tool_calls、dispatch 之前」就被抓到,6 个工具一个都不发,直接给 6 条占位 + 并入插话 + 回圈首重想,代价仅为多花一次大模型调用(重新决定该查谁),省下整批工具的钱和时间。代价我们也认:如果插话是「追加」型(「顺便也看下负债率」),这套逻辑同样会把刚决定的 6 个工具批取消、多花一轮大模型重新决定——结果正确,只是多一次调用,因为我们没有便宜的办法在 dispatch 前区分「改方向」和「追加」这两类插话。这是清醒认下的折中,不是没看见。

📌 总结

  • 插话 vs 取消,按「丢得起吗」分原语:插话必须并入当前 turn、一句不能丢,用 Redis List 持久化(写端 LPUSH+TTL,读端 RPOP 循环 = FIFO),agent 不在听也存着;取消丢得起(用户会再点一次),才敢用「最多一次」的 pub/sub。
  • 两个检查点各管一段窗口:圈首管「上一圈工具执行期间」的插话;分发前管「大模型已出工具、还没派发」的插话。后者把改方向型插话的延迟从「整圈」缩到「当前大模型流」,立省一整批已不需要的工具。
  • 取消批 + 重规划还不破协议:被取消的每个工具补一条占位 tool 消息(守住「每个 tool_call_id 必有 tool 消息」红线),并入插话、continue 回圈首重想;占位走旁路、不进台账,所以不污染「连续失败熔断」那道闸(见本类第 4 题)。
  • 不破坏状态 = append-only:消息列表是单一真相,插话只往尾部追加、从不回改已有消息,从结构上避开了「两个执行流改同一字段」的并发坑。
  • turn 原子:中间圈状态不持久化、崩溃即弃;重试是整 turn 从头重跑(原问题 + 全部并入的插话),工具走缓存命中、真实重花只有大模型调用;每 turn 换新 key + TTL,残留插话自然过期、不跨 turn 串台。

Q8

用原生 function calling 而不是框架的 tool 抽象,你踩过哪些坑?(qwen3 关思考、tool_call 参数合法化、非 deepseek 模型兼容)

★★★★☆
原生 function calling qwen3 关思考 参数合法化 流式分片拼接 cassette 真录

🎯 考察点分析

这道题是上一题(为什么退役框架)的"还账"环节。退役框架之后,模型那一层"脏活"就得自己接——面试官想确认:你是真的把协议跑通过、知道每个模型的怪脾气长什么样,还是只在 PPT 上喊"裸接更可控"。能讲出具体的报错码、具体哪个字段坏了、怎么发现的,才说明手是脏的。

  • 追问:所谓"框架会掩盖协议细节",到底掩盖了哪些?你举一个框架替你扛了、你裸接后得自己扛的具体例子。
  • 追问:你这些兼容补丁,是看文档加的还是跑出来加的?如果是跑出来的,你拿什么环境复现?为什么单元测试里的 mock 抓不到?
  • 追问:给 qwen3 加的 enable_thinking=false、给所有模型加的参数合法化——你怎么保证这些补丁不会反过来把原本好好的 deepseek 搞坏?
  • 追问:既然这么麻烦,当初为什么不干脆只支持 deepseek 一个模型,或者退回去用框架?

📚 原理讲解

先说清楚"原生 function calling"是什么意思。OpenAI 定了一套通用协议:你在请求里塞一个 tools=[...] 把工具的名字、参数长啥样告诉模型;模型如果决定调工具,它回的那一坨数据里 finish_reason 会是 tool_calls,并且带上"调哪个工具、参数是什么"。现在所有主流国产模型(deepseek、qwen3、…)都兼容这套协议。我们的对话引擎就是直接对着这套协议收发——自己拼请求、自己读模型回的字段,中间不夹 LangChain / LangGraph 那层"工具抽象"。

框架的工具抽象帮你做三件事:统一写工具定义、自动把模型回的 tool_call 解析成对象、抹平不同厂商的协议差异。听起来很香。但代价是:这三件事一旦出 bug,你看到的是框架内部的报错,真正的协议细节被它包在里面,你既看不见也调不动。我们退役框架(见本类第 3 题),换来的是控制流百分百自有——代价就是这层"抹平差异"得自己来。下面三道坑,全是这层抹平里漏出来的。

坑一:qwen3 是"思考模型",不关思考直接 400

qwen3 这类模型默认会先"想一段"(reasoning)再回答。问题是:在阿里云 dashscope 这个端点上,如果你用 function calling 又没显式把思考关掉,它直接回你一个 400 Bad Request——请求都进不去。deepseek 没这毛病,所以同一套代码,从 deepseek 切到 qwen3 当场就栽。

修法很轻:发请求前看一眼模型名,如果是 qwen3 开头,就在请求体里塞一个 extra_body={"enable_thinking": False};不是 qwen3 就什么都不塞。这个"不是 qwen3 就不塞"很关键——别的模型不认这个参数,你硬塞反而把它们弄 400。一个补丁,不能为了救一个模型把另一个搞坏。

坑二:回灌的 tool_call 参数必须是合法 JSON

多轮对话里,上一轮模型调过的工具调用,这一轮要原样塞回消息历史给模型看(它得知道"我刚才调了啥、拿到啥结果")。工具调用里有个 arguments 字段,是个 JSON 字符串。deepseek 很宽松:就算这个字符串是空的("")它也照收。qwen3 严:你把空串或者半截坏 JSON 回灌进去,它认为这不是合法 JSON,又是一个 400。

修法:回灌之前过一道"合法化"——逐个检查每个工具调用的 arguments,只要不是合法 JSON(空串、坏串都算),就兜底成 "{}"(一个合法的空对象),其余消息原样不动。妙处在于:合法 JSON 谁都收,所以这道补丁对 deepseek 也完全无害——它本来就能收合法 JSON。这就是"补丁要对所有模型安全"的范例。

注意区分两个不同环节(见本类第 4 题的"工具签名校验")。那边管的是"模型把工具名拼错了、参数对不上签名"——属于语义校验,放行后交给 schema 判。本题这道合法化管的是更底层的"这串字符还算不算 JSON"——属于回灌请求前的格式兜底。一个判签名、一个保 JSON,别混。
坑三:流式续片里 name="" 把已拿到的工具名冲掉了

这道是最阴的,也最能说明"为什么必须真录"。模型回工具调用时是流式分片的:工具名、参数会拆成好几个小片陆续吐出来,我们这边有个状态机(StreamAssembler)按片的序号(index)一片片攒起来。契约是:工具的 id 和 name 只在该工具调用的第一片里携带,后面的续片只补参数。

坑在哪?qwen 的续片里,name 字段不是省略、也不是 null,而是给你一个空串 ""。如果拼接逻辑写成"只要字段不是 null 就拿来覆盖",那第二片的 "" 就会把第一片攒到的真工具名冲掉——结果下游拿到一个空名字,根本不知道该调哪个工具。修法是把判定从"不是 null"改成"是真值"(空串视为假),只让非空的片更新槽位。这一个字的区别(is not None → 真值判断),不录真 API 永远想不到。

方法论硬骨头:这个 bug 用 mock 测试一辈子也复现不出来——因为 mock 是你自己捏的,你不会捏出一个"name 是空串而非 null"的续片,你压根不知道协议会这么干。只有把真 API 的响应录成 cassette(把真实往返存下来当回归基线),再回放,才暴露得出来。这也是项目里一条铁律:谈某个接口的行为,必须先录 cassette 核实,不能只看文档拍脑袋。

顺带一提流式还得拿两样东西:一是流式 usage——开 stream_options={"include_usage": True},流结束时能拿到这轮花了多少 token,喂给预算闸;二是缓存命中数——从 usage 里的 cached_tokens 读出来,知道有多少 token 命中了 prefix cache(这块省钱机制见本类第 5 题)。reasoning 和正文是两条独立的增量流,而且 assistant 消息回灌时绝不带 reasoning 字段——这是状态层的红线,带了会污染下一轮上下文。

💻 示例讲解

把三道坑的修法浓缩成发请求前的两道"垫片"+ 收响应时的一道"防覆盖",看逻辑怎么走(伪代码,真实函数名做锚点):

# ── 发请求前:两道兼容垫片 ──────────────────────────
def extra_body_for(model):
    # 坑①:qwen3 是思考模型,不关思考会 400;别的模型不认这参数,不能塞
    if model.startswith("qwen3"):
        return {"enable_thinking": False}
    return {}                       # 非 qwen3 → 什么都不加

def sanitize_tool_args(messages):
    # 坑②:回灌的 tool_call 参数必须是合法 JSON,空/坏 → 兜底 "{}"
    for m in messages:
        for tc in m.get("tool_calls", []):
            args = tc["function"]["arguments"]
            if not valid_json(args):      # 空串 / 半截坏 JSON 都算不合法
                tc["function"]["arguments"] = "{}"   # 合法 JSON 谁都收 → 对所有模型安全
    return messages

# 发请求:垫片只在该加的地方加,deepseek 走过去等于无操作
kwargs = {"model": model, "messages": sanitize_tool_args(messages),
          "stream": True, "stream_options": {"include_usage": True}}
if extra_body_for(model):                 # 仅 qwen3 命中
    kwargs["extra_body"] = extra_body_for(model)

# ── 收响应时:流式分片防覆盖(坑③)────────────────────
slot = {"id": None, "name": None, "arguments": ""}
for frag in tool_call_fragments:          # 同一 index 的片陆续到达
    if frag.id:                           # 真值判断,不是 "is not None"
        slot["id"] = frag.id              # 空串 "" 是假 → 不覆盖,保住首片的真值
    if frag.name:
        slot["name"] = frag.name          # ← 坑③ 修在这:续片的 name="" 进不来
    slot["arguments"] += (frag.arguments or "")   # 参数跨片拼接

推演:设一轮对话从 deepseek 切到 qwen3。① 请求出门:extra_body_for("qwen3-...") 命中,塞 enable_thinking=false——不塞就是 1 次 400,整轮废掉。② 历史里有一个上轮的工具调用,arguments 是空串:sanitize 把它改成 "{}"——不改又是 1 次 400。③ 模型回 3 个流式片:第 1 片带 name="get_quote",第 2、3 片 name="" 只补参数。旧逻辑会被第 2 片的 "" 冲成空名→下游抽不到工具→这一轮静默调错。三道坑各拦一处,任何一道漏掉,这轮 qwen3 对话就崩在不同位置。而这三个补丁对 deepseek 全是"无操作或无害",所以一套代码两个模型都能跑。

📌 总结

  • 裸接的代价就是这三道坑:qwen3 不关思考 400、回灌参数空/坏 JSON 400、流式续片 name="" 冲掉真工具名。框架会把它们包起来掩盖,自己裸接才暴露——这正是退役框架后要自己付的账。
  • 补丁要"救一个不害另一个":enable_thinking 仅 qwen3 注入(别的模型不认),参数合法化对所有模型安全(合法 JSON 谁都收)。这是兼容垫片的设计纪律,不是顺手写写。
  • cassette 真录是不可替代的回归面:空串覆盖 bug 用 mock 永远复现不出来——你不会捏出"name 是空串而非 null"的片,因为你不知道协议会这么干。铁律:谈接口行为先录 cassette 核实,别只看文档。
  • 这些垫片服务于"模型可热切换":有了它们,对话引擎在非 deepseek 模型上不栽在厂商专属要求上;换模型只改配置,内核循环不动。
  • 区分环节别混:本题的参数合法化是"回灌前保 JSON 合法",与第 4 题的"工具签名校验"(判模型有没有拼错工具名/参数)是两回事;还留了降级口——原生 FC 不达预期可退 JSON 约束输出,循环及以上不动。

一句话速记:退役框架换来控制流主权,代价是模型协议的脏活自己扛——三道坑(关思考 / 参数合法化 / 流式防覆盖),靠真录 cassette 一个个抓出来填平。
