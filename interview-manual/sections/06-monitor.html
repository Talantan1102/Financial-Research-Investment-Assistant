06持仓监控引擎

持仓监控引擎是 AlphaScout 的第二根产品支柱:一边是后台不停扫描用户持仓的「daemon」,一边是用户早盘扫一眼的 dashboard。这一组题从「为什么选这个用例」切入,逐层深入到定时调度怎么靠 Celery + Redis + PostgreSQL 协作、海量原始公告如何被收敛成 5 类可读提醒,以及从一条行情/公告到「该不该标红」的完整判定链路是怎么搭起来的。读完你能讲清这套引擎的产品取舍与工程骨架。

Q1

"持仓监控"和"对话研究"为什么是一体两面的?当初为什么选这个用例而不是另一个?

★★★☆☆
产品决策用例选型护城河做减法

🎯 考察点分析

这道题表面问"为什么做这个功能",其实面试官想看你有没有产品判断力——一个工程师在一堆都能做的候选里,凭什么标准挑一个、砍其它的。大模型应用岗最怕的是"什么都能接、什么都想做",最后做出一个样样通样样松、还打不过通用大模型的东西。所以面试官在探三件事:

  • 追问 1:你说"一体两面",到底哪两面?是真的共用一套东西,还是事后硬凑的故事?——逼你说清后台引擎和用户界面共享了什么。
  • 追问 2:你拿什么标准选用例?这个标准后来变过吗?——好的候选会承认自己一开始用错了判据、后来推翻了,这比"一上来就对"更可信。
  • 追问 3:被你砍掉/推迟的那个候选,它哪里好?——如果你只会贬低替代方案,说明你没真比较过;能讲清"它其实能打赢 ChatGPT 但我还是没选它",才显出取舍的分量。
  • 追问 4:你怎么验证这个选择没选错?——看你有没有给自己定可证伪的验收门槛。

📚 原理讲解

先说"一体两面"。同一件事,站在两个视角看,长得完全不一样,但底下是同一套数据和同一台引擎,所以它不该被拆成两个功能,而是一个。

哪两面

企业视角(后台盯盘引擎):一个不停运转的后台程序(我们叫它 daemon,就是"常驻后台、自己定时干活、不需要你点"的进程),按固定节奏去扫你持有的每一只股票,看有没有大跌、出公告、披露财报这类"异动"。这一面用户根本看不见,它只管把"哪只股票出了什么事"标记出来。

用户视角(对话式异动解读):你早上打开 dashboard(看板),看到的是一行行"今天哪只票为什么动了"的人话解读,点开还能接着问"这事严重吗、要不要减仓"。这一面就是"对话研究"——但它研究的对象,正是后台引擎刚标出来的那些异动。

两面共用同一份持仓数据(你拿了哪些票、各多少)和同一台监控引擎(判断什么算异动的那套规则)。后台扫出来的结果,直接喂给前台让你追问;你追问产生的判断,又沉淀回这只票的上下文。所以把它们拆成两个用例是重复造数据、重复造引擎,合成一个才对——这就是"一体两面"。

为什么选它,而不是别的候选

最初挑用例用的"硬度测试"是一句话:这个用例能不能单独打赢通用大模型(ChatGPT)?用这把尺子量,被否决的主要候选"事件追踪"(给重大事件画时间线、再映射到 A 股相关标的)反而通过了——它能独立打赢。但作者后来推翻了这把尺子本身:真正的平台产品不需要每个用例都单独赢,它们要一起拼成一条投资 workflow(研究 → 买入 → 持有跟踪 → 卖出),整条 workflow 一起赢。在这条流水线里,持仓监控是把"持有"这段串起来的主轴。

换了尺子之后,持仓监控胜出有四条理由,事件追踪一条都不占优:

  • 数据护城河最深:"你具体持有哪些票、各多少仓位"这种数据,通用大模型原理上拿不到——这是质的差距,不是它算力大点就能补的;事件追踪靠的是中国市场标的映射,那只是"它没我细",是量的差距,迟早被追上。
  • 投资闭环关键:光有"研究买入"不完整,得加上"持有期跟踪、何时卖出"才是闭环。持仓监控补的正是后半段。
  • dogfood 频率最高:作者自己每天都用(早盘前扫一眼);事件追踪一年只在议息、重大新政这种时候用,约 8-12 次。差不多 30 倍的反馈循环差距——天天用的东西才打磨得出来。
  • 它是组件的宿主:个股研究、财报速读、报告追问这些小功能本身撑不起一个独立用例,但它们天然寄生在"看持仓"这个场景里。持仓监控一立起来,这些组件就有地方挂。

还有一条工程层面的互补:持仓监控引入了规则引擎 + 事件流这套新技术栈(详细架构见本类第 2、4 题),正好扩展了简历的技术覆盖面;而事件追踪用的检索 + 写作那套,跟已经做完的深度尽调高度重复,做了也是炒冷饭。

💻 示例讲解

用一段教学伪代码把"用什么尺子选用例"显式化。注意尺子换过一次,代码里把两版都留着对照:

# 9 个原始候选用例
candidates = ["深度尽调", "持仓监控", "事件追踪",
              "个股研究", "财报速读", "报告追问",
              "行业判断", "术语解释", ...]

# 旧尺子:每个用例单独能不能打赢通用大模型
def old_ruler(uc):
    return can_beat_chatgpt_alone(uc)   # 事件追踪在这里 == True

# 旧尺子的结论:推事件追踪(因为它单独能打)
#   —— 后来被推翻:平台产品不该这么挑

# 新尺子:它在「投资 workflow」里是不是主轴 + 四条加分项
def new_ruler(uc):
    score = 0
    score += data_moat(uc)        # 数据护城河:持仓数据通用模型原理上拿不到 → 最高分
    score += closes_loop(uc)      # 是否补全 研究→持有→卖出 的闭环
    score += dogfood_per_year(uc) # 自己一年用几次:每天≈365  vs  事件追踪≈10
    score += hosts_components(uc) # 是不是其它小组件的宿主
    return score

# 砍掉通用大模型的强项领域(做不过就别稀释定位)
def explicitly_drop(uc):
    return uc in ["行业判断", "术语解释"]

# 最终:用新尺子选出主轴,组件挂上去,强项领域显式砍掉
pillar = max([c for c in candidates if not explicitly_drop(c)],
             key=new_ruler)       # → "持仓监控"

推演:把"事件追踪"和"持仓监控"分别代入 new_ruler。dogfood 一项:持仓监控 ≈ 365(每天),事件追踪 ≈ 8-12(一年),光这一项就差约 30 倍的反馈频率。数据护城河一项:持仓数据是"原理上拿不到"(满分),事件追踪只是"映射得没我细"(可被追上)。两项一叠,持仓监控胜出。9 个原始候选最终被重新归成 3 个独立支柱 + 3 个寄生组件 + 2 个显式不做——这个"砍"的动作本身,就是简历上比"我又加了个功能"值钱的产品判断。

⚖️ 决策对比

维度我们的选择:持仓监控替代方案:事件追踪(被否决)
能否单独打赢通用大模型不一定(早盘解读它也会)能——这是它唯一明显占优的一项
数据护城河持仓数据通用模型原理上拿不到(质的差距)标的映射,只是"没我细"(量的差距,会被追上)
在投资 workflow 里的位置主轴,补全"持有→卖出"闭环离散信息源,不构成闭环
自己用的频率(dogfood)每天(约 365 次/年)一年约 8-12 次,反馈循环差约 30 倍
对其它组件的承载是个股研究/财报速读等的天然宿主离散,串不起组件
工程技术栈新引入规则引擎+事件流,扩简历覆盖面检索+写作,跟深度尽调高度重复

公允裁决:事件追踪并不是个糟糕的候选——恰恰相反,它是唯一一个"用最初那把尺子量能单独打赢通用大模型"的候选,在"显示技术深度"这件事上完全够格,所以它没被砍死,而是推迟到后续版本。它真正输的地方有两点:一是工程上跟已经做完的深度尽调用的是同一套检索+写作,做了是重复劳动;二是一年才用十几次,你根本没机会靠日常使用去打磨它。更深一层,这场对比的胜负其实不在两个用例本身,而在判据被换掉了——从"每个用例独立打赢 ChatGPT"换成"用例群一起构成 workflow、整体打赢"。尺子一换,占优项(单独能打)就不再是决定性的,持仓监控的护城河、闭环、高频这三项才浮上来。

📌 总结

  • "一体两面"不是修辞:后台 daemon 盯盘(企业视角)和 dashboard 异动解读(用户视角)共用同一份持仓数据 + 同一台监控引擎,拆成两个就是重复造轮子,所以合成一个用例。
  • 选型的尺子换过一次:从"每个用例能不能单独打赢通用大模型",换成"用例群一起拼成投资 workflow、整体打赢"——这一换才是真正的洞察。
  • 被否决的事件追踪并不弱,它恰是唯一"能单独打赢"的候选,输在跟深度尽调工程重复、且一年才用十几次(反馈频率差约 30 倍),所以推迟而非砍死。
  • 持仓监控四条胜因:数据护城河最深(持仓数据原理上拿不到)、补全投资闭环、自己每天用、还是其它组件的宿主。
  • 把"9 个用例的平台"改写成"3 支柱 + 寄生组件 + 显式砍掉通用模型强项"——"做减法的产品判断"比"做加法的工程能力"更值钱。

一句话速记:它不是"又一个功能",而是投资 workflow 的主轴;选它不是因为它能单独赢,而是因为换了把"整条流程一起赢"的尺子后,它的护城河、闭环、高频才显出来。

Q2

定时监控你用 Celery + Redis + PostgreSQL 怎么协作的?为什么需要一个独立的 worker 进程?

★★★★☆
CeleryRedisPostgreSQL异步架构调度

🎯 考察点分析

面试官想确认两件事:第一,你是不是真的理解"定时任务"和"耗时任务"是两个不同的问题,而不是把它们一锅炖在 Web 进程里;第二,你能不能把三个组件各自的职责讲清楚,而不是背"Celery 是分布式任务队列"这种官话。这道题的核心张力是:大模型调用慢(单次 30 秒以上),而扫描必须快——你怎么让慢的那部分不拖死快的那部分。

  • 追问:为什么不直接在 FastAPI 的请求里开个 asyncio.create_task 异步跑?省掉 Redis 和 worker 这一整套依赖,不是更克制吗?
  • 追问:worker 进程在跑详情卡的时候突然崩了,那条已经标红但还没生成详情卡的提醒会怎么样?会丢吗?
  • 追问:扫描任务和大模型任务你为什么要分成两条队列?合并成一条会出什么问题?
  • 追问:这套东西你怎么测?在测试里你总不能真等 30 分钟一轮的定时器吧?

📚 原理讲解

先说三个组件各干各的活,别把它们想成一个东西:

三者分工:谁触发、谁排队、谁干活、谁存数据

Redis 是中转站(broker)。它本身不干活,只负责存"待办任务清单"——谁把任务塞进来、谁来取走,都经过它。顺带它也存着定时器自己的调度状态。Celery 是干活的框架,它分成两个角色:一个叫 beat 的进程专门看表,到点就往 Redis 里塞一条任务;一群叫 worker 的进程从 Redis 里抢任务、真正执行。PostgreSQL 是唯一的数据落地处——监控相关的 4 张表(运行记录、信号、提醒、通知)再复用主库已有的持仓表,早期监控数据是独立的 sqlite,后来全部迁进了主库,这样持仓数据和监控数据在同一个事务里,不会出现两套库对不上的尴尬。

部署起来到底跑几个进程

真正跑起来是 4 类进程加一个 Redis:① Web 进程(FastAPI),只处理 HTTP 请求,它有一条铁律——绝不直接调大模型;② beat 进程,定时把任务塞进队列,它不执行任务,只负责"按点投递";③ worker 进程,真正执行任务,并发设成 4(同时跑 4 个任务);④ Redis,任务队列。beat 和 worker 是两个独立进程,这点很关键——一个负责"什么时候发",一个负责"怎么干"。

为什么非要一个独立的 worker 进程

这是这道题的题眼。扫描标红的那一刻,我们要给用户预生成一张"异动详情卡"——这一步要调大模型写解读,耗时 30 秒以上。问题来了:盘内扫描是每 30 分钟一轮(周一至周五 9 点到 15 点之间每半点触发),一轮要扫一批股票。如果详情卡的大模型调用在扫描进程里同步做,那它就会把整轮扫描卡死在那里干等——本来该 1 分钟扫完的一轮,可能因为几只股票标红、每张卡 30 秒,被拖到几分钟甚至卡穿到下一轮。所以做法是:扫描发现标红,立刻写一条 alert 记录、立刻返回;详情卡这件慢活,甩成一条独立任务丢进队列,让独立的 worker 进程慢慢去补。扫描和写作彻底解耦,快的归快,慢的归慢。

失败容忍不是运气,是配出来的

独立 worker 还带来一个白送的好处:抗崩。worker 配了 acks_late(任务跑完才告诉 Redis"这条我处理完了",中途崩了 Redis 会把它重新派给别人)、详情卡任务最多自动重试 2 次、worker_max_tasks_per_child=100(每个子进程干满 100 个任务就重启,防大模型库的内存泄漏越积越多)、prefetch_multiplier=1(一次只抓一条任务,崩了不会连累一串预取的任务一起丢)。更朴素的兜底是:就算 worker 整个挂了,30 分钟后下一轮扫描会自动把漏掉的重新入队,失败成本极低;另外 16:30 收盘后还有一次全量扫描,专门捡盘中漏掉的。

💻 示例讲解

看一眼"扫描"和"详情卡"两个任务怎么分工。注意扫描任务只做轻活、把重活甩出去:

# ① 定时任务:每 30 分钟一轮,beat 到点把它塞进 default 队列
#    soft_time_limit=300 / time_limit=600 是给整轮扫描兜的超时
@celery_app.task(name="detection_cycle", soft_time_limit=300, time_limit=600)
def detection_cycle():
    alert_ids = []
    for code in 待扫股票:                 # 这批扫描全是轻活:查数据、算阈值
        level, signals = 跑信号检测(code)  # 没有大模型,批量并发地扫
        if level in (黄, 红):
            alert = 写一条提醒记录(code)    # 标红 → 落库,立刻返回
            alert_ids.append(alert.id)
    commit()                              # 先把提醒落定

    # 关键:只在提交成功后,才把"慢活"甩进队列。绝不在这里同步调大模型,
    # 否则 30 秒/张的详情卡会把整轮扫描卡死。.delay() = 丢进 Redis 就走人
    for alert_id in alert_ids:
        generate_detail_card.delay(alert_id)

# ② 大模型任务:被路由到独立的 llm 队列,worker 慢慢消化
#    acks_late=True       跑完才确认,崩了 Redis 自动重派,不丢
#    max_retries=2        失败自动重试 2 次,retry_backoff=True 指数退避(默认 1s 起翻倍)
#    rate_limit="5/m"     每分钟最多 5 个,防把 API 额度烧爆
@celery_app.task(name="generate_detail_card",
                 acks_late=True, max_retries=2, rate_limit="5/m")
def generate_detail_card(alert_id):
    alert = 取提醒(alert_id)
    if alert is None or alert.已就绪:     # 重派可能让同一张卡跑两次
        return "skip"                     # 幂等:已就绪的不重花 30 秒大模型钱
    报告 = 调大模型写详情卡(alert)        # 这一步 30 秒+,所以它必须在 worker 里
    alert.写回报告并标就绪()

推演:某轮扫描覆盖 200 只股票,其中 3 只标红。detection_cycle 在几十秒内扫完、写下 3 条 alert、立刻返回,这一轮扫描结束。同时 3 条 generate_detail_card 进了 llm 队列,worker 以 5/分钟的限速逐张调大模型,每张 30 秒+,大约 1.5 分钟把 3 张卡补齐。假如其中一张第一次调大模型超时,它会按指数退避(默认 1s 起翻倍)自动重试,最多 2 次;假如 worker 在补第 2 张时整个崩了,acks_late 让那张卡的任务回到队列被重派——而最坏情况也不过是 30 分钟后下一轮扫描兜底。扫描的快和详情卡的慢,被这条队列彻底隔开了。

⚖️ 决策对比

维度我们的选择(Celery + Redis 独立 worker)替代方案(在请求/Web 进程里定时,如 asyncio.create_task 或 APScheduler)
新增依赖要装 Redis、引 Celery、多跑 2 类进程零新依赖,纯进程内,最克制
慢任务隔离大模型调用在独立 worker,扫描发完即走,互不阻塞详情卡和扫描挤同一进程,30 秒大模型会拖慢 Web 响应或扫描循环
重启不丢任务在途任务存在 Redis,进程重启后被重新派发进程一重启,内存里在途的详情卡任务直接蒸发
失败重试 / 抗崩acks_late 自动重派 + autoretry 2 次,框架级保障得自己手写 try/重试/补偿,容易写漏
可观测性队列长度、任务状态、重试次数都能查只有日志,任务跑到哪了基本黑盒
横向扩展多开几个 worker 就能分担,worker 集群可扩受单进程上限,扩不动

公允裁决:替代方案确实更克制——这个项目的默认就是"能不加依赖就不加",asyncio.create_task 零成本、APScheduler 也就一个轻量调度库,对一个"30 分钟跑一轮、量不大"的个人作品而言,功能上完全够用。我必须诚实承认:上 Celery + Redis 是违背了项目"极简优先"默认的。仍然这么选,理由有两条,都站得住:其一,在途任务不能丢——详情卡是给用户看的承诺,进程一重启就蒸发掉、还只有日志没法观测,这种半残状态不可接受;其二也是更主要的——这是个面向求职的作品集,工业级的 broker + worker 集群 + 重启不丢,是 LLM 应用里面试官看得见的技术深度,而后续 roadmap 本来就要装 Redis(给记忆子系统用),与其晚装不如提前到这里一起做。所以它不是过度设计,是一次"提前支付、顺便展示深度"的有意识取舍。

🖼️ 图解

📌 总结

  • 三者分工一句话:Redis 是中转站(存任务队列)、Celery 负责定时触发与执行、PostgreSQL 是唯一数据落地处(监控 4 表已从独立 sqlite 全迁进主库,再复用主库持仓表)。
  • 独立 worker 的根本理由:详情卡要调大模型、单次 30 秒以上,在扫描进程里同步做会把 30 分钟一轮的扫描卡死;甩进独立 worker 队列,扫描标红即返回、详情卡异步补,快慢解耦。
  • 抗崩是配出来的:acks_late 跑完才确认(崩了重派)+ 自动重试 2 次 + 满 100 任务重启子进程防内存泄漏 + 一次只抓 1 条不丢一串。
  • 两条队列各管一摊:default 跑短的扫描(无大模型、并发),llm 跑长的详情卡(限流 5/分钟防烧 API 额度)。
  • 测试分层守护:轻量测试让任务在进程内同步跑(task_always_eager)、只验逻辑;重测试用 testcontainers 真起 Redis 和真 worker、验 acks_late 重派这类只有真 worker 才会触发的行为。

一句话速记:Redis 排队、beat 看表、worker 干活、PG 存数据;把 30 秒的大模型甩给独立 worker,扫描才能快进快出、还顺手白得了重启不丢。

Q3

原始公告那么多,你怎么把它们分成 5 类、又怎么从一条原始公告触发一条用户读得懂的提醒?

★★★☆☆
公告分类大模型分类器结构化输出信号触发噪声控制

🎯 考察点分析

这题面试官想看的不是"你会不会调用大模型分类",而是一个更现实的工程判断:A 股一只票一周能出十几条公告,绝大多数是噪声(改个章程、开个股东会),候选人能不能在"什么值得打扰用户"上做出克制的取舍,并且把"分类"和"给用户讲人话"这两件事用一条链路省下来。

  • 追问 1:为什么是大模型当分类器,而不是关键词匹配("立案"两个字一搜不就行了)?
  • 追问 2:分完类怎么决定标不标红?阈值是怎么定的,凭什么是 0.8 / 0.5?
  • 追问 3:分类的"理由"和给用户看的详情卡文案是什么关系?是各跑一次大模型,还是同一次?
  • 追问 4:减持、回购这些你为什么不报?漏报了用户骂你怎么办?

📚 原理讲解

先说为什么只挑 5 类。公告是个长尾,真正"我作为持仓人得马上知道"的就那么几种。我精选了 5 类:财报披露(季报/半年报/年报)、业绩预告(预增/预减/预亏)、ST/退市风险警示、重大资产重组/并购、重大监管处罚/立案调查。代码里就是一个枚举,5 类再加一个"其他"兜底,一共 6 个值。剩下的减持、回购、高管变动、股东大会决议、大宗交易,全部归到"其他"——这是显式选择漏报,不是忘了。它们信噪比中等、要做复杂过滤才好用,我先不碰,真有人痛了再加。

分类为什么不用关键词,而是让大模型当分类器

关键词匹配看着便宜,实际很脆。一条"关于撤销退市风险警示的公告"里也有"退市"两个字,但它是利好;一条立案调查可能标题里压根没"处罚"。公告标题写法五花八门,靠正则永远在打补丁。所以我的做法是:拉这只票近 7 天的公告,把标题加正文前 500 字喂给一个 fast 档大模型,用一个结构化 schema 强制它吐出三个字段——{类型, 分数 0~1, 一句话理由}。schema 这里很关键:它逼模型必须从 6 个枚举里选一个、分数必须落在 0 到 1、理由必须给一句话,不会返回一坨自由发挥的文字让我再去解析。

从"一条公告"到"一条人话提醒":理由字段喂进详情卡的写作

这里要把链路讲准,别夸大。模型那个"一句话理由"字段,除了给分类当解释,还会随这条信号一起带进异动详情卡写作器(Writer)的 prompt 上下文,作为写详情卡的输入。注意:详情卡本身仍是一次独立的大模型调用——也就是第 2 题里那次耗时 30 秒以上的异步写作(Writer 拿 alert 用一个单独的 schema 产出 100-200 字摘要 + 叙事 + 建议)。所以省下来的不是"详情卡那次调用",而是"为了写提醒文案再单独跑一次分类":分类只跑这一次,它的判定结论和理由直接复用进后续写作的输入,口径对齐、不用二次分类。

判定:从分数到红黄绿

拿到 {类型, 分数} 之后,判定规则很简单:类型是"其他"直接判绿灯(不打扰);属于 5 类里任意一类,再看分数——分数 ≥ 0.8 判红,0.5 到 0.8 之间判黄,低于 0.5 还是绿。只有黄和红会真的在看板里标红、并提前把详情卡预生成好。分数的语义在 prompt 里也讲清楚了:0 是中性披露(常规季报没大变化),0.5 是中等关注(业绩预减、重组初步意向),0.8+ 是重大利空(财报巨亏、ST、立案、并购终止)。

💻 示例讲解

下面是这条规则的骨架,去掉了异常分支,只看主干怎么走:

# 公告类型:5 类有意义的 + 1 个"其他"兜底(枚举共 6 值)
class 公告类型(枚举):
    财报披露 = "财报披露"           # 季报/半年报/年报
    业绩预告 = "业绩预告"           # 预增/预减/预亏
    ST退市 = "ST/退市风险警示"
    重组并购 = "重大资产重组/并购"
    监管处罚 = "重大监管处罚/立案调查"
    其他    = "其他"               # 减持/回购/高管变动 → 全归这里,不报

# 让模型必须吐出这三件套,而不是一段自由文字
class 分类结果(结构化Schema):
    类型: 公告类型
    分数: float   # 约束 0~1
    理由: str     # 一句话 —— 这句话稍后直接进详情卡

async def 评估(标的):
    # 1) 只看近 7 天的公告,拉不到就绿灯收工
    公告表 = await 拉公告(标的.代码, 近7天)
    if 公告表.空: return 绿灯("近 7 天无公告")

    # 2) 取最近一条,标题 + 正文前 500 字喂给 fast 档模型
    最近 = 公告表.第一条
    正文 = 最近.内容[:500]
    结果 = await 模型.结构化输出(           # 一次调用,拿到 {类型, 分数, 理由}
        标题=最近.标题, 摘要=正文,
        档位="fast", schema=分类结果,
    )

    # 3) "其他" → 不打扰;不为不存在的需求买单
    if 结果.类型 == 公告类型.其他:
        return 绿灯("非 5 类公告:" + 结果.理由)

    # 4) 5 类之内,纯看分数分流红黄绿
    if   结果.分数 >= 0.8: 级别 = 红
    elif 结果.分数 >= 0.5: 级别 = 黄
    else:                  级别 = 绿

    # 理由字段随信号一起带出 → 稍后喂进详情卡 Writer 的 prompt 输入(无需二次分类)
    # 详情卡本身仍由 Writer 另起一次独立的大模型调用生成(见第 2 题那次 30 秒+ 写作)
    return 信号(级别, 解释=f"{结果.类型}: {结果.理由}")

推演:假设这只票今天出了一条"控股股东拟减持不超过 2%"的公告。模型分类成"其他",第 3 步直接绿灯,用户看板上一点动静都没有——这就是我说的"主动漏报"。换成"公司收到证监会立案告知书",模型分到"重大监管处罚/立案调查",给分 0.9,理由写"因涉嫌信披违规被立案,基本面存在重大不确定性";第 4 步 0.9 ≥ 0.8 判红,看板标红,同时那句理由随信号带进详情卡 Writer 的 prompt,成为它写摘要时的输入。分类这一步只跑一次模型、零关键词规则;详情卡那段人话由 Writer 另起一次独立的大模型调用写出来(就是第 2 题里那次 30 秒+ 的异步写作)。

⚖️ 决策对比

维度我们的选择:单条规则 + 收紧 prompt 到 5 类替代方案:全量推送 / 拆 5 个独立规则文件
用户被打扰程度只推 5 类 × 分数过阈值,绝大多数公告静默全量推送等于把噪声原样转嫁给用户,通知一多就被关
每类不同阈值暂不支持(当前没这需求)天然支持每类一套阈值——但这是为不存在的需求买单
prompt 复用一份 prompt 列全 5 类,模型一次定类5 个规则各写一份分类 prompt,内容大量重复
规则间干扰单规则单出口,不会自己跟自己打架5 条规则可能对同一条公告同时触发,谁说了算要再仲裁
分类与文案的衔接分类只跑一次,理由字段喂进详情卡 Writer 的输入,口径对齐、无需二次分类(详情卡仍是 Writer 一次独立调用)分类和文案各成一套,容易为生成文案再单独跑一次分类,口径还可能漂
误报可控性单出口,调一处 prompt 就收紧全局误报要在 5 处分别排查,口径容易漂

公允裁决:拆 5 个独立规则确实有它的好——如果哪天产品要"财报用宽阈值、立案用严阈值",分文件是最干净的扩展点,这不是稻草人。但当前根本没有"每类不同阈值"的需求,提前拆等于为想象中的需求付出 5 份 prompt 维护成本和规则互相触发的仲裁成本。我选复用单规则:模型一次输出 {类型, 分数, 理由},理由还能直接喂进详情卡 Writer 的输入,链路对齐、误报可控(详情卡本身仍是 Writer 一次独立调用,这里省的是"为写文案再单独分类一次")。真到了需要分类差异化阈值那天,从单规则里裂出来也来得及。

📌 总结

  • 5 类是克制的产品决策:财报/预告/ST/重组/处罚,其余全归"其他"兜底,显式选择漏报减持回购,真痛了再加。
  • 分类用大模型不用关键词:公告标题写法太杂,正则永远在打补丁;fast 档模型 + 结构化 schema 强制吐 {类型, 分数, 理由}。

Q4

从原始市场数据到"该不该提醒用户"的判定链路怎么设计的?

★★★★☆
规则引擎判定链路信号聚合fail-loud阈值配置

🎯 考察点分析

这道题是想看你能不能把"一坨原始数据 → 一个该不该打扰用户的二元决定"这条链路拆成清楚的几段,而不是把检测逻辑糊成一个几百行的大函数。面试官真正关心的是三件事:你怎么把多个独立信号聚合成一个结论、阈值这种"会经常改的参数"放哪、以及当某个信号源挂了你往哪个方向兜底。最后一点是金融/监控类系统的命门——兜错方向会把真实风险静悄悄地黑洞掉。

  • 追问:5 条规则各报一个级别,你凭什么把它们合成一个?为什么不是投票、不是加权打分,而是取最严的那个?
  • 追问:某条规则报错了(比如拉数据超时),这只股票该判 GREEN 还是 RED?为什么这个方向的选择不是随便定的?
  • 追问:阈值(比如单日跌 10% 报警)写死在代码里有什么坏处?你说是"配置驱动",那和上一个重型规则引擎框架的区别在哪?
  • 追问:一千个用户持有同一只股票,你要跑一千遍检测吗?成本怎么省?

📚 原理讲解

整条链路我把它拆成四段,像一条从左到右的流水线。先讲这条链路在做什么,再讲三个关键的设计决定。

第一段:确定"扫谁"——从持仓表反推监控范围

监控对象不是一个单独维护的"客户名单",而是直接从持仓表里反推:谁的持仓数量大于 0,谁手里的哪只股,就成为一个"(用户,股票)对"。这一步叫 load_active_subjects。这么设计的好处是没有第二份名单要同步——用户清仓了,下一轮自然就不扫了,不会出现"人都不持有了系统还在提醒"的脏数据。

紧接着有个省钱的小动作:按股票代码去重。一千个人持有同一只茅台,行情和公告是一样的,大模型分析也是一样的,所以每只股只跑一次检测,算出级别后再"展开"回每个持有它的用户。这一刀直接把 API 调用和大模型成本从"按人头"降到"按股票"。

第二段:每只股跑 5 条规则——并发、各管一摊

很多人以为持仓监控就是看价格涨跌,其实远不止。我放了 5 条相互独立的规则:价格异动、公告分类、财务比率、现金流、股东人数。每条规则吃同一个监控对象,各自去拉自己需要的数据(价格规则拉日线、公告规则拉公告),各自产出一个结构化结果:{级别, 命中的值, 用的阈值, 一句人话解释}。5 条规则之间没有依赖,所以用 asyncio.gather 并发跑,谁慢不拖累谁。

关键决定一:聚合用"取最严级别",不是投票

5 条规则各报一个级别,怎么合成一个总结论?我把级别编码成数字——GREEN=0 / YELLOW=1 / RED=2——然后取最大值。直白说就是:任何一条规则报 RED,整只股就是 RED。为什么不投票?因为监控的本质是"宁可多打扰、不可漏报":股东人数暴跌但价格还没动,这恰恰是最该提前提醒的时刻,投票制会让这条孤独的红灯被 4 个绿灯淹没掉。取最严级别 = 让任何一个哨兵都有一票否决权。

关键决定二:阈值是配置,不是写死在代码里

"单日跌 10% 报红、跌 5% 报黄"这些数字,如果散在 5 个规则文件里,以后想统一调参就得满仓库找。我把所有阈值集中到一个配置字典(DEFAULT_THRESHOLDS),按规则名分组。规则代码读阈值时用 thresholds.get("键", 代码内默认值)——能集中改、又有兜底默认。这是"配置驱动"的轻量版:既享受了集中管理的好处,又没有引入一个完整规则引擎框架的重量(下面决策对比细讲)。

关键决定三:Fail-loud——报错往 RED 抬,绝不降成 GREEN

这是整道题的灵魂。某条规则跑崩了(拉数据超时、大模型返回乱码),我的处理是:把它判成 RED,并打出完整 traceback,而不是默默当它 GREEN 跳过。为什么?因为 GREEN 在这套系统里是"放行信号"——一个错误地放行的哨兵会把"数据源挂了"伪装成"扫描很干净",真实异动就被静悄悄黑洞掉了。这是项目的一条硬规则:禁止静默兜底。这个原则有层次:单条规则崩 → 抬成 RED(这只股还是会被提醒);某只股 5 条规则全崩 → 跳过它,等下一轮重扫;一整轮里所有股票全崩 → 直接抛错,拒绝把这一轮标成成功,因为那已经是系统性故障,标成功就是在撒谎。

第三段:分流落盘 + 顺手回写报价

聚合出级别后分两路:GREEN 的只记录不打扰;YELLOW/RED 的写一条 alert,再异步派一个任务去生成给用户看的详情卡(详情卡怎么写见本类第 3 题)。还有个一鱼两吃的细节:价格规则拉行情时顺手把当日最新报价回写到持仓表,让"算浮盈浮亏"和"做监控判定"共享同一份行情快照,不用各拉一遍。

💻 示例讲解

下面这段伪代码把"一只股跑 5 条规则 → 聚合 → fail-loud"这段核心讲清楚。注意 _safe 包裹里 except 分支的方向。

# 级别编码成数字,数字越大越严重
LEVEL = {"GREEN": 0, "YELLOW": 1, "RED": 2}

async def detect(stock, thresholds_per_rule):
    async def run_one(rule):
        try:
            # 每条规则只拿自己那一组阈值(按规则名取),get 不到就用代码内默认值
            my_thresholds = thresholds_per_rule.get(rule.name, {})
            return await rule.evaluate(stock, my_thresholds)
        except Exception as exc:
            # Fail-loud:规则崩了绝不降级成 GREEN(那会把故障伪装成"干净扫描")
            # 而是抬成 RED + 打 traceback,保证这只股仍然会触发提醒
            log.error("规则 %s 崩了", rule.name, exc_info=True)
            return Result(level="RED", explanation=f"规则报错,为可见性抬成 RED:{exc}")

    # 5 条规则互不依赖,一起并发跑,谁慢不拖累谁
    results = await gather(run_one(r) for r in RULES)

    # 聚合 = 取最严级别:任一条 RED,整只股就 RED(等价于一票否决)
    overall = max(results, key=lambda r: LEVEL[r.level]).level
    return overall, results

推演:假设某只股,价格规则报 GREEN(当日只跌了 3%,没过 5% 黄线),财务比率规则因为拉财报超时崩了。如果按"崩了当 GREEN"处理,这只股会被判 GREEN——干干净净不提醒,可财务到底有没有恶化没人知道。按 fail-loud,崩掉的那条被抬成 RED,max(0, 2)=2,整只股 RED,用户收到提醒、运维看到 traceback 去查为什么财报拉不到。再看正常命中:价格规则报 YELLOW(单日 -6%),其余全 GREEN,max(1,0,0,0,0)=1 → YELLOW,写 alert 但不算最高优先级。这就是"取最严"的两面:既不漏报真异动,也不漏报"我瞎了"这件事本身。

公允裁决:重型规则引擎不是稻草人——当规则有几十上百条、还互相依赖触发、业务方要不改代码自己配规则时,它的冲突消解、规则热加载、可视化编辑是实打实的价值,风控大厂用它有充分理由。但我这里只有 5 条彼此独立的规则、聚合策略就一句"取最严"、改规则的人就是我自己。引一个规则引擎,等于为了省一行 max 背上一套 DSL 的认知税和调试隔阂。另一头,纯硬编码确实最省事,但阈值散落 + 改参要全库搜是它的硬伤。我取的是中间那一档:逻辑用普通代码(保留可读和可调试),只把"会经常改的参数"抽成配置字典——拿到了集中调参的好处,没付框架的重量。等规则真的膨胀到几十条、业务方要自助配置那天,再升级到规则引擎也不迟,现在留好了规则类这个扩展点。

🖼️ 图解

📌 总结

  • 链路四段:持仓表筛数量>0 并按代码去重(省 API 和大模型成本)→ 每只股并发跑 5 条独立规则 → 取最严级别聚合 → GREEN 落盘、YELLOW/RED 写 alert 并异步生成详情卡。
  • 聚合 = 取最严:级别编码 GREEN=0/YELLOW=1/RED=2 取 max,任一规则 RED 整只股 RED——给每个哨兵一票否决权,宁多扰不漏报。
  • 阈值是配置不是写死:集中到一个字典按规则名分组,规则用 get(键, 默认) 读,既能集中调参又有兜底,且没背规则引擎框架的重量。
  • Fail-loud 分三层:单规则崩→抬 RED;某股全规则崩→跳过待重扫;一轮全股崩→抛错拒绝标成功。绝不让 GREEN 哨兵把故障伪装成干净扫描。
  • 一鱼两吃:价格规则的行情快照顺手回写持仓最新报价,浮盈计算与监控判定共享同一份数据。

一句话速记:5 条独立规则并发跑,取最严级别定红黄绿,阈值进配置字典、报错往 RED 抬——拒绝让任何故障静悄悄变成"一切正常"。
